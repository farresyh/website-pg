# Foundation Security & Financial-Integrity Checklist

**How to use this file:** before implementing (or reviewing) any feature that touches authentication, money, pricing, supplier calls, or customer PII, check it against every rule below that applies. This is the concentrated, actionable form of the security posture defined across [`prd.md`](./prd.md) (§9 Non-Functional Requirements) and [`adr.md`](./adr.md) (why each rule exists). If a change to this file is needed, it should come from a deliberate decision — see `adr.md` for the pattern (add a new entry, don't silently rewrite history).

---

## 1. Authentication & Access

- [x] Admin accounts can require MFA (TOTP), with step-up on the dangerous actions (AUTH-7, ADR-121, live 2026-10-14 via #437; ADR-124's three customer-login actions released via #514). Opt-in per account (`admin_users.mfa_enabled` / `mfa_required`); login goes through `/login/mfa` when it is on, and turning it off is SSH-only. MFA for affiliate/reseller accounts was dropped (ADR-019 2026-10-14 addendum).
- [x] Every backend endpoint enforces role-based access control server-side. Frontend route guards are convenience only, never the actual gate. — Admin and Middleware routes sit behind `admin.role:...` groups (`App\Http\Middleware\EnsureAdminRole`, checked against `$request->user()`, also enforces `is_active`), with `/middleware/*` and `/blacklist` `super_admin`-only per §3's policy (fixed 2026-08-14). Partner-portal and Reseller API routes have their own auth (Sanctum per account type; API key + IP allowlist for `/v1`, ADR-074). Routes outside any auth group are public by design: guest checkout, catalog, track-order, voucher preview, health, and the webhooks (`/webhooks/chip`, `/webhooks/digiflazz`, OpenWA), each authenticated by its own signature or HMAC. **When adding a route, check it lands in the right group** — re-check `routes/api.php` rather than trusting a list here (an enumerated list in this line went stale twice).
- [x] Withdrawals above a configured threshold require a **second, different** Super Admin's approval (maker-checker) — the requester can never be the sole approver. (WTH-5) — verified 2026-07-30: `WithdrawalController::approve()` row-locks the `Withdrawal` (`lockForUpdate()`), and at/above `config('withdrawals.maker_checker_threshold_sen')` rejects both a non-Super-Admin approver and the original requester approving their own request.
- [x] Vouchers above a configured threshold can only be created by a Super Admin — a **single-step role gate**, not the same two-person check as WTH-5. Deliberate deviation, decided 2026-07-24: voucher issuance is a store-credit obligation (never cash-out, per ADR-004), judged lower-stakes than an actual withdrawal, so the extra friction of a separate approver wasn't required. If this changes, update this line and `prd.md`'s VCH-6 row together — don't let them drift apart again. (VCH-6) — verified 2026-07-30: `VoucherController::store()` rejects a non-`super_admin` role at/above `config('vouchers.maker_checker_threshold_sen')`, no second-approver step.
- [x] Merging two or more vouchers into one new code has **no maker-checker gate at all** — any admin (`super_admin`/`admin`) can trigger it, deliberately. Not an oversight: a merge creates zero new ledger liability (the combined amount was already booked via each source's own original issuance), a materially different risk profile from *issuing* a genuinely new voucher (VCH-6, above) — so the mandatory `reason` field is the audit control, not a second approver. (ADR-036) — verified 2026-08-26: `VoucherController::merge()` sits behind the same `admin.role:super_admin,admin` group as every other voucher route, no threshold check anywhere in `VoucherService::merge()`.
- [x] Affiliate impersonation sessions are fully audit-logged: real admin identity, session start/end, visible "impersonating" banner, every action tagged. (RES-4) — built (see `prd.md` RES-4): `AffiliateImpersonationController` mints a short-lived `impersonate`-scoped token, audited in `affiliate_impersonation_sessions`; the banner is `reseller/src/components/ImpersonationBanner.tsx`. Impersonating a wallet **Reseller** (ADR-072) is not built.
- [ ] Reseller Bot channel (ADR-075): a compromised or shared WhatsApp group could place unauthorized orders against a real `Reseller` (wallet) balance — group membership, not individual sender, is the deliberate v1 trust boundary (ADR-075 decision 3), so anyone the reseller has added to their own group can spend it. Accepted risk, not a gap: the reseller controls their own group's membership, and a per-sender allow-list inside a group is a named, explicit revisit trigger (ADR-075's own consequence-to-track) if abuse or an unauthorized-order dispute is ever actually observed — not built speculatively ahead of that.
- [ ] Reseller Portal (ADR-072/073, PR-G): a `Reseller` (wallet) portal account can self-issue its own `reseller_api_keys` (capped at 5 active) — a compromised portal login (or an insider on the reseller's own side) can mint a fresh spending credential without admin involvement. Accepted risk, not a gap: the account itself is admin-vetted at registration (no self-serve signup, decision 1 of the PR-G planning addendum), the cap bounds sprawl, and every issued key is independently revocable by admin at any time from `/admin/resellers` regardless of who issued it.
- [x] Every login has a real expiry and re-auth story. — Admin (ADR-121, 2026-10-14): a Sanctum cookie session with CSRF, no token; it ends after 2 days unused (`config/session.php` `lifetime`) and 7 days at most (`EnsureAdminSessionFresh::MAX_AGE_SECONDS`), and the admin client redirects to `/login` on a `401`. Partner portal and impersonation: Sanctum tokens with `SANCTUM_TOKEN_EXPIRATION_MINUTES` (default 720, a 12h window off each token's `created_at`; first set 2026-08-14 when the admin still used tokens).
- [x] Failed logins are limited per account, not only per IP. — `App\Support\AccountLoginThrottle` (ADR-019 2026-09-29 addendum) locks an email for 15 minutes after 10 failures from any mix of IPs, on admin login, the MFA code, MFA step-up and the affiliate/reseller login, on top of each route's 5/min per-IP throttle. Tests: `AuthControllerTest` / `AffiliateAuthControllerTest::test_login_locks_an_account_after_10_failures_from_any_ips`.
- [x] Security headers. — The API adds HSTS over HTTPS (no `includeSubDomains`), `Referrer-Policy` and `Permissions-Policy` (`App\Http\Middleware\SecurityHeaders`, PRD §16 item 110); Forge's nginx adds `X-Frame-Options` and `nosniff`. Admin, storefront and portal send a CSP, `nosniff`, `Referrer-Policy` and `Permissions-Policy` from `next.config.ts`, no `x-powered-by`, and HSTS from Vercel.

## 2. Money & Pricing

- [x] Price, fee, profit, and cost are always computed **server-side** at transaction time from stored config. No endpoint accepts a client-submitted monetary value as authoritative. (ORD-9) — verified 2026-07-30: `CreateCheckoutRequest`'s rules contain no price/amount/cost field at all; `CheckoutService`/`PricingService`/`CheckoutTotalService` compute everything from the stored `Package`/`Reseller`/`PaymentMethod` rows.
- [x] A storefront's pricing terms (wholesale tier and brand markup) come from `Affiliate::storefrontPriceTerms()` alone, so no code path prices from `markup_pct` directly; an owned brand has no tier and no brand markup (ADR-061 2026-10-30 addendum), which a test proves across checkout, preview, the catalog and voucher preview.
- [x] Balance for any owner (platform, affiliate, or reseller wallet) is derived from `SUM(LedgerEntry)` — never read from or written to a mutable `balance` column. (D2 / ADR-002) — verified 2026-07-30: `LedgerAccount` (`app/Models/LedgerAccount.php`) has no balance column by design ("pure lock/mutex anchor"); `LedgerService::balance()` is `LedgerEntry::query()->...->sum('amount')`.
- [x] Every money-moving action (order profit credit, withdrawal debit, an admin-issued voucher) writes an immutable `LedgerEntry` row. Ledger rows are never updated or deleted, only inserted. A compensation voucher writes none: it is the customer's own cash already held (ADR-024 2026-10-12 addendum, live 2026-10-13; the 4 old debits got appended reversals, not edits). — verified 2026-07-30: `LedgerService` is the only class constructed by `WithdrawalController`, `VoucherController`, and `OrderFulfillmentService`; `LedgerEntry` (`const UPDATED_AT = null`) carries an explicit "never call ->update()/->delete()" doc comment and no code does.
- [x] No refund goes through the payment gateway and no cash-refund action exists in the system (D4 / ADR-004). A failed order is resolved by retry-delivery or store credit only: a compensation voucher, restoring the checkout voucher it paid with, or — for a reseller wallet order — a refund to the reseller's own wallet (ADR-073, an internal ledger credit, never cash out). A partially delivered combo is settled the same way for its undelivered share (ADR-094). Verified 2026-07-30; resolution list re-checked 2026-10-09. The one cash that leaves for a customer-side balance is a closed reseller's unused Purchase Balance (ADR-131): the admin sends a bank transfer outside the system first, then records it; the system only writes the debit.
- [x] Voucher redemption decrements `remaining` via an atomic, row-locked operation — verify this cannot allow two concurrent redemptions to both succeed against an insufficient remaining balance. (VCH-5) — verified 2026-07-30: `VoucherService::redeem()` wraps a `lockForUpdate()`-locked `Voucher` fetch in `DB::transaction()`, backed by `tests/Concurrency/VoucherRedeemConcurrencyTest.php` (a real second-process test, not just a unit assertion).
- [x] A supplier-sourced price is sanity-checked before it's ever written to a live `Package.cost_price` — a zero/negative value is never applied, and a swing past a configured threshold is held for admin review rather than applied silently. (ADR-025) — shipped 2026-08-21: `PackagePriceSyncService::evaluatePriceChange()` floor-rejects `price_sen <= 0` unconditionally (both the sync path and `SupplierProductController::promote()`); a swing past `PRICE_SWING_THRESHOLD_PERCENT` (default 50%) blocks the write and queues a `PendingPriceChange` row instead, deactivating the package under `deactivated_reason='price_anomaly'` until an admin Approves or Dismisses it.

## 3. Idempotency & Reconciliation

- [x] Every order generates a unique `reference_number` **before** the first supplier API call. Any retry of that same logical order reuses the same reference — it is never regenerated. (ORD-8) — verified 2026-07-30: `OrderFulfillmentService::fulfill()` calls `ReferenceNumberService::resolve($locked->reference_number)` (returns the existing value unchanged, generates only when none exists) before the `SupplierAdapter::createOrder()` call, inside the same row-locked transaction.
- [x] Payment webhook/callback handling is idempotent: receiving the same event twice must not create a duplicate order or duplicate credit delivery. (PAY-2) — `ChipWebhookController` verifies the signature, then hands the outcome to `OrderPaymentOutcomeService`, which applies it under the Order row lock and treats an already-Paid order as a no-op (item 63, 2026-10-04); `OrderFulfillmentService::fulfill()`'s own row lock is the second, structural layer. Re-checked against code 2026-10-08.
- [x] (PAY-3, payment-side) / [x] (ORD-10, delivery-side) — both shipped. **PAY-3** — `app:reconcile-pending-payments` (every 15 min) polls CHIP via `PaymentGateway::getPayment()` for any order stuck at `payment_status=pending` and applies the result through the same `OrderPaymentOutcomeService` seam the webhook uses, so the webhook is never the sole path to a final payment state ([ADR-021](./adr/ADR-021-next-session-priority-re-sequencing.md), ADR-110). **ORD-10** — `app:reconcile-pending-deliveries` (same cadence) covers ambiguous supplier outcomes: a genuinely unknown Digiflazz result stays Pending and is re-polled with the same reference; anything else ambiguous goes to `DeliveryStatus::NeedsReview` for an admin ([ADR-026](./adr/ADR-026-delivery-side-reconciliation-ord-10.md), ADR-102). A NeedsReview order never offers "Issue Voucher" directly (double-compensation risk).
- [x] Admin-issued standalone vouchers (Path A) are idempotent against a double-click or a network-retry — a repeated submission must return the same `Voucher`, never mint a second one and double-debit the platform ledger. (ADR-035) — shipped 2026-08-26: `vouchers.idempotency_key` (nullable, unique — Path B's `order_id`-keyed uniqueness, pre-existing, is unaffected), same two-layer shape as ORD-8/PAY-2 above — `VoucherController::store()` does a fast-path lookup first, then a DB unique-constraint catch-and-replay as the real guarantee against a genuine race. Client-generated once per `CreateVoucherModal.tsx` open (`OrderForm.tsx`'s own precedent), never regenerated across a resubmit of that same attempt.

## 4. Fraud Prevention

- [x] Every order creation checks the customer/player against the internal blacklist before payment or supplier submission proceeds. (FRAUD-1, FRAUD-2 — `BlacklistService`/`CheckoutController::assertNotBlacklisted()`, 2026-07-29)
- [x] The checkout/payment endpoint has its own, stricter rate limiting / velocity check distinct from general API rate limiting, to reduce card-testing (carding) abuse. (FRAUD-4 — `CheckoutVelocityGuard`, counts only blacklist-triggered rejections per IP, distinct from `throttle:10,1`)
- [x] The public Game ID Checker (`POST /api/player-check/{slug}`, ADR-123) can't be used as a free proxy to the player-ID provider checkout depends on: per-IP `throttle:player-check` (5/min + 30/hour), Cloudflare Turnstile verified server-side and **fail-closed** without `TURNSTILE_SECRET_KEY`, the ID format checked before any provider call, a 10-minute result cache, a 2-minute cooldown after a provider failure, and a 200/hour global provider budget (daily admin email when spent). It calls RedxGame only, plus UniPlay as MLBB's fallback (ADR-123 2026-10-28 addendum); never a supplier (MooGold, which was one, is no longer a validator), answers in our wording only (no provider name, raw country or provider text), and writes `public_player_checks`, which no checkout or resend approval reads. Verified on prod 2026-10-16.
- [x] The public payment check (`POST /api/track-order/{orderNumber}/check-payment`, ADR-110 2026-10-29 addendum) can't be used to hammer CHIP or to move an order the gateway has not decided: per-IP `throttle:10,1,check-payment` plus a 10-second per-order cache lock (one CHIP call per window), Pending orders with a `payment_ref` only, scoped to the storefront brand like `GET /api/track-order/{orderNumber}`, and it applies only what CHIP's own answer says (a failure only when `failure_is_final`), never anything the client sends. It returns the same masked payload as the GET.
- [x] The public reseller application (`/api/onboarding/*`, ADR-133) can't be used to spam emails or upload arbitrary files: stage 1 is refused while the admin's "Public applications open" switch is off, then needs a server-verified Turnstile token (fails closed) and its own per-IP limiter (3/min + 10/hour); the rest share 60/min per IP. Stage 2 is reached only through a 64-character single-use token stored as a SHA-256 hash, sent to the confirmed email, valid 14 days and revoked on regenerate or submit. Uploads are PDF, JPG or PNG up to 10 MB, the type read from the file's content (Laravel `mimes`), and only the kinds the applicant type needs. An email that is any portal login is refused. (`PartnerApplicationController`, `PartnerApplicationService`, 2026-11-01)
- [x] Blacklist entries always require a recorded reason and are attributable to the admin who added them. (FRAUD-3 — `blacklist_entries.reason`/`created_by`, `/admin/blacklist`)
- [x] Reseller Purchase Balance additions are limited (ADR-131, CHIP's activation condition 3): RM10,000 per top-up and a RM100,000 default balance cap, both settings (`/admin/settings`, step-up), with a per-reseller cap override (step-up). One check, `ResellerWalletService::assertWithinLimits()`, serves the self-serve CHIP top-up (portal and WhatsApp bot) and the admin manual credit, and takes the reseller's `ledger_accounts` mutex first because `LedgerService::credit()` takes no lock (`ResellerWalletTopupConcurrencyTest`: two simultaneous credits that fit singly but not together, one passes, and the test fails without the lock). A payment already received (`completeTopup`) and an order refund are never refused, so a balance can exceed its cap by at most one in-flight payment plus refunds. Verified 2026-10-29.
- [x] A reseller account is closed only by one admin action (ADR-131 decisions 12-16, `ResellerClosureService`, super_admin + step-up). It refuses while a wallet order is unfinished or a failed one is not yet refunded, or any Add Balance payment is pending (whatever its expiry); locks the wallet mutex and the reseller row; debits the whole balance (`wallet_closure_refund`) only after the admin records the transfer date (this month, accounting month open) and the bank reference; revokes API keys, portal logins and tokens, unlinks WhatsApp groups and disables the webhook in the same transaction. `OrderSettlementService::settle()` refuses a closed reseller's wallet; a paid payment that still arrives is credited and logged critical. Proved by `ResellerClosureConcurrencyTest` (two real processes: an order racing a closure, and two closures; both fail with the locks removed) and a `FinancialScenario` step (the cash-equation gap is unchanged). Verified 2026-10-29.
- [x] A branded (affiliate) domain takes no CHIP payment until an admin approves it (ADR-131 decisions 19-21, CHIP's condition 5: no branded store uses its payment services without CHIP's prior written approval). `affiliate_domains.payments_approved_at` (+ `_by`); one check, `StorefrontBrand::assertPaymentsEnabled()`, fed by `ResolveStorefrontBrand` from the domain row it already loads (a spoofed `X-Storefront-Host` cannot grant approval: it is read from the matched row), at the top of `CheckoutService::initiate()` (before the Order exists; skipped when a voucher covers it all), the no-link branch of `resume()`, and `MembershipSubscriptionService::initiate()`. Browsing is unaffected. The primary host and every non-storefront caller (console, queue, API, bot) carry no hostname and are never gated; the migration approved the primary affiliate's own rows only (an `is_owned` brand's stay unapproved). Approve and revoke: `PUT /affiliates/{id}/domains/{id}/payments-approval`, super_admin + step-up, stored with the admin. A purchase link made while approved stays payable until CHIP's own expiry (about 30 minutes). Proved by `AffiliateDomainPaymentGateTest` (removing the three calls fails exactly the three gate tests). Verified 2026-10-29. A `www` redirect twin (ADR-060's second 2026-10-30 addendum) never resolves a brand (`AffiliateDomain::servable()`), is never payment-approved (the approval route returns 422) and is never canonical or a CORS origin, so a request carrying a twin's host in `X-Storefront-Host` gets a 404, not a bypass.

## 5. Payment Gateway Integrity (CHIP)

CHIP is the sole payment gateway since ADR-022's 2026-09-01 addendum; Xendit and its webhook route were removed. Re-checked against code 2026-10-08.

- [x] `/api/webhooks/chip` has its own named rate limit (`throttle:600,1,webhook-chip`), so a flood can't share a counter with other routes (the per-route prefix exists since ADR-019's 2026-08-27 addendum; the limit was raised for promo bursts).
- [x] Every CHIP webhook is cryptographically verified before it is trusted: an RSA PKCS#1 v1.5 signature (`X-Signature`) checked against the account public key, cached with a rate-limited refetch (PAY-1, [ADR-022](./adr/ADR-022-multi-gateway-payment-strategy.md) 2026-09-02 addendum). An invalid signature returns `401` before any Order is touched (`ChipWebhookControllerTest::test_rejects_a_webhook_with_an_invalid_signature`, `ChipGatewayTest` signature cases). Verified live with real money on 2026-09-03.
- [x] The platform never touches raw card data. Payment happens on CHIP's hosted page, which keeps the platform out of PCI-DSS scope (PAY-4).
- [x] No gateway sub-account splitting: xenPlatform was dropped entirely (ADR-059 decision 6), not deferred.

## 6. Supplier Integration

- [x] No business logic reads a raw supplier response directly — every supplier is accessed only through its Adapter, which normalizes to one canonical internal shape. (ADAPT-1, ADAPT-2) — `GamevionAdapter` and `DigiflazzAdapter` are the only classes making `Http::` calls to a supplier; `OrderFulfillmentService`/`CheckoutController` depend only on the `SupplierAdapter` interface (re-checked 2026-10-08).
- [x] Never assume a supplier's auth scheme, response envelope, or validation-endpoint availability is uniform with any other supplier. Confirm per-supplier, per-game during onboarding. (D6 / ADR-006) — each adapter's doc comments record its own confirmed quirks (Gamevion: dual Bearer+X-API-KEY auth, `telp` rejects a leading `+`; Digiflazz: signed requests, async webhook with an `X-Hub-Signature` HMAC, rc-code classification per ADR-102).
- [x] ~~Validation-capability (`supports_validation`) is tracked per game-supplier mapping, not as a blanket flag on the Supplier record.~~ (GAME-12) — **dead requirement, dropped 2026-09-13** (`docs/prd.md` §16): neither Gamevion nor Digiflazz exposes player-validation via its own API — both `validatePlayer()` unconditionally throw `ValidationNotSupportedException` — and no code path anywhere ever reads the flag. The JSON field remains in `games.supplier_mappings` (harmless, unread). Real player-ID validation runs through the unrelated `Game.player_validator_enabled`/`player_validator_profile_id` (`PlayerValidatorRegistry`, ADR-093).
- [x] A circuit breaker trips per-supplier after repeated failures — a down supplier must not be able to cascade into blocking the whole delivery queue. (`App\Services\CircuitBreaker\CircuitBreaker` + `CircuitBreakingSupplierAdapter`, 2026-07-29 — see ADR-019's newest addendum)
- [x] If a supplier requires IP whitelisting, its Adapter routes through the one shared outbound proxy config (`config/services.php['proxy']`), never a supplier-specific, one-off proxy setup. (ADR-006 addendum) — verified 2026-07-30: `GamevionAdapter`'s optional `proxyUrl` constructor argument reads from that shared config key, not a Gamevion-specific one.
- [x] "Supplier item is active again" is confirmed by a sync run that happened *after* the package was taken offline — never by a stale `status_raw` value left over from before the deactivation. — fixed 2026-08-21 (real bug found live-verifying ADR-025, confirmed structural via a short-gap repro, not a long-sync-gap artifact — `docs/build-log-archive.md`, 2026-08-21): `PendingReactivationFinder::find()` now requires `SupplierProduct.last_synced_at` to be after the package's own `deactivated_at`. Regression tests: `tests/Feature/Services/Sync/PendingReactivationFinderTest.php` (both the bug repro and a control case for genuine reactivation).

## 7. Secrets & Data

- [x] Reseller KYC documents are never public: a private disk (`KYC_DISK=r2_kyc`, the `pekangame-kyc` bucket with its own token), never a public URL or a storage path in any response. A super_admin opens a file only through a signed link valid for 5 minutes that re-checks the admin is still an active super_admin, serves it inline with `nosniff` and `no-store`, and records who opened it and when (`partner_document_views`). Deleting applicant data needs step-up; the daily `app:prune-partner-applications` deletes declined applications 90 days after the decision, approved ones 90 days after the account closes, and unconfirmed ones after 7 days. (ADR-133, 2026-11-01)
- [x] Supplier credentials (`api_config`) and payment gateway secrets are encrypted at rest, never returned in full via any API response, and never shown unmasked in Developer Tools. (SUPP-5, DEV-2) — `Supplier.api_config` uses the `encrypted:array` cast and is `$hidden`; CHIP credentials are DB-first and encrypted (ADR-110). Developer Tools (`/middleware/developer-tools`) now exists and passes both the request preview and the response through `SupplierRequestPayloadRedactor` before returning them (`DeveloperToolController::redact()`). Checked in code 2026-10-08, not yet by a live click-through.
- [x] Request logs redact credentials and excess PII before being written. (MID-10) — shipped 2026-08-28: [ADR-051](./adr/ADR-051-middleware-request-logs-mid-10-11-mui-9.md) — `App\Services\Supplier\RequestLog\SupplierRequestPayloadRedactor` strips `Authorization`/`X-API-KEY` headers case-insensitively plus every body key `SupplierConfigSchema` marks `secret` for that supplier, *before* the row ever reaches the queue (`LogSupplierRequestJob`) or the database — redact-then-queue-then-write, never inline-then-redact. `validatePlayer` rows (the PII-carrying call type) additionally follow `player_validations`' existing 7-day retention window rather than the blanket 30-day default. Verified live: a real `Refresh Balance` call's `Authorization`/`X-API-KEY` confirmed redacted in `/middleware/request-logs`' detail modal.
- [x] Player/customer PII returned from validation calls (e.g. in-game nickname, country) is retained only as long as operationally needed — not logged or stored beyond what's needed to confirm the order to the customer. — closed 2026-07-30 (later same day): `App\Console\Commands\PlayerValidation\PrunePlayerValidationsCommand` (`app:prune-player-validations`), scheduled daily, deletes `player_validations` rows where `validated_at` is older than `config('services.player_validation.retention_days')` (7 days, grilled in [ADR-021](./adr/ADR-021-next-session-priority-re-sequencing.md)).
- [x] A customer's game-account login (Login Top-up / Joki) is held only while the order needs it. (ADR-124, released via #514, item 112) — its own `order_credentials` table with the secret fields encrypted (APP_KEY), no relation from `Order` (so no order `toArray()` can carry it), left out of every DB dump; a 15-minute critical sweep wipes it 24 h after the order closes, 24 h after creation if unpaid, or 14 days after it was last saved (all set in Settings → Customer Login Policy); only a super_admin can reveal or replace a secret field, behind step-up, rate-limited, each one a `credential_reveals` row. Since item 113 PR 1b (released via #514) checkout writes it with the order in one transaction, a password is never trimmed or put in the idempotency hash, and the login identifier is masked on every customer and affiliate surface, keyed on the order's own credential row (ADR-125 decisions 31, 38-41). Since item 113 PR 2a (released via #514) the only other reader is the supplier's short link `/s/<token>`: only the token's SHA-256 is stored, it opens only while that attempt is Pending on that supplier, GET never carries a secret (`no-store`, `no-referrer`, `noindex`), each POST reveal is a `credential_reveals` row with actor supplier, rate-limited per link and per IP, and the link is never stored in a message (ADR-125 decisions 50-52, ADR-124 2026-10-19 addendum).
- [x] No raw credentials are ever written to logs, error messages, or client-visible responses. — spot-checked 2026-07-30, not exhaustively grepped: `AuthController::login()`'s failure/success log lines carry `email`/`admin_id`/`ip`, never the attempted password; `CheckoutController`'s failure logs carry order/customer context, no gateway/supplier secrets. Held up everywhere checked, but this is a spot check of the highest-risk paths (auth, checkout), not a full audit of every `Log::` call in the codebase.
- [x] The guest order-status view (`GET /api/track-order/{orderNumber}` + the `OrderStatusUpdated` broadcast) returns the buyer's own contact **masked**, never raw. — [ADR-065](./adr/ADR-065-guest-order-status-detail.md), 2026-09-01: `App\Support\ContactMask` (`name`/`email`/`phone`) is applied only in `TrackOrderController::customerSafePayload()` (the one shape both producers share), never on the `Order` model — so admin/checkout/fulfilment/notification/ledger paths keep the raw values. The response also carries the customer-facing payment breakdown (`payment_method`/`selling_price`/`voucher_discount`/`transaction_fee`, all money shown at checkout) but still never `standard_selling_price`, profit, supplier fields, or `payment_ref`. Rate limit unchanged (`throttle:20,1,track-order`); the `order_number` ULID (~80 bits) stays the ownership proof. Verified live + by `TrackOrderControllerTest` (masked shape, raw-value leak guard, broadcast==endpoint parity).
- [x] Full-database backup archives are encrypted at rest and exclude PII past its own retention policy.
