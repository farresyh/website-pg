# Foundation Security & Financial-Integrity Checklist

**How to use this file:** before implementing (or reviewing) any feature that touches authentication, money, pricing, supplier calls, or customer PII, check it against every rule below that applies. This is the concentrated, actionable form of the security posture defined across [`prd.md`](./prd.md) (§9 Non-Functional Requirements) and [`adr.md`](./adr.md) (why each rule exists). If a change to this file is needed, it should come from a deliberate decision — see `adr.md` for the pattern (add a new entry, don't silently rewrite history).

---

## 1. Authentication & Access

- [ ] Super Admin and Admin accounts require MFA (TOTP) — enforced before any withdrawal/voucher/refund-affecting action. (AUTH-7) — explicitly descoped 2026-07-27 (founder call, see ADR-019's newest addendum), not a silent gap: `admin_users.mfa_secret`/`mfa_enabled` columns exist but `AuthController::login()` never checks them. Needs a real TOTP enrollment+verify feature, not a one-line patch.
- [x] Every backend endpoint enforces role-based access control server-side. Frontend route guards are convenience only, never the actual gate. — verified 2026-07-30: every mutating Admin/Middleware route in `routes/api.php` sits behind an `admin.role:...` middleware group (`App\Http\Middleware\EnsureAdminRole`, checked directly against `$request->user()` — not just route-tagged), which also enforces `is_active` server-side. Only genuinely public routes (`/login`, `/health`, `/checkout`, `/catalog/*`, `/vouchers/preview`, `/track-order/{orderNumber}`, `/games/{game}/validate-player`, `/webhooks/chip`) sit outside it, each by deliberate guest-checkout/webhook design (ADR-011), not oversight — this list corrected 2026-08-14 (and `/webhooks/xendit` dropped from it 2026-09-02 — the route no longer exists, ADR-022's 2026-09-01 addendum) to match `routes/api.php` as it actually stands (`/health`, `/vouchers/preview`, `/webhooks/chip` had all been added since this line was last written and were never backfilled in). **Correction, 2026-08-14:** the 2026-07-30 check confirmed a gate *existed* on every route but didn't verify the gate matched §3's *per-role* policy — a fresh audit found `/middleware/*` and `/blacklist` allowed the plain `admin` role in, not just `super_admin` as §3 requires ("Admin ... Cannot modify system settings, supplier credentials, or blacklist rules"). Fixed same session (`docs/prd.md` §14's 2026-08-14 entry) — all 6 route groups now `admin.role:super_admin`, with a real client-side redirect guard added to `admin/src/app/middleware/layout.tsx`. Re-verified: this line's claim is now actually true against §3, not just "a gate exists."
- [x] Withdrawals above a configured threshold require a **second, different** Super Admin's approval (maker-checker) — the requester can never be the sole approver. (WTH-5) — verified 2026-07-30: `WithdrawalController::approve()` row-locks the `Withdrawal` (`lockForUpdate()`), and at/above `config('withdrawals.maker_checker_threshold_sen')` rejects both a non-Super-Admin approver and the original requester approving their own request.
- [x] Vouchers above a configured threshold can only be created by a Super Admin — a **single-step role gate**, not the same two-person check as WTH-5. Deliberate deviation, decided 2026-07-24: voucher issuance is a store-credit obligation (never cash-out, per ADR-004), judged lower-stakes than an actual withdrawal, so the extra friction of a separate approver wasn't required. If this changes, update this line and `prd.md`'s VCH-6 row together — don't let them drift apart again. (VCH-6) — verified 2026-07-30: `VoucherController::store()` rejects a non-`super_admin` role at/above `config('vouchers.maker_checker_threshold_sen')`, no second-approver step.
- [x] Merging two or more vouchers into one new code has **no maker-checker gate at all** — any admin (`super_admin`/`admin`) can trigger it, deliberately. Not an oversight: a merge creates zero new ledger liability (the combined amount was already booked via each source's own original issuance), a materially different risk profile from *issuing* a genuinely new voucher (VCH-6, above) — so the mandatory `reason` field is the audit control, not a second approver. (ADR-036) — verified 2026-08-26: `VoucherController::merge()` sits behind the same `admin.role:super_admin,admin` group as every other voucher route, no threshold check anywhere in `VoucherService::merge()`.
- [ ] Reseller impersonation sessions (Phase 2) are fully audit-logged: real admin identity, session start/end, visible "impersonating" banner, every action tagged. (RES-4) — confirmed not built: no `Reseller` impersonation code exists anywhere; correctly still Phase 2, not a gap in the current MVP.
- [ ] Reseller Bot channel (ADR-075): a compromised or shared WhatsApp group could place unauthorized orders against a real `Reseller` (wallet) balance — group membership, not individual sender, is the deliberate v1 trust boundary (ADR-075 decision 3), so anyone the reseller has added to their own group can spend it. Accepted risk, not a gap: the reseller controls their own group's membership, and a per-sender allow-list inside a group is a named, explicit revisit trigger (ADR-075's own consequence-to-track) if abuse or an unauthorized-order dispute is ever actually observed — not built speculatively ahead of that.
- [ ] Reseller Portal (ADR-072/073, PR-G): a `Reseller` (wallet) portal account can self-issue its own `reseller_api_keys` (capped at 5 active) — a compromised portal login (or an insider on the reseller's own side) can mint a fresh spending credential without admin involvement. Accepted risk, not a gap: the account itself is admin-vetted at registration (no self-serve signup, decision 1 of the PR-G planning addendum), the cap bounds sprawl, and every issued key is independently revocable by admin at any time from `/admin/resellers` regardless of who issued it.
- [x] Admin Sanctum tokens have a real expiration and re-auth story, not `null` forever. — fixed 2026-08-14 (same session as the gap was found): `config/sanctum.php`'s `expiration` is now `env('SANCTUM_TOKEN_EXPIRATION_MINUTES', 720)` (12h rolling window off each token's `created_at`, Sanctum's own enforcement mechanism — no `expires_at` column write needed at issuance). `admin/src/lib/api-client.ts`'s `apiFetch`/`apiUpload` now clear the client session and redirect to `/login` on any `401`, so an expired token degrades to a clean re-login instead of every page growing its own error-banner handling. Regression test: `AuthControllerTest::test_token_older_than_the_configured_expiration_is_rejected`.

## 2. Money & Pricing

- [x] Price, fee, profit, and cost are always computed **server-side** at transaction time from stored config. No endpoint accepts a client-submitted monetary value as authoritative. (ORD-9) — verified 2026-07-30: `CreateCheckoutRequest`'s rules contain no price/amount/cost field at all; `CheckoutService`/`PricingService`/`CheckoutTotalService` compute everything from the stored `Package`/`Reseller`/`PaymentMethod` rows.
- [x] Balance for any owner (platform, or reseller in Phase 2) is derived from `SUM(LedgerEntry)` — never read from or written to a mutable `balance` column. (D2 / ADR-002) — verified 2026-07-30: `LedgerAccount` (`app/Models/LedgerAccount.php`) has no balance column by design ("pure lock/mutex anchor"); `LedgerService::balance()` is `LedgerEntry::query()->...->sum('amount')`.
- [x] Every money-moving action (order profit credit, withdrawal debit, voucher issuance) writes an immutable `LedgerEntry` row. Ledger rows are never updated or deleted, only inserted. — verified 2026-07-30: `LedgerService` is the only class constructed by `WithdrawalController`, `VoucherController`, and `OrderFulfillmentService`; `LedgerEntry` (`const UPDATED_AT = null`) carries an explicit "never call ->update()/->delete()" doc comment and no code does.
- [x] No cash-refund code path exists anywhere in the system. The only two resolutions for a failed order are retry-delivery or voucher issuance. (D4 / ADR-004) — verified 2026-07-30: no refund/reversal code exists; the only "refund" reference in `app/` is `VoucherController`'s own doc comment describing the store-credit path.
- [x] Voucher redemption decrements `remaining` via an atomic, row-locked operation — verify this cannot allow two concurrent redemptions to both succeed against an insufficient remaining balance. (VCH-5) — verified 2026-07-30: `VoucherService::redeem()` wraps a `lockForUpdate()`-locked `Voucher` fetch in `DB::transaction()`, backed by `tests/Concurrency/VoucherRedeemConcurrencyTest.php` (a real second-process test, not just a unit assertion).
- [x] A supplier-sourced price is sanity-checked before it's ever written to a live `Package.cost_price` — a zero/negative value is never applied, and a swing past a configured threshold is held for admin review rather than applied silently. (ADR-025) — shipped 2026-08-21: `PackagePriceSyncService::evaluatePriceChange()` floor-rejects `price_sen <= 0` unconditionally (both the sync path and `SupplierProductController::promote()`); a swing past `PRICE_SWING_THRESHOLD_PERCENT` (default 50%) blocks the write and queues a `PendingPriceChange` row instead, deactivating the package under `deactivated_reason='price_anomaly'` until an admin Approves or Dismisses it.

## 3. Idempotency & Reconciliation

- [x] Every order generates a unique `reference_number` **before** the first supplier API call. Any retry of that same logical order reuses the same reference — it is never regenerated. (ORD-8) — verified 2026-07-30: `OrderFulfillmentService::fulfill()` calls `ReferenceNumberService::resolve($locked->reference_number)` (returns the existing value unchanged, generates only when none exists) before the `SupplierAdapter::createOrder()` call, inside the same row-locked transaction.
- [x] Payment webhook/callback handling is idempotent: receiving the same event twice must not create a duplicate order or duplicate credit delivery. (PAY-2) — verified 2026-07-30: `XenditWebhookController::handle()` short-circuits to "already processed" if `payment_status` is already `Paid`; `OrderFulfillmentService::fulfill()`'s own row lock is the second, structural layer if a duplicate somehow reaches it anyway.
- [x] (PAY-3, payment-side) / [x] (ORD-10, delivery-side) — both shipped. **PAY-3** — `app:reconcile-pending-payments` (`App\Console\Commands\Payment\ReconcilePendingPaymentsCommand`, scheduled every 15 min in `routes/console.php`) independently polls Xendit via `PaymentGateway::getPayment()` for any order stuck at `payment_status=pending`, so the webhook is no longer the sole path to a final payment state — see [ADR-021](./adr.md). **ORD-10** — shipped 2026-08-14 as [ADR-026](./adr.md): `app:reconcile-pending-deliveries` (same 15-min cadence) covers two ambiguous-outcome shapes Gamevion's own idempotent `409 duplicate_reference` and a connection failure that exhausts every retry layer — routes both to a new `DeliveryStatus::NeedsReview` state, resolved via an admin's "Mark as Delivered" (requires the real Gamevion invoice number, manually cross-referenced against Gamevion's dashboard) or "Resend Delivery" — "Issue Voucher" is deliberately never available from this state (double-compensation risk).
- [x] Admin-issued standalone vouchers (Path A) are idempotent against a double-click or a network-retry — a repeated submission must return the same `Voucher`, never mint a second one and double-debit the platform ledger. (ADR-035) — shipped 2026-08-26: `vouchers.idempotency_key` (nullable, unique — Path B's `order_id`-keyed uniqueness, pre-existing, is unaffected), same two-layer shape as ORD-8/PAY-2 above — `VoucherController::store()` does a fast-path lookup first, then a DB unique-constraint catch-and-replay as the real guarantee against a genuine race. Client-generated once per `CreateVoucherModal.tsx` open (`OrderForm.tsx`'s own precedent), never regenerated across a resubmit of that same attempt.

## 4. Fraud Prevention

- [x] Every order creation checks the customer/player against the internal blacklist before payment or supplier submission proceeds. (FRAUD-1, FRAUD-2 — `BlacklistService`/`CheckoutController::assertNotBlacklisted()`, 2026-07-29)
- [x] The checkout/payment endpoint has its own, stricter rate limiting / velocity check distinct from general API rate limiting, to reduce card-testing (carding) abuse. (FRAUD-4 — `CheckoutVelocityGuard`, counts only blacklist-triggered rejections per IP, distinct from `throttle:10,1`)
- [x] Blacklist entries always require a recorded reason and are attributable to the admin who added them. (FRAUD-3 — `blacklist_entries.reason`/`created_by`, `/admin/blacklist`)
- [ ] Reseller Portal self-serve wallet top-up (ADR-072/073, PR-G): a `Reseller` account can top up its own wallet via CHIP with **no platform-imposed maximum** amount (PR-G planning addendum decision 3) — CHIP's/the bank's own per-transaction ceiling is the only limit. Accepted risk given the account is admin-vetted (no self-serve signup) and CHIP itself carries its own fraud/AML controls on the payment side; revisit (add a platform-side cap or manual-review threshold) if an actual abuse pattern is observed, same "not built speculatively ahead of evidence" posture as the WhatsApp-group line above.

## 5. Payment Gateway Integrity (CHIP)

**2026-09-01 (ADR-022 addendum): Xendit was removed — CHIP is the sole payment gateway.** The controls below were written and verified against Xendit-era code; **read every `Xendit`/`/api/webhooks/xendit`/`XenditWebhookController` reference below as `Chip`/`/api/webhooks/chip`/`ChipWebhookController`** — the route and class were renamed. `XenditGateway` is deleted; there is no `/api/webhooks/xendit` route any more. The *control* is unchanged (a cryptographic signature check before any Order is touched, per-route webhook rate limiting `throttle:120,1,webhook-chip`, no raw card data — CHIP-hosted fields keep it out of PCI-DSS scope) but the **mechanism differs**: CHIP webhook auth is an **RSA PKCS#1 v1.5 signature** (`X-Signature` header, `openssl_verify` against the account public key from `GET /public_key/`), not Xendit's `hash_equals` token compare — see [ADR-022](./adr.md)'s 2026-09-02 webhook-model addendum. **Verified live in production 2026-09-03** — a real RM1.94 FPX payment (order `PG-PYAYMRYNUYV0`) delivered a genuinely-signed `success_callback` that `ChipWebhookController` verified and applied; a `ChipWebhookControllerTest` case still proves an invalid signature is rejected `401` before any Order is touched. xenPlatform (§5's last item) stays out of scope — ADR-059 decision 6 dropped it entirely, not deferred it.

- [x] `/api/webhooks/chip` has its own rate limit (`throttle:120,1,webhook-chip`), distinct from a down-gateway flood just costing free DB queries pre-signature-check. — fixed 2026-08-14 (same session as the gap was found): both routes now carry `throttle:120,1` (`backend/routes/api.php`), generous enough not to risk throttling a real gateway retry burst. Regression test: `XenditWebhookControllerTest::test_rate_limits_repeated_requests_from_the_same_ip`. **Correction, 2026-08-27:** "own rate limit" wasn't actually true until this date — every bare `throttle:N,1` route in `routes/api.php` (this pair included) shared one counter per IP, since Laravel's default throttle key never includes the route path (see ADR-019's newest addendum, `docs/adr.md`). Both webhook routes now carry an explicit `webhook-xendit`/`webhook-chip` prefix, so this line's claim is finally actually true, not just configured to look that way.
- [x] All Xendit webhook/callback payloads are cryptographically verified before being trusted. An unverified callback is logged and discarded — never actioned. (PAY-1) — verified 2026-07-30: `XenditWebhookController::handle()` calls `PaymentGateway::verifyWebhookSignature()` (the `x-callback-token` comparison via `hash_equals`) first; a failed check logs a warning and returns `401` before touching the Order.
- [x] The platform never touches raw card data directly. Card entry happens only via Xendit-hosted fields/redirect — this keeps the platform out of PCI-DSS scope. (PAY-4) — verified 2026-07-30: no `card_number`/`cvv`/`card_details` handling exists anywhere in `app/`; the one `card_details` reference is a `PaymentMethodController` comment noting Xendit itself needs it (not that we supply it).
- [x] xenPlatform (sub-account splitting) is out of scope until Phase 2 — do not wire it in early "just in case." (D1 / ADR-001) — verified 2026-07-30: zero references to `xenPlatform`/sub-account/`for_user_id` exist anywhere in `app/`/`config/`.

## 6. Supplier Integration

- [x] No business logic reads a raw supplier response directly — every supplier is accessed only through its Adapter, which normalizes to one canonical internal shape. (ADAPT-1, ADAPT-2) — verified 2026-07-30: `GamevionAdapter` is the only class in `app/` making an `Http::` call to a supplier; `OrderFulfillmentService`/`CheckoutController` depend only on the `SupplierAdapter` interface.
- [x] Never assume a supplier's auth scheme, response envelope, or validation-endpoint availability is uniform with any other supplier. Confirm per-supplier, per-game during onboarding. (D6 / ADR-006) — verified 2026-07-30: `GamevionAdapter`'s doc comments record Gamevion-specific confirmed-not-assumed quirks (dual Bearer+X-API-KEY auth, `telp` rejects a leading `+`, no player-validation endpoint at all, sandbox uses a different field-name shape than production).
- [x] ~~Validation-capability (`supports_validation`) is tracked per game-supplier mapping, not as a blanket flag on the Supplier record.~~ (GAME-12) — **dead requirement, dropped 2026-09-13** (`docs/prd.md` §16): neither Gamevion nor Digiflazz exposes player-validation via its own API — both `validatePlayer()` unconditionally throw `ValidationNotSupportedException` — and no code path anywhere ever reads the flag. The JSON field remains in `games.supplier_mappings` (harmless, unread). Real player-ID validation runs through the unrelated `Game.player_validator_enabled`/`player_validator_profile_id` (`PlayerValidatorRegistry`, ADR-093).
- [x] A circuit breaker trips per-supplier after repeated failures — a down supplier must not be able to cascade into blocking the whole delivery queue. (`App\Services\CircuitBreaker\CircuitBreaker` + `CircuitBreakingSupplierAdapter`, 2026-07-29 — see ADR-019's newest addendum)
- [x] If a supplier requires IP whitelisting, its Adapter routes through the one shared outbound proxy config (`config/services.php['proxy']`), never a supplier-specific, one-off proxy setup. (ADR-006 addendum) — verified 2026-07-30: `GamevionAdapter`'s optional `proxyUrl` constructor argument reads from that shared config key, not a Gamevion-specific one.
- [x] "Supplier item is active again" is confirmed by a sync run that happened *after* the package was taken offline — never by a stale `status_raw` value left over from before the deactivation. — fixed 2026-08-21 (real bug found live-verifying ADR-025, confirmed structural via a short-gap repro, not a long-sync-gap artifact — `docs/prd.md` §14's 2026-08-21 entry): `PendingReactivationFinder::find()` now requires `SupplierProduct.last_synced_at` to be after the package's own `deactivated_at`. Regression tests: `tests/Feature/Services/Sync/PendingReactivationFinderTest.php` (both the bug repro and a control case for genuine reactivation).

## 7. Secrets & Data

- [ ] Supplier credentials (`api_config`) and payment gateway secrets are encrypted at rest, never returned in full via any API response, and never shown unmasked in Developer Tools. (SUPP-5, DEV-2) — **half verified, half not applicable yet**: `Supplier.api_config` uses Eloquent's `encrypted:array` cast and is `$hidden` (confirmed 2026-07-30, `app/Models/Supplier.php`) — the SUPP-5 half is real. The DEV-2 half (never shown unmasked in Developer Tools) can't be verified either way: Developer Tools (`§6.18` DEV-1/DEV-2) doesn't exist as a screen at all yet — nothing to check, not a confirmed pass. Leave unchecked until that screen exists and is actually verified to mask secrets.
- [x] Request logs redact credentials and excess PII before being written. (MID-10) — shipped 2026-08-28: [ADR-051](./adr.md) — `App\Services\Supplier\RequestLog\SupplierRequestPayloadRedactor` strips `Authorization`/`X-API-KEY` headers case-insensitively plus every body key `SupplierConfigSchema` marks `secret` for that supplier, *before* the row ever reaches the queue (`LogSupplierRequestJob`) or the database — redact-then-queue-then-write, never inline-then-redact. `validatePlayer` rows (the PII-carrying call type) additionally follow `player_validations`' existing 7-day retention window rather than the blanket 30-day default. Verified live: a real `Refresh Balance` call's `Authorization`/`X-API-KEY` confirmed redacted in `/middleware/request-logs`' detail modal.
- [x] Player/customer PII returned from validation calls (e.g. in-game nickname, country) is retained only as long as operationally needed — not logged or stored beyond what's needed to confirm the order to the customer. — closed 2026-07-30 (later same day): `App\Console\Commands\PlayerValidation\PrunePlayerValidationsCommand` (`app:prune-player-validations`), scheduled daily, deletes `player_validations` rows where `validated_at` is older than `config('services.player_validation.retention_days')` (7 days, grilled in [ADR-021](./adr.md)).
- [x] No raw credentials are ever written to logs, error messages, or client-visible responses. — spot-checked 2026-07-30, not exhaustively grepped: `AuthController::login()`'s failure/success log lines carry `email`/`admin_id`/`ip`, never the attempted password; `CheckoutController`'s failure logs carry order/customer context, no gateway/supplier secrets. Held up everywhere checked, but this is a spot check of the highest-risk paths (auth, checkout), not a full audit of every `Log::` call in the codebase.
- [x] The guest order-status view (`GET /api/track-order/{orderNumber}` + the `OrderStatusUpdated` broadcast) returns the buyer's own contact **masked**, never raw. — [ADR-065](./adr.md), 2026-09-01: `App\Support\ContactMask` (`name`/`email`/`phone`) is applied only in `TrackOrderController::customerSafePayload()` (the one shape both producers share), never on the `Order` model — so admin/checkout/fulfilment/notification/ledger paths keep the raw values. The response also carries the customer-facing payment breakdown (`payment_method`/`selling_price`/`voucher_discount`/`transaction_fee`, all money shown at checkout) but still never `standard_selling_price`, profit, supplier fields, or `payment_ref`. Rate limit unchanged (`throttle:20,1,track-order`); the `order_number` ULID (~80 bits) stays the ownership proof. Verified live + by `TrackOrderControllerTest` (masked shape, raw-value leak guard, broadcast==endpoint parity).
- [x] Full-database backup archives are encrypted at rest and exclude PII past its own retention policy. (BAK-1..5) — closed 2026-08-26: [ADR-039](./adr.md) — `config/backup.php`'s `password`/`encryption` (AES-256 via `BACKUP_ARCHIVE_PASSWORD`), `config/database.php`'s `dump.exclude_tables = ['player_validations']` on both `mysql`/`sqlite` connections (preserves `PrunePlayerValidationsCommand`'s 7-day retention above — a raw dump would otherwise silently undo it). Verified live: a real local backup archive was inspected and confirmed to contain no `CREATE TABLE player_validations` statement. Restore stays CLI/artisan-only, never a self-service Admin UI action (decision 5) — the one action in this system with the largest blast radius.
