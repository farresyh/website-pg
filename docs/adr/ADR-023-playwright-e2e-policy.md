# ADR-023: Playwright E2E policy — golden-path scope, growth triggers, and suite-hygiene rules

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-08-04 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any `e2e/` file was written)

**Context:** `ADR-020` decision #9 already decided *that* Playwright E2E should exist and named two golden paths (guest checkout → payment → order status; admin login → view order → Resend Delivery), recorded as the explicit next priority once Phase 1 CI shipped — which it has (`.github/workflows/ci.yml`, `ADR-020`'s own addendum). What that decision never pinned down is *how the suite behaves as the product grows* — the founder's own question opening this grilling session: "kalau ada new feature baru or update, adakah kita akan tambah tambah lagi e2e ni atau macam mana" (if there's a new feature or update, do we just keep bolting on more E2E tests, or is there a real policy). This ADR is that policy — a durable, standalone decision, not an addendum to `ADR-020`, since it governs ongoing behavior rather than correcting that ADR's original scope.

**A pre-existing gap surfaced and closed before this ADR could be finalized:** the third golden path proposed during grilling — admin issues a voucher for a failed order (`ADR-004`'s other resolution path, alongside Resend Delivery) — turned out to have no real UI to test. `VoucherController::storeFromOrder()` was fully built and tested (6 dedicated tests, race-condition-safe via a real unique index on `vouchers.order_id`), but the Admin Panel's Orders page had no "Issue Voucher" button — deliberately deferred, per that code's own comment ("no Orders admin UI to add a 'Create Voucher' button to"). Founder's call, once this was surfaced: build the button now (small, well-scoped, reuses the `ResendDeliveryModal` pattern exactly) rather than either faking a UI-less test or dropping the golden path to two. Shipped this session: `Order::voucher()` relation, `OrderController::show()` eager-loads it, `IssueVoucherModal.tsx` + the button on a failed order's detail view (hidden once `order.voucher` is set), `lib/orders.ts`'s `issueVoucherFromOrder()`. 2 new backend tests (`show()` includes/excludes the voucher), full suite 525 green, `tsc --noEmit`/`next build` clean. This is a concrete instance of the trigger policy below already working as intended — a small UI gap blocking real test coverage was fixed, not routed around.

**Decision:**

1. **Starting scope — exactly 3 golden-path tests, Chromium only:**
   - Storefront: guest checkout → payment → order status.
   - Admin: login → view order → Resend Delivery.
   - Admin: login → failed order → Issue Voucher.
   Firefox/WebKit are deliberately excluded from the start — multiplying a 3-test suite across 3 browsers multiplies the flakiness surface Decision 4 below takes seriously, for coverage a guest-checkout storefront's real traffic profile doesn't yet justify. Add a browser only if a real production incident (Decision 2's Trigger B) is traced to that specific browser.

2. **Growth is real but bounded to two named triggers — never ad hoc, never a reviewer's case-by-case call:**
   - **Trigger A (feature-level, not code-level):** a genuinely *new* way money moves (a new payment gateway — e.g. when `ChipGateway`, already code-complete per `ADR-022`, goes live) or a new order-resolution mechanism beyond retry-delivery/voucher (`ADR-004`). Deliberately feature-level, not code-level: a refactor of `OrderFulfillmentService` or a bugfix inside `CheckoutController` does **not** itself earn a new test just because it touched money-adjacent code — the existing golden-path tests already exercise that code as it's refactored. Code-level triggering was considered and rejected: it would fire on nearly every backend PR near money code, which just reinvents unbounded reviewer judgment under a different name.
   - **Trigger B (incident-driven):** a real production bug slips through, **and** its root cause is a pure browser-level UI break that PHPUnit structurally cannot see (a dead click handler, a broken redirect, a silently-failing form submit) — that flow earns a permanent E2E test as part of the incident fix. If the root cause is backend logic instead, the fix gets a PHPUnit test at that layer, not E2E — E2E never becomes the default destination for every production bug regardless of which layer it actually lived in.
   - No third path exists. A feature that is important but touches neither money-movement/resolution-mechanisms nor a proven UI regression (new admin screens, reports, filters, ordinary CRUD) stays PHPUnit/manual-QA only, by design, not by oversight — see Decision 6 for what this deliberately excludes today.

3. **Enforcement — a PR-template checklist item, not a CI-blocking gate.** A literal checkbox: "Does this PR add a new payment gateway, new payout mechanism, or new order-resolution path? If yes, an E2E test is required." A hard, path-based CI gate (failing the build if a diff touches `Services/Payment/*` without a matching `e2e/` change) was considered and rejected — this project's own established discipline is documentation/convention-driven (`adr.md`'s whole existence), not gate-driven, and a path-heuristic gate is easy to both trip falsely and route around; over-engineering for a team of one founder plus AI sessions.

4. **Flakiness — zero tolerance, fix-or-delete in the same PR, no quarantine lane.** A flaky test keeps CI red until someone either fixes the root cause or explicitly removes the test with a recorded reason — never a silently-left `test.skip()`. A quarantine lane (auto-tag flaky tests into a non-blocking job, grace period to fix or delete) was considered and rejected as machinery sized for a much larger suite than 3 tests; at this size, "fix now or explicitly remove and say why" is not a burden, and it's the single guardrail against the most common way E2E suites die everywhere — a red test everyone learns to ignore.

5. **Interim running, until CI wires this in — a documented AGENTS.md gotcha, matching the project's existing pattern.** `ADR-020`'s CI (`.github/workflows/ci.yml`) already exists, so once the suite is scaffolded, wiring a `playwright` job into it closes this gap almost immediately — but for the window between scaffolding and that CI job landing, running the suite is manual. Rather than trust that to memory, it gets the same treatment `AGENTS.md`'s "Known gotcha" section already gives the queue-worker-death and migration-not-applied gotchas: a documented reminder to run the suite before shipping a change touching checkout/resend/voucher-issuance, discoverable by a cold future session, not tribal knowledge from this conversation.

6. **Mocking strategy — Gamevion faked forever at the HTTP layer; Xendit hit for real against its working sandbox; a real webhook is simulated, not awaited.**
   - **Gamevion:** its sandbox was confirmed permanently broken for real orders when this decision was made (`ADR-006` — every real `product_code` either 500s or is rejected) — **correction, 2026-08-13/14: `ADR-006`'s newest addendum found this fixed on Gamevion's side, real `product_code`s now complete successfully in sandbox.** This decision's premise no longer holds, but the decision itself (fake Gamevion via `Http::fake()`, never talk to the real API) is left as-is here — determinism/speed/no external dependency are independent, still-valid reasons for a Playwright suite to mock a third party regardless of whether that party's sandbox happens to work today; revisit only if the founder actually wants E2E to hit real Gamevion sandbox, not silently via this correction note. E2E fakes it via `Http::fake()` and never talks to the real API. Supplier-contract drift (a field rename, a new required field — `ADR-006` already logged two such surprises, `telp` format and `callback_url`) is a different problem, owned by the existing `GamevionAdapterTest` PHPUnit suite, not by E2E — bolting contract-drift monitoring onto Playwright would conflate two different jobs neither this ADR nor `ADR-006` asked it to do.
   - **Xendit:** has a real, working sandbox, so E2E hits it for real rather than faking it. CI has no public URL to receive a genuine webhook callback, so the webhook is simulated by POSTing a validly-signed payload directly to `/api/webhooks/xendit` after the redirect step, rather than waiting on a real inbound callback.
   - **Test database:** a fresh `migrate:fresh --seed`-equivalent per run, not the local dev database.

7. **Fixtures — a thin, explicitly-owned `e2e/fixtures` file, built on existing Laravel model/factory patterns, not a parallel data-definition system.** Only `AdminUserFactory` exists today (no `Game`/`Package`/`PaymentMethod` factories) — rather than build out a parallel factory layer unscoped by this ADR, the fixture file creates exactly the fixed rows the 3 tests assert against (one admin, one game+package, one active payment method, one pre-existing failed order for the voucher test) directly via Eloquent, reusing `AdminUserFactory` where it already fits. Whoever's PR changes the relevant schema (a new required `Game`/`Package`/`Order` field) owns updating this fixture file as part of that same PR — never a separate, easy-to-forget follow-up task, and never left as "whoever notices it's broken fixes it."

8. **Infra — a dedicated, minimal E2E boot script, not `scripts/dev.sh`, not yet a Docker Compose file.** `scripts/dev.sh` already carries two documented gotchas (silent queue-worker death if `backend/node_modules` is missing; migrations not auto-applying to the dev DB) — reusing it for E2E would make those dev-tooling gotchas into E2E-suite gotchas too, undermining Decision 4's zero-tolerance flakiness policy with noise that isn't a real regression. A dedicated `docker-compose.e2e.yml` was considered and rejected for *now* — that's the right shape once real CI is actually orchestrating this (which it already can, via `ADR-020`'s Phase 1 CI), not before; building Docker E2E infra ahead of that need repeats the exact mistake `ADR-015`/`ADR-016`/`ADR-020` decision #1 were each built to avoid (designing against a shape with no real signal yet).

9. **Each spec file gets a one-line header comment citing its justifying ADR/trigger, in addition to a descriptive filename.** E.g. `// Golden path — ADR-023. Covers ADR-004's Issue Voucher resolution path.` A fresh reader (human or a future AI session with no memory of this grilling conversation) should be able to tell *why* a test exists and whether it's still needed without re-deriving this ADR from the filename alone — matching this codebase's existing habit of keeping the *why* next to the *what* (every ADR above cites exact files/services it touches).

**Rationale:** every sub-decision above resolves the same underlying tension the founder's opening question named directly — an E2E suite either grows without bound (rotting into slow, flaky, untrusted CI) or never grows at all (leaving new money-critical UI surface permanently uncovered). Trigger A/B (Decision 2) is the load-bearing answer: growth is real but always traceable to one of exactly two named, checkable conditions, never a vague "this seemed important" call. Every other decision (flakiness, fixtures, infra, mocking, documentation) exists to keep the suite trustworthy at exactly the size Decision 2 allows it to reach — not more machinery than 3 tests warrant, not less discipline than a money-moving system requires.

**Consequence to track:**
- The 2 remaining unbuilt "not started at all" admin areas most likely to trigger Decision 2 next: `ChipGateway` going live (Trigger A, once `ADR-022`'s CHIP merchant account is approved) and any real production incident traced to a pure UI regression (Trigger B) — neither exists yet, don't scaffold speculative tests for them now.
- Decision 5's interim AGENTS.md gotcha becomes moot, not wrong, once a `playwright` CI job is wired into `.github/workflows/ci.yml` — remove the gotcha note at that point rather than letting two overlapping reminders (manual + CI) coexist indefinitely.
- Decision 7's fixture file is the first thing to break if `Game`/`Package`/`PaymentMethod`/`Order` schema changes without updating it — this is expected friction, not a bug in the policy; per Decision 2, updating it is part of the schema-changing PR, not a separate task.
- This ADR is policy-only for the 3 named golden paths; the actual `e2e/` scaffold, spec files, fixture file, and CI wiring are the concrete next actions, tracked in `docs/prd.md` §14 as they ship.

**Addendum — scaffold built and all 3 golden paths verified passing for real, same session, 2026-08-04:** `e2e/` built per every decision above and actually run, not just written — full detail in `docs/prd.md` §14. One real, non-obvious bug found and fixed along the way, general beyond E2E: `php artisan serve` re-reads `backend/.env` for the process it spawns and only passes through a small hardcoded env-var whitelist from the calling shell unless `--no-reload` is given — without it, `boot-backend.sh`'s own `DB_DATABASE` export was silently dropped and the served process read the real local dev database instead of the throwaway e2e one, with no error surfaced anywhere. Now documented as a third `AGENTS.md` gotcha, since it can bite any script that boots `serve` against env vars set outside `.env`, not just this one. Also found and fixed: Next.js 16's dev-mode cross-origin request blocking (resolved by using `localhost`, not `127.0.0.1`, consistently across `e2e/`'s config and `config/cors.php`'s existing `ADMIN_URL`/`STOREFRONT_URL` defaults — not by adding `allowedDevOrigins`, which turned out unnecessary once the hostname matched); and the storefront checkout spec needing `page.route()` rather than `page.waitForResponse()` to read the `/api/checkout` response body before `OrderForm.tsx`'s own `window.location.assign()` navigates the page away from it. The storefront checkout test also confirmed this local dev environment's `backend/.env` already has a real Xendit test-mode key — enough to prove the full path for real (`POST /api/checkout` → `201` → a real `bank-web-mock.xendit.co` redirect → simulated webhook → `Delivered`) — CI still needs `XENDIT_TEST_SECRET_KEY` added as a repo secret before its own `playwright` job's checkout spec can pass there.

**Addendum — 4th golden path added under decision #2's Trigger A, 2026-08-21:** `admin login → needs_review order → Mark as Delivered` (ADR-026's `needs_review` state and its one non-retry exit) — a genuinely new order-resolution mechanism beyond retry-delivery/voucher, the literal example decision #2 names. New fixture (`KRS-E2E-NEEDSREVIEW-FIXTURE`) added to `E2ESeeder`, kept fully separate from the other two so no test's own state change affects another regardless of run order (decision #7's own convention). Two real bugs found live, both fixed, neither previously caught by PHPUnit (exactly the class of gap this ADR's whole policy exists to catch): (1) `Admin\OrderController::markDelivered()` returned a bare `$locked->fresh()` with none of `show()`'s eager-loaded relations — the admin panel's own `setSelected(updated)` then crashed rendering `DeliveryLogsTable` on the now-undefined `resend_attempts`; fixed by mirroring `show()`'s `->load([...])` (the sandbox counterpart, `SandboxOrderController::markDelivered()`, already did this correctly — only the real controller had drifted). (2) The success message (`markDeliveredMessage`) was rendered inside the same `{(failed || needs_review) && (...)}` block as the trigger buttons — since a successful Mark as Delivered moves `delivery_status` to `delivered` in the same render that sets the message, the block (and the message with it) unmounted before an admin ever saw it; fixed by moving the message outside that conditional. A third, separate finding — real but not code-caused — surfaced while chasing an apparently unrelated flaky failure: adding a 3rd admin spec exposed a pre-existing timing race in `next dev` (Turbopack) where navigating from `/admin` to `/admin/orders` immediately after login could abort `/admin`'s own in-flight `GET /api/me` verification call; `Admin\page.tsx`'s catch handler treated any error from that call (including a plain navigation-triggered abort) as "session invalid" and called `clearClientSession()`, and separately, `/admin/orders`' own independent `getClientSession()` check on mount could read before the previous page's state had settled, bouncing to `/login` with zero `/api/orders` calls ever made. Reproduced deterministically by swapping which spec ran 2nd in a 3-test serial run — content-independent, confirming it as a pre-existing infra race that a 2-test suite was simply unlikely to hit, not something the new spec introduced. Fixed in two parts: `admin/page.tsx`'s `/api/me` effect now guards against acting on a stale/aborted result via a `cancelled` flag (real hardening, kept regardless); and `e2e/tests/helpers.ts`'s `loginAsAdmin()` now waits for `networkidle` after landing on `/admin` before any test proceeds to navigate further — a real synchronization point, not an arbitrary sleep, and the fix that actually closed the race (confirmed via 4 consecutive clean 3-test runs after applying it, versus 100% reproduction before). `playwright.config.ts`'s own doc comment updated to reflect 4 golden paths, no longer "the 3... only."
