# ADR-046: Supplier Management screen — trimmed to config/health (SUPP-1/CRUD/SUPP-5), `Supplier.api_config` becomes the live credential source, per-supplier/per-game bulk deactivation

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-27 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any code touched)

**Context:** `docs/prd.md` §6.5 (SUPP-1..5) has sat unbuilt since the project's foundation. The `suppliers` table has existed since 2026-07-23 (`Supplier` model, `api_config` encrypted-at-rest + `$hidden`, per SUPP-5), and `SupplierAdapterFactory` (ADR-031) already resolves an adapter per `Supplier.slug` — but no admin UI exists to create a `Supplier` row, edit its credentials, activate/deactivate it, or view its balance/connection status. The only `Supplier` rows that exist today were created by a `firstOrCreate()` stopgap inside the sync commands, and both real adapters (`GamevionAdapter`, `DigiflazzAdapter`) still read their credentials from `config/services.php` (i.e. `.env`), never from `Supplier.api_config` — the Digiflazz binding's own comment in `AppServiceProvider.php` already names this as a deliberate stopgap pending "a real Digiflazz account exists to configure through the UI."

Separately, PRD's SUPP-2/3/4 (browse supplier catalog, add game from catalog, search catalog) describe functionality that `/middleware/product-manager` (`SupplierProductController`) already built and shipped — category-link + promote from the `supplier_products` staging table. Building those three requirements again as part of this screen would create two UIs doing the same job against the same data.

A second, unrelated operational gap surfaced during grilling: with 500+ packages live, a single problem supplier (delay, outage, or a problem isolated to one game) currently has no bulk remediation path — an admin must deactivate every affected `Package` row one at a time from `/admin/games`. Because ADR-034's storefront dedup (`dedupByDenomination()`) already filters to `is_active=true` packages before picking the cheapest match per `(game_id, denomination)`, deactivating the problem supplier's packages is sufficient by itself to let a healthy supplier's equivalent package take over — no new pricing/dedup logic is needed, only a bulk actuator for the existing `is_active` flag.

**Decision:**

1. **Screen scope is SUPP-1 + CRUD + SUPP-5 only.** SUPP-2/3/4 are explicitly dropped from this screen — `docs/prd.md` §15's Supplier Management row is updated to note the overlap with Product Manager and the reason, not silently left contradicting what's built.
2. **`api_config` becomes the live credential source.** `AppServiceProvider`'s `gamevion`/`digiflazz` adapter bindings are changed to read from `Supplier::api_config` instead of `config('services.*')`. This is a **hard cutover, not a fallback** — matches ADR-031's own precedent of removing the old binding cleanly once its replacement exists, rather than carrying two credential sources indefinitely. Prerequisite: the existing `gamevion` `Supplier` row's `api_config` is backfilled from its current `.env` values (`GAMEVION_BASE_URL`/`BEARER_TOKEN`/`API_KEY`/`SANDBOX`) as a one-time step before the binding change ships — the row already exists (via the sync-command stopgap) but its `api_config` is currently empty, so cutting over without backfilling first would break live Gamevion order fulfillment.
3. **The Edit form is structured per-supplier, not a blind JSON editor.** Each supplier's `api_config` keys are rendered per a small per-supplier field definition: secret-shaped fields (`bearer_token`/`api_key`/`username`) are write-only and masked (SUPP-5 — never redisplayed, shown only as a "Configured"/"Not configured" badge); non-secret operational fields (`base_url`, `sandbox`/`testing` booleans, `customer_no_separator`) are shown and edited as plain visible/toggle controls. This turns `GAMEVION_SANDBOX`/`DIGIFLAZZ_TESTING` — today a `.env`-edit-and-restart operation the project's own build log shows being flipped by hand across multiple sessions — into a live admin toggle. `api_config`'s shape is left schemaless (already true today, per the migration's own comment); a future correction to Digiflazz's actual sandbox shape (unverified — the account is still IP-whitelist-blocked, tracked separately in `docs/prd.md`'s backlog pointer) costs adding a key to its field definition, not a schema migration.
4. **`slug` on Create is a dropdown constrained to adapter slugs already registered in `SupplierAdapterFactory`** (`gamevion`, `digiflazz` today), not free text — `SupplierAdapterFactory::make()` only throws `UnsupportedSupplierException` at resolve-time (i.e., at the next real fulfillment/sync attempt), so a typo'd slug would otherwise sit silently broken until it's needed for a real order.
5. **Toggling `Supplier.is_active` to true surfaces a confirm warning** ("this supplier will be included in the next scheduled price sync") — `SyncSupplierProductsCommand`/`SyncSupplierPricesJob` (ADR-031 decision 4) loop over active `Supplier` rows automatically, so activation is a real, immediate, money-adjacent action, not an inert flag flip.
6. **Delete is allowed only when the row has zero references** (`packages.supplier_id`, `supplier_products.supplier_id`, `orders.supplier_id` counts all zero) — otherwise only Deactivate is offered. The three FKs behave inconsistently on a real delete today (`packages` restricts, `supplier_products` cascades, `orders` nulls historical `supplier_id`), so an unconditional Delete is unsafe; a zero-reference row is a same-session mis-creation with nothing to lose.
7. **Connection status on the supplier card reuses `CircuitBreaker::state()`** (the same read `DashboardService::health()` already performs, cache-derived from real traffic) rather than an on-demand live ping — consistent with DASH-2's own reasoning (ADR-045 decision 5): a live ping on every screen load risks tripping the very breaker being displayed.
8. **"Refresh Balance" performs a real, on-demand `checkBalance()` call** through the same circuit-breaker-wrapped adapter path (`CircuitBreakingSupplierAdapter`), storing the result in two new nullable `suppliers` columns, `last_tested_at`/`last_test_result` — directly mirrors the existing `payment_methods.last_tested_at`/`last_test_result` pattern (ADR-022) rather than inventing a new one. Unlike Payment Methods' "Test This Channel" (which creates a real RM1.00 payment-intent), `checkBalance()` is a genuinely free read-only supplier call — no analogous cost concern.
9. **Bulk package deactivation, two scoped actions on the supplier's detail view: "Deactivate All" and "Deactivate by Game."** Both bulk-set `packages.is_active = false` for the supplier (optionally further scoped to one `game_id`) — no new pricing/routing logic, since ADR-034's dedup already excludes inactive packages from the storefront's cheapest-match query. A paired "Reactivate" action (same scoping) is a separate, explicit control — **not** a reuse of the existing Pending Reactivation UI (SYNC-5/6), which is a different mechanism (automatic detection of a package reappearing at the supplier, not an admin-initiated manual override).
10. **`deactivation_logs` is extended, not forked.** Two new nullable columns — `admin_user_id` (FK to `admin_users`) and `reason` (text) — let one manual bulk action and one automatic Price Sync run write to the same audit table (`price_sync_run_id` already nullable) rather than splitting "why did this package go inactive" across two tables for the same underlying fact.
11. **Route prefix `/middleware/suppliers`, gated `admin.role:super_admin` only** — matches every other supplier-adjacent tool's existing convention (`middleware/supplier-products`, `middleware/price-sync`, `middleware/sandbox`, `middleware/payment-methods`, all `super_admin`-only per `routes/api.php`'s own comment: "Super Admin only — supplier config, per PRD §3").

**Rationale:** Every decision here follows the same discipline as ADR-031/034/045: reuse an existing seam instead of inventing a parallel one (`CircuitBreaker::state()`, `deactivation_logs`, the `payment_methods.last_tested_at` pattern, ADR-034's existing dedup filter), and don't build a second UI for something Product Manager already does. The hard-cutover-with-backfill (decision 2) matches ADR-031's own precedent for retiring a stopgap cleanly rather than layering a permanent fallback on top of it. The bulk-deactivation addition (decisions 9/10) exists because the founder's own real scenario — 500+ live packages, one supplier degraded, only one game actually affected — has no remediation path today faster than editing packages one at a time, and the fix costs nothing structurally new because ADR-034 already built the query-time fallback it depends on.

**Consequence to track:**
- The `api_config` cutover (decision 2) is the one change here that touches a live, money-critical path (`GamevionAdapter` construction) — the backfill step must be verified against the real local/production credential values before the binding change merges, not assumed correct from the migration alone.
- Digiflazz's real sandbox/production credential shape is still unverified (account IP-whitelist-blocked) — decision 3's schemaless-`api_config` choice means this ADR doesn't need to be revisited when that's confirmed, only Digiflazz's own field definition.
- Payment gateway credentials (Xendit `secret_key`/`webhook_token`, CHIP `secret_key`/`brand_id`) surfaced during grilling as the same unmigrated-`.env` gap this ADR closes for suppliers — tracked as a future, separate backlog item (no `payment_gateways`-equivalent table exists; `payment_methods` stores only per-channel activation/fee metadata, not gateway secrets), deliberately out of this ADR's scope.
- SUPP-2/3/4's removal from this screen (decision 1) should be treated as final unless a real gap in Product Manager's existing catalog-browse/promote flow surfaces later — not silently revisited.

**Addendum — "Refresh Balance" was silently showing the sandbox account's balance, and the card gained a Sandbox/Production badge, 2026-08-27 (same session, found live-testing).** Founder's own live browser test caught this: unticking Gamevion's `sandbox` field in the Edit form and refreshing showed a *different* balance than with it ticked — not a masked/scaled view of the same number, a genuinely different account. Root cause: `GamevionAdapter::client()` sends `X-ENVIRONMENT: sandbox` on **every** call whenever `$this->sandbox` is true (`GamevionAdapter.php:173`), and `checkBalance()` (decision 8's live call) went through that same client unconditionally — so whatever mode `sandbox` happened to be left in for order-routing/testing silently decided which account's balance a money-monitoring screen (SUPP-1/DASH-2) displayed. Digiflazz's `checkBalance()` was independently checked and confirmed **not** affected — its `testing` flag is only sent as a body param on the transaction-submission endpoint, never on `/v1/cek-saldo`.

1. **`GamevionAdapter::checkBalance()` now always forces production** (`client(forceProduction: true)`, a new optional param on the existing private `client()` method) — decouples "which environment orders route to" (a testing convenience, left to `sandbox`) from "what's our real balance" (must always be real, never conditional on a flag an admin could leave in the wrong state). `listProducts()`/`createOrder()`/`checkStatus()` are unchanged, still `sandbox`-aware.
2. **The Supplier card gains a Sandbox/Production badge next to its connection-status Tag** — a new `is_sandbox` field on the index response (`SupplierController::isSandbox()`), computed generically rather than the frontend hardcoding a per-supplier field name (`sandbox` for Gamevion, `testing` for Digiflazz): it looks up whichever key `FIELD_DEFINITIONS` marks `'boolean'` for that supplier and reads its current value. `null` (not `false`) when a supplier has no such field at all — a card should never claim "Production" for a supplier this codebase has no sandbox concept for. Founder's own reasoning: an admin shouldn't need to open Edit just to know which mode is currently live.

### Addendum (2026-09-24) — decisions 9/10's bulk toggle never cascaded onto dependent combos

**Context:** Found while auditing ADR-094's own combo reactivation cascade (its own 2026-09-24 addendum) for other call sites that flip a `Package.is_active` flag. `updatePackagesStatus()` (decisions 9/10) does a single mass `Package::query()->update()` for its "Deactivate All"/"Deactivate by Game"/"Reactivate" actions — never the per-component `ComboPricingService::cascadeDeactivate()`/`cascadeReactivate()` every other deactivation/reactivation path already calls. A supplier-wide (or game-scoped) bulk deactivate could take every component of a combo offline while the combo itself stayed `is_active=true`, listed and sellable, with no leg able to fulfill.

**Checked before deciding whether to fix now or park it:**
- **Real usage: twice ever**, both against Gamevion (`reason` text: "Test Deactivate" 2026-09-02, 43 packages; "Not used gamevion yet" 2026-09-17, 34 packages) — Gamevion has zero combos (all 49 system-wide combos are Digiflazz-only, since a combo's components must share one supplier). No real incident has ever occurred.
- **Live check: zero combos currently broken** (`is_active=true` with an inactive component) — the gap is real but has never fired against Digiflazz, the one supplier that actually has combos.
- **Real scale matters for the fix's own shape**: Digiflazz has 1,088 active packages today. A naive fix (loop every targeted package, call the existing per-component `cascadeDeactivate()`/`cascadeReactivate()`) would turn this endpoint's 2 existing bulk SQL statements into 1,000+ synchronous queries in one admin HTTP request — a real timeout risk for a plain "Deactivate All," not a safe drop-in.
- **Decision on process**: fixed now rather than parked (real, if rare, money-adjacent correctness gap — a customer could buy an unfulfillable combo), but not put through a full `/mattpocock-skills:grilling` session — the one open design question (silent cascade vs. an acknowledge-prompt, mirroring decision 13's single-package UX) is already answered by decision 13's own existing precedent (Price Sync's automated cascade is silent, surfaced only in that run's own report) and by this being conceptually the same kind of wide, already-deliberate action, not a narrow single-package toggle. Founder agreed with matching that precedent.

**Decision:**

11. **Two new batch methods on `ComboPricingService`** — `cascadeDeactivateForComponents()`/`cascadeReactivateForComponents()`, taking a `Collection` of component package ids rather than one `Package`. Each finds affected combos with **one** query against the `package_components` pivot table directly (not `whereHas('components', ...)` — see the note below), then bulk-writes only that small candidate set (bounded by total combo count, 49 today — never by the component count). Distinct from decisions 13/ADR-094's addendum's per-component `cascadeDeactivate()`/`cascadeReactivate()`, which stay unchanged for their own already-wired single-package call sites.
12. **`updatePackagesStatus()` wraps its reactivate branch in a `DB::transaction()` too** (previously only the deactivate branch was) and calls the matching batch cascade method inside each transaction, using the already-known `$packageIds`/`$gameIds` it collects for its own audit-log/cache-forgetting needs. A combo's own game is always one of `$gameIds` already (its components are enforced to share its game at creation — `StoreComboPackageRequest`), so no separate cache-forget path is needed for the cascaded combos.
13. **Response gains `updated_combos`** (both branches) — the number of combos cascaded, for admin visibility without a second lookup.
14. **Found and fixed as a direct byproduct, not scope creep**: the reactivate branch had no cache-forgetting at all before this addendum (only the deactivate branch called `GameController::forgetPackagesCache()`/`forgetIndexCache()`) — computing `$gameIds` correctly for the new cascade call meant this branch could no longer skip it either.

**A real bug found and fixed before merge, not shipped**: the first implementation used `Package::where('is_combo', true)->whereHas('components', fn ($q) => $q->whereIn('packages.id', $ids))`. For a self-referencing `belongsToMany` (`Package` through `package_components` onto itself), Laravel aliases the inner joined table (`laravel_reserved_0`) to disambiguate it from the outer query — a closure filtering on the literal `packages.id` string silently matches the **outer** (combo) side instead of the joined component row, so the whole cascade silently found nothing. Caught by the new tests themselves (`updated_combos` came back `0` instead of `1`), not a manual review. Fixed by querying `package_components` directly instead of `whereHas`. The existing per-component `cascadeDeactivate()`/`cascadeReactivate()` (ADR-094) were never at risk — they call `partOfCombos()`/`components()` directly as the query root, not nested inside a `whereHas` closure, so the alias never appears.

**Consequence to track:**
- `updated_combos` in the API response is new API surface for the admin frontend to optionally display — not wired into the Supplier Management UI's own confirm/toast copy in this addendum, left for whoever next touches that screen.
- Same as ADR-094's own addendum: `reactivation_stability_syncs`-style tuning has no equivalent here, since this path is entirely admin-triggered, not automated.
