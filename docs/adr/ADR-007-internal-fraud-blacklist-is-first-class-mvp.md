# ADR-007 (D7): Internal fraud blacklist is first-class MVP

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-07-23

**Decision:** The system maintains its own internal blacklist of player IDs and/or customer contacts, checked at order creation — independent of whatever blacklist (if any) a given supplier offers.

**Rationale:** Observed in a real competitor's API integration (a `check-blacklist` endpoint). The platform should not depend on a supplier providing this protection — it must be built and owned internally, populated from the platform's own chargeback/fraud history.

**Addendum — shipped, 2026-07-29 (new session, ~6 weeks after acceptance — genuinely the longest-outstanding accepted decision in this log, not blocked technically, just never picked as the priority until this session):** FRAUD-1..4 built end to end.

1. **Schema — two tables, not one.** `blacklist_entries` (`type`: `player_id`/`email`/`phone` via a real `BlacklistEntryType` enum, `value`, `reason` — required, matches `ledger_entries.reason`'s discipline for `adjustment` rows — `created_by`, `is_active`). `is_active` is a soft toggle, **never a hard delete** — FRAUD-3's "view history of orders blocked by a given entry" needs the entry to keep existing after an admin removes it, or `blacklist_hits` rows would point at nothing. `blacklist_hits` is the second table: one insert-only row per blocked attempt (`player_id`/`customer_email`/`customer_phone` as actually submitted, `ip`), same discipline as `price_change_logs`/`deactivation_logs`/`order_resend_attempts`. A blocked attempt never creates an `Order` (FRAUD-2 rejects before payment/supplier submission), so `blacklist_hits` is the *only* record it ever happened — there is no Order row to join against for this history.
2. **`App\Services\Fraud\BlacklistService::check()`** matches any active entry against non-null `player_id`/`email`/`phone` in one query (an `orWhere` per non-null field, each scoped to its own `type`). Wired into `CheckoutController::assertNotBlacklisted()`, called right after player-ID validation and before Reseller/payment-gateway resolution — matches `prd.md` §7.1 step 5's ordering exactly.
3. **FRAUD-4 — a genuinely distinct mechanism from ADR-014's general `throttle:10,1` on `/api/checkout`, not a stricter number on the same one.** `App\Services\Fraud\CheckoutVelocityGuard` (cache-backed, same `database`-store-visible-across-processes reasoning as `App\Services\CircuitBreaker\CircuitBreaker`) counts only **blacklist-triggered rejections** per IP, not every request — the general throttle already covers ordinary request-volume abuse; this counts the specific signal of someone probing with different player IDs/emails/phones hoping one isn't blocked. Default: 3 blacklist hits / 10 minutes (`config/fraud.php`, `FRAUD_VELOCITY_THRESHOLD`/`FRAUD_VELOCITY_WINDOW_MINUTES`) trips it for that IP regardless of whether the *next* attempt itself matches an entry.
4. **Rejection message is deliberately generic and identical either way** ("This order cannot be processed.") whether the block came from a blacklist match or a tripped velocity guard — never reveals *which*, so a real fraudster can't use the response itself to distinguish "wrong value, try a different one" from "you're rate-limited, wait it out."
5. **Admin screen, `/admin/blacklist`** (`Admin\BlacklistController`: `index`/`store`/`show`/`deactivate`) — stat cards (Active/Total), entry table with a clickable blocked-attempt count opening a history modal (`BlacklistHitsModal`, FRAUD-3's own requirement), add-entry modal with a type/value/reason form. Mirrors the Vouchers screen's existing structure (stats block + table + create modal) rather than inventing a new admin-panel pattern.

44 new backend tests (`BlacklistServiceTest` 6, `CheckoutVelocityGuardTest` 4, `BlacklistControllerTest` 9, `CheckoutControllerTest` +5 blacklist/velocity cases), full suite 440 green, 4 concurrency tests unaffected. Verified against real MySQL (`migrate:fresh`) as part of the same session's index-length lesson (ADR-019's newest addendum) — no repeat of that bug here. `npx tsc --noEmit`/`next build` clean; `npm run lint` shows the same pre-existing `react-hooks/set-state-in-effect` warnings the rest of the admin panel already has (confirmed by running lint against the unmodified `VouchersPage` first, same rule fires there too) — not a regression introduced by this feature, and not fixed here since it's a pre-existing, repo-wide pattern this session didn't scope to touch.
