# ADR-067: Digiflazz adapter completion — buyer-area scoping, dual product status, per-supplier Product Manager grouping (built 2026-09-02)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-09-02, grilled with the founder this session via `/mattpocock-skills:grilling` (20 questions over three rounds); **built the same session** (`feature/digiflazz-adapter-completion`, backend 1179/1179 fast + admin tsc/lint/build green — see PRD §14). **Modifies `ADR-030` decision 2** (the "games only" filter mechanism), **extends `ADR-031`'s Product Manager** to be supplier-aware, and builds on `ADR-034`'s denomination dedup. The `DigiflazzWebhookController` half of `ADR-032` decision 4 stays deferred to a future ADR.

**Context:**
- `ADR-030` built `DigiflazzAdapter` (buyer role, prepaid games). It has never completed a run against a live account — the account was outbound-IP-whitelist-blocked at build time (`rc: 45`). As of 2026-09-02 a real `Supplier` row exists, a dev-key smoke test passed via `/middleware/developer-tools`, and the founder then switched to a production key — but at that moment `listProducts()` still returned the Digiflazz **dev test SKUs**, so it was unconfirmed whether the production key actually persisted (the Supplier edit form masks secret fields and merges on save — `ADR-046` decision 3 — a plausible drop point). *(Resolved the same session — decision 11's pre-build check passed; see the Build note below.)*
- Full re-read of `developer.digiflazz.com` this session established: **`/v1/price-list` `cmd: prepaid` returns only the products the buyer has configured in their buyer area** (*"Daftar harga akan memberikan info mengenai daftar harga yang telah Anda setting"*), **not** Digiflazz's entire catalog. Each item carries `product_name`, `category`, `brand`, `type`, `seller_name`, `price`, `buyer_sku_code`, `buyer_product_status`, `seller_product_status`, `stock`, `unlimited_stock`, `multi`, `start_cut_off`/`end_cut_off`, `desc`.
- `DigiflazzAdapter::normalizeProduct()` currently keeps only `category` → `SupplierCatalogItem.category`, and maps `buyer_product_status` **alone** → `active`/`inactive`. It discards `brand`, `type`, `seller_product_status`, and `stock`.
- The Product Manager (`/middleware/product-manager`, `ADR-031` era) groups `supplier_products` by `category_raw`. For Digiflazz, `category` is the literal string `"Games"` for **every** game — so every Digiflazz game would collapse into a single `"Games"` group, making the "link a whole category group to one Game" model unusable. For Digiflazz the game identity is `brand` (`"MOBILE LEGENDS"`, `"FREE FIRE"`, …). Gamevion's `category` is edition-level (~22 groups over 316 items), which is why the model works there.
- `supplier_products` has no `brand`/`type` column. `ProductSyncService::applyCategoryWhitelist()` reads `api_config['category_whitelist']` but **no `SupplierConfigSchema` entry or admin UI ever sets it** — a dead path today.
- `SupplierProductController::categories()` does **not** scope by `supplier_id` — it merges every supplier's rows into one grouped list. With a second supplier whose grouping key differs, an unscoped merged list is incoherent.
- `CheckSupplierDeliveryJob` (`ADR-032` decision 5 / `ADR-026`) already resolves the adapter per-order via `order.supplier->slug` and calls `checkStatus()`, and `ReconcilePendingDeliveriesCommand::checkStalePending()` already reads `pending_stale_minutes` per-supplier — so **polling reconcile already covers the `Pending` path for Digiflazz**, webhook or not.

**Decision (each point grilled this session):**

1. **Buyer-area curation is the primary product filter, not our code.** The founder curates the game catalog at `member.digiflazz.com/buyer-area/product` (pick a seller per product, toggle it on); `price-list` then returns only those. Our system adds a *safety net*, not a primary filter.

2. **`category_whitelist` becomes a real, configurable field — reworks `ADR-030` decision 2's mechanism.** `ProductSyncService::applyCategoryWhitelist()` already exists; this ADR makes it reachable. Add `category_whitelist` to `SupplierConfigSchema` (split into `REQUIRED` vs a new `OPTIONAL` set so it is excluded from the "fully configured" gate) classified as a new `list` type, edited in the Supplier Management form (`ADR-046`) as a comma-separated string, `SupplierConfigSchema::normalizeConfig()` trims it to a `string[]` on save (a non-string/non-array value fails safe to `[]` — never "filter everything out"). Empty/absent = no filtering (unchanged behaviour). The `digiflazz` row is set to `["Games"]` by the founder. The filter stays in the sync layer (business policy), never in the adapter (protocol) — `ADR-030` decision 2's own reasoning, unchanged.

   **Pruning (addendum):** `ProductSyncService::sync()` now also *deletes* any `supplier_products` row a completed sync did not return — a category the whitelist now excludes, or a product removed from the Digiflazz buyer area — so a stale group stops lingering in Product Manager forever (`updateOrCreate` alone never prunes). Two guards: a **promoted** row is always kept (its Package is real inventory, and `PackagePriceSyncService`, running right after in the same job, needs the row's stale `last_synced_at` to deactivate the Package the proper soft, logged way); and **nothing** is pruned when the run returned zero items (a genuinely empty catalog or a whitelist typo — deleting every unpromoted row in either case is not worth the blast radius). Surfaced as `ProductSyncResult::$pruned` / `PriceSyncRun.stats.catalog_pruned`.

3. **"Active" requires `buyer_product_status` AND `seller_product_status` both true.** `DigiflazzAdapter::normalizeProduct()` maps `status = 'active'` only when both booleans are true, else `'inactive'`. A seller disabling a product makes it dead even if the buyer left it on. The sync-all-then-Stage-2-deactivate pattern (`PackagePriceSyncService`) is unchanged — only the definition of the raw `active` string tightens.

4. **Product Manager grouping is driven by a computed `group_label` column, set by the adapter.** New `supplier_products.group_label` (nullable then backfilled — see Consequences). `SupplierCatalogItem` gains `groupLabel` and `type`. **Each adapter sets `groupLabel` from its own catalog shape** — `DigiflazzAdapter` from `brand`, `GamevionAdapter` from `category` (its current `category_raw` value). `ProductSyncService` writes `$item->groupLabel` / `$item->type` with **no per-supplier branching**; the Product Manager controller and UI group by `(supplier_id, group_label)` uniformly with no supplier-specific code. This is the deep-module placement — AGENTS.md: adapters absorb supplier-specifics.

5. **Columns added: `group_label` + `type` only.** No separate `brand` column — for Digiflazz `brand` *is* `group_label`; for Gamevion it would always be null. `type` is stored raw (nullable) for a future checkout need (Digiflazz membership-tier games) but is **not** used for grouping.

6. **Product Manager becomes supplier-aware: one list, a Supplier column, an optional supplier filter — not hard per-supplier tabs.** The real workflow is linking both suppliers' equivalent group (Gamevion `"Mobile Legends"` and Digiflazz `"MOBILE LEGENDS"`) to the **same** Game and setting `denomination` for best-price dedup (`ADR-034`); hard tabs hide that side-by-side view. `categories()` groups by `(supplier_id, group_label)` and returns `supplier` on each row. **The link contract changes from `category_raw` to `supplier_id` + `group_label`**: `LinkSupplierProductCategoryRequest`, `linkSupplierProductCategory()` (`admin/src/lib/supplier-products.ts`), and `LinkCategoryModal` all take `supplier_id` (from the selected row); the group re-stamp becomes `->where('supplier_id', $s)->where('group_label', $l)->update([...])`.

7. **Discarded operational metadata stays discarded:** `stock`, `unlimited_stock`, `start_cut_off`/`end_cut_off`, `multi`. Games are effectively unlimited-stock; an order during a cut-off window or at zero stock returns `Gagal`, which the existing failure → store-credit-voucher path (`ADR-004`) already handles. Promote is **not** gated on stock.

8. **Cross-supplier group-label collisions are accepted, not normalised.** `"Mobile Legends"` (Gamevion) and `"MOBILE LEGENDS"` (Digiflazz) remain two rows; the founder links both to the same Game and `denomination` (`ADR-034`) resolves which package the storefront shows. Name normalisation is out of scope.

9. **`ADR-032`'s operational-guard config keys (`status_check_min_interval`, `max_reconcile_age_days`, `pending_stale_minutes`) are NOT added to the Supplier form in this pass** — they have `config()` defaults and don't block go-live. Backlog if tuning is ever needed.

10. **Webhook stays deferred; polling reconcile is the `Pending`-path mechanism.** `app:digiflazz-smoke-test` verifies the four official Digiflazz prepaid test cases: `087800001230` → `Sukses` and `087800001232` → `Gagal` end-to-end; `087800001233` and `087800001234` are verified as far as the `Pending` state **plus one reconcile poll** (`checkStatus` re-submit), with callback-completion left for the future `DigiflazzWebhookController` ADR.

11. **Pre-build live verification (blocks the smoke test, done before touching code):** confirm the production key actually saved by calling `checkBalance()` in `tinker` and seeing a real Rupiah balance (not the dev fake `deposit`); and confirm the production outbound IP is whitelisted at Digiflazz (`rc: 45` was the `ADR-030` blocker). If `checkBalance()` still shows the dev fake, the masked-field merge (`ADR-046` decision 3) is dropping the key — fix that first.

**Rationale:** The adapter was built protocol-faithful but never finished against reality; the two real gaps — a catalog filter that assumed one flat category, and a Product Manager that assumed one supplier — only surface now that a second supplier is being connected. Putting `group_label` on the adapter and `category_whitelist` in the sync layer keeps every supplier-specific fact in exactly one place and leaves the controller/UI supplier-agnostic, matching the ADAPT-1/3 and deep-module reasoning the codebase already follows. Deferring the webhook is safe because `ADR-032` decision 5's poll backup already resolves the adapter per-order.

**Consequence to track:**
- `supplier_products.group_label` is `NOT NULL` after the backfill migration (existing rows: `group_label = category_raw`, or `''` when `category_raw` is null — mirrors today's grouping fallback). The migration must also run as **plain `php artisan migrate`** against the local dev DB (AGENTS.md gotcha — the test suites never touch it); never `migrate:fresh`.
- `type` is null for every existing row and for all Gamevion rows until `GamevionAdapter` is taught to populate it (no `type` concept there today) — acceptable; it's a forward-looking column.
- The link-contract change (`category_raw` → `supplier_id` + `group_label`) is a **breaking change** to `POST /api/middleware/supplier-products/categories/link` — the admin frontend ships in the same PR.
- `category_whitelist` parsing: a text field split on commas, trimmed, empty entries dropped. A malformed value must **fail safe to "no filter"**, never to "filter everything out".
- The sync prune is a **hard delete** of raw un-promoted rows — deliberate (a raw mirror row is disposable, per the `supplier_products` migration's own comment), but it means a category the founder briefly whitelists then removes will re-appear only on the next sync, and its `game_id` link is gone. Re-linking is the recovery, same as any other group.
- Raw supplier price is still stored **only** as converted MYR sen (`price_sen`) — the original IDR amount is not persisted. Showing "Rp 20,000 = RM 4.56" in Product Manager for a sanity check would need `raw_price` + `raw_currency` columns on `supplier_products` — a tracked backlog item, not this ADR.
- `SupplierConfigSchema`'s `digiflazz` definition and the frontend `SUPPLIER_FIELD_DEFINITIONS` (`admin/src/lib/suppliers.ts`) must **both** gain `category_whitelist` — they're hand-synced (`ADR-046` decision 3).
- `checkBalance()` prod-vs-dev is the only pre-flight signal that the prod key saved. On this build the merge was **not** dropping the key (see the Build note) — but the masked-field merge (`ADR-046` decision 3) is still the kind of path a key rotation could silently no-op through, for Digiflazz or Gamevion; worth a follow-up look, not fixed here.
- Once `brand`-based grouping is live, a Digiflazz re-sync that adds a new `brand` to an already-linked Game's group leaves the new rows unlinked until someone re-links the group — the same "known, accepted gap" `ADR-031` already documents for `category_raw`.
- PRD §14 build-log + §15 status update owed on ship. A separate ADR for `DigiflazzWebhookController` (`ADR-032` decision 4, still unbuilt) remains outstanding.

**Region addendum — 2026-09-02, same day, founder caught it reviewing the Digiflazz buyer-area UI (`feature/digiflazz-region-grouping`).** Decision 4 grouped Digiflazz by `brand` alone, which collapses every region of a game — MLBB Malaysia / Indonesia / Global / Umum — into one Product Manager group. Digiflazz's own buyer area separates them: `category` = "Games", `brand` = "MOBILE LEGENDS", **`type` = the region** ("Umum" / "Malaysia" / "Indonesia" / "Global" / "Filipina" / …) — the region tabs in its UI, and a real field in the price-list response we already store (decision 5's `type` column). Gamevion already keeps regions apart (`"Mobile Legends (Indonesia)"` is its own `category`), so `brand` alone was the wrong granularity for parity. **Fix:** `DigiflazzAdapter` now sets `groupLabel = "{brand} — {type}"` (falling back to bare `brand` when a game has no `type`). `type` is still carried raw in its own column. No schema change — `group_label` just gets a more specific value on the next sync; `updateOrCreate` keys on `external_ref` so existing rows update in place (any `game_id` link already made survives and simply re-groups under the region label). GamevionAdapter is unchanged (its `category` already carries the region).
