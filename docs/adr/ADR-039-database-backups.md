# ADR-039: Database backups — app-level, host-agnostic backup/restore mechanism (BAK-1..5) (design 2026-08-26; built 2026-08-26)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled 2026-08-26, built same day (next session, same branch `feature/backups-adr`). All 11 decisions implemented and live-verified (browser, not just `php artisan test`) against the real local dev DB (sqlite).

**Build addendum, 2026-08-26:** `spatie/laravel-backup` (v10.3.2) installed and configured per the 11 decisions below — `config/backup.php` (files excluded, database-only; disk from `BACKUP_DISK`; AES-256 encryption via `BACKUP_ARCHIVE_PASSWORD`; 7d/4w/6m retention via `BACKUP_KEEP_*` env vars; own notification channels disabled in favor of a custom listener); `config/database.php`'s `mysql`/`sqlite` connections both get `dump.exclude_tables = ['player_validations']`; new `backup_runs` table + `BackupRun` model (one row per run, mirrors `price_sync_runs`); `RunDatabaseBackupJob` (queue `backups`, same "thin trigger, real work off-thread" shape as `SyncSupplierPricesJob`) does `backup:run --only-db` → locates the archive → `BackupRestoreTester` (driver-aware: sqlite locally via a real `sqlite3` subprocess restore + `migrate:status`, mysql via `mysql`/`mysqldump` CLI against a throwaway database — decision 8) → records the outcome; `BackupFailureAlerter` (`Log::critical` + email every active `admin_users` row) is wired to spatie's raw `BackupHasFailed`/`CleanupHasFailed` events (`AppServiceProvider::boot()`) and called directly for the restore-test-failed case, which isn't a spatie event at all; `routes/console.php` schedules `app:run-backup --triggered-by=system` daily at 02:00 and `backup:clean` at 03:00 (inert-until-real-cron, same pattern as Price Sync); `Middleware\BackupController` (`/api/middleware/backups`, `super_admin`-only) — index/stats/store/show/download/destroy, **no restore endpoint** (decision 5). 10 feature tests (`BackupControllerTest`) + 4 unit tests (`BackupRestoreTesterTest`, proving the tester actually distinguishes a good dump from one with a missing table or a missing migration — not just that it runs) — full suite 797/797 green (up from 783/783). Admin UI: `/middleware/backups`, PrimeReact-Tailwind exclusively (`Button`/`Tag`/`DataTable`/`Dialog`) per ADR-038 decision 3/6 — see that ADR's own build addendum for the PrimeUI license gotcha this surfaced.

**Real gaps this build closed that the design session didn't anticipate:**
- `backend/composer.json`'s `dev` script (`queue:listen --queue=orders,price-sync`) didn't include the new `backups` queue — `RunDatabaseBackupJob` would have sat `queued` forever under local dev, the exact "stuck job, no queue worker" class of gotcha this project has hit before (Price Sync, 2026-07-27). Fixed: `--queue=orders,price-sync,backups`. `docker-compose.prod.yml` gained its own `queue-worker-backups` service, matching `queue-worker-orders`/`queue-worker-price-sync`'s existing per-queue isolation pattern (ADR-020 decision #5's rationale — a slow dump+restore-test cycle must never block, or be blocked by, an urgent order job).
- A first attempt at the session guard on the new Backups page used `useSyncExternalStore` (intended as decision 8's real fix, ahead of that migration) instead of the `useEffect`+`setState` pattern every other `/middleware/*` screen uses. It looked correct and fixed the targeted lint warning, but live-browser testing found it left a genuinely logged-in admin bounced to `/login` on a hard page load/refresh (only a client-side `<Link>` navigation worked) — `getServerSnapshot` returning `null` never got corrected by a real re-render outside of an actual SSR-hydration-mismatch path, which this fully-client-gated page doesn't hit. Reverted to the proven `useEffect`+`setState` pattern (verified working via `/middleware/price-sync`) rather than ship an unproven fix on an auth gate; decision 8's `useClientSession()` hook is still unbuilt and now flagged with this specific failure mode for whoever attempts it next.

**Context:** `docs/prd.md` §15 lists Backups (BAK-1..5) as `⬜ Not started`, backend and Admin UI alike. Confirmed this session via a real filesystem/`composer.json` search: zero backup mechanism exists anywhere in `backend/` — no package, no script, nothing. This is a genuinely new architecture area for a money-critical system (`orders`, `ledger_entries`, `withdrawals`, `vouchers` all hold real value and real customer PII, per `backend/CLAUDE.md`'s own stated invariants).

`ADR-020` already decided production's database shape — DigitalOcean Managed MySQL, which itself provides automated backups and point-in-time recovery as part of the managed service. That could make this ADR look redundant, but it isn't: `ADR-037` separately decided staging runs a **containerized** MySQL on the shared droplet, with no such managed backup, and today — pre-launch, host not yet provisioned — even local dev has nothing. This ADR is scoped as an **application-level, host-agnostic feature** (the Admin UI tracker lists it with its own screen, not as pure ops-infra), not a restatement of `ADR-020`'s infra-level snapshot. `ADR-020` decision #1's separate Droplet Backups add-on (whole-disk snapshot) remains complementary and untouched by this ADR — one recovers the whole box, this one recovers just the database from an independent, queryable, host-agnostic source.

One real tension surfaced while grilling scope: `ADR-021`'s `PrunePlayerValidationsCommand` deletes `player_validations` rows after 7 days specifically for PII-retention reasons. A raw full-DB backup that retains those rows for the backup's own retention window would silently undo that policy's intent.

Deployment/hosting provisioning (`ADR-020`/`ADR-037`'s territory) and payment-gateway work are explicitly out of scope for this ADR — it decides backup mechanism and policy, not where a bucket physically lives.

**Decision:**

1. **Scope: a full database dump, every table, except `player_validations`.** A partial (money-tables-only) backup can't reconstruct a working system — `games`/`packages`/`admin_users`/settings are all needed for the app to function after a restore. `player_validations` is excluded by name specifically to preserve `ADR-021`'s 7-day PII-retention guarantee; nothing else is excluded.
2. **Trigger: both scheduled and manual.** A scheduled daily run follows this project's established `Schedule::call()` pattern (`routes/console.php`), inert until a real OS cron exists on a deployed host — same as Price Sync/payment-reconciliation/player-validation-pruning. A manual "Backup Now" action is also exposed (Admin UI, decision 9) for on-demand snapshots before a risky operation (a big Price Sync, a migration).
3. **Storage: the Laravel `Storage` filesystem-disk abstraction, local disk by default.** Mirrors Image Gallery's (`IMG-1/2`) own established precedent exactly — a later swap to a real S3-compatible bucket (Spaces, once host decisions are live) costs a disk-config change, not a rewrite. This ADR does not choose or provision that literal bucket.
4. **Backup archives are encrypted at rest (password-protected).** The dump contains real customer PII (email, phone) and real money/order history — matches this project's own security-conscious history (the `foundation-security.md` hardening pass).
5. **Restore is CLI/artisan-only, never a self-service Admin UI action.** A bad restore can silently roll back real ledger/order/withdrawal state to a stale point — a more destructive single action than anything else in this system, including a withdrawal. Deliberate friction (SSH/server access required) guards against an accidental one-click catastrophe; the Admin UI (decision 9) only lists and downloads backups, it never restores one.
6. **Retention: 7 daily + 4 weekly + 6 monthly, auto-thinning, config-adjustable.** Matches this project's own established pattern for a tunable operational threshold (e.g. `WITHDRAWAL_MAKER_CHECKER_THRESHOLD_SEN`) rather than a hardcoded constant. Sized for today's pre-launch scale (~125 orders/day per `ADR-020`'s own capacity analysis); revisit only if real volume or storage cost make it a real trade-off.
7. **Failure alerting: `Log::critical()` plus an email to admin users on any failed backup run — not gated on `SET-9`'s Telegram sender, which isn't built yet.** A backup job that fails silently for weeks is the same class of gap `ADR-020`'s own addendum already found for outage detection generally; this doesn't wait on an unrelated, unbuilt feature to close it. Reuse the Telegram path later once `SET-9` itself ships — not a blocker here.
8. **Every backup run is restore-tested automatically: restore into a throwaway database, then a sanity check (row count > 0, `migrate:status` clean).** An untested backup — one never proven to actually restore — is worth nothing; matches this project's own established "docs/assumptions alone aren't enough" discipline (the Xendit customer-object gotcha, the Gamevion `telp`-format bug, the concurrency suite's real-subprocess proofs). This restore-test result is itself recorded per run, not just pass/fail logged and discarded.
9. **Admin UI: `/middleware/backups` — a new ops-tooling screen, same tier as Price Sync/Sandbox/Validators/Product Manager, not `/admin/*`'s business-data-CRUD pattern.** One unified history table covering every run regardless of trigger (scheduled or manual), showing status (success/failed), size, timestamp, and the decision 8 restore-test result — a failed run is visible here directly, not only in the decision 7 email. A "Backup Now" button triggers decision 2's manual path. No restore action anywhere in this screen (decision 5).
10. **Access: `admin.role:super_admin` only** — same tier as Settings/Price Sync/SEO, all platform-wide config/ops screens, no reseller self-service portal yet (matches this project's own repeated reasoning for that tier).
11. **Implementation tool: `spatie/laravel-backup`.** The de facto standard Laravel package for exactly this shape — dump + archive + any Laravel filesystem disk + scheduled cleanup + failure notifications, all built in. Not itself a grilled trade-off (no real competing alternative was considered): the design decisions above are what this ADR settles; the package is simply the vehicle.

**Rationale:** Every decision above treats backups as a first-class, host-agnostic product feature rather than an artifact of whatever hosting `ADR-020`/`ADR-037` eventually finish provisioning — the right call given this system has real money-critical data today, in local dev, well before any droplet exists. The restore/UI split (decision 5 vs. decision 9) deliberately trades convenience for safety on the one action in this whole system with the largest possible blast radius; every other decision (scope, storage, retention, alerting, testing) follows this project's own already-established patterns (Image Gallery's disk abstraction, the `Schedule::call()` inert-until-cron convention, config-tunable thresholds, real-not-assumed verification) rather than inventing new ones.

**Incident + fix addendum, 2026-09-14 (`fix/backup-restore-test-gtid-privilege` → `staging`).** Founder checked `/middleware/backups` live and found every run since production go-live (2026-09-02) — 14/14 — recorded `status=failed`, `restore_test_passed=false`. Two compounding findings, root-caused against real production via SSH, not guessed:

1. **Restore-test itself, real root cause:** the dump archive was fine every time (real file, correct size) — only the automated restore-test step failed. `mysqldump` against the DigitalOcean Managed MySQL connection emits `SET @@SESSION.SQL_LOG_BIN=0` + `SET @@GLOBAL.GTID_PURGED=...` near the top of every dump whenever the source server has GTID enabled (which DO's managed offering does) and `spatie/db-dumper`'s `setGtidPurged` isn't explicitly turned off (default `'AUTO'`). Both statements need SUPER/SESSION_VARIABLES_ADMIN, a privilege DigitalOcean does not grant on managed-database users — so `BackupRestoreTester::testMysql()`'s plain `mysql ... < dump.sql` replay has failed on line 13 of every single production dump, unconditionally, since the day production went live. Confirms this ADR's own decision 8 flag above ("has never run against a real MySQL server") exactly. **Fix:** `backend/config/database.php`'s `mysql` connection gained `'dump' => ['mysql_gtid_purged' => 'OFF']` — `DbDumperFactory` already reads this key and passes `--set-gtid-purged=OFF` to `mysqldump`, which drops both lines from the dump entirely (the actual table data is unaffected). One-line config fix, no new dependency — the seam was already there, just never pointed away from the default.
2. **Why no one saw 12 days of failure alerts:** decision 7's "email every admin" was firing every time (`BackupFailureAlerter::alert()` was called correctly on every failed run) but landed nowhere — `config('mail.default')` is `log` in production (`MAIL_MAILER` was never provisioned), so Laravel's native `Mail::` facade was silently writing every alert to the log file instead of sending it. Blast radius check (repo-wide grep) confirmed this affects only `BackupFailedMail` — the only other real email path, Membership OTP, goes through `PlunkMailer` (a separate HTTP-based vendor, ADR-027's 2026-08-29 addendum), so customer-facing email was never affected. **Fix:** `BackupFailureAlerter` now sends through `PlunkMailer::send()` (already proven live) instead of `Mail::`, looping per active admin so one bad address can't swallow the rest. The now-fully-dead `App\Mail\BackupFailedMail` Mailable and its blade view were deleted (confirmed, repo-wide grep, this alerter was their only caller).
- Tests: **+3** new (`BackupFailureAlerterTest`: every active admin gets a real Plunk send attempt, an inactive admin doesn't, one recipient's send failure doesn't block the others, the critical log line always fires). Full backend suite **1846/1846**. Pint clean.

### 2026-10-14 addendum — one restore path, real verification, killed runs close themselves (PRD §16 item 97)

**Context.** Every nightly run from 2026-10-01 (#31–#44) was `failed`: `ERROR 1044 Access denied for user 'pekangame_app' to database 'defaultdb_restore_test_…'`. ADR-117's switch to `pekangame_app` (2026-09-30) granted only `defaultdb.*`, and its live check ran `backup:run`, which skips the restore test. Under that error sat three more faults, all found against production and real MySQL, not guessed:

1. **Killed runs.** Runs #26–#30 (2026-09-26..30) died at the generic 60s worker timeout (`TimeoutExceededException` ×5 in `failed_jobs`; successful runs had already climbed from 38s to 50s). The job had no `failed()`, so each row stayed `running`, nobody was alerted, and the decrypted plaintext dump stayed in `backup-temp` (removed by hand 2026-10-08).
2. **View definers.** Two views (`llm_report_catalog`, `llm_report_membership_fees`) are owned by `doadmin` (made by 2026-09-12 migrations). Restoring a dump of them as any user without `SET_ANY_DEFINER` fails: `ERROR 1227`, reproduced on MySQL 8.4 as a non-super user. Same class as the 2026-09-14 GTID fault.
3. **Weak verification.** "Tables exist + `migrations` table complete" passes a dump cut short after the `migrations` table, with `orders`, `vouchers` and the rest missing. Proven locally: spatie's sqlite dumper drops every table past roughly the 50th (`sqlite3` dot-command argument limit when `exclude_tables` is set), and the old check would have passed it. Sqlite is local-only; the MySQL dumper uses `--ignore-table` and is not affected.

Also: the repo had no restore command at all, although decision 5 says restore is CLI-only. So the nightly test proved a path nobody would use in a real restore.

**Decision.**

1. **One restore path, `BackupRestorer`.** The nightly test (`BackupRestoreTester`) and a new operator command, `php artisan app:restore-backup {--run=|--path=|--file=} --database=`, both download, decrypt, extract, restore and verify through it. Each nightly pass therefore proves the disaster-restore path.
2. **Restore only into an existing, empty database.** The restorer refuses a target that has any table. That covers a fresh cluster (empty `defaultdb`) and a side-by-side recovery, and nothing can write over live data (decision 5's friction, kept by state, not by a flag or a name).
3. **`DEFINER` clauses are dropped on restore,** so the restoring user owns the views. Lines starting `INSERT ` are passed through untouched, so customer data is never rewritten.
4. **The DB password stays out of argv.** The `mysql` client reads a `0600` `--defaults-extra-file` that is deleted afterwards.
5. **Verification is real.** Every live table (minus the dump's `exclude_tables`) must come back, and every migration the codebase knows must be recorded as run. The migration check is read directly, not scraped from `migrate:status` output. `restore_test_details` now holds `table_count`, `missing_tables`, `migrations_ran` and `pending_migrations`.
6. **Timeouts sized for batch jobs.** `supervisor-backups` and `supervisor-price-sync` run on `redis-long` with a 300s timeout (retry_after 330s; producers unchanged, same Redis keys). `HorizonQueueCoverageTest` already guards timeout < retry_after.
7. **Killed runs close themselves.** `RunDatabaseBackupJob::failed()` marks the row `failed` and alerts. Each run first deletes `restore-extract-*` folders left by a killed run. This is safe only because `supervisor-backups` runs one job at a time; the operator command uses its own `restore-cli-` prefix, which the job never touches. The 5 stuck rows were closed by migration `2026_10_14_100000_fail_stuck_backup_runs`.
8. **Schedule moved 02:00 → 02:07,** off the minute that price sync and the `*/15` jobs start on, because the restore test now writes to the same database server.

**Rejected.**
- Restoring into a local MySQL on the app box. It would avoid the grant, but it would not test the managed server's behaviour (which is how the GTID fault was found). It also re-adds infra and RAM on the 4 GB box OpenWA shares.
- Recreating the two views as `pekangame_app`. That fixes today's dump, but the problem returns with the next user change.
- Excluding Pulse table data from the dump. MySQL 8.4's `mysqldump` has no `--ignore-table-data`, and excluding the tables drops their structure.

**Consequence to track.**
- 300s is a ceiling. A breach now fails loudly through `failed()`. `backup_runs` keeps each run's duration; revisit the timeout when a run passes ~150s.
- The grant in ADR-117's 2026-10-14 addendum must be in place before the first run on this code, or the nightly run keeps failing at "could not create".
- Local sqlite backups stay incomplete (spatie + `sqlite3` argument limit). The dev DB is not backed up anyway; the restore test now reports this truthfully.

### 2026-10-15 addendum — fixed throwaway database name

The MySQL restore test now always uses `<db>_restore_test` (prod: `defaultdb_restore_test`), not `<db>_restore_test_<time>`.

**Why:** prod's `partial_revokes = 1` makes a wildcard GRANT literal (ADR-117 2026-10-15 addendum), so the app user can only be granted one exact name.

**How it stays safe:**
- Each run drops that database before creating it, so a run killed mid-restore can't block the next one.
- Only one backup job runs at a time (`supervisor-backups`, maxProcesses 1).
- The operator's `app:restore-backup` targets a database the operator names, never this one.
