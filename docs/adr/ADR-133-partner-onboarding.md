# ADR-133: Partner onboarding — a two-stage public application with KYC for resellers, and a computed readiness checklist in the portal for every partner

> **Standing (2026-11-01):** In force. Closes PRD §16 items 13 (self-serve reseller signup) and 146 (onboarding). Extends [ADR-072](./ADR-072-reseller-system-split.md) (accounts are still admin-provisioned in the end), [ADR-131](./ADR-131-chip-activation-conditions.md) condition 4 (documents collected from each reseller) and [ADR-132](./ADR-132-affiliate-monthly-auto-payout.md) decision 12 (the bank-details nudge it deferred). Touches no price, ledger or voucher write; two decisions touch the wallet top-up seam and the markup cap (20, 22) and were traced before they were built. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design), 2026-10-31. Grilled with the founder in four rounds, then stress-tested against the code (seven findings, folded into the decisions below). Nothing is built.

## Context

There is no onboarding anywhere: no checklist, first-run screen, readiness flag or pending state (traced 2026-10-31, backend, portal, admin, storefront). A new partner can get stuck silently:

- An affiliate's dashboard shows "Live" when the domain is Active, while every checkout is refused (`payments_approved_at` null, [ADR-131](./ADR-131-chip-activation-conditions.md)). Nothing tells them, and the portal's "we will let you know" has no notification behind it.
- Missing bank details make the monthly payout skip the affiliate every month with no notice (`skip = no_bank`, `AffiliateWithdrawalService.php:79`). The admin cannot enter bank details for them.
- A reseller with no tier gets `NO_TIER_ASSIGNED` on every API and bot order, but Add Balance still works, so they can fund an account that cannot order. Creating a reseller makes no portal login; that is a separate admin step.
- The admin cannot see who is stuck: neither list has a readiness column.

A reseller account can only be opened by the admin today (ADR-072/076, PRD item 13 "not designed"). [ADR-131](./ADR-131-chip-activation-conditions.md) condition 4 says CHIP expects the documents collected from each reseller; the onboarding procedure and the documents live outside the repo (decision 24 there). The founder wants applicants to apply on a public page and to be screened **before** any identity document is collected, so documents are never held for people who will not be accepted.

Facts the design rests on (read from code, 2026-10-31): the existing sandbox ([ADR-018](./ADR-018-sandbox-test-orders.md)) is admin-only and the reseller paths never mention `is_test`, so a partner has no sandbox; the portal's `proxy.ts` sends every session-less path except `/login`, `/set-password` and `/impersonate` to `/login`; `affiliate_users.email` is unique and a closed account only deactivates its users; the Spatie backup is a SQL dump only (`include => []`), so files are never in it; `TurnstileVerifier` exists and fails closed; wallet top-up has one seam, `ResellerWalletTopupService::initiate()`, used by both the portal and `.topupbaki`.

## Decision

### A. Public application and KYC (resellers only)

1. **Resellers only.** An affiliate stays admin-invited: its branded domain needs CHIP's written approval per domain anyway (ADR-131 decision 19–22), so an open form saves nothing. Affiliates still get Part B.
2. **Two stages, one table.** `partner_applications` holds one row per applicant: a `status` that spans both stages (`email_pending`, `new`, `invited`, `documents_submitted`, `approved`, `declined`), the stage-1 answers, a hashed token, `token_expires_at`, `notice_version`, a consent timestamp per stage, and a nullable unique `reseller_id`. `partner_application_documents` holds one row per file. No separate "enquiry" table.
3. **Stage 1 asks no document.** Owner name, company, phone, email; reseller experience (how long, which platforms); estimated monthly sales as a range, shown to the admin as "self-declared, not verified"; main games; how they plan to order (API, WhatsApp bot, not sure); how they heard of us; one consent box. The email is verified by a link before the application counts.
4. **Host and app.** `onboarding.pekangame.space` is served by the existing `reseller/` app, outside `(portal)` (public routes `/apply` and `/onboard/[token]`), not a fifth app. `proxy.ts` splits by host: the onboarding host serves only those routes, the portal host serves neither. `noindex`. The backend takes the submissions on its own unauthenticated route group with throttles and `TurnstileVerifier`. The widget's hostnames must include the onboarding host (founder action, same as ADR-123).
5. **Email identity.** An email that belongs to any portal user, active or closed, is refused at stage 1 ("contact us"); one active application per email. Approval re-checks inside its transaction; the unique constraint is the last guard.
6. **Admin screen.** A list and a detail page that reads like a form. Actions: **Send stage-2 link**, **Decline** (one short polite email, no reasons, once), **Invite directly** (creates an application already at stage 2, for someone the founder knows), **Regenerate link**, **Delete applicant data** (a data-subject request).
7. **Stage-2 link.** A long random token, stored as a hash, single use, 14 days, sent only to the verified stage-1 email. Progress can be saved and resumed until submitted, then it locks. Regenerating revokes the old token. No login.
8. **Documents** follow the founder's CHIP list: the owner's identity, business details, SSM, proof of business address, one or two months of a bank statement (redacting transaction lines is allowed, because they hold third parties' data), and the tax identification number. An individual without SSM is not accepted yet. PDF, JPG or PNG, a size cap, the real file type checked (not the extension). Storage is **private**, never a public URL; the admin views a file through a link valid for 5 minutes, and every view is logged (who, when). No OCR or automatic verification; the founder reads them.
9. **Retention.** A declined application's rows and files are deleted after 90 days by one scheduled, idempotent command. An approved applicant's documents stay while the account is open and for a period after closure (**owed**, decision 25). The notice says plainly that a deleted row can remain in older database dumps until they expire (the dump is SQL only; files are never in it).
10. **PDPA (Malaysia).** Two notices, one per stage, each **bilingual (Malay and English)** because section 7 requires both; each with its own consent box. `notice_version` and the consent time are stored on the application. The notices are versioned text in code, **written with a lawyer** (draft kept outside the repo until reviewed). Rights to access, correct and delete go through a named contact; the admin's delete action serves them. Cross-border transfers (private storage region, Plunk email, Cloudflare Turnstile) are recorded in this ADR's consequence list. The breach procedure (72-hour notice to the Commissioner, as reported by secondary sources, to be checked against the official guideline) is a document outside the repo.
11. **Approval is one service.** `PartnerApplicationService` owns every status transition under a row lock; approving twice cannot make a second reseller (`reseller_id` unique). "Approve" must pick a **tier** and calls `ResellerProvisioningService` (decision 21). The invite email is queued **after commit**, not inside the transaction (unlike the affiliate create, where a Plunk failure rolls everything back); "Resend invite" already exists.
12. **Three ways to get a reseller.** (a) Public apply; (b) the admin's **Invite directly**; (c) the admin's **Create internal account**, kept for test or internal accounts (FixFast for CHIP): super_admin with MFA step-up, a required reason in the audit log, and the list shows "No KYC on file". Existing resellers stay as they are (no migration; their documents were collected outside the system, the list says "KYC outside the system", not an error).

### B. Readiness and first-run in the portal

13. **One read-only `PartnerReadinessService`** returns the steps and each step's state (`done`, `todo`, `waiting_on_us`, `optional`) for an affiliate or a reseller, with `forMany()` for the admin lists (eager-loads, no N+1; no cache, because stale readiness is worse; `ponytail:` a few hundred partners). It **never recomputes a gate that already exists**: it calls the same predicates the real code uses. Bank presence becomes one `Affiliate::hasBankDetails()`, which the two existing copies (`Affiliate/WithdrawalController.php:61`, `AffiliateWithdrawalService.php:79`) and the service all call; domain Active and payments approval use the existing domain and `StorefrontBrand` checks; "first order" uses the same paid, `is_test = false` scope the reports use. One invariant test: "ready to sell" is true exactly when a checkout on that store can pay.
14. **Affiliate steps:** password (already done on arrival, so the list starts at 1 of N), bank details, connect domain, DNS verified (with the deadline: a domain pending 14 days is torn down), payments approval (shown as "waiting on us", never promising a date: CHIP's written approval comes first), branding (logo and a theme other than PekanGame's default), review markup, first order. Required to sell: password, domain, DNS, approval. An owned brand skips bank and markup. **Reseller steps:** password, add Purchase Balance, choose how to order (an active API key **or** a linked WhatsApp group, defaulting to the stage-1 answer), first order, webhook (optional). Tier is not a step: approval always sets it. For the bot, the portal shows the instructions and the link state, which it never mentioned.
15. **Banners and the checklist.** The checklist can be collapsed (browser `localStorage`, no column) and collapses itself when every required step is done. A banner that cannot be dismissed appears only for what costs money or blocks selling: an affiliate with no bank details; a domain that is Active but not approved ("Your store is online, payments are not enabled yet"); an older reseller with no tier. The dashboard's "Live" badge splits into **Online** and **Ready to sell**.
16. **First order and empty states.** There is no partner sandbox (see "Not decided here"), so a reseller's first order is real money. A "Your first order" card says: use a small package, check the player ID first, a failed order returns to the Purchase Balance. Empty Orders shows one button (an affiliate: copy the store link, or "connect your domain first"; a reseller: choose how to order); empty Balance shows Add Balance.
17. **Notifications.** An email to the affiliate when the admin approves payments (fulfils the portal's existing promise); an item in the admin's "Needs attention" list when a domain is Active and not approved. Approval stays a manual step after CHIP's written approval (PRD §16 item 141).
18. **Admin lists** get a readiness column from the same service ("Ready" or "Needs: bank, approval").
19. **Language.** The portal, the public forms and emails to applicants are English; the set-password page (Malay today) becomes English. The two privacy notices stay bilingual by law (decision 10).

### C. Fixes folded in (each its own PR)

20. **A reseller with no tier cannot add balance.** The guard sits in `ResellerWalletTopupService::initiate()`, the one seam the portal and `.topupbaki` share, and **never** in `completeTopup()`: a top-up already paid must still credit. The admin's manual credit stays allowed. A test starts a top-up, removes the tier, and proves it still completes.
21. **One `ResellerProvisioningService`** (reseller + ledger account + portal user + invite, tier required) used by decision 11 and by both admin create paths, so the admin create makes the login too and no second copy exists.
22. **`max_markup_pct` null** means "no ceiling" for the admin form and the pricing code, but the portal's markup edit casts it to 0 and answers "at most 0%". Fixed as its own PR after a trace of every writer and reader of the column. **Settled 2026-10-31:** null means no markup opened (a ceiling of 0) everywhere, [ADR-061](./ADR-061-every-storefront-is-a-reseller.md)'s 2026-10-31 addendum.
23. **Set-password language** (decision 19).

### Not decided here
- **A partner sandbox** (a test-type API key: orders flagged `is_test`, no Purchase Balance debit, `FakeSupplierAdapter` outcomes, webhook still sent) is its own money-critical ADR after this one: it must be proved not to touch the wallet, ledger, reports, receipts, rate limits or the bot. The checklist's first-order step changes to "test in the sandbox, then order" when it exists. Refreshing the admin sandbox for wallet and combo orders is a separate backlog line.
- Affiliate public signup, a store preview mode for affiliates, OCR, a "Go live" status flag and daily nudge emails: not planned.

## Rationale

- **Documents only after screening** removes the harm of holding IC and bank statements for people the founder will not accept, and makes stage 1 cheap to read.
- **A separate application table** leaves every money path untouched: no code that places an order, tops up or logs in learns a "pending" reseller.
- **One readiness service reading real gates** removes the drift that two copies of the bank check already show; a third copy would eventually disagree with the payout.
- **Computed, not flagged:** no new status to keep in sync with the admin's manual approval step.
- **The guard at `initiate()`** covers the portal and the bot with one change, and leaving `completeTopup()` alone keeps paid money safe.

### 2026-10-31 addendum — what PR 1a settled while building the backend

- **The password step is not "required".** Decision 14 listed it among the steps that block selling, but a store takes payments with or without a portal password, and decision 13 makes "ready" mean exactly what the real gate says. So `ready` for an affiliate is: the account is active and an Active, servable domain has payments approved (the `domain`, `dns` and `payments_approval` steps, all `required`). For a reseller: the account is active and the `tier`, `add_balance` and `order_channel` steps are done. The invariant test asks the real storefront (`GET /api/catalog/branding`, ADR-131's gate) across seven domain states and both account states.
- **Two more shared predicates, beside `Affiliate::hasBankDetails()`:** `AffiliateDomain::paymentsApproved()` (read by the storefront resolver, the admin domain list, the portal domain list and the readiness service) and `Order::scopePaidAndReal()` (paid and not a sandbox order, read by the affiliate sales figures and the readiness "first order").
- **`ResellerProvisioningService`** has `create()` and `addPortalUser()` only; the admin controller calls both, with no behaviour change (a tier is still optional there). The method that requires a tier and combines them is added in PR 2 and PR 3, when it gains its callers, so no code waits unused.
- **The markup step is `optional` and never done:** nothing records that an affiliate reviewed their markup, and a step that can never complete should not hold the checklist open.

### 2026-10-31 addendum — what PR 1b settled while building the screens

- **The admin's "Needs attention" item (decision 17) is the Setup column.** No admin list of domains waiting for approval exists to extend (the Withdrawals page's "Needs attention" is payouts only), so the Affiliates list's Setup column carries it: "Awaiting your approval" when the only open step is PekanGame's, "Needs: ..." otherwise, "Ready" when done. The platform's own brand has no readiness.
- **The payments-approved email** goes to each active portal login (the affiliate's contact email if there is none), once, only on the move from not approved to approved; revoking or approving again sends nothing, and a mail failure is logged and never undoes the approval. It is sent after the update, not in a transaction (decision 11's reasoning).
- **Optional steps keep their link** ("Review pricing", "Set a webhook") beside the Optional badge, and are left out of the "n of m done" count.
- **Banner and checklist failures are silent:** if the checklist cannot be read, the page it sits on still works.
- **Browser check** (2026-10-31, throwaway backend, 44 checks): every state of both account types, the collapse remembered across a reload, mobile 390 px with no sideways scroll, text contrast at least 4.5 in light and dark, the English set-password page, and the admin Setup column. The approve action itself (step-up MFA) is proved by the backend tests, not the browser.

### 2026-10-31 addendum — what PR 2 settled while building the top-up guard and the admin create

- **The guard (decision 20) is the first check in `ResellerWalletTopupService::initiate()`**, before the minimum, the CHIP lookup of an older pending attempt and the wallet mutex, and it throws the existing `NoResellerTierAssignedException`. The portal answers 422 with "Your account has no pricing set up yet, so you cannot add balance. Contact PekanGame to set it up."; the bot replies in Malay and logs `topup_no_tier_assigned`. It needs no lock: traced 2026-10-31, an assigned tier is only ever swapped (`assignTier` requires one, the foreign key restricts delete, a tier with active resellers cannot be deleted), never cleared. No credit path (CHIP webhook, the 15-minute reconcile, the admin manual credit) reads the tier; a test starts a top-up, clears the tier in the database and proves it still credits. Production on 2026-10-31: 3 resellers, all with a tier and a login, no pending top-up, so nobody is affected today.
- **`provision()` is all or nothing:** the reseller, its wallet ledger account, the first portal login and the set-password invite in one transaction, so a failed invite leaves no account behind (the affiliate create's choice). The login is the form's contact name and email, both now required; the email must not belong to any portal user (decision 5). `create()` became private. The tier is required in the service itself, not only in the request, and the admin create accepts only an **active** tier. PR 3's approval path moves the invite after commit (decision 11), in this service.
- **"Create internal account" (decision 12(c))** is `POST /api/resellers/internal`: super_admin, MFA step-up (added to the pinned step-up route list), the same fields plus a reason (10 to 500 characters). The reason is kept in a new nullable `resellers.internal_reason` and written to the log with the admin's id; there is no generic admin audit table, and the log is the existing record for reseller admin actions. The list reads it: "Internal · No KYC on file" when set, "KYC outside the system" otherwise (PR 3 adds "on file").
- **The plain "Add Reseller" stays until PR 3,** now with the tier and the login required, because a real reseller in onboarding needs an account before the public application exists; their documents are collected outside the system. PR 3 decides whether it becomes "Invite directly".
- **Existing accounts are not marked.** FixFast (the account given to CHIP) shows "KYC outside the system" until someone sets its reason; that is a production data write, for the founder to approve.

### 2026-10-31 addendum — the founder's document list, the retention period, storage and the widget hostname

Decided with the founder on 2026-10-31; revises decisions 8 and 9 and closes four "owed" items.

- **Documents (revises decision 8).** The applicant says at stage 1 whether they apply as a **company** (registered with SSM) or an **individual** (not registered yet). An individual is now accepted: some resellers start before they register.
  - Company: the SSM certificate; the business address (typed in the form, no proof document, since the SSM certificate already shows the registered address); the owner's name, address, phone and email; a bank statement for one or two months (transaction lines may be redacted); the tax identification number, **optional**. No identity card is asked of a company's owner.
  - Individual: the identity card (front and back); the owner's name, address, phone and email; the bank statement; the tax identification number, optional.
  - Dropped from the first list: the proof of business address document and the required tax number.
- **Retention (revises decision 9, closes the owed post-closure period).** A declined application's rows and files are deleted 90 days after it was declined (unchanged). An approved reseller's documents and application data are deleted **90 days after the account is closed**. The ledger, orders, top-ups and receipts are never deleted by this; only the application and its documents. The same scheduled command does both, and the PDPA notices state both periods.
- **Storage (closes the bucket check).** The platform's file storage is Cloudflare R2, not the Forge box. Documents go to a **new private bucket `pekangame-kyc`** in Asia-Pacific (APAC), with its own scoped token and its own disk (`r2_kyc`, the `r2_accounting` shape: no `url`, `throw` on), never a shared bucket, so a leaked token for one bucket cannot expose another. The founder creates the bucket and the token (a credential); local development uses the private local disk. The cross-border note in decision 10 names Cloudflare R2 (APAC).
- **Turnstile hostname (closes the owed widget item).** The widget "PekanGame Game ID Checker" lists `pekangame.space`, and a widget hostname covers its subdomains (Cloudflare's documentation), so `onboarding.pekangame.space` needs no new entry. PR 3's browser check proves it on the real host.
- **Still owed:** a lawyer's review of both bilingual notices (they now say individuals may apply and give the two 90-day periods); the `pekangame-kyc` bucket and its token; whether CHIP receives copies of the documents. *(2026-11-01: the bucket and token exist; CHIP copies settled by listing recipients by class; the notice text is read before the open switch is turned on. See the 2026-11-01 addendum.)*


### 2026-11-01 addendum — what PR 3a settled (the application backend)

Decided with the founder on 2026-10-31 (plan recap before code); closes the "CHIP receives copies" item.

- **PR 3 is three PRs:** 3a the backend (this), 3b the public forms on `onboarding.pekangame.space` in the portal app, 3c the admin screen. 3a's routes have no caller until 3b and 3c ship.
- **Recipients are listed by class, not by company (closes "whether CHIP receives copies").** Both notices say the details may be disclosed to: payment service providers, on request, for compliance and verification; regulators, law enforcement and courts, where the law requires; professional advisers, in confidence; and the service providers that store and send data for us (cloud storage in Asia-Pacific, email), which may process it outside Malaysia. PDPA section 7 asks for the class of third parties, so a change of payment provider needs no new notice version. The founder had the approach checked by a contact in the legal industry; the full text (`PartnerApplicationNotice`, version `2026-11-01`) is still read before the switch below is turned on. The data user's name, registration number and address are read live from Settings; the rights contact is `services.onboarding.privacy_contact` (`partners@pekangame.space` by default).
- **A "Public applications open" switch** (`platform_settings.partner_applications_open`, default off, in the admin): stage 1 and its email are refused while it is off. A stage-2 link already sent, and Invite directly, work either way.
- **"Add Reseller" becomes "Invite directly"** (decides the PR 2 addendum's open point): every real reseller then has its documents in the system; test accounts use "Create internal account". The backend endpoint is in 3a (`POST /api/partner-applications/invite`); the admin button and the removal of the old create are in 3c, so the admin keeps a working create in between.
- **Files:** PDF, JPG or PNG, at most 10 MB each, the type read from the content (Laravel's `mimes`). A company uploads the SSM certificate and one or two bank statements; an individual the identity card's front and back and one or two bank statements. Uploading a single-file kind again replaces the earlier file; a third bank statement is refused. Disk `filesystems.kyc_disk` (`KYC_DISK=r2_kyc` in production, the bucket `pekangame-kyc` with its own `R2_KYC_ACCESS_KEY_ID` / `R2_KYC_SECRET_ACCESS_KEY`; the private `local` disk elsewhere).
- **Viewing a file:** the admin asks for a signed link valid for 5 minutes; opening it re-checks that the admin is still an active super_admin, streams the file inline with `nosniff` and `no-store`, and writes a `partner_document_views` row (who, when). The detail page lists the views.
- **Emails:** stage 1's confirmation link and the admin's stage-2 link and decline are sent inside the transition's transaction, so a mail failure changes nothing and the action can be retried. Only the approval's set-password invite is sent after commit (decision 11); a failure is logged and "Resend invite" covers it. A decline is emailed only to a confirmed address.
- **Unconfirmed applications:** sending stage 1 again before confirming refreshes that application and its link (a lost email). One never confirmed is deleted 7 days after it was last sent; it never reached the admin and holds a stranger's answers. The retention command (`app:prune-partner-applications`, daily, routine tier) does this together with the two 90-day rules; closing a reseller soft-deletes it, so "closed" is its `deleted_at`.
- **Delete applicant data** (behind step-up) removes the files and the row; a reseller approved from it stays and its list label falls back to "KYC outside the system". The reseller list shows "KYC on file" while the application is held.
- **Turnstile** reuses the Game ID Checker's widget and secret (`TurnstileVerifier`, fails closed: 503 when unconfigured).

### 2026-11-01 addendum — what PR 3b settled (the public forms)

- **Host rule:** `proxy.ts` treats any host starting with `onboarding.` as the onboarding host (`onboarding.pekangame.space` in production, `onboarding.localhost:3002` locally, no env needed). There it serves only `/apply`, `/apply/verify` and `/onboard/…`, sends anything else to `/apply` and adds `X-Robots-Tag: noindex, nofollow` (the pages also carry `robots: noindex`). The portal host answers 404 for those paths. Still one Vercel project (`pekangame-reseller`) with one more domain.
- **Turnstile is allowed only on the application pages.** The portal's CSP had no third-party script host, so it blocked the Turnstile script (found in the browser check). `next.config.ts` now builds the policy twice and adds `https://challenges.cloudflare.com` to `script-src` and `frame-src` only for `/apply` and `/onboard`; the signed-in portal keeps its strict policy. The portal needs `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (the storefront's site key).
- **Confirming the email takes a click.** The verification page shows "Confirm my email" instead of confirming on load: the token is single-use, and an email security scanner that opens links (or React's development double effect, which spent the token in the browser check) must not use it before the applicant does.
- **The backend allows the onboarding origin** (`ONBOARDING_URL` in `config/cors.php`); the same variable builds the links in the applicant emails, so production needs `ONBOARDING_URL=https://onboarding.pekangame.space`.
- Stage 2 saves the answers on "Save progress" and again before submit; each file uploads when chosen (refused in the browser above 10 MB, checked again on the server), and a single-file kind says that uploading again replaces it.
