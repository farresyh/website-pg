# ADR-015: Price Sync — cost propagation + deactivation detection (built 2026-07-26)

> **Standing (2026-10-09):** In force; decision 3 (manual-only reactivation) reversed by ADR-100. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-07-26 (grilled with the founder one decision at a time, using the `codebase-design`/`domain-modeling` vocabulary, before any code — explicit founder instruction: this session is audit + research + plan only, build happens next session)

**Context:** Founder question after reviewing `/middleware/product-manager`: is the price shown there real-time from Gamevion? Confirmed no — `SupplierProductController::promote()` copies `supplier_products.price_sen` into `Package.cost_price` **once**, at promote time; `ProductSyncService::sync()` (Stage 1) refreshes `supplier_products` on every re-run but **deliberately never touches `Package`** (by its own docblock). This exact gap was already flagged and deferred on 2026-07-25 (`prd.md`:608) as a future dedicated "Price Sync" feature (§6.4, SYNC-1..6) rather than a Stage-1/2 patch. Also confirmed live: **zero automation exists anywhere** — `routes/console.php`/`bootstrap/app.php` register no `Schedule::` calls at all, so even Stage 1's raw-catalog mirror is 100% manual (`php artisan app:sync-supplier-products`) today. This ADR is that deferred feature's design session — no code was written; every decision below was walked through one at a time before being accepted.

**Decision (per sub-area, each grilled with the founder one at a time before being accepted):**

1. **Scope for this build phase** — two correctness-critical mechanisms only: **Price Propagation** and **Deactivation Detection**. The full Admin "Price Sync Center" UI (SYNC-1/2/3's dashboard stats, run-history browsing, currency FX display) is deliberately deferred to a later pass — it can layer on top of these two mechanisms without changing their design, so it isn't a dependency of shipping them.
2. **Price Propagation** — on every sync run, for **every** promoted `Package` regardless of `is_active`, auto-apply the supplier's current `price_sen` into `cost_price`/`reseller_cost_price` (recomputed via the existing `PackageMarkupService`, preserving the package's own `markup_percent`), **in both directions (increase or decrease), with no approval gate**. Founder explicitly rejected an up/down asymmetry here (see Rationale). Every *actual* change (no-op skipped) writes a `price_change_logs` row for audit, since there's no review step to catch a bad value before it applies — this matters more, not less, given Gamevion's API has already been observed returning bad/inconsistent data (ADR-006's sandbox `500`/`422` findings).
3. **Deactivation Detection — asymmetric by direction.** When a promoted package's supplier item goes inactive, **or disappears entirely from the latest full catalog sync** (treated identically — both mean "can no longer be fulfilled," and Stage 1's `updateOrCreate` loop currently has no way to notice a vanished item at all): auto-set `is_active=false`, `deactivated_reason='supplier_sync'`, `deactivated_at=now()` — no approval needed, since protecting a customer from buying something unfulfillable is the safe default. When a package deactivated this way later shows active again at the supplier, it is **not** auto-reactivated — it surfaces in a new **Pending Reactivation** queue for the admin to **Approve** (`is_active=true`, clear the two fields) or **Dismiss** (`deactivated_reason` → `'admin'`, converting it into an admin decision so future supplier flips stop being monitored for this package).
4. **`deactivated_reason` distinguishes admin intent from system detection** — new nullable columns on `packages`: `deactivated_reason` (`admin`|`supplier_sync`) and `deactivated_at` (also powers the Pending Reactivation table's "days inactive" column). A package an admin manually turned off via `/admin/games` is never touched by Deactivation Detection/Pending Reactivation — only `supplier_sync`-reasoned rows are monitored for reactivation.
5. **Trigger mechanism — async queued job, both manual and (future) scheduled.** A new `SyncSupplierPricesJob` (queued, `database` driver, same pattern as `FulfillOrderJob`) orchestrates: existing `ProductSyncService::sync()` (Stage 1, unchanged) → a new propagation/deactivation service → one `price_sync_runs` row written (status/stats/error). The admin's "Sync All Prices Now" button dispatches this same job — chosen async specifically so the admin panel never blocks on a live Gamevion call (founder: "kita mmg tahu yang feature ni mmg kita akan pakai jangka masa yang lama"). The new `/middleware/price-sync` page polls run-status while it's `queued`/`running`.
6. **Scheduled automation is genuinely blocked on infra, not code.** Confirmed live: the backend still runs only via local Laravel Herd — no VPS/cloud deployment, no Procfile/CI-deploy config anywhere in the repo (the one existing VPS, from ADR-006's proxy addendum, is a narrow outbound-proxy-only box, unrelated to hosting the app). A real cron-driven schedule needs an always-on host regardless of this feature. Decision: write the `Schedule::job(...)` entry now (env-configurable interval, `PRICE_SYNC_INTERVAL_MINUTES`, default 10) so it activates for free the moment a real OS cron (`* * * * * php artisan schedule:run`) exists on a deployed host — but **migrating to a VPS/cloud is tracked as its own, separate initiative**, not a blocker for shipping this feature's manual-trigger path. (Also noted, not acted on: the same infra gap affects Xendit webhook reliability in real production, not just this feature.)
7. **Dedicated new admin page**, `/middleware/price-sync` — not bolted onto `/middleware/product-manager`. Founder's own reasoning: enough distinct surface area (trigger button, run-status, Pending Reactivation table, and later the full Center UI) to justify its own page, matching the PRD's own MUI-6 nav item rather than overloading Product Manager's existing two-level category/item structure.

**Rationale:** Every mechanism above changes `Package`'s data and the sync pipeline's *implementation*, not `SupplierAdapter`'s or `ProductSyncService`'s existing interfaces — Stage 1 (`ProductSyncService::sync()`) is untouched, matching this codebase's established "deepen the module, don't reshape the seam" discipline (ADR-001/ADR-006/ADR-014). The asymmetric deactivation logic (auto-off, review-on) and the symmetric price-propagation logic (auto both ways) were each argued from the same underlying principle — **auto-apply the direction that's safe by default (can't lose money or oversell), require a human for the direction that could silently override a deliberate decision or act on a possibly-bad signal** — except price, where the founder explicitly rejected an up/down asymmetry: the entire point of this feature is to stop losing margin silently, and gating price *increases* behind approval would just recreate that same problem with an approval-lag instead of solving it.

**Consequence to track:** this ADR records *design intent only* — no code exists yet (explicit founder instruction: this session is audit + research + plan). Update `prd.md` §14/§15 once each piece actually ships; do not treat this entry as proof any of it is built. The full "Price Sync Center" UI (dashboard/history/FX) is intentionally not designed yet — that discussion is deferred until after this phase ships, per the founder's own explicit sequencing.

**Addendum — shipped, 2026-07-26 (build session, same day):** Price Propagation and Deactivation Detection (decision #1's actual scope) are now built and covered by 22 new tests (full suite: 350 tests, all green). Implementation matched the design above, with one real bug caught and fixed, and two things clarified on contact with code that weren't decided at design time:

1. **[Fixed] "Seen this run" cannot be compared via `Carbon::equalTo()`.** `supplier_products.last_synced_at` is a plain `datetime` column (sqlite and MySQL alike, no fractional-seconds precision) — it silently truncates the microseconds every `now()` call carries, so comparing the in-memory sync timestamp against what was actually persisted for a row touched the *same* run always came back "not equal." Left unfixed, this would have made every real sync run deactivate every promoted package, every time — the opposite of decision #3's intent. Caught by a feature test, not manual QA (`PackagePriceSyncServiceTest::test_propagates_a_price_increase_and_recomputes_reseller_cost_price` failed first), same "verify against real DB behavior, not an idealized one" discipline as ADR-014's own database-cache-serialization addendum. Fixed by comparing whole-second Unix timestamps (`->timestamp`) instead of full `Carbon` equality.
2. **Pending Reactivation is computed live, not stored.** No extra column or job-maintained flag tracks "this deactivated package's supplier item is active again" — `PendingReactivationController::index()` joins `packages` (`is_active=false`, `deactivated_reason='supplier_sync'`) against the current `supplier_products` snapshot at request time, the same pattern `GameController::packages()` already uses for its read-only `supplier_active` indicator (§14/§8 of `prd.md`). This keeps `SyncSupplierPricesJob` from having to maintain a second piece of state that could drift from the first — decided during implementation, not specified by decision #3 itself, but consistent with it.
3. **Decision #4's two invariants collapse to one guard.** "Never touches an admin-deactivated row" and "never re-deactivates an already-deactivated row" both reduce to a single `if (! $package->is_active) return;` check in `PackagePriceSyncService::deactivate()`, since `deactivated_reason` is only ever non-null when `is_active` is already `false` by this codebase's own write paths (every place that sets one sets the other in the same update). No separate reason check needed — trusting the invariant rather than defending against a state that can't occur.

**Scope actually shipped, matching decision #1's own stated boundary:** Price Propagation, Deactivation Detection, the Pending Reactivation queue (approve/dismiss, single and bulk per SYNC-6), a manual "Sync All Prices Now" trigger with run-status polling, and the `Schedule::call()` entry (decision #6 — still inert, no cron infra exists). **Not shipped, deliberately ADR-016's territory, not this ADR's:** the stat cards, Sync History browsing, Sync Details modal, and Manually Dismissed Packages section. `/middleware/price-sync` today is only the trigger + Pending Reactivation table decision #7 itself calls for — confirmed live against a real running server (`php artisan serve`, real Sanctum token, real `POST`/`GET`), not just `phpunit`.
