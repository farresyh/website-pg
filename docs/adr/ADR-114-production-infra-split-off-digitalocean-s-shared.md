# ADR-114: Production infra split off DigitalOcean's shared team — droplet + managed MySQL rebuilt into a new DO team (`LWF Group Sdn Bhd`)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted & built — core cutover live and real-checkout-verified 2026-09-25. OpenWA bot channel migration completed the same day (see 2026-09-25 addendum below) — both pieces of this ADR are now fully live.

**Context:**

PekanGame and Nakhoda (a separate, older business with real external customers) shared one DigitalOcean account ("My Team"): Nakhoda's own droplet/Postgres, and PekanGame's droplet `pekangame-prod` (157.245.203.250, reserved IP 137.184.250.200) + managed MySQL `topup-prod-mysql`, both under a DO project named "Topup Website". The founder confirmed PekanGame is becoming a legally/financially separate business entity from Nakhoda — this is a real entity-separation requirement, not billing-invoice tidiness. DigitalOcean has no droplet/managed-DB transfer between teams (confirmed live in the DO console — no "move to another team" option, and no automated backups/snapshots existed yet on `pekangame-prod` to make a transfer-by-snapshot viable either). PekanGame's live orders at the time of this decision were 100% the founder's own testing, zero external customers — so this migration carried zero external-customer blast radius, unlike a similar move would for Nakhoda.

**Decision:**

1. **Rebuild, not transfer.** A new Forge-provisioned droplet (`pekangame-prod-lwf`, 159.223.39.16) was created inside a brand-new DO team, **LWF Group Sdn Bhd**, from the same repo and re-entered `.env` secrets — not a DO-level move of the existing droplet.
2. **Database migrated via dump/import**, not replication: `mysqldump` off the old `topup-prod-mysql` cluster, imported into a new managed MySQL cluster (same name, `topup-prod-mysql`) provisioned inside the new team. `DEFINER` clauses were stripped from the dump before import (the new cluster's admin user differs from the old one's).
3. **Cloudflare Authenticated Origin Pulls (mTLS) replicated exactly** — new server's nginx `site.conf` byte-for-byte matched to the old server's, new Cloudflare Origin CA certificate installed via Forge's Domains → Certificates → Existing certificate (15-year validity) rather than re-deriving the mTLS setup from scratch.
4. **DNS cutover for `api.pekangame.space`** to the new droplet only after the new box's full stack (Horizon — every queue including `price-sync`/`orders`/`orders-combo`/`backups`/`reseller-webhooks`, Reverb, Pulse, and the server-level `schedule:run` Every-Minute cron under Forge Settings → Processes → Scheduler) was confirmed running and a real order was smoke-tested end-to-end.
5. **OpenWA WhatsApp bot deliberately left running on the old droplet, migrated separately.** The bot's session is device-bound (stored locally, tied to the WhatsApp Web pairing) — it cannot be copied to a new box, only re-linked via a fresh QR scan, which means brief bot-channel downtime whenever it happens. Bundling that downtime into the same cutover window as the DB/API migration was rejected; the bot channel currently has zero external customers either (see ADR-072/075's Reseller Bot channel), so there was no urgency forcing the two migrations together.
6. **Old droplet (`pekangame-prod`, old DO team) and its `topup-prod-mysql` cluster kept running in parallel**, not decommissioned immediately — rollback safety net until the new server has been stable for a few days. No teardown date set as of this entry.
7. **The already-deferred "OpenWA droplet resize" backlog item** (`docs/prd.md` §16, tied to a future real capacity signal, not part of this decision) was confirmed via 14-day DO Insights to still have no capacity pressure, and was deliberately **not** bundled into this migration — kept a separate, later decision.

**Rationale:**

- A rebuild-not-transfer avoids depending on a DO capability that doesn't exist (cross-team droplet/DB transfer) and, as a side effect, produces a clean-slate server with no accumulated cruft from the SSH-mishap rebuild ADR-020 already went through once on the old box.
- Byte-for-byte replicating the Cloudflare mTLS/nginx config rather than reconfiguring from first principles removed an entire class of subtle mismatch risk (a slightly different cipher/cert setting silently breaking Authenticated Origin Pulls) for a piece of infra that gates all production traffic.
- Splitting the bot migration out of the DNS-cutover critical path let the core API/DB migration ship without taking on the bot's own unavoidable downtime (QR re-link) at the same time — the two migrations have genuinely independent failure domains (API/DB availability vs. a WhatsApp session), so coupling them would only have widened the blast radius of the riskier day.

**Consequence to track:**

- **OpenWA bot migration still owed** — create the `bot.pekangame.space` Forge site (Custom type, nginx-only proxy) + install OpenWA on `pekangame-prod-lwf`, fresh QR-code re-link, then decommission the old droplet's `bot.pekangame.space` site + OpenWA process alongside it (not before — keep the bot working on the old server until the new one is ready). A 2026-09-25 audit session confirmed the bot is currently in a **partially-broken interim state**: the new server's `.env` (`/home/forge/api.pekangame.space/.env`, symlinked into each release via Forge's zero-downtime `current/` layout) already carries the correct `OPENWA_WEBHOOK_SECRET` (matches the bot's own config, so inbound `OpenWaWebhookController` traffic verifies correctly), but `OPENWA_BASE_URL` still defaults to `http://127.0.0.1:2785` — nothing listens there on the new box since the bot itself hasn't moved, so any *outbound* backend→bot call (e.g. a bot-initiated reply send) fails. Not urgent to fix ahead of the full bot migration — zero external customers on this channel — but worth knowing precisely which direction is broken rather than assuming the whole channel is silently offline.
- **Old droplet/DB decommission timing** — no date set; only after the new server proves stable for a few days. Includes deleting a stray duplicate `schedule:run` scheduler entry accidentally added on the *old* server mid-migration-session (harmless, points to its own path) whenever convenient.
- **New server uses Forge zero-downtime deploy** (`releases/<id>/` + a `current` symlink Forge atomically repoints after a successful deploy) — the old server does not (Quick Deploy off, deploys write directly into `backend/`). This was not a deliberate choice re-evaluated for this migration; it's what Forge provisioned for the new site, and it is a strict improvement for a money-critical checkout path (no window where nginx/php-fpm can serve a half-updated release, and rollback is an atomic symlink flip instead of a `git revert` + redeploy) — kept, not reverted. **Doc drift this caused, fixed same session:** the `reference_forge_box_ssh` memory (there is no server-path reference in `AGENTS.md` itself) described the old server's flat `backend/` layout as canonical; updated with a new-server addendum (`.env` lives at `/home/forge/api.pekangame.space/.env`, app code at `current/backend/`) so a future session doesn't look for `backend/.env` at the wrong path against the new box, as this session initially did.
- This ADR was written retroactively (2026-09-25 audit session, not the migration session itself) — the migration's own session ended without an ADR or build-log entry, discovered as a doc-audit gap. Going forward, infra migrations of this scale should get their ADR/build-log entry in the same session they ship, per `AGENTS.md`'s task lifecycle step 7.

### Addendum (2026-09-25, later same session) — OpenWA bot migration completed; three per-instance credentials don't travel with a `.env` copy

**Status:** Both consequence items above are now resolved. OpenWA bot channel is live on `pekangame-prod-lwf`, DNS cut over, real end-to-end WhatsApp round-trip verified. Old droplet's Horizon/Reverb/Pulse daemons and scheduler are **paused** (not destroyed) — see below.

**What shipped:** `bot.pekangame.space` created as a Custom Forge site on the new droplet (browser-driven), SSL cloned from the old site's own certificate (sidesteps needing DNS to already point here for Let's Encrypt HTTP validation — the same trick decision 3 used for `api.`), OpenWA (`github.com/rmyndharis/OpenWA`) cloned fresh, `npm install` clean (1031 packages, same patches as the old install), nginx `site.conf` hand-typed to match the old server's proxy block (`proxy_pass http://127.0.0.1:2785` + websocket upgrade headers — the Forge nginx-config editor is a CodeMirror instance whose own auto-indent compounds with manually-typed leading whitespace on multi-line paste; typing flush-left with no manual indentation avoided the corruption), registered as a Forge background process (`npm run prod`, working directory `/home/forge/OpenWA`). DNS (`bot.pekangame.space` + `www.bot.pekangame.space` A records, Cloudflare-proxied) cut over to `159.223.39.16` once the new instance answered `200` locally.

**Three separate credentials/identifiers live in OpenWA's own SQLite database (`data/openwa.sqlite`/`data/.api-key`), not in `.env` — copying `.env` alone (decision 1's stated approach) does not carry them, and this cost real debugging time discovering each one only after the previous fix didn't fully work:**

1. **Dashboard login key** (`data/.api-key`) — auto-generated fresh on first boot when `API_MASTER_KEY` is unset in `.env` (it was). Different from the old server's by design; not a functional problem, only affects who can log into the OpenWA web dashboard. Stabilizing this (pinning `API_MASTER_KEY` to a known value) was raised but not done this session — still open, low priority.
2. **Webhook registration secret** — the `webhooks` table's `secret` column is per-registration, not read from any `.env` var. A fresh webhook created via the dashboard's "Create Webhook" form has **no secret field at all** in that dialog, so a naively-created registration ships with `secret = NULL` — OpenWA signs (or fails to sign) deliveries with nothing, and `OpenWaWebhookController`'s `hash_equals()` check against the real `OPENWA_WEBHOOK_SECRET` rejects every delivery with 401 "invalid signature". Fixed by setting the new registration's `secret` column directly via `sqlite3 UPDATE` to the same value already in both servers' `.env` (the value itself travels fine via `.env`; only the *registration's use of it* doesn't default correctly).
3. **Outbound API key + session ID** — `OpenWaClient::sendNow()` calls `POST /api/sessions/{sessionId}/messages/send-text` with `Authorization: Bearer {apiKey}`. Both are per-instance: the `api_keys` table (issued keys, scoped, hashable) lives in the same excluded `data/` SQLite DB, so the old server's key (copied into `.env` byte-for-byte along with everything else) is simply unknown to the new instance's `api_keys` table → 401. Separately, and non-obviously, **the WhatsApp session's own ID is assigned fresh by OpenWA at link time, not reused from the old session** — the new "reseller-bot" session got `21c01762-8740-49f1-b4a5-176cac374e5c`, nothing like the old `c9def5ab-d080-45b6-a995-ac964ff7a1b9` still sitting in `.env`'s `OPENWA_SESSION_ID`. Fixing only the API key still 401'd — because the endpoint path itself named a session ID that doesn't exist on this server. Both had to be corrected in backend `.env` (new API key issued via the dashboard's API Keys screen; new session ID read directly from the `sessions` table) before outbound replies worked. **A `config:cache` alone does not pick this up on a running Horizon** — `php artisan horizon:terminate` (forcing Supervisor to refork workers against the freshly-cached config) was required each time; this is a known, already-documented gotcha (`AGENTS.md`'s deploy-script rationale) that bit this session anyway because the fix was applied out-of-band from a real deploy.

**Verified end-to-end, not just individually:** a real WhatsApp message sent into the founder's own test group round-tripped — `message.received` delivered inbound (`OpenWaSessionStatus` cache showed `status: ready`), the reply dispatched outbound and OpenWA's own `webhook_outbox_events` table recorded a matching `message.sent` event a few seconds later, zero rows in `webhook_delivery_failures` for either direction.

**Found and fixed as a byproduct, not part of the bot migration itself:** the old droplet's Horizon was still fully live post-cutover (rollback-safety, decision 6) and — because `Supplier.api_config` for Digiflazz was copied verbatim into both databases — **both droplets' schedulers were independently running `SyncSupplierPricesJob` against the same real Digiflazz account concurrently**, tripping Digiflazz's own rate limiter (`[83] Anda telah mencapai limitasi pengecekan pricelist`) on a cadence matching neither server's sync interval alone. This had been silently happening since the `api.` cutover (2026-09-25 earlier the same day), not something the bot migration introduced — just found while scanning logs for *other* problems before closing this session out, per the founder's own ask. **Fixed:** old droplet's Horizon/Reverb/Pulse daemons and Forge scheduler paused (founder-executed via Forge dashboard) — the OpenWA daemon deliberately left running (still the rollback target until its own decommission). This is the correct steady state until full old-droplet decommission: the old box keeps serving as a DB/API rollback target and the bot's own fallback without placing any real load on shared external suppliers.

**Consequence to track:**

- `API_MASTER_KEY` still unset on the new OpenWA instance — dashboard login key stays random-per-boot until pinned. Low priority, no functional impact.
- Old droplet's daemons/scheduler are paused, not removed — full decommission (per the original ADR's decision 6) still has no date set. A future session doing that decommission should also formally retire the old droplet's now-idle `Supplier.api_config` credentials from being live-callable at all (currently just dormant because nothing schedules a call, not because access was revoked).
- If OpenWA is ever re-provisioned again (another droplet move, a disaster-recovery rebuild, a second bot instance), **the three credentials above must be treated as a checklist, not assumed to travel with a `.env` copy**: (1) webhook registration secret, set manually per registration; (2) an issued API key, generated fresh, no old key is valid; (3) the session ID, read from the `sessions` table after QR link, never reused from the old instance. `AGENTS.md` or this project's OpenWA-specific runbook (none exists yet) would be a better home for this than only living in this ADR addendum — worth writing up as a standalone runbook if OpenWA is ever re-provisioned a third time.

### Addendum (2026-09-30) — old droplet/DB decommissioned, closing the original ADR's decision 6

**Status:** Old-droplet decommission (no date previously set, both prior addenda above) is now done. `docs/prd.md` §16 item 52 split this off from the `doadmin` least-privilege fix it was originally bundled with — that fix remains open, unrelated to this teardown.

**Pre-destroy audit (model-driven, live SSH + DO dashboard, before any teardown action):** found the old droplet's Horizon/Reverb/Pulse were **not actually paused** as the 2026-09-25 addendum assumed — a leftover Forge Quick-Deploy-style auto-pull on the *old* site was still triggering on every push to `main` (confirmed: the old droplet's backend HEAD matched the day's latest `main` merge commit, and `supervisor.service`'s own uptime showed a fresh restart minutes after that merge), independent of the CI-driven `FORGE_DEPLOY_HOOK` this project's `deploy` job actually calls. This explains the recurring daemon-alive state neither prior addendum caught. Despite that, real risk was zero: the old box's own local Redis queues were empty (`LLEN` 0 on every queue), nginx's access log showed only internet background port-scanning (HTTP 444-dropped, no real application traffic), and the old `topup-prod-mysql` cluster's last real order (`orders.created_at`) was 2026-09-24 11:01 — frozen since *before* the 2026-09-25 cutover, confirming zero data divergence risk from destroying it.

**Destroyed via DO dashboard (founder's own final confirmation click, per this session's safety classifier — the model filled every field but was blocked from typing the destroy-confirmation name itself):** the `pekangame-prod` droplet, the `topup-prod-mysql` managed MySQL cluster, and the droplet's Reserved IP (`137.184.250.200` — a separate $5/mo line DO does not auto-delete with the droplet unless explicitly selected in the destroy dialog). All three confirmed gone from the DO dashboard afterward. The stray duplicate `schedule:run` entry and the dormant `Supplier.api_config` credentials (both flagged in the first addendum's consequence list) are moot now that the droplet itself no longer exists.

**Consequence to track:**

- The old droplet's Forge server entry (Forge's own dashboard, not DO's) is now orphaned — pointing at a destroyed droplet. Not a cost or security issue (Forge itself doesn't bill per-server the way DO does), but worth removing from Forge's server list next time someone is in there, for hygiene.
- This closes the original ADR's decision 6 and every "decommission timing" consequence bullet across both prior addenda. Nothing about this ADR remains open except the unrelated `doadmin` least-privilege item tracked separately in `docs/prd.md` §16 item 52.

### Addendum (2026-10-01) — decision 2's "database migrated via dump/import" left local-disk private files behind; discovered only after the old droplet was already destroyed

**Status:** Real gap found and worked around; underlying durability risk still open, no code changed.

**What happened:** the founder hit a real `500` downloading a Supplier Funding receipt (`/admin/accounting/suppliers/{id}/transfers`) during the unrelated 2026-09-30 accounting-audit session. Root cause traced via prod log (`League\Flysystem\UnableToRetrieveMetadata`): `accounting_disk` is the `local` filesystem driver — `storage/app/private`, a real directory on whichever droplet is currently serving traffic, not a database table. Decision 2's migration only `mysqldump`'d the database; nothing rsynced `storage/app/private` from the old droplet to the new one. Every `supplier_transfers.receipt_path` created before the 2026-09-25 cutover (5 rows — the fields' own values travelled fine via the DB dump, only the *files* they point to didn't) pointed at a file that only ever existed on the now-destroyed old droplet.

**Blast radius, checked precisely, not assumed:** exactly 5 receipts, all `SupplierTransfer` rows (`created_at` 14–21 Sept, all pre-cutover) — zero `BudgetEnvelopeEntry` receipts existed yet at migration time, so the Envelope Ledger wasn't affected. 2 of the 5 belong to already-voided transfers (`id` 1 and 2) — `SupplierFundingService::recordCorrection()` runs every correction through `lockNotVoided()`, so a voided transfer's receipt can't be replaced even if the founder wanted to (the UI doesn't even render the "Correct…" action for one, confirmed live) — and since a voided transfer is excluded from every real total (`supplierPrepaidTopup()`/`bankTransferFees()`/`weightedAverageRate()`'s own `whereNull('voided_at')`), its lost receipt has no bearing on any figure that matters. The other 3 (all active, real transfers the newly-corrected RM 742.97 total depends on) were re-uploaded by the founder from his own kept Wise receipts via the now-live "Edit Details" → Replace receipt flow, verified live (`Storage::exists()`/`size()` against the real file, not just a 200 on the download route) — real PDFs, correct sizes, all 3 downloadable again.

**Consequence to track:**

- **Unrecoverable data loss for the 2 voided rows' receipts is permanent** — the old droplet is gone (this ADR's own 2026-09-30 addendum). Accepted, not chased further: zero effect on any real figure, per the exclusion logic above.
- **The durability gap itself is still open.** `accounting_disk` = `local` today means a receipt uploaded on whichever droplet happens to be serving traffic at the time only survives as long as that exact droplet does — any future infra move of this shape (another droplet rebuild, a disaster-recovery restore) will reproduce this exact incident unless storage is rsynced as its own explicit migration step, or the disk itself moves off local storage entirely. `App\Models\Gallery` already solved this identical problem for public images via Cloudflare R2 (ADR-095, 2026-09-2x) — `accounting_disk` moving to R2 (or a second, private-ACL R2 bucket/prefix) the same way is the durable fix, not yet built. Not urgent (low receipt volume, the founder now knows to re-check receipts after any future droplet move) but a real, named gap — tracked as `docs/prd.md` §16 (Hardening).
- **Process lesson for the next infra migration of this shape:** `mysqldump`-based decision 2 in the original ADR only ever claimed to migrate the database — this addendum is not a criticism of that decision, it's the gap between "the DB migrated cleanly" and "every private-disk file reference in that DB still resolves," which this ADR's own Consequence section never explicitly called out at the time. A future migration of this kind should treat `storage/app/private` (and any other local-disk-backed private storage) as its own explicit migration step with its own verification, not assumed to be covered by the DB dump.

**Addendum (2026-10-08) — the durability gap is closed (PRD §16 item 56).** `ACCOUNTING_DISK` and `WALLET_RECEIPTS_DISK` now point at `r2_accounting`, a private R2 bucket (`pekangame-accounting`: no custom domain, public URL off) with its own token scoped to that bucket, the same least-privilege shape as `r2_backups`. One bucket serves both disks (founder's call): both are private finance receipts. Unlike `r2_backups`, the disk sets `throw => true`, so a failed upload fails the save (a wallet credit rolls back) rather than storing `receipt_path = false`. The two receipt deletes in `SupplierFundingService::recordCorrection()` became best-effort, so a storage error after commit can't 500 a saved correction. Built in #375, released via #376. The 3 live supplier receipts were copied to R2 at the same paths, and all 3 stream back as valid PDFs. `WalletTopupReceipt` stores its disk per row, so it needed no copy (0 rows). The next infra move no longer has to carry `storage/app/private` for receipts.
