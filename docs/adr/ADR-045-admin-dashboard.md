# ADR-045: Admin Dashboard — DASH-1..6, `orders.delivered_at`, and a per-metric self-documenting `definition` convention

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted, built — 2026-08-27 (grilled via `/mattpocock-skills:grilling` before implementation, four rounds, 27 pinned decisions).

**Context:** `docs/prd.md` §6.2 (DASH-1..6) has sat unbuilt since the project's foundation — `admin/src/app/admin/page.tsx` (the route every login lands on, per `AppSidebar.tsx`'s existing "Dashboard" nav entry) is still literally the placeholder scaffold from day one, its own doc comment reading "DASH-1..DASH-6 ... come later — this is deliberately just 'who am I'". `foundation-security.md` §6 and `prd.md` §9 both name the per-supplier circuit-breaker display as an explicit MVP requirement, and `App\Services\CircuitBreaker\CircuitBreaker::state()` (ADR-019) was built specifically anticipating this screen but has never been wired to anything.

This ADR exists because Dashboard's obvious-looking requirements hide the same category of landmine Reports (RPT-1..3, no ADR of its own — see that build-log entry) found before it: metrics that look like a one-line COUNT/SUM actually need a real pinned definition (which timestamp, which table, cohort vs. snapshot) or they'll quietly compute something the founder didn't ask for. Unlike Reports, this ADR **is** numbered — Reports' decisions were entirely self-contained to `ReportService`/`ReportController`, consumed nowhere else; Dashboard's decisions cross-reference and reuse several existing seams (`ReportService`, `CircuitBreaker`, the `delivery_reconciliation` config, `OrderStatusService`) and add a new one (`orders.delivered_at`) that future sessions may build on, so a stable numbered reference point earns its keep here in a way it didn't for Reports.

Scope: **all six** DASH-1..6 requirements, built in one pass — founder's explicit call after weighing the alternative (DASH-1/2 only now, DASH-3..6 in a later grilled session) against building the dashboard route once instead of revisiting the same file twice.

**Decision:**

### DASH-1 — KPI cards (Sales / Orders / Profit / Vouchers Today, vs. yesterday)

1. **"Refunds Today" is renamed "Vouchers Issued Today."** The literal PRD wording directly conflicts with ADR-004 (no cash refunds, ever — the only two resolutions for a failed order are retry-delivery or Voucher issuance). Same category of fix Reports already made (dropping a reference design's non-applicable "Refund Rate"/"Chargeback Rate" tiles) — rename to the concept that actually exists here instead of faking the literal wording.
2. **"Vouchers Issued Today" counts Path B (order-triggered) vouchers only, not Path A (admin standalone).** Path B is the real compensation-for-a-failed-order signal this tile exists to show; Path A vouchers (promo/goodwill) are a different business event that would muddy it.
3. **Sales/Orders/Profit Today reuse `ReportService`'s existing pinned definitions verbatim** — ledger-sourced profit (never `Order.platform_profit`/`reseller_profit` directly), `payment_status=Paid` scoped by `paid_at` (never `created_at`), `is_test` excluded, Asia/Kuala_Lumpur day boundary. No new definition invented; `DashboardService` calls into `ReportService` for this leg rather than duplicating its logic.
4. **"vs. yesterday" renders as a percentage with an up/down arrow, colored green/red** (consistent with the `dataviz`-skill palette convention already used on `/admin/reports`'s trend charts). When yesterday's value for that metric is `0`, render **"New"** instead of computing a percentage (avoids an infinite/`NaN` result).

### DASH-2 — System Health

5. **Supplier API status is derived, never live-pinged.** Reads `CircuitBreaker::state()` (Closed/Open) per real `SupplierAdapter` implementation — no on-demand network call to the supplier on dashboard load, both because that would blow the §9 NFR's 2-second budget and because pinging a struggling supplier on every admin page load is exactly the retry-storm behavior the circuit breaker exists to prevent.
6. **No new "last checked" timestamp is added.** `CircuitBreaker` only stores `openedAt` (when it tripped), nothing for the closed-state "last successful call" case. Display state only (plus remaining cooldown seconds when Open) — adding new tracking for a "last checked: Xm ago" label is scope creep for a first cut, not required by DASH-2's own wording.
7. **"Stuck orders" reuses the existing `delivery_reconciliation` config (`DELIVERY_RECONCILIATION_STALE_AFTER_MINUTES`, default 15; `PENDING_STALE_MINUTES`, default 10), not a new dashboard-specific threshold.** These are the exact same numbers `ReconcilePendingDeliveriesCommand::retryStuckProcessing()` already uses to decide "stale enough to act on" — reusing them means Dashboard's "stuck" and the reconciliation job's "stale" can never silently drift apart into two different definitions of the same word. Rendered as **one combined count**: `DeliveryStatus::NeedsReview` (confirmed-ambiguous) + `Processing` orders older than the stale-after threshold + `Pending` orders older than the pending-stale threshold. Click-through target is `/admin/orders`'s existing `needs_review`/`pending_delivery` filters (already built, ADR-026/ADR-032) — no new admin screen needed for the drill-down.
8. **Pending payments count is a direct `payment_status=pending` count** — the same population `app:reconcile-pending-payments` (ADR-021, PAY-3) already targets.
9. **Queue depth is scoped to the `orders` queue only** (`FulfillOrderJob`/`ResendOrderDeliveryJob`/`CheckSupplierDeliveryJob`'s queue), not a breakdown of all four named queues (`default`/`orders`/`price-sync`/`backups`) — `orders` is the one queue whose depth is a genuine delivery-health signal; the others aren't part of the money-critical customer-facing path this screen exists to monitor. Reported as two numbers: pending count (`jobs` table, `queue='orders'`) and failed count (`failed_jobs` table, same queue) — a job that's failed after exhausting retries is a materially different signal from one merely waiting its turn.
10. **`/api/dashboard/health` sits behind `admin.role:super_admin,admin`**, matching `/api/reports/*`'s existing tier (a read-only overview screen, no reason to restrict further than Reports already is).
11. **No caching on the health endpoint — every load computes fresh.** All of DASH-2's data sources are local DB/cache reads (no live supplier network call, per decision 5) — comfortably inside the 2-second budget without a cache layer adding staleness for no real benefit.

### DASH-3 — Conversion Funnel (Orders Created → Payment Confirmed → Delivered, last 7 days)

12. **A real cohort funnel, not three independent daily counts.** Orders *created* in the last 7 days are the cohort; the funnel measures what fraction of that same set reached Payment Confirmed, then Delivered — not three separately-windowed counts (Created by `created_at`, Paid by `paid_at`, Delivered by current status) that would each describe a different set of orders and make "drop-off" meaningless.
13. **Right-censoring is an accepted, documented limitation, not something engineered around.** An order created on day 7 of the window hasn't had time to convert yet and will show as a "drop" even though it may still convert tomorrow. Recorded here rather than silently shipped, same as this project's other accepted-residual calls (e.g. ADR-041's narrower-race-window note) — not worth a corrective mechanism for a 7-day snapshot read.
14. **"Delivered" is read from the order's *current* `delivery_status`, a live snapshot — not a point-in-time-of-delivery check.** This is actually the semantically correct choice for a cohort model (the funnel asks "did this order eventually reach Delivered," not "was it delivered within the 7-day window"), so the fact that `orders` had no `delivered_at` column before this ADR (see decision 21) never blocked DASH-3 itself.
15. **Binary terminal check: only `DeliveryStatus::Delivered` counts as reaching the funnel's last step.** `Failed`/`NeedsReview`/`Pending`/`Processing`/`NotStarted` are all "not yet / dropped," no partial credit.
16. **The Created leg excludes `is_test` orders**, via a new direct `Order::query()` (not `ReportService::scopedOrders()`, which is Paid-only by design) — consistent with every other exclusion of ADR-018 sandbox orders from real metrics.

### DASH-4 — Top Games Weekly Ranking

17. **Reuses `ReportService::gameBreakdown()` unchanged**, called with a rolling trailing-7-day window (today back 6 days, Asia/Kuala_Lumpur) — same window definition as DASH-3, so "weekly" means the same thing everywhere on this screen. Ranking is therefore implicitly Paid-only/`paid_at`-scoped (whatever `scopedOrders()` already enforces), which is correct for a revenue ranking.
18. **"% change" compares the same window against the prior 7-day period** (day 8–14 ago) — two `gameBreakdown()` calls, diffed per game. **"New"** fallback (decision 4's same rule) when a game had zero revenue in the prior window.

### DASH-5 — Hourly Activity

19. **Single-day view, not a 7-day aggregate.** The day selector picks one specific date within the last 7 days; the chart renders that one day's 24 hourly buckets. An aggregate-across-the-week reading would make the day selector meaningless.
20. **Counts orders by `created_at`, excluding `is_test`** — matches DASH-3's Created leg (raw activity/attempt volume, not payment-filtered), giving this screen one consistent "created" definition instead of two.
21. **Hour buckets are 00–23 in Asia/Kuala_Lumpur**, matching every other day/time bucketing already established (`ReportService::dailyTrend()`).

### DASH-6 — Auto-refresh

22. **Only the DASH-2 health section auto-refreshes, every 60 seconds** — DASH-1/3/4/5's figures barely move within an hour; refreshing them on a timer burns backend load for no visible benefit. Plain client-side `setInterval` re-fetch of `/api/dashboard/health` — no WebSocket/SSE/Reverb infrastructure. `laravel/reverb` is not installed anywhere in this codebase, and standing up a broadcast server (new process, a `wss://` port through ADR-020's droplet, TLS for it) is real new infrastructure this project doesn't otherwise need yet, for a 60-second-cadence single-screen number — push-based delivery is the right tool once there's a genuine multi-admin real-time need (e.g. live notifications), not for this.
23. **Always-on, no pause/toggle control.** DASH-6 is an "Important," not MVP, requirement — a pause control is its own small feature not worth building for this.

### Cross-cutting: `orders.delivered_at` and the `definition` convention

24. **New nullable `orders.delivered_at` timestamp column, stamped at the exact point `delivery_status` becomes `Delivered`.** Found while pinning DASH-3 that no such column existed (`paid_at`'s own equivalent was never mirrored for delivery) — the founder's own call once this surfaced: worth fixing now, not scope-creeping around it, since the actual cost turned out low: `OrderStatusService`'s three `Delivered`-returning transitions (`markDelivered()`, `markDeliveredManually()`, `finalizePendingSuccess()`) are all consumed by exactly **three assignment sites, all in one file** (`OrderFulfillmentService.php`) — cheaper than `paid_at`'s own 4-5-file rollout. A backfill migration sets `delivered_at = updated_at` for any already-`Delivered` order missing it, flagged the same way `paid_at`'s own backfill was: `updated_at` is the best available proxy, not a guaranteed-exact original delivery timestamp (an order's `updated_at` could reflect a later, unrelated touch). DASH-3 itself doesn't depend on this column (decision 14) — its value is independent, opening the door to a future delivery-SLA/time-to-deliver metric without another schema pass.
25. **Every KPI/metric value returned by the new `/api/dashboard/*` endpoints ships alongside a `definition` string** — e.g. `{"value": 125000, "definition": "SUM(final_amount) where payment_status=Paid, paid_at = today (Asia/Kuala_Lumpur), excludes is_test orders"}` — rendered as a small clickable `(i)` info affordance on every card, both DASH-1 and DASH-2 through DASH-5 alike. Founder's own reasoning: a future definition change (e.g. deciding "stuck" should mean something different) shouldn't require asking Claude to re-derive and re-explain the current definition first — the answer is already sitting in the API response, self-auditable at any time via the network tab alone. **The definition string is generated backend-side, colocated with the calculation it describes** (in the same `DashboardService`/`ReportService` method, not hand-copied into the frontend) — a definition and its calculation living in two different codebases (Laravel vs. Next.js) would be exactly the kind of two-copies-of-one-fact drift this project's own conventions (ADR-044 decision 6, for instance) already exist to avoid.

### Endpoint shape

26. **Five granular endpoints under a new `Admin\DashboardController`, matching `Admin\ReportController`'s existing one-endpoint-per-concern shape** (lazy-fetched independently by the frontend, same as `/admin/reports`'s per-tab fetch pattern): `GET /api/dashboard/summary` (DASH-1), `GET /api/dashboard/health` (DASH-2, the only one polled per decision 22), `GET /api/dashboard/funnel` (DASH-3), `GET /api/dashboard/top-games` (DASH-4), `GET /api/dashboard/hourly-activity?date=YYYY-MM-DD` (DASH-5, the only one taking a request param, for the day selector). All five share the same `admin.role:super_admin,admin` tier (decision 10).
27. **Business logic lives in a new `App\Services\Dashboard\DashboardService`**, which delegates DASH-1 to `ReportService` (decision 3) rather than duplicating its rules, and owns DASH-2/3/4/5's own logic directly — DASH-3/5 need a raw `Order::query()` (decision 16/20) since `ReportService::scopedOrders()` is Paid-only by design and can't serve a Created-based leg.

**Rationale:** Every metric definition here follows the same discipline Reports established (pin the exact source/timestamp/table before writing a query, not after a bug surfaces) — DASH-3's cohort-vs-three-counts choice and DASH-2's derived-vs-live-ping choice are this ADR's two `Order.platform_profit`-style landmines, both resolved by asking "which one is actually true to what the requirement is asking," not by picking whichever is easiest to query. Reusing `ReportService` (DASH-1/4) and the `delivery_reconciliation` config (DASH-2) instead of parallel re-definitions is a direct application of AGENTS.md's "Single Source of Truth" principle — the same reasoning ADR-044 already applied to zod schemas replacing hand-written interfaces.

**Consequence to track:** The right-censoring bias in DASH-3 (decision 13) means a founder glancing at "today's" funnel drop-off during a traffic spike will see an inflated drop-off rate for orders too recent to have converted yet — worth a one-line UI caveat near the funnel, not just a code comment, so it doesn't get mistaken for a real quality signal. `delivered_at`'s backfill (decision 24) is an approximation for historical rows — don't treat pre-this-migration `delivered_at` values as precise if a future feature (e.g. delivery-SLA reporting) is built on top of it; only rows created after this ADR ships have a trustworthy value. The `definition` string convention (decision 25) is new precedent — any *future* dashboard/report metric this project adds should carry one too, or this screen ends up with some cards self-documenting and others not, undermining the whole point.
