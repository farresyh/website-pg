# ADR-041: Checkout-level idempotency key — client-generated key, unique DB constraint, replay/resume branching (built 2026-07-29)

**Context:** ADR-019's fix-now list closed most resilience gaps but explicitly left one open: a retried `POST /api/checkout` (customer double-click, client-side timeout retry) mints a brand-new `order_number` each time, which Xendit's own `reference_id` dedupe can't catch. **Decision (verbatim from ADR-019's original addendum):**

**Addendum — checkout-level idempotency key shipped, 2026-07-29 (later same session, new day's work — surfaced as a pre-requisite, not deferred further, while planning the platform's first deliberate real end-to-end purchase-workflow proof: Xendit test-mode + Gamevion production, grilled via `/mattpocock-skills:grilling` before implementation, same discipline as every other ADR-014-through-019 decision):** closes the one item this ADR's fix-now list explicitly left open above — a retried `POST /api/checkout` (customer double-click, client-side timeout retry) minting a brand-new `order_number` each time, which Xendit's own `reference_id` dedupe can't catch. Founder's own framing for why now, not later: about to run a real production-money test (Gamevion in production mode) for the first time — a network hiccup during *that* session is exactly when a double-order is most likely, so the known gap had to close before the test, not after.

Design (grilled decision, not assumed): a client-generated `idempotency_key` (storefront: `crypto.randomUUID()`, generated once when the Review Modal opens, unchanged across a resubmit of that same attempt — see `OrderForm.tsx`'s `idempotencyKeyRef`), stamped onto the Order **at creation** (not after payment succeeds) under a new `orders.checkout_idempotency_key` (nullable, **unique**) column — reserved this early specifically so a genuine race between two near-simultaneous requests carrying the same key fails one of them at the DB layer (`23000` unique-violation, caught as `DuplicateCheckoutAttemptException`), not just at an app-level `SELECT` that both requests could pass before either commits.

`CheckoutController::store()` now looks up `Order::where('checkout_idempotency_key', ...)` **before** re-running player-validation/blacklist/velocity checks (an Order tagged with the key already passed those in the request that created it — re-running would be redundant at best, double-count a velocity hit at worst) and branches three ways:
1. **Key not found** → normal `CheckoutService::initiate()` flow, now stamping the key at creation.
2. **Found, `payment_ref` already set** → pure idempotent replay (`200`, not `201`) — the same order/payment_actions a fresh checkout would have returned, no new Order, no second gateway call.
3. **Found, `payment_ref` still null** → the earlier attempt's Order was created but its payment call failed (gateway rejection, or the process died in between). New `CheckoutService::resume(Order, PaymentGateway, channelCode, channelProperties)` retries **only** the payment leg against that same Order, reusing its own already-snapshotted `final_amount`/customer fields (ORD-9 — never recomputed) — Xendit's own `reference_id` dedupe (`order_number`, unchanged) still applies as a second layer if that earlier attempt secretly reached Xendit despite failing to persist locally.

Deliberately **not** solved, recorded as an accepted residual rather than silently dropped: a race narrower than the unique-constraint window above — two requests that both pass the initial lookup in the same few milliseconds, before either's `INSERT` commits — resolves correctly (loser gets `DuplicateCheckoutAttemptException`, refetches the winner) but the winner's response may still show a null `payment_ref` if returned mid-flight. Judged not worth a retry-loop/polling mechanism for a window this narrow.
