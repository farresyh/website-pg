# ADR-022: Multi-gateway payment strategy — CHIP for Malaysia-local, Xendit retained for international + split-payment (built 2026-08-04)

> **Standing (2026-10-09):** In force as CHIP-only; Xendit decisions reversed by its own 2026-09-01 addendum. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-07-30 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, following primary-source research on CHIP and HitPay). **Superseded in part by this ADR's own 2026-09-01 addendum: decision 4 (retain Xendit) is reversed and decision 3 (CHIP scope) narrowed — the system is now CHIP-only, Xendit deleted. The seam and the rest of the 2026-08-03 addendum stand.** **Decision 2's "split-payment / payout API" framing is superseded by [ADR-059](./ADR-059-reseller-portal.md) decision 6:** reseller payout is a plain manual bank transfer (WTH-1..5), no CHIP Send / Disbursement integration.

**Context:** ADR-001 chose Xendit for the MVP with `xenPlatform` (OWNED sub-accounts) deferred to Phase 2 for reseller payout splitting — a design decision never actually exercised, since real third-party reseller onboarding has stayed out of scope (`docs/prd.md` §4.2) and the `Reseller` table's only row today is the platform owner (ADR-013). Two things changed this session:

1. While correcting `payment_methods`' seeded fee defaults against Xendit's real published rate card (`xendit.co/en/pricing`, see this doc's own prd.md §14 2026-07-30 entry), the founder confirmed Xendit's real Malaysia fees are materially higher than assumed — e.g. e-wallets 1.80%–2.50% (not the 1.9% blanket placeholder previously seeded), international cards 3.80%.
2. The founder stated, when grilled directly, that **real third-party reseller onboarding is now genuinely near-term**, not a hypothetical Phase 2 "someday" — which makes gateway-level split-payment/payout capability a live requirement, not a deferred one.

This prompted researching two candidate gateways — **CHIP** (`chip-in.asia`) and **HitPay** — against their own primary docs (full findings in `docs/archive/research-payment-gateways-2026-07-30.md`), then grilling the founder through the tradeoffs.

**Decision:**

1. **Split-payment/payout capability is a mandatory criterion today**, per the founder's explicit, non-negotiable call — reseller onboarding is near-term, not speculative.

2. **But gateway-level fund *segregation* is not itself mandatory.** Grilled directly: does the platform need the gateway to hold reseller funds in a separate pool (what `xenPlatform` OWNED does), or does it only need (a) a way to programmatically pay a reseller's computed share to their bank account, and (b) the reseller never learning who the underlying processor is? The founder agreed `ledger_entries`/`ledger_accounts` (ADR-002, lock-guarded, concurrency-proven, real-subprocess-tested) is already a sufficient source of truth for "who is owed what" — a gateway-side balance ledger would be a second, redundant safety net, not a load-bearing requirement. This reframes "split-payment capability" from "needs xenPlatform specifically" to "needs any payout API the platform can call on the reseller's behalf, invisible to the reseller" — which both `xenPlatform` **and** CHIP Send (a flat merchant-payout API, no sub-merchant concept) can satisfy mechanically the same way Phase 2 already planned for Xendit Disbursement (ADR-001's own consequence note: "the platform must supply the destination bank account on every Disbursement API call" — never automatic at the gateway either).

3. **Adopt CHIP as an additional gateway, scoped to Malaysia-local channels only** (FPX first). Decisive, confirmed-not-guessed reason: Xendit's real FPX rate is **also flat** (RM2.10 personal / RM2.90 business, `xendit.co/en/pricing`), so CHIP's flat RM1 (B2C) / RM2 (B2B1) FPX fee (`chip-in.asia/collect`) is an **unconditional per-transaction saving** — RM1.10/txn — with no breakeven or basket-size dependency, unlike an initial (wrong) draft of this analysis that assumed Xendit's FPX was percentage-based. Accepted tradeoff: CHIP's webhook verification is RSA PKCS#1 v1.5 (`X-Signature` + public-key fetch/cache), a genuinely more expensive integration than Xendit's plain-token compare — judged worth it for the FPX saving alone.

4. **Retain Xendit as the gateway for (a) international/cross-border customer-facing payment acceptance and (b) split-payment/reseller payout**, both roles, unchanged from today. Reasoning, per-role:
   - **International channel coverage:** the founder's named requirement is accepting each customer's own local method — Indonesia (GoPay/DANA/OVO/BCA), Philippines (GCash/Maya), Singapore (PayNow). Verified directly (not assumed): Xendit publishes GoPay/OVO/DANA/ShopeePay/QRIS/Virtual Accounts for Indonesia, GCash/Maya for Philippines (`xendit.co/en/products/all-payment-methods/`), and PayNow QR for Singapore (`docs.xendit.co/docs/payment-channel-page-push-14`) — full coverage of every named method. HitPay was evaluated and found weaker on this axis specifically for Indonesia: its own `availability-by-market` docs list Indonesia only via a generic cross-border QRIS scan, not named GoPay/DANA/OVO/BCA channels (Indonesia isn't a HitPay "core market" the way Philippines/Singapore/Malaysia are). The founder correctly pointed out QRIS alone can reach those same wallets since it's Bank Indonesia's interoperable standard — but since **Xendit also supports QRIS** for Indonesia in addition to the named channels, this narrows the gap without reversing it; Xendit remains at least as capable, at zero incremental integration cost.
   - **Split-payment safety:** Xendit's `xenPlatform` OWNED shape is **confirmed** (ADR-001, 2026-07-24 addendum) to satisfy the founder's non-negotiable "reseller must never know who the underlying processor is" requirement. HitPay's comparable feature ("Platforms", `X-PLATFORM-KEY`) is real but its OWNED-vs-MANAGED shape is **unverified** in HitPay's own docs — and a specific red flag was found, not just an absence of information: `docs.hitpayapp.com/apis/guide/platform-apis` describes sub-merchant integration via "direct API key access **or OAuth token authentication**," and the feature is not linked from HitPay's main API overview/nav at all (reachable only by direct URL or emailing `support@hit-pay.com` to enable). OAuth-based sub-merchant integration is the signature of a MANAGED shape (the sub-merchant authorizes their own connected account), the opposite of what the founder requires. **Decision: treat HitPay as disqualified for the split-payment role until/unless HitPay support confirms an OWNED-equivalent shape in writing** — not pursued further this session.
   - Net effect: HitPay is **not adopted in any role** this round. Its genuine strengths (widest channel breadth generally, cheapest webhook integration — HMAC-SHA256 vs CHIP's RSA) didn't move the decision because the two criteria that mattered most this session (Indonesia-specific coverage, split-payment safety) both favor the status quo (Xendit) once checked against primary sources.

5. **Sequencing for the CHIP adapter build:**
   - Start CHIP merchant registration now (business info + bank details, ~1–3 business day approval per `blog.chip-in.asia`'s own registration guide) — low-cost, doesn't block anything else.
   - **Whether CHIP issues test-mode API keys before that approval completes is genuinely unconfirmed** — checked directly against CHIP's authentication page, introduction page, and registration blog post; none state it either way. Unlike Xendit's history, don't assume pre-approval test access is available — confirm directly (registration itself, or asking `support@chip-in.asia`) rather than blocking adapter work on an assumption.
   - In parallel, build the `ChipGateway` adapter foundation (implementing the existing `PaymentGateway` interface — `createPayment()`/`getPayment()`/`verifyWebhookSignature()`/`parseWebhookEvent()`) directly from CHIP's published OpenAPI spec (`docs.chip-in.asia/openapi/chip-collect.yaml`), with `Http::fake()`-based unit tests matching the documented request/response shapes — the same seam-extension discipline this codebase already applies to `SupplierAdapter`/`PaymentGateway` (ADR-001, ADR-006: extend an implementation, don't reshape the interface). This can proceed without a live CHIP account.
   - **Do not mark the adapter "verified" or flip any `payment_methods.gateway` row to `'chip'` for a live channel until a real smoke-test command** (`app:chip-smoke-test`, mirroring the existing `app:xendit-smoke-test`/`app:gamevion-smoke-test`) proves it end-to-end against a real CHIP test or live account. This project has been bitten twice by undocumented API quirks only live testing caught — Xendit's mandatory `customer`/`customer_id` object (ADR-001, 2026-07-25 addendum) and Gamevion's `telp`-format bug (ADR-006) — docs-only confidence has already proven insufficient twice here, not a hypothetical risk.

**Rationale:** Every sub-decision above traces back to the same two moves: (a) recognizing that `ledger_entries`/`ledger_accounts` (ADR-002) already carries the load `xenPlatform` was originally chosen to help with, which reframed "split-payment capability" from a gateway-shape requirement into a much smaller, easier-to-satisfy "payout API + processor invisibility" requirement — and (b) insisting on primary-source verification over both the founder's and this assistant's own initial assumptions at three separate points (Xendit's FPX being flat not percentage-based, Xendit's Indonesia/Philippines/Singapore channel coverage, and HitPay's Platforms shape) before letting any of them settle the decision, matching this codebase's established "don't guess, verify against real docs" discipline (ADR-001, ADR-006, ADR-019, ADR-021).

**Consequence to track:**
- HitPay is not permanently ruled out — only disqualified for lack of a confirmed-safe split-payment shape today. Revisit if `support@hit-pay.com` confirms Platforms is OWNED-equivalent in writing.
- Xendit's Singapore PayNow activation may require its own Singapore business KYC (ACRA/UEN, director ID, SG corporate bank account per `xendit.co/en-sg`'s own onboarding requirements) distinct from the existing Malaysia-registered Xendit account — **not confirmed this session whether the existing account can simply add PayNow, or whether a parallel SG entity/KYC is needed.** Resolve before counting on PayNow specifically.
- CHIP's card channel (`CARDS`-equivalent) real-world tiering (debit/credit/international) and Boost support remain unverified per the research doc — relevant only once/if CHIP's card channels are activated, not blocking the FPX-first rollout.
- Whether CHIP issues test keys pre-approval is unconfirmed — resolve by actually registering, don't assume either way.
- This ADR is design/decision only: no adapter code written, no CHIP account registered, nothing purchased. Building `ChipGateway` and starting CHIP registration are the concrete next actions — update `docs/prd.md` §14/§15 as they ship, per this doc's own convention.

**Addendum — reconciliation gateway-routing gap closed, payment-method identity pinned, storefront live-wiring scoped, 2026-08-03 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any `ChipGateway` code):** planning the actual `ChipGateway` build (decision #5 above) surfaced a real latent bug this ADR itself had already flagged but not resolved: `ReconcilePendingPaymentsCommand` resolves `PaymentGateway` via the **default container binding**, not `PaymentGatewayFactory`, because `Order` has never persisted which channel/gateway it checked out with — silently correct only because Xendit is the only gateway that has ever existed. The moment a CHIP-paid order goes stale, this job would misroute it to `XenditGateway::getPayment()` instead of CHIP's — a silent money-status bug, not a hypothetical. Founder's explicit brief: prefer the solid, multi-step fix over the minimal one. Decisions, in order:

1. **`orders.payment_gateway` and `orders.channel_code` — denormalized snapshot columns, not an FK to `payment_methods`.** `payment_methods` rows are mutable admin config (fee/status edits already happen; nothing structurally prevents a future edit to `gateway`/`channel_code` either), so an FK would let historical orders' resolved gateway silently change if the row it points to is ever edited — the same reasoning this codebase already applies to pricing (ORD-9: `Order.cost_price`/`selling_price` snapshot at creation rather than following a live `Package` FK). Both columns are stamped in `CheckoutService::initiate()` at `Order::create()` time, using the `PaymentMethod` row `CheckoutController::store()` already resolves before calling in (confirmed: it's fully in hand at that point, nothing new to fetch). `channel_code` is snapshotted alongside `payment_gateway` even though reconciliation only strictly needs the latter — cheap to add now, and useful for support/reporting (which specific channel a stuck order used) independent of which gateway processed it.
2. **Backfill existing orders:** `payment_gateway = 'xendit'` for every existing row with a non-null `payment_ref` (every real order to date genuinely did go through Xendit — CHIP didn't exist yet, so this is fact, not a guess), `channel_code` left `NULL` for pre-existing rows (unrecoverable retroactively, and not needed for reconciliation's gateway-resolution logic, only for future orders' diagnostics). This keeps `ReconcilePendingPaymentsCommand`'s new `PaymentGatewayFactory::make($order->payment_gateway)` call from needing a NULL-handling special case for every order that predates this fix.
3. **Genuine-NULL edge case (should be near-impossible post-fix, but not assumed away):** if `payment_gateway` is still `NULL` when the job goes to reconcile an order, **skip that order and `Log::error()`** (not `Log::warning()`) with an explicit message pointing at `CheckoutService` as the place to investigate — deliberately never guess/fall back to `'xendit'`, which would silently reintroduce the exact misrouting bug this fix closes. The severity is escalated above the job's own pre-existing `flagIfStale()` warning (which fires for a *genuinely* ambiguous non-terminal gateway status — a normal, expected outcome) because a NULL `payment_gateway` here means the checkout path itself failed to do its job, a code bug signal, not routine payment ambiguity.
4. **`payment_methods.method_key`** — a new column identifying "the real-world payment method" independent of gateway (e.g. `tng`, `fpx_maybank2u`, `grabpay`), distinct from `channel_code` (gateway-specific, already unique) and from the existing coarse `category` (fpx/ewallet/card/virtual_account — too broad, since a category legitimately holds several simultaneously-active *different* real methods, e.g. TnG and GrabPay both active under `ewallet`). Surfaced by walking through the founder's intended storefront UI (one button per real payment brand, gateway never customer-visible — confirmed `PaymentMethod` has no `$hidden` but the storefront never fetches `gateway` today regardless, see #5) and asking directly what happens if, say, a Xendit-TNG row and a CHIP-TNG row are both `is_active` at once: since nothing today prevents two rows sharing a customer-facing identity from both being active, the storefront's existing one-button-per-`channel_code` rendering would show two visually-identical buttons for the same real payment method, with the customer unable to tell (or care) which processor either one uses — confirmed a real bug, not a theoretical one, since the founder's actual end-state (see the multi-region note below) is regional gateway *replacement* per method, never simultaneous dual-offering of the same method to the same customer. Fix: `PaymentMethodController::updateStatus()` gains an **app-level check** (not a DB-level constraint) blocking activation of a row whose `method_key` already has another `is_active` row, with a clear error message. App-level only was judged sufficient — unlike the automated, unattended Price Sync job that justified a real unique-index guard (ADR-015), this is a manual, low-frequency, single-admin action with no realistic concurrent-race exposure.
5. **Storefront payment-method rendering is not actually live today, for either gateway — a separate, pre-existing gap this session's UI walkthrough surfaced.** `storefront/src/lib/placeholder-data.ts`'s `PLACEHOLDER_PAYMENT_CHANNELS` is a hand-maintained, hardcoded list of channel buttons; no public endpoint returning `payment_methods` exists at all (`PaymentMethodController::index` is admin-only, behind `auth:sanctum`). The list only "works" today because whoever edited it manually kept it in sync with real active Xendit rows — the file's own doc comment already admits this ("accurate today even though the checkout call itself will 422 until an admin activates a matching row"). Left as-is, activating a CHIP row in `/middleware/payment-methods` would have **zero customer-facing effect** — CHIP would be fully built and smoke-tested but practically invisible, the same failure class as the CORS/redirect gaps this project has hit before (backend correct, unreachable from the browser). Decision: build one gateway-agnostic public endpoint returning active `payment_methods` (customer-safe fields only — `label`/`channel_code`/`category`; `gateway` and `method_key` stay backend-only, never serialized to the storefront), wire the storefront to it, and delete `PLACEHOLDER_PAYMENT_CHANNELS` once wired. Scoped into this same body of work rather than deferred, since it closes the pre-existing Xendit gap and is what makes CHIP reachable by a real customer at all — not multi-gateway-specific work.
6. **Build order, decided explicitly rather than left open:** (1) the `Order` snapshot columns + `ReconcilePendingPaymentsCommand` fix, shipped and fully tested standalone — deliberately *before* any `ChipGateway` code, since it's a real fix to today's Xendit-only reconciliation path and isolating it keeps any test failure attributable to one change, not a mixed batch; (2) `method_key` + the `updateStatus()` guard; (3) the public payment-methods endpoint + storefront wiring; (4) `ChipGateway` + config/env scaffolding + the `payment-gateway.chip` binding; (5) `ChipWebhookController` (RSA PKCS#1 v1.5 verification, per this ADR's own decision #3); (6) `PaymentMethodSeeder` gains the CHIP FPX row(s), `is_active=false`; (7) `app:chip-smoke-test`.
7. **Recorded here as an addendum, not a new ADR number** — every decision above is a direct consequence of adopting CHIP (closing a gap this ADR's own decision #5 sequencing implicitly required, and a UI/identity question that only exists because a second gateway now exists), not an independent architectural choice.

**Out of scope, deliberately not decided here:** the founder's longer-term intent is **country-based gateway routing** — Malaysia-detected customers pay via CHIP, other countries via Xendit, automatically, with no dual-offering of the same method to the same market. This is explicitly a future phase, blocked on multi-currency/multi-country storefront architecture that doesn't exist yet (geo-IP detection, per-country channel sets, currency-conversion implications on `PricingService`), and deserves its own grilled ADR when that work is actually planned — not decided or built as part of this addendum. `method_key` (decision #4) is deliberately shaped to stay compatible with that future direction (a stable per-method identity a future router could pick one active gateway-row for, per country) without needing rework, but no routing logic itself exists yet.

**Addendum — CHIP-only cutover, Xendit removed entirely, 2026-09-01 (grilled with the founder two rounds via `/mattpocock-skills:grilling`, before any code):** this addendum **reverses decision 4** (retain Xendit for international acceptance + split-payment) and **narrows decision 3** (CHIP scoped to FPX-first → CHIP is now the *only* gateway, covering whatever CHIP Collect methods the account activates). The multi-gateway framing of this ADR's title no longer describes the system: there is one gateway, CHIP.

**Context — what changed since 2026-08-04:**
- **The Soloz partnership did not close.** ADR-022's decision 4 rationale rested on the founder's 2026-07-30 statement that "real third-party reseller onboarding is now genuinely near-term." That has not materialised — [ADR-056..061](./ADR-056-reseller-wholesale-pricing-subscription-tiers.md) built the reseller *platform* but real external resellers remain unsigned, and revised volume expectations are ~RM100k/month (peak RM200–300k), down from the RM2M/month the larger-server and multi-gateway posture assumed.
- **Xendit's international-acceptance role was never actually wired.** Verified in-code this session, not assumed: `CheckoutService::requestPayment()` hardcodes `currency: 'MYR'` and `country: 'MY'` — the storefront has no multi-currency path, no geo-IP, no per-country channel set. The Indonesia/Philippines/Singapore local-method coverage decision 4 preserved was always a *future option*, never a live capability. Dropping Xendit removes zero working functionality.
- **Xendit's split-payment/payout role is already dead.** [ADR-059](./ADR-059-reseller-portal.md) decision 6 made reseller payout a manual bank transfer (WTH-1..5) — no CHIP Send, no Xendit Disbursement, no `xenPlatform`. `Reseller.xendit_subaccount_id` is a nullable column that has never held a value ([ADR-001](./ADR-001-payment-gateway.md) addendum's Phase 2 plan, superseded). RES-2 confirms all money — platform brands and `is_owned` reseller brands alike — lands in one company CHIP account.
- **CHIP does more than decision 3 assumed.** CHIP Collect's own account portal (`portal.chip-in.asia`, checked live this session) offers FPX (B2C + B2B1), DuitNow QR, e-wallets, ShopeePay, local + international cards, Atome / SPayLater BNPL, Google Pay, and cross-border QR from Singapore / Thailand / Indonesia. The "no API to report which channels are enabled" claim in `PaymentMethodSeeder`'s doc comment is **wrong for CHIP** — `GET /payment_methods/?brand_id=…&currency=MYR` returns `available_payment_methods` for the account (test/live keyed by the API key used). The cross-border QR support also means the Indonesia/PH/SG reach decision 4 wanted is partly recoverable through CHIP itself if it ever becomes real.

**Decision:**

1. **Delete the Xendit integration outright** — `App\Services\Payment\Xendit\XenditGateway`, `XenditWebhookController`, the `/webhooks/xendit` route, `XenditSmokeTest`, the `config/services.php` `xendit` block, the `payment-gateway.xendit` container binding, `Reseller.xendit_subaccount_id` (drop-column migration), and all Xendit-specific tests. `PaymentGateway::class`'s default container binding moves from Xendit to CHIP.

2. **Keep the seam** — the `PaymentGateway` interface, `PaymentGatewayFactory`, `payment-gateway.<name>` binding convention, and the `orders.payment_gateway` / `orders.channel_code` snapshot columns all stay exactly as they are. They are already gateway-agnostic; a future multi-region ADR that re-introduces a second gateway wants them back, and removing then re-adding the factory is pure churn. `ChipWebhookController` and `ReconcilePendingPaymentsCommand` keep resolving through the factory. Historical orders keep their `payment_gateway = 'xendit'` snapshot value (it is true — those orders did go through Xendit).

3. **CHIP is the only gateway; it covers whatever CHIP methods the account activates.** `ChipGateway` already passes `payment_method_whitelist: [channelCode]` straight through — supporting a new CHIP method is a `PaymentMethodSeeder` row plus admin activation, no adapter change. No adapter rewrite is done pre-emptively; real request/response shapes are verified against the live API via `app:chip-smoke-test` and patched from what the real responses show, per this ADR's own decision 5 discipline (which stands).

4. **Launch scope: FPX B2C + DuitNow QR active, FPX B2B1 seeded inactive.** These are the two methods the founder has requested on the CHIP account (both `Pending` review as of 2026-09-01); B2B1 (corporate-client FPX) is seeded but left inactive — a top-up storefront serves individuals, flip it on only if corporate demand appears. E-wallets, cards, and BNPL each need their own CHIP `Request` + approval (cards additionally need underwriting, and carry chargeback exposure + tiered debit/credit/international rates ADR-022's consequence list already flags as unverified) — each is its own follow-up: request → approve → seeder row → smoke-test → activate. Cards specifically get a short ADR note on chargeback/fee handling before activation.

5. **DuitNow QR redirect-model risk, resolved at build time.** FPX redirects the customer to CHIP's hosted page. If CHIP renders the DuitNow QR on that same hosted page (redirect model), `ChipGateway`'s existing `actions: [{type: REDIRECT, …}]` normalisation is sufficient. If CHIP instead returns a raw QR payload the storefront must render itself, that is a storefront change and DuitNow QR is deferred — launch FPX-only, add DuitNow QR when it can be verified end-to-end. The smoke test settles which.

6. **Webhook model resolved at build time, not grilled.** CHIP has two webhook mechanisms — portal-configured webhooks (each with its own key pair) vs a Purchase-level `success_callback` verified against the account key from `GET /public_key/` (what `ChipGateway::verifyWebhookSignature()` assumes today). The assistant resolves which to use against CHIP's current docs during the build and configures it; the founder is told only if it carries a cost or decision implication.

7. **This-session deliverable vs staging.** CHIP methods are `Pending` (not yet approved), so this session ships: `ChipGateway` verified as far as a pending test account allows, Xendit deleted, archive branch + tag, this addendum, `.env` wired (test key + `brand_id`), `app:chip-smoke-test` run and its result documented (a "method not active" failure is expected and acceptable — the `Http::fake`-based `ChipGatewayTest` still proves adapter correctness). Real end-to-end (a live test payment through the hosted page + a real webhook delivery) is done on staging after CHIP approves FPX. **Launch gate: ≥1 CHIP method smoke-tested green and live — not "all methods approved."**

8. **Archival:** branch `archive/xendit-gateway` (pushed to origin, never deleted) + tag `xendit-archive-2026-09-01`, both pointing at the pre-removal `staging` HEAD, so the full Xendit integration stays recoverable without leaving dead code in the tree.

**Rationale:** decision 4 of the original ADR was explicitly contingent on near-term reseller onboarding and international selling, both of which the founder confirmed this session are not happening on the relevant horizon. With those gone, retaining Xendit means carrying a second, un-smoke-tested gateway integration (config, binding, webhook route, ~500 lines + tests) purely to keep a future option open — an option that a future multi-region ADR would re-open anyway by adding whatever gateway fits *that* market, behind the seam decision 2 preserves. The cost of deletion is one archive branch; the cost of keeping is ongoing maintenance of a code path nothing exercises. CHIP's flat FPX fee (RM1 B2C / RM2 B2B1 vs Xendit's RM2.10 / RM2.90) was already the reason CHIP was adopted; making it the sole gateway just removes the half of ADR-022 that time has invalidated.

**Consequence to track:**
- **International acceptance is now genuinely gone, not merely dormant.** If cross-border selling becomes real, it needs its own grilled ADR — CHIP's cross-border QR (SG/TH/ID) is the first thing to evaluate before re-adding any second gateway.
- The multi-region routing note in the founder's backlog is reframed: "add a gateway when multi-region selling is actually planned," not "keep Xendit idle for it."
- `ChipGateway` correctness beyond FPX (e-wallet redirect shapes, card 3DS/tiering, DuitNow QR rendering) stays unverified until each method is approved and smoke-tested — do not activate a CHIP method on the strength of `Http::fake` tests alone (decision 5 of the original ADR, unchanged).
- The `PaymentMethodSeeder` doc comment claiming "neither gateway has an API to report which channels are actually enabled" is corrected for CHIP. A future "sync CHIP methods from `GET /payment_methods/`" feature (a mini Price Sync) is deliberately **not** built here — it is real scope and gets its own ADR if wanted; activation stays manual per decision 5.
- `docs/prd.md` §14/§15 updated as this ships.

**Smoke-test result, 2026-09-01 (same day):** `app:chip-smoke-test` run against the real CHIP API with the JW CORE VENTURE test-mode key — **`createPayment` and `getPayment` both succeeded**, despite FPX being `Pending` review (CHIP's test mode created the purchase anyway, `payment_method_whitelist: ['fpx']` accepted). Confirmed live, not assumed: Bearer auth, the `POST /purchases/` request body shape (`brand_id` / `reference` / `client` / `purchase.products` / `purchase.currency` / `payment_method_whitelist`), `GET /purchases/{id}/`, and that CHIP returns a bare `checkout_url` string which `normalizePurchase()` turns into the `actions: [{type: REDIRECT, descriptor: WEB_URL, value}]` array the storefront already consumes. Real request/response shapes match `ChipGatewayTest`'s `Http::fake` assumptions — `ChipGateway::createPayment()`/`getPayment()` are now **verified** per decision 5. **Still unverified:** the webhook path (RSA `X-Signature` verification, `parseWebhookEvent()`) and the `paid`-status flow — these need a real test payment carried through CHIP's hosted page plus a real webhook delivery, done on staging once it has a public URL and CHIP approves FPX. No `payment_methods` row is flipped `is_active` until both of those land.

**Webhook-model resolution — per-purchase `success_callback`, 2026-09-02 (the 2026-09-01 addendum's decision 6 deferred this to build time; FPX is now approved, so it is resolved here — grilled with the founder via `/mattpocock-skills:grilling`, 3 rounds, since it is the money path).**

**Context:** the 2026-09-01 addendum's decision 6 left "portal-registered webhook vs per-purchase `success_callback`" for the assistant to settle at build time. CHIP FPX approval unblocked the real end-to-end test, forcing the choice. Facts confirmed from CHIP's live OpenAPI spec + docs (`docs.chip-in.asia/openapi/chip-collect.yaml`, `/chip-collect/overview/webhook-signatures`), not assumed:
- **`success_callback`** (a URL on `POST /purchases/`) delivers a signed, JSON-encoded Purchase + an `event_type` field **only when a purchase is successfully paid** (or captured, for `skip_capture=true` — this adapter never sets that). Verified against the account key from `GET /public_key/` — exactly what `ChipGateway::verifyWebhookSignature()` already does, and the payload shape `ChipGatewayTest`/`ChipWebhookControllerTest` already assume.
- **Registered webhooks** (portal- or API-created) carry a **per-webhook** `public_key`, subscribe to 27 typed events (`purchase.payment_failure`, `purchase.cancelled`, `payment.charged_back`, `payout.*`, …), and are portal state that can drift (deleted, wrong URL, wrong event set, key regenerated).

**Decision:**

1. **Use the per-purchase `success_callback`.** `ChipGateway::createPayment()` now sends `success_callback` = `config('services.chip.callback_url')` (a new key, default `rtrim(APP_URL,'/').'/api/webhooks/chip'`, env override `CHIP_CALLBACK_URL` only for pointing a local tunnel at it during go-live testing). No portal webhook is registered. `verifyWebhookSignature()` is unchanged in mechanism (account key from `GET /public_key/`).

2. **Non-paid outcomes (failure / cancel) are handled by `ReconcilePendingPaymentsCommand` (PAY-3), not the webhook.** `success_callback` never fires for them; grilled and accepted — the customer already saw the failure on CHIP's hosted page and was returned to `failure_redirect`, so the only server-side work outstanding is flipping the order to `Failed` and restoring any reserved voucher, which the 15-min poll does. The controller's existing non-paid branch stays (it costs nothing and covers a hypothetical future event source).

3. **Typed-event model deliberately not adopted.** Its consumers are all out of scope: refunds (ADR-004 — none, ever), chargebacks (FPX/DuitNow QR are bank-debit, effectively none; cards deferred with their own ADR note per the 2026-09-01 addendum decision 4), payout automation (ADR-059 decision 6 — manual bank transfer). If any becomes real, that ADR adds a registered webhook then — the same way this ADR keeps the `PaymentGateway` seam for a future gateway.

4. **Key-rotation resilience.** A cached account key that stops verifying a genuinely-signed delivery is what a CHIP-side rotation looks like. `verifyWebhookSignature()` now re-fetches once and retries against a genuinely-different key before rejecting, rate-limited to one live `GET /public_key/` per 60 s so a forged-signature flood can't hammer CHIP. A still-rejected delivery falls through to PAY-3 (the order still gets delivered, just on the 15-min poll instead of instantly). 24 h happy-path TTL unchanged.

5. **Go-live test sequence** (no separately-deployed staging server exists — AGENTS.md): **(a)** local backend + a temporary public tunnel (`cloudflared`) + `CHIP_CALLBACK_URL` pointed at it + CHIP **test-mode** key — create a purchase, mark it paid in CHIP's test tools, confirm the real signed `success_callback` verifies, parses, flips `payment_status=Paid`, and dispatches `FulfillOrderJob` (delivery completes against **Gamevion sandbox**, which is functional per ADR-006 — zero real money, and the sandbox flag never touches a production Supplier row). **(b)** production, CHIP **live** key, one real RM1 FPX payment through a temporarily-promoted cheap Gamevion package — proves the live key + real bank redirect + live callback signature; delivery may land in `NeedsReview` (supplier balance is Rp 0) and is cleared by hand, since the fulfilment path itself was already proven in (a). **(c)** flip the `fpx` `payment_methods` row `is_active`. **(d)** DuitNow QR is a separate phase — same `success_callback` (channel-agnostic), but its hosted-page-vs-raw-QR render model still needs the check the 2026-09-01 addendum decision 5 describes.

**Consequence to track:**
- `success_callback` gives no server-side signal for a failed/cancelled payment — a stuck `pending` order waits up to 15 min for PAY-3 to resolve it and restore its voucher. Acceptable per decision 2; revisit only if that window proves too long in practice.
- The webhook route is now named `webhooks.chip`; `config('services.chip.callback_url')` is the single source for the URL CHIP is told.
- Chargeback exposure stays zero only while the active channels are FPX / DuitNow QR. Activating cards (its own ADR) must add a registered webhook for `payment.charged_back` at that point.
