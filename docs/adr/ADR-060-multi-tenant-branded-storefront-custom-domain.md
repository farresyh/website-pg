**Context:**
- `ADR-020` / `ADR-066`: production is a DigitalOcean droplet managed by **Laravel Forge** (native PHP-FPM/nginx/Redis/Horizon), TLS via Forge Let's Encrypt, at `api.pekangame.space`; the three frontends are on Vercel. The Cloudflare-fronting / Cloudflare-for-SaaS piece (ADR-020 decision 8) is still pending the domain transfer. `ADR-037` staging *infra* (a deployed staging environment, as opposed to the branch workflow) is not built.
- Founder decision this session: **custom domains only, no subdomains.** A reseller buys their own domain and points it at the platform; the platform serves them a branded storefront on that domain. No `reseller.ourplatform.com` option.
- Money flow, settled this session: the end customer on a reseller's branded storefront pays the **full retail price into the one company CHIP account**. On payment + delivery, the ledger splits — platform revenue = the reseller's wholesale cost (`cost_price × (1 + tier.markup_percent)`, ADR-056); the reseller's earnings account is credited the margin (`customer_price − wholesale_cost`). The reseller never collects retail directly in this channel. `/admin/orders` shows every reseller order in full, labelled per reseller (founder).
- `storefront/` is one Next.js app on Vercel (`output: "standalone"` was removed in ADR-066 — Vercel-native, not Dockerized). `ADR-011`: guest checkout only, no cookies.

**Decision:**

1. **One `storefront/` app serves every reseller domain** — multi-tenant by `Host` header, resolved server-side (SSR / route handler) to a `Reseller` row via its `domains` JSON (existing column) or a dedicated `reseller_domains` table (decision 4). Not a deploy per reseller. The platform's own storefront is the `Reseller::platformOwner()` row on the platform's own domain — the same code path; `platformOwner` is just another tenant.

2. **Per-`Host` resolution scopes** branding (`reseller_branding` / `reseller_footer_settings` / `reseller_seo_settings`, `ADR-028` / `ADR-029`), catalog visibility (ADR-059 decision 3 game toggles), and pricing (ADR-056 — `customer_price = effective_base × (1 + reseller.markup_pct / 100)`). An unrecognized `Host` returns a generic 404 / landing — never the platform storefront's content under the wrong brand.

3. ~~**Custom-domain TLS via Cloudflare for SaaS (SSL for SaaS).** The reseller creates a CNAME (`shop.` or `www.` of their domain — an apex needs CNAME flattening, documented in the portal) pointing at a platform fallback-origin hostname; the platform registers their hostname via the Cloudflare Custom Hostnames API; Cloudflare issues and auto-renews the edge certificate. Chosen over host-Nginx Let's Encrypt automation because Cloudflare is already the platform's edge (`ADR-020` decision 8) and per-customer-domain cert lifecycle is precisely what this Cloudflare product does. Cost (~USD 0.10 / active hostname / month + plan) is accepted.~~ **Reversed 2026-09-06 — see the "domain lifecycle fully specified" build addendum below.** The premise (storefront is a Dockerised app on the droplet behind Cloudflare's edge) died with ADR-066 (storefront moved to Vercel) and the 2026-09-06 Cloudflare cutover (all three frontends deliberately kept Vercel-direct). Custom-domain TLS + routing is now Vercel's native per-project custom-domain support.

4. **Domain lifecycle** — the admin adds the reseller's domain in Reseller Management (ADR-058); the system calls the Cloudflare API to create the custom hostname, stores its status, and the portal's Domain screen (ADR-059) shows the reseller the CNAME + any DCV TXT record to set. Status polls Cloudflare (or consumes a Cloudflare webhook): `pending` → `active`. Reuses the `last_checked_at` / `last_status` shape from `PlayerValidatorProfile`. Deactivating (RES-5) or deleting (RES-6) a reseller removes the Cloudflare custom hostname.

5. **The ledger split is written at the same point the platform storefront writes its order ledger entries today** — on payment confirmed + delivery, inside the existing fulfillment path, extended to: (a) credit the reseller earnings account the margin, (b) book platform revenue at the wholesale amount rather than the full retail. `pricing_basis` (already on `orders`, `ADR-027`) gains a `reseller` value alongside `standard` / `member`; `reseller_id`, `reseller_markup_pct`, `reseller_profit` (columns already on `orders`) are snapshotted per ORD-9.

6. **No membership and no vouchers on a reseller storefront** — membership per `ADR-027` decision 9; vouchers deferred because "which ledger absorbs a voucher on a reseller sale" is an unanswered question and not needed for launch. The CHIP transaction fee is charged on top of the customer price, customer-borne, same as the platform storefront today (`transaction_fee`, ORD-9). Order delivery failure ⇒ retry (`ADR-004`); no voucher path on this channel for now.

7. **Reverb / realtime** (`ADR-047`) — the branded storefront's order-status tracker needs the same realtime channel wiring as the platform storefront; the per-`Host` origin must still reach `/app/` on the same backend. Confirm the Cloudflare custom-hostname config proxies WebSocket for reseller domains too.

**Rationale:** One app, `Host`-resolved (decision 1), is the only tenant model that doesn't multiply deploy / ops cost per reseller and keeps the platform storefront on the exact same code path (it's just `platformOwner`'s tenant). Cloudflare for SaaS (decision 3) is chosen not on cost but on fit — the alternative (Let's Encrypt on the host Nginx, on-demand issuance + renewal + LE rate-limit management for arbitrary customer domains) is a real ops burden for a solo founder, and Cloudflare is already the edge. Decision 5 (collect retail centrally, split in the ledger) is the founder's explicit money model and is what makes xenPlatform unnecessary (ADR-059 decision 6) — the ledger does the split.

**Build addendum — domain lifecycle fully specified + custom-domain mechanism reversed (Cloudflare for SaaS → Vercel-native), grilled 2026-09-06.** A scoped grill (domain-lifecycle sub-area only — the ledger split, the `PricingResolution` resolver, and `Host` resolution were explicitly *not* re-opened) closed every remaining unknown in how an affiliate's custom domain gets registered, verified, served, and torn down. The `affiliates.domains` JSON column and decision 3's Cloudflare-for-SaaS mechanism are both replaced.

**A. Data model — new `affiliate_domains` table, not `affiliates.domains` JSON.** The reference UI the founder wants (multiple domains, per-row validate tick, per-row status, a "Set Primary" button) needs per-row lifecycle state a JSON blob can't index or uniquely-constrain. Columns: `affiliate_id` (FK, `BelongsToAffiliate` trait like `Redirect`), `hostname` (**globally unique** — one hostname belongs to exactly one affiliate across the whole system), `is_primary` (bool), `status` (`pending` / `active` / `failed` / `suspended`), `provider` (string, default `'vercel'` — a provider-neutral column so a future swap needs no migration), `provider_ref` (nullable — the provider's domain-on-project identifier; **NULL on the seeded primary rows**), `verification` (JSON nullable — the TXT-challenge payload when the provider requires an ownership proof), `last_checked_at`, `verified_at`, `last_error` (nullable, sanitised), timestamps. The existing `affiliates.domains` JSON column is migrated to rows (prod has none) and dropped; `domains` is removed from `StoreAffiliateRequest` / `UpdateAffiliateRequest` (admin no longer sets domains — see F).

**B. Custom-domain TLS + routing — reverses decision 3, now Vercel-native.** One `storefront/` Vercel project, many attached custom domains (Pro: effectively unlimited, soft cap 100k/project, **$0 per domain** vs Cloudflare's ~$0.10/hostname/mo). A `VercelDomainService` (the one seam, credentials per ADR-046: `services.vercel.{token, team_id, storefront_project_id}`, token scoped to Domains on that project only) calls `projectsAddProjectDomain` / `projectsGetProjectDomain` / `projectsVerifyProjectDomain` / `projectsRemoveProjectDomain`. Vercel issues **and auto-renews** the per-domain certificate — no fallback-origin hostname, no DCV-delegation record, no Cloudflare Custom Hostnames API, no webhook-HMAC (decision 7's WebSocket concern also dissolves — the storefront's realtime channel already runs against `api.pekangame.space`, unchanged). A TXT ownership record is required **only** in the rare case the hostname is already attached to another Vercel account; otherwise the affiliate sets one record and Vercel auto-verifies.

**C. Provider opacity — the portal never names the provider (founder's explicit call, risk reduction).** The affiliate-facing Domain screen — every label, help string, status badge, and error message — must be provider-agnostic. Concretely:
- The CNAME target the affiliate copies is **a platform-owned alias**, `connect.pekangame.space`, a DNS-only (grey) CNAME in the platform's own Cloudflare zone pointing at the storefront project's Vercel CNAME target. A chained CNAME (`shop.affiliatedomain.com` → `connect.pekangame.space` → Vercel) resolves and verifies fine — this is the standard white-label pattern; confirm during PR-5.
- Apex-with-ALIAS/flattening points at the same `connect.pekangame.space` (no IP exposed). Apex-without-ALIAS is the only case that falls back to the raw A record (`76.76.21.21`) — a minor, accepted provider signal an affiliate would have to actively look up; `www.` / `shop.` is the recommended path and keeps the provider fully hidden.
- Every error surfaced from the Vercel API is **sanitised** before it reaches the affiliate ("this domain is already registered elsewhere — contact support", not the raw provider string). The ADR and internal docs may name Vercel; the portal may not.

**D. Onboarding + approval — full self-serve, no admin gate.** The affiliate adds a hostname in the portal → the system calls the provider API immediately → the row sits `pending` → the storefront serves that brand **only** once `status = active`. There is no admin approval step: provider-side domain-control verification *is* the ownership proof (the cert never issues for a domain the affiliate can't set DNS on). Guards: a per-affiliate cap of **5** domains; `hostname` globally unique; a denylist rejecting `*.pekangame.space` and any `is_owned` affiliate's domains; FormRequest rejection of IPs, ports, paths, and malformed hostnames. Only `status = 'active'` affiliates may manage domains — a not-yet-activated (`pending`) affiliate sees "activate your account first"; a **lapsed-subscription** affiliate keeps full domain management (domain ≠ subscription; its storefront still serves, at standard pricing per the 2026-09-05 addendum §3); a **deactivated** (RES-5) affiliate's Domain screen is read-only.

**E. Multi-domain, canonical, redirects.** Up to 5 domains per affiliate; exactly one `is_primary` (must be `active`), used for the canonical URL (`<link rel="canonical">`, OG url, sitemap) — non-primary domains still serve the full storefront, not a redirect, but carry the canonical tag pointing at the primary to avoid duplicate-content penalties. The first domain to reach `active` auto-becomes primary; the affiliate can re-point primary later, only among `active` domains. `www`↔apex redirects: the affiliate may set both hostnames, and the system registers both on Vercel with the redirect configured there; which one is canonical is the affiliate's choice.

> **2026-10-08 — the canonical half of section E was never built** (no `rel=canonical` anywhere; sitemap/robots/`llms.txt`/JSON-LD on affiliate domains all read `pekangame.com`). Built by **ADR-120** decisions 1–3: the backend returns the brand's `canonical_origin` from its active `is_primary` domain.

**F. Admin controls — read-only + two break-glass buttons.** The existing `AffiliateDetailModal` gains a "Domains" section: the hostname list with per-row status and `last_checked_at`, plus **"Force re-check"** (calls the provider) and **"Remove domain"** (deletes the provider domain + the row — for abuse or an affiliate request). **No add-domain form in admin** — the single write path is affiliate self-serve (or the founder via RES-4 impersonation). This narrows decision 4's "the admin adds the reseller's domain".

**G. CF/provider hostname lifecycle transitions.**
| Event | Action |
| --- | --- |
| Affiliate deactivated (RES-5) | Every domain row → `suspended`; the provider domain is left attached but the storefront returns 503 for a `suspended`/non-`active` Host. Reactivate → rows return to `active` (DNS still valid) or `pending`. |
| Affiliate deleted (RES-6, earnings = 0 only) | `VercelDomainService` removes every provider domain; rows soft-delete with the affiliate. |
| Stuck `pending` (affiliate never sets DNS) | After **14 days** the daily reconcile command removes the provider domain and marks the row `failed`; Plunk reminder emails on day 3 and day 7. The affiliate can re-add. |
| Affiliate removes the CNAME after `active` | The poll (or a provider webhook, if wired) flips the row to `failed`; the storefront returns 503 for that Host. If it was the primary and another `active` domain exists, primary auto-fails-over to it; if none, that brand's storefront is unreachable but checkout/orders on other channels are unaffected. |

**H. Status sync.** Primary mechanism: a daily `app:sync-affiliate-domain-status` command polls the provider for every non-`active` / non-`suspended` row (same posture as the Digiflazz poll backstop). Plus a portal "Check now" button that polls on demand. A provider webhook is optional and additive, not required.

**I. Primary affiliate's own domains.** `pekangame.space` and `www.pekangame.space` are seeded as ordinary `affiliate_domains` rows on the primary affiliate (`provider_ref = NULL`, `status = 'active'`, `is_primary` on the apex). **All lifecycle logic — create / verify / suspend / delete / poll / stuck-pending TTL — skips any row where `provider_ref IS NULL`.** `Host` resolution treats them identically to any affiliate's rows, so there is exactly one code path. This matches ADR-061: the primary is just another tenant; "our own brand" and consumer-membership are the *only* real differentiators, and other `is_owned` brands (a second business) go through the normal Vercel custom-domain flow like any third party.

Infra prerequisite (a `/wizard`-shaped founder step, before PR-5, not a code PR):** issue a Vercel API token (Domains scope, storefront project only) into Forge `.env`; create the `connect.pekangame.space` DNS-only CNAME in the platform Cloudflare zone pointing at the storefront project's Vercel CNAME target; confirm the storefront project's team is on the Vercel Pro plan.

**PR-2 build addendum — `X-Storefront-Host` transport pinned, backend `Host` resolution shipped (2026-09-06).** One thing the ADR body never pinned: *how* the affiliate's domain reaches the backend. The storefront (Vercel) calls `api.pekangame.space` directly from both SSR and the browser, so the visitor's own domain (`shop.acme.com`) never arrives as the HTTP `Host` — it is `api.pekangame.space` on every backend call. Resolved: the storefront forwards it in an explicit **`X-Storefront-Host`** header (PR-3 wires the frontend side).

- **Trust model:** the header is spoofable, but a brand only controls branding display, catalog visibility, and markup — and a third-party affiliate's price is always ≥ the primary's (they add margin on top of standard retail), so there is no price arbitrage. Worst case is a mis-attributed `affiliate_id` on an order, which grieves an affiliate's margin for no attacker gain. A later hardening (signed header, or trusting only the Vercel egress) can tighten this without touching the resolver. **Founder-approved 2026-09-06.**
- **Shipped in PR-2:** `affiliate_domains` table (per addendum section A — globally-unique `hostname`, `status`/`is_primary`/`provider`/`provider_ref`/`verification`/`last_checked_at`/`verified_at`/`last_error`; `BelongsToAffiliate`). *(PR-2 also seeded the primary's hostnames from `STOREFRONT_PRIMARY_HOSTS` into this table; PR-3 dropped that in favour of a config short-circuit — see the PR-3 addendum. The table now holds only non-primary brands' domains.)* `AffiliateDomainStatus` enum. `App\Support\StorefrontBrand` (scoped holder, lazy `Affiliate::primary()` fallback). `App\Http\Middleware\ResolveStorefrontBrand` (`storefront.brand` alias) — reads the header, resolves an **active** row whose affiliate is **active + not soft-deleted**, else `abort(404)` (decision 2 — never serve a brand under an unknown/suspended host); clears the holder at the top of every request (Octane / sequential-test safety, mirrors `SetAffiliateContext`). Applied to the `catalog` route group + the membership routes. `BrandingController::show`, `SeoController` (settings/redirects/recordRedirectHit/scripts), `MembershipController`, `MembershipOtpController` resolve via `StorefrontBrand` instead of `Affiliate::primary()`.

PR-2 is **entirely inert in production until PR-3 sends the header** — its value is the proven seam.

**PR-3 build addendum — storefront sends the header; primary hostnames are config not rows (2026-09-06).**

- **`X-Storefront-Host` from the frontend** (`storefront/src/lib/api-client.ts`): browser → `window.location.host`; SSR → the incoming request's `x-forwarded-host ?? host` via a guarded dynamic `import("next/headers")` (kept out of the client bundle). Also appended as a `__brand` query param on **cached** SSR reads so Next's Data Cache keys per brand regardless of header-keying behaviour (the backend ignores `__brand`).
- **Multi-tenant ⇒ dynamic rendering.** Reading `headers()` opts every storefront route out of static prerendering (`ƒ Dynamic` in the build) — inherent to a per-`Host` shell, and it reverses part of ADR-071's static-shell posture. `next: { revalidate: 60 }` still Data-Caches the branding/SEO/catalog `fetch`es (independent of route-level dynamic), now per brand, so a warm render is cache-lookups not backend round-trips. `safeRead` + `resolveStorefrontHost` both call `unstable_rethrow` so the `headers()` prerender bail-out (and `notFound()`/`redirect()`) propagate cleanly instead of being swallowed and hanging `next build`.

This removes the local-dev / E2E migration-timing friction (just set the env, no seed-before-migrate). The PR-2 migration's seed block is dropped (it was a no-op in every environment — the env was set nowhere). "Our own infra hostnames are config; customer domains are data."
- **Per-brand NOW:** store name / description / support contacts, SEO meta + GA/FB/TikTok pixels, Organization JSON-LD, footer store name — all already flow from the PR-2 brand-resolved endpoints once the header arrives, so the frontend needed no render-layer changes beyond the header. **Deferred:** logo (`affiliate_branding.logo_url` → PR-6), per-brand hero slides (`hero_slides.affiliate_id` → PR-6), catalog + checkout **pricing** and the backend catalog **cache keys** (→ PR-4, atomically with the ledger split so display never diverges from charge). An unrecognised `Host` currently degrades to the fallback storefront (default branding, empty catalog) rather than a hard "store unavailable" page — the hard 404 needs a storefront `middleware.ts` and waits for PR-5, when custom domains (hence unknown hosts) first exist.
- **E2E:** `e2e/scripts/boot-backend.sh` exports `STOREFRONT_PRIMARY_HOSTS=localhost` (the Playwright storefront host).
- Production impact: the live `pekangame.space` storefront now routes through the header path but resolves (via the config short-circuit) to the same `Affiliate::primary()` — **zero behaviour change**, only the render mode shifts to dynamic.

**Build addendum — PR-4 grilled + re-split into four sub-PRs, foundation-first (2026-09-06).** A full codebase audit of every money seam ahead of PR-4, then a `/mattpocock-skills:grilling` session with the founder. The founder's framing drove it: **affiliate / reseller-wallet / membership are one ecosystem, serviced differently — the backend core must be solid before a fourth money path is wired onto it.** The audit found the "one seam" is only half-built: `CheckoutPricingResolver` covers storefront checkout (standard/member) but the reseller-wallet channel (API + Bot) hand-rolls the same `PricingService::calculateForAffiliate(cost, standard, tier%, 0.0)` call **inline in three places** (`ResellerOrderPlacementService`, `ResellerBotService::handleListGamePackages`, `ResellerApi/CatalogController`), and `Order::query()->create([...])` is hand-built in three services with divergent column sets and duplicated idempotency/dispatch logic. Wiring `affiliate` pricing into that as-is would deepen the divergence at the exact moment real third-party money starts splitting.

**Decisions:**

1. **`PricingResolution` becomes the cross-channel money VO for product-sale order channels** (guest top-up / member top-up / affiliate storefront / reseller-wallet). `CheckoutPricingResolver` is renamed **`OrderPricingResolver`** with two channel-explicit entry methods, each returning one `PricingResolution`:
   - `resolveStorefront(...)` — the existing standard/member/affiliate/affiliate-lapsed 2×2 (`tierMarkupPct` null ⇒ Standard basis, non-null ⇒ Affiliate basis).
   - `resolveResellerWallet(costSen, standardSellingSen, tierMarkupPct)` — the wallet channel, mirroring `PricingService`'s own `calculate()` vs `calculateForAffiliate()` split.
   `ResellerOrderPlacementService`, `ResellerBotService` and `ResellerApi/CatalogController` all call `resolveResellerWallet()` — the three inline copies are deleted.
   **Membership subscription stays a parallel path and is out of scope** — it is a subscription *fee* (`MembershipCheckoutAttempt`, `membership_fee` ledger credit), not a product sale; it shares only `LedgerService` + the payment gateway + `CheckoutTotalService`, never `Order` / `PricingResolution` / fulfilment. That is correct and deliberate — "one ecosystem" for membership means one *ledger*, not one order path.

2. **New `OrderFactory` seam** (`OrderFactory::create(OrderDraft): Order`) — the single place the money-critical `Order::query()->create([...])` array is built and the unique-constraint (`23000`) violation is caught (→ `DuplicateOrderException`). `OrderDraft` is a DTO carrying a `PricingResolution` plus every non-pricing field. Deliberately **does not** own the payment leg or `FulfillOrderJob::dispatch` — the storefront flow (create → maybe gateway → Pending) and the wallet flow (create → debit → Paid → fulfil) are genuinely different orchestrations and stay in their own services. `SandboxOrderController`'s hand-rolled create is left for a later pass (it is `is_test`-only, super-admin-only, and already drifted from the current schema).

3. **Storefront-brand resolution gates on `pricing_basis` / `is_owned`, never on primary-ness.** An `is_owned` brand (the founder expects 2–3: e.g. a KOL who takes a flat monthly payment *from* the platform rather than a per-order markup, so the platform takes 100% of the margin under that KOL's brand name) behaves with **full primary parity** — membership, vouchers, standard-chain pricing off its own `markup_pct`, `affiliate_profit` accruing to a company sub-account (ADR-061: every `is_owned` brand's ledger is company money). Only a genuine third-party `affiliate`-basis order is treated differently. The platform→KOL monthly payout mechanism is **its own future ADR**, not PR-4.

4. **`orders.wholesale_markup_pct`** (nullable `decimal(5,2)`) — snapshot the wholesale tier markup actually applied, for the `affiliate` and `reseller-wallet` bases (ORD-9: snapshot every price input). Without it, `OrderResendService` cannot recompute profit correctly for those bases — a latent bug **already live** for `reseller-wallet` orders (its `resend()` routes every non-`member` basis through the standard `PricingService::calculate()`, silently wrong for a wallet order). PR-4b makes `OrderResendService` branch fully on `PricingBasis` via `OrderPricingResolver` with the order's frozen inputs, and supports resending a `reseller-wallet` order (not refund-only). Existing wallet-order rows are backfilled (`wholesale_markup_pct` derived from the stored `platform_profit + cost_price`, or the reseller's current tier — settled at build time).

5. **Vouchers become brand-scoped** — `vouchers.affiliate_id` **NOT NULL** (existing rows backfilled to `Affiliate::primary()`; production is not yet commercially live so this is near-empty). A voucher issued from Brand A is redeemable **only** on Brand A — the same "brand-scoped customer instrument" rule membership session tokens already follow (`session['affiliate_id'] !== $affiliateId`). `VoucherService::issue()` records the brand (compensation vouchers from `storeFromOrder` take `order.affiliate_id`); `preview()` / `redeem()` / `findUsableVoucher()` filter on it against the `Host`-resolved brand; the admin promo-voucher form gets a **required brand picker** (default primary); `merge()` gains a same-brand assertion alongside its existing same-customer one. The voucher *accounting* is unchanged and already reconciles — `VoucherService::issue()` books the full liability as a `voucher_issued` debit to **Platform** at creation, so **Platform always absorbs voucher cost, including on a third-party affiliate storefront** (this closes ADR-060 decision 6's "which ledger absorbs a voucher on a reseller sale" open question — Platform does, always; an affiliate-shares-the-discount model stays unbuilt until an affiliate actually asks).

6. **Grace ≠ Lapsed.** ADR-060's 2026-09-05 addendum §3 says a "lapsed" tier falls back to standard pricing — precisely, the fallback is `!AffiliateSubscriptionStatus::grantsWholesaleRate()`, which is **`Lapsed` or no subscription**. A subscription in `Grace` (missed a charge, still inside the 3-day window) **keeps wholesale-tier pricing** (ADR-056). `Affiliate::wholesaleTierMarkupPct(): ?float` is the one place this is resolved (`grantsWholesaleRate() ? tier.markup_percent : null`), consumed by catalog + checkout + preview + voucher-preview.

**Addendum — optional content fields + mobile-crop fix (2026-09-19), grilled with the founder.** Reverses this PR-6 addendum's own "`primary_cta_label`/`primary_cta_href` required — a CTA-less banner is a dead slide" call.

- **Context.** Two problems surfaced together while reviewing a real production banner (a 3264×1088 upload against the documented 1600×800/2:1 spec): (1) the founder wanted an asset-only banner option (all marketing copy baked into the image, no title/CTA overlaid) — the exact pattern both `acidgameshop.com` and `topagentgames.com/my` ship (checked live, mobile viewport) — which today's NOT-NULL `title`/`primary_cta_label`/`primary_cta_href` block outright; (2) `HeroSlider.tsx`'s container used a fixed `min-h-[360px]` (mobile) / `h-[420px]` (desktop) with `object-cover`, unrelated to the image's actual ratio — so even a spec-correct 2:1 upload still gets center-cropped on mobile (≈1:1 box), which is what turned the mismatched upload's baked-in text into an unreadable collision with the real headline.
- **Decision — content fields.** `title`, `primary_cta_label`, `primary_cta_href` become nullable (migration `2026_09_19_hero_slides_optional_content_fields`, both `SaveHeroSlideRequest`s — admin and `Affiliate\Storefront`). `is_active`/`sort_order` stay required-with-a-form-default (operational toggle/order, not content — out of scope for "optional"). New guards: at least one of `image_url` or `title` must be present (no fully-blank slide); `primary_cta_label`/`primary_cta_href` gain mutual `required_with` (both present or both absent — no dead half-a-button). An asset-only slide stays purely decorative (no whole-card link) and keeps `alt=""` (decorative image, same posture as both competitor sites checked) — both deliberately deferred, not built now.
- **Decision — sizing.** `HeroSlider.tsx`'s fixed-height container is replaced by a single `aspect-ratio: 2/1` applied at every breakpoint (matches the existing 1600×800 upload spec — no separate mobile ratio), applied to the no-image "paper card" fallback too (same box height, avoids a rotate-triggered layout jump between an image slide and a text-only one). A correctly-exported 2:1 image now renders with zero crop on any viewport, mobile included. The live mismatched (3264×1088) banner still crops until re-exported — no `object-position`/focal-point control was built as a stopgap (deliberately not over-engineering for one legacy asset).
- **Decision — navigation.** The prev/next arrow buttons (`hidden lg:flex` — already desktop-only) are removed outright: left-anchored title/CTA text and the vertically-centered left arrow occupied the same zone and could collide. Dot indicators (already real, keyboard-focusable `<button>`s) + swipe + auto-rotate remain the sole navigation, matching mobile's existing behaviour (which never had arrows) and both competitor sites (neither ships arrow controls either).
- **Scope.** Both `hero_slides` writers — admin (global/per-brand-null rows) and affiliate self-serve (`reseller/` `HeroTab.tsx`) — get the same relaxation; they write the same table and render through the one shared `HeroSlider.tsx`, so a split rule would be inconsistent and the affiliate side has the stronger case for pure-image brand creative.

**Consequence to track:** the live 3264×1088 banner (and any other off-ratio upload) keeps a visible (lesser) crop until whoever manages that slide re-exports at 1600×800; nothing in this addendum re-validates existing rows. `alt=""` on an asset-only slide is a known accessibility gap, consciously deferred rather than solved here.

**CI-minute tuning addendum (ADR-066), 2026-09-07.** Private repo, billed Actions minutes: ~135 workflow runs over 7 days was burning ~1900 min/mo, driven by run *count* (7 parallel jobs, each rounded up to the minute) not run size. Two `ci.yml` changes, both safe today because `staging`/`main` have **no branch protection or rulesets** (a skipped workflow can't wedge a never-reported required check):
- **`concurrency: { group: per-PR, cancel-in-progress: pull_request only }`** — a newer commit on a PR cancels the older in-flight run (double runs were visible in history). A `push:main` run is never cancelled (deploy must finish).
- **`pull_request.paths-ignore: ['docs/**', '**/*.md']`** — a docs-only PR no longer runs the full matrix; `push:main` stays unfiltered so a docs merge still fires `deploy` (a harmless no-op rebuild).

`cancel-in-progress` means a superseded commit never gets its own green check — acceptable. Revisit both if branch protection is ever turned on (would need the "skipped = success" dummy-job pattern or `dorny/paths-filter` in-job).

**PR-6 planning addendum — affiliate storefront-config editors, grilled 2026-09-07** (`/mattpocock-skills:grilling`, five rounds, all frontier settled; founder confirmed shared understanding before write-up). PR-6 is the last piece of ADR-060: the `reseller/` portal editors that let a non-primary affiliate configure the per-`Host` branded storefront PR-1…4d already renders. Everything here consumes seams that already exist (`ResolveStorefrontBrand`, `StorefrontBrand`, the per-brand catalog/branding/SEO caches, `PricingService::calculateForAffiliate`, PR-5's `assertWritable`); the only new backend concept is a shared image-ingest seam.

**Scope — six editors, one portal screen:** branding text (`affiliate_branding` identity fields) · logo upload · per-affiliate hero slides · GA/FB/TikTok pixel IDs (`affiliate_seo_settings`, the *only* SEO field an affiliate controls — meta templates / OG / schema toggles stay admin-central) · `markup_pct` editor + live preview · `affiliate_game` catalog on/off toggle. **Explicitly out:** theme/colour system (future THM ADR, PRD §6.15) · `is_owned` second-brand portal path (no such brand exists) · schedule window on affiliate hero slides · Zod for the portal boundary · gallery→webp + R2 cutover (its own ADR).

**Design decisions:**

1. **One PR, commit-per-slice** (`feature/adr-060-pr-6-storefront-config` off `staging`), matching PR-5's shape — one CI cost, reviewable commits. The `markup_pct` slice (the only one touching a money path) is committed **last** and is independently revertable.

2. **One "Storefront" portal screen, four tabs** (Branding · Hero · Catalog · Pricing), slotted next to Domains in `AFFILIATE_SECTIONS`. Each tab lazy-loads its own data on select; tab state carried in a `?tab=` query param. Mobile-first (≈80% of traffic is mobile, and resellers configure from phones): the markup preview renders as a card-per-package stack on narrow viewports, never a wide table; the game list is single-column with a sticky search; hero slides stack vertically and order via a numeric `sort_order` field (no drag — deliberately, drag is poor on touch).

3. **`affiliate_game` table** — full join `(affiliate_id, game_id, is_visible)`, `BelongsToAffiliate`, lazily upserted; an absent row means visible (default-on). Chosen over a sparse `affiliate_disabled_games` list for an explicit, extensible state column (a future `sort_order`/featured flag slots in without a migration). Composite unique `(affiliate_id, game_id)` + standalone FK indexes (AGENTS.md `constrained()`-index gotcha). **Min-1 guard:** the affiliate cannot turn off their last visible game (server-side 422; the last switch renders disabled + tooltip). Accepted edge: an admin globally deactivating an affiliate's only visible game still empties that storefront's catalog — admin action, admin's responsibility, not something the affiliate-side guard can prevent.

4. **Image ingest — `App\Services\Media\ImageIngestService`, backed by `intervention/image` v3.** `ingest(UploadedFile $file, string $prefix, int $maxEdge): string` returns the stored disk path. GD was the first recommendation and was **reversed during grilling**: GD needs the box's GD build compiled with WebP (not guaranteed on Forge) and hand-rolled EXIF-orientation correction; Intervention v3 (one composer dep, Laravel-standard, GD or Imagick driver) handles both automatically, and the service seam isolates the choice for a later swap. Always re-encodes to `.webp` (quality 82), caps the longest edge (`logo` 512px, `hero` 1600px), strips metadata. Writes through `Storage::disk(config('filesystems.gallery_disk'))` — **not** a hardcoded `/storage/` path — so the future R2 cutover is a config + data-migration change, never a code change. Prefixes: `affiliate-logos/{affiliateId}.webp` (fixed path, replace overwrites), `affiliate-hero/{affiliateId}/{uuid}.webp` (per-slide, cleaned on replace/delete). Ingest writes to a temp path → moves → then the DB row is written; any failure cleans the temp file and returns 422 (same rollback discipline as PR-5's domain-attach). Input guard: FormRequest `dimensions:max_width=5000,max_height=5000` + mime allowlist `jpeg,png,webp` (SVG rejected — GD/Intervention cannot rasterise it; a documented limitation) + `max:2048` KB.

5. **`gallery` disk stays local (droplet) — R2 deferred.** R2 is its own ADR + `/wizard` (bucket, CDN hostname, CORS, cache headers, `next/image` `remotePatterns`, migration of every existing gallery + hero URL, backup strategy). PR-6's job is to route all new uploads through the disk-config seam so that ADR becomes a config swap; it also ships WebP-at-upload for its own paths now, so those files are already in the target format when R2 lands. Fold into that future ADR: gallery→WebP via the same seam, gallery-delete referential safety.

6. **Schema — one additive migration**, run with plain `php artisan migrate` against the local dev DB before the feature is called done (AGENTS.md additive-migrate gotcha):
   - `affiliate_game` table (decision 3).
   - `hero_slides.affiliate_id` — nullable FK, standalone index, `BelongsToAffiliate` on the model. **Null = global/primary slides** (the "null = global" convention `membership_plans` established). A brand with **zero active** slides falls back to the null-`affiliate_id` set (fallback keys on *effective content*, not row existence — an affiliate who deactivates all their slides wants the default, not a blank hero).
   - `hero_slides.image_path` — nullable string, the disk path for affiliate-uploaded slide images (null for admin's URL-pasted rows; the table is deliberately dual-natured — one query/render/cache path, cleanup branches on `image_path !== null`).
   - `affiliate_branding.logo_path` — nullable string. **Deviation from the 2026-09-05 addendum §1**, which specified `logo_url` holding an absolute URL: a stored absolute URL breaks on the R2 cutover. The column holds a path; `BelongsToAffiliate`-scoped `AffiliateBranding` gets a `logo_url` *accessor* deriving `Storage::disk(config('filesystems.gallery_disk'))->url($logo_path)` at read time. The addendum wording predated this session's R2-seam reasoning.
   - `affiliate_markup_changes` table — append-only audit (`affiliate_id`, `old_pct`, `new_pct`, `changed_by` nullable FK to the acting user, `source` enum `portal|admin`, `created_at`). **Reversed during grilling** from "no audit table, orders self-prove the rate": orders snapshot the effective rate per ORD-9, but a zero-order day leaves no record and an admin-side `max_markup_pct` change has no trail at all. Mirrors ADR-058's `affiliate_tier_changes` pattern; the cost is low and `markup_pct` is a money-affecting self-serve field.

7. **Backend controllers — thin, per-resource, under `Affiliate\`** (matching PR-5's `DomainController`/`ProfileController` split), routed under `/api/affiliate/storefront/*` inside the existing `auth:affiliate` + `account.type:affiliate` + `affiliate.context` group. Each mutating route gets its own FormRequest (AGENTS.md). `assertWritable($affiliate)` (403 unless `affiliate.status === 'active'` — copied verbatim from PR-5, so a *lapsed subscription* keeps full edit access while a *deactivated* affiliate is read-only) is extracted to a shared `AssertsAffiliateWritable` trait rather than copy-pasted.
   - `Affiliate\BrandingController` — `GET`/`PUT storefront/branding` (identity fields), `POST`/`DELETE storefront/branding/logo`.
   - `Affiliate\SeoController` — `GET`/`PUT storefront/seo` (the three pixel IDs only). A dedicated controller despite being thin, to mirror the admin `Admin\SettingsController` vs `Admin\SeoController` split and keep one model per controller; the Branding tab UI simply calls two endpoints.
   - `Affiliate\HeroSlideController` — `GET storefront/hero-slides`, `POST` (multipart), `PUT/{slide}`, `PATCH/{slide}/status`, `DELETE/{slide}`. Cap 6; `is_active` toggle only (no schedule window); `{slide}` tenant-checked by `affiliate_id`.
   - `Affiliate\StorefrontGameController` — `GET storefront/games` (all `is_active` games + this brand's `is_visible` state), `PUT storefront/games/{game}` (upsert + min-1 guard).
   - `Affiliate\PricingController` — `GET`/`PUT storefront/pricing` (`markup_pct`, hard-capped at `max_markup_pct` on write, floor 0, writes an `affiliate_markup_changes` row), `POST storefront/pricing/preview` (body `{markup_pct}` → three rows — low/mid/high band from the brand's visible catalog — via `PricingService::calculateForAffiliate`, plus a `wholesale_rate_active` flag driving the "wholesale rate paused" note when the subscription is lapsed).

8. **Pixel IDs — charset allowlist, not a format regex, not a free string.** They render inside a `<script>` in the storefront `<head>` (`gtag('config', '…')` etc.), so a value like `'); evil(); //` is stored XSS on every brand's storefront. Rule: `^[A-Za-z0-9._-]{0,64}$`, `nullable`, empty → stored `null`. This is a security gate on a semi-trusted (paid, bank-verified) but self-serve input, *not* a format check — GA/FB/TikTok ID formats drift and a strict regex is a latent support ticket. The storefront additionally renders the value JSON-encoded, never by raw interpolation.

9. **Cache invalidation — per-brand, precise:**
   - Add `CatalogController::forgetIndexCache(?int $brandId = null)` — a single-brand variant that stops the existing all-brands loop when the brand id is known. A catalog-visibility toggle busts only this (the game *list*), not the packages cache.
   - Add a per-brand tag `catalog.packages.brand.{brandId}` to the packages cache's tag set (the store already supports tags — this is one line, not a key-shape change). A `markup_pct` change flushes only `catalog.packages.brand.{X}` + the single-brand index — **not** the blunt whole-`catalog.packages` flush the grilling first landed on.
   - A branding save busts `BrandingController::forgetCache($id)` **and** `SeoController::forgetCache($id)` (the `{store_name}` token is substituted into SEO meta) **and** the single-brand catalog index.
   - Hero: a new `HeroSlideController::forgetCache(?int $brandId)` keyed `catalog.public.hero_slides.brand.{brandId}`. Because a brand with no active slides caches the *global* set under its own brand key, the **admin** `Admin\HeroSlideController` (which writes null-`affiliate_id` rows) must, on write, bust every per-brand hero key (loop brand ids, like `forgetIndexCache` does) — hero writes are rare, the loop is acceptable.
   - `NextRevalidation::purge()` stays tag-`catalog` (one storefront project, one tag) — a per-brand config change purges every brand's ISR. Accepted: config saves are infrequent.

10. **Storefront render — consume side (`storefront/`):**
    - `HeroSlideController::index()` (public, already inside `storefront.brand`) becomes brand-aware: `live()->where('affiliate_id', $brand->id)`; if empty, `live()->whereNull('affiliate_id')`.
    - `BrandingController::show()` adds the derived `logo_url` to its response; the branding Zod wire schema gains `logoUrl`; `Logo.tsx` renders `next/image` when present (the backend `/storage` host is already in `remotePatterns` and covers every brand — images are always served from the backend, never the affiliate's domain), else keeps the placeholder mark.

This is a money-path rule, pinned here.

### Addendum — public proof-of-ownership lookups are brand-scoped (2026-09-10, `fix/storefront-tenant-scope-tracking`)

The two public `order_number`-as-proof-of-ownership routes (`GET /api/track-order/{n}`, ADR-011; `POST /api/orders/{n}/review`, ADR-053) shipped **without** the `storefront.brand` middleware, and their controllers looked up the order by `order_number` alone. Consequence: an order number placed on one affiliate's storefront resolved on *any* other's — leaking the buyer's game, masked contact, order status, and that brand's own retail `selling_price` across the tenant boundary. Not an enumeration hole (the number is ~62-bit CSPRNG), but a real cross-brand leak for anyone who *has* another brand's number (a forwarded screenshot, an operator testing).

Fix: both routes get `storefront.brand`; both controllers scope through the new `Order::scopeForStorefrontBrand(Affiliate $brand)` (primary brand also matches `affiliate_id IS NULL` legacy rows, mirroring `ReviewCatalogController::gameReviews()`). A cross-brand hit returns the **same 404** as an unknown number — never confirm an order exists under a storefront it wasn't placed on.

**Deliberately still open:** the realtime `order.{order_number}` broadcast channel (`OrderStatusUpdated`) stays a public, unscoped channel — its payload is already the masked `customerSafePayload`, the order number is the proof-of-ownership token, and brand-scoping it needs a private channel + auth callback. Tracked as a follow-up, not a blocker. Also unchanged: the storefront support card's contact details are the *brand's* (`useSiteConfig().whatsappHref`) — a separate cosmetic fix (`fix/storefront-brand-polish`) de-hardcodes the "PekanGame" strings in the message body.

### Addendum — portal guide recommends the main domain first (2026-10-02, PRD §16 item 49)

**Context:**
- The 2026-09-06 build addendum (section D) kept "portal still recommends `www.` / `shop.` first". Its only reason was provider opacity: an apex on a DNS host without ALIAS/flattening must use the raw A record (`76.76.21.21`), which is a recognisable signal of our hosting provider.
- Building the domain setup guide, the founder pointed out the user reality: an affiliate who buys `pasarripo.com` wants the shop on `pasarripo.com`, not on `shop.pasarripo.com`.
- A guide that steers them to a subdomain mostly produces confused affiliates. The opacity cost it was protecting is small; this ADR itself already accepted it as "minor".

**Decision:**
1. The portal guide (`DomainSetupGuide.tsx`) presents the **main domain as the primary path**, with records per provider:
   - Cloudflare: `CNAME @` to the alias, DNS only. Flattening keeps the IP hidden.
   - GoDaddy and providers without ALIAS: edit the existing `A @` ("Parked") to the A-record IP.
   - Providers with ALIAS/ANAME: point `@` at the alias.
2. `www` and other prefixes stay supported as optional extra rows.
3. **`www` is not auto-registered.** Section E's "the system registers both on Vercel with the redirect configured there" is not built: `AffiliateDomainService` has no `www`/redirect logic. So the guide tells the affiliate to add `www.yourbrand.com` as a second domain, which then serves the same storefront with a canonical tag to the primary. Building the automatic `www` pairing plus redirect is a separate, unscheduled item.
4. The provider-opaque rule otherwise stands. The guide never names our host; it shows the A-record IP only where the affiliate's DNS host gives no alternative.

**Consequence to track:**
- Section E's `www` ↔ apex auto-registration is documented here as unbuilt, not silently assumed. Revisit if affiliates repeatedly add only the apex and then report `www` not working.
