# ADR-014: 24/7 burst-resilience baseline — queue, retry, indexing, caching, rate-limiting, observability

> **Standing (2026-10-09):** In force; queue driver revised by ADR-048, cache driver by ADR-077. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-07-26 (design session while blocked on Gamevion support's reply re: ADR-006's sandbox `500`; founder explicitly asked to strengthen the foundation in parallel rather than wait idle). **Partly revised:** decision 5's app-wide `CACHE_STORE=database` was reversed to Redis by [ADR-077](./ADR-077-storefront-read-path.md) (2026-09-07) once production Pulse showed the `cache` table was the system's biggest latency source.

> **Superseded in part by ADR-077 (2026-09-07):** decision 5's app-wide `database` cache store is cut to Redis — production Pulse showed the `database` `cache` table had become the system's single biggest latency source (a 52-second `select from cache` under lock contention). Decision 4's index list is extended there too. Decision 7's "state on `database`, ready to scale" note still holds for sessions; the cache half moved. The "cache values must be plain arrays" rule from this ADR's own addendum below is now belt-and-braces rather than load-bearing (Redis does not corrupt nested objects) — kept for portability.

**Context:** A read-only audit of the live codebase (not assumption) found the money-critical path had zero protection against exactly the failure modes a 24/7 top-up storefront with bursty concurrent traffic will hit: `XenditWebhookController::handle()` calls `OrderFulfillmentService::fulfill()` — which makes a live Gamevion HTTP call — **synchronously inside the webhook request**, while holding `fulfill()`'s own row lock (added in the 2026-07-24 security review); `orders.payment_ref`, the exact column every webhook looks up by, has **no index**; outbound calls to Xendit/Gamevion have **no retry** on transient failure; there is **no caching** anywhere (`grep Cache::` returns zero hits); there is **no rate-limiting** on any route (`grep throttle` returns zero hits) — `POST /api/checkout` and the webhook endpoint are both wide open; and there is no error-tracking/health-check beyond Laravel's default file log. Full findings are in the session transcript, not duplicated here.

**Decision (per sub-area, each grilled with the founder one at a time before being accepted):**

1. **Queue** — introduce a `database`-driver queue (the `jobs` table already exists from the Laravel scaffold, unused until now — zero new infra). `XenditWebhookController` becomes thin: verify signature → update `payment_status` → `dispatch(new FulfillOrderJob($order))` → ack. `OrderFulfillmentService`'s own interface and its `lockForUpdate()` guard are untouched — only *where* it's called from moves. Redis is deferred until real traffic actually justifies the extra infra/ops burden; this project currently has no production infra defined at all (`backend/docker-compose.yml` is MySQL-for-testing only).
2. **Retry (network)** — add `->retry(3, [200, 500, 1000])`-shaped backoff to `GamevionAdapter`/`XenditGateway`'s shared `client()`, scoped to transient failures (timeout/5xx) only — a 4xx like `422 invalid product code` (the exact error ADR-006's sandbox retest just reproduced) must never be retried, since retrying a validation error just wastes the budget and delays the real failure signal.
3. **Retry (business)** — `FulfillOrderJob` gets its own `$tries`/`backoff()` aligned with #2. When exhausted, the order lands at `delivery_status: failed` for admin review — same terminal state `OrderFulfillmentService` already produces today, just reached after automated retry instead of on the first blip. Exposing a manual retry from `/admin/orders` (ORD-7, already tracked as unbuilt in `prd.md` §14/§15) becomes part of this same effort rather than a separate later pass, since a queued job without an operator-visible retry path is a worse UX than the current synchronous one.
4. **Database indexing** — add an index on `orders.payment_ref` (every webhook's lookup column, currently unindexed — the single highest-impact fix found) and a composite index on `orders(payment_status, delivery_status)` (the Admin Orders `need_action`/`processing`/`completed` filters, per `OrderController`). Pure migration work, no interface change, no founder trade-off — proceeding without a grill question.
5. **Caching** — `Cache::remember()` (TTL 60s) on read-heavy, admin-curated listings only (Games/Packages, Payment Methods) with **invalidate-on-write**: any admin action that changes a cached row (status toggle, markup/fee update) clears that cache key immediately rather than waiting out the TTL, so a customer is never shown a stale toggle for more than a moment. **Explicitly out of scope: pricing/checkout calculation itself** — `PricingService`/`CheckoutTotalService`/`CheckoutService::initiate()` keep reading live from the DB, unchanged. This preserves ORD-9's existing "money is snapshotted at checkout time from a live source, never from a stale intermediate copy" discipline; caching is a read-listing optimization, not a money-path optimization, and the two must never blur.
6. **Observability** — founder chose to **stay on file-based logging for now, no external error-tracking service** (Sentry etc. explicitly declined — cost/data-residency judged not worth it before real production traffic exists). What *is* being added: consistent structured log context (`order_number`/`reference_number` attached to every log line on the fulfillment/payment path, not just ad-hoc `Log::warning()` calls as today), a `GET /api/health` endpoint (DB + queue connection check), and `throttle:10,1` on `POST /api/checkout` (10 requests/minute/IP — chosen loose enough not to block a genuine customer retrying after a failed attempt, tight enough to blunt a flood). The Xendit webhook route is deliberately **not** IP-rate-limited the same way — `x-callback-token` verification is already its auth boundary, and by-IP throttling risks blocking Xendit's own retry infrastructure, which shares egress IPs across their customers.
7. **Load balancing** — deferred, no code change now. Recorded only because the audit confirmed the codebase is *already* positioned for it whenever it's needed: auth is Bearer-token (Sanctum), not cookie/session-affinity-based, and `SESSION_DRIVER`/`CACHE_STORE` both already default to `database`, not `file` — so horizontal scaling later needs new infra, not a rewrite of how state is held.

**Rationale:** Every sub-area above was scoped to change an implementation, not an interface — `SupplierAdapter`, `PaymentGateway`, and `OrderFulfillmentService`'s public contracts are untouched by #1–#3; this is the same "deepen the module, don't reshape its seam" discipline the codebase already follows for the Adapter/Gateway layer (ADR-001, ADR-006), applied to resilience concerns instead of business features.

**Consequence to track:** this ADR records *design intent*, agreed before implementation started (per the founder's explicit request — plan and review first). Update `prd.md` §14/§15 as each numbered item actually ships; do not treat this entry as proof any of it is built yet.

**Addendum — real caching bug found and fixed live, 2026-07-26 (Hero Banner session):** while building the public catalog endpoint and Hero Banner (both new `Cache::remember()` call sites), a genuine correctness bug in decision #5 above was found by actually hitting an endpoint twice against a real running server (`php artisan serve`), not just trusting the automated test suite. `CACHE_STORE` defaults to `database` (per #7's own note) — every `Cache::remember()` value gets `serialize()`d to store it and `unserialize()`d on every read. **Caching a raw Eloquent Collection/Model, or even just one raw `Carbon` date buried inside an otherwise-plain array, corrupts on the very next read**: the JSON response silently turns into `{"__PHP_Incomplete_Class_Name": "Illuminate\\...\\Collection", ...}` — no exception, no log, just wrong data. Reproduced reliably: first request after a cache-clear is correct, every request after that within the 60s TTL is broken, until the entry expires or is invalidated.

This was **never caught by the automated test suite** — `phpunit.xml` sets `CACHE_STORE=array` for tests, which keeps everything in PHP memory and never actually serializes anything, so the bug was invisible to `php artisan test` no matter how many times it ran.

Found and fixed in **all four** existing `Cache::remember()` call sites, not just the two new ones being built this session:
- `GameController::index()`/`packages()` (admin Games & Packages — pre-existing from this same ADR's original implementation, 2026-07-26)
- `Middleware\PaymentMethodController::index()` (pre-existing, same original implementation — found during a docs-accuracy sweep *after* the first three fixes, not in the original pass)
- `CatalogController::index()` (public catalog, built this session — `created_at` was left as a raw Carbon instance inside an otherwise-plain array)
- `HeroSlideController::index()` (public Hero Banner, built this session — designed correctly from the start once the bug was understood)

**Fix, applied uniformly:** every cached value must be a plain array/scalar tree — never a raw Model, Collection, or any nested object (Carbon included) — before it reaches `Cache::remember()`. In practice this means calling `->toArray()` on the Eloquent Collection (which also flattens any Carbon date attributes to strings) or building the array by hand and explicitly casting date fields (e.g. `$game->created_at?->toISOString()`).

**Addendum, 2026-09-29 — storefront throttles vs mobile CGNAT (pre-release review PR-D, grilled Q4).** The original `throttle:10,1` per IP on `/checkout`, `/vouchers/preview` and `/games/{game}/validate-player` assumed one IP ≈ one customer. Malaysian mobile carriers put many subscribers behind one CGNAT address, so during a promo strangers sharing an IP would 429 each other. This was an audit K-low that never made it into PRD §16.
- **Decision:** `/checkout` moves to a named `checkout` limiter: 10/min per customer (IP + `customer_email`) plus a 60/min ceiling per IP. `/vouchers/preview` and `/validate-player` go to 30/min per IP.
- **Rationale:** a per-customer bucket still stops one person from flooding. The per-IP ceiling still caps a single source. Validate-player's per-call cost is already bounded by Wave 4 K-2's 8s chain deadline.
- **Consequence to track:** email is client-supplied, so a flooder can rotate emails. The 60/min IP ceiling and FRAUD-4's velocity guard are what bound that.
