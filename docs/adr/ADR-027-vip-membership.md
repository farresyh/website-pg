**Context:** The founder brought a reference document from a separate discussion (with Gemini) proposing a subscription-based VIP membership tier for the topup store, modeled on Costco's wholesale-membership business (most operating profit from membership fees, not markup on goods sold — members buy near cost price, non-members pay full retail). Explicitly treated as external inspiration only, not ground truth for this project, per the founder's own framing at the start of the session.

This reference's own supporting numbers (22,181 completed & delivered orders, 6,105 unique customers, ~12.3% average gross margin, a 6-tier customer spend-distribution table) were initially assumed to come from a different, larger business — "kedairuncitsoloz," a real prospective partner whose real monthly sales the founder states range RM400k–2,000,000, roughly 3-15x this project's own real monthly revenue (RM66.5k–244k per `ADR-020`'s addendum). That partnership is not yet confirmed and kedairuncitsoloz's own real order/margin data is not yet available.

Mid-session, a real cross-check reversed that assumption: this project's own real order export (`/Users/farresyh/Downloads/orders.csv`, 28,848 rows — the exact same file already used for `ADR-020`'s capacity analysis, confirmed real, not the deleted `docs/orders.csv` copy) produced a paid+delivered order count (22,297) and spend-tier distribution (Micro 27.1%/Casual 29.8%/Regular 16.6%/Active 13.3%/Hardcore 9.7%/Whale 3.5%) matching the reference document's own numbers (22,181; 26.8%/29.7%/16.6%/13.6%/9.7%/3.6%) to within rounding. This is almost certainly the same underlying dataset, analyzed once by Gemini and once fresh in this session — meaning the reference's numbers describe **this project's own real history (under its `karrashop`/`keroxshop` branding), not kedairuncitsoloz's**. Kedairuncitsoloz's real numbers remain genuinely unknown. For this ADR, this project's own verified real order history is used as the reference dataset, with customer/order **counts** (not per-order unit economics) scaled ×5–×10 to approximate kedairuncitsoloz's stated volume range — the founder's own proposed approximation once the mistaken assumption above was surfaced.

The real analysis also corrected two numbers the reference and this project's own config had wrong: real weighted-average margin across the verified dataset is **5.59%** (`Σmarkup/Σcost`), well below both the reference's assumed 12.3% and this project's own `packages.default_markup_percent` config default of 15% (likely skewed low by "Weekly Diamond Pass" items dominating the sample — flagged to re-segment by package category before finalizing pricing, see Consequence). A live competitor price-check the same session found Malaysia's mainstream top-up resellers (Codashop, SEAGM, Joytify) cluster tightly around RM0.075–0.078/diamond for Mobile Legends, while a smaller, lesser-known site (gamejus.com) undercuts them at ~RM0.069/diamond — and this project's own real Gamevion cost for the same denomination (`Package` id 3, "13+1 Diamonds": `cost_price` RM0.94 against gamejus's real sale price RM0.96) is already almost at gamejus's own retail price, meaning beating gamejus specifically requires a member markup near 2%, not the 5–8% that would beat only the mainstream three.

This ADR also narrows `ADR-011` (storefront stays guest-checkout, no Customer account) rather than reversing it outright — see Decision 2/3.

**Decision:**

1. **Dual goal, not single**: both recurring subscription revenue and retention/lock-in are explicit objectives — the founder rejected treating "does the fee cover the margin given up" as the only lever worth optimizing, which is why Decision 8's breakeven check exists as a real constraint check, not the design's starting premise.

2. **Identity: phone number + OTP, not a full email/password Customer account.** A deliberately narrower reversal of `ADR-011` than the reference's own account-based model — the founder chose this specifically after confirming a member dashboard (status, quota, order history) is achievable without full account/session infrastructure. Verification and reminders both go over **WhatsApp** (Decision 11's billing channel and this identity channel share one vendor, not two).

3. **Profile materializes on demand, not universally.** Guest checkout's existing mandatory `customer_name`/`customer_email`/`customer_phone` fields (`CreateCheckoutRequest`) are unchanged — no new field, no new forced step for the ~87%+ of customers who won't subscribe. A phone-verified session is created only when a customer actively chooses to verify (to subscribe, or to check existing membership/order status). Because `Order.customer_phone` already exists as a plain column on every order, past and future orders link to a verified session by matching on phone — no new linkage table or Order schema change needed for order-history display.

4. **Two tiers, launched together, deliberate decoy/anchor pricing** — the founder's own framing, borrowed from cinema ticket-size pricing (Medium priced disproportionately close to Large, to nudge the upsell). Requires both tiers live simultaneously to work; a single-tier pilot would remove the anchor the psychology depends on. `membership_plans` must be a config-driven table (fee, quota, per row), not hardcoded tiers, so a future third tier is a data row, not a code change.

5. **Member price = the package's own configured `markup_percent`, reduced by a relative discount, floored at 0%** — never a flat member-wide markup override, and never sold below cost. Preserves this codebase's existing per-package markup customization (`Package.markup_percent`, admin-adjustable) instead of collapsing every package to one number regardless of its own real margin.

6. **Competitive target: beat the single cheapest verified competitor (gamejus.com), not just the mainstream cluster.** The founder's explicit, informed choice after seeing Decision 8's breakeven numbers — a materially thinner, higher-conviction margin than "just beat Codashop/SEAGM/Joytify" would have required.

7. **Quota is tracked and consumed in member-price-paid currency (RM actually charged at member rate), not cost price or a separately-computed retail-equivalent.** Avoids dual-accounting; matches the "RM100/RM200 spend cap" framing the founder used throughout. Resets on a **rolling 30-day cycle anchored to each member's own subscription date** — not a shared calendar-month reset — per the founder's own "standard business practice" framing (fairness for mid-month subscribers). Implementation note: this requires a daily scan for per-user cycle-elapsed rather than one shared cron trigger.

8. **Breakeven check against real data (this session), draft anchors only:** at the Decision 6 target (~2% member markup), forgone margin per RM100/150/200/300/500 of quota consumed is RM3.34/RM5.01/RM6.68/RM10.02/RM16.70 per month. The reference's own suggested fees (RM8.90, RM19.90) exceed forgone margin at every quota level tested, even at this aggressive target — informed the founder's Decision 6 choice. Draft shape floated for future discussion, **explicitly not final** (Consequence): Tier 1 ~RM8.90/mo at ~RM100 quota, Tier 2 ~RM19.90/mo at ~RM300 quota (not the reference's own RM500 — leaves headroom against the RM19.90 breakeven while widening the Decision 4 anchor gap).

9. **No cost price ever surfaces to the customer.** Product/browse pages show the normal price and a generic, non-personalized member price side by side, plus a "Save X%" badge computed as `(normal − member) / normal` — identical content for every visitor, cacheable, no per-visit DB lookup. Rejected the founder's own alternate idea (computing the shown discount off cost price directly) as unnecessarily convoluted for no real benefit over the simple normal-vs-member delta.

10. **Personalization happens once, at "Proceed to Pay," never at browse time.** A session-recognized existing member gets the member price silently; anyone else sees an optional, non-blocking prompt ("Verify & get member price" vs. "Continue as guest") — guest checkout is never gated or interrupted, preserving `ADR-011`'s original intent for every customer who doesn't opt in. This keeps the one DB-side membership/quota check to a single point per checkout, the same shape as this codebase's existing per-checkout checks (blacklist velocity guard, voucher validation, player-ID validation) — not a new class of load, and negligible against `ADR-020`'s own real burst numbers (busiest 5-minute window ever recorded: 28 orders).

11. **Billing: hybrid, gateway-dependent.** Manual renewal (a one-time payment link through the existing checkout/payment-gateway flow, no stored card) is the baseline, always available regardless of gateway. True recurring auto-charge is layered on only where the resolved gateway genuinely supports it — confirmed this session that Malaysia recurring billing is real but uneven across the project's two gateways: Xendit has a real Subscriptions API, but Malaysia-specific FPX/direct-debit self-serve activation isn't confirmed in its docs (activation contacts listed only for Indonesia/Philippines); CHIP's recurring is card-only via a saved token with no built-in scheduler, and has no FPX/e-wallet recurring at all. No commitment here to which gateway carries recurring for which channel — decide at build time against each gateway's then-current real capability, not this session's snapshot.

12. **Anti-abuse: the quota cap alone, for the pilot — no additional per-day/per-order rate limit.** The founder's own quota design (a hard monthly spend cap) is treated as sufficient first-line defense against the resale-arbitrage risk a near-cost member price creates on a liquid, resellable digital good; an additional rate limit is deliberately not built pre-emptively, matching this codebase's own established norm (`AGENTS.md`) against designing for a problem not yet observed. Revisit only if real abuse is seen.

13. **Member dashboard scope (the "what does a normal member get" the founder asked to pin down as step one)**: membership status + expiry + a renew action, remaining quota this cycle, and order history. The last is free from Decision 3's existing `Order.customer_phone` match — no new table needed to support it.

**Rationale:** Every layer of this design was kept deliberately smaller than the reference document's own version of it — identity is OTP-only, not full accounts; personalization is checkout-time-only, not page-load-time; quota consumption is designed to reuse this codebase's own proven concurrency-safe pattern (`LedgerService`/`VoucherService`'s row-locking, not a new mechanism — see Consequence); and Decision 6's aggressive margin target was only accepted after Decision 8's real breakeven math, not on the reference document's own optimism. The one deliberate exception to "keep it small" is Decision 4's two-simultaneous-tiers requirement — accepted specifically because the anchor/decoy psychology the founder wants structurally requires the comparison to exist from day one; a staged single-tier launch would remove the mechanism the founder is actually trying to use.

**Addendum, 2026-08-29 (recorded after the build session, status OPEN) — membership × reseller pricing reconciliation, member-order accounting, and the money-view rework.** Recorded explicitly OPEN for re-challenge at the founder's request, so a fresh session can re-argue every point below from first principles. Nothing here is final; the codebase still prices every order on the standard chain and no member-priced order can exist yet (Phase 6 unbuilt). No code landed with this addendum — this is a record of the founder's own framing, the problem it exposed, and the proposed solution, for the next session to challenge.

*The founder's own framing (the situation he described):*

1. The platform was originally designed **reseller-only**: `cost × markup = reseller_cost_price`, per-package `markup_percent`, two admin markup surfaces — Platform Settings' bulk action (`SettingsController::bulkMarkup`) and Admin Games' per-package inline edit (`PackageController::updateMarkup`) — both write `package.markup_percent` and recompute the stored `reseller_cost_price` via `PackageMarkupService`.
2. After learning the **Costco wholesale-membership model**, membership became the PRIMARY feature and reseller became secondary. Member price is computed off **supplier cost** (`cost_price`), not reseller cost: `member_price = cost × (1 + package.markup_percent × (1 − tier.discount_percent))`, floored at 0% markup (ADR-027 decision 5, unchanged).
3. The founder realised the two pricing systems were **never reconciled**, and that the money-critical views — admin order details and the report pages — only show the standard chain: cost price, reseller cost, selling price, voucher discount, transaction fee, final amount, platform & reseller profit. Nothing reflects membership, so an admin cannot read the business's real cashflow once memberships are live.
4. The founder proposed **unifying the two**: member AND reseller both buy near-cost (effective markup ≈ 3%); members are quota-capped (RM300/month, ADR-027 decision 7), resellers are unlimited but add their own margin on top. The membership quota is the **deliberate anti-reseller mechanism** — a customer may resell, but only within the monthly cap; the founder accepts this consciously.
5. The founder clarified the reseller's own margin (`Reseller.markup_pct`) is a per-reseller field whose home is the **Reseller management page** (PRD RES-1..6, Phase 2) — already planned — not a new config surface.

*The problem the founder's framing exposed (verified against the code, not assumed):*

- **Accounting mismatch on member orders.** Every order books `platform_profit = reseller_cost_price − cost_price` (the margin model, `PricingService`), regardless of what the customer actually paid. On a member order this overstates real cash margin — e.g. member pays RM103, supplier cost RM100, but the system books RM15 (reseller_cost − cost) as profit when the real cash margin is RM3. Reports therefore show profit that is not cash.
- **No way to distinguish a member order from a standard order.** `orders` has no member/non-member column and no snapshot of the applied membership discount, so reports silently mix full-margin (standard) and thin-margin (member) revenue with no way for an admin to tell them apart.
- **Two pricing chains exist but were never reconciled.** Member price is derived from supplier `cost_price` + reduced `package.markup_percent`; the standard price from `reseller_cost_price` + `reseller.markup_pct`. Because the discount only ever reduces markup (never negative), member price is always ≤ `reseller_cost_price`, so the membership discount is entirely borne by the platform's own margin and the reseller's margin is never touched.
- **Membership fee revenue is invisible.** `membership_plans.fee_sen` is draft config, collection is off-platform/manual, there is no `ledger_entries` type for it, and no report line — the Costco model's main profit driver has no home in the money views.
- **Known doc drift found alongside:** `SettingsController::bulkMarkup()`'s doc comment claims `PackageController::updateMarkup()` writes a `PriceChangeLog`; it does not. Cosmetic, fix opportunistically.

*The proposed solution (all OPEN for challenge):*

1. **No new markup config anywhere.** Membership is priced off supplier cost, riding the existing two markup surfaces; `package.markup_percent` remains the single source for both the stored `reseller_cost_price` (standard chain) and the live-computed member price. Editing markup via either existing admin surface changes the member price immediately (already proven by tests).
2. **Unified pricing model, one anchor.** Three buyer prices derive from `cost_price`: guest (standard) = `cost × (1 + package.markup_percent)`; member = `cost × (1 + package.markup_percent × (1 − tier.discount_percent))`, quota-capped; reseller = near-cost wholesale base + the reseller's own `markup_pct` (configured on the Reseller page, Phase 2).
3. **Reseller wholesale rate and the member×reseller interaction at a reseller storefront are deferred design intent (Phase 2)** — per this project's own convention, do not build a setting for a mechanism that does not exist yet. No `reseller_base_markup` config is built now; `reseller_cost_price` keeps its current meaning, no data migration.
4. **Member-order accounting must book real cash margin, not the standard margin model:** `platform_profit = member_price − cost_price`, `reseller_profit = 0`. Guest/reseller orders keep the existing formulas.
5. **Order schema snapshots the pricing basis (ORD-9):** `pricing_basis` (`standard`|`member`, default `standard`), `member_discount_percent` (applied tier discount), `normal_selling_price` (the counterfactual retail the order would have paid as a non-member).
6. **Money views reworked for cashflow clarity:** admin order detail shows a "Member" badge + normal-vs-member price breakdown + margin given up when `pricing_basis = member`; reports split member vs standard sales and show margin forgone to members.
7. **Membership fee revenue stays a named absence, not an accident:** when fee collection is built, book a `membership_fee` ledger type and add a report line; until then it is recorded as a known gap.

*Consequence to track (addendum-specific):*

- ALL decisions here are OPEN for challenge — the founder's explicit instruction, mirroring ADR-027's own standing "re-argue at build time" condition. A fresh session should read this before assuming the pricing model is settled.
- Phase 6 (checkout-time member detection, applying the member price, booking the corrected profit, race-safe quota decrement) remains unbuilt. The schema and views can land before it (additive, standard-default); the accounting fix only activates once Phase 6 produces member-priced orders.
- `OrderResendService` recomputes profit from live package values on resend — it must use the member formula for member-priced orders, not just the standard chain, once Phase 6 ships.

**Addendum (continued), 2026-08-29 — grilled via `/mattpocock-skills:grilling`, same day, decisions settled.** The OPEN addendum above proposed unifying member and reseller pricing under one anchor (its own item 2). Grilling that proposal with the founder surfaced a real problem it didn't account for: the founder's own first refinement — a reseller-tier discount unlocked by how many of the reseller's *own downstream customers* subscribe to platform membership — was worked through and rejected, not adopted. It required either honoring the member price on a reseller's storefront (which crushes reseller margin via stacking: a reseller already buying near-cost cannot also resell near-cost and stay solvent) or keeping member pricing platform-exclusive (which removes any reason for a reseller's own customer to ever pay a membership fee, since it buys nothing at the store they actually use). Both failure modes trace back to the same root cause the founder identified independently: **member pricing and reseller wholesale pricing are two different buyer relationships (individual, quota-capped, consumer-loyalty vs. business, unlimited-volume, wholesale-contract) that don't compose safely through one shared discount mechanism.** The settled design keeps them fully separate instead.

8. **Rename `reseller_cost_price` → `standard_selling_price`.** The field's actual usage today is the guest/standard retail price at the platform owner's own storefront (`cost_price × (1 + package.markup_percent)`) — the name has never accurately described a reseller-specific price, which is exactly the confusion that triggered this whole reconciliation. Applies to both the `packages` column and the `orders` snapshot column (ORD-9). Needs the same call-site-enumeration discipline `ADR-028` decision 9 established for `Reseller::platformOwner()` — done as part of the actual rename migration, not left implicit. `docs/prd.md`'s ORD-9 row and `Reseller` data-model row both still say the old name; not yet renamed in code, marked pending there rather than silently rewritten as already-true.

9. **Membership stays exclusive to the platform owner's own storefront. No membership feature exists on any reseller storefront, and reseller pricing is never derived from anything a reseller's own customers do.** This directly narrows the OPEN addendum's own item 2 (member/reseller unification) — rejected in the form originally proposed, replaced by decisions 10-14 below: reseller pricing is its own independent mechanism, decoupled entirely from `membership_plans`/`tier.discount_percent`.

10. **A new table, `reseller_membership_tiers`** (name, monthly fee, markup percentage over `cost_price`) — kept separate from `membership_plans` per this codebase's own "distinct concern gets its own table" convention (`reseller_branding`/`platform_settings`/`reseller_footer_settings` precedent), not a shared table with a buyer-type discriminator. No `quota_sen` column — reseller volume is unlimited by design, unlike the consumer quota (Decision 7 of the base ADR). **CRUD-editable from the admin UI** (add/edit/remove tiers freely), unlike `membership_plans`' locked-at-exactly-2-rows shape — that lock exists only because the base ADR's Decision 4 anchor/decoy psychology structurally needs two simultaneous consumer-facing tiers; no equivalent constraint applies to a B2B wholesale-rate ladder, and the founder wants the flexibility to add tiers as the reseller base grows.

11. **A reseller's effective purchase price = `cost_price × (1 + tier.markup_percent)` for their currently active paid tier, or `standard_selling_price` (Decision 8) if no tier is active** — never paid, or lapsed past the grace period (Decision 13). Replaces `docs/prd.md`'s `Reseller` data-model row, which currently claims Phase 2 reseller rows don't change "the table and pricing formula" — no longer accurate once this ships; noted as a pending PRD delta below.

12. **Billing: monthly, paid directly by the reseller to unlock a tier — no referral, volume, or fee-sharing mechanic.** Same "pay to unlock" shape as consumer membership (base ADR Decision 4's tier config), but entirely decoupled from anything downstream of the reseller — the rejected proposal this addendum narrows (Decision 9) is the reason this is stated explicitly rather than left implicit.

13. **A ~3-day grace period after a missed monthly payment before reverting to `standard_selling_price`.** The manual-payment stopgap (Decision 15 below) can lag a few days for reasons unrelated to the reseller's intent to keep paying (bank/transfer processing, an admin who hasn't logged the payment yet); an immediate cutoff on the due date risks damaging a real business relationship over an internal processing delay rather than a genuine lapse.

14. **Floor for a reseller's best tier: ~3% markup over `cost_price`, not 0%.** Unlike the consumer floor (base ADR Decision 5, 0%, justified by the hard monthly quota capping total platform exposure per member), reseller volume is unlimited — a 0% floor would mean the platform earns nothing per unit no matter how large a reseller's volume grows, leaving the flat monthly tier fee as the only profit source regardless of scale. **Both floors (consumer 0%, reseller ~3%) are admin-editable from the UI, not hardcoded constants** — the founder's own ask, so either can be tuned without a code change once real data exists to tune against.

15. **Two new ledger types, not one: `membership_fee` (consumer, per the OPEN addendum's own item 7) and `reseller_tier_fee` (reseller, new).** Kept separate rather than one type with a payer-type discriminator, so reports can split consumer-membership revenue from reseller-tier revenue cleanly — the two have materially different business dynamics (recurring small-value consumer subscription vs. a small number of larger B2B monthly payments), and collapsing them would just push the same split back onto every report query instead of the schema. Both reuse the same manual-entry stopgap (base ADR's Decision 3 above — no payment-gateway automation yet, an admin keys in a "fee received" ledger row) rather than building two separate collection flows; upgrade either to a real invoice/automated flow later if volume justifies it.

16. **`Reseller.markup_pct`/`max_markup_pct` are unchanged in meaning.** Still the reseller's own margin, applied on top of whatever they pay the platform (Decision 11), when reselling to their own downstream customers — entirely orthogonal to the new tier system (Decisions 10-14). Nothing here touches those existing fields or `docs/prd.md`'s existing Glossary entry for "Reseller Markup (Phase 2)".

**Addendum, 2026-08-29 (same day, grilled live via `/mattpocock-skills:grilling`, then built) — Phase 6.5: member registry + fee collection + membership money views.** Triggered by the founder asking to continue the membership work immediately after Phase 6 shipped. Grilling surfaced that the "membership fee collection + money views" gap (the OPEN addendum's own item 7) was bigger than it read on paper: **there was no code path anywhere that actually creates a `memberships` row** — Phase 6 only *reads* one at checkout. No subscribe endpoint, no admin entry — so the whole feature was inert until a member could come into existence. The grilling pinned the member lifecycle, then the build delivered it. Decisions Q1-Q15 (below) are settled, not open.

*Member lifecycle (grilled, settled):*

- **Q1 — renewal while still active extends, not resets:** a mid-cycle payment sets `expires_at += 30 days` (cumulative), never a fresh now+30d window.
- **Q2 — quota resets only at the cycle boundary, never on payment:** the rolling 30-day cycle anchored to `cycle_started_at` is the sole refill trigger (already implemented by `ResetMembershipCyclesCommand`); a mid-cycle renewal extends the paid-through date only, leaving `quota_remaining_sen` and `cycle_started_at` untouched. A member who paid twice within one cycle keeps using their remaining quota until the boundary, then gets a fresh full quota. This is the stricter anti-abuse reading of decision 7/12 — renewal cannot mint extra quota mid-cycle.
- **Q3 — `super_admin` only:** matches the tier-config screen's own gate.
- **Q4 — fee pre-filled from `plan.fee_sen`, editable, reason required on deviation:** manual collection realistically produces lump-sum/promo/waived amounts that don't exactly equal the plan fee; a non-plan amount needs a `reason` (audit trail), mirroring the VCH Path A admin-typed-amount precedent.
- **Q5 — plan change on renewal allowed:** the record-payment action carries a tier picker; `membership_plan_id` is always set to the submitted plan (upgrade/downgrade is a natural renewal-time action).
- **Q6 — no maker-checker:** this is income into the platform, not a payout; a plain `super_admin` action with the ledger `created_by`/`reason` audit is sufficient.
- **Q7 — the `active → expired` flip is now real:** `ResetMembershipCyclesCommand` flips `status=expired` for any active membership past `expires_at` BEFORE the quota refill sweep runs (and the sweep skips expired rows). This makes `status` a trustworthy field (the enum + doc intent existed since Phase 5 but nothing ever wrote `expired`), fixes the registry filter, and stops a lapsed member's quota being pointlessly refilled.
- **Q8 — reactivation updates the same row:** a lapsed/expired email's record-payment reactivates the existing row (`active`, fresh cycle, full quota, `expires_at = now+30d`) — order-history linkage by email (decision 3) survives, no new row.
- **Q9 — registry is a flat table, no drill-down:** email/tier/status/cycle/expiry/quota used/order count, search + status filter + pagination. Per-member order drill-down stays in Customer Analytics (ADR-049).
- **Q10 — membership money view:** a new Membership tab in Reports splits Paid-order sales by `pricing_basis` (member vs standard), shows margin forgone = Σ(`normal_selling_price − selling_price`) over member orders (the discount the platform gave, in cash terms), and membership fee revenue = Σ `ledger_entries.type=membership_fee` scoped by the entry's `created_at`.
- **Q11 — idempotency key, not just a confirm modal:** `membership_fee_records.idempotency_key` (nullable unique) + a fast-path pre-check, mirroring ADR-035 — a double-submit can't double-book.
- **Q12 — single seam for the future auto path:** `MembershipFeeService::recordFeePaid()` is the only entry point; a future payment flow's webhook calls the same method.
- **Q13 — zero-amount waiver allowed:** `amount_sen` may be 0 with a reason (founder waives / free period), still activating the membership.
- **Q14 — not gated on the kill switch:** admin registry/record-payment stay usable pre-launch (admin needs to manage members regardless of the customer-facing `membership_enabled` flag).
- **Q15 — effective status computed at query time:** until the scheduled flip runs (still inert-until-real-cron locally), the registry computes `(status==expired || expires_at < now) ? expired : active`, so a lapsed-but-not-yet-flipped member still reads `expired`.

*Shipped (all on `feature/membership-fee-registry-money-views`):*

- `membership_fee_records` table + `MembershipFeeRecord` model (insert-only audit, unique `idempotency_key`).
- `MembershipFeeService::recordFeePaid()` — create/extend/reactivate/plan-change in one transaction, `lockForUpdate` on the membership row (after it's guaranteed to exist — locking a missing email would gap-lock/deadlock), ledger `membership_fee` credit, fee-record insert as the idempotency serialization point. Two distinct unique-constraint recoveries: `memberships.email` (caught *inside*, re-read via a CURRENT `lockForUpdate()` read — a REPEATABLE-READ snapshot read cannot see the winner's committed row) vs the fee record's `idempotency_key` (propagates *out*, rolls back, returns the winner's membership).
- `LedgerService::credit()` gained an optional `$reason` param (additive).
- `Admin\MembershipController` (`GET /api/memberships` registry, `POST /api/memberships/record-payment`) behind `admin.role:super_admin`; `RecordMembershipPaymentRequest` (reason-required-on-deviation cross-field rule).
- `ResetMembershipCyclesCommand` — the Q7 flip + skip.
- `ReportService::membershipBreakdown()` + `ReportController` endpoint + `GET /api/reports/membership-breakdown`.
- Admin `/admin/membership` "Members" section (DataTable + Record Payment modal) and a new "Membership" Reports tab.

**Consequence to track (this addendum):**
- `membership_fee` is now a real ledger type; `reseller_tier_fee` (decision 15 of the prior addendum) remains unbuilt — only the consumer membership fee is booked today.
- The full cycle (Q7 flip, quota refill) still runs on the inert-until-real-cron schedule — locally `app:reset-membership-cycles` must be run by hand (Q15's derived status covers the display gap in the meantime).

**Addendum, 2026-09-20 — badge/copy fix, tier-economics redesign, and quota-transparency UX, grilled with the founder over an extended session.** Started from the founder noticing `/membership`'s "Save 60%" badge didn't match the catalog's real ~5% savings — the raw `discount_percent` (a "% cut off package markup" config value) was being shown as if it were the real price-level savings customer actually gets.

- **Root cause of the badge bug**: `MembershipSubscribe.tsx` displayed `plan.discountPercent` directly. `PackageGrid.tsx`/`MembershipPromoCard.tsx` already computed the real number correctly (`(1 - memberPrice/sellingPrice) * 100`) — three call sites duplicating the same formula, one of them wrong. Fixed by extracting a shared helper (`lib/membership-savings.ts`) all three now call.
- **A hard mathematical ceiling, found while modeling why the real % is so much smaller than the config knob**: the platform's markup is flat 10% across 99.8% of the catalog (a deliberate competitive-pricing floor, confirmed live against production — the founder does not want to raise it). Since a member price floors at cost (never below), the maximum possible real savings at *any* `discount_percent` — even 100%, i.e. the member pays raw cost — is `markup% / (1 + markup%)` ≈ 9.09%. No copy fix or discount-tuning can make the badge honestly bigger than that ceiling.
- **A second, more consequential structural finding**: a member whose realized monthly spend clears their tier's own break-even point (`fee ÷ forgone-margin-rate`) is *less profitable per RM* to the platform than if they had stayed a standard-price guest — the customer's savings and the platform's forgone margin are the exact same dollars, moving from one side to the other. Simulating the *current* numbers (Tier 1: RM8.90/50%/quota RM200, Tier 2: RM19.90/60%/quota RM500) against a 28,848-row proxy dataset (**not** PekanGame's own sales — a different reseller network's historical order data, used only as a realistic customer-spend-pattern stand-in, since PekanGame itself has had exactly one real member and 19 real paid orders to date) under a *self-selecting* adoption model (only customers whose typical spend already clears break-even choose to subscribe) showed the platform's aggregate profit lift over "no membership at all" was razor-thin (~+RM476 over the dataset's 9-month window) — thin because both tiers' `quota_sen` sat well **above** their own break-even, so a member who maxed their quota cost the platform up to RM1.10 (Tier 1) / RM10.10 (Tier 2) a month versus never having subscribed.
- **The founder's Costco-model framing, and why it doesn't transplant directly.** Costco's own merchandise margin is thin too — the membership *fee* is the real profit center, made durably profitable in the US by card-based recurring billing (a member who "forgets to cancel" keeps paying while under-using the discount). Checked CHIP Collect's real capability for this (its OpenAPI spec confirms genuine `remember_card` + `recurring_token` + `POST /purchases/{id}/charge/` tokenized recurring billing) — technically buildable, but the founder judged Malaysian top-up customers overwhelmingly prefer FPX/DuitNow QR over cards for small-ticket purchases (**<10% expected card adoption**), so a card-only auto-renew mechanism would only ever reach a small minority. **Deliberately out of scope for this addendum** — every renewal here is assumed manual/deliberate, not aided by billing inertia.
- **Final tier numbers**, arrived at by explicitly optimizing for customer benefit subject to "aggregate platform profit must not fall below the flat-10%-no-membership baseline" (the founder's own stated constraint, confirmed via a binary-search-to-crossover simulation against the same proxy dataset) and a deliberate real-save% gap between tiers (so Tier 2 reads as a clearly better deal, not a close call — the anchor psychology decision 4 already established):
  - **Tier 1**: fee RM19.90 (replaces the old RM8.90 tier — modeling showed *no* fee, however small, can make a subscription tier genuinely serve casual/light spenders once the 10% markup ceiling is accounted for, so the cheap tier was dropped rather than kept as a false promise), discount 70% (real-save ≈6.36%), quota RM335.
  - **Tier 2**: fee RM49.90 (up from RM19.90), discount 95% (real-save ≈8.64%), quota RM605.
  - Both tiers' quota now sits *above* their own break-even (a deliberate reversal of the "quota ≤ break-even, guaranteed-safe" design explored mid-session) — the founder chose maximizing genuine customer value over a per-member safety guarantee, accepting bounded platform exposure per heavy member in exchange for a value story that isn't just "break-even at best."
  - **Operational note**: the existing cross-tier `discount_percent` validation (Tier 2 must stay strictly above Tier 1) means these two edits must be applied in a specific order in `/admin/membership` — Tier 2 to 95% *before* Tier 1 to 70%, or the intermediate state (Tier 1 at 70% while Tier 2 is still at its old 60%) is rejected.
- **`UpdateMembershipPlanRequest`'s `discount_percent` rule tightened from `max:1000` (an oversight, never a deliberate ceiling) to `max:95`** — a small, deliberate buffer against ever hard-setting a literal 100% (member pays exact cost, zero margin, zero cushion against price-sync lag or a stale `cost_price`), discussed and rejected as the final number specifically because of that lack of buffer.
- **The old "quota ≤ break-even" hard-safety idea (drafted mid-session) is *not* enforced as a validation rule**, since the founder's final numbers deliberately violate it — replaced with a soft, computed warning in the admin tier-edit form (break-even spend + the resulting max monthly loss at full quota use, both derived client-side from the fee/discount/quota the admin is about to save), so an admin can see the exposure and choose to accept it rather than being blocked.
- **Dynamic "Rule of 100" savings badge**: below a package's RM100 standard price, the badge shows the percentage (`Save 8.64%`) — above RM100, it shows the absolute amount (`Save RM43.20`) — because at low prices the percentage digit reads larger than the RM digit and vice versa above the RM100 crossover (a well-established retail pricing-psychology rule, not project-specific intuition). Applied everywhere the shared savings helper renders a badge.
- **Quota transparency, a UX gap found while discussing the all-or-nothing per-order quota mechanic** (`OrderPricingResolver::resolveMember()` silently reverts an entire order to standard price if its member price would exceed the remaining quota — no partial application, since a package is a single atomic price, not a splittable cart line). Storefront now surfaces this *before* checkout rather than only after: `PackageGrid.tsx` shows a "Member quota left this cycle" strip plus a per-card note on any package that would exceed the remaining balance; `ReviewModal.tsx` shows a prominent warning ahead of "Confirm & Pay" when the real preview resolves to standard price for a signed-in member. Deliberately inline, not a popup — `PackageGrid` shows several packages at once, and a modal firing on every tap while comparing would be modal-fatigue, not native-app polish; the *existing* `ReviewModal` (already a deliberate blocking step) is where a modal-strength warning belongs.
  - **Two real bugs found live-testing this addendum before it shipped**, both against the actual browser, not just the type checker: (1) the "Member Price" row label and its "Standard price" strikethrough were driven by the catalog's `memberPricePersonalized` flag, which doesn't know about quota — an order that fell back to standard price due to insufficient quota still showed a "Member Price" label on the (identical, standard) number, doubly confusing; fixed by deriving the label from the real checkout `preview.member_discount_percent` once it loads, falling back to the catalog flag only while a preview is in flight. (2) The new quota warning fired for a visitor who had verified their email via OTP (so a valid membership-session token exists) but never actually subscribed to a paid tier — `isMember` was wrongly derived from "has a verified session" instead of "has an active plan"; fixed to key off `activeTierName !== null`, which is only set once a real `Membership` row with a plan exists.
- **Numbers not seeded via migration** — matching this project's existing precedent (`fee_sen`/`quota_sen`/`discount_percent` have always been founder-typed via `/admin/membership`, not code-shipped), this addendum ships the mechanism only; the founder applies the new Tier 1/Tier 2 values in production themselves, in the order noted above.

**Consequence to track:** the CHIP recurring-card-billing capability is now a confirmed, buildable option (`remember_card`/`recurring_token`) for a future auto-renew feature, should card adoption ever justify it — nothing here forecloses it, it's simply not this addendum's scope. **Addendum 3, 2026-09-22 (HTML Email Templates):** Grilled and accepted via `/mattpocock-skills:grilling`. Replaces plain-text string concatenation for the 5 existing Plunk-routed emails (membership OTP, affiliate portal invite, membership receipt, domain status nudge, backup failure alert) with Laravel's built-in Markdown Mailables.

- **Decision 1 (Location):** Templates live in code (`resources/views/emails`) as Laravel Blade Markdown components (`<x-mail::message>`). Keeps code-as-truth rather than outsourcing design into Plunk's external visual editor.
- **Decision 2 (Adapter Mechanism):** Retains direct `PlunkMailer` usage (`POST /v1/send`), avoiding a massive Custom Mail Driver rebuild. Adds a `sendView()` method to `PlunkMailer` to render the Markdown Mailable into an HTML string before sending it to Plunk's `body` payload.

**Post-grill correction, same day:** the first pass assumed an `Affiliate::branding` Eloquent relation that doesn't exist anywhere in the codebase (every real caller — `BrandingController`, `Admin\SettingsController`, `GalleryImageController` — queries `AffiliateBranding::where('affiliate_id', ...)` directly). Two failure modes from this: (1) `SendMembershipReceiptJob` eager-loaded `'affiliate.branding'`, which throws `RelationNotFoundException` — caught live by `ChipWebhookControllerTest`, a 500 on every paid-membership webhook under the `sync` test queue, a silently-failed job under the real Redis queue; (2) every other read used `$affiliate?->branding`, which Eloquent's magic getter just resolves to `null` — so no email ever actually carried affiliate whitelabel branding, contrary to what this addendum implies shipped. Fixed by adding `PlunkMailer::brandingFor(?Affiliate $affiliate)`, which queries `AffiliateBranding::withoutAffiliateScope()->where('affiliate_id', ...)` (the same ADR-057 scope-bypass every other caller already uses) instead of a relation. `resources/views/vendor/mail/html/header.blade.php`'s DB-query fallback (same broken relation, plus an unnecessary query on every email that doesn't pass branding explicitly) was removed outright — those emails (invite/backup/domain-status) are platform-to-affiliate-or-admin mail and were always meant to render as plain PekanGame, no lookup needed.
