# ADR-096: Admin "Check from Supplier" / "Check from Gateway" manual poll — a deliberate, scoped ADR-014 exception, shared logic with the existing reconcile jobs, cache-based cooldown

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled 2026-09-15 on `feature/adr-096-manual-poll-buttons` (not yet built as of this entry).

**Context:**

Trigger: a real prod incident the same day. Two orders — order 7 (combo, placed via a Reseller wallet, `PG-MXDUOIZN6KSK`) and order 8 (plain, storefront Membership, `PG-HXLHGZ1H8ZFM`) — were both confirmed `Sukses` on Digiflazz's own dashboard and delivered in-game, but stuck at `delivery_status=pending` in our system. Root cause (see the same-day fix, `fix/digiflazz-webhook-sku-case-mismatch`): Digiflazz's `update` webhook event lowercases `buyer_sku_code`, our stored ref is uppercase, `DigiflazzWebhookController`'s exact `!==` compare rejected every real callback with a 409. Not a Reverb problem — Reverb only broadcasts after `finalizePendingDelivery()` runs, so it never got the chance.

Founder's first question after the root-cause fix: could an admin-triggered manual poll button shorten the wait instead of relying only on the ~10-15 min scheduled reconcile poll. Facts checked before grilling further:

- **Real order volume is 5 total (non-test), ever**, as of this grill — pre-scale, the founder having just funded the Digiflazz wallet this same day. Both stuck orders **self-healed via the existing `ReconcilePendingDeliveriesCommand` → `CheckSupplierDeliveryJob` poll** before this ADR's grill even finished (confirmed `delivered` in prod at 09:15:06, ~13-17 min after creation) — the webhook fix alone, at today's volume, already resolves the underlying bug for future orders.
- A separate order (`PG-ZUOSHF3Q9FOC`) has sat at `payment_status=pending` since 2026-09-11 — a real, live example of the payment-side counterpart (`ReconcilePendingPaymentsCommand`'s own reconcile territory), not just a theoretical case for the "Check from Gateway" half.
- `CheckSupplierDeliveryJob` already contains the exact per-order status-check + finalize logic needed (including combo per-leg looping, ADR-094 decision 7) — it's queued (ADR-014), used only by the scheduled poll today. `ReconcilePendingPaymentsCommand`'s equivalent payment-side logic (`reconcile()`/`recover()`/`markFailed()`/`flagIfStale()`) is `private`, buried in the command, no reusable public entry point.
- `delivery_status=Processing` (Gap X, ADR-026) is a structurally different state from `Pending` — an order that never successfully submitted to the supplier at all (no `supplier_ref`), whose correct recovery is a fresh `FulfillOrderJob` re-attempt (`retryDelivery()`/`resend()`, already built), not a status *inquiry* against a submission that doesn't exist supplier-side.
- Digiflazz's own docs: don't re-submit a status check for the same transaction within 1 minute of the previous one.

**Decision:**

1. **Build it now, alongside the webhook fix — not deferred despite the low current pain.** The founder's own call: the fix alone resolves today's specific incident, but real order volume is about to grow now that the supplier wallet is funded, and an admin-facing status-check surface is worth having in place before that happens rather than retrofitted under pressure later.
2. **Scope: `delivery_status=Pending` only for "Check from Supplier"** (not `Processing`, which already has its own recovery path via Retry/Resend Delivery) and **`payment_status=Pending` only for "Check from Gateway"**. Two buttons, each gated on its own single status value — no new bucket invented.
3. **One button per order, not per-leg, for a combo order.** `CheckSupplierDeliveryJob`'s existing `checkComboLegs()` already loops every still-`Pending` leg for the order in one call — the manual trigger reuses that as-is; no separate per-leg UI.
4. **Placement: Order detail page only**, not the order list row — the result is a JSON receipt that needs real display space, matching the existing Resend Delivery modal's own footprint rather than a list-row action.
5. **Synchronous call, a deliberate scoped exception to ADR-014.** ADR-014's "never call the supplier synchronously" rule was written for *scheduled commands* dispatching unpredictable-duration work off the request thread — this is a single, short, read-only status-inquiry call, admin-initiated, not a scheduled job's own unattended execution. The founder explicitly wants to see the raw JSON response the moment the button is clicked, which a queued job can't give without a second polling/refresh mechanism this feature's size doesn't warrant. Short timeout (~10s), caught and surfaced as an error state rather than left to bubble.
6. **Auto-apply, not preview-then-confirm.** A terminal outcome (Sukses/Gagal, Paid/Failed) finalizes the order immediately, through the exact same locked write path a webhook or the scheduled poll would use (`finalizePendingDelivery()`/`finalizePendingDeliveryLeg()` for supplier; the payment recover/markFailed logic for gateway) — the JSON shown is a receipt of what happened, not a draft awaiting a separate approval click. Matches the button's actual purpose (speed up confirmation) rather than adding a manual-review gate nothing else in this flow has.
7. **Shared logic, not duplicated.** `CheckSupplierDeliveryJob`'s checkStatus+finalize+leg-loop body is extracted into a plain service method the Job (unchanged scheduled-poll behaviour) and the new admin controller action both call. `ReconcilePendingPaymentsCommand`'s private `reconcile()`/`recover()`/`markFailed()`/`flagIfStale()` are extracted into a new public `PaymentReconciliationService`, used the same way by both the command and the new controller action. Neither existing scheduled path changes behaviour — this is a second caller of the same logic, not a rewrite.
8. **Cache-based cooldown, not a new DB column.** A Redis cache key (`manual-check:{order_id}` / `manual-check:{order_id}:leg:{leg_number}`, ADR-077's existing cache driver) with a TTL default of 60s — matching Digiflazz's own documented 1-minute re-check limit — set after *every* attempt (success, terminal failure, or error/timeout alike), so a spammed click or a supplier outage never triggers a rapid-fire retry loop against a possibly-degraded upstream. Overridable per-supplier via `Supplier.api_config['manual_check_cooldown_seconds']`, mirroring the existing `pending_stale_minutes`/`max_reconcile_age_days` override pattern (ADR-032 decision 6) for a supplier with a different real limit. The endpoint rejects (422) with the remaining cooldown seconds while active; the button disables client-side with a countdown from the same value.
9. **No new admin permission gate.** Reuses the existing `admin.role:super_admin,admin` middleware already covering every other order action — the JSON shown is the supplier/gateway's own raw response, not one of this codebase's own internal financial fields (`cost_price`/`platform_profit`/etc.), so no new exposure concern beyond what an admin can already see via `supplier_response`.

**Rationale:**

- Narrowing scope to exactly `Pending` (never `Processing`) keeps this feature from overlapping with — or confusing admins against — the existing Resend/Retry Delivery actions, which solve a structurally different problem (re-submission vs. status inquiry).
- Sharing logic with the scheduled reconcile paths (decision 7) is the same "deep modules, stable seams" discipline this codebase already applies to `SupplierAdapter`/`PaymentGateway` — a second caller of proven logic, not a parallel implementation that can silently drift from the one the scheduled poll relies on.
- The ADR-014 exception (decision 5) is scoped narrowly and explicitly on purpose — a single short read-only call, never extended by implication to any other supplier/gateway interaction (e.g. this does **not** license a future synchronous order-creation call from a request thread).
- The cooldown (decision 8) protects the real constraint (Digiflazz's own rate limit) with the least new infrastructure — a cache key over a schema migration — while staying overridable for a supplier with a different real number, consistent with how this codebase already handles per-supplier reconciliation tuning.

**Consequence to track:**

- If real order volume grows enough that admins are clicking these buttons constantly (rather than the rare manual check this was designed for), that's a signal the *scheduled* poll's own cadence (`pending_stale_minutes`, `pending_after_minutes`) should tighten — not a reason to loosen this feature's cooldown.
- Decision 5's ADR-014 exception is intentionally narrow — do not treat this ADR as precedent for a different synchronous-from-request-thread supplier/gateway call without its own explicit grill.
- If a future supplier's real re-check rate limit differs meaningfully from Digiflazz's 1 minute, set it via `Supplier.api_config['manual_check_cooldown_seconds']` (decision 8) rather than changing the global default.
