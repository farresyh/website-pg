# ADR-078: Custom-domain storefront gaps — dynamic CORS, edge-cache staleness, membership-toggle visibility

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-07, grilled with the founder in the same three-round session as ADR-077, split out by natural boundary (this is ADR-060's lineage — the gaps that surfaced once a real custom affiliate domain went live — not the platform-wide cache work). No code in this ADR.

**Context:**

ADR-060 PR-1…PR-6 shipped to production 2026-09-06/07 and the founder attached a real custom affiliate domain. Three gaps surfaced that PR-5's checklist did not cover.

1. **CORS blocks every browser-originated call from a custom affiliate domain.** `config/cors.php` `allowed_origins` is a static list built from `ADMIN_URL` + `STOREFRONT_URL` + `RESELLER_PORTAL_URL`. A custom affiliate domain is not in it, so the browser gets no `Access-Control-Allow-Origin` header and blocks the request; `apiFetch` surfaces the storefront's generic "something went wrong". SSR calls are unaffected (no browser, no CORS), which is why the storefront *looks* alive — but every `"use client"` call fails: `POST /api/games/{game}/validate-player`, `POST /api/checkout` + `/checkout/preview-totals`, the `/membership` OTP send/verify and dashboard, `GET /api/track-order/{orderNumber}`, and the personalised (membership-token) `GET /api/catalog/games/{slug}/packages` — so on a custom domain neither the standard nor the member price loads client-side. This is one gap with many symptoms; PR-2 wired `X-Storefront-Host`, PR-5 shipped custom domains, CORS was never updated. `fruitcake/php-cors` v1.4.0 (`isOriginAllowed()`) matches `allowed_origins` by `in_array` and `allowed_origins_patterns` by `preg_match` only — **no closure support**, so a config-level callback against the DB is not available.
2. **`storefront/src/proxy.ts` serves stale redirect rules and stale host verdicts for up to 60 s.** It runs on every storefront request and makes up to two backend calls (`GET /api/catalog/seo/redirects`, `GET /api/catalog/storefront-status`), each cached in **module memory** with a 60 s TTL and **no way to bust it**. So a newly-added SEO redirect does not fire for up to a minute; a just-verified custom domain shows `/store-unavailable` for up to a minute; a just-removed/suspended one keeps serving. Each Vercel Node instance has its own independent cache age. `AffiliateDomainService` never calls `NextRevalidation::purge()`.
3. **An `is_owned` affiliate has `membership_enabled` defaulting to `false`.** `affiliates.membership_enabled` (migration `2026_08_31_010000`) defaults `false`, and `Affiliate::membershipEnabledEffective()` is `membership_enabled && PlatformSettings.membership_enabled`. So a freshly-created "our own brand" affiliate shows no member pricing and no `/membership` nav until the founder ticks `membership_enabled` for it in `/admin`. ADR-061 made membership a deliberate per-brand opt-in; the gap is that the admin creating an `is_owned` affiliate is not told they need to tick it.
4. **`api.pekangame.space/` (bare backend root) throws `RouteNotFoundException`.** `routes/web.php` serves `resources/views/welcome.blade.php`, which calls `route('login')` / `route('register')` — neither is registered (no Breeze/Fortify/laravel-ui). Bots hitting the API root trigger it (Pulse: 4 occurrences, ~23 h apart). Separately, that same `/` route is a **closure**, which means `php artisan route:cache` in the Forge deploy script should throw `LogicException` (closures are not serialisable) — so route caching is either silently failing or being skipped in production, a small per-request cost on every API call.

**Decision:**

1. **Dynamic CORS via a rebound `CorsService` singleton.** In a service provider, bind `Asm89\Stack\CorsService` (Laravel resolves it as a singleton, effectively per-request under PHP-FPM) with `allowedOrigins` computed as the existing configured origins plus `AffiliateDomain::query()->where('status', 'active')->pluck('hostname')` mapped to `https://{hostname}` (and the apex/`www` variants as applicable). The active-domain list is `Cache::remember`'d (Redis, 60 s) and busted by the same `AffiliateDomainService` hook added in decision 2. `supports_credentials` stays `false` (the storefront API is guest / no-cookie, ADR-011), so this is not a credentialed-CORS risk. A wildcard (`allowed_origins: ['*']` or an `https://.+` pattern) was rejected: legal here, but it drops the allow-list entirely and would not survive a security review — the founder asked for "clean, reliable".
2. **`proxy.ts` staleness: shorten the TTL and skip the check for the primary host.** `CACHE_TTL_MS` drops from `60_000` to `15_000` — redirects and domain onboarding both tolerate a 15 s lag, and the extra backend calls (one per 15 s per instance) are negligible. `isKnownHost()` gains a short-circuit: if the request host is in a storefront-side `NEXT_PUBLIC_PRIMARY_HOSTS` list, return `true` without any backend call — so the primary storefront (the overwhelming majority of traffic) pays nothing for the host check, and only custom domains hit `/api/catalog/storefront-status`. `AffiliateDomainService` starts calling `NextRevalidation::purge()` on every state change (add/verify/remove/suspend/setPrimary) so the Next.js Data Cache and the decision-1 CORS list both bust — but no cross-Vercel-instance proxy invalidation is built; 15 s is an acceptable floor. Deleting the module cache entirely (hit the backend every request) was rejected: it adds a Vercel→Cloudflare→droplet hop to every storefront page's TTFB, on the exact perceived-latency path ADR-071 spent five PRs improving.
3. **`is_owned` membership: keep the `false` default, add an admin-form warning.** When `is_owned` is checked in the affiliate create/edit form (`admin/`), show an inline note that membership pricing and the `/membership` surface stay off for this brand until `membership_enabled` is ticked, with the toggle right there. ADR-061's per-brand opt-in is deliberate and not reversed; the fix is that the admin is now told. The existing `fixfastapp.com` affiliate is left with membership off (it is a third-party `is_owned` brand, not the founder's own storefront — the founder can tick it whenever that brand wants membership).
4. **Replace the backend root route.** `Route::get('/', …)` points at a tiny invokable controller (or `HealthController`) returning `response()->json(['service' => 'PekanGame API', 'status' => 'ok'])` — no Blade, no `route()` call, no closure. This removes the `RouteNotFoundException` source and unblocks `php artisan route:cache` (which the deploy script runs). `resources/views/welcome.blade.php` is deleted.

**Explicitly out of scope:** the OpenWA nginx `127.0.0.1` IP restriction on `/api/webhooks/openwa` and the droplet resize (Forge-box config / founder tasks, tracked in ADR-075); the ADR-060 real-reserved-domain end-to-end SSL/custom-hostname verification (a founder manual step, tracked in ADR-060); `CommandNotFoundException` in Pulse (not reproducible from the repo — most likely a manual `php artisan <typo>` or a Forge cron entry outside version control; noted, not actioned).

**Delivery:** Feature branch `feature/adr-078-custom-domain-gaps` off `staging`, after ADR-077's PR-1 (decision 1's CORS cache wants Redis).

- **PR-1 — dynamic CORS** (decision 1): the rebound `CorsService`, the cached active-domain list, a feature test that a request with an active custom-domain `Origin` gets the header and an unknown one does not.
- **PR-2 — proxy staleness** (decision 2): `CACHE_TTL_MS` 15 s, the `NEXT_PUBLIC_PRIMARY_HOSTS` short-circuit, `AffiliateDomainService::purge()` at every state change.
- **PR-3 — admin warning + root route** (decisions 3, 4): the `is_owned` form note, the root-route swap, `welcome.blade.php` deletion.

**Rationale:**

- The CORS gap is a straight regression — PR-5 shipped custom domains and the CORS list was simply never updated. It belongs on PR-5's checklist retroactively; recording it as an ADR decision (rather than a silent fix) is worth it because the *mechanism* (rebinding the framework's CORS singleton against a DB-backed list) is non-obvious and a future reader adding a fourth first-party origin needs to know why `config/cors.php` alone is no longer the whole story.
- The proxy TTL shortening over a proper invalidation signal is the deliberate "good enough, less to maintain" call: a cross-instance cache-bust for a Node-runtime middleware is real machinery for a 15-second improvement on a rare event (redirect edits, domain onboarding).
- Keeping the `is_owned` membership default at `false` respects ADR-061; the problem was never the default, it was the missing signposting.
- The root-route fix is tiny but it also quietly restores `route:cache` in production — worth doing deliberately and recording so the next person who sees `RouteNotFoundException` in Pulse knows it was addressed.

**Consequence to track:**

- **`docs/prd.md` §14/§15** — log each PR; §15's Resellers / Storefront rows note the CORS and proxy fixes.
- **The CORS active-domain list is now a runtime DB read on the request path** (cached, but the cache can miss) — confirm the 60 s Redis cache + the `AffiliateDomainService` bust keep it off the hot path, and that a preflight `OPTIONS` for an unknown origin fails fast (no DB call if the cache is warm).
- **`NEXT_PUBLIC_PRIMARY_HOSTS` is a second place the primary hostnames are configured** (the backend already has `STOREFRONT_PRIMARY_HOSTS`) — they must stay in sync; a mismatch means the primary storefront pays for the host check (harmless) or a primary host is wrongly short-circuited as known (also harmless — it *is* known). Document the pairing.
- **`AffiliateDomainService::purge()` is a new backend→storefront coupling** — same failure mode as ADR-071's revalidate webhook: if it fails silently, staleness falls back to the (now 15 s) proxy TTL and the 30 s Data-Cache backstop. Greppable log line.
- **Deleting `welcome.blade.php` and swapping the root route** — confirm nothing (a health check, an uptime monitor, a load balancer probe) depends on `GET /` returning 200 HTML; the JSON 200 should satisfy all of them, but check the DO uptime check and Forge's own.
- **If `route:cache` was silently failing before** — enabling it may surface a latent route-definition problem (a duplicate name, a stale cache). Run `php artisan route:cache` locally as part of PR-3 and in CI to catch it before deploy.

### PR-1 build addendum (2026-09-08) — mechanism changed from "rebound `CorsService`" to a prepended middleware

Decision 1's sketched mechanism (bind a custom `Fruitcake\Cors\CorsService` whose `allowedOrigins` includes the DB-backed list) does not work against Laravel's own `HandleCors`:

- `Illuminate\Http\Middleware\HandleCors::handle()` calls `$this->cors->setOptions($config['cors'])` **unconditionally on every request whose path matches `cors.paths`** — overwriting anything a rebound service pre-computed at bind time.
- Overriding `setOptions()` to re-merge the dynamic origins there *does* survive that call, but `setOptions()` has no `Request`, so it cannot tell a real CORS request (has `Origin`) from a plain one — every `api/*` request would then do the (cached, but cache-missable) `affiliate_domains` read, including health checks and server-to-server calls. Two suites that make HTTP calls without migrating the DB (`ExampleTest`, `TrustedProxiesTest`) failed outright on the missing table.

**Built instead:** `App\Http\Middleware\AllowActiveCustomDomainCors`, `prepend`ed to the global stack so it runs before `HandleCors`. It reads the `Origin` header; if present and not already a configured first-party origin, and it matches the active custom-domain list, it appends that one origin to `config('cors.allowed_origins')` for the request. `HandleCors` then reads the mutated config as normal. A request with no `Origin` does zero work and never touches the cache or DB.

- `App\Services\Cors\ActiveCustomDomainOrigins` — `all()` returns `https://{hostname}` for every `AffiliateDomainStatus::Active` row (`withoutAffiliateScope()`), `Cache::remember`'d 60 s (Redis in prod, ADR-077); `flush()` busts it. **PR-2 wires `flush()` into `AffiliateDomainService` at every state change** (alongside the `NextRevalidation::purge()` call that PR is already adding) — until then the 60 s TTL is the only freshness bound, acceptable for domain onboarding.
- `supports_credentials` stays `false` (untouched — the merge only ever *adds* an origin string).
- Coverage: `tests/Feature/Http/CorsConfigTest.php` — active-domain `Origin` gets `Access-Control-Allow-Origin` (preflight + actual request), unknown origin gets none, pending/suspended/failed rows get none, the list caches and flushes, `Access-Control-Allow-Credentials` never appears. Full fast suite 1617/1617.
- The ADR-078 doc text and decision 1 keep the "rebound `CorsService`" language for the historical record; this addendum is the authority on what shipped.

### PR-2 build addendum (2026-09-08) — proxy staleness

Shipped as decision 2 specified, with the propagation hook covering PR-1's CORS cache too.

- **`storefront/src/proxy.ts`:** `CACHE_TTL_MS` `60_000` → `15_000` (both the redirect-rule cache and the per-host verdict cache). New `PRIMARY_HOSTS` set from `NEXT_PUBLIC_PRIMARY_HOSTS` (comma-separated, lower-case) — `isKnownHost()` returns `true` for a primary host with **no backend call** (port stripped before matching, for local dev), so only a third-party custom domain hits `/api/catalog/storefront-status`.
- **`App\Services\Affiliate\Domain\AffiliateDomainService`:** new private `propagateChange()` — `ActiveCustomDomainOrigins::flush()` (PR-1's CORS list) **and** `NextRevalidation::purge()` (the storefront Next.js Data Cache). Called from `add()`, `remove()`, `setPrimary()`, `suspendAll()`, `removeAllForDelete()`, `tearDownStuckPending()` unconditionally, and from `recheck()` **only when `status` or `is_primary` actually moved** (so the daily `app:sync-affiliate-domain-status` loop doesn't purge the storefront catalog once per domain per day for no reason). `resumeAll()` propagates via its inner `recheck()` calls.
- No cross-Vercel-instance invalidation for the `proxy.ts` module cache — 15s is the floor, as decision 2 accepted.
- **Deploy prerequisite:** `NEXT_PUBLIC_PRIMARY_HOSTS` must be set on the storefront's Vercel project (pair of the backend's `STOREFRONT_PRIMARY_HOSTS`, set in Forge 2026-09-06). Safe to ship before it is set — an unset value just means the primary storefront falls through to the (harmless, always-`known`) backend host check, a perf regression only, never a breakage.
- Tests: `AffiliateDomainServiceTest` gains "a state change busts the CORS cache and purges the storefront" + "recheck with no state change does not propagate". Full fast suite 1619/1619; storefront `tsc` / lint / build clean.

### PR-3 build addendum (2026-09-08) — admin `is_owned` warning + root route

**Decision 3 — `is_owned` membership signposting.** `admin/src/components/affiliates/AffiliateFormModal.tsx` already had the `is_owned` block with the "Enable consumer Membership" checkbox inline. Added: when `is_owned` is on **and** `membership_enabled` is off, an inline amber note — *"this storefront shows standard pricing only — member prices and the `/membership` section stay hidden, even with the global membership switch on (ADR-061 makes Membership a per-brand opt-in)"*. Default stays `false`; `fixfastapp.com` left as-is. No other change.

**Decision 4 — root route.** New invokable `App\Http\Controllers\ApiRootController` returning `response()->json(['service' => 'PekanGame API', 'status' => 'ok'])`. `routes/web.php` `GET /` points at it; `resources/views/welcome.blade.php` deleted. `ExampleTest` now asserts the JSON contract instead of "200 HTML". `HealthController` (the DB+queue probe at `/api/health`) is untouched — this route depends on nothing.

- **Correction to the decision's premise:** `php artisan route:cache` does **not** currently throw on this Laravel version — a closure `GET /` route serialises fine via `Laravel\SerializableClosure` (verified locally before and after the change). The `RouteNotFoundException` from `welcome.blade.php`'s guarded `route('login')` path on bot traffic is the real, reproduced motivation; removing the Blade view also removes the only closure/`route()` call from `routes/web.php`, so the change still stands on cleanliness grounds — just not because `route:cache` was broken.
- Nothing depends on `GET /` returning HTML: the DO uptime check + Forge health probe target `/up` (framework health route) and `/api/health`; a JSON 200 satisfies a plain reachability probe too.
- `php artisan route:cache` run clean locally; CI's existing steps cover it on deploy.
