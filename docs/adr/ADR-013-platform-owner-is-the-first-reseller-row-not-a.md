# ADR-013: Platform owner is the first Reseller row, not a parallel single-tenant concept

> **Standing (2026-10-09):** Superseded by ADR-061. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-07-25 (formalizes a decision discussed but not previously written down; surfaced as a documentation gap during the CheckoutController planning pass). **Superseded by [ADR-061](./ADR-061-every-storefront-is-a-reseller.md) — 2026-08-30.** ADR-013's core idea (the platform owner is a `Reseller` row, not a parallel code path) is *kept and hardened*; what ADR-061 changes is the discriminator — the `business_name = 'Platform Owner'` magic string is replaced by explicit `is_owned` / `is_primary` flags, and "there is exactly one internal reseller" stops being true (the founder is onboarding a second internal brand).

**Decision:** There is no separate "platform owner" concept modeled alongside `Reseller`. The platform owner *is* the first `Reseller` row (`business_name = 'Platform Owner'`, `markup_pct = 0`), created once (seeded in `DatabaseSeeder`, with a `firstOrCreate` safety net in `CheckoutController` for any environment that skipped seeding). Every Order's `reseller_id`, and both `LedgerEntry` rows a delivered order writes (platform + reseller profit), reference this same row in MVP.

**Rationale:** This was already implied by `prd.md` §8's own Reseller data-model row ("Table exists from MVP... exactly one row is created for the platform owner's own internal storefront, typically with `markup_pct = 0`, so the pricing/ledger formulas never special-case 'no reseller yet'") and by ADR-003's tenant-ready-schema-from-day-1 decision — but the table was never actually built, and the *why* (avoid a parallel single-tenant code path that Phase 2 would have to delete) was never captured as its own decision. Making it explicit now: `PricingService::calculate()` always takes a `resellerMarkupPct`; `OrderFulfillmentService::creditProfit()` always writes two ledger entries (platform + reseller). Neither has an "if no reseller yet" branch — MVP and Phase 2 run the exact same code path, just against more `Reseller` rows.

**Consequence to track:** `CheckoutController` resolving `Reseller::firstOrCreate(['business_name' => 'Platform Owner'], ...)` is a stopgap for "exactly one MVP reseller," not a pattern to repeat once Phase 2 onboards real resellers — at that point, checkout needs a real reseller-resolution strategy (subdomain/custom-domain routing, per ADR's own open question in `prd.md` §12), and this hardcoded lookup gets replaced, not extended.
