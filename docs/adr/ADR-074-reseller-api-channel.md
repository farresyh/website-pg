# ADR-074: Reseller API channel — per-tenant API keys, order-placement/status endpoints

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-04, same grill session as ADR-072/073. Depends on ADR-073 (consumes its order-placement contract).

**Context:**
- This channel is a `Reseller` (wallet, ADR-073) account whose order-placing interface is a documented HTTP API the founder hands the reseller's own system, rather than a WhatsApp bot (ADR-075). The underlying money/tier/order logic is identical to the Bot channel — only the transport and the identification mechanism differ.
- No machine-facing (non-human-login) credential mechanism exists in this codebase today. Direct code check before this ADR: `AuthController`/`ResellerAuthController` mint Sanctum tokens with default `['*']` abilities and no expiry; the one scoped-ability precedent is `ResellerImpersonationController`'s `createToken($name, ['impersonate'], $expiresAt)` (always time-limited). `Supplier.api_config` (`encrypted:array` cast, `$hidden`) is this codebase's existing pattern for storing a *third party's* credentials safely, but there is no precedent for the inverse — issuing a long-lived credential *to* an external tenant.

**Decision:**

1. **A `Reseller` (wallet) account's API interface is authenticated by a dedicated `reseller_api_keys` table** (hashed key, shown once at creation, revocable/rotatable from the reseller's own Wallet portal screen or by admin), checked by a new dedicated middleware on the order-placement/status endpoints — **not** the portal-login `reseller` Sanctum guard token. Kept deliberately separate for the same reason ADR-058 kept the admin and reseller guards separate: "can I view my dashboard" and "can I spend real money placing orders" are different security surfaces and should never share one credential, especially given the portal-login token today defaults to unscoped `['*']` abilities.
2. **A `Reseller` (wallet) account may hold an API key and a linked WhatsApp group (ADR-075) simultaneously** — the two channels are not mutually exclusive. There is no reason to force an exclusive choice given the underlying wallet/tier logic is identical either way; a reseller can start on Bot and add API access later without a new account.
3. **The order-placement/status endpoints are the concrete HTTP surface over ADR-073 decision 4's contract**: create an order (package, target account/server, and the caller-supplied `idempotency_key` ADR-073 decision 4 now requires — same field/semantics `CheckoutController` already uses), fetch order status, fetch the current wallet balance and price list for the account's assigned tier. Exact route/payload shape is a build-time API-docs detail handed to the founder for the reseller-facing documentation, not a further design decision here.
4. **Per-`Reseller`-account rate limiting** (ADR-073 decision 9) applies at this HTTP layer specifically, its own throttle bucket keyed on the API key, not the caller's IP (an external reseller's own system may itself be shared infrastructure behind one IP).

**Rationale:** Decision 1's separate-table-and-middleware approach (rather than scoping the existing Sanctum guard with a new ability) avoids retrofitting `tokenCan()` checks onto a token-minting path (`createToken('reseller')`) that has never enforced abilities at request time anywhere in this codebase — a fresh, narrowly-scoped mechanism is safer to reason about and to test than adding the first-ever ability-gate to an existing broad-access guard.

**Consequence to track:**
- A key-rotation/revocation flow must exist from day one (not a "later" item) — a leaked long-lived API key that can spend a wallet balance is a real financial-exposure risk, unlike a portal-login session token that only reads.
- API documentation for the reseller-facing contract (decision 3) is an external-facing deliverable, tracked as its own task once the endpoint ships — not assumed covered by this ADR's internal design text.

**Orders visibility follow-up, same PR (founder-flagged during the live-verify walkthrough):** `/admin/orders` had no way to see, at a glance, which `Affiliate` (brand) or `Reseller` (wallet, ADR-074/075) an order came from — the DB columns (`affiliate_id`, `wallet_reseller_id`) and the detail endpoint's eager-loaded relations already existed, but the list endpoint didn't load them and neither the list table nor (for `wallet_reseller` specifically) the detail view rendered them. **Pricing card follow-up, same PR (founder question: "does the pricing card differ per order type?" — it didn't):** `OrderDetailCards.tsx`'s Pricing card was one generic layout for every `pricing_basis`, only `"member"` got its own extra fields — a `"reseller-wallet"` order rendered the exact same rows with several structurally-always-zero/inapplicable: `standard_selling_price` (the storefront's own guest/list price, never what a wallet order is actually priced off), `voucher_discount`/`transaction_fee` (no voucher path or CHIP round-trip exists for a wallet debit), `affiliate_profit` (always 0 by construction, ADR-073 decision 1's `affiliateMarkupPct: 0.0`) — reading as "something's missing" rather than "not applicable here." Simplified to pass `$package->cost_price`/`$package->standard_selling_price` straight through, dropped the now-unused `PricingService` constructor dependency, and removed a second now-redundant manual `reseller_tier_id === null` guard (the service's own `NoResellerTierAssignedException`, already caught, covers it) — added a test asserting that exception path is actually wired to a 422, not just theoretically reachable.

Live-verified against the same real wallet order from the walkthrough above (`cost_price=1000, selling_price=1100` → Reseller Markup renders `10.00%`, matching the tier's own `markup_percent` exactly). Backend 1351/1351 fast, Pint clean. Admin `tsc`/`eslint`/`next build` clean.

**Addendum — cross-reseller idempotency-key isolation gap, found + grilled 2026-09-26.** A same-day 4-branch production audit (Affiliate portal, Affiliate whitelabel storefront, Reseller Bot, Reseller API+docs — one background agent per branch) flagged this ADR's own order-placement contract (decision 4's idempotency check, as implemented in `ResellerOrderPlacementService::placeOrder()`) as the single **critical** finding: the lookup `Order::query()->where('checkout_idempotency_key', $request->idempotencyKey)->first()` (line 63, and its race-recovery twin at line 133) carries **no `wallet_reseller_id` filter** — it matches across every reseller, not just the caller's own account.

- **Real failure mode, worse than a benign accidental collision.** `docs-site`'s own `idempotency.md` only requires an 8-100 character key, not a UUID — two integrators independently sending a predictable value (their own internal order id, e.g. `"order-1001"`) is a plausible accident, not a stretch. Worse: nothing stops a malicious API caller from *deliberately* sending a key equal to a real Bot-channel order's derived key format (`wa:{group_id}:{message_id}`, ADR-075) to fish for another reseller's order. Since every Bot-channel order has `reseller_api_idempotency_payload_hash = null` by design (this ADR's PR-1 decision 5 — the Bot's key already derives from a WhatsApp message id, so no client payload exists to hash), `assertPayloadMatches()` skips its mismatch check entirely on a null-hash row and silently hands back a **200 Idempotent-Replayed** response carrying the real victim reseller's `player_id`/`price_sen`/`order_number`/`delivery_status` — a genuine violation of [ADR-084](./ADR-084-reseller-api.md) decision 2's explicit invariant ("never any other reseller's data").
- **Live facts confirmed before deciding anything** (`ssh pekangame-prod-lwf`, read-only `tinker`): **zero** real Reseller-API-placed orders exist in production today — all 6 `wallet_reseller_id`-set orders are Bot-channel (`wa:...` keys, reseller 1 ×3, reseller 2 ×3); **zero** duplicate `checkout_idempotency_key` values exist across all 30 orders that have one set. No backward-compatibility/migration conflict risk.
- **Three scoping strategies grilled, in order:**
  1. *App-level `WHERE` filter only* — rejected outright: the underlying column keeps its single global `UNIQUE` constraint, so a genuine two-reseller collision on `INSERT` still throws, gets caught as `DuplicateOrderException` (line 126), and the **race-recovery re-query at line 133 has the identical unscoped bug** — narrowing only the happy-path lookup does not close the leak.
  2. *Composite DB unique index* `(wallet_reseller_id, checkout_idempotency_key)` on the real column — rejected: MySQL treats every `NULL` as distinct inside a unique index, so this composite would silently **remove** the uniqueness guarantee for every `wallet_reseller_id IS NULL` row — i.e. every guest-storefront and Affiliate-whitelabel-storefront order (`checkout_idempotency_key`'s original purpose, [ADR-041](./ADR-041-checkout-level-idempotency-key.md)) — reopening the exact double-order-on-retry bug ADR-041 was built to close, for a much larger population than the one this fix targets.
  3. *Application-layer key namespacing* (prefix the stored value, e.g. `"r{reseller_id}:{key}"`) — rejected on hygiene grounds, raised directly by the founder: stringly-typed scoping mixes two semantically distinct values into one opaque column, breaks a future "look this order up by the exact key the reseller quoted in a support ticket" query, produces a third inconsistent key format alongside the storefront's raw UUID and the Bot's `wa:...` shape, and leaves the isolation invariant enforced only in application code, never declared in the schema.
- **Decision — a dedicated `STORED GENERATED` column.** `orders.idempotency_scope` (`INT NOT NULL AS (IFNULL(wallet_reseller_id, 0)) STORED`), with the real composite `UNIQUE (idempotency_scope, checkout_idempotency_key)` replacing the bare-column unique constraint. The DB derives the scope automatically from the already-populated `wallet_reseller_id` — no application code writes it, so it cannot drift or be forgotten on a future insert path. `checkout_idempotency_key` itself stays untouched/unmangled (confirmed via grep: the raw key is never echoed back in any Reseller API response shape, so no display/masking concern either). `wallet_reseller_id IS NULL` (every guest and Affiliate-whitelabel order) collapses to the same `idempotency_scope = 0`, byte-for-byte preserving ADR-041's original global-uniqueness guarantee for that population — this fix's blast radius is the Reseller channel only.
- **`ResellerOrderPlacementService::placeOrder()`'s two lookups (lines 63 and 133) both gain an explicit `->where('wallet_reseller_id', $reseller->id)`** — the generated column makes the DB constraint correct; the app-level `SELECT`s still need their own filter, since the composite index prevents a bad *insert*, not a cross-tenant *read*.
- **Bot-channel payload-hash (the related, separately-flagged gap) — investigated and dropped, not deferred.** `whatsapp_message_id` is 1:1 with one immutable message's content; OpenWA redelivering the same message id can only ever replay the identical original command, never a different order under the same key — the class of bug a payload hash exists to catch (same key, different content) is structurally impossible on this channel. A reseller also never sees or supplies this key (system-derived), so they cannot accidentally reuse it the way an API integrator can. Once `idempotency_scope` closes the cross-tenant path, no residual risk survives worth tracking.
- **Landing spot, confirmed during the grill:** this addendum, not a new ADR number — it tightens this ADR's own decision 4 idempotency-check implementation and closes a gap against [ADR-084](./ADR-084-reseller-api.md) decision 2's already-declared invariant, rather than opening new architecture. Cross-referenced from ADR-084 and ADR-041.

**Addendum — optional `max_price_sen` price ceiling on `POST /v1/orders`, grilled 2026-10-08 (§16 item 63, last API bullet).**

*Context.* The backlog line read "catalogue cached 60s, no ceiling". The trace corrected the premise: the charge is computed live at order time (`resolveByCode()` reads `Package` uncached; `placeOrder()` prices via `resolveResellerWallet()` and debits that), and both catalogue caches are flushed on every price write (`SyncSupplierPricesJob` → `forgetIndexCache()` → `ResellerCatalogService::CACHE_KEY` + `PRICED_CACHE_TAG`). The real gap is the time between a reseller *reading* a price (their own cached catalogue, or `.list` minutes earlier) and *ordering*. Other causes: a 30-minute price sync, `cheapestActiveFor()` switching the code to another package, a tier markup edit. Prod, 7 days to 2026-10-08: 11,683 cost changes over 1,438 packages, 5,406 up, 230 up by >2%, 12 by >10%, max +37%. Reseller API orders ever: **0** (2 keys); Bot: 7.

*Decisions.*
1. **Optional, additive, stays `/v1`** (ADR-084 decision 9). `null` = accept the live price (unchanged behaviour). Docs recommend sending it. A per-key "require max price" switch is not built.
2. **A ceiling, not an exact match** — a lower live price is charged as is (same semantics as Digiflazz's own `max_price`, cf. ADR-030 decision 4).
3. **`422 PRICE_CHANGED` + `details.current_price_sen`.** 422 to sit with `INSUFFICIENT_BALANCE`; 409 stays the idempotency conflict only. `current_price_sen` is the caller's own price, nothing private.
4. **Not in the idempotency payload hash.** It guards a charge; it isn't the order's identity. A rejected order leaves no row, so the same key may retry with a higher max; a replay of a placed order returns the original whatever its max. Stored hashes stay valid.
5. **Bot: no change now.** Its reply already shows `Harga`; an optional `max=` token is a §16 line. The DTO field is `null` for the Bot.
6. **No per-code log.** No API rejection is logged today; if observability is ever wanted it goes in the one `ResellerApiException` render hook for every code (§16 line).
7. **Lands here** (the order contract), cross-referenced from ADR-084's error list.

*Stress test (founder-requested).* Revised two answers: `details` is now documented as **code-specific** (`errors.md`) rather than putting a top-level field outside the uniform envelope — the PHP type was already `array<string, mixed>`, only the docs said validation-only; and decision 6 replaced a one-off `Log::info`. Held: the guard sits in `ResellerOrderPlacementService::placeOrder()` because only it knows the final price (a controller guard would recompute pricing); it compares the very `$pricing` object the debit uses (`sellingPriceSen` is `int`), so the guarded and charged amounts can't differ; it runs after the replay check; a new error code reachable only by opting in can't surprise an old client; no new query or lock.

*Code-trace (money).* For a wallet order `selling_price` = `final_amount` (`OrderDraft::resolvedFinalAmountSen()`, no voucher/fee) = the debit = `price_sen` in the order response = `price_sen` in the catalogue (same resolver). The guard writes no money column. Basis: ResellerWallet only. Callers of `ResellerOrderPlacementRequest`: API (passes it), Bot and `ResellerOrderPlacementTestPlaceOrder` (null).

*Consequence to track.* An integrator that auto-retries at `current_price_sen` has no ceiling at all; the docs say so. Revisit the Bot `max=` token if a Bot reseller complains about a price they didn't see.
