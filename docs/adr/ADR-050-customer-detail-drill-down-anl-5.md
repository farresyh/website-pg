# ADR-050: Customer Detail drill-down (ANL-5) — profit-panel scoping, kept consistent with the delivery-gated ledger rule

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-28 (grilled via `/mattpocock-skills:grilling`, one round, same session as ADR-049 — most prerequisites were already settled by that ADR)

**Context:** Founder supplied a reference screenshot from **keroxshop's own admin panel** (this project's own prior/legacy storefront — a reference to critique and adapt, not a source of fact about this project, same discipline `ADR-029`'s SEO reference and `legacy-reference-notes.md` already apply) showing a per-customer "Customer Details" page: identity header, 4 stat cards, a profit-reconciliation table, a monthly spend trend chart, top packages/top resellers for that one customer, and a full order history. Not originally itemized in `docs/prd.md` §6.12 — added here as **ANL-5**, post-launch of ADR-049's list screen.

The reference's profit table (`Total Revenue − Supplier Cost − Reseller Commission − Transaction Fees = Net System Profit`) is arithmetic that only reconciles if all five lines share one consistent order population. Every order in the reference happens to be `delivered`, so it never surfaces the real landmine: this codebase's `Total Spent` stat (ADR-049 decision 2, Paid-scoped) and its ledger-sourced profit (`ReportService`'s own rule — a paid-but-undelivered order contributes **$0** profit, forever, until it delivers) are already two deliberately different scopes on the same page. Copying the reference's table verbatim against a Paid-scoped order set would silently produce a Revenue/Cost/Commission/Fees breakdown that doesn't actually sum to the displayed Profit for any customer with an order still in flight.

**Decision:**

1. **New route `/admin/customer-analytics/[email]`** (URL-encoded `customer_email` as the identifier — consistent with ADR-049 decision 1's "customer is a derived `customer_email` grouping," not a new numeric id).
2. **The Profit Analysis panel (Total Revenue, Supplier Cost, Reseller Commission, Transaction Fees, Net System Profit) is scoped entirely to this customer's *delivered* orders only** — all five lines share one population, so the arithmetic actually reconciles. This is deliberately **narrower** than the stat cards' Paid-based `Total Spent`/`Total Orders` (unchanged from ADR-049) — two different, each internally-consistent scopes on the same page, not a contradiction, the same way `ReportService`'s RPT-2 (always-7-day trend) and RPT-3 (year/month-filtered) already stay independent concerns without confusing each other.
   - **Supplier Cost** = `SUM(cost_price)` over that delivered set — `cost_price` is a checkout-time snapshot (ORD-9), safe to sum directly, unlike profit.
   - **Reseller Commission** / **System Profit** = ledger-sourced (`ledger_entries.type=order_profit`, `owner_type=reseller`/`platform`), never `Order.reseller_profit`/`platform_profit` directly — the identical rule `ReportService`/`CustomerAnalyticsService` already apply, re-expressed here rather than invented fresh.
   - **Transaction Fees** = `SUM(transaction_fee)` over the same delivered set.
3. **Monthly Spending Trend (last 12 months) uses the Paid-scoped definition** (same population as `Total Spent`) — a spend timeline shows money that arrived, independent of the Profit panel's delivery-gating one section below it.
4. **Top Packages / Top Resellers: top 5 by spend, Paid-scoped**, mirroring `ADR-045` Dashboard's Top Games Weekly Ranking limit precedent — not an unbounded list.
5. **Order History table is Paid-scoped** (one row per order, so an admin can see a paid-but-undelivered order too, not just delivered ones) — but its **Reseller Profit / System Profit columns show `—` for any order outside the delivered/ledger-confirmed set**, never a fabricated `RM 0.00` that could be misread as "zero profit recognized" instead of "not yet known."
6. **The detail page always shows the customer's full lifetime data across every reseller**, regardless of whatever `reseller_id` filter is active on the list view — it is the one source-of-truth page for that customer, not a scoped sub-view. (Top Resellers, decision 4, already gives the per-reseller breakdown for anyone who needs that angle.)

**Rationale:** Decision 2 is the load-bearing call this ADR exists to record — it resolves the exact "looks like a one-line SUM, hides a landmine" pattern `ReportService`'s own doc comment already warned about, applied to a screen a reference screenshot made look simpler than it is. Decisions 3/4/5 each pick the scope that answers what the section is actually asking (a spend timeline vs. a profit reconciliation vs. a full audit trail), rather than forcing one scope to serve every section for superficial consistency. Decision 6 keeps this page a genuine drill-down (full picture of one customer) rather than accidentally becoming a second, redundant reseller-filtered view of the list screen.

**Addendum, 2026-09-18 — "Source" replaces "Affiliate," alongside ADR-049's own addendum above.** Same terminology note applies: decision 4's "Top Resellers" above predates ADR-072's rename and means today's "Top Affiliates" — this addendum is about the *new* wallet-`Reseller` entity ADR-072/073 introduced afterward, which `customerDetail()` had no awareness of.

- **The gap.** A wallet Reseller order's `affiliate_id` is always the primary brand (ADR-073 decision 5), so grouping this customer's order history by `affiliate_id` alone — as "Top Affiliates" and the Order History "Affiliate" column both did — silently merged a reseller's wholesale volume into the primary brand's own direct-sales bucket, and rendered "PekanGame" for a wallet order that a wallet Reseller placed, not a genuine primary-brand storefront sale.
- **Fix: "Top Affiliates" → "Top Sources," "Affiliate" column → "Source."** Both now group/label by a composite rule — `Reseller: {business_name}` when `wallet_reseller_id` is set, the affiliate's `business_name` otherwise — the exact "Reseller: {name}" wording `Admin\OrderController`'s own Source column already established (ADR-074's "Orders visibility follow-up"), so the same term means the same thing everywhere in the admin. `topSpendBreakdown()`'s grouping key was generalized from a bare column name to an optional callable (plus a companion id-resolver) to support this composite key — `top_packages` above is unaffected, still grouped by the plain `package_id` column.
- Decisions 2/3/5/6 above (Profit Analysis scope, Monthly Trend, delivery-gated `—` columns, always-lifetime-across-every-affiliate) are all unchanged — this addendum only touches the *label*, not the underlying money/scope rules.
