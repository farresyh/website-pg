# ADR-093: Reseller Bot `.order` fat-finger safety net — auto player-ID/region validation before placing, player ID echoed in the confirmation reply, no mandatory 2-step confirm

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted & built — grilled 2026-09-12, built 2026-09-13 on `feature/adr-093-bot-order-safety-net`. `ResellerBotService::handleOrder()` gained a new `validatePlayerForOrder()` step (decision 2 — invalid ID or wrong-region both reject before any debit, `ProviderUnavailableException`/`UnsupportedPlayerValidatorException` both fail-open per decision 2's stated intent), reusing the same `reseller-bot-checkid` rate-limit bucket (decision 3) and `PlayerValidation` audit trail `handleCheckId()` already writes. `ResellerBotReplyFormatter::orderPlaced()` now echoes the player ID + server ID for every order (decision 4). Zero touch to `ResellerOrderPlacementService`/ledger/locking.

**Context:**

The 2026-09-10 reseller-family audit's item 5: `.order {productCode} {playerId} [{serverId}]` places a real wallet order (debit + supplier submission) synchronously off one WhatsApp message, no confirmation step. A non-existent product code is already safe — `ResellerCatalogService::resolveByCode()` rejects it before any debit. The genuine risk is narrower than "any typo": a **player ID that's wrong but happens to be a real, different account**, or a **product code typo that resolves to a different real package** — both let the order succeed and *deliver*, landing on `delivery_status=Delivered`, which is **never** refund-eligible (`Admin\OrderController::refundToWallet()` gates on `Failed` only, ADR-073 decision 7). This is the one truly unrecoverable case in the whole family, distinct from a normal `Failed` delivery that ADR-092 already covers.

Founder set the direction up front: the Bot channel exists specifically for B2B speed, so a mandatory 2-step confirm on *every* order (extra round-trip even for the ~100% that are correct) was rejected in favour of a layered safety net that only slows down the cases actually at risk.

**Facts checked against real code before grilling further:**
- `.checkid {gameCode} {playerId} [{serverId}]` already exists as a **separate, optional** command — a reseller must remember to run it before `.order`; nothing requires it. It validates player-ID existence and (since the ADR-076 PR #107 region-mismatch fix) whether the ID's own country maps to a *different* game's `reseller_code` than the one being used.
- **Correction to ADR-076 decision 8's stated rationale**, found by reading the three validator implementations (`MoogoldValidator`/`AcidGameShopValidator`/`NexoneValidator`) directly rather than trusting the docblock: none carries an API key, token, or any billing mechanism, and all three self-describe as **"unofficial"** — MooGold's is an unauthenticated replay of its own storefront's public WooCommerce AJAX id-check widget, AcidGameShop's a stateless public JSON endpoint, Nexone's a scraped public form-token flow. ADR-076 decision 8 framed `.checkid`'s separate 10/min limit as **cost control** against "real provider cost" — founder confirmed in this grill there is no known separate paid arrangement, so that framing was mistaken. The real risk these three integrations carry is **getting PekanGame's server IP rate-limited or blocked by the source site** for scrape-like traffic, or the source markup changing underneath the hardcoded field names (already called out in `MoogoldValidator`'s own docblock) — not a per-call bill. (Per this doc's own "do not edit past entries" rule, ADR-076's text is left as-written; this entry is the correction of record.)
- `ResellerBotReplyFormatter::orderPlaced()` — the message sent immediately at placement — echoes order number, product name, and price, but **not the player ID the reseller just typed**, despite that being the exact value most at risk of a fat-finger.
- Neither the Bot nor the Reseller API give a reseller any self-serve retry/cancel/refund path (`.order`/`.trackorder`/`.baki`/`.topupbaki`/`.listharga` only) — only an admin can act, via the panel ADR-092 now surfaces proactively.

**Decision:**

1. **No mandatory 2-step confirmation for `.order`.** Rejected per the founder's speed-first direction above — every order, including the overwhelming majority placed correctly, would otherwise pay a second round-trip.
2. **`.order`'s existing `handleOrder()` auto-runs the same `PlayerValidatorRegistry` validation `.checkid` already uses**, for any game with `player_validator_enabled` + a configured profile — before `placeOrder()` is called, so a caught problem never reaches the debit:
   - Validator returns **invalid** → reject, no order placed, no debit. Same reply shape `.checkid` already gives.
   - Validator returns **wrong region** (a real ID, but for a different game's `reseller_code`) → **also reject**, telling the reseller the correct code to use — closing the gap before a debit happens is strictly better than letting it proceed and likely fail at the supplier anyway (which would just mean an avoidable `Failed`→admin-refund round trip).
   - Validator throws **`ProviderUnavailableException`** (the scraped source is down/timing out) → **fail-open, proceed with the order** — an outage in an unofficial third-party integration must never block a legitimate paid order; this degrades to exactly today's no-validator behaviour, not worse.
   - A game with **no validator profile configured** → unchanged, no check possible, proceeds exactly as today.
   - This mirrors `handleCheckId()`'s own wrong-region resolution logic (`PlayerRegionMapping` lookup) rather than re-deriving it — reuse, not a parallel implementation.
3. **Auto-validation calls inside `.order` consume the same `reseller-bot-checkid` rate-limit bucket (10/min per reseller) `.checkid` itself already uses** — re-framed, per the corrected Context above, as anti-scrape-abuse-pattern protection for the unofficial source sites rather than cost control, but the existing number and mechanism carry over unchanged. Exhausting it inside `.order` behaves exactly like exhausting it via `.checkid` directly — the standard "terlalu banyak permintaan" rejection, no order placed, not a silent skip of the safety check.
4. **`ResellerBotReplyFormatter::orderPlaced()` gains the player ID (and server ID, when present) in its reply body** — for every order, not just validator-covered games, since a non-validator game has no other safety net at all. Lowest-cost, highest-value change in this ADR: the reseller re-reads their own just-typed ID a few seconds later, the single strongest human-error catch available, for zero added latency or cost.
5. **No self-serve `.cancel` command and no artificial delivery delay.** A reseller who spots a mistake via decision 4's echo (or the already-shown product name) escalates to admin over the same WhatsApp group — consistent with ADR-092/ADR-073's "admin makes the final call" posture rather than introducing a second, bot-side resolution path with its own edge cases. Adding a real cancel window would require deliberately delaying `FulfillOrderJob` dispatch for every Bot-placed order (today's dispatch-after-commit is near-immediate) — rejected as slowing down 100% of orders to give a self-serve out this ADR doesn't otherwise need, now that ADR-092 gives admin fast visibility instead.
6. **A wrong-but-real *product code* typo (right player, wrong package) is not separately mitigated here.** The existing `orderPlaced()` reply already names the package ordered; decision 4 doesn't add new coverage for this case beyond what's already visible today. Left as a known residual risk (Consequence, below) rather than inventing a second confirmation mechanism for a narrower case decision 1 already ruled speed-first on.

**Rationale:**

- Reusing `PlayerValidatorRegistry` and the existing wrong-region resolution rather than writing new validation logic keeps this ADR's actual new surface small: one call site added inside `handleOrder()`, zero new services.
- Blocking on wrong-region (decision 2) rather than letting it proceed to a likely supplier-side failure is the more solid choice, not just the safer-sounding one — it avoids manufacturing an avoidable `Failed`→refund cycle for a mistake the platform can already detect for free before any money moves.
- Correcting the cost framing (Context) before deciding decision 3, rather than carrying ADR-076's "paid provider" assumption forward unverified, is exactly this project's own "orient first, verify against real code" discipline (`AGENTS.md`) — the number chosen (10/min) turned out still to be the right call under the corrected reasoning, so nothing needed to change except *why*.

**Consequence to track:**

- Decision 6's residual risk (wrong product code, right player) stays open. If it ever proves to be a real recurring problem in practice (not just theoretical), the next lever to pull is a stricter product-code confirmation specifically — e.g. echoing the resolved package name *before* committing, not just after — rather than reopening decision 1's no-mandatory-confirm call wholesale.
- If MooGold/AcidGameShop/Nexone's unofficial endpoints ever get IP-blocked or change shape, `.checkid` and this ADR's auto-validation both degrade the same way (fail-open, decision 2) — a full outage of all three validator fallbacks means every order silently loses this safety net, worth a monitoring line item if it ever recurs, not a build-time gap today.
- This ADR and ADR-092 share one governing principle worth keeping visible together: automation stays narrow (typo-catching, visibility), and the actual money judgment call — refund vs. retry, place vs. reject — stays with a human, either the reseller (via the echo) or the admin (via the KPI cards). Neither ADR should be extended into a self-serve automated-refund/automated-cancel feature without a fresh, explicit grill.
