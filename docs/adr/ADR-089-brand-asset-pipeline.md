# ADR-089: Brand asset pipeline — aspect-preserving logo sizing, a primary-brand admin Logo/Favicon panel, per-brand dynamic favicon

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled + built 2026-09-11.

**Context:**

The founder flagged three connected gaps while looking at a real affiliate storefront (`fixfastapp.com`) live in production:

1. **Logo sizing.** `storefront/src/components/ui/Logo.tsx` forced any uploaded logo into a fixed square (34px header / 32px footer, `width:size,height:size,objectFit:contain`) regardless of its real aspect ratio. FixFast's logo — a wide icon+wordmark combo, the common real-world shape — was squeezed into that square and became illegible. `Affiliate\Storefront\BrandingController::LOGO_MAX_EDGE = 512` only clamped the longest edge on ingest; nothing constrained or guided what would actually render legibly at the header's tiny display size.
2. **No primary-brand logo/favicon UI.** `AffiliateBranding` (`logo_path`, `theme_preset`) is a real row keyed to the primary/`is_owned` `Affiliate` (ADR-081 decision 3 already established primary can use the same column), but `admin/src/app/admin/settings/page.tsx`'s "Store Branding" tab (`StoreBrandingSection.tsx`) had no logo field at all — only the affiliate portal's `BrandingTab.tsx` could upload one. The founder had no way to set PekanGame's own real logo through the UI.
3. **No favicon mechanism, at all.** Confirmed by grep: no `favicon.ico`, no `app/icon.tsx`/`app/favicon.ico` route — `proxy.ts`'s matcher only *excludes* `favicon.ico` from its own routing, it doesn't generate one. The founder asked whether an uploaded logo becomes the tab favicon automatically or needs manual code — the honest answer was neither: this was an unbuilt gap, not a wiring bug.

Grilled over two rounds before any code: whether "darkmode" (raised in the same conversation) meant a per-viewer toggle or a per-affiliate fixed choice (settled as the latter — folded into [ADR-090](./ADR-090-theme-preset-background-ink-tokens-a-per.md) instead, a separate token-architecture concern from this ADR's asset-pipeline one); whether the header logo slot should become rectangular (founder: not required, just make it visibly bigger — a single logo asset, no separate wordmark asset); whether primary needed its own theme-preset picker alongside the logo field (founder: no — primary stays on `default` colours permanently, this ADR is logo/favicon only); and whether a favicon should be auto-cropped from the header logo or uploaded as its own square asset (favicons need to stay legible at 16-32px, and a wide wordmark crops badly to a square — a separate asset was the clear answer).

**Decision:**

1. **`Logo.tsx` takes a `maxHeight`/`maxWidth` bounding box, not a single `size` forcing a square.** Header: 48px tall / 180px wide max. Footer: 36px tall / 140px max. `object-fit: contain`, aspect ratio always preserved. The ADR-063 placeholder mark (the bolt-in-square SVG) stays a fixed square — it's deliberately drawn as one, not an uploaded asset with its own ratio.
2. **The primary brand gets a Logo + Favicon panel in `admin/src/app/admin/settings`'s existing "Store Branding" tab** (`StoreBrandingSection.tsx`), not a new screen — reusing the exact upload/delete pipeline the affiliate portal already has (`ImageIngestService`, WebP re-encode, `AffiliateBranding.logo_path`/`favicon_path`), gated by admin auth (`Admin\SettingsController::uploadLogo`/`destroyLogo`/`uploadFavicon`/`destroyFavicon`) instead of the affiliate guard. No theme-preset picker added here — out of scope per the grill.
3. **A favicon is a separate, square asset from the header logo** — never derived by auto-cropping it. `favicon_path`/`favicon_url` are new columns/accessors on `AffiliateBranding`, validated by a dedicated `UploadFaviconRequest` (`dimensions:min_width=512,min_height=512,ratio=1/1` — Laravel's built-in `ratio` rule enforces square at the boundary, not a manual check). Both the affiliate portal (`BrandingTab.tsx`) and the admin panel show the same new hint copy: *"Recommended: 512×512px square, PNG, transparent background — this becomes your browser tab icon."* — the first size-recommendation hint pattern in either app; no such precedent existed to follow.
4. **The favicon is served per-brand via `storefront/src/app/icon.tsx`** (Next.js's `icon` file-convention route, not a static `favicon.ico`), reading `branding.faviconUrl` through the same host-resolved `getBranding()` seam every other branding surface uses (ADR-060) — so it varies by `Host` exactly like the logo and theme preset already do. A real uploaded favicon is proxied through as-is (already square WebP, so no server-side crop is needed against a well-formed upload); no upload falls back to an `ImageResponse`-rendered version of the same bolt-in-square placeholder mark, so a brand with no favicon set still gets a coherent — if generic — tab icon rather than the browser's blank default. `getBranding()` reads `next/headers()` internally (a Request-time API), so this route is dynamic per request rather than statically optimized at build time, which is required since the resolved brand varies by host.

**Rationale:**

- Sizing the header slot as a bounding box rather than a forced square is the minimal fix that actually matches how real-world logos look (wordmark, icon+text combo) — confirmed against the founder's own competitor screenshots, which all use a wide, non-square header slot.
- Reusing the affiliate portal's exact upload pipeline for the primary brand (rather than inventing a second one) keeps `ImageIngestService` the single seam every branding image goes through, and means the admin-side code is almost entirely wiring, not new logic.
- A favicon as its own asset — not an auto-crop of the logo — avoids the one failure mode that would have made this feature actively worse than doing nothing: a wide wordmark logo squished into an illegible square browser-tab icon. The `ratio=1/1` + `min_width=512` validation catches a bad upload at the API boundary rather than silently shipping a broken favicon.
- Building the favicon route on the same `getBranding()`/`Host`-resolution seam as everything else (rather than a parallel mechanism) means every future whitelabel brand gets a working favicon automatically, with no per-brand wiring.

**Consequence to track:**

- The favicon endpoint fetches the upstream image on every uncached request (no favicon-specific cache layer beyond whatever HTTP caching the browser/CDN already applies to `/icon`) — acceptable at current traffic; revisit if favicon requests ever show up as meaningful load.
- `apple-icon`/multi-size favicon variants (the full "six files" favicon handbook approach) are not built — a single 512×512 source via `icon.tsx` covers modern browser tabs, which was the actual ask. Add `apple-icon.tsx` as its own small follow-up if home-screen "Add to Home Screen" icons matter later.
- The primary brand's logo/favicon panel intentionally has no theme-preset picker — if that decision is ever revisited, ADR-081 decision 3 already confirmed the backend has no obstacle to it.
