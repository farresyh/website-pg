# ADR-076: Reseller Bot v2 — two-stage order-completion messaging, `.trackorder`/`.checkid`/`.info`, reply styling

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-05, grilled `/mattpocock-skills:grilling` across two rounds (all frontier resolved, founder confirmed shared understanding before write-up). Depends on ADR-075 (PR-F, shipped) — this is a follow-up to that channel, not a new one.

**Context:**
- Live-tested with a real OpenWA session 2026-09-05 (see ADR-075's own "OpenWA provisioned + live-verified" addendum) — the bot works, but two real gaps surfaced: (1) `.list {kod}`'s package order is not sorted by denomination, and (2) reply styling is cramped/unaligned versus the founder's reference bots (`tomystarkdiamond` et al.), which use a monospace-aligned, decorated (headers, separators) format.
- Root cause of (1): `Package::cheapestActivePerGame()` (the method `ResellerCatalogService::listAvailable()` calls) has no `orderBy` at all — Collection `groupBy('denomination')` preserves first-appearance order, not numeric order. The storefront's `CatalogController::dedupByDenomination()` (and, per its own comment, the admin's `GameController::packages()`) already sort ascending by denomination, nulls last by name — this method is the one place that never got that convention.
- The Bot currently sends exactly **one** message per `.order`, at placement time, worded as if the order already succeeded ("Order berjaya!"). This is factually premature: `ResellerOrderPlacementService::placeOrder()` creates the `Order` and debits the wallet synchronously, then dispatches `FulfillOrderJob` **after** commit — delivery is queued, not yet known, at the moment that reply is sent (`backend/AGENTS.md`'s "fulfillment is queued, never inline" rule, ADR-014). The reference bots send two messages per order: an immediate "received, processing" ack, then a second "success/failed" update once resolved — confirmed as the desired shape.
- `OrderObserver::updated()` broadcasts `OrderStatusUpdated` (`DB::afterCommit()`) on **every** `payment_status`/`delivery_status` change, not gated to a terminal state — a single `OrderFulfillmentService::fulfill()` call can write `delivery_status` 2-3 times (e.g. `NotStarted→Processing→Delivered`), each a separate fire. `OrderResendService::resend()` (admin's "Resend Delivery") delegates to the same `fulfill()`, so a later resend fires the event again on the same order. `Admin\OrderController::refundToWallet()` (the wallet-channel replacement for ADR-004's Voucher path — a `LedgerService::credit()` back into the reseller's balance, no cash leaves the platform) deliberately does **not** touch `payment_status`/`delivery_status`, so it never fires this event at all.
- `orders` has no free-form metadata/json column to carry a WhatsApp group id (`supplier_response` is a typed, semantically-committed json column, not a general bucket) — a new place to store it is required. `reseller_whatsapp_groups.reseller_id` is **not** unique (one `Reseller` may link several groups; only `whatsapp_group_id` is unique) — so "the reseller's group" is ambiguous, and the exact group that placed a given order must be captured at placement time, not re-derived later.
- `TrackOrderController::customerSafePayload()` is the existing canonical customer-safe `Order` shape (masks contact via `ContactMask`, excludes `cost_price`/`standard_selling_price`/`platform_profit`/`affiliate_profit`/`payment_ref`) — the money-safety rule this codebase already enforces once, meant to be reused, not re-derived per caller.
- `PlayerValidatorRegistry::resolve(string $key)` resolves a validator by a game's own configured `player_validator_profile` key (`AVAILABLE_KEYS` currently binds only `'mlbb'`) — generic by construction, not tied to any one game in the mechanism itself, gated purely by whether a game has a profile configured (`games.player_validator_enabled`/`player_validator_profile_id`, same fields the storefront checkout wizard already reads).

**Decision:**

1. **`Package::cheapestActivePerGame()` gains the same ascending-by-denomination, nulls-last-by-name sort `CatalogController::dedupByDenomination()` already applies** — mirrored/extracted, not reinvented, so the storefront, admin, and both reseller channels (API + Bot) stay ordering-consistent automatically, including for any future consumer of this method.
2. **Every Bot reply is wrapped in a WhatsApp monospace code block** (triple-backtick) so key:value column alignment renders reliably regardless of device font. Package-list lines drop the per-item emoji from the first styling draft (name/price/code only) — section headers keep their emoji/decoration. Exact copy for every reply (list/order/track/checkid/info/errors) is pinned to the founder-confirmed previews recorded in this session, not restated verbatim here.
3. **Two-stage order messaging.** Message 1, sent synchronously at successful placement (mirrors today's timing, new copy: "Pesanan Diterima" — order number, product, charged price, "sedang diproses"). Message 2, sent only once `delivery_status` resolves to `Delivered` or `Failed` — never for `Processing`/`Pending`/`NeedsReview`, which stay silent on this channel (admin is already alerted internally for `NeedsReview`; a reseller can `.trackorder` to check manually in the meantime).
4. **New table `reseller_bot_order_notifications`** (`order_id` FK unique, `whatsapp_group_id`, `last_notified_delivery_status` nullable, `refund_notified_at` nullable) — created by `ResellerBotService::handleOrder()` immediately after a successful `placeOrder()` call, capturing the exact originating group (decision, addressing the Context's group-ambiguity problem) rather than trying to re-resolve it later from `reseller_id` alone. Deliberately a **separate small table**, not new columns on `orders` — matches this family's existing convention (`reseller_bot_command_logs` is likewise separate) of keeping Bot-channel concerns off the shared, money-critical `Order` model.
5. **A new queued listener on `OrderStatusUpdated`** sends message 2: fires only when a `reseller_bot_order_notifications` row exists for the order (i.e., it was placed through this channel specifically — API/Portal-placed wallet orders have no WhatsApp group and are correctly untouched) **and** the new `delivery_status` is `Delivered` or `Failed` **and** differs from the row's stored `last_notified_delivery_status`, then updates that column. This is a state-*diff* guard, not a fire-once-ever guard — deliberately so that a later `OrderResendService` success (`Failed→Delivered`) still sends a fresh "now succeeded" message, while the same terminal state re-firing (defensive) or an intermediate transition never double-sends or spams.
6. **`Admin\OrderController::refundToWallet()` gains an explicit, non-event-driven call into the same notification-sending seam**, right after its `LedgerService::credit()` succeeds — since this action deliberately never touches `payment_status`/`delivery_status` and so is invisible to decision 5's listener. Guarded by the new row's `refund_notified_at` column so a repeat action (or a UI double-click) can't double-send. Sends the "Refund Wallet" copy to the order's stored `whatsapp_group_id`.
7. **New command `.trackorder {order_number}`** — calls `TrackOrderController::customerSafePayload()` verbatim for its masking rule (zero new money-safety logic), then re-formats it as WhatsApp text. **Scoped to the requesting `Reseller`'s own orders** (`wallet_reseller_id` match) — unlike the public, anonymous, order-number-as-proof endpoint this reuses the payload shape from. A wrong order number and a real order belonging to a different `Reseller` return the **identical** generic "not found" reply, deliberately not distinguished, so a reseller can never use this command to confirm another reseller's order number exists.
8. **New command `.checkid {kod} {playerId} [{serverId}]`** — generic across every `reseller_code`-mapped game with a validator profile configured (today only MLBB is bound; a future game needs no new command, only a profile), resolving the game the same way `.list`/`.order` already do and calling `PlayerValidatorRegistry` exactly as the storefront checkout wizard does. Replies with a plain "game ini tidak menyokong semakan ID" when no profile exists for the resolved game — never a crash or an unrecognized-command reply. **Rate-limited separately from the shared 60/min command limit — 10/min per `reseller_id`** — because unlike every other read-only command here, this one can call a paid external provider (Moogold/AcidGameShop/Nexone) per invocation, and group chat "let's test it" behavior would otherwise translate directly into real provider cost.
9. **New command `.info`** — a static reply listing every current command with one-line usage. `handleUnrecognized()` is refactored to call the same formatter rather than maintaining a second, divergent copy of the command list (today's actual bug risk — the two already drifted once this session's draft was written).

**Rationale:** Every new piece of money/identity logic here is reuse, not invention — `TrackOrderController`'s existing masking, `PlayerValidatorRegistry`'s existing per-game resolution, `CatalogController`'s existing sort convention, `OrderStatusUpdated`'s existing broadcast — matching this codebase's "deep module, stable seam" discipline (`AGENTS.md`) the same way ADR-075's original design did. The one genuinely new mechanism is decision 4/5's state-diff notification table, sized to solve the Context's two real problems at once (which group to reply into; how to avoid `OrderObserver`'s multi-fire-per-order behavior turning into notification spam) without a heavier general-purpose event-sourcing mechanism this codebase doesn't otherwise use.

**Consequence to track:**
- Decision 4's table is populated only for Bot-channel orders — correct today (no other channel has a WhatsApp group to notify), but the listener should carry a one-line comment noting this so a future reseller channel doesn't silently assume 2-stage notification comes for free.
- Decision 8's separate 10/min `RateLimiter` key must be verified as a genuinely independent counter from the existing per-reseller 60/min command limit, not accidentally sharing/clobbering one key namespace — the same category of mistake ADR-073/075's own per-reseller limiter keys already had to watch for.
- Decision 6 is the one place in this design that isn't event-driven — if a future change ever makes `refundToWallet()` also touch `delivery_status`, both the explicit call and decision 5's listener could fire for the same refund; flag for whoever next touches that controller.
- The previously-planned `.topupbaki {amount}` Bot command (self-serve wallet top-up over WhatsApp, founder's own idea, not yet built) is unaffected by and compatible with this design — it would reuse `ResellerWalletTopupService` as-is and needs no changes here.
- `docs/prd.md` §14/§15 gain this PR once shipped, same convention every other PR in this family has used.

**Build addendum — PR-H (`.topupbaki`) planning, grilled 2026-09-05.** Self-serve wallet top-up over the Bot channel, the founder's own idea (first raised in ADR-072..075's own build log) — deliberately not folded into ADR-076's own PR to avoid scope-creep mid-build, but grilled together with it since it reuses this ADR's exact 2-stage-notification shape and the founder correctly flagged it belongs with the rest of this Bot-channel work, not a standalone follow-up. Grilled 1 round, all resolved.

**Context (confirmed by direct code read, not assumed):**
- `ResellerWalletTopupService::initiate(Reseller $reseller, int $amountSen, string $channelCode, array $channelProperties): WalletTopupAttempt` is the one entry point (already built for PR-G's portal top-up) — returns an attempt carrying a `checkout_url` once the CHIP call succeeds. `MIN_AMOUNT_SEN = 1000` (RM10), no maximum (ADR-072/073's own decision).
- **Same group-ambiguity gap ADR-076 decision 4 fixed for orders exists here too, unfixed**: `wallet_topup_attempts` has no `whatsapp_group_id`/channel-tracking column at all.
- **Worse than `refundToWallet()`'s gap**: `ChipWebhookController`'s topup-complete branch (`ResellerWalletService::completeTopup()`) dispatches *no* event whatsoever — not even an `OrderStatusUpdated`-equivalent exists for wallet top-ups to hook.
- `initiate()` already throws `PendingWalletTopupAlreadyExistsException` (message carries the existing attempt's id) when one `pending`+unexpired attempt exists per reseller — the one-at-a-time guard ADR-072/073 already decided.

**Decision:**

1. **New table `reseller_bot_wallet_topups`** (`reseller_id` FK, `whatsapp_topup_attempt_id` FK unique, `whatsapp_group_id`, `notified_at` nullable) — mirrors `reseller_bot_order_notifications`' shape exactly (a separate table, not new columns on `wallet_topup_attempts`, same reasoning: keep Bot-channel concerns off a shared, money-adjacent model). Created by the new `.topupbaki` command handler right after a successful `initiate()` call.
2. **`ChipWebhookController`'s topup-complete branch gains an explicit, non-event-driven notify call** — identical posture to `refundToWallet()` (ADR-076 decision 6): since nothing fires an event here at all (worse than the order case, which at least had `OrderStatusUpdated` to hook), the only option is calling the notify seam directly from inside `ResellerWalletService::completeTopup()` (or its caller), guarded by `reseller_bot_wallet_topups.notified_at` against a double-send on a webhook redelivery.
3. **A pre-existing pending attempt is not an error to the reseller — the bot replies with that attempt's own `checkout_url`** rather than a plain rejection. `PendingWalletTopupAlreadyExistsException` already carries the existing attempt's id; the handler resolves it and re-sends the link, so a reseller who lost the first message (or forgot they had one pending) can always self-serve without asking admin.
4. **Separate rate limit, stricter than `.checkid`'s 10/min: 5/min per `reseller_id`** (`RateLimiter::attempt("reseller-bot-topupbaki:{$reseller->id}", 5, fn () => true, 60)`, same call shape ADR-076 decision 8 established) — `.topupbaki` creates a real CHIP payment-link/reference row per successful call (not just a paid-API read like `.checkid`), the most financially-sensitive command in the Bot channel's command set.
5. **Command shape**: `.topupbaki {amount}` (RM, e.g. `.topupbaki 50`) — parses to sen, validated against `ResellerWalletTopupService::MIN_AMOUNT_SEN` before calling `initiate()` (a below-minimum amount replies with the exact minimum, no wasted CHIP call). Reply on success: the checkout link + "Klik untuk bayar, link sah selama 30 minit." Reply on webhook-confirmed success (decision 2): "Top-up berjaya! Baki wallet anda sekarang RM{balance}."

**Rationale:** Every decision here is a direct application of a pattern ADR-076 already settled for orders (separate small tracking table, explicit non-event-driven notify where no event exists, a command-specific stricter rate limit) — no new mechanism invented, matching this codebase's established "reuse the seam" discipline. Decision 3 is the one place this command's design improves on a naive port of the order pattern: an order has no equivalent "someone already tried, here's their old link" self-service case, but a top-up genuinely does, and it's nearly free to support.

**Consequence to track:**
- `reseller_bot_wallet_topups` and `reseller_bot_order_notifications` are structurally near-identical (FK + group + notified-state) — if a third Bot-channel money action ever needs the same shape, that's the trigger to extract a shared base, not before.
- Pure build from here — no further grilling needed, sequenced after `/set-password` and ADR-076's own live-verification per the founder's stated next-session order.

**Build addendum — PR-F planning, grilled 2026-09-05 (`/mattpocock-skills:grilling`, one round, all frontier settled).** ADR-075's own text deliberately left several items as "build-time detail, not decided further here" (decision 5's command set, decision 6's resize timing was tied to a single engine assumption) — this addendum pins those before any code is written, and records one reversal.

1. **Engine reversed: launch on `baileys`, not `whatsapp-web.js`** — modifies decision 6. Founder's own call: start on baileys's lower RAM footprint (~30-80MB/session) and warm the number up gradually, watching for ban signals, before ever moving to the heavier/safer `whatsapp-web.js`. Confirmed via OpenWA's own docs this session: engine is a deployment-level `ENGINE_TYPE` env var, not a per-session parameter — the REST API surface and every webhook/command-parser call this codebase makes is identical either way, so the swap costs zero backend code changes when it happens. One caveat OpenWA's docs don't cover: the two engines' session auth state is very unlikely to be portable (baileys' multi-device WebSocket creds vs. whatsapp-web.js's Chromium profile), so a future switch should be planned as a new QR scan / brief re-onboarding, never assumed to be a hot, zero-downtime swap. **Switch trigger is a founder manual review (~4 weeks in), not an automated metric** — WhatsApp gives no advance ban-risk signal a backend could poll, so a computed threshold would be false precision. **Decision 6's droplet resize is deferred, not dropped**: baileys' footprint fits inside the production droplet's existing ~1.4GiB headroom without any resize at all; the 4→8GiB resize (and its cost) only actually triggers if/when the founder later switches to `whatsapp-web.js`, tied to that switch specifically — not scheduled ahead of it.
2. **Command/chat logging is narrow (failed/unrecognized only), not a full conversation archive.** A successful bot order is already visible on `/admin/orders` (the Source column shipped in PR-E's own follow-up) — logging it again here would be pure duplication. New `reseller_bot_command_logs` (raw command text, `whatsapp_group_id`, parse/placement failure reason, timestamp) written only on an unrecognized command or a `ResellerOrderPlacementService`/`ResellerCatalogService` exception — mirrors `ClientErrorController`'s narrow single-log-sink pattern, not `supplier_request_logs`'s dedicated CRUD screen. **Retention: 7 days**, matching `player_validations`' own window rather than `supplier_request_logs`' 30 — a command payload can carry a player/server ID, the same PII class.
3. **Group-linking UX, filling in ADR-075 decision 2's mechanism:** admin adds the bot + the reseller into a shared WhatsApp group and sends any message; the webhook receiver, on a `message.received` event from a group not yet in `reseller_whatsapp_groups`, writes a short-lived pending row (`group_id`, first-seen timestamp) instead of silently dropping it. **Group messages only** — a direct message to the bot number outside any group is never captured into the pending list (no product reason to, and it would let a stranger flood the list by messaging the number directly; ADR-075 decision 3's group-membership trust boundary already excludes individual senders). **24-hour TTL** on an unmatched pending row — long enough for the admin to link it before the next test message would need to repeat, short enough the list doesn't accumulate stale noise. Admin links/unlinks from a new modal on `/admin/resellers` (mirrors `ResellerApiKeysModal.tsx`'s/`ResellerWalletModal.tsx`'s existing per-row-action shape) — `reseller_whatsapp_groups.is_active` toggle for unlink (reseller departs, dispute), reusing the same activate/deactivate convention already on `Reseller`/`ResellerTier`.
4. **v1 command set, pinned** (`.` prefix, matching the reference-bot market convention ADR-075's own Context already cites): `.listharga` — directory of every reseller-coded game (`Game.name` + `reseller_code`), with a "guna `.list {kod}` untuk harga, contoh: `.list MLMY`" usage hint in the reply so a first-time user is walked to the next command, not left to guess. `.list {reseller_code}` — that game's packages: price at the caller's own tier + each package's `{reseller_code}-{denomination-or-catalog_code}` order code (`ResellerCatalogService::listAvailable()`, PR-E's own bulk-listing method, reused as-is — built anticipating exactly this). `.order {code} {playerId} [{serverId}]` — space-separated, `serverId` omitted entirely for a game with none; the parser reads whether a game needs one from `games.validation_rules` (the same field the storefront checkout wizard already reads), never a per-game hardcoded rule. `.baki` — wallet balance + status (mirrors the Reseller API's `GET /balance`). **This is a UX-layer decision only, unrelated to Digiflazz's own internal `customer_no` wire format** (`DigiflazzAdapter::normalizeCustomerNo()`, ADR-030 decision 5) — `player_id`/`server_id` reach the order-placement contract as two already-separate fields (same shape `PlaceOrderRequest` already validates for the Reseller API), and Digiflazz's own real separator stays exactly as unverified/tracked as it already was before this ADR (gated on funding the supplier account, not a PR-F concern).
5. **OpenWA/session-down posture: an active health signal, not a silent failure.** Reversed from the "same as a stuck queue worker" default this codebase otherwise uses, because this channel is a reseller's live paid ordering path (ADR-075's own rationale: "a ban is an outage of their business, not a cosmetic degradation" — the same logic extends to any session outage, not only a ban specifically). Reuses the existing `/admin` System Health chip pattern (DASH-2's low-balance amber chip precedent) rather than inventing a new mechanism — the webhook receiver records the last-known `session.status` event, surfaced as an amber/red chip alongside the existing supplier circuit-breaker states.

**Bugfix addendum — `.list` reply chunking, 2026-09-14 (`fix/reseller-bot-list-length-chunking` → `staging`).** Founder reported `.list MLID` returning nothing while every other game worked. Root cause: OpenWA's `send-text` endpoint hard-rejects any message over 4,096 chars with a `400` (`MESSAGE_TEXT_MAX_LENGTH`, confirmed by reading OpenWA's own source on the droplet — `src/modules/message/dto/send-message.dto.ts`, not documented anywhere on our side), silently, with `SendResellerBotReplyJob` exhausting all 3 retries and logging "reply lost." `ResellerBotReplyFormatter::listPackages()` built one unbounded message — `.list MLID` (79 active denominations, the biggest single-game catalogue) came to 7,605 chars.
