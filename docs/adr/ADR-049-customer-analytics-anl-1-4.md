# ADR-049: Customer Analytics (ANL-1..4) — identity as a derived grouping, segmentation rules, and date-range scope

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-28 (grilled via `/mattpocock-skills:grilling`, three rounds, before any code touched)

**Context:** `docs/prd.md` §6.12 (ANL-1..4) has sat unbuilt since the project's foundation — §15's own tracker entry notes it was "not blocked on supplier, needs real orders to be meaningful," and real Paid orders now exist (Reports/Dashboard both already read them live). Same category of landmine Reports/Dashboard found before it: "customer," "total spent," and each segment name look like a one-line GROUP BY/COUNT but hide real decisions that need pinning first, compounded here by one thing neither Reports nor Dashboard had to face — this platform has **no persistent customer identity at all** (`ADR-011`: guest checkout, no `Customer` model, `Order.customer_email` is the only thing resembling one). Customer Analytics is the first feature to treat that field as a grouping key, so how it does so needs to be decided deliberately, not assumed.

**Decision:**

1. **"Customer" is a derived grouping of `Order` rows by `customer_email`, never a stored entity.** No `Customer` model, no `customer_id`, no login — this does not reopen `ADR-011`, it reads `Order.customer_email` the same way Reports already does for its `latest_order.customer_email` field. Pinned in `docs/prd.md` §13 Glossary so a future session doesn't reintroduce a `Customer` table "for analytics" without realizing that's a re-litigation of `ADR-011`, not a free addition. `customer_phone` is deliberately **not** part of the identity key — it's more prone to reuse/typo (shared family lines) than email, which Reports already treats as the stable per-order identifier.
2. **Metric definitions (total spent, avg order value, order count) reuse `ReportService`'s pinned rule verbatim**: `payment_status=Paid` orders only, scoped by `paid_at` (never `created_at`), summed from `final_amount`, `is_test` excluded. No new definition invented for this feature — an abandoned/unpaid checkout has no analytics value any more than it has reporting value.
3. **Segmentation is computed from each customer's full lifetime order history, never re-sliced by the ANL-4 date-range filter.** Segment membership is an identity-level attribute (this customer's standing, full stop) — re-slicing it per date-range would make a customer's segment flicker based on which month an admin happens to be looking at, which isn't what "VIP" or "Dormant" mean. The date-range filter instead narrows which orders count toward the *displayed* spend/orders-count figures and CSV export rows, independently of the segment tag shown — mirrors how `ReportService::dailyTrend()`'s 7-day window and `RPT-3`'s year/month filter already stay independent concerns on the same underlying order set.
4. **Segment definitions and evaluation order**, most-significant-first (a customer matching more than one rule shows only the first that matches):
   - **VIP** — lifetime Paid spend ≥ a configurable threshold, default **RM5,000** (500,000 sen)
   - **Frequent** — 20+ lifetime Paid orders
   - **Dormant** — most recent Paid order is more than 60 days ago
   - **New** — first-ever Paid order is less than 30 days ago
   - **One-time** — exactly 1 lifetime Paid order
   - A customer matching none of the above (2-19 orders, none in the last 60 days, not a first-timer) has no badge — falls through to a plain count/spend row, same as any tracker row with nothing special to flag.
5. **Only the VIP threshold is configurable** (new field on `platform_settings`, mirroring `ADR-028`'s existing singleton-config pattern) — Frequent/Dormant/New/One-time stay hardcoded constants. The PRD's own wording is the tell: VIP is the only one of the five originally phrased as "≥ **threshold**" (implying a tunable business lever); the other four were given concrete literal numbers in the spec itself. Founder can revisit any of the hardcoded four later as its own small change, not a blocker now.
6. **Computed live on every request, no caching or materialized snapshot.** Matches Reports' own precedent (no aggregation caching anywhere in that service) — `ADR-014` decision 5's caching policy is explicitly scoped to "read-heavy, admin-curated listings" (Games/Packages/Payment Methods), not money/analytics aggregation, and order volume today doesn't yet justify the added staleness risk for a screen whose whole point is an accurate live number.
7. **Reseller-aware from day one** — a `reseller_id` filter alongside a default combined view, exactly mirroring `ReportService`'s and `ADR-013`'s "MVP and Phase 2 run the same code path" discipline. `Reseller` is still Phase 2-unbuilt, but the platform-owner row (`ADR-013`) already gives every order a real `reseller_id` to scope by, so there's no reason for this feature to hardcode a single-tenant assumption it would just have to delete later.

**Rationale:** Decision 1 is the load-bearing one this ADR exists to record — every other decision here builds on top of "customer" being a query-time grouping, not a schema change, which is exactly the boundary `ADR-011`'s own consequence-to-track warned future work to respect. Decisions 2/6/7 are direct reuse of `ReportService`/`ADR-013`'s existing discipline rather than parallel reinvention, the same "Single Source of Truth" reasoning `ADR-044`/`ADR-045` already applied elsewhere. Decision 3 (lifetime segmentation, period-scoped display) is the one genuinely non-obvious call — resolved by asking what "VIP"/"Dormant" are supposed to mean (a standing, not a snapshot) rather than what's easiest to query against a filtered set.

**Consequence to track:** the hardcoded Frequent/Dormant/New/One-time constants (decision 5) live wherever the segmentation logic itself lives (a `CustomerSegment` enum or equivalent, not scattered magic numbers) — if a future session makes any of them configurable too, that's a small follow-up, not a schema surprise, since `platform_settings` already holds the VIP precedent. The "no badge" fallthrough (decision 4's last bullet) should be reflected in the admin UI as an explicit state (e.g. a dash or "—"), not silently blank, so it doesn't read as a rendering bug.

**Build addendum, 2026-08-28 (same day) — all 7 decisions shipped exactly as recorded, no scope changes.** `App\Services\CustomerAnalytics\CustomerSegment` (enum) + `CustomerAnalyticsService` (`aggregatesByEmail()` — one `GROUP BY customer_email` query shared by both lifetime and period-scoped callers, `classify()`, `stats()`, `customers()`); `platform_settings.vip_spend_threshold_sen` migration + `PlatformSettings` model/`UpdatePlatformSettingsRequest` update + a new field on the existing Platform Settings tab; `Admin\CustomerAnalyticsController` (summary/customers/export, reuses `ReportService::dateRangeForYearMonth()` for the year/month parsing rather than duplicating it); new `/admin/customer-analytics` page mirroring `/admin/reports`' own filter-row/stat-card/DataTable structure (PrimeReact-Tailwind, ADR-038).

**Real bug found and fixed before merge, not shipped silently:** `classify()`'s first cut computed `CarbonImmutable::now()->diffInDays($pastTimestamp)` — this Carbon version returns a **signed** diff (negative when going now→past), not the absolute value older Carbon versions gave. Every existing order's negative diff satisfied `< 30` (falsely tagging every customer New) while never satisfying `> 60` (Dormant never fired at all). Caught immediately by the service's own test suite (5 of 12 tests failed on the first run), root-caused via a direct `tinker` check of `diffInDays()`'s actual sign behavior rather than guessed at, fixed by always diffing from the stored past timestamp forward to now. A reminder that this codebase's Carbon-diff conventions can't be assumed stable across versions — any new "N days ago" comparison should verify sign behavior the same way, not copy older code that predates this change.

**Also found, unrelated to this ADR's own logic:** `PlatformSettings::current()`'s `firstOrCreate([], ['currency' => 'MYR'])` never populated `vip_spend_threshold_sen` in the returned in-memory model on a fresh row — Eloquent doesn't re-fetch a column's DB-level `DEFAULT` after `INSERT`, so a brand-new settings row read back `null` for any column relying on that default rather than an explicit create-time value. Fixed by passing `vip_spend_threshold_sen` explicitly in `current()`'s create array, same as `currency` already was — a DB column default alone is not enough for any Eloquent-created singleton row.

24 new backend tests (`CustomerAnalyticsServiceTest`, `CustomerAnalyticsControllerTest`, +2 in `SettingsControllerTest`); full backend suite **920/920 green**. `npx tsc --noEmit`/`eslint`/`next build` clean on `admin/`. Browser-verified live: seeded 6 real customers (one per segment + one no-badge case) against the real local dev backend, confirmed all 5 segment tags render correctly, and cross-checked the Avg Order Value stat against `/admin/reports`' own number for the same data — both read `RM 222.65`, confirming the two features' independently-re-expressed scoping rules (decision 2) stayed consistent with each other.

**Addendum, 2026-09-18 — reseller-wallet awareness (founder-flagged, grilled 2 rounds).** Note on terminology first, since this ADR predates ADR-072's rename: decision 7's "`reseller_id` filter" above means today's `affiliateId` (`Affiliate::primary()` et al.) — it is **not** the thing this addendum is about. What this addendum adds is genuinely new: the wallet-`Reseller` entity `ADR-072/073` introduced *after* this ADR shipped, which this service had zero awareness of until now.

- **The gap.** A `wallet_reseller_id`-owned order (ADR-072/073) always carries `affiliate_id = Affiliate::primary()->id` by construction (ADR-073 decision 5 — no whitelabel storefront is involved). Founder-flagged, 2026-09-18: `CustomerAnalyticsService` had no `wallet_reseller_id` concept at all, so a wallet Reseller's own orders (`customer_email` = the reseller's real email, or the synthetic `wallet+reseller-{id}@pekangame.internal`) showed up as an ordinary retail "customer" of the primary brand — same gap ADR-086 PR-2 already closed for Reports via `resellerBreakdown()`, just never carried over here.
- **Decision (grilled): include, don't exclude, tag + filter.** Founder's explicit call, over this session's own first instinct (exclude wallet orders from the population entirely, on the theory that ANL's segmentation is about retail behavior): keep wallet-Reseller rows visible in Customer Analytics, don't hide them — add a `Source` indicator (`Reseller: {business_name}` vs. plain retail) and a `resellerId` filter parameter, symmetric to and independently-combinable with decision 7's existing `affiliateId` filter (picking a non-primary Affiliate + a Reseller at once naturally returns nothing — not a conflict worth guarding against, same as an impossible affiliate+date combination already does).
- **Segmentation (decision 3/4 above) is unchanged, on purpose.** A high-volume wallet Reseller can still earn a VIP/Frequent tag under the exact same rules as any retail customer_email — grilled and confirmed rather than special-cased, on the reasoning that the Source tag is what tells an admin "this is a B2B row," not a bent threshold.
- **Implementation.** `scopedOrders()`/`aggregatesByEmail()` gained an optional `$resellerId` filter (`where('wallet_reseller_id', ...)`, mirrors `$affiliateId`'s shape exactly); the per-email `GROUP BY` now also resolves `MAX(wallet_reseller_id)` and, when set, the `Reseller`'s `business_name` (`withTrashed()`, same precedent `ReportService::resellerBreakdown()` already set so a since-removed reseller's historical rows keep their name) — surfaced as `wallet_reseller_id`/`reseller_name` on every `customers()` row and the CSV export. `stats()`/`customers()`/`export()`/the controller all thread the new filter through positionally-safe (`?int $resellerId = null` appended, zero existing call sites touched).
- Admin frontend: `/admin/customer-analytics` gained a "Reseller" filter dropdown (reuses `lib/resellers.ts`'s existing `listResellers()`, no new endpoint) next to the existing "Affiliate" one, and a "Source" column tagging each row `Reseller: {name}` or `Retail`.

Browser-verified live against real seeded demo data: the Reseller filter, the Source column ("Retail" vs. "Reseller: Demo Wallet Reseller"), and a mixed customer's drill-down (below) all confirmed correct.
