# ADR-024: Voucher-at-Checkout — redemption timing, wallet model, and admin visibility (built 2026-08-14)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-13 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any code touched)

**Context:** `VoucherService::redeem()` (row-locked, `DB::transaction()`-wrapped, VCH-5-proven) has existed since ADR-002/the original Voucher build, but is dead code — no route calls it. `CheckoutController`'s own doc comment says so explicitly: "No voucher-at-checkout support yet (`VoucherService::redeem()` exists but isn't wired here) — deliberately out of scope." The storefront (`storefront/src/`) has zero voucher references anywhere (grepped, confirmed empty) — no input field, no API client function. The pricing plumbing is partially pre-built: `CheckoutRequest->voucherDiscountSen` (always `0` today, nothing populates it), `CheckoutTotalService::calculate()` already computes `feeBase = sellingPrice - voucherDiscount` and charges the transaction fee only on `feeBase`, and `orders.voucher_discount` already gets stamped from that at `Order::create()` — but since nothing ever sets `voucherDiscountSen`, it's a live column that's always `0` in practice.

The founder raised four real gaps in one review pass, live-testing the existing Issue Voucher flow: (1) the admin `/admin/vouchers` page has a list + Create modal only, no detail/view route at all — confirmed no `[id]/page.tsx`, no view button; the founder's own reference screenshot (status/remaining/usage-history/source-order/edit-history) is from a legacy system, not this codebase; (2) the `Voucher` model schema (`amount`/`remaining`/`status` only) has no redemption-event log, so that reference UI can't be built without new schema regardless of frontend work; (3) the storefront gap above; (4) two genuine money-correctness questions — does the row-lock in `redeem()` actually prevent the same voucher being spent twice from two simultaneous browser sessions, and what happens to a voucher's `remaining` balance if the customer applies it then abandons or cancels payment mid-flow. A follow-up question sharpened (4) into a concrete numeric case: selling price RM20, voucher RM10 — is the RM10 balance charged a transaction fee, and does crediting `platform_profit` on the resulting order double-count against the `voucher_issued` ledger debit already booked when the voucher was created. Tracing the code answered the profit-doubling half directly: `PricingService::calculate()` computes `platformProfit = resellerCostPrice - costPrice`, entirely independent of `sellingPrice`/`voucherDiscount`, so `OrderFulfillmentService::creditProfit()` crediting it in full on delivery does not collide with the voucher's own already-booked liability — two independent, correctly-decoupled economic events, not a bug. What remained genuinely undecided was everything about *when* and *how* `remaining` itself gets consumed and potentially given back — this ADR is that design.

**Decision:**

1. **Redemption timing — locked at gateway-success for a partial-cover order, immediately at order creation for a full-cover order; never at `Order::create()` time for a partial-cover order.** Concretely: inside `CheckoutService::requestPayment()`, *after* `$payment->success` is confirmed (the moment `PaymentGateway::createPayment()` has actually produced a real, redirectable payment request), `VoucherService::redeem()` is called — not before. Rejected alternative: locking at `Order::create()`, before the gateway call. That would mean a synchronous gateway failure (network error, Xendit rejects the request) leaves a voucher already spent with nothing to show for it, needing an extra restore path for a failure mode that locking-after-gateway-success eliminates outright — if the gateway call fails, the voucher was never touched at all.

2. **Usage model — wallet, not single-shot.** A voucher's `remaining` balance can be spent partially across many separate orders over time (unchanged from today's schema intent — `remaining` already exists for this), until it hits `0` (`status` flips to `exhausted`, matching `VoucherService::redeem()`'s existing logic). New table, `voucher_redemptions` (`voucher_id`, `order_id`, `amount`, `status` — `reserved`/`committed`/`restored` — timestamps), is the audit trail this model needs: one row per redemption attempt, resolved to `committed` (order delivered) or `restored` (payment/delivery ultimately failed). **No new `ledger_entries` are written by redeem or restore.** The voucher's full liability is already booked once, at issuance (`VoucherController::issue()`'s existing `voucher_issued` debit to the `platform` ledger) — redeeming or restoring only moves bookkeeping about which part of that already-booked liability has been *spent*, never a new real money movement. This is the direct answer to the founder's "ledger kena solid" concern: solidity here lives in `voucher_redemptions`' row-locked status transitions, not in additional ledger rows.

3. **Server-side lookup, ownership lock, and discount cap — never a client-submitted discount amount (ORD-9).** Checkout resolves the voucher by its code server-side, rejects unless `status=active`, not expired, and the voucher's `customer_email`/`customer_phone` matches the checkout's own submitted identity (a voucher is compensation for a specific customer, not a public bearer coupon — a leaked code must not be redeemable by anyone else). The discount actually applied is `min(voucher.remaining, sellingPrice)` computed server-side; `CheckoutTotalService`'s existing guard (throws if `voucherDiscount > sellingPrice`) stays as the final backstop, not the primary check.

4. **Partial-cover math — reuse `CheckoutTotalService::calculate()` unchanged.** `feeBase = sellingPrice - voucherDiscount`; the transaction fee is charged on `feeBase` only, never on the voucher-covered portion; `finalAmount = feeBase + transactionFee` is what the customer actually pays through the gateway. Already correctly built and tested — this ADR wires it up, it doesn't change it.

5. **Full-cover — skip the payment gateway entirely, zero transaction fee, straight to fulfillment.** When `voucher.remaining >= sellingPrice`, the order owes `RM0` in cash: `CheckoutService::initiate()` skips `PaymentGateway::createPayment()` altogether, sets `transaction_fee = 0` **unconditionally** (closing a real gap found while designing this: `PaymentMethodFeeConfig`'s flat-fee component, e.g. FPX's RM2.10, would otherwise still apply even at `feeBase = 0`, since only the percentage component scales with the base — a flat fee firing on a transaction that never touches a payment gateway makes no sense and directly contradicts the founder's own reasoning, "itu dah macam wallet mereka"), sets `payment_status = Paid` directly, and dispatches `FulfillOrderJob` immediately — same job a real webhook would dispatch, just triggered from checkout instead. `payment_ref` stays `null` — a real, structural signal that no gateway was ever involved, not a placeholder to fill in later. Confirmed this can't collide with `ReconcilePendingPaymentsCommand`: its query only ever selects `payment_status = pending`, and a full-cover order is never `pending`.

6. **Restore — exactly two triggers, both tied to a real terminal outcome, never to an intermediate state:**
   - **(a) Payment never completes.** A webhook delivers a terminal failed/expired/cancelled status, or `ReconcilePendingPaymentsCommand`'s existing stale-pending detection catches an abandoned checkout — both already-built mechanisms. Restore reuses the same threshold already configured (`payment_reconciliation.pending_after_minutes`, 30 minutes today) — no new voucher-specific timer, per the founder's own "boleh" to reusing the existing window rather than inventing a shorter one.
   - **(b) Delivery fails *and* the admin gives up.** `delivery_status = Failed` by itself is explicitly **not** a restore trigger — Resend Delivery must stay fully available for as long as the admin hasn't decided to stop, no matter how many resend attempts fail. Restore is tied specifically to the admin clicking **Issue Voucher** (`VoucherController::storeFromOrder()`), the one action that actually means "no more retries." A resend that later *succeeds* after any number of prior failures commits the voucher permanently instead (no restore) — the three-outcome shape this collapses to is exactly `ORD-11`'s existing two independent state machines (`payment_status`, `delivery_status`) resolving to (payment fails → restore), (payment succeeds, delivery ultimately abandoned → restore), (both succeed → committed, permanent).

7. **Two vouchers, never merged, when a voucher-funded order is abandoned via decision 6b.** Restoring the original voucher's `remaining` and issuing a new voucher for the order's cash portion (`storeFromOrder()`'s existing formula, `final_amount - transaction_fee` — already excludes the voucher-covered portion, confirmed by the math trace in Context, so no double-compensation) happen together in one transaction. Rejected alternative: merging the restored balance into the newly issued voucher — no functional benefit (a customer can already hold multiple simultaneously-active vouchers; `VoucherController::index()` has no one-per-customer constraint), and merging would add real bookkeeping (transferring a balance between codes, expiring one of them) for a purely cosmetic "one code instead of two."

8. **New guard, found while designing decision 6b, in scope for this build: block Resend Delivery once a voucher exists for that order.** `Voucher::where('order_id', $order->id)->exists()` becomes a hard precondition on the resend action (both `Admin\OrderController`'s endpoint and the UI affordance) — without it, a resend attempted *after* a voucher was already issued could succeed and deliver, double-compensating the customer (goods delivered *and* a voucher already in hand). This is a pre-existing gap, not introduced by voucher-at-checkout — but it directly threatens the correctness of decision 6b's own restore mechanism, and this session already has the relevant files open.

9. **Admin UI — build the full voucher-detail page in this same pass, not defer it.** Status, remaining, `voucher_redemptions`-backed usage history, source order link, edit history — the page the founder's reference screenshot described, now real instead of aspirational. Sequenced after decision 2's schema, since the data it displays doesn't exist without it.

10. **Reseller-liability — unchanged for MVP, deferred to Phase 2.** Voucher issuance keeps debiting the `platform` ledger only. A `voucher.reseller_id` scoping column (so a Phase 2 reseller's own voucher can't be redeemed at a different reseller's storefront, per the founder's own framing) is recorded here as a known future need, not built now — no second reseller exists yet to need it, matching this project's own "don't design for hypothetical future requirements" convention (`AGENTS.md`).

**Rationale:** Every decision above traces back to two hard constraints this codebase already lives by and that this feature cannot violate: ADR-004's no-cash-refund policy (which is what makes decision 1's "lock only after the gateway confirms a real payment request exists" load-bearing — a post-payment voucher failure would have no legal move, since cash can't be handed back) and ORD-9's "never trust client money input" (decision 3). Decision 2's "no new ledger entries" keeps `LedgerService` the single writer it's always been (ADR-002) — this feature adds a new *bookkeeping* table for redemption status, never a second path into the money ledger itself. Decision 6's two-trigger restore model is deliberately narrower than "restore on any failure signal" specifically because `delivery_status = Failed` is a recoverable, pending-admin-decision state in this codebase (ORD-7), not a terminal one — collapsing that distinction would either restore vouchers prematurely (while a resend might still succeed) or never restore them at all (if tied to the wrong signal).

**Addendum, 2026-09-17 — restore-only: a full-cover-by-voucher order minted a pointless RM0.00 compensation voucher; closes the gap in decisions 5+6b+7 together, grilled with the founder via `/mattpocock-skills:grilling` before any code changed.** Founder-reported: `VoucherController::storeFromOrder()` computes `amount = final_amount - transaction_fee` with no floor, so a decision-5 full-cover order (both forced to `0`) that later fails delivery still unconditionally called `VoucherService::issue(amount: 0, ...)` alongside the genuinely meaningful `restore()` call decision 7 requires — persisting a `Voucher` row with `amount=0`/`remaining=0`/`status=active` plus a `0`-value `voucher_issued` ledger debit, both real rows carrying no real value. No test/seed/migration exercised this scenario before this session (a live gap, not a regression).

Decisions, grilled one at a time:
1. **Skip zero exactly, not near-zero.** Any non-zero cash portion (even RM0.01) still gets a real voucher; only `amount === 0` routes to restore-only.
2. **One button slot, auto-routed — not two admin-chosen buttons.** The system already knows `final_amount - transaction_fee` before render; the admin never manually picks "Restore" vs "Issue" — the same button's label, dialog title/copy, and which backend call fires are all decided from the order's own state.
3. **Every mint call site, not just the admin action.** In practice only `storeFromOrder()`'s ordinary (non-partial-combo) branch was actually missing a guard — Path A (`store()`) already floors at `min:1`, and the partial-combo branch is always admin-typed and already floored the same way, so both were confirmed already-safe rather than needing a change.
4. **Leave historical RM0.00 vouchers alone.** No backfill/cleanup in this pass — a separate one-off script if the founder wants one later, not part of this fix's scope.
5. **One endpoint, branch internally — not a second route.** `storeFromOrder()` still always calls `restore()` unconditionally (decision 7 unchanged); it only skips the `issue()` call when the computed amount is `0`. Response shape unified to `{restored_only: bool, voucher: Voucher|null}` for both outcomes (the endpoint's only consumer, the admin frontend, was updated in the same PR — no external backward-compatibility constraint applied).
6. **Explicit success copy, not a silent no-op-looking success.** "Voucher restored — order fully covered by voucher, no new voucher issued," so an admin who just clicked never wonders if anything happened.
7. **Button-hiding via a new computed flag, not a new column.** `restore()` is idempotent (its gate is `voucher_redemptions.status='reserved'`; a second call finds none and no-ops — confirmed by code trace, not assumed) but writes no ledger entry and leaves no `Voucher` row, so the existing `!order.voucher` gate alone would leave the button visible forever after a restore-only click. New `Order::isVoucherRestored()` (`voucherRedemption()->where('status','restored')->exists()`) backs a new `has_voucher_restored` boolean on both `OrderController::index()`/`show()` — no new column, reused status already on `voucher_redemptions`.
8. **Partial-combo's own `min:1`-blocked RM0 edge case stays out of scope.** That amount is admin-typed, not auto-computed — if an admin sees RM0 there, they simply don't submit; the bug this addendum closes is specifically the auto-computed, admin-invisible zero.
9. **No actor/audit column added to `voucher_redemptions` for the restore action.** It never recorded who triggered a restore before this session either — not a regression introduced here, left as a possible separate accounting-audit item (ADR-083 family) if ever needed.
10. **List-row compensation badges: emoji → `<Tag>` pills, plus a 4th ("Restored").** Founder feedback, unprompted, mid-grill: the existing 🎫/🎟️/💰 `<span>` markers (ADR-102 decision 12) read as noisy/inconsistent next to the Payment/Delivery status `<Tag>` pills. Replaced with "Voucher Paid" (secondary)/"Voucher Issued" (warn)/"Wallet Refunded" (info), plus new "Restored" (success) backed by `has_voucher_restored` — since `has_compensation_voucher` alone would never be true for a restore-only order. `RefundInformationCards` (ADR-102 decision 11) gained a matching 4th card variant for detail-page parity.
11. **Found and fixed during the grill, beyond the original ask: `Order::isAlreadyCompensated()` had a real guard gap.** It only checked `voucher()->exists() || isAlreadyRefundedToWallet()` — a restore-only order (no `Voucher` row ever minted) would read as NOT compensated, silently reopening every resend/retry/mark-delivered guard built on top of it (`OrderController::retryDelivery()`/`resend()`/`markDelivered()`/`confirmFailed()`, `OrderResendService::assertResendable()`, `OrderFulfillmentService::fulfill()`'s two calls) — a further resend could have delivered goods on top of a voucher already given back. Fixed by folding `isVoucherRestored()` into `isAlreadyCompensated()`'s OR; the four guard error messages updated to say "voucher issued/restored" instead of just "voucher issued."

**Rationale:** Every decision traces to the same root distinction ADR-024 decision 7 already drew — restore (giving back an existing liability) and issue (booking a new one) are separate operations that happen to run in the same transaction, not one combined action. The original bug was treating them as inseparable (one button, one unconditional pair of calls); this addendum makes the pairing conditional on there being a second real liability to book at all, while keeping restore unconditional exactly as decision 7 requires. Decision 11's guard fix was not something the founder asked for — it surfaced from tracing `isAlreadyCompensated()`'s callers while designing decision 7's UI-gating equivalent (decision 7 above), and was fixed in the same PR rather than filed separately, since shipping the button fix alone would have reopened a real double-compensation window for exactly the order type this addendum targets.

**Addendum, 2026-09-29 — M-6 (full system audit): a full-voucher-cover checkout could give away free goods repeatedly, since nothing analogous to a real payment protected it the way the partial-cover path's own accepted residual race relies on. Narrows that accepted-race rationale specifically for the full-cover branch; grilled with the founder via `/mattpocock-skills:grilling` before any code changed.** The 2026-08-13 addendum's "accepted residual race" (`logAcceptedVoucherRedemptionRace()`) was written on the premise that "by this point the customer has already been charged (or the order already marked Paid)... ADR-004 forbids clawing that back." That premise is true for the partial-cover path (a real CHIP payment request already exists by the time `redeem()` can lose) but was silently also being applied to the full-cover path, where it's false: `Order::create()` stamped `payment_status=Paid` and `FulfillOrderJob` dispatched *before* `redeem()` ever ran, purely by code choice, with zero cash ever moving and `payment_ref` permanently null. Concretely: N concurrent checkout requests from the same customer (voucher ownership is email/phone-scoped, decision 3) citing a voucher whose `remaining` exactly covers one order's price all passed the unlocked `preview()`, all got their own real `Order` created as `Paid`, and all got fulfilled — only the first to reach `redeem()`'s lock actually spent the voucher; every other "loser" still shipped real goods for free, repeatably, bounded only by how many parallel requests an attacker sent.

Decisions, grilled one at a time:
1. **Reorder — `redeem()` becomes this branch's real commit checkpoint, not an afterthought.** Generalizes decision 1's own principle ("lock only after the gateway confirms success") to the full-cover case: since there's no gateway to wait for, `redeem()` itself stands in as the checkpoint. The Order is now created `Pending` (matching the partial-cover path's own starting state, no longer special-cased to `Paid` at creation) and only flips to `Paid`/`paid_at` *after* `redeem()` actually succeeds.
2. **Scope: full-cover branch only — the partial-cover path's existing accepted-race behavior is unchanged.** Real money (or a real gateway payment request) has already moved by the time `redeem()` can lose there, so ADR-004 genuinely applies and `requestPayment()`/`createPaymentFor()` still logs-and-proceeds exactly as before.
3. **A lost race fails the checkout outright, and the Order stays visible as `Failed` — not silently deleted or never created.** Consistent with how every other failed checkout in this codebase leaves a visible, audit-trail Order row (a declined CHIP payment does too) — an admin can see repeated attempts against the same voucher if abuse is ever suspected. The customer gets a generic error (`CheckoutFailedException`, "This voucher is no longer available for order {order_number} — its balance was just used by another order"), the same exception class and controller-side handling `createPaymentFor()` already uses for a real gateway failure — no new exception type needed.
4. **Membership quota decrement moves to the success branch only.** Previously ran unconditionally alongside the `redeem()` attempt regardless of outcome; now only fires after `redeem()` succeeds and the order is confirmed `Paid` — simpler than a decrement-then-restore round-trip in the same request for an order that's about to fail anyway.

**Rationale:** The root cause was treating "stamp Paid and dispatch fulfillment" as safe-by-default for full-cover the same way it genuinely is for a real payment, when the two have completely different risk profiles — one has already moved value, the other hasn't moved anything at all until the voucher lock actually clears. Once the analogy is corrected (redeem() *is* the full-cover path's payment-equivalent event), the fix falls directly out of decision 1's original design rather than requiring new machinery.

**Shipped, 2026-09-29 (same session).** `CheckoutService::initiate()`'s `OrderDraft` no longer special-cases `paymentStatus`/`paidAt` for a full-cover order — always `Pending`/`null` at creation. `settleWithVoucher()` now updates the order to `Failed` and throws `CheckoutFailedException` when `redeem()` throws `InvalidVoucherException`, or to `Paid`/`paid_at=now()` (then decrements quota, then dispatches `FulfillOrderJob`) on success. New `tests/Concurrency/CheckoutSettleWithVoucherConcurrencyTest.php` (two real OS processes racing `initiate()` against the same exactly-covering voucher, via a new `app:checkout-test-initiate-full-cover` test-only command) proves exactly one side settles `Paid` and the voucher is spent exactly once — manually verified red (both sides `Paid`, voucher double-spent) against the pre-fix code via `git stash`, green against the fix, 3x each. Full fast suite **2334/2334** green, full concurrency suite **24/24** green.

**Consequence to track:**
- `logAcceptedVoucherRedemptionRace()` (the 2026-08-13 addendum's log helper) is now reachable only from the partial-cover path (`createPaymentFor()`) — its own doc comment's "by this point the customer has already been charged" premise is now actually true for every caller, not just most of them.
- A losing full-cover checkout now consumes a real `order_number` (a visible `Failed` order) — if `order_number` generation or checkout analytics ever assume every created Order was a genuine sale attempt that could plausibly succeed, this is a source of "phantom" Failed orders with `final_amount=0`, distinguishable by `voucher_id IS NOT NULL AND final_amount=0 AND payment_ref IS NULL`.

`ADR-094`'s 2026-10-04 addendum (decisions 33-34) keeps decision 7's two-un-merged-vouchers rule but makes the restore of the paid-with voucher proportional to the undelivered share, via a new `voucher_redemptions.restored_amount`. ### Addendum, 2026-10-04 — a lost voucher or quota reservation fails the checkout closed (pre-launch money audit #3, PRD §16 item 60)

**Status:** Accepted. Grilled with the founder via `/mattpocock-skills:grilling` (Q1–Q15, including a stress-test round), plus the money-ADR code-trace pass. Supersedes the 2026-08-13 addendum's "accepted residual race" and M-6 decision 2 ("partial-cover keeps log-and-proceed").

**Context.** The partial-cover path reserved the voucher (`redeem()`) and the member quota (`MembershipQuotaService::decrement()`) only after the CHIP link existed. A lost race was logged and the checkout went ahead. Pricing reads both balances unlocked (`VoucherService::preview()`, `OrderPricingResolver.php:165`), so one customer opening N tabs got N orders discounted by one voucher balance, or N member-priced orders against one quota. Example: a RM10 voucher, two RM20 orders: both pay RM10 + fee, the voucher drains once, RM10 of goods given away per extra tab. The 2026-08-13 addendum accepted this on two premises, both wrong:
1. *"Only the same customer can race, so it is a narrow accident."* The owner of the voucher is exactly the person with a reason to race it, and can do so on purpose, repeatedly.
2. *"Money has already moved, ADR-004 forbids clawing it back."* At reservation time only a payment *link* exists. The customer has paid nothing and has not even received the link, so refusing is free.

The full-cover path (M-6) already failed closed on the voucher, but still decremented quota after marking the order Paid, with log-and-proceed. Production scale at decision time: 27 paid orders, 4 vouchers, 2 memberships, no race log line ever fired.

**Code-trace pass.** Writers of `vouchers.remaining`: `issue`, `merge`, `redeem`, `restore`. Writers of `memberships.quota_remaining_sen`: `decrement`, `restore`, `MembershipFeeService` (subscribe/renew, absolute), `ResetMembershipCyclesCommand` (locked, absolute). `CheckoutService` is the only production caller of `redeem()` and `decrement()`. Pricing bases: Standard, Member and every Affiliate brand go through `CheckoutService`; Reseller wallet orders use neither instrument. Reports, Customer Analytics and the export read only Paid orders, so a failed-closed order never reaches a money total. Lock order (Order → Voucher → Membership) matches `OrderSettlementService` and the CHIP webhook.

**Decisions.**
1. **Keep decision 1's timing; fail closed on a lost race.** Reservation still runs after the CHIP link exists (no new seam, no new restore trigger for a gateway failure). If either reservation loses, whichever one succeeded is restored, the order is marked `Failed`, and checkout throws. The link never reaches the customer because `initiate()` only returns after reserving. Rejected: reserving before the gateway call, which needs a restore on gateway failure and a reconcile path for orders with `payment_ref = null` (`ReconcilePendingPaymentsCommand` only selects orders with one).
2. **Both instruments, one rule.** Voucher and member quota, including a voucher that expired or was merged between preview and reserve.
3. **Partial win restores the winner.** Voucher reserved but quota lost (or the reverse): restore the reserved one with the existing `restore()`, then fail.
4. **Full-cover decrements quota before marking Paid** (extends M-6). Quota loss restores the voucher and fails the order the same way.
5. **Reservation and the Failed write run in one transaction holding the Order row lock**, separate from the `payment_ref` transaction (the 2026-09-29 note stays true). `redeem()`/`decrement()` treat an existing row for the order as success even if it was restored, so the Order lock is what makes a concurrent replay see the final state.
6. **The idempotent replay path reserves before handing out a link.** A replay of a `Failed` order is refused. A replay of a `Pending` order with a `payment_ref` reserves first (idempotent) and fails closed on loss. A `Paid` replay is unchanged. This also closes an older gap: a process dying after `payment_ref` committed but before reservation used to let the replay return a link with nothing reserved.
7. **Distinct error.** `CheckoutAttemptClosedException` (a `CheckoutFailedException`) becomes a 422 with `code: checkout_closed`: the race message for a lost reservation, a generic "this checkout attempt has closed" for a replayed `Failed` order. Named for the attempt rather than the voucher (the grill's working name was `voucher_race`) because the replay case is not always a race.
8. **Storefront on `checkout_closed`:** new idempotency key, applied voucher cleared, totals preview re-fetched, so the next click is a fresh, correctly priced checkout. A quota-only loss changes the price without changing any input the preview was keyed on, so the re-fetch must be forced. Other errors keep the same key, so the double-click/timeout protection is unchanged.
9. **The orphaned CHIP purchase expires on its own** (`due_strict`, 30 minutes). Its expired webhook lands on an already-Failed order and `restore()` no-ops. No `cancelPayment()` on the gateway seam.
10. **If that orphaned purchase is somehow paid** (the customer never saw its link; CHIP emailing it is the only conceivable route), the existing Paid-after-Failed branch puts it in NeedsReview. The customer paid a discounted price for which no voucher or quota was spent. The admin must **Issue Voucher** for the cash paid and must **not** Resend or Mark Delivered. Guidance only; add a code guard if it ever happens once.
11. **Admin voucher pill and card read `voucher_redemptions`, not `orders.voucher_id`.** A failed-closed order keeps its `voucher_id` and `voucher_discount` (ORD-9 snapshot, audit trail of which voucher was tried) but shows no "Voucher Paid" pill or "Voucher Used to Pay" card, since nothing was spent. Rejected: clearing the columns, which would break `final_amount`'s arithmetic and the snapshot.

**Out of scope.** `decrement()` does not check that the membership is still active; a membership lapsing in the seconds between pricing and reserve still gets debited. Pre-existing, no loss beyond one member price.

**Consequence to track.**
- A failed-closed order is a visible `Failed` row with `voucher_id` or `membership_id` set and no matching reservation. A burst of these from one customer is an abuse signal (logged at warning: "Checkout reservation lost — order failed closed").
- Item 63's unconditional CHIP Paid write is a separate fix; this addendum does not depend on it, because Paid-after-Failed already routes to NeedsReview.
