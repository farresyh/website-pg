# ADR-026: Delivery-side reconciliation (ORD-10) — `NeedsReview` state for ambiguous Gamevion order-creation failures (built 2026-08-14)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-14, grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any code touched.

**Context:** A fresh full-system audit (same session, see `prd.md` §14) re-confirmed ORD-10 (delivery-side reconciliation) as the one still-open item from `foundation-security.md` §3's split payment-side/delivery-side outcome — payment-side has had automatic stuck-order detection since ADR-021 (`app:reconcile-pending-payments`); delivery-side never got its counterpart. Investigating *why* surfaced it is structurally harder than payment-side, not merely unbuilt out of neglect:

Two genuinely distinct ambiguous-failure shapes exist in `OrderFulfillmentService`/`FulfillOrderJob`/`GamevionAdapter`, neither previously documented as two separate problems:

- **Gap X — silent stuck-`processing`.** A connection-level failure exhausts both the HTTP-layer retry (`TransientFailureRetryPolicy`, 3×/200-500-1000ms) and the job-level retry (`FulfillOrderJob`, 3×/10-30-60s backoff, per its own doc comment). The job lands in `failed_jobs`; the `Order` stays at `delivery_status=processing` forever, with **zero `supplier_response` recorded** — completely invisible in the Admin Panel today, only discoverable by querying `failed_jobs` directly.
- **Gap Y — unactioned `duplicate_reference`.** Gamevion's `/api/order` is idempotent on `referenceNumber` (confirmed live 2026-07-29, ADR-006's addendum) — a resubmit against an already-accepted reference returns `409`, which `GamevionAdapter::createOrder()` already normalizes to `supplier_response.error_code='duplicate_reference'`. This is **already recorded in the data today**, both going forward and retroactively for any past order that hit it — grep confirmed nothing in `app/` ever reads or acts on that specific value; it's treated identically to any other business-level delivery failure.

Unlike payment-side's `ReconcilePendingPaymentsCommand`, which can always resolve ambiguity by polling `PaymentGateway::getPayment()` keyed on `payment_ref` (guaranteed present before the gateway call ever happens), Gamevion's `checkStatus()` requires **its own invoice number** (`supplier_ref`) — confirmed via `GamevionAdapterTest`'s own doc comment ("Gamevion's OWN order id... never our reference_number") — and that invoice number is precisely the value missing in both Gap X and Gap Y. Re-confirmed live during this grilling session: Gamevion's entire API surface is 4 endpoints total (re-checked against `docs.gamevion.com/gamevion-api`, matching ADR-006's 2026-07-25 addendum; a live re-fetch attempt this session was blocked by the site returning `403` to automated fetches, so this rests on the last-confirmed record, flagged below to re-verify before shipping), none of which accept our `reference_number` as a lookup key; the `409` error body itself carries no invoice field either (status+description only, per `GamevionAdapter::failureFrom()`'s own doc comment). The founder additionally checked Gamevion's real merchant dashboard live during this session (screenshot reviewed together) — it supports Status/Payment Status/date-range filters and a "Search Invoice" field keyed on *Gamevion's own* invoice format, with **no reference-number search at all**. So automated resolution of Gap Y is not possible against Gamevion's currently-confirmed API or dashboard surface — only a human, manually cross-referencing the dashboard's date-range filter against the TARGET (player ID) and SERVICE (game) columns, can determine the real outcome.

This "safe to retry `createOrder()` by reusing `reference_number`, and `409` specifically means idempotent-duplicate" mechanism is confirmed specific to `GamevionAdapter`'s own implementation — the generic `SupplierAdapter` interface declares no idempotency contract at all. Per ADR-006's own standing principle ("never assume a supplier's auth scheme, response envelope, or validation-endpoint availability is uniform with any other supplier"), this design's auto-retry step (decision 3) must be **re-verified, not assumed**, if/when a second real supplier adapter is ever added — deliberately not generalized into a capability flag now, since only one supplier exists today (AGENTS.md's own "don't design for hypothetical future requirements").

**Decision:**

1. **Scope: Gap X and Gap Y only.** Orders stuck at `delivery_status=not_started` (the queue worker never picked up the job at all) are explicitly **out of scope** — a different root cause (infra/ops; already has its own documented gotcha in `AGENTS.md`), not a Gamevion-response ambiguity. Belongs to a future alerting/health-check concern, not this feature.

2. **New `DeliveryStatus` enum case: `NeedsReview`.** A typed state, not a flag/column layered on top of `Failed`/`Processing` — matches this project's own precedent (`PaymentStatus` gaining a typed field during the `ChipGateway` build, ADR-022's addendum) for the same reason: the type system forces every call site to handle it explicitly, rather than trust a convention a future change could silently miss.

3. **New scheduled command `app:reconcile-pending-deliveries`**, same 15-minute cadence as `app:reconcile-pending-payments` (`routes/console.php`). Targets orders stuck **>15 minutes** — comfortably past `FulfillOrderJob`'s own worst-case exhaustion window (up to ~9 attempts across HTTP + job-level retry layers):
   - **Gap X** (`supplier_ref` null, still `processing`): attempts **one** `createOrder()` retry, reusing the order's existing `reference_number` (ORD-8, never regenerated on retry). A real `invoice_number` back means it genuinely failed before and is now resolved — auto-mark `Delivered` exactly as a normal successful delivery would (credits ledger profit via the existing path). A `duplicate_reference` back falls through to `NeedsReview`, same as Gap Y.
   - **Gap Y** (`delivery_status=failed` with `error_code=duplicate_reference`, including any that already reached this state via a manual "Resend Delivery" click before this feature existed): moves directly to `NeedsReview` — no further automated resolution attempted, since neither Gamevion's API nor its dashboard support a reference-number lookup (confirmed above).

4. **`NeedsReview` has exactly three admin-facing exit actions:**
   a. **"Mark as Delivered"** (new action — no equivalent exists today, deliberately, since money-critical state has never trusted a bare admin claim before). Admin manually cross-references Gamevion's dashboard (date-range filter + TARGET/SERVICE columns — the only fields usable for this lookup, confirmed above) to determine the real outcome, then submits **with the real Gamevion invoice number they found** — this populates `supplier_ref` (closing the exact data gap that caused the ambiguity) and credits ledger profit through the same path a normal delivery does.
   b. **"Resend Delivery"** — the existing `OrderResendService`/modal, gate extended to also accept `delivery_status=NeedsReview` (currently `Failed`-only).
   c. **"Issue Voucher"** — **explicitly blocked** from `NeedsReview` (its existing gate stays `Failed`-only, deliberately not extended). This is the one exit this feature does not open, because voucher issuance from an unconfirmed state carries exactly the double-compensation risk (a customer receiving both real game credits Gamevion silently already delivered, and a store-credit refund) that this whole feature exists to prevent. An admin must resolve the order to `Delivered` or a genuine `Failed` first.

5. **Admin UI reuses the existing `/admin/orders` list + detail-view pattern** — a new filter value `needs_review` alongside the existing `need_action`/`processing`/`completed` filters, surfaced inside the existing Order detail view (no new standalone screen). For a `NeedsReview` order specifically, the detail view additionally surfaces `created_at`, `player_id`, and the game/service name prominently — exactly the fields needed to manually cross-reference Gamevion's dashboard.

6. **No backfill script.** The scheduled job scans by current state + elapsed time on every run, not by "when created" — any order already stuck in a Gap X or Gap Y state before this ships gets picked up automatically the first time the job runs post-deploy. No separate one-time migration/backfill needed.

**Rationale:** Gap X and Gap Y are handled by one job because they converge on the same terminal state and the same "no automated resolution possible" reality — splitting them into two features would duplicate the `NeedsReview` state, the admin UI, and the three exit actions for no real benefit. The one-retry-then-flag design (decision 3) mirrors this codebase's existing bias toward auto-resolving the common case (most connection blips are already healed by the two retry layers that ran *before* reaching this job; what's left after 15 minutes is disproportionately the genuinely-stuck minority) while refusing to guess on the genuinely ambiguous remainder. Decision 4c's asymmetry — two exits opened, one deliberately not — is the load-bearing decision of this whole ADR: every other choice here is either infrastructure (the job, the state) or a UI convenience; this is the one that actually prevents the double-compensation failure mode the founder specifically asked about being explicitly closed rather than left to admin discipline.

**Consequence to track:**
- This ADR records design intent only — no code exists yet, matching this project's own established practice for design-only ADRs (`ADR-013`/`ADR-015`/`ADR-016`/`ADR-017`/`ADR-018`/`ADR-020`/`ADR-022`/`ADR-024`/`ADR-025`). Update `docs/prd.md` §14/§15 once this actually ships.
- The "Gamevion has only 4 endpoints, no reference-number lookup anywhere" fact this whole design leans on is a **3-week-old record** (last confirmed live 2026-07-25) plus a founder-reviewed dashboard screenshot from this session — a live re-fetch attempt this session was blocked (`403`). Worth one more direct check with Gamevion support before shipping decision 4a's "no automated path exists" as a permanent fact, not just at design time.
- `createOrder()`'s idempotent-retry-by-`referenceNumber` semantics (decision 3) are a **Gamevion-specific** confirmed behavior, not a `SupplierAdapter` interface guarantee — flagged in Context above, re-verify explicitly before extending this auto-retry pattern to any future second supplier adapter.
- `NeedsReview`'s real-world trigger rate is genuinely unmeasured — this project has no live production traffic yet. The founder specifically asked about volume/burst risk (2,000 concurrent orders); the honest answer given was structural reasoning, not a real percentage. Worth watching the actual rate once live and revisiting the 15-minute threshold/job cadence if it turns out materially different from the "small tail, not a flood" expectation this design assumes.
- Every existing `match`/`switch` over `DeliveryStatus` (`OrderController`'s status filters, `OrderStatusService`'s transition guards, any frontend `DeliveryStatus` display mapping) needs an explicit audit at build time to confirm none of them silently mishandle the new `NeedsReview` case via a default/fallthrough branch — PHP's `match` (no fallthrough, throws on unmatched) mostly protects backend call sites structurally; TypeScript's own exhaustiveness needs the same check on the frontend.
- `OrderStatusService::startDelivery()`'s existing guard (`in_array($currentDeliveryStatus, [NotStarted, Failed])`) needs `NeedsReview` added so "Resend Delivery" (decision 4b) can actually re-enter `Processing` from that state.

**Addendum, 2026-08-14 (same session, after build) — sandbox coverage.** Founder asked whether `NeedsReview` could be exercised in the ADR-018 sandbox the same way a real order would hit it. Turned out to be nearly free: `ResendSandboxOrderDeliveryRequest`'s `error_code` field is already free-text, and `SandboxOrderController::resend()` already calls the exact same `OrderFulfillmentService::fulfill()` this ADR's duplicate_reference handling lives in — so typing `duplicate_reference` into the sandbox's existing "Simulated Outcome" picker reaches `needs_review` with zero backend changes. What *was* missing, both fixed same session: `SandboxOrderController` gained a `markDelivered()` counterpart to decision 4a (reusing `markDeliveredManually()` unchanged — `creditProfit()`'s existing `is_test` guard, decision #6 of ADR-018, already keeps this off the real ledger with no new guard needed), and `/middleware/sandbox`'s own Resend button was gated `=== "failed"` only, same oversight the real `/admin/orders` page had before this ADR's decision 4b fix — extended to match. 7 new backend tests, full suite **598/598 green**.

**Addendum, 2026-09-16 (found shipping ADR-098, grilled via `/mattpocock-skills:grilling`, bundled into the same PR #219) — the missing "resolve to a genuine Failed" exit decision 4c's own text always assumed existed.** Decision 4c's rationale literally reads "An admin must resolve the order to Delivered or a genuine Failed **first**" before Issue Voucher becomes available — but no action transitioning `needs_review → Failed` was ever actually built. Confirmed in real code: `Admin\OrderController` had exactly the two decision-4a/4b exits (`markDelivered()`, `retryDelivery()`/`resend()`), nothing else; `VoucherController::storeFromOrder()`'s gate stayed `Failed`-only. Always a latent gap (Gamevion's `duplicate_reference` trigger is rare), but ADR-098 makes it load-bearing: a `transactionAlreadyFormed` Digiflazz order (e.g. rc=02) can *never* be resolved by retry (the same reference only ever replays the stored result, proven via real production request-log comparison across resend attempts on order `PG-JLOMUJ1H23NE`) — so without this fix, that entire class of order became a permanent dead end the moment ADR-098 shipped, where before it simply sat at plain `Failed` and a voucher issued normally.

Decisions (grilled, each confirmed against real code before building):

1. **New action "Confirm Failed" (`OrderFulfillmentService::confirmDeliveryFailed()`, `OrderStatusService::markNeedsReviewAsFailed()` — a new dedicated `NeedsReview`-only guarded transition, mirroring `markDeliveredManually()`'s own single-purpose guard) lands the order on plain `Failed`.** Issue Voucher (unchanged) is a deliberately separate, admin-triggered second step — not collapsed into one mega-action, matching decision 4c's own two-step wording.
2. **`note` is required, not optional** (unlike `MarkOrderDeliveredRequest`'s optional one) — this is an admin's own "I've confirmed this genuinely failed" claim, exactly the class of consequential judgment call this codebase already requires written justification for elsewhere.
3. **`supplier_response` is MERGED, not overwritten** — unlike `markDeliveredManually()`'s overwrite (correct there: delivery succeeded, the prior ambiguous data no longer matters), the original `error_code`/`error_message` here IS the actual evidence this failed, and stays alongside the admin's own `confirmed_failed_by`/`note`/`confirmed_at`.
4. **Excludes a genuine partial-combo-delivery `needs_review` order** (`Order::isPartialComboDelivery()`, ADR-094 decision 9's own carve-out) — that case has its own dedicated custom-amount voucher path; confirming the WHOLE order "failed" would be wrong when some legs genuinely did deliver.
5. **Sandbox counterpart built too** (`SandboxOrderController::confirmFailed()`), same precedent as this ADR's own 2026-08-14 sandbox-coverage addendum above — no voucher-exists or partial-combo-delivery check there (sandbox has no voucher feature and never builds a combo order), same reasoning `markDelivered()`'s sandbox counterpart already established.
6. **`NeedsReviewBanner.tsx` made supplier-aware.** The original copy hardcoded Gamevion's own confirmed dashboard capabilities (a real, founder-reviewed-screenshot fact from this ADR's own Context) for every `needs_review` order regardless of trigger — now misleading once Digiflazz is a second real trigger (ADR-098). Fixed: Gamevion keeps its exact original copy; every other supplier gets generic "check the supplier's own transaction records" copy (no invented capability claims for a supplier this project has no equivalent verified dashboard fact for) plus the actual stored `error_code`/`error_message` so the admin has concrete context regardless of which supplier or copy variant applies.
7. **New `Order::deliveryRetryLikelyFutile()`** (reconstructs the same `transactionAlreadyFormed` classification from the persisted `error_code` alone — `DigiflazzAdapter::transactionAlreadyFormed()` stays the single source of truth, never a second hand-copied rc list; supplier-scoped the same way `ReconcilePendingDeliveriesCommand`'s own catch-up query is, to avoid the same Gamevion `error_code`-collision risk) drives a small warning next to the Resend Delivery button ("Resending is unlikely to change this outcome…") — **the button itself is never hidden**, kept as a live option for the edge case this classification hasn't fully proven impossible, just clearly labeled as unlikely to help.

**Consequence to track:**
- This ADR's own decision 4c framing ("two exits opened, one deliberately not") is now "three exits opened, deliberately not collapsing Confirm Failed and Issue Voucher into one action" — the double-compensation guard the original decision protected is unchanged, since Confirm Failed itself credits nothing.
- No fact exists yet about Digiflazz's own dashboard capabilities (unlike Gamevion's, confirmed via a founder-reviewed screenshot) — the banner's generic Digiflazz copy should be sharpened to name real capabilities once/if that's ever confirmed live.
