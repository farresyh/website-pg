# ADR-035: Voucher Path A double-submission guard — idempotency key, mirroring checkout (built 2026-08-26)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled 2026-08-25, built 2026-08-26 exactly as designed, no changes on contact with code

**Context:** Parked from the 2026-08-24 fat-controller audit: unlike Path B (`VoucherController::storeFromOrder()`), which serializes on `vouchers.order_id`'s unique index, Path A (`VoucherController::store()`, admin-issued standalone voucher) has no natural equivalence key — two rapid identical submissions (double-click, or a client-side network timeout/retry) genuinely create two separate valid `Voucher` rows, each with its own ledger debit (`VoucherService::issue()`). The audit recorded three candidate designs without picking one: an idempotency key + unique constraint, accepting the risk as-is, or a short debounce lock.

The founder confirmed, this session: (1) worth fixing now, not accepting as-is — the fix is cheap relative to a silent duplicate ledger debit; (2) both failure modes matter — a literal double-click (already partly covered client-side, `CreateVoucherModal.tsx`'s `submitting`-disables-the-button state) **and** a silent network-retry, where the admin's first request actually succeeded server-side but the response never came back, so client-side button state alone cannot catch it; (3) two vouchers of the identical amount, for the identical customer, submitted minutes apart can be entirely legitimate (two separate reasons) — so the guard must key off "this exact request was submitted twice," never a content-based fingerprint (customer+amount+time-window), which would silently block a legitimate second voucher.

An exact precedent already exists in this codebase for the identical problem: `orders.checkout_idempotency_key` (`CreateCheckoutRequest.php:32-40`, `CheckoutService.php:90-146`) — client generates a UUID once per checkout attempt (`crypto.randomUUID()`, held in a `useRef` so it survives retries of that same attempt, `storefront/.../OrderForm.tsx`), server does a fast-path lookup by that key first, then a DB-level unique constraint is the real backstop for a genuine race (`UniqueConstraintViolationException` caught, the winning row re-read and returned — not an error).

**Decision:**

1. **New nullable, unique `vouchers.idempotency_key` column.** Path B (`storeFromOrder()`) never sets it — nullable+unique is safe (multiple `NULL`s are distinct under a unique index), so Path B's own rows never collide with each other or with Path A's.
2. **Client generates the key once per modal-open, not once per click** — `CreateVoucherModal.tsx` holds it in a `useRef` (mirrors `OrderForm.tsx`'s exact pattern), stable across retries of one attempt, reset only when the modal is closed and reopened. A fresh legitimate second voucher (decision above, item 3) gets a fresh key by construction, since it necessarily starts from a fresh modal-open.
3. **Server: fast-path lookup, then unique constraint as the real guarantee — exactly `CheckoutController`'s two-layer shape.** `VoucherController::store()` looks up `idempotency_key` first (cheap, friendly); the real serialization is the DB unique constraint, caught via `UniqueConstraintViolationException`, re-reading and returning the winning `Voucher` row rather than erroring.
4. **Duplicate detection is silent — an idempotent success, never a warning shown to the admin.** Matches checkout's own behavior: only one `Voucher` genuinely exists either way, so there is nothing for the admin to be alarmed about, whether the duplicate was a network retry or an accidental double-click.
5. **Scoped to Path A only.** Path B keeps `order_id`'s own unique index, untouched.

**Rationale:** Mirrors a pattern already proven correct in this exact codebase for the identical class of problem, rather than inventing a new mechanism for a solved problem — lowest risk, fastest to build correctly, and one less pattern for a future reader to learn. A request-scoped key (not content-scoped) is the only shape that satisfies both "catch a silent network retry" and "never block a legitimate identical-looking second voucher" at the same time — a debounce lock keyed on content (customer+amount+window) would satisfy the first at the cost of the second.
