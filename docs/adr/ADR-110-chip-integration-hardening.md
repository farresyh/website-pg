**Context:**

The founder was investigating why `/track-order` intermittently shows "too many attempts" (a separate, already-diagnosed issue — the storefront's adaptive poll cadence in `OrderStatusTracker.tsx` outpaces the `throttle:20,1,track-order` route limit; not part of this ADR — **correction, 2026-09-22: "diagnosed" never actually meant "tracked" — no backlog entry existed for this until the founder reproduced it again 3 days later on a real order; now `docs/prd.md` §16 item 20**) and asked to check a specific stuck order via SSH: **`PG-ZUOSHF3Q9FOC`**, `payment_status=pending` since **2026-09-11 14:59:33**, still pending 8 days later.

Investigation traced this to a real bug, not the reconciliation job failing to run: `app:reconcile-pending-payments` (ADR-021/PAY-3) had been firing every 15 minutes exactly as designed, and production logs (`storage/logs/laravel.log`) showed a consistent `Payment reconciliation: order flagged for review` warning every 15 minutes since at least 2026-09-18, carrying `"gateway_status":"overdue"`. `ChipGateway::mapPurchaseStatus()` (`backend/app/Services/Payment/Chip/ChipGateway.php:251-257`) only maps `paid`→`Paid` and `error`/`cancelled`→`Failed`; every other raw CHIP status — including `overdue` — falls through to the `default => PaymentStatus::Pending` case. The class's own docblock (lines 39-42) claims this is the complete terminal-status set; it isn't. Pulling CHIP's real OpenAPI spec (`https://docs.chip-in.asia/openapi/chip-collect.yaml`, fetched raw and grepped directly — a rendered/summarized fetch of the same page silently dropped this detail, confirming this project's own repeated "verify against the raw doc, not a summary" lesson) shows the actual `PurchaseStatus` enum has 21 values, three of which are unhandled failure-adjacent terminal states this adapter has never recognized: **`overdue`** ("past its `.due`, but payment for it is still possible"), **`expired`** ("past its `.due` and payment for it isn't possible anymore — as a result of `purchase.due_strict` having been set to `true`"), and **`blocked`** ("like `error`, but payment attempt was blocked due to fraud scoring"). `ChipGateway::createPayment()` (lines 83-108) never sends `due`/`due_strict` in the `purchase` payload at all — so a CHIP purchase this platform creates can never actually reach `expired`, only sit at `overdue` (CHIP's own wording: "payment... still possible") indefinitely. Confirmed live twice: the 2026-09-18 log excerpts, and a direct `ChipGateway::getPayment()` call against production via `php artisan tinker` this same session, both returned raw `status: "overdue"` for this exact purchase — a 20-minute browser-based investigation of a competitor's own MLBB ID-checker tooling (redxgame.com, unrelated to this ADR) is what originally surfaced the general question of "does our own stuck-pending handling actually work," leading here.

Once the root cause was clear, the founder asked to fix it via the fuller of two options offered — not just complete the status mapping (Option A), but also start sending `due`/`due_strict` so CHIP itself formally closes a stale purchase (**Option B**) — and then asked to fold in two adjacent, previously-deferred CHIP-related backlog items rather than ship three separate small changes: **ADR-083 PR-2** (`docs/prd.md` §16 item 12 — "waits for real order flow + a real settlement file from the PekanGame CHIP account," a precondition the founder confirmed is now met: several real orders have been tested in production, and a real settlement export (`settlements-20260919025821.xlsx`) was downloaded from the actual PekanGame CHIP account and read directly this session — see decision 5) and the **CHIP credential `.env`→DB migration** (parked since 2026-09-13 specifically because it "touches live payment secrets" and needed its own ADR + grill, referenced but not duplicated by ADR-087 decision 10's own Gemini-key discussion).

**Decision:**

**PR-A — Purchase status mapping + `due`/`due_strict` expiry (ships first: today's live bug, smallest blast radius):**

1. **`ChipGateway::mapPurchaseStatus()` gains three more terminal mappings**: `overdue`, `expired`, and `blocked` all map to `PaymentStatus::Failed`, alongside the existing `error`/`cancelled`. In this platform's guest-checkout context (never a B2B invoice a customer might come back to pay days later), a purchase CHIP itself has flagged as unpaid-past-due or fraud-blocked is treated as dead — the same terminal outcome `error`/`cancelled` already produce via `PaymentReconciliationService::markFailed()` (order `Failed`, any reserved voucher restored). The class docblock (lines 39-42) is corrected to list the real, spec-confirmed terminal set.
2. **`ChipGateway::createPayment()` starts sending `due` (now + 30 minutes) and `due_strict: true`** in the `purchase` payload, for **every** caller of `PaymentRequest` uniformly — `CheckoutService` (retail order), `MembershipSubscriptionService` (self-serve subscribe), `ResellerWalletTopupService` (wallet top-up), and `PaymentMethodController`'s channel test-probe. `PaymentRequest` gains no new field for this — it's set unconditionally inside `ChipGateway::createPayment()` itself, not threaded through from callers, since by the time any of these four flows creates a CHIP purchase the customer has already committed to paying and is mid-redirect; the realistic completion window (a bank-app round trip) doesn't meaningfully vary by what's being purchased. 30 minutes matches this codebase's own existing convention for "how long do we give someone to pay" (`wallet_topup_attempts.expires_at`, ADR-073 decision 8; `payment_reconciliation.pending_after_minutes`, both 30) rather than inventing a new number.
3. **No backfill and no manual intervention for already-stuck orders, including `PG-ZUOSHF3Q9FOC` itself.** An order created before this ship has no `due` on its CHIP purchase and can only ever reach `overdue` (never CHIP-side `expired`) — but decision 1's mapping fix alone is sufficient: the very next `app:reconcile-pending-payments` run (≤15 minutes after deploy) will see `overdue`, now map it to `Failed`, and resolve it exactly like any other order — self-healing, no `MANUAL_ADJUSTMENT`-style correction needed. Deliberately left as the first live proof the fix works, rather than cleared by hand ahead of it.

**PR-C — CHIP credential `.env`→DB migration (ships second: foundational, not urgent, deliberately careful with live secrets):**

4. **New `payment_gateways` table**, one row per gateway (`chip` the only one today): `gateway_key` (unique string), `api_config` (`encrypted:array` cast — Laravel's built-in cast, not manual `Crypt::` calls), standard timestamps. Mirrors `Supplier.api_config` (ADR-046, SUPP-5) **verbatim** — same cast, same `$hidden` treatment (never serialized in any `toArray()`/`toJson()`), same masked-value-on-display convention.
5. **`api_config` holds `secret_key`, `brand_id`, and `base_url`** — `base_url` moves in alongside the two secrets, not kept separately, matching `Supplier.api_config`'s own precedent (its migration comment: "adapter needs `base_url`/bearer_token/api_key/sandbox" — all in the one encrypted blob, not split by secret-vs-operational). `timeout`/`connect_timeout`/`webhook_public_key_ttl`/`callback_url` (`config/services.php:136-144`) stay in `config/services.php` — generic HTTP-client tuning and a value already derived from `APP_URL`, not properties of the CHIP account itself.
6. **New `/middleware` admin screen** (not `/admin` — matches this project's own established convention that supplier/gateway *integration* config lives under `/middleware` even on a shared or adjacent model), mirroring `Supplier`'s own create/edit form: `super_admin`-only, a connection probe on save (`GET /public_key/` — CHIP's cheapest authenticated-adjacent call, the equivalent of `SupplierController::probeConnection()`'s live `checkBalance()` check), masked display of the stored secret.
7. **`ChipGateway`'s existing container binding swaps its `config('services.chip')` read for a `payment_gateways` DB read**, inside the same `bind()` closure (`AppServiceProvider.php:205-227`) — trivial, since it was already a `bind()` (re-resolved fresh every call), never a `singleton()`; a credential rotated via the new admin screen takes effect immediately, with no app restart, unlike today's `.env`-read behavior.
8. **Cutover is manual, no seed command, no dual-read fallback.** The founder re-enters the already-live `secret_key`/`brand_id`/`base_url` into the new `/middleware` screen once, confirms the probe succeeds, confirms a real request still works — then removes `CHIP_SECRET_KEY`/`CHIP_BRAND_ID` from the Forge dashboard directly (an action the founder performs themselves, not this agent, per this project's own standing rule against an agent touching production secrets/config). No `payment-gateway:seed-from-env` artisan command is built — `Supplier` credentials have never had one either; typing them into the admin form is this project's own established onboarding path, and building a second, only-used-once path is unwarranted complexity.

**PR-B — CHIP settlement reconciliation, fills ADR-083 PR-2 (ships last: largest scope, built exactly as ADR-083 already designed it):**

9. **Unchanged from [ADR-083](./ADR-083-internal-accounting-financial-reconciliation.md) decisions 7 and 8** — `payment_settlements` table, an admin "CHIP Settlements" screen for `.xlsx` upload + match (`openspout/openspout`, keyed on column name not index, iterating every non-"Summary" sheet), the Monthly Accounting Summary screen, and the monthly FX-variance true-up. No redesign — the 2026-09-10 grill (6 rounds/26 questions) already stress-tested this scope, and nothing found this session changes it.
10. **ADR-083's own "Pre-PR-2 verification" step is satisfied, confirmed directly this session, not merely asserted.** A real settlement export from the actual **PekanGame** CHIP account (`settlements-20260919025821.xlsx`, settlement date range 2026-09-07, a single real RM11.00 FPX transaction) was read (`openpyxl`, read-only) and its column set matches what ADR-083 decision 7 assumed: sheet `Summary` (`Settlement Date Range` / `Total Amount` / `Total Fee` / `Total Net Amount`, plus a `Type`/`Acquirer`/`Currency`/`Amount` breakdown table) and one sheet per acquirer — here, `FPX` — carrying `Transaction ID`, `Reference`, `Amount`, `Fee`, `Net Amount`, `Settled On (MYT)`, `Customer Name`/`Email`/`Phone Number`, plus several extra columns (`Type`, `Status`, `Acquirer`, `Payment Method`, `Country`, `Brand ID`, `Paid At (MYT)`, `Description`, `Related To ID`) the parser will simply ignore, keyed as it already was designed to be on column name, not position.

**Rationale:**

- **PR-A** treats CHIP's own documented status vocabulary as authoritative rather than assumed — the original `ChipGateway` docblock's terminal-status claim was written without checking the full spec (this codebase's own repeated "docs alone aren't enough, verify against the raw source" lesson, e.g. ADR-051/ADR-105's build-time corrections) and this ADR closes that gap the same way. `due_strict` moves the "when is this dead" decision from an indefinite wait to an explicit, CHIP-enforced boundary, matching the house 30-minute convention rather than picking a new number.
- **PR-C** treats `Supplier.api_config` as the proven precedent for encrypted-at-rest, admin-editable integration credentials rather than inventing a second pattern — the same reasoning ADR-087 decision 10 already deferred to when it declined to build a bespoke credential store for the Gemini key. Placing the screen under `/middleware` (not `/admin`) keeps integration config physically grouped the same way `Supplier` config already is.
- **PR-B** is unchanged because nothing new was found to change — it closes the loop on ADR-083's only open precondition (a real settlement file to verify against) rather than reopening a design that was already thoroughly grilled.
- Bundling three otherwise-independent concerns under one ADR (rather than three) was the founder's own explicit call, made after this session surfaced the real tension (urgency/risk/precondition mismatch) directly — recorded here so a future reader doesn't mistake the combination for this session's own unprompted scope creep.

**Consequence to track:**

- `due`/`due_strict` (decision 2) is a genuinely new constraint on every CHIP purchase this platform creates, across all four callers — if a real customer is later found completing a legitimate slow bank redirect past 30 minutes (e.g. an unusual FPX bank flow), that's the signal to revisit the window, not evidence the whole mechanism was wrong.
- PR-C's cutover (decision 8) has a real window where `.env` still holds the live secret alongside the new DB row — the founder's own manual removal step is the one that actually closes it; this agent does not touch Forge's environment configuration.
- PR-B's parser (decision 10) was verified against exactly one real settlement file with one transaction on one acquirer (FPX). If a second acquirer (DuitNow QR, `fpx_b2b1`) is ever activated, its sheet's column set should be spot-checked against a real file before being trusted, the same "verify once real, don't assume the shape generalizes" discipline ADR-083 already applied to FPX.
- Update `docs/prd.md` §15 (Payment Gateway row) and §16 (clear the ADR-083 PR-2 backlog line and the parked CHIP-credential-migration line) once each PR ships; `docs/build-log.md` gets one entry per PR.

**PR-B addendum, 2026-09-19 (before any PR-B code, founder's own question while walking the plan) — a real gap in ADR-083 decision 7's original design, not previously surfaced: nothing guarded against re-uploading the same (or an overlapping-date-range) settlement `.xlsx`.**

ADR-083 decision 7 sketched `payment_settlements` as one coarse row per uploaded batch (`expected_*`/`actual_bank_amount`/`status`) but never persisted the *per-transaction* match it describes producing (Transaction ID ↔ `payment_ref`) — so a founder re-uploading the same file, or a second file whose date range overlaps an earlier one, would reprocess the same CHIP transactions a second time, double-counting their `Fee`/`Net Amount` into the "payment processing gain/(loss)" figure the Monthly Accounting Summary (decision 8) depends on. Confirmed a real, not hypothetical, risk — a solo founder manually downloading/uploading weekly `.xlsx` exports (this ADR's own recommended cadence, see the entry's own follow-up discussion) will eventually re-upload or overlap by mistake.

**Fix — a new `chip_settled_transactions` table, additive to decision 7's `payment_settlements`, not a replacement:**
- One row per CHIP transaction actually matched during ingest: `transaction_id` (**unique** — the CHIP purchase UUID, the dedup key), `matched_type`/`matched_id` (polymorphic — `Order`, `MembershipCheckoutAttempt`, or `WalletTopupAttempt`, the three tables that can hold a `payment_ref`/`chip_payment_ref`), `amount`, `fee`, `net_amount`, `settled_on`, `payment_settlement_id` (which batch/upload it was first recorded against).
- Ingest checks this table **before** counting a row toward a new upload's totals: a `transaction_id` already present is skipped (never reprocessed, never double-counted) and reported back in the upload result as "already reconciled, skipped" — separate from the genuine unmatched/exception list decision 7 already describes. This makes re-uploading the exact same file, an overlapping date range, or (in the unlikely case CHIP's own export repeats a row) a duplicate row inside one file all safe by construction, regardless of which of those three caused it — the guard is keyed on the transaction's own identity, never on the upload's date range.
- Matching three tables (not just `orders`), confirmed by grep this session: `orders.payment_ref`, `membership_checkout_attempts.payment_ref`, `wallet_topup_attempts.chip_payment_ref` — a settlement file's `Transaction ID` can belong to any of the three CHIP-charging flows this platform has (retail/affiliate checkout, self-serve membership subscription, self-serve reseller wallet top-up).

Grilled inline (not a separate `/mattpocock-skills:grilling` session — one direct question, one direct answer, founder confirmed immediately) rather than a full multi-round grill, since it's an additive fix to an already-thoroughly-grilled design with no competing alternative seriously in play.

**Also settled in the same walk-through, recorded for completeness (no design change, just decisions that were open):**
- **Recommended reconciliation cadence: weekly**, not daily or monthly — CHIP settles T+1/T+2 (fast enough that a month of unmatched transactions would be needlessly hard to trace back), and daily is disproportionate manual effort for today's low order volume (no CHIP settlement API exists — this is a manual dashboard download every time, decision 7's own Context). Not enforced in code (the upload screen accepts any date range the founder gives it) — an operational recommendation, not a build constraint. The Monthly Accounting Summary (decision 8) is the one hard deadline: reconciled weekly through the month, all matched by the time that month closes.
- **New payment methods (DuitNow QR, `fpx_b2b1`) need no parser code change when activated** — the ingest already iterates every non-"Summary" sheet by name, keyed on column name not position (decision 7's own design). Per the ADR-083 lesson already tracked above (Consequence to track, this ADR's own bullet on FPX), a new acquirer's sheet should still be spot-checked against one real file once it has real transactions — the architecture handles a new sheet automatically, but its exact column set has never been observed.

**Second addendum, 2026-09-19 (same day) — "automatic reconciliation": `status` is now fully computed, never founder-typed. Grilled properly (`/mattpocock-skills:grilling`, 2 rounds, 11 questions) after the founder live-tested PR-B/PR-C in production and hit two real gaps in the manual-bank-figure design in one afternoon: a `variance` status with no visible reason, and no way to re-edit a saved bank figure. Founder explicitly asked to stress-test the fix, not just patch the two symptoms.**

**Context:** SSH investigation into the confusing `variance` (a real settlement, window 2026-09-03→2026-09-19, Expected Net RM145.69 vs File/Bank RM33.14) found the root cause was decision 7's own `expected_*` computation: it summed **every** CHIP-paid order/membership-attempt/wallet-topup whose `paid_at`/`updated_at` fell in the file's calendar date range, regardless of whether CHIP had actually finished settling it (T+1/T+2) by the time the file was pulled — so a large "variance" was the **normal**, expected outcome whenever anything near the window's tail end hadn't settled yet (confirmed: the RM112.55 gap was exactly 2 orders + 1 wallet top-up paid on the file's own last day). Preparing this grill, a second, subtler problem was caught before it was ever discussed with the founder: even after scoping "expected" to only the transactions a file actually contains, comparing at **net** (fee-inclusive) would still show `variance` whenever this platform's own `transaction_fee` assumption differs from CHIP's real MDR fee — but that gap is not an error, it's the exact, legitimate thing "payment processing gain/(loss)" (Monthly Accounting Summary, decision 8) already exists to capture as its own line. Comparing at **gross** (the literal customer-charged amount, which should be byte-identical between this platform's own record and CHIP's file for the same real-world charge) avoids that conflation entirely.

**Decision (grilled point by point):**

1. **`expected_*` → `matched_*`, computed once at ingest, never a calendar-window query.** `payment_settlements.matched_gross_sen`/`matched_fee_sen`/`matched_net_sen` sum ONLY the transactions this specific settlement actually matched (via `chip_settled_transactions`), never "everything paid in the window." Frozen (not recomputed live like `paidButNotSettled()`) — deliberately different from that method's own precedent, because the reason `paidButNotSettled()` must be live (new settlement files arriving later change its answer) doesn't apply here: a settlement's own matched-transaction set never changes after ingest (`chip_settled_transactions.transaction_id` is unique, inserted once, never re-matched), and the underlying local records' own gross amounts (`orders.final_amount`, `*_attempts.total_charged_sen`) are never edited after checkout in this codebase. Frozen is both safe (never stale) and cheaper (the settlements list reads flat columns, no per-row join at list-view time).
2. **Comparison is per-transaction GROSS, not an aggregate NET sum.** New columns on `chip_settled_transactions`: `local_gross_sen`/`local_fee_sen` — this platform's own gross/fee for the matched record, snapshotted at match time (mirrors CHIP's own `amount_sen`/`fee_sen` shape on the same row). `status = 'variance'` if **any** matched transaction's `local_gross_sen` disagrees with CHIP's own `amount_sen` for that same row — never a lump-sum comparison, which could mask two offsetting errors. Exact 0-sen tolerance (all money is already integer sen; a genuine match should be bit-identical, and even a 1-sen gap is worth surfacing, not masking).
3. **`status` becomes fully computed and read-only — never admin-typed.** `UpdatePaymentSettlementRequest` no longer accepts `status` at all; `PaymentSettlementController::update()` can only ever touch `actual_bank_amount_sen`/`variance_note`. `status` values: `pending` (nothing was newly recorded — an empty file, or every transaction already reconciled by an earlier upload), `variance` (any gross mismatch, **or** any unmatched transaction — see the same-day follow-up fix below), `matched` (everything else).
4. **`actual_bank_amount_sen` survives, demoted to a purely optional annotation — founder's own explicit call, not the assistant's.** The assistant's first-pass proposal was to keep it on a monthly cadence tied to when real bank statements arrive; the founder rejected the cadence requirement outright: "CHIP takkan salah transfer ke bank, so far takda pengalaman macam tu" — no experience of CHIP ever misremitting, so a forced recurring bank check has no real payoff for this business today. Final shape: the column stays, admin can fill it in whenever (no reminder, no deadline), it **never** derives `status` and is never required. If CHIP is ever found to misremit in practice, that's the signal to revisit — not a preemptive process built for a failure mode with zero observed incidents.
5. **Race-condition hardening.** The pre-check-then-insert loop in `ingest()` had a real (if narrow) window — two concurrent uploads (a double-click, two admin tabs) touching the same new `transaction_id` could both pass the "not already reconciled" check before either inserted, and the loser would crash on `chip_settled_transactions.transaction_id`'s unique constraint. Now caught via `Illuminate\Database\UniqueConstraintViolationException` (the same driver-aware exception class `OrderFactory`/`VoucherService::redeem()` already rely on for the identical class of problem) and treated as "already reconciled by a concurrent request" — incremented into `alreadyReconciledSkippedCount`, never a 500.
6. **Column rename, not a rename migration.** `expected_gross_sen`/`expected_fee_sen`/`expected_net_sen` are dropped outright and `matched_gross_sen`/`matched_fee_sen`/`matched_net_sen` added fresh — a `renameColumn` would imply "same data, new label," which is false here; the *meaning* changed (matched-subset vs calendar-window), not just the name.
7. **Backfill for the couple of real settlement rows already in production, embedded directly in the migration's `up()`, not a separate manual step.** Judged safe to automate (unlike a real `ledger_entries`/`supplier_ledger_entries` correction) — `payment_settlements`/`chip_settled_transactions` are diagnostic/reconciliation aids derived from other tables, deterministic to recompute, not themselves a source of financial truth. A companion migration adds `chip_settled_transactions.local_gross_sen`/`local_fee_sen` and backfills them for already-matched rows (three simple correlated-subquery `UPDATE`s, one per `matched_type`) *before* the `payment_settlements` migration runs its own backfill, so the ordering is safe. Both run automatically as part of Forge's existing `migrate --force` deploy step (ADR-066) — no manual SSH action needed.
8. **`MonthlyAccountingSummaryService::paymentProcessingGainLoss()` updated to `matched_fee_sen`** (was `expected_fee_sen`) — the only other consumer of these columns, found via a full grep before starting. This incidentally fixes a latent version of the exact same window-scope bug in an already-shipped line item that had gone unnoticed (a transaction not yet settled at month-close would have inflated `expected_fee_sen` there too).

**Same-day follow-up, found live re-testing locally right after this addendum's own first build — before any of it shipped:** a settlement where every transaction was unmatched (a local dev DB with none of the real production orders a real settlement file references) showed a clean `matched` status, since decision 2's gross-mismatch check has nothing to compare when nothing matched at all. This was flagged back to the founder directly rather than silently shipped: an unmatched transaction is real money CHIP reports settled that this platform cannot identify at all — just as serious a reconciliation failure as a gross disagreement, not a lesser, ignorable case. Founder's call: **any unmatched transaction now also flips `status` to `variance`**, alongside a gross mismatch (decision 2 above). `pending` is unaffected (still purely "nothing was newly recorded at all"). The settlement detail screen's own per-row `Tag` colors (orange = unmatched, red = gross mismatch, green = clean match) are what a founder actually uses to tell the two `variance` causes apart once they click in — `status` itself only needs to say "this one needs a look."

**Rationale:** Every decision here traces back to a concrete gap found by actually using the feature the same day it shipped, not speculative hardening — matching this session's own recurring pattern (build, live-test, fix). Gross-not-net (decision 2) is the one genuinely subtle insight: it was caught by the assistant re-reading ADR-083's own rationale before the grill, not by the founder hitting it live, and is exactly the kind of conflation a less careful automatic-reconciliation design would have shipped with a permanent false-positive rate baked in.

**Consequence to track:**
- The optional `actual_bank_amount_sen` (decision 4) still leaves a real, if low-probability, gap: automatic gross-matching only proves this platform's own records and CHIP's file agree with each other — it can never prove the money genuinely reached the real bank account. Acceptable per the founder's own explicit risk call (zero observed CHIP misremittance incidents); revisit if that ever changes.
- `resolveMatch()`'s `Order` lookup now excludes `is_test = true` — a sandbox order's `payment_ref` must never match a real CHIP settlement transaction (sandbox never calls the real gateway, so this is a defensive-only guard, not a fix for an observed bug).
- 6 new/revised backend tests in `SettlementReconciliationServiceTest` (matched-only totals excluding an out-of-file order, sandbox-order exclusion, gross-mismatch → variance, fee-only-difference stays matched, pending-when-nothing-recorded, unmatched → variance) plus updated `MonthlyAccountingSummaryServiceTest`/`PaymentSettlementControllerTest` coverage for the renamed columns and the now-read-only `status`.

### Addendum, 2026-10-04 — one locked seam for every CHIP answer about an order (pre-launch audit item 63)

No design decision changes; this records a consolidation and one behaviour change.
- `OrderPaymentOutcomeService` (`applyPaid` / `applyFailed`) is the only place a gateway's terminal answer about an order is applied. The CHIP webhook and `PaymentReconciliationService` (scheduled sweep and "Check from Gateway") both call it. Before, each carried a copy, read the status unlocked, then wrote; the M-4 and Paid-after-Failed → NeedsReview branches (2026-09-29) were only ever added to the webhook copy.
- Every decision runs under the Order row lock and re-reads the status there. Lock order Order → voucher → membership.
- **Behaviour change:** a non-terminal status (`created`, `viewed` and other unmapped CHIP states → `Pending`) is acknowledged and never written. It used to be able to move a Failed order, whose voucher and quota were already given back, back to Pending, so a later Paid skipped NeedsReview and fulfilled at the discount.
- Wallet top-up and membership attempts: every Failed/Expired write (webhook, both reconcile commands, gateway-call failure) goes through `LeavesPendingOnce::leavePending()`, a conditional update, so a stale answer cannot overwrite Paid.
- Proved by `OrderPaymentOutcomeServiceTest` (the state × answer matrix) and `OrderPaymentOutcomeConcurrencyTest` (Paid vs Failed in two processes).
