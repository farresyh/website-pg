# ADR-098: Digiflazz `rc`-code terminal-vs-retriable classification — `SupplierResponse::$transactionAlreadyFormed`, generic across suppliers

> **Standing (2026-10-09):** In force; decision 6 superseded by ADR-102. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled + built 2026-09-16 (`/mattpocock-skills:grilling`, `feature/digiflazz-rc-terminal-classification`) — see `docs/build-log.md`.

**Context:** Sparked by a real ADR-097 verification incident. Founder placed a real order for `gangstar-mirage-city` (a `zone_id` game, Digiflazz `customer_no_separator=pipe`) — order `PG-JLOMUJ1H23NE`. It failed at `createOrder()` (rc=03 Pending → the reconcile poll's `checkStatus()` got rc=02 "Transaksi Gagal"), **before** ADR-097's per-game separator fix existed, so the `customer_no` sent was almost certainly malformed (concatenated, not pipe-joined) — the founder confirmed with Digiflazz support that the missing pipe was indeed the real cause, which is exactly why ADR-097 was built. Founder tried "Resend Delivery" after ADR-097 shipped. `/middleware/request-logs` showed the outbound request now correctly carried the pipe — but the response still came back rc=02 "Transaksi Gagal", and the response's own echoed `customer_no` field showed the OLD concatenated value, not what was just sent.

**Root cause, found by comparing this order's full request-log history against a second real order, `PG-PYAYMRYNUYV0`** (the very first live CHIP order, 2026-09-02, unrelated to zone/separator — `extra_field=server_id`, no pipe involved): that order failed 3 times with rc=44 "Saldo tidak cukup" (Digiflazz balance), then succeeded on a 4th attempt (same `reference_number`, unchanged) once the Digiflazz account was topped up — rc genuinely changed 44→03→00 across attempts, proving Digiflazz re-evaluated it fresh each time. Gangstar's rc=02 never changed across 3 attempts spanning hours, and its response `customer_no` never reflected the corrected pipe-joined value sent at resend time — proving Digiflazz was replaying an already-stored result, not reprocessing.

**Confirmed against Digiflazz's own docs** (`developer.digiflazz.com/api/buyer/response-code/`, fetched live — not assumed), which is NOT organized around a "permanent/transient" label (a first, looser fetch attempt produced exactly that framing, and it was **wrong** — that was the summarizing tool's own inference, corrected by re-fetching the raw table verbatim before using it for anything). The real, literal column is **"Terbentuk Transaksi"** (Ya/Tidak — "transaction formed/recorded"): `Ya` means Digiflazz's own system already created a transaction record against that `ref_id`, so any resubmit of the same `ref_id` can only return/replay that stored record, never reprocess. `Tidak` means no record was ever created, so a resubmit is genuinely fresh. This maps exactly onto both real incidents: rc=44 (Saldo tidak cukup) → `Tidak` → genuinely retriable, matches `PG-PYAYMRYNUYV0`. rc=02 (Transaksi Gagal) → `Ya` → not retriable via the same `ref_id`, matches `PG-JLOMUJ1H23NE`.

**Facts checked against real code before deciding:**

- ADR-026 already established the exact same *shape* of problem for Gamevion: a `409` resubmit response is normalized to `errorCode='duplicate_reference'`, and `OrderFulfillmentService::fulfill()`'s inline Failure branch (and `attemptLeg()`'s combo counterpart) special-case that literal string to route to `NeedsReview` instead of plain `Failed` — "evidence a prior attempt for this reference_number already reached them, not evidence it was rejected." This ADR generalizes that exact concept across suppliers rather than inventing a parallel one.
- **A real, separate gap found reading the code, not assumed:** `OrderFulfillmentService::finalizePendingDelivery()` — the ONE shared path behind the Digiflazz webhook, the ADR-096 scheduled reconcile poll (`SupplierDeliveryCheckService::checkOrder()`/`checkComboLegs()`), and the ADR-096 admin manual "Check from Supplier" button — has **zero** duplicate-reference-or-equivalent distinction today. Every `Failure` outcome routes to plain `Failed` unconditionally. This is exactly the path Gangstar's real incident went through (`createOrder()` returned Pending, the reconcile poll's `checkStatus()` got the terminal rc=02 and finalized straight to `Failed`) — Gamevion's own `duplicate_reference` fix in ADR-026 never actually reaches this path, because Gamevion never returns `SupplierOutcome::Pending` at all (confirmed: `grep SupplierOutcome::Pending` across both adapters finds it only in `DigiflazzAdapter`) — so this gap has been latent and unexercised for Gamevion, but live and real for Digiflazz.
- `OrderStatusService::markNeedsReview()`'s own transition guard **already** explicitly allows `Pending` as a valid source state (`[Processing, Failed, Pending]`), with its own doc comment citing "ADR-032 decision 6 adds a third: a Pending order too old to safely re-poll... is flagged here too" — the plumbing for calling `markNeedsReview()` from a Pending-origin context already exists and is already proven safe (`ReconcilePendingDeliveriesCommand::checkStalePending()`'s 90-day age-out branch already does exactly this, for a *different* trigger — staleness, not a terminal rc). No collision between the two mechanisms.
- **`ReconcilePendingDeliveriesCommand::flagStaleDuplicateReferences()`** already exists — an ongoing (not one-time) scheduled catch-up: `WHERE delivery_status='failed' AND supplier_response->error_code='duplicate_reference' AND updated_at <= stale threshold`, auto-flagging to `NeedsReview`. This is the project's own established precedent for "a Failed order stuck because of this exact class of unretriable rejection, from before or after the fix shipped, gets caught automatically" — a first draft of this ADR wrongly assumed "no backfill needed, per ADR-026's own precedent" (conflating this with ADR-026's *narrative* text, without having re-read this command's actual body first) — corrected once the real code was checked.
- **A real collision risk, checked before deciding the catch-up's exact shape:** `GamevionAdapter::failureFrom()`'s second branch sets `errorCode` from Gamevion's own response `code` JSON field verbatim (`(string) ($response->json('code') ?? 'unknown')`) — an unbounded, supplier-controlled string. A flat, supplier-unscoped `error_code IN (...)` match against Digiflazz's own numeric rc codes (e.g. `'02'`, `'50'`) risks misclassifying an unrelated Gamevion failure that happens to share the same string. Gamevion's `409` branch (the actual `duplicate_reference` case) is unaffected — that's a literal, hardcoded string, never collides. The 20-code Digiflazz classification must be supplier-scoped wherever it's checked against stored data.

**Decision:**

1. **New, supplier-agnostic `SupplierResponse::$transactionAlreadyFormed` (bool, default `false`)** — a fact about the SUPPLIER's own state ("did they already record a transaction against this reference"), not a business-consequence name like "requiresManualReview." Matches ADAPT-2's existing "canonical shape, business logic decides what it means" split — `OrderFulfillmentService` (not `SupplierResponse` itself) is what decides "if true, route to `NeedsReview`," the same way it already decides what `SupplierOutcome::Success/Pending/Failure` mean.
2. **`GamevionAdapter`'s existing `409`→`'duplicate_reference'` branch also sets `transactionAlreadyFormed: true`** — the exact same real-world fact (Gamevion already has a record for this reference), now expressed through the generic field instead of a Gamevion-only string comparison living in business logic. `errorCode` stays `'duplicate_reference'` unchanged (display/diagnostic value preserved).
3. **`DigiflazzAdapter` gains a private, real-data-sourced rc-code table** (not admin-editable/config — this is Digiflazz's own documented protocol fact, not a business policy the founder tunes), scoped to exactly the codes that are BOTH `Status=Gagal` AND `Terbentuk Transaksi=Ya` (codes that are `Sukses`/`Pending`-status, or that never form a transaction at all, are excluded — they either never reach the Failure branch, or are genuinely retriable): **01, 02, 50, 51, 52, 53, 54, 55, 57, 58, 59, 60, 70, 71, 72, 73, 74, 84, 85, 86** (20 codes). Comment cites the real docs URL so a future session can re-verify if Digiflazz's table ever changes. `submitTransaction()`'s Gagal branch sets `transactionAlreadyFormed` from this table for every rc it sees — reached identically by both `createOrder()` and `checkStatus()` (the same shared method), so the classification applies uniformly regardless of which call produced the terminal rc.
4. **An rc not in the table defaults `transactionAlreadyFormed=false`** (today's behavior: plain `Failed`, resendable) — not a conservative default toward `NeedsReview`. Matches this codebase's existing "fail safe, never fail loud" discipline (e.g. `translateSeparator()`'s own unknown-value fallback) and doesn't invent routing beyond what the real docs currently confirm.
5. **`OrderFulfillmentService::fulfill()`'s inline Failure branch and `attemptLeg()`'s combo counterpart** read `$result->transactionAlreadyFormed` instead of the Gamevion-specific `errorCode === 'duplicate_reference'` string comparison — one generic check, not two supplier-specific ones plus a third new one.
6. **`OrderFulfillmentService::finalizePendingDelivery()` gains the same check, closing the real gap decision above found.** Its signature widens with a `bool $transactionAlreadyFormed = false` parameter; the Failure branch calls `$this->orderStatus->markNeedsReview($locked->delivery_status)` when true, `finalizePendingFailure($locked->delivery_status)` (unchanged) when false. Every caller must thread the real value through: `SupplierDeliveryCheckService::checkOrder()`/`checkComboLegs()` (has the full `SupplierResponse` already, from its own `checkStatus()` call — just needs to stop discarding it down to a hand-built `['error_code' => ..., 'error_message' => ...]` array and pass the flag too) and `DigiflazzWebhookController` (which builds its outcome from the raw webhook payload's `data['status']` alone today, discarding `data['rc']` entirely for this purpose — its own plain-order and combo-leg branches both need to derive `transactionAlreadyFormed` from `data['rc']` via the same table, reusing `DigiflazzAdapter`'s classification rather than a third copy of the code list). **Found at build time, not in the original grill: `finalizePendingDeliveryLeg()` — the exact leg-level counterpart, reached by `SupplierDeliveryCheckService::checkComboLegs()` and `DigiflazzWebhookController::handleComboLeg()` — has the identical gap and needed the identical fix.** Also found: `FakeSupplierAdapter` (the ADR-018 sandbox) constructs its own `SupplierResponse::failure()` from an admin-typed free-text error code — fixed to set `transactionAlreadyFormed: true` when that text is literally `'duplicate_reference'`, preserving the sandbox's existing, already-documented "type duplicate_reference to reach needs_review" testing convention now that routing reads the generic flag instead of the raw string.
7. **`ReconcilePendingDeliveriesCommand::flagStaleDuplicateReferences()` (or a renamed/widened sibling) is extended to also catch a stale `Failed` order whose stored `error_code` is one of Digiflazz's 20 codes** — not just the literal `'duplicate_reference'` string. **Supplier-scoped** (joins/filters on the order's own `supplier_id`/slug, not a bare cross-supplier `error_code IN (...)`) to avoid the Gamevion `code`-field collision risk found above. Reuses `DigiflazzAdapter`'s own code table/classification method as the single source of truth — the command never hand-maintains a second copy of the 20-code list. This closes the gap for orders (like the real `PG-JLOMUJ1H23NE`, if it hadn't already been vouchered) that got stuck `Failed` before this ADR shipped.
8. **Recorded as its own ADR** (not an addendum to ADR-030 or ADR-026) — it reopens ADR-030's 2026-09-03 "no lookup table of rc codes" call with new evidence AND generalizes ADR-026's `duplicate_reference` pattern into a cross-supplier mechanism; an addendum to either alone would leave a reader missing half the picture.

**Rationale:** The generic `transactionAlreadyFormed` field (decision 1) is deliberately not Digiflazz-specific — the founder's own framing during the grill: a future third supplier is a real possibility, and a clean generic signal now costs nothing extra over a second Gamevion-style string comparison, while avoiding a third bespoke check being invented when that supplier arrives. Routing through the exact same `markNeedsReview()` transition (decisions 5/6) rather than a new status keeps this inside the platform's existing money-critical state machine and its existing admin tooling (Issue Voucher, retry-delivery gating on `[Failed, NeedsReview]`) — no new UI surface needed. The 20-code table (decision 3) is grounded in Digiflazz's own literal, machine-readable table column, not a summarizer's inferred "permanent/transient" label — the first fetch attempt produced exactly that wrong inference, caught and corrected before it could drive a design decision, the same fact-discipline this project applies everywhere else.

**Consequence to track:**

- If Digiflazz ever revises its response-code table, decision 3's 20-code list is the thing to re-verify against the real docs URL cited in the code comment — it is deliberately NOT config/admin-editable, so a table change requires a code change, by design (it's protocol fact, not business policy).
- `GamevionAdapter`'s `code`-field collision risk (decision 7) should be kept in mind if Gamevion's own `code` values ever become better-documented — today's supplier-scoping is defensive against an unknown/unbounded string space, not a response to a confirmed real collision.
- The real order that sparked this (`PG-JLOMUJ1H23NE`) is being resolved via Issue Voucher (ADR-004, no cash refund) independently of this ADR — this ADR does not attempt to resurrect it, only to route future/other stuck orders correctly and automatically.
- A genuinely fresh Digiflazz order for the same game/zone (a NEW `reference_number`) was placed and confirmed **Delivered end-to-end** (webhook auto-finalized, review popup fired, storefront voucher-reuse validation correctly rejected an already-used code) — proving ADR-097's separator fix itself works; this ADR is purely about how the platform *routes* a Digiflazz failure it cannot resolve via a same-reference resend, unrelated to whether the underlying fix works.
