# ADR-112: Affiliate/Reseller portal mobile-first redesign — role-aware shell, dashboards, and Orders

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — design and staging implementation complete (2026-09-24). Grilled with the founder over multiple rounds after a live desktop/390px audit of both production portal roles; text wireframes for Reseller Dashboard, Affiliate Dashboard, and mobile Orders were reviewed and approved before this entry. PR1 shell/navigation and PR2 dashboard/Orders presentation are merged to `staging` in PRs #275 and #276. No production release is implied; a `staging`→`main` release remains a separate founder decision.

**Context:** ADR-059 established the Affiliate portal; ADR-072 deliberately put Affiliate and prepaid-wallet Reseller accounts in one `reseller/` app with distinct economics and backend-enforced account-type authorization; ADR-073 owns wallet behavior. The existing desktop screens are usable but leave large empty areas and bury common actions. At 390px, both Orders tables require horizontal scrolling that hides payment/delivery and compensation facts, with no clear affordance. The mobile header calls even an Affiliate session "Reseller Portal"; the mobile drawer remains open after a navigation link is chosen. Reseller's recent Dashboard rows are not links. Affiliate's Dashboard has metrics and subscription state but no recent orders or paths to its daily tasks. These are presentation and navigation problems, not a reason to reopen the economic model or the compensation semantics in ADR-102 and ADR-059's 2026-09-23 addendum.

**Decision:**

1. **One visual system, two task hierarchies.** Retain the shared app, auth boundary, and light/dark modes. The role-aware shell supplies the correct Affiliate/Reseller header. On mobile, use a persistent four-slot navigation bar: Dashboard, Orders, the role's money page (Wallet for Reseller; Earnings for Affiliate), and More. More exposes that role's remaining existing destinations and closes after navigation. Desktop retains a sidebar. This is an evolution of the portal's visual tokens and components, not a full rebrand or an automatic import of the admin-only ADR-104 design system.
2. **Reseller Dashboard:** prioritize wallet balance, a "Top up wallet" link to the existing Wallet page, then a bounded list of recent, clickable order updates and a route to all Orders. The link does not initiate a top-up. No portal order-placement action is invented: Reseller placement remains through API/Bot. Do not call recent orders an exhaustive "needs attention" count.
3. **Affiliate Dashboard:** prioritize withdrawable earnings, the existing **Sales today** and **Sales this month** metrics (their current paid-order definition is unchanged), recent clickable order updates, and links to Withdrawal and Storefront. Wholesale tier and subscription remain visible at lower prominence. Paid sales and withdrawable earnings stay visually and semantically separate; no new chart or revenue series is fabricated.
4. **Orders:** retain the desktop table; on phone render each result as a tappable card with order/game/package, total, date, and separate Payment and Delivery labels. Show the existing role-appropriate compensation fact independently when present (Reseller Wallet Refunded with ledger-backed detail; Affiliate Voucher Issued or Restored). A failed delivery is still `failed`, not a new `refunded` delivery enum. Keep existing server-side filters and Affiliate search. Reseller has no search endpoint, so do not implement a misleading current-page-only search. The card opens the existing order detail. Empty, loading, and error states must be explicit.
5. **Strict frontend-only boundary.** Reuse current tenant-scoped responses and status/compensation markers from the PR #273 work now merged into `staging`; do not alter backend routes, response contracts, payment, ledger, top-up, voucher, delivery, or API-key/Bot behavior. A precise all-orders "needs attention" aggregate and pending-top-up read/resume/cancel flow require separate backend and money-critical design; neither is implied by this UI. The existing one-active-top-up/30-minute behavior and possible second-attempt 422 remain unchanged. Affiliate Earnings ledger order-link work and deep redesign of Wallet, Withdrawal, and Storefront are also outside this first phase.
6. **Sequence:** PR 1 changes only shared portal shell/navigation/header and responsive visual primitives. PR 2 changes the two Dashboards and Orders list presentations using existing API data. Each lands in `staging` through CI and a role-by-role Vercel Preview/browser check; production release is not automatic from `staging`.

**Rationale:** A shared shell prevents role drift without pretending Affiliate profit and Reseller wallet spend are the same business concept. Mobile cards put payment, delivery, and compensation together within one viewport; keeping the desktop table preserves information density where space permits. Existing paginated order responses can supply a bounded recent list, but cannot prove a global exception count. Keeping top-up as navigation avoids introducing a new payment action in a visual redesign. Separating the two PRs limits the blast radius of shell changes before changing data presentation.

**Acceptance criteria before calling the redesign done** (apply the shell-specific checks to PR 1 and the Dashboard/Orders checks to PR 2):

- Verify both account types at 375/390px phone, 768px intermediate, and desktop around 1440px; no page-level horizontal overflow or hidden primary order status on mobile. A bottom bar must not cover the final list item or controls.
- The role label, mobile destinations, active state (including order detail), More/drawer closing, and sign-out remain correct for both account types. Links between Dashboard, Orders, order detail, and the role's money page work by click/tap and keyboard.
- Mobile Orders displays Payment, Delivery, and available compensation as **separate labeled facts** for delivered, processing/needs-review, failed-uncompensated, and failed-compensated examples. A Reseller Wallet Refunded marker reflects only the existing ledger-backed field; Affiliate voucher/restoration information never exposes a voucher code.
- Dashboard values match existing API responses; recent updates have an honest bounded label and never claim to be an exhaustive count. Affiliate paid-sales totals keep the existing meaning and label; no client-side money calculation is introduced.
- Test loading/empty/error states, long game/package names, light/dark contrast, visible focus, and touch targets of at least 44px. Run `reseller/` typecheck, lint, build and relevant frontend tests, then browser-verify both roles on the PR preview; CI green remains the merge gate. No backend or payment regression claim follows merely from a frontend build.

**Consequences to track:** The Wallet pending-attempt UX still can produce the existing 422 if a user starts a second active top-up; solving it safely requires a separate tenant-scoped read/resume/cancellation decision and gateway/webhook review, not a cosmetic button. An accurate cross-order exception counter likewise needs a backend aggregate rather than summing paginated lists client-side. Neither is silently included in this ADR. Record actual shipped state in `docs/build-log.md` and move the §16 backlog item only after both PRs merge and preview verification is complete.

**Implementation note (2026-09-23, PR1 merged):** `feature/adr-112-portal-shell` implements decision 1 and the shell-specific acceptance checks: one role-derived navigation model powers the desktop sidebar and mobile Dashboard/Orders/Wallet-or-Earnings/More bar; the mobile More drawer holds secondary destinations and account controls. The mobile header names the current role, navigation highlights nested order detail, the drawer closes on navigation/Escape, and the tablet breakpoint matches the `lg` layout. PR #275 merged this slice to `staging`; it is not a production release.

**Implementation note (2026-09-24, PR2 merged):** `feature/adr-112-portal-dashboards-orders` adds bounded recent-order panels to both dashboards, responsive Orders cards below the desktop breakpoint, separate Payment/Delivery/compensation facts, and PrimeReact-backed filter/input/button/status primitives for the new presentation. Browser QA against isolated Affiliate and Reseller fixtures passed at 390px and 776px with no horizontal overflow; desktop table rendering also passed. PR #276 merged this slice to `staging`; production release remains separate.
