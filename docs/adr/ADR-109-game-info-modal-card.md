# ADR-109: Game info modal card — customer-facing description/important-notes popup + admin-editable per-game instant-delivery badge

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled 2026-09-18 (`/mattpocock-skills:grilling`, 3 rounds). **Built 2026-09-18** — full backend suite 2119/2119, `admin/`+`storefront/` `tsc`/`eslint`/`next build` all clean, storefront live-verified in a real browser against the local dev DB. See the build addendum at the end of this entry.

**Context:** The founder noticed a real gap on the storefront's `order/[slug]` product page: nothing tells a customer what a game's package actually covers, how top-up works, or any caveat that isn't captured elsewhere (a reference competitor, topagentgames.com, shows this as a modal that auto-opens on page load with bulleted "Important Notes" — e.g. a semi-manual top-up category only processed 10:30am–12am with a 3–10 minute, sometimes-longer window). Separately, `ProductHeaderCard.tsx` hardcodes an "Instant Delivery ⚡ / Average delivery: 1–3 minutes" badge identically for every game — real supplier categories are not all instant (Digiflazz has semi-manual categories), so a false "instant" claim on a slower game is a real customer-trust risk, not cosmetic.

**Facts checked before deciding:**

- `games` table (`create_games_table` + 3 follow-up migrations) has no `description`, no notes/content field, and no delivery-timing field of any kind — confirmed via the model's `$fillable` and every migration touching `games`.
- `ProductHeaderCard.tsx:27-29` hardcodes the literal strings "Instant Delivery" and "Average delivery: 1–3 minutes" — no per-game data backs either.
- `EditGameModal.tsx` is a single flat form today, no tab/pill UI — `admin/src/components/ui/tabs.tsx` (a `primereact/tabs` wrapper) already exists and is proven in production (`/admin/reports`), so no new tab primitive is needed.
- `AffiliateGame` (ADR-060 PR-6) carries only `is_visible` — no per-brand content-override precedent exists anywhere in the Affiliate whitelabel model.
- No locale/i18n switching exists anywhere in `storefront/` (confirmed via grep) — `seo_title_local`/`seo_description_local` are admin-facing bilingual SEO metadata only (ADR-029/042 scope), not a customer-facing language switch. This ADR's new fields are single-language, matching every other customer-facing string in the app.
- `admin/src/components/*/`'s existing content-heavy tabbed modals (`AffiliateFormModal`, `BlacklistHitsModal`) use `max-w-2xl` — the current `EditGameModal` (`max-w-md`) needs widening to match, per the founder's own observation that it's cramped today.
- `ADR-097`'s own doc comment on `EditGameModal` draws the project's standing catalog-vs-supplier-integration line: catalog-display fields belong in `EditGameModal`; supplier-integration config (`validation_rules`) explicitly does not. This ADR's fields are squarely catalog-display, so extending `EditGameModal` (rather than `CheckoutInputEditor` or a new screen) is the correct continuation of that already-drawn line, not a new one. `ADR-042` decision 11 moved SEO fields the *other* direction (out of `EditGameModal`) specifically because SEO is a large, separately-scoped multi-page module — a 4-field addition is not that.
- Checked `AGENTS.md`'s "money is never trusted from the client" rule for relevance: not applicable — nothing here is priced or affects checkout math, purely display copy.

**Decision:**

1. **New nullable columns on `games`** (one additive migration, no backfill needed beyond defaults): `description` (text, nullable), `important_notes` (json array of strings, nullable), `delivery_mode` (enum `'instant'` | `'manual'`, **default `'instant'`**), `delivery_subtext` (string, nullable — **default `'Average delivery: 1–3 minutes'`** at the application layer wherever `null`, so every existing game keeps rendering exactly what it renders today with zero admin action required).
2. **`important_notes` is a plain textarea in the admin UI, newline-separated, split into a string array on save** — not a dynamic add/remove list-row UI. Matches this project's "don't build UI complexity a real usage pattern hasn't demanded yet" discipline (same reasoning ADR-097 decision 6 used for `zone_options`).
3. **`delivery_mode` is a 2-value enum with fixed preset label+icon per mode, not free text.** `instant` → "⚡ Instant Delivery" (existing `Lightning` icon), `manual` → "🕐 Manual Processing" (a new clock-style icon). Admin edits only the **subtext** (`delivery_subtext`, e.g. "1–3 minutes" / "5–30 minutes" / a custom schedule string) — never the badge label itself. Prevents inconsistent/typo'd label wording drifting across games; the enum stays deliberately closed at 2 values since the founder confirmed only these two real cases exist today (extend later only if a real third case shows up).
4. **No "hide entirely" state for the delivery badge.** Every game always renders one of the two modes — reduces state space, matches decision 1's zero-admin-action-required default, and avoids a game silently losing its delivery-expectation info by omission.
5. **Global scope only — no per-Affiliate-brand override.** `AffiliateGame` (ADR-060 PR-6) has no content-override precedent; `description`/`important_notes`/`delivery_mode`/`delivery_subtext` all live on the base `Game` row and render identically across the primary storefront and every Affiliate whitelabel brand. Revisit only if a real Affiliate asks to customize their own copy (a new ADR, not assumed here).
6. **`EditGameModal` restructured into two PrimeReact tabs** (`admin/src/components/ui/tabs.tsx`, the same component already proven at `/admin/reports`): **Basic Info** (today's existing fields — Name, Slug, Category, Reseller Code, Image URL, Active, Player ID Validator — unchanged, just relocated under a tab) and **Content** (this ADR's 4 new fields: Description textarea, Important Notes textarea, Delivery Mode select, Delivery Subtext input). Modal widens from `max-w-md` to `max-w-2xl`, matching `AffiliateFormModal`/`BlacklistHitsModal`'s existing precedent for tabbed, content-heavier modals.
7. **`UpdateGameRequest` gains the 4 new fields** (`description` nullable string, `important_notes` nullable array of strings, `delivery_mode` `Rule::in(['instant','manual'])`, `delivery_subtext` nullable string, max length capped generously e.g. 500) — structural validation in the FormRequest per `AGENTS.md`'s standing rule, no new business-rule branching needed since nothing here is cross-field or DB-dependent.
8. **Storefront (`order/[slug]`) auto-opens the info modal once per page load — literal every visit, no `sessionStorage`/`localStorage` suppression** — matching the reference site's own behavior exactly. Simplest correct behavior for a v1; revisit to session-scoped suppression only if this proves genuinely annoying in real use, not preemptively.
9. **Auto-open is gated on content presence: only fires when `description` OR `important_notes` is non-empty.** Delivery info is not part of this gate (it always has a value per decision 1's default, and is not part of the modal's content — see decision 11) — without this gate, all ~486 existing Digiflazz-synced games (none of which have `description`/`important_notes` set) would auto-pop an empty modal on every single visit.
10. **Manual re-open trigger is gated by the identical presence check as decision 9** — a small "ⓘ Cara Membeli" button rendered only when there's real content to show, placed in `Step1AccountInfo.tsx` beside the existing Verify Account/Continue button (`flex justify-between` — button on the left, Verify/Continue stays right-aligned as today).
11. **Modal content = Description + Important Notes only — delivery info is NOT repeated inside the modal.** The delivery badge already has its own permanent home on `ProductHeaderCard`; duplicating it inside a popup that only sometimes appears would make it the *less* reliable place to find that fact, the opposite of the goal.
12. **`ProductHeaderCard.tsx`'s hardcoded strings are replaced with `game.deliveryMode`/`game.deliverySubtext`**, both flowing through `CatalogController`'s public game-detail response and the storefront's `GameDetail` type (same flat-sibling-field shape `catalog.ts` already uses for `extraField`/`zoneOptions`, per the `publisher` field's own doc-comment precedent: never fabricate a customer-facing value with no real backing column).

**Rationale:** Every structural choice here reuses a seam this codebase already has for the identical job elsewhere — the tab component (`/admin/reports`), the `max-w-2xl` tabbed-modal precedent (`AffiliateFormModal`), the newline-textarea-to-array pattern (ADR-097's `zone_options` reasoning), and the flat-sibling-field catalog shape (`extraField`/`zoneOptions`) — rather than inventing new UI or data-shape conventions. The enum-not-free-text call for `delivery_mode` (decision 3) and the zero-admin-action-required defaults (decision 1) both follow this project's recurring "a new admin capability must never silently change behavior for anyone who hasn't opted in" discipline, most recently applied by ADR-097 decisions 3/7.

**Consequence to track:**

- `docs/prd.md` §16 should gain (then later clear) a line for this once build starts/ships.
- Decision 8's "no suppression, every visit" auto-open is an explicit UX bet — if real usage feedback says it's annoying, that's the signal to add `sessionStorage`-scoped suppression, not a sign the design was wrong.
- Decision 5's global-only scope means an Affiliate whitelabel brand cannot today write its own description/notes for a shared game — track if a real Affiliate requests this; it would need its own ADR (an `AffiliateGame`-level content override), not a quiet extension of this one.
- The `delivery_mode` enum is deliberately closed at 2 values (decision 3) — if a real third delivery-timing case surfaces (e.g. a scheduled-window category distinct from both today's cases), that's a small follow-up decision, not a sign this ADR under-designed.

**Build addendum, 2026-09-18 — one design revision after the founder reviewed a live browser preview, plus two implementation-level details worth recording.**

27. **The modal is centered at every breakpoint, not a bottom-sheet drawer.** The design-preview pass initially reused `RateOrderModal.tsx`'s exact shell (`items-end lg:items-center`, rounded top only on mobile) for visual consistency with the rest of the order flow. The founder reviewed both a desktop screenshot and a real mobile-viewport screenshot and asked for a centered popup with margin on every side instead, at every screen size — `GameInfoModal.tsx` now always renders `items-center` + `p-4` backdrop gutter + `rounded-lg` on all four corners, deliberately diverging from `RateOrderModal.tsx`'s own drawer pattern rather than reconciling the two (no shared-shell requirement was ever decided; they're independently-designed modals that happen to solve different problems).
28. **The trigger button reads "How to Buy", not "Cara Membeli"** — founder's own call, made after being shown the design preview: the rest of the storefront's UI copy is English-only (Instant Delivery, Verify Account, Player ID, etc.), so a lone Malay label read as inconsistent, not localized.
29. **`UpdateGameRequest`'s `delivery_mode` rule is `sometimes`, not `required`.** The Decision section above didn't pin this down explicitly; `required` broke every pre-existing `GameControllerTest` case that PUTs a partial payload without touching the Content tab (the same shape `is_active` already required, but those tests already supplied it) — `sometimes` matches decision 1's own "zero admin action required" principle: a caller not touching the Content tab shouldn't be forced to also resend a delivery mode. The real admin UI's `<select>` always has a value bound to it, so this never weakens real usage, only unblocks partial/API-style payloads.
30. **Verified against the real local dev DB, not just the test suite** — `php artisan tinker` set a real game's (`arena-breakout`) `description`/`important_notes`/`delivery_mode: 'manual'`/`delivery_subtext`, confirmed in a live browser: the badge switched to "🕐 Manual Processing / 5-30 minutes", the popup auto-opened with the description and both notes rendered, and the "How to Buy" button was gated correctly (present only when content exists). Reverted after screenshotting — no lasting change to the dev DB's real catalog data. Storefront's `catalogCache` (`revalidate: 30`) needed a ~30s wait after the tinker write before the new value appeared, same TTL every other catalog read already has — not a bug specific to this ADR's fields.
31. **Admin UI (`EditGameModal.tsx`'s new Content tab) was verified via `tsc`+`eslint`+`next build` only, not a live click-through** — no admin session was available to this Claude session itself (`/admin` sits behind Sanctum login; the Chrome extension only works inside the founder's own logged-in profile, and passwords are never typed by the agent), matching the same gap ADR-108's own build note already recorded for the same reason. Founder's own click-through of `/admin/games` → Edit → Content tab is still owed before this is treated as fully verified end-to-end.

**Addendum, 2026-10-08 — decision 31's gap closed (PRD §16 item 67).** Clicked through in a real browser against the local dev DB, logged in with the seeded dev admin: the Content tab saved description, two notes, Manual Processing and a custom subtext; the reopened modal showed them; the public `GET /api/catalog/games/{slug}` served them at once (catalog cache flushed on save); clearing every field saved back to `null` / `instant`. The original values were restored afterwards. No code change was needed.
