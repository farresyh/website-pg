# ADR-100: Pending Reactivation auto-approve — reverses ADR-015 decision #3's manual-only gate

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`) + built 2026-09-16 (`feature/adr-100-pending-reactivation-auto-approve` → `staging`), same session as [ADR-099](./ADR-099-backup-dump.md).

**Context:** ADR-099's own Pending Reactivation investigation (ruling out the backup-lock theory) surfaced a real founder question: packages land on `/middleware/price-sync`'s Pending Reactivation queue almost every day — is that expected, and should any of it be automated? ADR-015 decision #3 made reactivation deliberately manual: *"require a human for the direction that could silently... act on a possibly-bad signal."* That rationale was tested directly against real data before any redesign, not assumed still valid or still necessary.

**Evidence gathered, all against real production data:**

1. The near-daily 1-4-package trickle (`price_sync_runs.stats->deactivated`, 14-day window) is genuine Digiflazz/Gamevion stock flapping — exactly ADR-015 decision #3's own target case, not a bug.
2. Two real outlier spikes exist in the same window (82 deactivated in one run on 2026-09-12, 13 on 2026-09-13), traced to Digiflazz flipping `status_raw` across 11+ unrelated games/regions in a single sync (`catalog_created=0`, `catalog_pruned=0` — nothing vanished, nothing new) — a platform-wide Digiflazz-side event, not one game's real outage.
3. **A single-snapshot or flat-N-consecutive-sync design would have been unsafe.** Querying `deactivation_logs` directly: several packages flap 9-10 times in a 14-day window (e.g. package IDs 97/106/107/126/320) — genuinely chronic, not one-off. Converting each flap's timestamp to Asia/Jakarta local time showed a hard clustering (package #320: 10/10 occurrences fell in a 20-minute band, 23:40-00:00 WIB) — a real, recurring daily pattern, not noise.
4. **The founder independently recognized this pattern from Digiflazz's own seller dashboard**, which shows a per-product "cutoff time." Digiflazz's own API docs (`developer.digiflazz.com/api/buyer/daftar-harga`, fetched live) confirmed `start_cut_off`/`end_cut_off` ("hh:mm") are real fields in the same `/v1/price-list` response this project already calls hourly — `DigiflazzAdapter::normalizeProduct()` was simply discarding them. This turned "unexplained flakiness" into "Digiflazz's own documented, predictable maintenance schedule," changing the whole design from "wait long enough to trust a noisy signal" to "recognize the schedule and stop treating it as noise at all" for the packages it actually explains.
5. Gamevion showed no comparable spike or clustering in the same window, and its adapter has no cutoff-shaped field to read — the cutoff mechanism below is Digiflazz-only by construction (no field to key off elsewhere), not a supplier config toggle.
6. `deactivation_logs` already exists (ADR-015's own audit trail for `deactivate()`) and gave 14 real days of flap history for free — no backfill needed for the flap-count gate below. No comparable history exists for "was this item continuously active for the last N syncs" (`supplier_products` has only ever held the latest snapshot), so that gate needed new state (`consecutive_active_syncs`).
7. The live Pending Reactivation queue right now is 2 packages (`HOK_GB_16_PG2` — package #320 from the cutoff-pattern evidence above; `MLBB_ID_355_PG1`), not the 53 total currently-`supplier_sync`-deactivated packages (most are still genuinely inactive at the supplier, not yet confirmed active again) — corrected mid-grill after the founder's own dashboard check didn't match an initial mis-framed number.
8. No audit trail exists today for either a manual Approve or a manual Dismiss (`deactivated_reason='admin'` has zero rows in production) — Dismiss has apparently never been used.

**Decision:**

1. **Automate, but gated by two independent triggers, both off by default under one kill-switch.** `config('packages.pending_reactivation_auto_approve')` (env `PENDING_REACTIVATION_AUTO_APPROVE`, default `false`) — Pending Reactivation stays 100% manual (today's actual behavior) until a founder explicitly flips this; a one-line env change either direction, no deploy needed to turn it back off.
2. **Cutoff-window trigger (Digiflazz only).** `ProductSyncService::sync()` now persists `start_cut_off`/`end_cut_off` onto `supplier_products` (`cutoff_start`/`cutoff_end`, raw "hh:mm" strings — carried through a new `SupplierCatalogItem::$cutOffStart`/`$cutOffEnd`, mapped only by `DigiflazzAdapter`). A pending package whose confirming supplier item has usable cutoff data, where the current Asia/Jakarta time falls inside that window (wraparound-aware, e.g. `23:00`-`01:00`), auto-approves **immediately** — no waiting, since Digiflazz's own schedule is the evidence, not a signal this project needs to independently corroborate.
3. **`cutoff_start === cutoff_end` (e.g. Digiflazz's own `"00:00"`/`"00:00"`) is treated as "no real cutoff data," not a genuine instant-midnight window** — ambiguous and unconfirmed against a raw API value during this session (blocked by Digiflazz's own pricelist rate limit), so it falls through to the stability gate below rather than risk silently suppressing a real reactivation. The safe default either way, since the stability gate still catches a genuinely-stable case.
4. **Stability-confirmed trigger (every other case).** Requires `consecutive_active_syncs` (new column, incremented by `ProductSyncService::sync()` each run a row stays `'active'`, reset to 0 the moment it isn't — the one piece of sync history `supplier_products` has ever retained) to reach `config('packages.reactivation_stability_syncs')` (default 2 — roughly 2 hours at the current hourly cadence) AND the package's own `deactivation_logs` count over the trailing `reactivation_flap_window_days` (default 14) to stay at or under `reactivation_flap_limit_per_14_days` (default 2).
5. **A historical flap whose own timestamp falls inside the package's *current* cutoff window is excluded from that flap count** — computed fresh at evaluation time (not stored per-log), so a package like #320 can flap 10 times in 14 days from its own daily cutoff and never once count against the instability limit; only a genuinely unexplained flap (outside any known cutoff window) counts.
6. **New `PendingReactivationAutoApprover` service**, invoked once per supplier from `SyncSupplierPricesJob::handle()` immediately after `PackagePriceSyncService::apply()` succeeds for that supplier — in its own try/catch, deliberately separate from stage 1/2's, so a failure here can never turn an otherwise-successful sync run `'failed'` or drop it out of the run's own success stats (this is best-effort automation layered on top, not part of, the existing two stages).
7. **New `package_reactivation_logs` table/model** (`package_id`, `price_sync_run_id`, `trigger`) — every auto-approval's audit trail. A **sibling** to `deactivation_logs`, not a widened one (a new `action` column there would blur a table whose name and every existing reader assumes means "this row is a deactivation"). A manual Approve via `PendingReactivationController` writes nothing here — this table is scoped to exactly what this class decided on its own, matching decision above's evidence point 8 (no audit trail existed for the manual path either, and retrofitting one is out of this ADR's scope).
8. **Dismiss is untouched and always available**, regardless of what a package would otherwise auto-qualify for — it's a permanent admin override (`deactivated_reason → 'admin'`, stops being monitored at all), a different category from auto-approve's temporary/reversible confirmation.
9. **No new delivery-failure safety net.** If an auto-reactivated package still fails to deliver for a real order, it goes through the exact same failure machinery every other order does (ADR-026/ADR-098's `NeedsReview`/voucher path) — auto-approve only decides whether a package is *offered for sale again*, the same as any package that was never deactivated; nothing in this platform has ever guaranteed delivery success independent of that.
10. **`PendingReactivationFinder::find()` gains an optional `?int $supplierId` parameter** (both the `Package` query and its confirming `SupplierProduct` sub-query, the latter closing a latent, pre-existing cross-supplier `external_ref` collision risk for the new scoped call — `external_ref` is only unique per supplier) — reused by `PendingReactivationAutoApprover` rather than a second, duplicated "what's confirmed active again" query. Every existing unscoped caller (`PendingReactivationController`, `PriceSyncController::stats()`) is unaffected — the parameter defaults to `null`.
11. **The 2 packages already sitting in the live queue at deploy time are deliberately left on the old, fully-manual path** — no retroactive backfill of `consecutive_active_syncs` (no history exists to backfill from) and no special-casing. Only a package deactivated *after* this ships accrues streak/flap data the new gates can evaluate.
12. **Recorded as its own ADR**, not an addendum to ADR-015 — it reverses one of that ADR's explicit decisions with new evidence gathered specifically for this question, the same "new entry supersedes, doesn't silently edit" discipline this log's own header requires.

**Rationale:** The two-trigger split exists because they answer genuinely different questions — a cutoff match means "we know exactly why and when this recovers, no signal-trust question at all," while a stability-confirmed match means "we still don't know why, but it's held steady long enough and hasn't flapped enough recently to trust it anyway." Collapsing them into one flat rule would have meant either trusting a single Digiflazz cutoff-window blip as much as a genuinely unexplained flap (unsafe — decision evidence point 2's 82-package spike is a real example of a single-snapshot signal that shouldn't be trusted), or making every cutoff-driven package wait out a stability window it doesn't need, defeating the whole point of recognizing the schedule. The flap-count exclusion for cutoff-explained history (decision 5) exists because a flat count would otherwise permanently manual-lock the *most* predictable packages (a real, verified failure mode found live against package #320's own data before this design was finalized) — the opposite of what a flap-count gate should protect against.

**Consequence to track:**

- `start_cut_off`/`end_cut_off`'s exact raw value for at least one real Digiflazz product (e.g. `HOK_GB_16_PG2`) was never directly confirmed against a live API response this session — Digiflazz's own pricelist-check rate limit blocked every retry attempt. The founder's own dashboard read (`"00:00"`-`"00:00"` for that product) is consistent with, but doesn't independently confirm, the `cutoff_start === cutoff_end` "ambiguous" handling in decision 3 — worth a live spot-check once the rate limit isn't a concern, though the code's conservative fallback (treat as no-cutoff-data) means an unconfirmed guess here fails safe either way.
- `.env.example` was not updated with `PENDING_REACTIVATION_AUTO_APPROVE` / `REACTIVATION_STABILITY_SYNCS` / `REACTIVATION_FLAP_LIMIT_PER_14_DAYS` / `REACTIVATION_FLAP_WINDOW_DAYS` — outside this session's write scope (`.env.example` is permission-denied to the agent, same standing gap ADR-077 PR-3's build-log entry already recorded for `PRICE_SYNC_INTERVAL_MINUTES`). Founder-owed before flipping the toggle on: the defaults in `config/packages.php` (`false`/2/2/14) apply either way without it — the file just won't self-document them.
- Every threshold here (`reactivation_stability_syncs=2`, `reactivation_flap_limit_per_14_days=2`, `reactivation_flap_window_days=14`) is a first-cut guess reasoned from the one real 14-day window this session had, not tuned against months of data — same "revisit once real cycles produce real data" caveat as `price_swing_threshold_percent` (ADR-025) and `PRICE_SWING_THRESHOLD_PERCENT`.
- The toggle stays `false` until the founder turns it on after reviewing behavior — this ADR does not itself constitute a decision to enable auto-approve in production.

### Addendum (2026-09-24) — drop the flap-count gate, streak-only stability

**Context:** Founder-requested audit of a recurring "70-100 packages pending" complaint. `PENDING_REACTIVATION_AUTO_APPROVE` had been live in production (`=true`) since this ADR's original build, with `REACTIVATION_STABILITY_SYNCS=1`. Live data pulled via SSH:

1. 599 `deactivation_logs` rows in the trailing 7 days; 307 auto-approvals in the same window (302 via `stability_confirmed`, 5 via `cutoff_window`) — the mechanism was working, but a meaningful subset of packages were never reaching either trigger.
2. Of the 162 packages currently deactivated with `deactivated_reason='supplier_sync'`, 81% (132) had `cutoff_start === cutoff_end` (mostly literal `"0:0"`) — the ambiguous case decision 3 above deliberately treats as "no cutoff data," pushing them entirely onto the stability gate.
3. **Direct proof of the bug**: all 11 packages the live queue currently shows as supplier-confirmed-active (Valorant Singapore, 1000/11000 VP and others, package IDs 943-966) had `consecutive_active_syncs=19` (confirmed active ~19 hours straight) but `flap14d=4` — over the old limit of 2 — so every one of them was skipped by `stabilityConfirmed()` every single sync, regardless of streak length. Founder independently confirmed via Digiflazz's own dashboard that these packages were genuinely online. The flap-count gate had no way to age back under its limit while a package kept legitimately (if infrequently) flapping — a rolling 14-day window that, for a package flapping roughly weekly, never clears.
4. This is the same class of failure this ADR's own decision 5 already fixed once for cutoff-explained flaps (package #320) — the flap-count gate remained unsafe for the *un*explained-but-still-eventually-stable case.

**Decision:**

1. **Retire the flap-count gate entirely.** `stabilityConfirmed()` now checks only `consecutive_active_syncs >= reactivation_stability_syncs` — no `deactivation_logs` query, no `reactivation_flap_limit_per_14_days` / `reactivation_flap_window_days` config. Historical flap count no longer disqualifies a package from auto-approval once its current streak is long enough.
2. **`reactivation_stability_syncs` default raised 2 → 3** (`config/packages.php`; prod `.env` to be updated to `3` on the founder's own timeline as a deploy-adjacent step, same as this ADR's original toggle) — the streak requirement is now the only safety margin, since the flap-count layer that previously covered chronic flappers is gone. A single lucky tick still can't pass this gate; three consecutive confirmed-active hourly syncs (≈3 hours) is the new bar for every package, not just previously-under-limit ones.
3. **`deactivation_logs` is untouched as a table** — still written by `PackagePriceSyncService::deactivate()` on every deactivation, still the audit trail for "how often has this package gone offline." It's just no longer read by the auto-approver.
4. **No admin-facing change.** `PendingReactivationController`/`DismissedPackageController` (manual approve/dismiss) were never flap-gated to begin with — this only changes what the automated path will do on its own.

**Rationale:** The founder's framing cut through the original design's own hedge: they were not interested in tuning the flap limit further — they wanted a way to trust "confirmed online right now" that doesn't get vetoed by ancient history. Streak length already *is* that signal (it resets to 0 the instant a row goes inactive, so it can't be gamed by a stale confirmation), and it was already sufficient on its own before decision 4 of the original ADR bolted the flap-count check on as an extra safety margin. Given live proof that the extra margin was actively harmful for the exact "popular SKU with occasional real flaps" case this platform's storefront depends on, and that a genuinely unstable package still can't pass the streak gate on a fluke (it needs 3 sustained hours, not 1 lucky tick), removing it is the more defensible position — not a de-risked compromise, a straight fix.

**Consequence to track:**

- ~~Prod `.env`'s `REACTIVATION_STABILITY_SYNCS=1` (looser than this addendum's new default of 3) needs updating to `3`~~ — **DONE 2026-09-24, settled at `6` instead of `3`.** The founder also raised `PRICE_SYNC_INTERVAL_MINUTES` 60→30 in the same sitting (fresher prices) — since `consecutive_active_syncs` increments once per price-sync run, halving the interval would have silently halved the real-world stability window (3 syncs × 60min ≈ 3h → 3 syncs × 30min ≈ 1.5h) had the streak requirement not moved with it. `6` at the new 30-minute cadence keeps the same ~3h window the founder originally intended. `REACTIVATION_FLAP_LIMIT_PER_14_DAYS` / `REACTIVATION_FLAP_WINDOW_DAYS` in prod `.env` are now dead config — harmless to leave, safe to remove whenever `.env` is next touched.
- `reactivation_stability_syncs=6` is still a first-cut number (founder's own pick from a menu, not months of tuned data) — same "revisit once real cycles produce real data" caveat as the original ADR.
- The cutoff-ambiguity issue (81% of pending packages hitting the `cutoff_start === cutoff_end` fallback) is unchanged by this addendum — those packages still rely entirely on the streak gate rather than the immediate cutoff trigger. Confirming with Digiflazz what `"0:0"`/`"0:0"` actually means (or comparing against a live Digiflazz API response the way the original ADR's own consequence log wanted) remains open, separate work.
