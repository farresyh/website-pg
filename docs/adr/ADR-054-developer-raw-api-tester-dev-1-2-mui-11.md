# ADR-054: Developer raw API tester (DEV-1/2, MUI-11) — typed-DTO editor over the real adapter seam, backend-driven dry-run, production-mode block on `createOrder`

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-28 (grilled via `/mattpocock-skills:grilling`, two rounds, before any code touched)

**Context:** `docs/prd.md` §15 flagged this as the one remaining real gap in the Middleware Panel row (line 1421's own note: "deliberately not bundled into ADR-052's batch — different risk profile: fires raw requests at a live supplier API, needs its own grilling on sandbox-only enforcement / production-mode blocking / its own audit trail"). §6.18/§6.20 spec it thin: DEV-1 says "supplier API tester: check balance, test validate player, test create order with dry-run toggle"; DEV-2 says "raw JSON editor and response viewer, with credentials always masked." MUI-11 is the identical screen — one build satisfies both.

Investigation before grilling found the supporting infrastructure already exists, which shaped every decision below:
- `SupplierAdapter` (`app/Services/Supplier/SupplierAdapter.php`) exposes 5 methods, not the 3 the spec names: `checkBalance()`, `listProducts()`, `createOrder(SupplierOrderRequest)`, `checkStatus(SupplierStatusCheckRequest)`, `validatePlayer(string, ?string)`.
- Credential masking already has a single source of truth: `SupplierConfigSchema::fieldsFor($slug)` classifies each `api_config` key as `text`/`secret`/`boolean`, and `SupplierRequestPayloadRedactor` (ADR-051 decision 4) uses that same classification to redact both headers (`Authorization`, `X-Api-Key`) and body secrets before a request/response payload is ever persisted or displayed.
- Every real adapter call already flows through `SupplierRequestLogger::attach()` (ADR-051) via each adapter's shared `client()` — any call made through the real adapter is automatically logged to `supplier_request_logs`, no new logging path needed.
- Each adapter's credentials are bound server-side from `Supplier.api_config` (encrypted at rest, `hidden` on the model) at container-resolution time — no interface method takes credentials as a parameter, so a caller of `SupplierAdapter` can never see or pass a secret through it regardless of what this feature builds.
- [[feedback_sandbox_flag_leaks_into_health_checks]] (found live during ADR-046): each adapter's own sandbox/testing `api_config` flag behaves inconsistently — `GamevionAdapter`'s `sandbox` flag is a blanket header on every call via its shared `client()`; `DigiflazzAdapter`'s `testing` flag only affects its transaction-submission endpoint, confirmed **not** applied to `checkBalance()`. This is adapter-specific, not a platform-wide guarantee.
- This feature is orthogonal to the existing Sandbox Test Orders screen (`/middleware/sandbox`, ADR-018): that screen tests *this platform's own* order-lifecycle logic against a `FakeSupplierAdapter` that never makes a real network call and always writes a real `Order` row (`is_test=true`). This feature tests *the real supplier integration itself* — real adapters, real (or the supplier's own sandbox) network calls, no `Order` row ever created.

**Decision:**

1. **Expose all 5 `SupplierAdapter` methods**, not just the 3 named in DEV-1's spec text — `listProducts`/`checkStatus` are strictly lower-risk (read-only) than `createOrder`, and a developer tester covering a subset of the actual interface contract would be a worse tool for no safety gain.
2. **The JSON editor edits a typed DTO's fields, never a raw HTTP body sent straight to the supplier.** A `createOrder` test still goes through `SupplierOrderRequest` and the real `GamevionAdapter`/`DigiflazzAdapter::createOrder()` method — the editor changes what populates that DTO, not the wire format underneath it. This keeps `SupplierAdapter` as the stable seam AGENTS.md calls out (extend/use an implementation behind it, don't reshape or bypass it) and guarantees a value that was never validated by anything can't reach a live supplier's API as a raw body.
3. **Dry-run (default ON) means no network call at all** — the backend builds the exact same typed request object the real call would use and returns it as a preview; turning dry-run OFF is what actually dispatches the request through the real adapter. This is evaluated on the backend (not previewed client-side), so the preview is provably the same construction path a real send would use, not a JS approximation of it.
4. **`createOrder` is hard-blocked (not just confirm-dialoged) when dry-run is OFF and the target supplier's own sandbox/testing `api_config` flag is `false`.** The other 4 methods are read-only/side-effect-free from this platform's perspective and may live-fire regardless of the supplier's mode. `createOrder` is the one call with a real financial/order side-effect on the supplier's side, and per decision setup this screen has no `Order` row of its own to reconcile against if a real production order actually gets created by a test — so it's blocked outright rather than trusted to a warning dialog.
5. **`createOrder` test requests get a non-editable, prefixed reference (`DEVTEST-...`)**, never an admin-typed value — keeps this feature's calls unambiguously identifiable on the supplier's own side and structurally incapable of colliding with the real `reference_number` sequence real orders use.
6. **`checkStatus` accepts any admin-typed reference, including a real customer order's** — it's a pure read-only lookup against the supplier directly, useful for support/debugging without going through `/admin/orders`' own detail view.
7. **Real (non-dry-run) calls reuse `SupplierRequestLogger`/`supplier_request_logs` unchanged**, tagged with a `call_type` prefix (e.g. `dev_test_checkBalance`) so they're visibly distinguishable from order-flow-originated calls in the existing `/middleware/request-logs` viewer. No new log table. Dry-run previews are not logged — no network call occurred to log.
8. **The response viewer applies `SupplierRequestPayloadRedactor` to on-screen output**, not only to what gets persisted — a live response containing a secret-derived value (e.g. Digiflazz's `sign`) is masked the same way whether it's being written to a log row or shown directly to the admin who just triggered the call.
9. **A static, per-adapter caveat note is shown next to the sandbox/testing toggle's raw value**, documenting the known scope inconsistency from [[feedback_sandbox_flag_leaks_into_health_checks]] (e.g. "Digiflazz: testing mode does not apply to checkBalance"). A dynamic per-call-type "which mode will this actually run in" oracle was considered and rejected as overengineering for a tool serving 2 adapters today.
10. **New standalone page, `/middleware/developer-tools`** — not folded into `/middleware/suppliers`. The spec (§6.20) already lists MUI-11 as its own page, and its workflow (ad-hoc raw testing across suppliers) is a different concern from that screen's config/CRUD scope.
11. **No new permission tier** — standard `/middleware` admin auth already gates this whole area, and this is a solo-founder operation (AGENTS.md); the risk this tool carries is already bounded by decisions 3/4 (dry-run default, production `createOrder` block), not by who's allowed to open the page.

**Rationale:** Decision 2 is the load-bearing call — "raw JSON editor" could easily have meant a literal pass-through to the supplier's HTTP API, which would have quietly reintroduced exactly the kind of unvalidated-value-reaches-a-live-money-system risk this codebase's other conventions (money computed server-side, FormRequest validation at every mutating boundary) exist to prevent. Tying the editor to the existing typed DTOs gets the "raw" feel (admin sees and can change the exact JSON) without bypassing the one seam (`SupplierAdapter`) this whole integration layer is built around. Decision 4 is the second load-bearing call: unlike the other 4 methods, a real `createOrder` can cost real money or create a real fulfillment obligation on the supplier's side that this platform has no record of and no way to reconcile — a confirm dialog is adequate friction for a mistake, not for an action with an unrecoverable, un-tracked external consequence, so it's blocked structurally instead.

**Consequence to track:** if a third supplier adapter is ever added, decision 9's static caveat note needs a new per-adapter line rather than being assumed to generalize — [[feedback_sandbox_flag_leaks_into_health_checks]] already established this is adapter-specific, not a pattern. If this tool's `createOrder` block (decision 4) is ever found too restrictive in practice (e.g. the founder genuinely needs to test a production `createOrder` once CHIP/Digiflazz go live), revisit it as its own decision then — don't quietly loosen it as a side effect of unrelated work.
