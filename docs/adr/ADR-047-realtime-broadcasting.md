# ADR-047: Realtime broadcasting — Laravel Reverb + Echo, replacing application-level polling (items 1-3 built 2026-08-27, closed at that scope — see addendum)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted, items 1-3 shipped — 2026-08-27 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any code touched; Reverb itself was non-negotiable going in, the grill scoped *how*, not *whether*)

**Context:** A backlog review found five real, independent `setInterval`-based polling loops already live in the codebase: `storefront/src/components/order/OrderStatusTracker.tsx` (customer-facing order/delivery status), `admin/src/app/middleware/price-sync/page.tsx` (Price Sync run status while in-flight), `admin/src/app/middleware/backups/page.tsx` (Backup run status, 3s interval while in-flight), `admin/src/lib/sandboxOrders.ts` (Sandbox order status), and `admin/src/app/admin/page.tsx` (Dashboard System Health, 60s interval, `HEALTH_POLL_MS`). None of these are money-computation paths (pricing/checkout stay server-computed and synchronous, unaffected by this ADR), but the customer-facing one (`OrderStatusTracker`) sits directly in the highest-anxiety moment of a real purchase — waiting to find out if a paid order actually delivered.

Backend is Laravel 13; `predis/predis` and a `redis:7-alpine` container are already provisioned (`docker-compose.prod.yml`, ADR-020 decision #3) but currently cache-only. The storefront is guest-checkout-only (ADR-011, no customer accounts) — any realtime channel design for customer-facing updates has to work without a login/session. `docs/foundation-security.md` has no existing WebSocket/broadcast guidance — this is a blank slate, not a constraint to work around.

**Decision:**

1. **Adopt Laravel Reverb (self-hosted, first-party) + Laravel Echo (JS client)** to replace all five polling loops above — not a subset, all five, converted in one deliberate sequence rather than built simultaneously. Priority order, by proximity to real money/customer risk, not build convenience: (1) `OrderStatusTracker` (storefront, customer-facing), (2) Price Sync run-status (admin, pricing-adjacent), (3) Backup run-status (admin, 3s poll — highest-frequency but lowest-risk), (4) Sandbox order poll (admin, test-only, zero real money), (5) Dashboard health (admin, 60s already tolerable, lowest urgency). Reverb was confirmed non-negotiable by the founder before this grill started; this decision fixes the sequencing, not the choice of tool.
2. **Storefront channel design — public channel, keyed directly by the order's own `order_number`** (e.g. `order.{order_number}`), no new broadcast-authorization endpoint. Safe because `order_number` is generated by `OrderNumberService.php:20` as `self::PREFIX.Str::ulid()` — a 128-bit random value already treated as an unguessable bearer-token-equivalent by the existing unauthenticated `GET /api/track-order/{orderNumber}` endpoint. Broadcasting on an order's own ULID-keyed channel introduces no new trust boundary beyond one that already exists and is already relied on.
3. **Admin channel design — private channels, authorized through Laravel's standard broadcasting-auth route gated `auth:sanctum`**, matching the bearer-token auth every other admin endpoint already requires. No new auth mechanism invented for this.
4. **`OrderStatusTracker` alone keeps a slow-interval polling fallback** alongside its new push subscription — a WebSocket disconnect during a real customer's checkout-wait must never leave them silently stuck with no path to a status update. The other four (admin-only, internal ops tooling) drop polling entirely once converted; a disconnected admin can manually refresh, which is an acceptable degrade for a non-customer-facing screen.
5. **Deployment shape — a new `reverb` service in `docker-compose.prod.yml`** (`command: php artisan reverb:start`, same `build: context: ./backend` as the existing `queue-worker-*` services), reverse-proxied through the **existing** `nginx` entry point on a new path (e.g. `/app`), not a new published port — one TLS/domain surface for HTTP and WebSocket traffic alike, consistent with ADR-020 decision #8's Cloudflare/Nginx setup. Buildable and locally verifiable now, exactly like ADR-020 Phase 1's Dockerfiles/CI — real deployment waits on ADR-020's still-outstanding droplet provisioning, same as every other service already in that file.
6. **`REVERB_APP_ID`/`REVERB_APP_KEY`/`REVERB_APP_SECRET` stay `.env`-only.** These are self-issued values for this app's own self-hosted server, not a third-party vendor credential — they don't trigger the `Supplier.api_config`-style rotation/masking treatment ADR-046 built for actual third-party secrets (Gamevion/Digiflazz), and don't belong in the same future backlog item as the still-open Xendit/CHIP `.env` migration gap.

**Rationale:** Every channel-design choice reuses a trust boundary this codebase already relies on (`order_number`-as-secret, Sanctum bearer tokens) rather than inventing a new one — same "deepen the module, don't reshape the seam" discipline as `ADR-031`/`ADR-034`/`ADR-046`. Sequencing conversion by customer/money proximity rather than build convenience matches the project's established money-path-first discipline (`ADR-014`, `ADR-019`). Keeping a fallback specifically (and only) on the customer-facing screen reflects that this is the one polling loop whose failure mode has a real person waiting on real money, not an admin who can just hit refresh.

**Consequence to track:**
- This ADR records design intent only — nothing is built yet, matching `ADR-018`/`ADR-020`'s own established practice. Update `docs/prd.md` §14/§15 as each of the five conversions actually ships, in the sequence decision 1 sets.
- Decision 1's priority order means `OrderStatusTracker` alone is the minimum viable slice if implementation is ever time-boxed — the other four can ship opportunistically after, similar to the PrimeReact migration's own opportunistic-trigger pattern.
- A future reseller/partner API phase (Phase 2, explicitly deferred per `docs/prd.md` §4.2) would need its **own** private-channel-plus-API-key-auth design if partners ever want push delivery of their own order/webhook events — decision 2's guest-ULID pattern is scoped to storefront guest checkout and does not extend to that use case. Flagged now so it isn't silently assumed to "just work" whenever that phase starts; not a blocker today.
- Decision 5's nginx path choice carries no security exposure beyond what `ADR-020` decision #7 already covers (Cloud Firewall restricted to 80/443/22) — it's a new `proxy_pass` path inside the existing Nginx config, not a new open port.
- This ADR does not touch the queue driver or introduce Horizon/Pulse — see `ADR-048` for that separate (related but independently-scoped) decision.

**Addendum — items 1-3 shipped, item 4 found to not exist, item 5 deliberately left as poll, 2026-08-27 (same day, later session).**

**Built, decision 1's own sequence, items 1-3:**
1. `OrderStatusTracker` (storefront) — `OrderStatusUpdated` event, public `order.{order_number}` channel, fired from a single `OrderObserver` seam (`payment_status`/`delivery_status` change) rather than instrumenting every individual writer (`OrderFulfillmentService`'s three transition methods, both payment webhooks, the reconciliation command, `CheckoutService`'s fully-voucher-covered path — all covered for free). `ShouldDispatchAfterCommit` on the event — every one of those writers updates inside `DB::transaction()`/`lockForUpdate()`, so broadcasting must wait for the real commit, both now (queue driver `database`, same-connection transactional visibility already made this safe) and once `ADR-048` moves the queue to Redis (where it would otherwise not be safe). Decision 4's fallback poll kept, slowed from 5s to 20s. Found and fixed a related bug while reusing `TrackedOrderSchema` for the broadcast payload: its zod `delivery_status` enum was missing `"needs_review"` (ADR-026) — would have crashed parsing for that state on both the poll and push paths.
2. Price Sync run-status — `PriceSyncRunUpdated`, private `price-sync-run.{id}` channel, `PriceSyncRunObserver` on `PriceSyncRun.status`.
3. Backups run-status — `BackupRunUpdated`, one shared private `backups` channel (the screen already refetches its whole list/stats on any change, never tracked one run's fields incrementally, so a per-run channel would have added nothing) — `BackupRunObserver` on `BackupRun.status`.

Both admin channels authorized in `routes/channels.php` against the exact `super_admin` role their own REST routes already require (`routes/api.php`'s `admin.role:super_admin` groups) — no channel grants broadcast access a role couldn't already get through the ordinary API. `admin/src/lib/echo.ts` needed a custom Echo `authorizer` (not the library default): this app has no cookie/session auth at all (ADR-009, bearer-token only), so the authorizer reads the current token fresh from `getClientSession()` on every subscribe rather than assuming a cookie the browser will send automatically. Per decision 4, both admin screens drop polling entirely once converted — an admin who's disconnected from Reverb just sees the page's last-loaded state until they navigate back, an accepted degrade for internal ops tooling that never applies to the storefront.

**Item 4 ("Sandbox order poll") found not to exist.** The backlog research that produced this ADR's decision 1 matched the word "polling" inside a doc comment in `admin/src/lib/sandboxOrders.ts` that says *"no polling needed"* — a false positive from a keyword grep, not a real `setInterval`. `resendSandboxOrderDelivery()` runs synchronously (no queue); there is, and never was, a poll loop on `/middleware/sandbox`. Nothing converted, nothing left undone — this item is simply void.

**Item 5 (Dashboard health) deliberately left as-is, founder's own call.** `DashboardService::health()` turned out structurally different from items 1-3, found only while about to build it: it's a live, uncached aggregate (per-supplier `CircuitBreaker::state()` reads plus time-windowed stale-order counts) with **no discrete write-event to observe** — unlike an `Order`/`PriceSyncRun`/`BackupRun` status column, nothing in the database changes at the moment an order merely *becomes* "stale" by wall-clock time passing, so the `Observer`-on-a-model-write pattern items 1-3 all share doesn't apply here. Converting it for real would need a new scheduled command that periodically recomputes `health()` and broadcasts the result — moving the poll server-side (one shared computation instead of N admin browsers each polling independently) rather than eliminating polling as a concept, a different mechanism from decision 1's own framing of this ADR. Given decision 1 already ranked this item lowest priority ("60s already tolerable, lowest urgency"), the founder chose to close this ADR at items 1-3 rather than build a new mechanism for the one item the ADR itself flagged as least urgent. `admin/src/app/admin/page.tsx`'s 60s poll is unchanged and is the accepted, permanent state for Dashboard health — not a placeholder waiting on a future session.

**Addendum, 2026-09-19 — extends decision 1's admin scope to the Orders screen, closing a founder-reported gap; no new grill.** Founder noticed several admin Orders actions needed a hard browser refresh before their status change was visible — traced to two queued actions (`FulfillOrderJob` via "Retry Delivery", `ResendOrderDeliveryJob` via "Resend Delivery") whose HTTP response is just a "queued" ack, with the frontend never learning about the job's later DB write. This is the exact class of problem items 1-3 already solved elsewhere (a queued/async status change with no push); extending the existing mechanism to a fourth screen is a refinement of this ADR's own scope, not a new decision axis, so it stays an addendum.

1. **Confirmed via code read before any fix, not assumed:** `markDelivered()`/`confirmFailed()`/`refundToWallet()`/`checkSupplier()`/`checkGateway()` are all synchronous and already return fresh state — unaffected. Only `retryDelivery()` (`OrderController.php`) and `resend()` were the fire-and-forget gap. "Resend Delivery" already had a partial client-side mitigation (a bounded 1.5/3.5/6/9.5s poll, `page.tsx`'s old `handleResent()`) that silently gave up if the job's own retry/backoff (up to 60s+) outlasted it; "Retry Delivery" (combo orders) had no mitigation at all — just a static "refresh in a moment" message.
2. **`OrderStatusUpdated::broadcastOn()` gains a second channel, `PrivateChannel('admin-orders')`**, alongside the existing public `order.{order_number}` one — no new event, no new observer call site (`OrderObserver`'s single seam already fires for every relevant write, decision 1's original design goal paying off exactly as intended). One admin-wide channel, not one per order — same "the screen already refetches its whole list on any change" reasoning `BackupRunUpdated`'s own doc comment gives, not `PriceSyncRunUpdated`'s per-run shape. Reuses the existing customer-safe `broadcastWith()` payload verbatim as a pure "order X changed" signal; the admin frontend always refetches its own authoritative data from the REST API, never trusts this payload as a source of truth (it couldn't carry internal fields even if trusted — same payload the public channel gets).
3. **`routes/channels.php`'s `admin-orders` channel is authorized for `super_admin,admin` (both roles)**, not `super_admin`-only like `price-sync-run`/`backups` — mirrors `routes/api.php`'s own `admin.role:super_admin,admin` group on `/api/orders` exactly, per decision 3's own "never grants access a role couldn't already get through the ordinary API" rule.
4. **Admin `orders/page.tsx`: both bounded-poll and fire-and-forget gaps replaced by the same push subscription** — a `pendingStatusWatch` state (`{orderId, action: "resend"|"retry"}`) set when either action is fired, resolved by the new `admin-orders` listener once `OrderStatusUpdated` actually arrives for the currently-open order (refetches it, resolves the matching message, clears the watch). The list itself refreshes on *any* order's change, not just the watched one. Per decision 4, no polling fallback kept — an admin who's disconnected from Reverb sees the page's last-loaded state until they hit "Refresh" or navigate back, the same accepted degrade every other converted admin screen already has.

**Rationale:** `OrderObserver`'s single-seam design (decision 1's original build) is exactly why this cost one `broadcastOn()` line plus one `routes/channels.php` entry instead of a new event/observer — every write path that already broadcasts to the storefront channel (`OrderFulfillmentService`'s transitions, both payment webhooks, the reconciliation command, `CheckoutService`'s voucher-covered path, `OrderResendService`) now reaches the admin channel for free, `FulfillOrderJob`/`ResendOrderDeliveryJob` included.

**Addendum, 2026-09-28 — reconcile-on-resume safety net across all four converted screens, plus two resubscribe races and one silent-broadcast-drop gap found by a full audit and closed; grilled with the founder (`/mattpocock-skills:grilling`) before any code touched.**

**Context:** A founder question ("does everything really need a hard refresh?") prompted re-reading every consumer of decisions 1-4 and both prior addenda end to end, not just the customer-reported symptom (a track-order page stuck on "Failed" after an admin resend later delivered it). Found four real, independent gaps, all downstream of one shared root cause — **no consumer of a push channel ever had a designated moment to reconcile against REST truth once its first subscription was live**, so a missed delivery (a resubscribe race, a backgrounded mobile tab whose WebSocket silently died, or the broadcast job itself failing server-side) had no recovery path short of a hard refresh:

1. `admin/src/app/middleware/price-sync/page.tsx`'s run-status subscribe effect depended on `run?.status` — every status tick made it `leave()` + resubscribe the private `price-sync-run.{id}` channel (a fresh auth round-trip), *including the tick the listener itself had just delivered*. `SyncSupplierPricesJob`'s own two transitions (`queued→running`, `running→success/failed`) mean a fast-failing sync (a supplier outage throwing immediately) can flip straight to `failed` inside that resubscribe's own window — with this screen's polling already dropped per decision 4, that final event had nowhere else to land, sticking the card on "running" forever.
2. `storefront/src/components/order/OrderStatusTracker.tsx`'s poll loop stops entirely once `isTerminal()` (`payment_status===failed` or `delivery_status===failed`) — but `delivery_status=failed` is *not* actually a dead end in this system (`OrderResendService`/`retryDelivery()` can revive it into `delivered`), unlike a genuinely final state such as a compensated/voucher-issued order. From that point on, recovery depended on one WebSocket delivery with no replay and no reconnect-triggered refetch — exactly the founder-reported symptom.
3. `admin/src/app/admin/orders/page.tsx`'s `admin-orders` subscribe effect depended on `orderFilters` — the same resubscribe-on-tick pattern as item 1, triggered by a filter tweak instead of a status change. Lower risk (filter changes are infrequent, manual, and always paired with an explicit refetch) but the same underlying smell.
4. `config/horizon.php`'s `supervisor-price-sync`/`supervisor-backups` both ran `tries: 1` — deliberately correct for the queue's own job (`SyncSupplierPricesJob`/`RunDatabaseBackupJob` each pin `public $tries = 1` at the class level for their own reasons, unaffected by this addendum), but the generic `Illuminate\Broadcasting\BroadcastEvent` job sharing that same queue inherited the same one-shot limit with no override of its own, and no failure of it was ever logged — a transient Reverb hiccup at broadcast time was a permanent, silent drop.

**Decision:**

1. **New shared trigger, `useReconcileOnResume(callback)`** — duplicated as a small hook in both `storefront/src/lib/` and `admin/src/lib/` (two separate Next.js apps, no shared package today; not worth standing up workspace tooling for one ~30-line hook). Fires `callback` on `visibilitychange` turning `visible` (a backgrounded tab's WebSocket may die without ever emitting its own `disconnected` event — `visibilitychange` fires immediately on resume regardless) **and** on Echo's own connection reaching `connected` again (catches a network blip while the tab stayed foreground, which `visibilitychange` never sees). Wired into all four converted screens (storefront `OrderStatusTracker`, admin `price-sync`/`backups`/`orders`) as a pure addition — no existing poll/push logic touched.
2. **Price Sync (item 1) and admin-orders (item 3) subscribe effects fixed at the root** — deps changed to subscribe once per stable id (`run?.id`, or just `session` for the session-wide `admin-orders` channel) instead of on every status/filter tick; both now read the value they used to depend on via a `useRef` inside the listener instead, matching the "a subscription costs nothing while idle" shape `backups`'/`admin-orders`' own original conversions already used elsewhere. This closes the race outright rather than narrowing it — narrowing alone (just dropping the dependency without also adding decision 1's reconcile hook) would still leave the very first subscription's own bootstrap window exposed.
3. **Storefront (item 2) deliberately does *not* get its poll loop revived after terminal.** Considered and rejected: re-adding a client-side "is this order still resendable" check would duplicate `Order::isAlreadyCompensated()`-style business logic that the backend already deliberately owns (`AGENTS.md`'s "money is never trusted from the client" line extends naturally to "resendability" as backend-authoritative state), and would resurrect the exact always-polling pattern this ADR's decision 4 moved away from for terminal/settled orders. Decision 1's reconcile hook is judged sufficient — it recovers the tab the moment the customer returns to it or reconnects, without the frontend needing to know anything about *why* an order might still change.
4. **`config/horizon.php`'s `supervisor-price-sync`/`supervisor-backups` bumped from `tries: 1` to `tries: 3`** (matching `supervisor-orders`), confirmed safe by checking every job on those two queues first — only `SyncSupplierPricesJob`/`RunDatabaseBackupJob` (both pin their own `$tries=1`, unaffected) and the broadcast events share them, so this only gives the generic `BroadcastEvent` job real retries. **New `App\Listeners\Broadcasting\LogFailedBroadcastJob`** (registered on `Illuminate\Queue\Events\JobFailed` in `AppServiceProvider::boot()`) logs when a `BroadcastEvent` job exhausts its retries on `orders`/`price-sync`/`backups` — visibility only (Horizon's own failed-jobs UI already has the full payload), scoped to all three broadcast-carrying queues per the founder's own call rather than just the two that changed `tries` here, since `orders`' `tries=3` was never a guarantee against a real failure either.

**Rationale:** Decisions 1-4 are one root-cause fix expressed as four small, targeted changes rather than three unrelated patches — every gap traced back to the same missing reconcile moment, and closing it once (decision 1) plus removing the two self-inflicted resubscribe races (decisions 2/4) is a smaller, more maintainable surface than bolting a bespoke recovery mechanism onto each symptom individually. Rejecting a storefront poll revival (decision 3) keeps the frontend from re-deriving backend-owned business rules, matching this codebase's existing "deepen the module, don't reshape the seam" discipline (`ADR-031`/`ADR-034`/`ADR-046`) applied here to "resendability" as much as to pricing.
