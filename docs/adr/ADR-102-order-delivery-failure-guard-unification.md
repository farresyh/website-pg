# ADR-102: Order delivery-failure guard unification + Digiflazz `rc`-classification correction + admin refund-clarity UI

> **Standing (2026-10-09):** In force; decision 12 reversed by ADR-108. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`) 2026-09-16. **Phase 1 (decisions 1-2) built + merged to `staging` same day** (PR #225). **Phase 2 (decisions 3-9) built + merged to `staging`** (PR #226). **Phase 3 (decisions 10-13, player/server-ID resend correction + admin refund-info UI) built** — see the 2026-09-16 addenda below. This ADR's own decisions are now fully built; only sibling ADR-103 (combo per-leg reference independence) remains.

**Context:** Founder walked 4 real production orders end-to-end (`PG-CGDZOLEHAIR8`/id 5, `PG-JLOMUJ1H23NE`/id 9, `PG-LXC90WQ8KQFC`/id 12, `PG-HHHRXLG1AR0N`/id 13) while reviewing Digiflazz `rc`-code handling, and found the guard logic around Resend Delivery / Issue Voucher / Refund to Wallet has real gaps a live customer-service hire (not the founder) would not be able to reason about from the UI alone:

1. **`retryDelivery()`/`resend()` (`OrderController.php:189-204,226-238`) guard on `Voucher::where('order_id',...)->exists()` only** — never on a reseller-wallet refund already paid out. Order id 5 is a real prod example: `wallet_refund` ledger entry exists, `delivery_status=failed`, and nothing stops a further resend from delivering the goods on top of the refund already given (double-compensation, real money).
2. **`delivery_retry_likely_futile` (`admin/src/app/admin/orders/page.tsx:385-389`) is warning-text-only** — the Resend/Retry button next to it is never actually disabled, so an admin can click a resend the backend will just reject (or, worse, that just replays a stored Digiflazz result) with no upfront indication it's pointless.
3. **Re-reading ADR-098 against Digiflazz's own docs (`developer.digiflazz.com/api/buyer/response-code/`, re-fetched live this session) found a real modeling flaw in that ADR's own decision 6, not just a UI gap.** ADR-098's 20-code `TRANSACTION_ALREADY_FORMED_RC_CODES` table (`DigiflazzAdapter.php:65-68`) is — confirmed by the live re-fetch — scoped to exactly the codes that are `Status=Gagal` **and** `Terbentuk Transaksi=Ya`. That means Digiflazz has *already told the platform the definitive final outcome* (a confirmed failure) for every one of those 20 codes — there is no genuine outcome ambiguity to route to `needs_review` for. ADR-098's own rationale for choosing `needs_review` over a plain `Failed` (`docs/adr.md:5391`, "keeps this inside the platform's existing... admin tooling... no new UI surface needed") was pure reuse-convenience, not a safety argument — and it actively backfired: Issue Voucher is blocked from `needs_review` (ADR-026 decision 4c), so a confirmed-Gagal order requires an extra manual Confirm-Failed detour before compensation is even possible. `needs_review` should mean "outcome genuinely unknown" (Gamevion's HTTP 409 `duplicate_reference`, which carries no status field at all; or an unexpected exception/timeout where no response was ever received) — not "outcome known, but the same reference can't be resubmitted."
4. **Order 13 (`PG-HHHRXLG1AR0N`) surfaced that `VoucherService::restore()` (ADR-024 decision #7 — restoring a paid-with voucher's balance when the order it paid for later fails and gets its own compensation voucher) has never actually fired in production** (`voucher_redemptions` has exactly 2 rows total; order 13's is still `reserved`). Verified correct by code inspection and existing unit coverage (`VoucherServiceTest.php`) — not a bug, just unproven live, worth flagging rather than silently trusting.
5. **A combo order with one leg landing in genuine leg-level ambiguity while other legs already delivered has no correct resolution path today** — `isPartialComboDelivery()` (`Order.php:131-148`) explicitly excludes any leg at `NeedsReview`/`Pending` from its "clean partial delivery" bucket, so `confirmFailed()`'s guard doesn't block it, and confirming the whole order Failed would compute a full-order-value voucher (`VoucherController.php:225`) on top of legs that already delivered — a real over-compensation path, not yet hit live but structurally present.
6. **Digiflazz's own dedup for an already-formed `ref_id` is keyed on the reference alone, not on what's resubmitted with it** — proven by the real `PG-JLOMUJ1H23NE` incident (a corrected `customer_no` resubmitted under the same `ref_id` still came back echoing the *old* value). A package swap via the existing ADR-017 resend modal therefore does **not** escape an already-formed block either — only a genuinely new `reference_number` does, and `reference_number` is this platform's own generated idempotency key (`ReferenceNumberService`), never Digiflazz's.
7. **No admin path exists to correct a customer-typo'd `player_id`/`server_id` before a resend** — `ResendOrderDeliveryRequest` (`ResendOrderDeliveryRequest.php:27-31`) only accepts `package_id`/`note`; `Order.player_id`/`server_id` have no edit endpoint anywhere in `Admin\OrderController`. A wrong-ID failure today can only be resolved by Issue Voucher + a brand new customer-placed order.
8. **The Order Detail page's voucher/refund information is a single line**, not enough for an admin unfamiliar with the platform's internals to understand at a glance what happened to an order's money — screenshots reviewed during the grill (a richer "Refund Information" card; a small compensation badge next to the delivery-status tag on `/admin/orders`) informed decisions 12-13 below.

**Decisions:**

1. **New `Order::isAlreadyCompensated()`** — true when either a `Voucher` exists for this order (`order_id`) or `wallet_refunded` is true (reusing `OrderController::alreadyRefundedToWallet()`'s existing ledger check, promoted out of the controller so both the pre-check and the actual write path can share it). Every guard that currently hand-rolls `Voucher::query()->where('order_id', $order->id)->exists()` (`retryDelivery()`, `resend()`, `markDelivered()`, `confirmFailed()`) is retrofitted onto this one method. `OrderResendService::assertResendable()`'s own re-check at job-execution time (its docblock already documents "state can change between click and job run") is likewise retrofitted — this closes the exact TOCTOU window that let `PG-JLOMUJ1H23NE` get overwritten back onto `needs_review` after a compensation voucher already existed for it.
2. **A `wallet_refunded=true` order is a hard, no-override block on Resend/Retry Delivery** — same severity as an issued voucher, added to `isAlreadyCompensated()` in decision 1. No admin override exists for this one; reversing an already-paid-out wallet refund is a separate, deliberate accounting action (outside this ADR), never a checkbox on the resend flow.
3. **`delivery_retry_likely_futile` (renamed `deliveryRetryUnsafeWithSameReference` per decision 5's split) now actually disables the Resend/Retry button — scoped so it can't misfire once decision 9 ships:**
   - **Non-combo order:** disable only when `delivery_status === NeedsReview` (and the flag is true). A non-combo `Failed` order always resubmits on a fresh reference (decision 9), so it is **never** futile — the flag must not be consulted for `Failed` at all here, or a perfectly resendable order (e.g. a confirmed-Gagal order now correctly landed on `Failed`) would be wrongly disabled forever.
   - **Combo order:** keep checking the flag regardless of `Failed`/`NeedsReview`, unchanged from today. Decision 9 is explicitly non-combo-only (see decision 9's scope note and ADR-103) — a wholly- or partially-Failed combo still retries on the *same* whole-order reference until ADR-103 ships, so it can still be genuinely futile even while sitting at `Failed`.
   - Either way, an admin can still override, but only via a mandatory free-text reason (logged — this is money-critical, an override needs an audit trail), available to any admin with Orders access (no role tiers exist yet to restrict it further). Copy explicitly states a package swap does not escape this either (per Context point 6) — closes a plausible dead-end an admin could otherwise waste an attempt on.
4. **Reclassify Digiflazz's 20 already-formed `rc` codes: route to `Failed`, not `needs_review`.** This **supersedes ADR-098 decision 6** for exactly this case (ADR-098's text is left untouched, per this log's own "new entry supersedes, doesn't silently edit" rule at the top of this file). `needs_review` is narrowed to genuinely-unknown-outcome cases only: Gamevion's `duplicate_reference` (HTTP 409, no status field to confirm anything) and an unexpected exception/timeout with no supplier response at all. A confirmed-Gagal order reaches `Failed` directly, with Issue Voucher immediately available — no Confirm-Failed detour needed.
5. **`SupplierResponse::$transactionAlreadyFormed` is split into two independent concerns** it was previously conflating: `resendUnsafeWithSameReference` (drives decision 3's button-disable — true for both Digiflazz's 20-code table and Gamevion's `duplicate_reference`) and a new `outcomeConfirmedFailed` (drives decision 4's status routing — true only when Digiflazz's own `status` field is definitively `Gagal`, i.e. the 20-code table; always false for Gamevion, since a 409 carries no status confirmation at all). `DigiflazzAdapter::submitTransaction()`'s `default` (Gagal) branch sets both flags from the same 20-code table; `GamevionAdapter`'s 409 branch sets only `resendUnsafeWithSameReference`.
6. **Every site ADR-098 decision 6/7 already threads `transactionAlreadyFormed` through must be re-threaded onto the split flags from decision 5** — explicit checklist, since ADR-098 itself found call sites missed on the first pass: `OrderFulfillmentService::fulfill()`'s inline Failure branch, `attemptLeg()` (combo counterpart), `finalizePendingDelivery()` + `finalizePendingDeliveryLeg()` (Phase 3b webhook/poll path), `DigiflazzWebhookController` (both its plain-order and combo-leg branches), `SupplierDeliveryCheckService::checkOrder()`/`checkComboLegs()` (reconcile-poll), and `ReconcilePendingDeliveriesCommand` (decision 7 below). Each site's Failure handling now reads `outcomeConfirmedFailed` to choose `Failed` vs `NeedsReview`, and `resendUnsafeWithSameReference` only for the button/futility signal. **`FakeSupplierAdapter`** (ADR-018 sandbox) is added to this checklist too — it already has a `duplicate_reference` free-text convention for `resendUnsafeWithSameReference` (ADR-098 decision 6); it needs a second admin-typed convention to simulate `outcomeConfirmedFailed=true` (a confirmed-Gagal-alike) so decision 4's routing is sandbox-testable without a real Digiflazz call.
7. **`ReconcilePendingDeliveriesCommand` gains a recurring catch-up clause** (not a one-time cleanup script) that reclassifies any existing `needs_review` order whose stored `error_code` is one of Digiflazz's 20 confirmed-Gagal codes back to `Failed` — a permanent safety net against any future misroute (a new bug, a webhook race), not just a fix for today's known-stuck orders (9, 12). Reuses `DigiflazzAdapter`'s own code table as the single source of truth, matching ADR-098 decision 7's existing pattern for the `duplicate_reference` case.
8. **No new per-leg `error_code` column.** Decision 4's reclassification means a combo leg that hits a Digiflazz-confirmed-Gagal code now lands the leg itself on `Failed` (never `NeedsReview`), which already rolls correctly into `isPartialComboDelivery()`'s existing "clean Delivered+Failed mix" bucket — closing Context point 5 as a side effect of decision 4, with no new infrastructure. A leg landing on genuine ambiguity (Gamevion `duplicate_reference` in a combo, or a leg-level exception) keeps today's already-correct `NeedsReview` leg handling, unchanged.
9. **`reference_number` regeneration, scoped by the status a resend is initiated from — a deliberate, narrow exception to ORD-8's "never regenerated" rule, not a reversal of it. Non-combo orders only** (`delivery_legs` empty) **— explicitly out of scope for combo orders, see below and ADR-103:**
   - Resend/Retry initiated from `Failed` (any reason: a confirmed-Gagal code, a genuinely-retriable `Tidak` code like `44`, or a validation failure that never reached the supplier) **always generates a fresh `reference_number`** before resubmitting. Safe because `Failed` (post-decision-4) always means confirmed non-delivery — there is no ambiguity a fresh reference could accidentally double up on. This also makes a package swap (ADR-017) genuinely effective again for these cases, since a fresh reference is never subject to Context point 6's replay behavior.
   - Resend/Retry initiated from `NeedsReview` **keeps reusing the same `reference_number`**, exactly as ORD-8 always specified. This is deliberate, not an oversight: reuse is the actual safety mechanism here — if a genuinely-unknown-outcome order actually did succeed silently, Digiflazz's/Gamevion's own dedup on the *same* reference naturally prevents a real second delivery. Regenerating here would remove that protection.
   - `order_number` (customer-facing) is never affected either way — it is a separate field, never sent to any supplier.
   - No new table needed to track prior references per order — every one is already captured in `supplier_request_logs.request_payload` (ADR-051), queryable per `order_id`, viewable at `/middleware/request-logs`.
   - **Combo orders are deliberately excluded from this decision, kept on today's behavior (always reuse the one whole-order reference, regardless of `Failed`/`NeedsReview`).** Found mid-grill: a combo leg's `ref_id` is `{order.reference_number}-L{n}` — derived from one order-level reference, not independently stored per leg (`DigiflazzWebhookController.php:122-130`'s regex-based parse). A combo can genuinely mix a `Failed` leg (safe to regenerate) with a `NeedsReview` leg (must reuse) at the same time; regenerating the shared order-level reference to help the first would also change the second's, reopening the exact double-delivery risk this decision exists to close. Giving each leg an independently regenerable reference needs its own stored column and a rework of the webhook/reconcile-poll matching mechanism (currently regex-based, would need to become a direct per-leg lookup) — real, money-critical infrastructure serving every combo delivery today, not just this failure-recovery path, so it gets its own dedicated ADR (**ADR-103**, grilled separately) rather than being folded in here.
10. **`ResendOrderDeliveryRequest` gains optional `player_id`/`server_id` fields** (extending ADR-017's existing package-swap pattern with a second, independent correction), letting an admin fix a customer-typo'd ID before resubmitting — closes Context point 7. Structural validation (format) lives in the FormRequest; `OrderResendService` applies the override onto the order before calling the adapter, same place the existing package swap is applied.
11. **Order Detail gains three independent "Refund Information" card variants** (Voucher Used to Pay / Compensation Voucher Issued / Wallet Refund), each rendered only when its underlying fact exists on the order — replacing today's single-line mentions. Two backend gaps need closing first: (a) the voucher **used to pay** for an order (`order.voucher_id`) is not currently eager-loaded or exposed at all in `orderDetailResponse()` (only the compensation voucher relation is) — needs its own eager-loaded relation and fields (code/amount/remaining/status/created_at); (b) `wallet_refunded` is currently a bare boolean — needs the underlying `LedgerEntry`'s `amount`/`created_at` exposed alongside it for the card to show more than a yes/no.
12. **`/admin/orders`' list table gains small badges** (🎫 Used Voucher · 🎟️ Voucher Issued · 💰 Refunded to Wallet) next to the existing payment/delivery status tags, computed from the same fields decision 11 exposes — deliberately **not** new `delivery_status` enum values (status is one axis — "what happened to delivery" — compensation is an orthogonal one, and an order can carry both a "Used Voucher" and a later "Voucher Issued" badge at once; folding them into one enum would explode the value space and fragment every existing `delivery_status`-grouped report/KPI, e.g. ADR-092's cards).
13. **`NeedsReviewBanner` gains one contextual plain-language line** when `resendUnsafeWithSameReference` is true, on top of its existing raw `error_code`/`error_message` display — explaining in plain terms why the button is disabled and that a package swap doesn't help either (Context point 6) — not a full glossary/tooltip system (judged higher-maintenance, more likely to be skipped-over noise than a single line surfaced exactly when it's relevant).
14. **Recorded as its own new ADR, explicitly superseding ADR-098 decision 6** — ADR-098's own text is left untouched (this log's standing rule); a future reader sees both the original reasoning and why it was revisited.

**Rationale:** The guard-logic gaps (decisions 1-3) and the classification flaw (decisions 4-9) share one root cause worth naming: `transactionAlreadyFormed`/`Voucher::exists()`-style checks were each added independently, at different times, for different specific incidents, without ever being unified into "what does 'this order is settled, leave it alone' actually mean end-to-end" — exactly the kind of drift a solo-founder, incident-driven build history produces. Reclassifying the Digiflazz `rc` codes (decision 4) is not a UI nicety layered on top of ADR-098 — it's correcting that ADR's own conflation of "can't resubmit safely" with "outcome unknown," found only by re-reading ADR-098's own cited evidence (the live rc-code table) against what its rationale actually claimed. The reference-number regeneration (decision 9) is deliberately scoped to `Failed`-only, preserving ORD-8's original reuse-on-`NeedsReview` safety property exactly where double-delivery risk is real — this is a narrow, provably-safe exception, not a loosening of ORD-8 across the board. The UI decisions (11-13) exist because this platform's stated goal is to be operable by a future non-technical hire, not just the founder — a badge/card system that mirrors the same underlying facts at both the list (scan) and detail (full picture) level, without inventing new status semantics, is the cheapest way to get there without adding a second data model to maintain.

**Consequence to track:**

- Once decisions 4 and 9 both ship, `resendUnsafeWithSameReference`'s Digiflazz branch (decision 5) can never actually be reached from a **non-combo** `Failed` order anymore — it always gets a fresh reference on resend, which is never unsafe. It stays live for **combo** orders (decision 9 excludes them, deferred to ADR-103) and for Gamevion's `duplicate_reference` on any order shape — so this is *not* dead code to remove, just a flag whose non-combo/Digiflazz branch will simply go quiet until ADR-103 ships. Re-check this note once ADR-103 lands (combo orders get the same fresh-reference treatment then, and at that point the branch genuinely would become unreachable and worth removing).
- **ADR-103 covers combo per-leg `reference_number` independence** — the piece decision 9 explicitly excludes above. Until it ships, a wholly- or partially-`Failed` combo order behaves exactly as it does today (reuse one shared reference, decision 3's combo branch keeps the futile-check regardless of status) — no regression, just no improvement yet for that one order shape.

**Addendum, 2026-09-16 (same session, building Phase 1): found a second, more serious pre-existing gap while implementing decision 1's `isAlreadyRefundedToWallet()`.** `OrderController::refundToWallet()`'s own comment claimed "the ledger reference pair is the structural backstop" against a double refund — checked directly (every migration touching `ledger_entries`) and that's false: there is no unique index on `(type, reference_type, reference_id)`, unlike `vouchers.order_id`'s real unique index backing the equivalent voucher check. Two concurrent `refundToWallet()` requests for the same order could both pass the existence pre-check and both credit — a genuine double-refund, structurally identical to the exact bug class ADR-102 exists to close, just on the other side of `isAlreadyCompensated()`. Fixed the same way `VoucherController::storeFromOrder()` already relies on for its own real backstop: `refundToWallet()` now wraps its check-then-credit in `DB::transaction()` with `Order::lockForUpdate()` acquired first, and `storeFromOrder()` gained the identical lock (it previously relied on the `vouchers.order_id` unique index alone, catching a race only *after* two inserts were attempted, not before) — both now contend on the exact same lock `fulfill()`/`fulfillCombo()`/`markDeliveredManually()`/`confirmDeliveryFailed()` already acquire, so a resend, a voucher-issue, and a wallet-refund on the same order can never race each other into a bad end state. Proven with a new `RefundToWalletConcurrencyTest` (real subprocess race, matching `WithdrawalApproveConcurrencyTest`'s pattern) — exactly one of two simultaneous requests succeeds, exactly one ledger row is ever written. Phase 1 built + verified same session: full backend suite 2044/2044, concurrency suite 16/16 (real MySQL), `admin/` `tsc`/`eslint` clean — see `docs/build-log.md`'s matching entry for the full file list.

**Addendum, 2026-09-29 — automatic recovery instead of NeedsReview for replay-safe suppliers (pre-release review PR-D).** Grilled with the founder (`/mattpocock-skills:grilling`, Q1–Q8, every recommendation accepted).

*Context:* audit fix M-3 routed every genuinely ambiguous outcome (a thrown timeout/connection error, a 5xx, `CIRCUIT_OPEN`) to NeedsReview. Wave 4 K-3 then made the breaker count timeouts. Together these meant that during a Digiflazz slow patch, every order in each 60s cooldown landed in NeedsReview, and an admin had to cross-check each one against the Digiflazz dashboard. The pre-release code review also found three stranded-order paths:
- #1 / #9: a late CHIP Paid on an order whose payment had already been marked Failed stayed `NotStarted`, because `markNeedsReview()` rejected `NotStarted`. It was never flagged, and quota was already restored.
- #2: the M-4 `NotStarted` sweep re-dispatched phase-1 guard failures forever.
- #3: a worker killed mid-call (after M-1's phase 1) left the order at `Processing` permanently. `retryStuckProcessing()` re-dispatched it, but `startDelivery()` rejects `Processing`.

*Decisions:*
1. **Per-supplier replay safety is a protocol fact.** It lives in `SupplierAdapterFactory::resubmitReplaysOutcome()` (Digiflazz only). Digiflazz's `checkStatus()` already *is* a same-`ref_id` topup re-submit, and Digiflazz returns the stored result for a known `ref_id`. Gamevion answers a repeat with `duplicate_reference` and no status, so it stays NeedsReview.
2. **For a replay-safe supplier, an ambiguous outcome goes to Pending, not NeedsReview.** This covers a thrown exception, a Failure with `resendUnsafeWithSameReference && ! outcomeConfirmedFailed` (which includes `CIRCUIT_OPEN`), and a stale `Processing`. It applies to plain orders and combo legs alike. The existing Pending poll re-submits with the same reference; if the first request never reached the supplier, that poll *is* the first send. Confirmed Gagal still goes to Failed (unchanged).
3. **A delayed `CheckSupplierDeliveryJob` fires about 2 minutes after going Pending.** That respects Digiflazz's "don't re-check within 1 minute" and the breaker's 60s cooldown. The 15-minute reconcile stays as the backstop.
4. **Pending ages out to NeedsReview after 2 hours**, measured from when the order went Pending (`updated_at`). A poll that is still Pending or ambiguous never writes to the order, so `updated_at` marks entry into Pending. A resend of an old order therefore isn't aged out on arrival (a small correction to the grill's "from order creation"). Overridable per supplier via `api_config['pending_max_hours']`. The existing 90-day `ref_id` limit stays as the last line.
5. **A Paid webhook arriving after the payment was marked Failed** (voucher and quota already restored) always goes to NeedsReview with an error log, never auto-fulfilment. `markNeedsReview()` now also accepts `NotStarted`. This one rule covers voucher and quota (#1 + #9).
6. **A paid order still `NotStarted` after `FulfillOrderJob` exhausts its tries goes to NeedsReview** (in `failed()`), whatever the cause: a data problem such as a null `supplier_product_ref`, or a compensated order. The M-4 sweep therefore only ever re-dispatches jobs that genuinely never ran, and it skips `is_test` orders.
7. **Stale `Processing` (killed worker) goes to Pending** for a replay-safe supplier and to NeedsReview otherwise. It is never re-dispatched into a transition that can't succeed.
8. **Audit trail:** the automatic choice is recorded in the order's `supplier_response` (and therefore in the ADR-106 attempt row) as an `auto_recovery` note. No new UI.

*Consequence to track:* if Digiflazz ever changes its same-`ref_id` behaviour (their docs say more than 90 days creates a new transaction), decision 1 is the one place to revisit. The 2-hour window is a starting number; tune it from real Pending durations.

**Addendum, 2026-10-05 — a late supplier result after NeedsReview; compensate only on a supplier-confirmed Gagal (PRD §16 item 63, bullet 1).** Grilled with the founder (`/mattpocock-skills:grilling`, Q1–Q15, every recommendation accepted except Q3's override, withdrawn in Q6) plus the money-ADR code-trace pass. Touches ADR-094 (combo roll-up), ADR-096 (Check supplier) and ADR-026's Confirm Failed addendum; recorded here because the 2-hour age-out (decision 4 above) is what opens the gap.

*Context:* reproduced with a real test through the real paths (reconcile command → signed webhook → `confirmDeliveryFailed()`). A Digiflazz order Pending for 2 hours ages out to NeedsReview. A later `Sukses` (webhook or poll) reaches `finalizePendingSuccess()`, which accepts only Pending, so it throws, and the webhook answers `200 already finalized`. The order stays NeedsReview with no SN and no `order_profit` row, though the supplier balance *is* updated from `buyer_last_saldo`. Nothing polls a NeedsReview order, Check supplier refuses it (Pending-only), and Confirm Failed accepts it without asking the supplier. Issue Voucher / Refund to Wallet then compensate an order the customer actually received. Digiflazz has no cancel or void endpoint (buyer API: Cek Saldo, Daftar Harga, Deposit, Topup, Cek Tagihan, Bayar Tagihan, Cek Status, Inquiry PLN), so the late `Sukses` cannot be stopped; only our compensation can wait for the supplier. Combo legs behave the same, and the age-out cascades Pending legs to NeedsReview. Production on 2026-10-05: 0 NeedsReview orders, the 2 orders ever Confirm-Failed were genuine Gagal (rc 55, rc 02), the slowest normal Digiflazz delivery took about 19 minutes. Never happened; it opens on a slow Digiflazz day.

*Decisions:*
1. **A late `Sukses` on a NeedsReview order or leg finalizes it as Delivered** through the existing Success branch: SN, `creditProfit()` (receipt + `order.delivered` reseller webhook), voucher commit, real cost, drawdown. Implemented at the one seam (`finalizePendingSuccess()` accepts Pending or NeedsReview), so the webhook, the poll and Check supplier all get it. Profit comes from the order's stored columns, the same as Pending→Delivered today, so every pricing basis behaves as it already does.
2. **Only NeedsReview, never Failed or PartiallyDelivered.** After decision 4, Failed means Digiflazz itself said Gagal, which is final (Digiflazz refunds the balance on Gagal; a resend from Failed takes a fresh reference, so an old reference's callback 404s). No Failed→Delivered transition, and a reseller never sees `order.failed` followed by `order.delivered`.
3. **Backstop, not a transition:** a supplier result that contradicts a terminal status (`Sukses` for Failed/PartiallyDelivered, `Gagal` for Delivered, e.g. after a wrong manual Mark Delivered) is merged into `supplier_response` as evidence and logged at error level. Status is never changed. No new column or UI unless it actually happens.
4. **Confirm Failed on a replay-safe supplier (Digiflazz) asks the supplier first and applies the answer**, through `SupplierDeliveryCheckService` (the same seam the poll and Check supplier use): `Sukses` → Delivered (decision 1); confirmed `Gagal` → Failed with the admin's note kept; Pending, an ambiguous failure, or an unreachable supplier → refused with a clear message. **No override** (Q6): compensation exists only after the supplier's own final answer; until then the customer waits and the admin re-checks later. Two exceptions, both from facts rather than admin choice: no `reference_number` (the supplier never received it, so a "check" would be a first purchase) and an order older than `max_reconcile_age_days` (Digiflazz treats a `ref_id` over 90 days old as a new transaction). Both confirm without a check and record why. Gamevion (not replay-safe) and sandbox orders keep today's behaviour.
5. **The check may itself deliver.** If Digiflazz never actually received the order, the same-`ref_id` re-submit is the first send (decision 2 above already relies on this). Accepted: the customer paid. The Confirm Failed modal says so.
6. **Check supplier is available on NeedsReview** as well as Pending, with the same cooldown (respects Digiflazz's 1-minute rule). A confirmed `Gagal` there moves NeedsReview→Failed, consistent with `reclassifyConfirmedFailedNeedsReview()` (decision 7 of the original ADR). Because it is the same seam (`finalizePendingFailure()` accepts NeedsReview), a webhook `Gagal` or a poll's confirmed `Gagal` on a NeedsReview order does the same; an ambiguous failure still never moves it.
7. **Combo:** `resolveComboOutcome()` can leave NeedsReview: all legs Delivered → Delivered (profit credited); any leg still NeedsReview → stays NeedsReview (a no-op, not a throw); Delivered + Failed mix → PartiallyDelivered (already allowed). The leg finalize and the roll-up commit in **one transaction**, so a leg can no longer be saved Delivered with its order left behind. Drawdown stays after commit. Confirm Failed on a combo checks every NeedsReview leg (`checkComboLegs()` widened from Pending-only); any leg still Pending refuses, as today.
8. **No package swap from NeedsReview on a replay-safe supplier.** A NeedsReview resend reuses the `ref_id` (ORD-8), so Digiflazz replays the original SKU while the order would record the new package's profit, and a late `Sukses` for the original SKU would be rejected as `sku mismatch`. Same-package Retry stays; swap from Failed (fresh reference) stays.
9. **A re-submit's Gagal confirms only for a formed transaction (correction, found in the local browser check).** Decision 4 trusted "confirmed Gagal", and ADR-102 decision 5's broad form treated *any* `status: Gagal` as confirmed. Digiflazz's own rc table (developer.digiflazz.com/api/buyer/response-code, re-fetched 2026-10-05) marks each Gagal code "Terbentuk Transaksi" Ya or Tidak. A "Tidak" code (40–45, 47, 49, 56, 61–69, 80–83, 87, 88: IP, signature, saldo, rate limit…) rejected *this request* before Digiflazz looked at the `ref_id`. On a first submit that is a real answer (nothing exists for that `ref_id`); on a re-submit — `checkStatus()`, or a `createOrder()` reusing a stored reference (a NeedsReview retry, `SupplierOrderRequest::$resubmit`) — it says nothing about the original transaction. Live proof: the local browser check had an un-whitelisted IP, Digiflazz answered `Gagal, rc 45` to every call, and Check supplier and Confirm Failed both failed NeedsReview orders. Rule: on a re-submit, Gagal confirms only for a code in `TRANSACTION_ALREADY_FORMED_RC_CODES` (the existing 20-code table, re-verified identical to the docs), minus the rate limits 85/86 that Digiflazz marks "Ya"; anything else is an unknown outcome (Confirm Failed refuses, the poll leaves it, a retry parks it Pending per decision 2 of the 2026-09-29 addendum). A first submit is unchanged. This also closes a pre-existing path: a Pending order's poll answered `rc 45` (e.g. during an IP change; production logged one `rc 45` resend attempt) used to go to Failed.
10. **Not built:** continued polling of NeedsReview (Q4: the webhook plus decision 4 close the only money path; add if admins start seeing delivered NeedsReview orders), automatic clawback of compensation (Q2: decision 4 makes it unreachable for Digiflazz).

*Consequence to track:* a Digiflazz outage now blocks Confirm Failed for its duration; if that ever strands a customer too long, revisit decision 4's no-override rule rather than adding a bypass. Re-check decision 2 if Digiflazz ever documents a Gagal→Sukses transition.
