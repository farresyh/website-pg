# ADR-103: Combo order per-leg `reference_number` independence

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`) 2026-09-16. **Built + merged to `staging` 2026-09-17** (PR TBD, branch `feature/adr-103-combo-leg-reference`) — all 9 decisions, full backend suite (2071/2071) + concurrency suite (17/17, real MySQL, including a new leg-level finalize race test) green, migration applied to the local dev DB.

**Context:** ADR-102 deliberately excluded combo orders from its "regenerate `reference_number` on resend-from-`Failed`" fix (decision 9), because a combo leg's `ref_id` is not independently stored — it's derived on the fly as `{order.reference_number}-L{leg_number}` and parsed back out of an inbound webhook by regex. A combo order with one leg genuinely `Failed` (confirmed-Gagal, safe to give a fresh reference) mixed with one leg genuinely `NeedsReview` (ambiguous, must reuse) cannot be handled correctly under that scheme — regenerating the one shared order-level reference to help the first leg would also change the second leg's reference, reopening the exact double-delivery risk ADR-102 decision 9 exists to close.

**Facts gathered before deciding anything** (sub-agent investigation, not assumed):

- `order_delivery_legs` (`2026_09_15_100200_create_order_delivery_legs_table.php:31-44`) has no reference-related column beyond `supplier_reference` — a nullable string populated only *after* a call, from the supplier's own returned reference, not the idempotency key sent *to* them.
- Exactly 3 code sites touch the `{reference_number}-L{n}` format: `OrderFulfillmentService::attemptLeg()` (`:354`, constructs it) and `SupplierDeliveryCheckService::checkComboLegs()` (`:142`, also constructs it — both derive it fresh, deterministically, on every call) construct it; `DigiflazzWebhookController` (`:128`, `preg_match('/^(.+)-L(\d+)$/', ...)`) parses it back. `finalizePendingDeliveryLeg()` itself never touches the string — it receives an already-resolved `OrderDeliveryLeg` model.
- `retryDelivery()`/`FulfillOrderJob` are order-level only, with zero per-leg branching in the controller or job — every bit of per-leg iteration and outcome-handling already lives one layer down, inside `OrderFulfillmentService::fulfillCombo()`/`attemptLeg()`. No per-leg admin route exists today (`routes/api.php:520-540` are all `{order}`-scoped).
- **Production has exactly one combo order that has ever existed** (order id 7), 2 legs, both `delivered` cleanly — no leg has ever sat at `Pending`/`NeedsReview` for any length of time, and none currently do. This is a structurally-real gap, not yet a live incident — informed decision below to build it now anyway (small scope, cheap while context is fresh) rather than defer to "when it actually breaks."

**Decisions:**

1. **New `order_delivery_legs.reference_number` column** (nullable string, **unique index** — it becomes the real idempotency key for this leg, same property `orders.reference_number` already has). Backfilled for every existing leg with the value the old derived formula would have produced (`{order.reference_number}-L{leg_number}`) — identical to what the regex parse already resolves to, so no in-flight webhook/poll match changes for historical data.
2. **New `order_delivery_legs.resend_unsafe_with_same_reference` column** (nullable boolean) — the leg-level twin of ADR-102 decision 5's `resendUnsafeWithSameReference`, populated the same way (from the supplier response `attemptLeg()`/`finalizePendingDeliveryLeg()` already receive) whenever a leg lands on `NeedsReview`. **Not** a second rc-code table — ADR-102 decision 8 already established leg-level `Failed`-vs-`NeedsReview` classification needs no new lookup table; this is a narrower, orthogonal need — telling apart a genuinely-futile `NeedsReview` leg (Gamevion `duplicate_reference`) from a genuinely-worth-retrying one (an exception/timeout with no response at all), the same distinction ADR-102 decision 3 already makes at order level.
3. **`attemptLeg()`'s reference selection mirrors ADR-102 decision 9, at leg granularity:** leg `not_started` (first-ever attempt) generates and stores `{order.reference_number}-L{leg_number}` — unchanged from today's value, just now persisted instead of re-derived; leg currently `Failed` generates a **new** reference and overwrites the stored one; leg currently `NeedsReview` reuses the stored reference unchanged. Same safety reasoning as ADR-102 decision 9 — `Failed` (post ADR-102 decision 4) always means confirmed non-delivery for that leg, `NeedsReview` means genuinely unknown and reuse is the double-delivery protection.
4. **Regenerated leg references append a short ULID suffix, not a sequential attempt counter:** `{order.reference_number}-L{leg_number}-{ulid}` — collision-safe by construction, no new "attempt count" column needed to number them. Every reference a leg has ever used remains fully queryable via `supplier_request_logs` (ADR-051) regardless.
5. **`checkComboLegs()` (the reconcile-poll and admin "Check from Supplier" path) becomes read-only with respect to the reference** — it reads the leg's currently-stored `reference_number` instead of re-deriving one, and never writes a new one. "Check status" means asking about an attempt already made; only `attemptLeg()` (the retry path) ever mints a new reference.
6. **`DigiflazzWebhookController` drops the regex parse entirely**, replaced by two direct lookups: `Order::where('reference_number', $refId)` first (plain order, unchanged), then `OrderDeliveryLeg::where('reference_number', $refId)->with('order')` if the first misses (combo leg, now a direct column match). A hygiene win independent of the money-safety fix — a brittle string-format parse is replaced by an indexed lookup.
7. **No per-leg admin UI.** The single combo-wide "Retry Delivery…" button (ADR-017) is kept exactly as today — it fires `fulfillCombo()`, which independently applies decision 3's fresh-vs-reuse rule to each outstanding leg under the hood. An admin never needs to reason about individual legs.
8. **The combo-wide futile/disable treatment (ADR-102 decision 3's "combo order" branch) is retired and folded into the same rule as non-combo, via an OR-rollup**: the Retry button is flagged unsafe-to-click-blindly if **any** outstanding leg's `resend_unsafe_with_same_reference` is true — since one click retries every outstanding leg together, one unsafe leg is enough to warrant the same disable+mandatory-override-reason treatment ADR-102 decision 3 defined. This is the point ADR-102's own "Consequence to track" flagged as needing a fold-back once this ADR ships.
9. **Single-release deploy** (migration + code together, no staged rollout) — safe specifically because production currently has zero legs in `Pending`/`NeedsReview` (verified live, not assumed), so there is no in-flight state the migration could strand mid-transition. Revisit this call if combo volume grows enough that a future migration of this shape can no longer assume an empty in-flight set.

**Rationale:** This closes a structurally-real gap with a small, contained change (2 new columns, 3 already-identified call sites, no new admin surface) rather than deferring it indefinitely — the founder's own call, given the actual build scope turned out smaller than the initial "webhook-matching mechanism rework" framing implied once the facts were in. Keeping the fix scoped to exactly the sites already touching the derived string (not a broader combo-delivery refactor) matches this project's standing discipline of extending an existing seam rather than reshaping it. The read-only/write split for check-vs-retry (decisions 3 and 5) exists because conflating them was silently fine only by accident — both computed the same deterministic value, so it never mattered that "check status" was implicitly also "regenerate the request"; the moment references become independently stateful, that conflation would have quietly broken semantics no one intended to change.

**Consequence to track:**

- Needs the same subprocess-based concurrency proof this project's other lock-guarded money-critical writes carry (per `backend/AGENTS.md`) — two concurrent calls racing a leg's `reference_number` write (an admin retry racing an in-flight webhook/poll finalize) is exactly the kind of scenario `finalizePendingDeliveryLeg()`'s existing `lockForUpdate()` already guards for the status write; decision 3's new reference write needs to sit inside that same lock, proven the same way.
- `FakeSupplierAdapter` (ADR-018 sandbox) needs a leg-level equivalent of ADR-102 decision 6's testing convention, so decision 2's `resend_unsafe_with_same_reference` is sandbox-testable per leg, not just per order.
- Order id 7 (the one real combo order) needs no backfill action beyond decision 1's blanket backfill — both its legs are already `Delivered`, so nothing about its historical references will ever be read again by the new lookup paths.
- Revisit decision 9's "safe because zero in-flight legs today" reasoning once real combo volume exists — this ADR does not set up any ongoing monitoring for that, the same gap ADR-102 noted for its own Cloudflare-tier revisit trigger.

**Addendum, 2026-09-17 (built).** All 9 decisions built on `feature/adr-103-combo-leg-reference` (off `staging`), full backend suite green (2071/2071) plus the concurrency suite (17/17, real MySQL). Notable build-time findings not obvious from the design above:

- **Decision 3's reference persist needed its own crash-safety fix, found by an EXISTING test.** `attemptLeg()`'s reference write sits inside the SAME `DB::transaction()` as the supplier call — a thrown exception (the 2026-09-15 resilience addendum's own scenario) rolls that write back along with everything else, so the outer `catch (Throwable $e)` block's separate recovery transaction (marks the leg NeedsReview) now also re-persists the reference, captured into a variable by reference before the inner transaction runs so it survives the rollback. Without this, `test_retrying_a_leg_that_previously_threw_completes_the_order_normally` (an existing ADR-094 test) failed — a leg that landed on NeedsReview via the exception path lost its reference on the next retry.
- **Decision 2's flag is written ONLY when a leg actually lands on NeedsReview**, not on every Failure — re-read literally ("populated ... whenever a leg lands on NeedsReview") after an initial draft wrote it on every Failure branch. A plain-Failed leg never needs it: decision 3 always mints it a fresh reference on retry, so it can never be the kind of futile decision 8's rollup exists to catch.
- **Decision 8's OR-rollup is scoped to NeedsReview legs only**, not "every outstanding (not-yet-succeeded) leg" as an early reading of the decision text suggested — a Failed leg is never genuinely futile (decision 3), so including it in the rollup would have produced false positives. `Order::resendUnsafeToOverride()`'s combo branch now reads `deliveryLegs->where('status', NeedsReview)->contains(...)`.
- **New leg-level concurrency test added** (`OrderDeliveryLegFinalizeConcurrencyTest` + its `app:order-delivery-leg-finalize-test-finalize` test-only command) — two concurrent `finalizePendingDeliveryLeg()` calls on the same leg (duplicate webhook), proving the leg's own `lockForUpdate()` (already used by ADR-094 for `status`) also serializes decision 2's new column write. The order-level lock proven by `OrderFulfillmentComboConcurrencyTest` already fully serializes any admin double-click retry before it ever reaches the leg loop, so this was the one genuinely new race surface worth a dedicated proof.
- Several existing tests (`DigiflazzWebhookControllerTest`'s combo fixtures, `SupplierDeliveryCheckServiceTest`'s combo test, `CheckSupplierDeliveryJobTest`'s combo fixtures, `OrderManualCheckTest`'s combo test) had to start setting `reference_number` explicitly on their hand-built `OrderDeliveryLeg` fixtures — decision 6's direct-lookup webhook resolution and decision 5's read-only `checkComboLegs()` both now depend on that column actually being populated, which a real `attemptLeg()` call always does but a bare test fixture didn't.
- Migration applied to the local dev DB (`php artisan migrate`, plain, not `:fresh`) — zero existing `order_delivery_legs` rows there, so the backfill was a no-op locally; verified the backfill logic itself via the full test suite's combo fixtures instead.
