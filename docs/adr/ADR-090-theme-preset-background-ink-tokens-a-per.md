# ADR-090: Theme preset background/ink tokens + a per-affiliate Site Mode (light/dark), the first slice of ADR-081's pinned dark-mode requirement

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled + built 2026-09-11.

**Context:**

The founder compared PekanGame's 4 non-default theme presets (ADR-081) against several competitor top-up sites' own dark themes and found the difference stark: switching preset on PekanGame barely changed the page, while the competitors' dark themes visibly flipped the *entire* page (background, cards, borders — not just accent colours).

A code read found the exact cause: `storefront/src/lib/theme-presets.ts`'s `THEME_PRESETS[x].tokens` only ever defined Material-3 **accent** tokens (`--color-primary`/`secondary`/`tertiary`/`warning` + their container/on-* variants) — the tokens that colour buttons, badges, and borders. `storefront/src/app/globals.css` defines `--color-surface`, `--color-surface-container*`, and `--color-ink` (page background, card backgrounds, text, the neo-brutalist 2px border colour) exactly once, on bare `:root`, and no preset's `tokens` map — nor `generateThemeCss()` — ever touched them. Every preset was structurally incapable of recolouring the page background, in light mode or otherwise; this was true before "dark mode" ever entered the conversation.

ADR-081 itself already named the adjacent gap and pinned a hard requirement on whoever opened this ADR: *"Dark mode is still a separate future ADR... presets today define light `:root` tokens only... future ADR MUST add a `tokensDark` variant per preset — dark mode is not allowed to collapse every brand back onto one identity."*

Grilled over two rounds. Round 1 settled: "dark mode" means a **per-affiliate fixed choice** (an affiliate picks Light or Dark for their whole storefront, every visitor sees the same thing) — not a viewer-side `prefers-color-scheme`/toggle mechanism; and that the surface/ink token promotion is worth doing as its own fix regardless of dark mode, since it's the actual root cause of the founder's complaint even in light mode. Round 2 settled the shape: Site Mode as an **independent control** from Color Preset (not 10 combined named options), scoped to build `tokensDark` for `default` only now (hand-authoring a dark palette per preset is design time, not engineering time — the other 4 stay backlog), and the primary brand gets no Site Mode toggle at all (founder: primary stays on its current colours/mode permanently).

**Decision:**

1. **All 5 existing presets get `--color-surface`, `--color-surface-container-lowest/low/DEFAULT/high/highest`, `--color-on-surface`, `--color-on-surface-variant`, `--color-ink`, `--color-outline`, `--color-outline-variant` added to their `tokens` map**, hand-picked to tint the whole page in the preset's hue family (e.g. `bumblebee` gets a pale warm-yellow surface, not the neutral base cream) — the direct fix for "preset barely changes the page," independent of any dark-mode work. `default` is untouched (its `tokens` already equals the `globals.css` base, so `generateThemeCss` keeps short-circuiting to `""` for it in light mode).
2. **A new `theme_mode` column** (`affiliate_branding.theme_mode`, string, default `light`) is a per-affiliate fixed choice, resolved and injected server-side exactly like `theme_preset` already is — not a viewer preference, not `prefers-color-scheme`. Validated `in:light,dark` in `UpdateBrandingRequest`.
3. **`ThemePreset` gains an optional `tokensDark`.** Only `default` has one today — a hand-authored dark counterpart of the base palette (near-black surfaces, light `--color-ink` so the neo-brutalist 2px border stays visible against a dark background, accent colours kept close to their light values since they already read well on dark). `generateThemeCss(preset, mode)` picks `tokensDark` when `mode === "dark"` and the preset actually has one; a preset without a dark palette silently has no dark option surfaced, rather than falling back to its light palette on a brand flagged dark.
4. **The reseller portal's `ThemeTab.tsx` gets a "Site Mode" control** (Light/Dark buttons) independent of the Color Preset picker, disabled for Dark on any preset without a `tokensDark` (with an explanatory note), and its live preview panel now reads the selected mode's actual tokens (surface/ink included) instead of the portal's own static `bg-surface`/`border-ink` classes — so the preview genuinely shows what the storefront will look like, not just accent-colour swatches.
5. **The primary brand gets no Site Mode toggle** — stays permanently on `light` (the migration default), matching the same "primary doesn't change colours" decision `[ADR-089](./ADR-089-brand-asset-pipeline.md)` made for its logo panel.

**Rationale:**

- Fixing the surface/ink token gap is the actual root-cause fix for what the founder saw in production — a preset that can't touch the background was never going to feel impactful regardless of dark mode. Doing it as a light-mode fix first, decoupled from dark mode, means every existing brand on a non-default preset benefits immediately without waiting on a full dark-mode build.
- A per-affiliate fixed Site Mode (not a viewer toggle) matches how `theme_preset` already works and needs no new client-side state/persistence mechanism, no FOUC-avoidance machinery, and no `prefers-color-scheme` media-query plumbing — it's the same server-resolved-token-injection seam, one more axis.
- Scoping `tokensDark` to `default` only, with the UI honestly hiding Dark elsewhere rather than silently degrading, follows ADR-081's own "hand-authored, no automated invert" principle without blocking the whole feature on hand-crafting 4 more palettes up front.
