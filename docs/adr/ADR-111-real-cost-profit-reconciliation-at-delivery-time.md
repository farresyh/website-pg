# ADR-111: Real-cost profit reconciliation at delivery time — widens ADR-033's FX conversion boundary to a second call site

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`, 2 rounds, 8 questions) 2026-09-21/22, sparked by a real production incident investigated live via SSH. **Built 2026-09-22, decisions 1-9 exactly as decided below, no design changes made mid-build. 🟢 LIVE PROD, flag enabled, verified against a real delivered order same day.** Feature-flagged (`config('services.real_cost_reconciliation.enabled')`) — capture (decision 2) runs unconditionally on every delivery; only whether it's USED to recompute `platform_profit` (decision 3) is gated. Founder set `REAL_COST_RECONCILIATION_ENABLED=true` in Forge before the `staging`→`main` release (PR #266); confirmed live via SSH against real order `PG-4VPQQFOLJQQ1` (Digiflazz, delivered 2026-09-22 06:45:53 UTC) — `real_cost_price_sen=360`, `cost_basis=real`, `platform_profit=36` exactly matches `selling_price(396) − real_cost(360) − affiliate_profit(0)`.

**Context:** Founder ran a real production test of the Combo Package feature: order `PG-B2BL0G1YDMVS` (3× 60UC = 180UC combo). The first delivery attempt failed at Digiflazz's internally-assigned seller (`@Csmgs`/MGS); the founder switched the product's seller on Digiflazz's own dashboard to `@Excellentstoreid` and retried. The retry succeeded — genuinely at a **higher real per-unit price** (confirmed directly from raw `SupplierRequestLog` response payloads: `price: 15394` IDR for the failed MGS attempt vs `price: 15634` IDR for the successful Excellentstore retry, both under the identical `buyer_sku_code: PUBGG_60_PG1` — Digiflazz's own internal seller routing is entirely opaque to this platform; only the response `price` field reveals it moved).

Investigation (not assumption) traced the actual numbers: `resolveComboOutcome()`'s reconciliation (ADR-107 decision 2) read `componentPackage->cost_price` — **355 sen** — a value confirmed via `price_change_logs` to be the *stale, pre-sync* catalog price still in effect at the moment of delivery (13:56), because the next scheduled Price Sync run didn't catch the real price move until **14:00:32**, four minutes later, updating the catalog to **360 sen**. Direct math confirms which seller each catalog value actually reflects: `15394 IDR × 0.00023 (the FX rate in effect) ≈ 354.06 → 355 sen` (the failed MGS attempt's price) and `15634 IDR × 0.00023 ≈ 359.58 → 360 sen` (the successful Excellentstore attempt's real price). **The reconciliation literally used the failed seller's price, not the seller that actually delivered the order** — not a rounding quirk, a wrong-source-of-truth bug. Resulting `platform_profit` (108 sen) overstated the true figure (~93 sen) by 15 sen on this RM11.73 order — small here, but the same mechanism scales with order size and could produce a materially larger, silently-wrong profit figure on a bigger combo.

Confirmed via the real `supplier_ledger_entries` drawdown rows that the actual money-owed-to-supplier tracking is already accurate (correctly recorded -15634 IDR per leg, the real Excellentstore price) — the bug is narrowly in the *reported* `platform_profit` figure, the same "real cash is fine, reported margin is wrong" shape ADR-105 and ADR-107 both already found and fixed once each, in different mechanisms. This is that same bug's third occurrence, in a third mechanism.

**Scope discovered during the grill, wider than the triggering incident:** this codebase has exactly one place profit ever gets reconciled against a live cost figure post-checkout — and in all three cases (`OrderResendService::resend()`'s package-swap formula, `OrderFulfillmentService::resolveComboOutcome()`'s combo residual, and the plain non-combo retry path, which has **zero** reconciliation at all today, not even a stale one) the live figure read is `Package.cost_price` — a catalog snapshot on its own Price Sync cadence, never the real per-transaction price the supplier actually charged. The plain-retry gap is arguably worse than combo's: `OrderFulfillmentService::fulfill()`'s non-combo success branch never touches `platform_profit` at all once an order leaves checkout — a same-package retry (server hiccup, no swap) that costs more or less at the supplier leaves the checkout-time estimate frozen forever, with nothing to correct it, ever.

**Decision:**

1. **Extract `ProductSyncService::toMyrSen()` (currently `private`) into `CurrencyRateService::convertToSen(?float $price, string $fromCurrency): ?int` (new `public` method)** — same formula, unchanged (`round($price * 100)` for MYR, `ceil($price * rate * 100)` for IDR, protecting margin by rounding cost up, matching ADR-033's own established convention). `ProductSyncService` calls this instead of its own private copy (removes the duplication, doesn't add any). This is deliberately a **widened boundary, not a second one**: `CurrencyRateService` was already the one class that owns FX-rate knowledge; it now serves two call patterns (Price Sync's catalog conversion, and this ADR's delivery-time conversion) through the exact same method, not two divergently-evolving copies of the same formula.

2. **Two new nullable columns capture the REAL price at every point a delivery outcome becomes final with a real price known:** `orders.real_cost_price_sen` (non-combo) and `order_delivery_legs.real_cost_price_sen` (combo, per leg). Written at all **four** call sites where a real price is genuinely known, found by enumerating every path that can mark a delivery Delivered — not just the two obvious synchronous ones:
   - `OrderFulfillmentService::fulfill()`'s plain Success branch (synchronous, non-combo)
   - `OrderFulfillmentService::finalizePendingDelivery()` (async resolution — Digiflazz `rc=03` later confirmed via webhook/poll, non-combo)
   - `OrderFulfillmentService::attemptLeg()`'s Success branch (synchronous, combo leg)
   - `OrderFulfillmentService::finalizePendingDeliveryLeg()` (async resolution, combo leg)

   Each converts `$result->data['price']` (or the async equivalent) via `CurrencyRateService::convertToSen()` and stores it alongside the existing status/reference updates in the same `update()` call — no extra query, no extra transaction.

3. **One basis-agnostic residual formula, reused everywhere, formula shape unchanged from ADR-105 decision 8 / ADR-107 decision 2 — only its cost INPUT changes:** `platform_profit = selling_price (frozen) − real_cost_price_sen (or Σ real_cost_price_sen across legs, for combo) − affiliate_profit`. `affiliate_profit` and `selling_price` are **never** touched by this correction — whatever checkout or `OrderResendService::resend()`'s own per-basis formula (Standard/Member/Affiliate/ResellerWallet) already determined for those two fields stays exactly as-is; only `platform_profit` absorbs the gap between what was assumed and what was actually paid. This is why the fix is basis-agnostic without needing basis-specific branches: it was already the exact principle ADR-105 decision 8 established to make combo/non-combo share one formula, now extended to also make first-attempt/retry, and catalog-cost/real-cost, share the same one. **Reseller Wallet orders carry the most exposure** — per the platform's own economic model (PRD glossary), a Reseller Wallet order's entire markup surfaces as `platform_profit` (its own `affiliate_profit` equivalent is always 0 by construction), so any cost drift here is not split with anyone, it hits reported platform margin in full.

4. **Applies to EVERY successful delivery, not just retries.** A first-ever delivery has the same drift exposure as a retry (the queue dispatch → actual supplier call gap, however short, is still a real window a Price Sync run can land inside) — restricting this to "retries only" would leave the more common case (a clean first-attempt delivery) still silently trusting a catalog estimate. Confirmed cheap enough to justify the wider net: see decision 6.

5. **`OrderResendService::resend()` needs no code change of its own for this fix.** It already sets `affiliate_profit` correctly (per its own per-basis formula) *before* calling `fulfill()`; decision 3's new unconditional correction inside `fulfill()`'s success branch automatically re-derives `platform_profit` from the now-known real cost immediately afterward, using the `affiliate_profit` `resend()` already set. The admin's existing override-reason (ADR-105 decision 4, required when the pre-attempt catalog estimate would sell below cost) **stays valid without re-approval** — it represents the admin's willingness to accept a loss, not agreement to one specific number; a more accurate final figure only refines that number; it doesn't retroactively invalidate the decision to proceed.

6. **Reuses the already-warm FX cache — confirmed safe for a queued, async workflow, not a live-fetch-per-order risk.** `CurrencyRateService::rate()`'s `Cache::remember()` (TTL ~12-24h) means a delivery-time call is a cache read in the overwhelming common case (same shared cache key Price Sync itself populates), not a live HTTP call — verified by reading the implementation, not assumed. `FulfillOrderJob`/`ResendOrderDeliveryJob` already run on a Horizon queue worker, never the customer-facing request/webhook thread (ADR-014), so even the rare cold-cache live-fetch (5s timeout, capped) never blocks a customer. Exception path: `CurrencyRateService::lastKnown()` only throws when literally no rate has ever been stored for that pair — caught, falls back to today's existing catalog-cost behavior for that one delivery (`real_cost_price_sen` stays null), logged, **never blocks delivery** (matches ADR-107 decision 3's own "never block" commitment, now the standing rule for every fulfillment path, not just combo).

7. **Visibility signal widens from combo-only to universal, and from negative-only to a calibrated drift threshold.** Today's `combo_profit_reconciled_negative` (derived, `platform_profit < 0`, combo-only) is replaced by a general `profit_reconciled_negative`-style signal that (a) still always fires on any negative result, any order type, and (b) additionally fires when `real_cost_price_sen` differs from the catalog-based estimate the order would otherwise have shown by **more than RM1 AND more than 1% of `selling_price`** (both conditions, not either — a flat sen threshold alone under-protects a large order; a percentage alone over-fires on a small, normally-volatile one). Persisted (not log-only): a boolean/derived-but-materially-different signal needs a value to persist past the reconciliation moment for Order Detail to keep showing it on a later view, not just a `Log::warning()` line an admin would need to go hunting for.

8. **Feature-flagged rollout, config-gated, default-on only once verified.** This is the largest blast radius of anything decided this session — it changes `platform_profit` computation for every future successful delivery in the system, not a scoped subset. `config('services.real_cost_reconciliation.enabled')`, checked once at the top of the shared correction logic — a single-line kill switch if something is found wrong live, without a code revert/redeploy. Not this codebase's usual pattern (it rarely uses flags), but justified here by blast radius alone.

9. **Explicit per-`pricing_basis` test coverage required at build time — Standard, Affiliate, Member, ResellerWallet — not inferred from decision 3's reasoning alone.** The residual formula's basis-agnosticism is a reasoned conclusion from ADR-105 decision 8's own already-accepted design, not yet empirically re-verified against this specific new code path. Build session must not consider this done until all four have a real, green test case.

**Rationale:** The same lesson ADR-105 and ADR-107 already each drew once (a reported profit figure decoupled from the real cost actually incurred) recurs a third time because the underlying root cause was never actually fixed, only patched per-mechanism: `Package.cost_price` is a *catalog* concept (accurate for pricing the *next* sale), reused as if it were also a *transactional* concept (what *this specific* delivery cost) — the same category error ADR-106 already named for mutable status columns being asked to also serve as history, just applied to price instead of state. The fix widens ADR-033's single conversion boundary rather than reopening it ad-hoc per call site (which would have meant three-plus divergent, duplicated FX-handling implementations) — one shared method, four write sites, one residual formula, matching this project's own "deep modules, stable seams" discipline (`OrderFulfillmentService` is a named seam; this ADR deepens it, doesn't reshape its interface for external callers).

**2026-09-22 addendum — "Cost Price + Cost Basis," founder-caught before merge, not a new numbered ADR.** Reviewing the build, the founder correctly caught that `real_cost_price_sen`'s introduction created two problems this entry's own decisions didn't address: (1) Order Detail's "Cost Price" card still shows the old catalog `cost_price`, so with the flag on `Platform Profit` no longer reverse-calculates from what's on screen; (2) `/admin/orders`'s CSV export — the documented order-level P&L source of truth — would gain a second, competing cost column, ambiguous to an auditor.

Fix: `Order::effectiveCostPriceSen()`/`costBasis()` — one cost figure per order, not two. Reverse-engineers which cost input actually satisfies the stored `platform_profit`'s own residual formula, rather than trusting whether `real_cost_price_sen` is merely non-null (it's captured unconditionally regardless of the flag — decision 2 — so presence alone is a false signal for "was it used"). Three basis values: `real`, `mixed` (combo only — some legs real, one or more fell back to catalog), `estimated`. Wired into both Order Detail (new `effective_cost_price`/`cost_basis` fields, a Real/Mixed tag next to Cost Price) and CSV export (same reconciled figure, new "Cost Basis" column) — one shared helper, so `Selling Price − Cost Price − Affiliate Profit` always equals `Platform Profit` in both places, for every row.

Also closed at the founder's explicit request: decision 9's per-`pricing_basis` coverage requirement, re-verified for COMBO specifically (the original build only proved it non-combo) — 4 new tests confirm `resolveComboOutcome()`'s aggregation holds `affiliate_profit` untouched across Standard/Affiliate/Member/ResellerWallet combo orders too.

9 new tests total, full backend suite 2228/2228 green, Pint/tsc/eslint/build clean. Same PR (#265), not yet merged.
