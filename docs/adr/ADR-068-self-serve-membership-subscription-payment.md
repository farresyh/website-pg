# ADR-068: Self-serve membership subscription payment — customer pays for a tier through the CHIP checkout, membership auto-created on webhook (ADR-027 Phase 7, payment half)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-03, grilled with the founder this session via `/mattpocock-skills:grilling` (17 questions over three rounds), before any code touched. **Design only — no code exists yet.** Completes [ADR-027](./ADR-027-vip-membership.md)'s deferred "Phase 7" — the **payment half only**; the WhatsApp renewal-reminder half stays deferred, vendor still unpicked. Reuses the CHIP `PaymentGateway` seam (ADR-001 / ADR-022 / `backend/AGENTS.md`) and the `MembershipFeeService::recordFeePaid()` single-seam that ADR-027's 2026-08-29 Phase 6.5 addendum (decision Q12) built for exactly this caller. Folds in two member-identity-correctness fixes surfaced by the first real production member order `PG-PYAYMRYNUYV0` (see the secondary section).

**Context:**
- Consumer VIP Membership (ADR-027) shipped Phases 1–6.5 and is live in production with the dual kill switch ON since 2026-09-03. Everything works **except** a customer cannot buy a membership themselves: the only code path that creates a `memberships` row is the admin `POST /api/admin/memberships/record-payment` action → `MembershipFeeService::recordFeePaid()`, a manual stopgap. `/membership`'s verified-but-no-membership state shows an honest "Subscription plans are coming soon." placeholder (`storefront/src/components/order/MembershipClient.tsx`).
- The CHIP payment rail is proven end-to-end in production with real money (order `PG-PYAYMRYNUYV0`, 2026-09-03): CHIP hosted page → `success_callback` to `/api/webhooks/chip` → signature verified against the live `GET /public_key/` → order flipped `Paid`.
- `PaymentGateway` (interface) + `ChipGateway` are **not** coupled to the `Order` model — `createPayment(PaymentRequest)` takes a generic `referenceId` + `amountSen` + `description` + optional `PaymentCustomer`, no Order lookup, no amount cross-check inside the gateway. But `ChipWebhookController` **is** Order-coupled: it resolves `Order::where('payment_ref', $event->paymentRequestId)->first()` (matches on the CHIP purchase `id`, stored in `orders.payment_ref` — not the `reference` field), returns 404 if none, and every downstream branch operates on `$order`.
- `MembershipFeeService::recordFeePaid(int $resellerId, string $email, int $planId, int $amountSen, int $adminUserId, ?string $reason, string $idempotencyKey): Membership` already does create / extend / reactivate / plan-change in one `DB::transaction()` (`lockForUpdate` on the membership row once it is guaranteed to exist), books a `membership_fee` ledger **credit** (owner `('platform', null)`), and is idempotency-key'd against `membership_fee_records.idempotency_key` (fast-path pre-check + unique-index serialization, two distinct constraint recoveries). Its docblock states outright: "a future real payment flow's webhook calls this exact same method, so the manual and automated paths can never drift apart." `$adminUserId` is currently a non-nullable `int`; `membership_fee_records.admin_user_id` is already a nullable column.
- The membership session token (`MembershipSessionTokenService` — 30-day, `APP_KEY`-encrypted, stateless, no DB row) embeds `reseller_id` + `email` only — **no plan id**. `GET /api/membership/plans` is deliberately anonymous, cached (60s, tagged), and narrow: `{name, fee_sen, discount_percent}` only — no `id`, no `quota_sen` (ADR-055 decision 3).
- Brand is always resolved server-side via `Reseller::primary()` (ADR-060 will later swap this for `Host` resolution); the storefront never sends a brand or `reseller_id`.
- Missed-webhook recovery for orders is `ReconcilePendingPaymentsCommand` — its query is `orders`-table-coupled, gateway-generic via the factory keyed on `orders.payment_gateway`.
- `ReportService::membershipBreakdown()` computes `membership_fee_revenue` as `Σ ledger_entries WHERE type = 'membership_fee'` in the report window (by entry `created_at`) — source-agnostic.
- During order `PG-PYAYMRYNUYV0` the founder, logged in as member `faris9745@gmail.com`, mistyped the checkout contact email as `farres.work1019@gmail.com`. The order priced correctly at member rate (member detection is by Bearer token, not the typed email) but `orders.customer_email` stored the typo, and `MembershipController::orderHistory()` matches strictly `where('customer_email', $verifiedEmail)` — so the real member's `/membership` dashboard showed no orders and the unrelated email's would.

**Decision (each point grilled this session):**

*Scope*

1. **v1 covers new-subscribe, renew, and upgrade/downgrade — all self-serve.** Admin `record-payment` stays as the manual fallback (free/waived memberships via its zero-amount-with-reason path — ADR-027 Phase 6.5 Q13 — and promo lump sums). The three self-serve flows share one mechanism: pick a plan → pay its fee → `recordFeePaid()` with that plan. **No proration.** A mid-cycle upgrade pays the full new-tier fee; `expires_at += 30 days`; tier (and therefore member pricing) changes immediately; quota is untouched until the rolling 30-day boundary, then refills at the new tier's quota — exactly the existing `applyTransition()` behaviour the admin path already produces. A downgrade behaves symmetrically (keeps the higher remaining quota until the boundary) — accepted, not special-cased.

*Payment rail*

2. **A new table `membership_subscription_payments` holds the pending→terminal state** — the analogue of how `orders` holds a pending payment. Columns: `id`, `reseller_id`, `email`, `membership_plan_id`, `amount_sen` (snapshot), `payment_ref` (CHIP purchase id — nullable until the gateway call returns, then unique), `status` (`pending` | `paid` | `failed` | `expired`), `idempotency_key` (unique — the `recordFeePaid` key), `channel_code`, timestamps. Not `membership_fee_records` (insert-only audit of *completed* payments — a lifecycle there muddies it); not a `pending` status on `memberships` itself (the `create` branch of `recordFeePaid` assumes Active).

3. **One webhook endpoint, branch by which table owns the `payment_ref`.** `ChipWebhookController` tries `Order` first (path unchanged); on no match, tries `membership_subscription_payments` by `payment_ref`; on neither, 404 as today. CHIP purchase ids are globally unique, so no collision. This avoids adding a `callbackUrl` field to the `PaymentRequest` DTO — a separate `/api/webhooks/chip/membership` route would need one, since `ChipGateway` reads a single `callbackUrl` from config today. The membership branch verifies the signature identically (`ChipGateway::verifyWebhookSignature`, reused as-is), cross-checks `$event->amountSen !== $payment->amount_sen` → 409 (mirrors the order path), guards re-processing on `status === 'paid'` (mirrors the PAY-2 idempotency guard), and on a fresh `paid` event calls `MembershipFeeService::recordFeePaid()` with the row's snapshotted data.

4. **Amount is server-computed and snapshotted.** The subscribe request carries `membership_plan_id` only, never a money value (ORD-9). `amount_sen` is read from `membership_plans.fee_sen` at row-creation time and frozen on the `membership_subscription_payments` row; the webhook cross-checks the CHIP callback against that snapshot, not the live plan — so an admin editing `fee_sen` between a customer starting and finishing checkout never changes what that customer is charged (same discipline as the ORD-9 order snapshot). No promo/voucher on the membership fee in v1.

*Client-facing endpoints*

5. **`POST /api/membership/subscribe`** — session-token gated (`resolveSession`; brand + email come from the token, never a request field). Input: `membership_plan_id`, `payment_method` (a `payment_methods` channel code), `channel_properties`. It reuses the `payment_methods` catalog + `PaymentGatewayFactory` exactly as the top-up checkout does — the customer picks an active channel (only `fpx` today; built channel-agnostic). It calls `gateway->createPayment()` **synchronously in the request** (the one sanctioned synchronous gateway call on a customer path, mirroring `CheckoutService::initiate()`), writes the returned `payment_ref` onto the `membership_subscription_payments` row, and returns `{ checkout_url }`. `PaymentCustomer` carries the member email only (membership has no name/phone field). Throttled with its own named bucket (`throttle:…,membership-subscribe`). Gated on `Reseller::primary()->membershipEnabledEffective()`, same as `plans()`.

6. **`GET /api/membership/subscribe-options`** — a new **authenticated** endpoint (session token). Returns the full plan rows (`id`, `name`, `fee_sen`, `quota_sen`, `discount_percent`), the caller's `current_plan_id` (or null), and a per-plan `relation` label (`subscribe` | `renew` | `upgrade` | `downgrade`). The anonymous `GET /api/membership/plans` keeps its deliberately narrow ADR-055 shape untouched — the subscribe view needs member context (current tier) anyway. Gated on `membershipEnabledEffective()`.

*Transaction fee*

7. **The payment-channel transaction fee is added on top of the membership fee**, shown as a separate line item ("Membership fee RM8.90 + Payment fee RM1.00 = RM9.90"), same `CheckoutTotalService` treatment as a top-up order. The channel fee is the channel's cost, not the platform's; the `membership_fee` ledger credit is booked for the **full** `fee_sen` (e.g. RM8.90), not net. An "absorb the fee, advertise exactly RM8.90" alternative was considered and rejected for v1 — ~11% overhead on an RM8.90 fee would eat the subscription margin; revisit if the fee ratio looks bad against the founder's real numbers.

*Seam changes*

8. **`recordFeePaid()`'s `$adminUserId` becomes `?int` end-to-end** (`recordFeePaid`, `bookFee`, and `LedgerService::credit`'s `$createdBy` if it is not already nullable — `membership_fee_records.admin_user_id` already is). The self-serve path passes `null` + a fixed `reason` of `"self-serve subscription"`. `ReportService::membershipBreakdown()` sums `membership_fee` ledger entries regardless of source, so the Reports tab keeps working with no change.

9. **The Plunk confirmation email is dispatched from inside the `recordFeePaid` seam** (after the transaction commits), so **both** the admin `record-payment` path and the self-serve path send the member a receipt — a member should have a written record of a recurring charge regardless of who keyed it. This is an intended behaviour change to the admin path. The mailable carries tier, amount paid, new `expires_at`, and quota; it renders a zero-amount waiver as "Complimentary membership" / "RM0.00", not a broken receipt, and reads correctly for a reactivation as well as a fresh subscribe.

*Reconciliation & lifecycle*

10. **A sibling command `app:reconcile-pending-membership-payments`**, scheduled `daily()` in `routes/console.php`. It queries `membership_subscription_payments WHERE status = 'pending' AND payment_ref IS NOT NULL AND created_at <= now()-threshold`, calls `gateway->getPayment($payment_ref)`, and: `Paid` → `recordFeePaid()`; `Failed` → `status = 'failed'`; still pending past a longer window → `status = 'expired'`. A sibling, not an extension of `ReconcilePendingPaymentsCommand`, because that command's query is `orders`-coupled and `routes/console.php` already follows a one-command-per-concern pattern.

11. **Each subscribe click creates a fresh `membership_subscription_payments` row and a fresh CHIP purchase** — no dedup of concurrent/abandoned attempts (mirrors the top-up checkout). Two genuinely completed payments simply produce two 30-day extensions (legal per decision 1 / ADR-027 Phase 6.5 Q1 — a member who pays twice gets 60 days, the same "customer's own problem" risk top-up double-pay carries). `recordFeePaid`'s per-row `idempotency_key` prevents a single payment being double-booked across webhook retries plus the reconcile sweep. `expired`/`failed` rows may be TTL-pruned after 90 days — low priority, not a launch blocker.

*Post-payment UX*

12. **`success_redirect` → `/membership?checkout=success`** (via `channel_properties`, mirroring how `CheckoutService::requestPayment()` sets the order-status return URL). The page shows a "Confirming your payment…" state and polls `GET /api/membership/me` every ~3s for up to ~30s: membership active → the dashboard; timeout → "This is taking longer than expected — we'll email you when it's confirmed." **`failure_redirect` → `/membership?checkout=failed`** → "Payment not completed, try again" back to the tier picker.

13. **The `/membership` subscribe surface** replaces the "coming soon" placeholder. Verified with no membership → tier cards (fee, discount %, quota) + "Subscribe". Active member → current-tier card + "Renew" (same tier, pre-filled) and "Change tier" (the other tiers, labelled upgrade/downgrade from `subscribe-options`). Every action runs the same subscribe → channel-pick → pay flow. `MembershipPromoCard`'s CTA already points at `/membership`, so it lands on the real view with no code change once this ships.

*Admin per-member view*

14. **A new sub-route `/admin/membership/[id]`** (`memberships.id`), reached by a "View" action on each row of the existing Members registry DataTable on `/admin/membership` — the same list→detail pattern as `/admin/orders`. `/admin/membership` keeps its dual role (tier config + Preview Pricing + Members registry as the index); the 519-line `page.tsx` is split into components as part of this. Read-only. Chosen over an inline drawer / expand-row for deep-linkability (support can paste a member's URL) and to keep `page.tsx` from growing.

15. **The `/admin/membership/[id]` detail shows, in ADR-068 scope:** (1) **State** — current tier, status, cycle, `expires_at`, quota (the registry columns, gathered); (2) **Fee Payments** — `membership_fee_records` rows (date, tier, `amount_sen`, source: admin user name or "Self-serve", reason) **plus recent `membership_subscription_payments` attempts including `pending` / `failed` / `expired`**. This last part is the reason the view is in scope at all: self-serve introduces payment states the flat registry cannot show, and "the member says they paid, the admin cannot verify" is a day-one support gap otherwise. Each fee record links to its `ledger_entries` row by id — no separate ledger browser. A **Member Orders summary** (count, spend, margin forgone, link to a filtered `/admin/orders`) is optional — same PR if cheap, else a follow-up.

**Secondary — member-identity correctness (folded in; surfaced by order `PG-PYAYMRYNUYV0`):**

16. **When a verified member session is active, the checkout contact email is bound to the membership email — two layers.** Frontend: the email field is pre-filled and read-only with a small "Your member email — not you? Sign out" note (`OrderForm`). Backend: `CheckoutService::initiate()` forces `customer_email = membership.email` whenever a member is resolved, ignoring the payload email (defence in depth — the ORD-9 "never trusted from the client" principle applied to identity). Name, phone, and Player ID stay editable — a member legitimately tops up other game accounts, for other people; email is the identity key that must match. A hard reject on mismatch was considered and rejected as too harsh for an ordinary typo.

17. **`MembershipController::orderHistory()` matches `where('customer_email', $email)->orWhere('membership_id', $membershipId)`** — a union, not the current strict email match. Orders have carried `membership_id` since Phase 6, so any order bought as this member surfaces even if its contact email differs (legacy orders, or a pre-fix mistyped one). No backfill of `PG-PYAYMRYNUYV0` — cosmetic, one test order.

**Rationale:** The payment rail is the only missing piece of a feature that is otherwise live — and ADR-027's Phase 6.5 deliberately built `recordFeePaid()` as the single seam a webhook would call, so the automated path is a new *caller* of an existing, concurrency-proven method, not new money-path logic. A dedicated `membership_subscription_payments` table keeps the pending-state shape identical to how `orders` already works, and branching the one webhook endpoint by `payment_ref` ownership avoids reshaping the `PaymentGateway` seam (`AGENTS.md`: extend an implementation behind a seam, not the seam itself). The admin per-member view is scoped to exactly the diagnostic surface self-serve failure states create — no more. The two folded fixes share a root cause (member identity vs. typed contact detail) and surfaced from the same real order, so they belong with this change rather than a separate ADR.

**Stress-test addendum — 2026-09-03, same session, re-grilled via `/mattpocock-skills:grilling` (16 findings over three rounds)**, per this ADR's own "stress-test before built" instruction. The following supersede or tighten the decisions above; none reopens the scope.

- **S1 (fixes decisions 2 + 3) — the row snapshots two amounts, not one.** `fee_sen` (the plan fee — passed to `recordFeePaid`, booked to the ledger) and `total_charged_sen` (`fee_sen` + the payment-channel fee, decision 7). The webhook amount cross-check is against `total_charged_sen` (the CHIP `purchase.total`), mirroring `orders.final_amount`. Decision 3's "cross-check `amount_sen`" was wrong — with the channel fee added on top, every real payment would 409.
- **S2 + S9 + S10 (extends decision 2, mirrors the Order idempotency pattern) — the row carries three identifiers:**
  - `idempotency_key` — client-generated UUID, unique. Dedups an HTTP retry of `POST /api/membership/subscribe` (the `checkout_idempotency_key` analogue).
  - `subscription_number` — server-generated `MS-XXXXXXXX`, unique. Used as the CHIP `reference`, as the human-readable ref on the admin view + receipt email, and as the `recordFeePaid` idempotency key (the `order_number` analogue).
  - `payment_ref` — the CHIP purchase `id`, nullable until `createPayment()` returns.
  - `checkout_url` is also stored on the row once `createPayment()` returns.
  - **The webhook membership branch matches on `subscription_number` (echoed back as the event `referenceId`), not `payment_ref`** — the reference is known before CHIP is ever called, closing the lost-response gap that would otherwise leave a charged customer with no membership. `subscribe` is idempotent on `idempotency_key`: a retry finds the existing row and returns its stored `checkout_url`, or — if the first `createPayment()` call's response was lost — re-calls `createPayment()` with the same `subscription_number` as `reference` so CHIP dedups (the `resume()` pattern). CHIP's dedupe-on-`reference` behaviour is a design assumption to verify with `app:chip-smoke-test` at build time (the same caveat the Order path carries).
- **S3 (tightens decision 5) — a failed `createPayment()` call marks the row `failed` immediately** and returns an error to the client; no row is ever left `pending` with a null `payment_ref` and no CHIP purchase behind it.
- **S4 (reverses decision 11's "no dedup") — `subscribe` dedups within a short window.** If a `pending` row younger than 15 minutes exists for the caller's email, `subscribe` returns that row's stored `checkout_url` instead of creating a new row + CHIP purchase. A membership double-charge costs the customer a 30-day extension they did not want (unlike a top-up double-pay, which at least delivers goods), so the short-window dedup is worth it. Rows older than 15 minutes are treated as abandoned; a fresh `subscribe` creates a new row.
- **S5 (narrows decision 1) — downgrade is dropped from the self-serve UI.** v1 self-serve is **subscribe / renew / upgrade** only. `subscribe-options` still returns the lower tiers, labelled `downgrade`, but their button is disabled with a "takes effect when your current membership ends" note. A mid-cycle paid downgrade has no clean financial meaning (pay to receive less). **Downgrade stays possible via the admin `record-payment` action only** — `applyTransition()` already sets `membership_plan_id` to whatever plan is submitted, no code change.
- **S6 (corrects decision 7) — `CheckoutTotalService` is not reused.** The total is computed directly: `total_charged_sen = fee_sen + channelFee(fee_sen, payment_method)` using the same `payment_methods` fee formula (`percentage_rate` / `flat_fee_sen`). No voucher, no velocity checks — those are order-only concerns.
- **S7 (confirms decision, adds a consequence) — the webhook honours a payment even if the kill switch was turned off after checkout started.** `recordFeePaid` is not gated on `membershipEnabledEffective()` (same as the admin path) — money received must produce value. Accepted; turning the switch off post-launch is the founder's responsibility for any in-flight checkout.
- **S11 (renames the decision-2 table) — `membership_subscription_payments` → `membership_checkout_attempts`.** The row is a lifecycle-bearing checkout attempt (`pending` → `paid` / `failed` / `expired`), not a record of a completed payment (`membership_fee_records` already owns that). Aligns with the "checkout" language already in the codebase (`checkout_idempotency_key`, `CheckoutService`). Pin in `prd.md` §13 Glossary; run `/mattpocock-skills:domain-modeling` at build time.
- **S12 (tightens decision 9) — the receipt email is dispatched only on an actual create/transition** (after `bookFee`, after the transaction commits), never on `recordFeePaid`'s fast-path return — so a webhook + reconcile race produces exactly one email. The ledger `reason` is `"self-serve subscription"` for a new membership, `"self-serve renewal"` for an extend/reactivate.
- **S13 (clarifies decision 1's wording) — the ADR text reads: self-serve = subscribe / renew / upgrade; downgrade via admin `record-payment` only.**
- **S14 (adds to the test consequence) — a new `tests/Concurrency/MembershipCheckoutWebhookReconcileConcurrencyTest.php`** (mirroring `MembershipFeeRecordConcurrencyTest`): two processes hit the payment-processing path concurrently for one `subscription_number` → exactly one membership, one ledger credit, one email, row ends `paid`. In PR-1.
- **S15 (clarifies decision 6) — an `expired` member in `subscribe-options` is treated as having no current plan** (`current_plan_id = null`, every tier labelled `subscribe`); a paid action on it runs `applyTransition()`'s reactivate branch.
- **S16 (sequences the e2e work) — the e2e golden-path test (verify → subscribe → fake-pay → active) and the `FakePaymentGateway` membership-callback simulation land in PR-1**, not PR-2 — the webhook branch is money-path and should be proven end-to-end before the UI is built.
