# ADR-107: Combo order profit reconciliation on retry + partial-delivery voucher accuracy

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`) 2026-09-17, same session as ADR-105/106. Sparked by the founder's own follow-up question after ADR-105 merged ("takkan ada kesalahan lagi... reseller or reseller API betul?") — confirming every pricing basis was covered surfaced that combo orders have a structurally different, unaddressed version of the same root problem. **Built 2026-09-17, merged to `staging`** (PR #237, bundled with ADR-106), with decisions 1/2 revised during the founder's own plan-review before any code was written — see the build addendum at the end of this entry. **Partially superseded by [ADR-111](./ADR-111-real-cost-profit-reconciliation-at-delivery-time.md) (2026-09-22):** decision 2's cost INPUT — live `componentPackage->cost_price` — is replaced by the supplier's real per-transaction price when ADR-111's flag is enabled (live in prod since 2026-09-22), with a per-leg fallback to this ADR's own catalog-cost read when the real figure is genuinely unavailable; decision 3's `combo_profit_reconciled_negative` signal is renamed `profit_reconciled_flagged` and generalized to every order type. The residual FORMULA itself (decision 2's own shape) and every other decision here (frozen `selling_price_sen`, the voucher apportionment fix) are unchanged and still load-bearing.

**Context:** ADR-094 decision 10 blocks combo orders from `OrderResendService`'s package-swap resend entirely (a combo has multiple legs/suppliers — "swap to one different package" doesn't apply). A combo's only recovery path is the ordinary "Retry Delivery" button, which calls `OrderFulfillmentService::fulfillCombo()` → `attemptLeg()` (one leg at a time, its own transaction) again. Confirmed via `resolveComboOutcome()`'s own comment: "credit profit once... since platform_profit/affiliate_profit were already frozen onto the Order as one figure at checkout, ORD-9." `creditProfit()` fires exactly once, whenever every leg finally reaches `Delivered`, using whatever was frozen at the order's *original* checkout — never reconciled against what a retried leg's live cost actually turned out to be. This is the same root family as ADR-105's bug (a reported profit figure decoupled from live cost) but a structurally different mechanism: ADR-105's bug reconciled with the *wrong formula*; a combo retry doesn't reconcile *at all*.

Confirmed the real cash side is unaffected and already correct: `SupplierFundingService::recordOrderDrawdown($order, $price, $leg)` records the actual live price paid to the supplier per leg (`SupplierLedgerEntry`, `reference_type='order_delivery_leg'`), at whatever the supplier actually charged at attempt time — accurate today, independent of anything below. The gap is narrowly in the *reported* `platform_profit`/`affiliate_profit` figure: if a retried leg's live cost has risen since checkout (the component `Package.cost_price` is itself kept live-synced by `ComboPricingService::recomputeForComponentChange()`, the same price-sync mechanism behind ADR-105's original bug), the platform now pays the supplier more (correctly recorded in the funding ledger) but never reports a smaller margin to match — silently overstating real margin, with nothing (no schema, no formula) currently capable of catching it, since `order_delivery_legs` has no cost snapshot column at all (`id, order_id, component_package_id, supplier_id, leg_number, reference_number, status, supplier_reference, delivered_at, failure_reason, resend_unsafe_with_same_reference` — confirmed via schema listing this session).

A second, related finding in the same investigation: `Order::suggestedPartialVoucherAmount()` (ADR-094 decision 9's compensation prefill for a genuine partial-combo delivery — some legs Delivered, some Failed) sums each Failed leg's *current* `componentPackage->standard_selling_price` — a live relation read, not a frozen snapshot. If that component's price has moved since checkout, the suggested amount no longer reflects what the customer actually paid for that leg. Lower severity than the profit gap: `StoreVoucherFromOrderRequest` hard-caps any submitted amount at `order.final_amount` (a real, frozen ceiling — can never exceed what was actually collected), and the amount is admin-typed/reviewed before submission, never auto-applied — so this is a misleading suggestion, not a silent-overpay risk. The founder's own explicit principle, confirmed this session: a voucher always reflects what the customer paid (`final_amount − transaction_fee`), never anything about supplier cost, resend outcomes, or live pricing — the same principle the ordinary (non-combo) Failed-order voucher path already follows correctly (`storeFromOrder()`'s `else` branch), and what this ADR extends to the partial-combo case specifically. Confirmed this bug is combo-only: `isPartialComboDelivery()` returns `false` immediately when `deliveryLegs` is empty, which is always true for a non-combo order (legs are only ever seeded for a combo) — an ordinary order's Failed-delivery voucher was never affected.

Prod check: exactly one combo order has ever existed, both legs delivered clean on the first attempt, never retried and never partially failed — this ADR is 100% latent, not a live financial discrepancy, unlike order 15's real ADR-105 impact.

**Decision:**

1. **New `order_delivery_legs.cost_price_sen` and `order_delivery_legs.selling_price_sen` columns**, both frozen at `seedDeliveryLegs()` time (essentially checkout — this runs synchronously inside `fulfillCombo()`'s first pass, dispatched by `FulfillOrderJob` moments after payment confirmation, the same effective timing ADR-017/ADR-105's own order-level snapshot fields already use) from the leg's `component_package_id`'s then-current `cost_price`/`standard_selling_price` × the leg's own quantity-of-one (each repeated component already expands into its own leg row, ADR-094 decision 1). `cost_price_sen` feeds decision 2's profit reconciliation; `selling_price_sen` feeds decision 3's voucher-apportionment fix. Both are genuinely new information — nothing today records what portion of a combo's aggregate `cost_price`/`standard_selling_price` any single leg represented.

2. **`platformProfit` is reconciled once, at final resolution** — the moment `resolveComboOutcome()` determines every leg has reached `Delivered` and is about to call `creditProfit()` for the first (only) time — as the same money-conservation residual ADR-105 decision 8 established for the single-package case: `order.selling_price (frozen) − Σ(actual cost paid per leg) − affiliateProfit`. `affiliateProfit` itself is **not** reconciled per-leg — it keeps the exact value `OrderPricingResolver` computed once at checkout (the same "affiliate's own formula stays untouched, only platform absorbs a live-cost shortfall" principle ADR-105 decision 8 established), consistent across every `pricing_basis` a combo order can carry (Standard/Member/Affiliate/ResellerWallet — nothing about combo-ness changes which basis prices it). "Actual cost paid per leg" is the live price captured at that leg's own successful delivery (stored directly on the leg row when `attemptLeg()`'s success branch runs — the same figure already passed to `recordOrderDrawdown()`, not a second source of truth requiring a cross-table join against `SupplierLedgerEntry`). Recomputing once at final resolution (not after every individual leg attempt) matches the existing "credit once" invariant exactly — no new intermediate state to reason about.

3. **A resulting loss is never blocked.** ADR-105 decision 4/8's override-reason gate assumes a synchronous admin action that can be told "provide a reason to proceed" — a combo's finalization can just as easily be reached via a Digiflazz webhook or `ReconcilePendingDeliveriesCommand`'s scheduled poll, neither of which has an admin present to supply one. Blocking delivery over an accounting question would strand a paid customer's goods, violating the same spirit ADR-004 ("no cash refunds, ever" — nothing here should ever become "no goods, ever" either) already protects. Instead: the order still completes and delivers normally; the reconciled (possibly negative) `platformProfit` is recorded as-is; a `Log::warning()` fires; and the Order Detail page gains a new visibility signal (a badge/card in the same family as ADR-102's Refund Information cards) so an admin notices after the fact, rather than being asked to approve before it. This is a deliberate, load-bearing difference from ADR-105's own guard — not an inconsistency to reconcile later.

4. **The partial-combo voucher suggestion apportions `order.final_amount − order.transaction_fee` proportionally across Failed legs' frozen `selling_price_sen` weights**, replacing the current live-price sum: `suggestedAmount = round((final_amount − transaction_fee) × (Σ Failed legs' selling_price_sen) / (Σ all legs' selling_price_sen))`. Proportional (not a flat per-leg retail sum) so it correctly scales down when the order was voucher-discounted or affiliate-marked-up relative to guest retail — the actual amount the customer is owed for the failed portion, never the listed retail value of that leg. Still just a prefill: `StoreVoucherFromOrderRequest`'s existing `final_amount` hard cap and admin-typed `amount` field are unchanged — this fixes the suggestion's accuracy, not the safety mechanism (which was already correct).

**Rationale:** Same lesson as ADR-105, applied to a structure ADR-105 explicitly didn't reach (ADR-094 decision 10 keeps combo orders out of `OrderResendService` entirely, for good reason — a package-swap tool doesn't map onto multiple legs/suppliers). The fix isn't "make combo use `OrderResendService`" but "give combo's own retry path the same reconciliation discipline, expressed in terms combo's own structure already has" — per-leg cost snapshots feeding the identical money-conservation residual, and a voucher formula anchored to what was actually collected rather than a live catalog price. The never-block decision (3) is the one genuinely new principle this ADR adds beyond porting ADR-105's pattern — a direct consequence of combo's finalization not always having an admin in the loop, a distinction ADR-105 never had to make.

**Consequence to track:**

- Zero real combo resends/partial-deliveries exist in prod — this entire ADR is preventative. Once real combo volume exists (the same trigger `docs/prd.md` §16 item 16 and ADR-103's own "revisit once real combo volume exists" note are both watching for), confirm the new admin-visibility badge (decision 3) is actually being seen and acted on, not just silently accruing.

The two are fully independent and can ship in either order or as separate PRs. **Build-time addendum, 2026-09-17 (same day, before any code was written) — decisions 1 and 2 revised, a real currency-correctness gap found during plan-review.**

Decision 2 as originally accepted said "actual cost paid per leg" reuses the exact figure already passed to `SupplierFundingService::recordOrderDrawdown()` for that leg. That figure is `$drawdownPrice` — the supplier's createOrder() response `price`, in the **supplier's own raw currency** (confirmed: Digiflazz's is literal IDR, `DigiflazzAdapter.php`'s own `rawCurrency: 'IDR'` comment; Gamevion's is MYR, no conversion). Building the ADR exactly as written would have summed this raw-currency figure directly against `order.selling_price`/`affiliate_profit`, both MYR sen — a silent ~4400x currency-scale corruption the moment a Digiflazz-sourced combo leg was ever resent, never caught by any existing guard (nothing type-checks currency scale). Found before any code existed, by walking the founder through the exact mechanism decision 2 depended on.

**Revision:** decision 2 now reads each Delivered leg's `componentPackage->cost_price` **LIVE at final resolution** (inside `resolveComboOutcome()`'s Delivered branch) — already MYR sen, converted once at sync time (ADR-033/067's conversion boundary), never the literal per-call response price. This mirrors ADR-105 decision 1's own established precedent for the non-combo case (which already, deliberately, reads the target package's live `cost_price` rather than the literal supplier response for its own reconciliation) rather than introducing a second, divergent pattern. Rejected alternative: convert `$drawdownPrice` via `CurrencyRateService` and store it as a second per-leg column (`actual_cost_price_sen`) — rejected because it pulls a network-dependent service (`CurrencyRateService::rate()`, which throws `CurrencyRateUnavailableException` on a cold cache + failed live fetch) into `attemptLeg()`'s success branch, a real-time delivery hot path that decision 3 already commits to never blocking — a second failure surface with no proportionate accuracy benefit, since the live-catalog figure is already what every other cost-reconciliation path in this codebase (ADR-105) treats as ground truth.

**Consequence for the schema:** decision 1's originally-planned `order_delivery_legs.cost_price_sen` frozen-snapshot column is dropped — nothing reads it under the revised decision 2. Only `selling_price_sen` (decision 4's voucher-apportionment input, unaffected by this revision) is actually built. The owning migration (`2026_09_17_190000_add_selling_price_sen_to_order_delivery_legs_table.php`) and `docs/build-log.md`'s matching ADR-107 entry carry the full reasoning.

No other decision changed. Decisions 3 and 4 are built exactly as originally accepted.
