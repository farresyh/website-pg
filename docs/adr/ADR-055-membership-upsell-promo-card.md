# ADR-055: Membership upsell promo card — storefront Order Summary, Tier 2 teaser (design only, grilled 2026-08-30; built 2026-08-30)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-30 (grilled with the founder via `/mattpocock-skills:grilling`, one question at a time, before any code touched). **Built 2026-08-30** — see the build addendum below; `docs/prd.md` §14/§15 updated same session.

**Context:** While live-testing this session's membership pricing fixes (this file's `ADR-027` 2026-08-30 addendum), the founder asked for a simple promo card below the storefront's Order Summary sidebar: "unlock {package} at {Tier 2 price}, save {%/RM}, subscribe for only {monthly fee}" — placeholders following whichever package the customer currently has selected. Investigation before grilling surfaced two real gaps this ADR had to resolve, not just a UI placement question:

1. **Tier 2's monthly fee (`fee_sen`) is 100% admin-only today.** `backend/routes/api.php`'s `membership-plans` prefix is gated `admin.role:super_admin` end to end — no route exposes any `MembershipPlan` field (`name`/`fee_sen`/`discount_percent`/`quota_sen`) publicly. The public catalog (`CatalogController::packages()`) already exposes a computed per-package `member_price_sen`/`member_price_personalized` (this session's earlier addendum) but never the raw plan fee itself.
2. **The storefront has no self-serve subscribe/pay flow at all.** `storefront/src/components/order/MembershipClient.tsx`'s own doc comment: "The 'subscribe' side of decision 4's two-tier flow isn't built yet (checkout wiring, ADR-027's own later phase) — a verified visitor with no active membership sees an honest 'coming soon' state here, not a fake subscribe form." The only way anyone becomes a member today is the founder manually recording payment in admin (`/admin/membership` Record Payment, ADR-027 Phase 6.5). ADR-027 Phase 7 (self-serve subscribe+pay) is explicitly unbuilt.

So the card's CTA had nowhere real to send a customer to actually complete a subscription — a genuine product decision, not an implementation detail, and the reason this got a full grill rather than being coded straight from the founder's rough copy.

**Decision:**

1. **Scope stays a display-only teaser — no self-serve subscribe/pay flow is built as part of this.** The card's CTA links to `/membership`'s existing "coming soon" messaging. Turning this into the trigger for Phase 7 (a real recurring/one-time membership-fee payment flow via Xendit/CHIP) was considered and explicitly rejected as its own, much larger scope — deserving its own dedicated grill when the founder is ready to build it, not absorbed silently into "add a card."
2. **Visibility:** hidden entirely when `PlatformSettings.membership_enabled` is off, and hidden for a customer already on Tier 2 (nothing left to upsell — showing it would be nonsensical). Shown for an anonymous guest and for a Tier 1 member, both cases always promoting **Tier 2** specifically (the top tier), matching the founder's own original wording.
3. **New public backend endpoint, `GET /api/membership/plans`** — deliberately separate from the existing admin-gated `membership-plans` prefix, not a reuse of it. Returns only `name`, `fee_sen`, `discount_percent` per tier (both Tier 1 and Tier 2, even though this card only needs Tier 2 — a direct reuse target for `/membership`'s own still-unbuilt Tier 1 vs Tier 2 comparison, ADR-027 decision 25). No `quota_sen`, `id`, or timestamp fields — narrower than what's plausibly useful later, on purpose (`AGENTS.md`'s "don't design for hypothetical future requirements"; add fields only when an actual consumer needs them). Empty/404 when `membership_enabled` is off.
4. **Savings shown per-package only, no break-even-after-N-purchases framing.** Matches the founder's own original wording exactly (a simple "save X now, subscription costs Y/month" pairing) — a break-even calculation was considered and rejected as unrequested complexity resting on an assumption (repeat-purchase frequency) this feature has no data to back.
5. **Card appears only once a package is selected** — its placeholders (`{package name}`, `{Tier 2 price}`, `{savings}`) have nothing to render before then. Lives in the same `OrderSummarySidebar` region as the Package Price/Transaction Fee/Total breakdown (this session's other addendum), appearing at the same point those rows start rendering.
6. **One copy template, not two — only the CTA phrase swaps by audience.** Guest: "Become a Member." Tier 1 member: "Upgrade to Tier 2." Everything else in the card (package name, Tier 2 price, savings, fee) renders identically for both audiences.
7. **Plumbing:** fetched server-side in `order/[slug]/page.tsx` alongside the existing `getGame`/`getGamePackages`/`listPaymentChannels` calls, not a separate client-side round trip. Cached with the same 60s TTL/tagged-store discipline as `CatalogController`'s own public endpoints (`ADR-014`), invalidated from the same write path that already flushes `catalog.packages` on a membership plan edit (`CatalogController::forgetPackagesCacheForMembership()`).
8. **Ships as its own branch/PR off `staging`**, not folded into the `fix/membership-tier-markup-and-record-payment-ui` branch this session's bug fixes and the Package Price/Transaction Fee breakdown shipped on — this is a genuinely new feature surface, not a fix, and that branch already carries four stacked pieces of work from one session.

**Rationale:** Decision 1 is the load-bearing call — the founder's rough ask ("add a simple card") could have silently absorbed a full payment-flow feature (Phase 7) if the CTA had been built to actually complete a subscription; scoping it to a teaser keeps this session's actual ask (a display element) from ballooning into unplanned payment-integration work. Decision 3's new public endpoint (rather than loosening the existing admin-gated one, or inlining `fee_sen` into the catalog packages response) keeps the admin-only `membership-plans` routes untouched and gives `/membership`'s own known-incomplete comparison UI (decision 25 of `ADR-027`'s earlier addendum) a ready-made data source instead of a second one being built later for the same need.

**Consequence to track:**
- This ADR is design-only — no code exists yet. Implementation (backend endpoint, storefront card component, `docs/prd.md` §14/§15 update) is deferred to a future session, per the founder's own instruction this session.
- If Phase 7 (self-serve subscribe+pay) is ever scoped, decision 1's teaser-only framing for this card should be revisited then — the CTA may be worth pointing at a real subscribe flow instead of `/membership`'s "coming soon" state once one exists.
- Decision 3's new endpoint returning both tiers (not just Tier 2) is unused surplus until `/membership`'s own comparison UI is actually built — acceptable since it's the same data shape either consumer needs, not speculative scope beyond what's already decided to expose.

**Addendum, 2026-08-30 — built, all eight decisions implemented as designed.** Shipped on `feature/adr-055-membership-upsell-card` (decision 8's own branch, off `staging`).

*Backend:*
- `MembershipController::plans()` + `GET /api/membership/plans` (public, no session token). Returns both tiers' `{name, fee_sen, discount_percent}` only (decision 3 — no `quota_sen`/`id`/timestamps), `[]` when `membership_enabled` is off — resolved the ADR's open "Empty/404" in favor of **Empty** (`[]`, 200): a single contract shape the storefront renders as "no card" without a 404 special case, matching the codebase's narrow-response-shape discipline.
- Cached in the existing `catalog_packages_store` (redis, 60s TTL), tagged `catalog.packages` — so `CatalogController::forgetPackagesCacheForMembership()`, already flushed on every `membership_plans` edit and kill-switch toggle, invalidates this endpoint for free (decision 7).

*Storefront:*
- `lib/membership.ts`: `listPlans()` + `MembershipPlan` type (zod, ADR-044).
- `order/[slug]/page.tsx`: `listPlans()` fetched server-side alongside `getGamePackages`/`listPaymentChannels`, passed down (decision 7 — no client round trip).
- `OrderForm.tsx`: audience detection — the existing membership-token effect now also calls `getMe(token)` to learn the visitor's own tier (keyed by token like the personalized-packages state, so a guest/SSR render reads back null without setState-in-effect). 
- `OrderSummarySidebar.tsx`: unchanged back to its pre-card state — the promo is its own card, not a section inside it. `OrderForm.tsx` resolves the visibility and renders `MembershipPromoCard` as a **separate rounded card in the same right-hand column, below the Order Summary card** (founder's own placement call after seeing it inside the card) — visible only once a package is selected, hidden when plans are empty (kill switch off) or the visitor is already on the top tier (decision 2). Top tier resolved by max `discount_percent`, robust against admin renaming a tier's `name`. One copy template, CTA phrase swaps by audience — "Become a Member" (guest) vs "Upgrade to Tier 2" (Tier 1), decision 6. CTA links to `/membership` (decision 1 — teaser only, no Phase 7 scope).

*Implementation nuance worth recording (not in the original decisions):* the card always promotes Tier 2, but a Tier 1 member's `packages` prop is personalized to their own tier — so the card's Tier 2 member price is sourced from the **anonymous SSR anchor** (`initialPackages`, always the best-tier price) rather than the personalized package list. Both displayed numbers remain backend-computed (ORD-9); the savings row is a pure render of two server-provided values.

*Tests:* 3 new `MembershipControllerTest` cases (empty-when-disabled, narrow-tier-shape-when-enabled, and cache-invalidation-via-`forgetPackagesCacheForMembership`). Full backend suite **1063/1063 green**. `npx tsc --noEmit`/`eslint`/`next build` clean on `storefront/`.

**Consequence to track (this addendum):** the original "not yet built" consequence bullet above is superseded — the card is live on the feature branch; only decision 1's Phase-7 revisit and decision 3's unused-surplus note remain, unchanged in kind.

**Addendum, 2026-09-18 — second touchpoint (`ReviewModal`) + a smart-scroll UX fix, both refinements of this ADR's existing scope, no new grill.** Founder-initiated, live-iterated with the founder over several rounds via a real-browser design preview (`storefront/src/app/dev-preview/review-modal`, mounting the real `ReviewModal.tsx` against mock data, deleted once approved — the same disposable-preview pattern ADR-109 used). Neither addition changes money computation (still ORD-9, backend-computed values only), adds an endpoint, or touches a seam — both are placement/UX refinements of an already-Accepted feature, so this stays an addendum rather than a new numbered ADR.

1. **Second promo touchpoint, inside the Order Review modal itself** (the last checkpoint before payment), not just the sidebar card. Reuses `OrderForm.tsx`'s existing `showPromo`/`selectedTier2MemberPriceRm` computed values verbatim — no new computation, no new endpoint. New `ReviewModal` props: `showMembershipPromo?: boolean`, `topTierMemberPriceRm?: number | null` (both optional, default off — every existing caller/test unaffected).
2. **Deliberately different copy and hierarchy from the sidebar card** — the founder's own call, arrived at through the live-preview iteration: no savings amount/percent shown (unlike the sidebar card's "save RM{y} ({z}%)"), just "Members pay RM{x} for this." The member price itself is the largest, boldest element in the strip (`font-mono text-xl font-bold`) — the actual selling point at this late-funnel moment — with a small "MEMBERS PAY" caption above it and a de-emphasized "Become a Member →" link, so it doesn't compete with the modal's one real primary action ("Confirm & Pay").
3. **Visual style: `border-2 border-ink`, matching every other card on this page** (the modal shell itself, `StepCard`, `OrderSummarySidebar`) — a softer 1px-border/12px-radius variant was tried live and explicitly rejected: it broke the neo-brutalist system's own established language (ADR-062/063's "ink-navy strokes, hard offset shadows") on an element sitting directly beside others that all use the thick-ink-border convention. No `.neo`/`.neo-sm` drop shadow, though — kept deliberately quieter than the sidebar card, so it doesn't visually compete with the "Confirm & Pay" CTA.
4. **Icon: Phosphor `Crown`**, reusing the same membership motif already used in `BottomNav.tsx` and `WhyChooseUsSection.tsx` — not a new icon choice.
5. **Same visibility gate as the sidebar card** (`showPromo`) — hidden when membership is off, or the visitor is already on the top tier. Never shown when `isMemberPrice` is already true (nothing left to upsell in the modal itself).
6. **Smart-scroll: picking a package (Step 2) auto-scrolls to Step 3 + the sidebar promo card**, mobile/tablet only (`< 1024px`, the same `lg` breakpoint the layout itself switches its two-column/one-column structure on) — desktop's two-column layout already keeps Step 3 and the sidebar card in view side by side, so an unrequested scroll jump there would be a more jarring surprise for a mouse-driven visitor than a helpful one. Founder's own call after seeing both behaviours live.
7. **The scroll offset is computed manually** (`target.getBoundingClientRect().top + window.scrollY - headerHeight - 12`), not bare `element.scrollIntoView({block:"start"})` — the naive version was tried first and overshot past Step 3's own title, because `scrollIntoView` has no awareness of `SiteHeader`'s `sticky top-0` header sitting on top of it. Respects `prefers-reduced-motion` (falls back to `behavior: "auto"`, no smooth animation).

**Consequence to track (this addendum):** none — both additions are pure client-side rendering/UX, no backend surface, no new decision axis to revisit later.
