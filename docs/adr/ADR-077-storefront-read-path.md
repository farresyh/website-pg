# ADR-077: Storefront read-path — Redis cache cutover, eviction policy, invalidation fan-out, propagation freshness

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-07, grilled with the founder over three rounds via `/mattpocock-skills:grilling` before any code was written; this entry is that shared understanding. No code in this ADR — the "Build addendum" sections land as each PR ships. Paired with ADR-078 (custom-domain gaps), split from the same session's diagnosis by natural boundary.

**Context:**

Two background audits plus a live read of Laravel Pulse (`/pulse`, 7-day window, production) established that the storefront's read path has one dominant bottleneck and several smaller ones. The founder asked for the fix to be "clean, maintainable, reliable, scalable" — not a minimal patch.

1. **The `database` cache driver is the system-wide bottleneck.** `config/cache.php` `CACHE_STORE` defaults to `database` (ADR-014/019, chosen before Redis existed in this stack — Redis arrived with ADR-048 for the queue). Pulse Slow Queries (>1s threshold, so these are the tip of the iceberg):
   - `select * from cache where key in (?)` — **52,754 ms** (`vendor/laravel/horizon/src/Console/WorkCommand.php:53`, i.e. a Horizon worker boot reading cached config)
   - `select * from cache …` — **6,272 ms** (`HeroSlideController.php:37`)
   - `select * from resellers where is_primary = 1 …` — **5,071 ms** (`Reseller.php:96`, i.e. `Affiliate::primary()` — the row has a unique index, so 5s is pure lock contention, not a missing index)
   - `insert into cache … on duplicate key update` — 1,271 ms (`CatalogController.php:54`)
   The `cache` table is a MySQL table with no eviction algorithm (`Illuminate\Cache\DatabaseStore` expires entries lazily on read only — no scheduled sweep, no `cache:prune-stale` in `routes/console.php`), so dead rows accumulate indefinitely. Combined with the every-10-minute Price Sync's `Cache::forget()` storm and ADR-060 PR-4c's per-brand key-loop invalidation, row-locking on that one table cascades into every code path that touches cache: hero-slide/branding/SEO endpoints, Horizon worker boot, even `Affiliate::primary()`.
2. **Cache hit rate is 32.68% over 7 days** (19,472 hits / 40,089 misses). The ADR-060 PR-4c per-brand keys are the worst: `catalog.public.games.index.brand.1` sits at **0.77%** (639 misses, ~5 hits), `catalog.public.hero_slides.brand.1` at **0.45%** — because `CatalogController::forgetIndexCache()` loops **every** affiliate (`Affiliate::withTrashed()->pluck('id')`) on every package/price/game edit and on every Price Sync run, nuking those keys faster than a low-traffic storefront re-warms them.
3. **Price Sync runs every 10 minutes** (`routes/console.php:37`, `cron("*/{$priceSyncIntervalMinutes} …")`, `PRICE_SYNC_INTERVAL_MINUTES=10` from `config/packages.php:19`). Pulse: `SyncSupplierPricesJob` — **720 runs / 7 days**, slowest **46,300 ms**; the supplier HTTP calls inside it (`api.digiflazz.com/v1/price-list`, `api.gamevion.com/api/product`) are ~10 s each. It monopolises the single-process `default` Horizon queue, so `PurgeNextCatalogCache` (ADR-071 PR2, the job that tells the storefront to drop its Next.js Data-Cache tag) queues behind it — turning the intended ~2 s propagation into tens of seconds during a sync.
4. **The "must refresh 2–3 times" symptom** (reported by the founder after ADR-060 went live, and previously logged as a post-deploy item). Root cause is a compound of layers: `PurgeNextCatalogCache` is `->afterCommit()` + queued + `ShouldBeUnique(uniqueFor: 10)`; then the Next.js side calls `revalidateTag(CATALOG_TAG, "max")` (`storefront/src/app/api/revalidate/route.ts`) — the `"max"` argument is stale-while-revalidate, so the first request after a purge is served the **old** value and only *triggers* a background regen; the request after that is fresh. On a low-traffic storefront the founder is "the next request", so: refresh → stale, refresh → stale (regen not done), refresh → fresh.
5. **Three admin/middleware write paths change storefront output with no cache invalidation at all** (confirmed by reading each): `Admin\AffiliateMembershipTierController::update` (wholesale-tier `markup_percent` — re-prices every storefront on that tier), `AffiliateSubscriptionService` + `AffiliateTierFeeService` (a subscription lapsing — which happens automatically from the nightly `app:charge-affiliate-tier-fees` job with no human in the loop — flips `Affiliate::wholesaleTierMarkupPct()` between a value and `null`, moving every price on that brand), and `Middleware\SupplierController::updatePackagesStatus` (the ADR-046 "supplier is down, deactivate all their packages" tool — flips `is_active` on hundreds of `packages` rows). None mis-charges money (checkout re-prices live from `Package`/`Affiliate` rows), but the **displayed** price can disagree with the **charged** price for up to ~2 minutes, which reads as broken.
6. **Missing DB indexes** on hot read paths. Cross-checked against every migration: `ledger_entries` has only `(owner_type, owner_id)` — nothing on `(type, reference_type, reference_id)`, which `ReportService::profitTotals`/`profitByKey`/`exportRows` and `DashboardService::summary` (called twice per dashboard load) scan on every call; `orders` has no index on `customer_email` (Customer Analytics), no `(delivery_status, updated_at)` (Dashboard health, 3× per poll), only a single-column `affiliate_id` index (affiliate-portal order list filesorts on `created_at`); `supplier_products` has nothing on `(supplier_id, group_label)` despite everything grouping by it; `supplier_request_logs` has no standalone `created_at` for its retention-delete.
7. **One real N+1**: `ResellerCatalogService::listAvailable()` (`GET /api/reseller/v1/catalog`) loops ~486 games calling `Package::cheapestActivePerGame($id)` once each, and is **not cached at all**. (The storefront `CatalogController` paths are already correctly eager-loaded and cached — this is the only genuine N+1 in the read layer.)
8. **`ReportService` / `DashboardService` aggregate in PHP.** Seven of `ReportService`'s methods (`dailyTrend`, `dailyBreakdown`, `gameBreakdown`, `paymentMethodBreakdown`, `affiliateBreakdown`, `membershipBreakdown`, `exportRows`) do `->get()` then aggregate in a `foreach`; with a null year filter this pulls **every paid order in history** into memory on each Reports-tab load. `DashboardService` caches nothing (deliberate, ADR-049/050). The full rewrite is money-critical (an order carries *two* `order_profit` ledger rows — platform + affiliate split — so a naive JOIN would double-count `final_amount`; the day-bucketing is in `Asia/Kuala_Lumpur`) and overlaps the founder's already-planned Reports restructure (Membership + Reseller dimensions together — see the `reports-restructure-backlog` memo). **This ADR does the index and the cheap collapse only; the grouped-SQL rewrite is deferred to that restructure ADR so it is grilled once, properly.**
9. **Pulse itself is under-configured for this job.** `PULSE_SLOW_QUERIES_THRESHOLD` / `PULSE_SLOW_REQUESTS_THRESHOLD` are 1000 ms, so Pulse is blind to N+1 and to the 200–900 ms queries that matter at scale; `PULSE_INGEST_DRIVER` is `storage` (recorders write on request termination, not offloaded to Redis); `PULSE_DB_CONNECTION` is unset so Pulse writes its samples to the same MySQL it is measuring.

**Decision:**

1. **Cut the application cache store from `database` to `redis`** (`CACHE_STORE=redis`). This reverses the app-wide-store half of ADR-014/019 — that choice predated Redis in this stack (ADR-048), and Pulse now shows the `database` `cache` table is the single biggest latency source in production. Redis (`config/database.php` `redis.cache` connection, DB 1 — already provisioned, already used by `catalog_packages_store` and Pulse's dashboard-render cache) has no table locks, microsecond reads, and native tag support. `SESSION_DRIVER` stays `database` (sessions are a separate concern, unaffected). Rollback is a one-line env flip back to `database` + deploy.
2. **Set a Redis eviction policy: `maxmemory 512mb` + `maxmemory-policy volatile-lru`.** The Forge box's Redis is a single instance shared between the queue (DB 0, no TTLs on job data) and the cache (DB 1, everything TTL'd). `volatile-lru` evicts only keys that carry a TTL, so a cache-key flood can never evict queued-job data. `allkeys-lru`/`allkeys-lfu` were rejected for that reason; LFU's marginal edge on a catalog access pattern does not outweigh the queue-safety of `volatile`. The one `Cache::forever()` call site (`OpenWaSessionStatus.php:27`, `openwa:session_status`) is changed to a long TTL (1 hour) so it too is eviction-safe — it self-heals on the next `session.status` webhook. `REDIS_CACHE_LOCK_CONNECTION` is set to `cache` (DB 1) so cache locks stop landing in the queue DB.
3. **Add a scheduled `cache:prune-stale` (daily).** Harmless on Redis (no-op), and it keeps the `database` store from bloating during the cutover window and in any environment left on `database`.
4. **Kill the per-brand key-loop; use Redis tags.** With Redis as the default store, `CatalogController::forgetIndexCache()` stops looping `Affiliate::withTrashed()->pluck('id')` and instead flushes a `catalog.index` tag — one operation regardless of affiliate count. `catalog_packages_store` **stays a separate named store** (its per-game / per-brand tags already work and are harmless); only the affiliate-loop smell is removed. The `Cache::remember()` values stay `->toArray()`/`->toISOString()`-normalised as AGENTS.md requires — Redis serialisation would tolerate objects, but the discipline costs nothing, is already universal in the code, and keeps the store swappable.
5. **Fix the three un-invalidated write paths (decision 5 in Context):**
   - **Observer** on `AffiliateSubscription` and `AffiliateMembershipTier` (`saved` + `deleted`). The observer resolves the affected affiliate id(s) — for a tier change, `AffiliateSubscription::where('affiliate_membership_tier_id', $tier->id)->pluck('affiliate_id')` — and calls `CatalogController::forgetCacheForBrand($id)` for each. The observer is the right mechanism here specifically because the lapse path fires from a scheduled job where no one would remember to add a manual call; this matches the codebase's existing `Order`/`PriceSyncRun`/`BackupRun` observer precedent.
   - **Explicit call** in `Middleware\SupplierController::updatePackagesStatus`: after the bulk `Package::query()->update(...)`, collect the affected `game_id`s and loop `CatalogController::forgetPackagesCache($id)` (which already fires `NextRevalidation::purge()`), then `forgetIndexCache()` once — mirroring exactly what `SyncSupplierPricesJob` does. An observer on `Package` would **not** fire here: a query-builder mass `update()` bypasses Eloquent model events, so this path must be explicit.
6. **Reduce Price Sync cadence to hourly** (`PRICE_SYNC_INTERVAL_MINUTES=60`). Supplier catalogue prices do not move on a 10-minute timescale; Price Propagation remains manually triggerable from the Price Sync Center for when a real change needs to land immediately. `->withoutOverlapping()` is already on the schedule entry.
7. **Give `PurgeNextCatalogCache` its own Horizon queue and supervisor.** A new `revalidation` queue + `supervisor-revalidation` (`maxProcesses: 1`, ahead of `default` in the `waits` priority) so a Price Sync run on the `default`/`price-sync` queues can never delay a storefront cache purge. `uniqueFor` on the job drops from 10 s to 5 s so two edits a few seconds apart each get a timely purge while a genuine burst still collapses.
8. **`SyncSupplierPricesJob` fan-out fix.** Hoist `CatalogController::forgetIndexCache()` and `NextRevalidation::purge()` out of the per-affected-game loop — call `forgetPackagesCache($gameId)` per game (its per-game tag flush is cheap and necessary), then `forgetIndexCache()` + one `NextRevalidation::purge()` after the loop. Currently a sync touching K games with N affiliates does K×N `Cache::forget()` calls and K revalidation HTTP dispatches.
9. **Eliminate the stale-while-revalidate double-serve on the storefront.** Drop the `"max"` argument from `revalidateTag(CATALOG_TAG, "max")` in `storefront/src/app/api/revalidate/route.ts` so a purge forces a blocking regeneration on the next request (the request that follows a purge is fresh, not stale-then-fresh). `storefront/src/lib/cache.ts` `catalogCache.revalidate` drops from `60` to `30` as a pure failure backstop (the purge webhook is the freshness mechanism). The exact Next.js API used to achieve the blocking behaviour is an implementation detail for the build — a Route Handler cannot invoke a Server Action, so `updateTag`'s blocking mode is not directly available; plain `revalidateTag(tag)` without the SWR argument is the expected route.
10. **`ResellerCatalogService::listAvailable()`** — replace the per-game loop with one `Package::whereIn('game_id', $ids)->where('is_active', true)->get()->groupBy('game_id')` + PHP dedupe, and wrap the shaped listing in `Cache::remember('reseller.catalog.available', 60, …)` returning a plain array (mirroring `CatalogController::packages`). Pricing stays the caller's job (per reseller tier), so the cached value is tier-independent — one key. Its invalidation hooks into the same `forgetPackagesCache`/`forgetIndexCache` choke points.
11. **Index migration** (one migration, additive, plain `migrate` against the local dev DB per the AGENTS.md gotcha, `SHOW INDEX` verification on MySQL, 64-char identifier-name check):
    - `ledger_entries` → `(type, reference_type, reference_id)`
    - `orders` → `(delivery_status, updated_at)`
    - `orders` → `customer_email`
    - `orders` → replace the single-column `affiliate_id` index with `(affiliate_id, created_at)` — **PR-4 build note (2026-09-07): pulled from PR-4 and deferred to the Reports restructure ADR.** On MySQL the only `affiliate_id` index is the FK-support index; adding the composite makes InnoDB drop it as redundant, leaving the composite as the FK's sole support, so `down()` (and the concurrency suite's `DatabaseMigrations` rollback) then fails `1553 Cannot drop index … needed in a foreign key constraint`. A safe swap = drop + re-add the FK on the `orders` money table (row re-validation lock) for a filesort that only bites past thousands of orders per affiliate. Not worth it as a drive-by; folded into the ADR that already owns the affiliate reporting dimension.
    - `supplier_products` → `(supplier_id, group_label)`
    - `supplier_request_logs` → `created_at`
12. **`ReportService::summary()` collapse only** — its three separate `scopedOrders(...)` passes (sum, count, first) become one `selectRaw('SUM(final_amount) …, COUNT(*) …')` + the single `latest` query. **The grouped-SQL rewrite of the seven PHP-aggregation methods is explicitly deferred** to the planned Reports restructure ADR (which will also add the Membership/Reseller breakdown dimensions) — so the timezone-bucketing and the double-count-safe profit rollup are grilled once, in the ADR that owns Reports. The `ledger_entries` index (decision 11) removes the acute pain in the meantime.
13. **Pulse tuning** (folded here because it is downstream of decision 1's "reduce MySQL load"): `PULSE_INGEST_DRIVER=redis` with a dedicated `PULSE_REDIS_CONNECTION` on Redis DB 2 (not DB 0 — that is the queue); `PULSE_SLOW_QUERIES_THRESHOLD=200`, `PULSE_SLOW_REQUESTS_THRESHOLD=500`. `PULSE_DB_CONNECTION` is left unset — on a single MySQL box a second "connection" to the same server does not reduce load, and moving ingest to Redis already takes the write path off the request thread. 7-day retention unchanged.

**Explicitly out of scope** (and why): the grouped-SQL rewrite of `ReportService`'s breakdown methods (deferred to the Reports restructure ADR, decision 12); Cloudflare R2 for gallery/backup storage (its own future ADR, `cloudflare-r2-storage-backlog` memo); managed Redis (a later follow-up, ADR-020's own note — the box's own `redis-server` is fine at this scale); a cross-Vercel-instance proxy-cache invalidation mechanism (ADR-078 decision 3 covers the proxy staleness with a shorter TTL instead); tuning `supervisor-default`'s process count or any other Horizon scaling (no throughput problem — the issue is queue *priority*, fixed by decision 7's dedicated queue).

**Rationale:**

- The founder's instinct on the earlier ADR-071 grill — "do we even have a scale problem?" — was right then and is wrong now only in one specific place: the `database` cache table. Pulse's 52-second `select from cache` is not a perceived-latency artefact, it is a real lock storm, and it is the one backend-throughput problem this system actually has. Moving to Redis is the highest-leverage change and it is a reversal of a recorded decision, so it earns a full ADR entry with the Pulse evidence attached.
- `volatile-lru` over `allkeys-*` is the "reliable" choice the founder asked for: a cache flood is a self-correcting nuisance, an evicted queued job is a lost order.
- The observer-vs-explicit split for the three un-invalidated paths is not arbitrary: the subscription-lapse path has no human in the loop (nightly job), so it needs the mechanism that cannot be forgotten; the supplier-bulk path is a query-builder mass update that Eloquent events do not see, so an observer there would be a silent no-op.
- Deferring the `ReportService` rewrite is the discipline the `reports-restructure-backlog` memo already asked for — patching it here, separately from the dimensional restructure, would mean grilling the money-critical bucketing and profit-rollup logic twice and half each time.
- Recording this before any code, with the three-round grill captured, follows the project's "record decisions, don't just make them" practice — a future reader needs to know the `database`→`redis` cutover was deliberate and evidence-driven, not drift, and why `volatile-lru` specifically.

**Consequence to track:**

- **`docs/prd.md` §14/§15** — log each PR as it ships; §15's storefront/performance and money-core areas get status lines.
- **The Redis cutover is a cold-cache event** — the first request after deploy misses every key and rebuilds. On a low-traffic storefront this is a handful of slow requests over ~60 s, not an outage. Confirm on the Vercel preview / first prod hit.
- **`volatile-lru` depends on the Forge box actually having the policy set** — it is a `redis.conf` edit + restart, delivered by the PR-1 wizard, not by code. If the box is left on the default (`noeviction`), a full Redis refuses new cache writes (writes throw) rather than evicting — worse than the current state. The wizard must verify `CONFIG GET maxmemory-policy` after the change.
- **Pulse ingest on Redis DB 2 needs that DB to exist and be uncontended** — confirm `PULSE_REDIS_CONNECTION` points at a connection block that resolves to DB 2, and that nothing else uses it.
- **The `catalog.index` tag flush replaces a loop that also covered soft-deleted affiliates** — confirm a deactivated/soft-deleted brand's stale index entry is still reached by the tag (it is, if the tag is on the key not the affiliate row), or is harmlessly orphaned.
- **Lowering Price Sync to hourly widens the window where a real supplier price change is stale on the storefront** — up to 1 hour vs 10 minutes. Accepted because (a) real supplier moves are rare, (b) Price Propagation is manually triggerable, (c) the payable total is always server-recomputed at checkout. Revisit if a supplier starts moving prices intraday.
- **The `"max"`→plain `revalidateTag` change makes the first post-purge request slower** (genuine cache miss, blocks on regen) instead of instant-but-stale. This is the intended trade: correct-immediately over fast-but-wrong. If p75 TTFB after a catalog edit becomes a complaint, PR-3's `catalogCache.revalidate: 30` backstop can be tuned, or PPR revisited (ADR-071 decision 4).
- **`ReportService::summary()` is called twice per Dashboard load** (`DashboardService::summary` runs it for two comparison windows) — the collapse halves that cost but the real fix is the deferred rewrite + the decision-11 index. Track whether Dashboard load time is acceptable post-PR-4; if not, that is the trigger to pull the Reports restructure forward.
- **ADR-014's "cache values must be plain arrays" rule is now belt-and-braces, not load-bearing** — Redis would not corrupt a nested object. Keep the rule (portability, and it is already universal), but a future reader should know the original hard reason is gone.
- **`RouteNotFoundException` / `CommandNotFoundException` in Pulse Exceptions** are handled in ADR-078 (root route) and noted as non-reproducible-from-repo respectively — not this ADR's scope, cross-referenced so a reader chasing the Pulse data lands in the right place.
