# ADR-075: Reseller Bot channel — OpenWA WhatsApp gateway, group-identity mapping, deploy topology

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-04, same grill session as ADR-072/073/074. Depends on ADR-073 (consumes the same order-placement contract as ADR-074, over a different transport).

**Context:**
- The founder's target market for this channel is WhatsApp-community sellers who are already comfortable buying stock through a command-driven bot (`.order ML86 12345`, `.listmlmy`, a saldo/role "Info Akun" reply) — reference screenshots of real competitor bots (`tomystarkdiamond`, `neetstore.id`) confirm this exact UX pattern is the market norm, not a novel design.
- Chosen gateway: [OpenWA](https://github.com/rmyndharis/OpenWA) — a self-hosted, community-maintained Node 22/NestJS 11 WhatsApp API gateway (13.7k GitHub stars), REST API + HMAC-signed webhooks, multi-session support, two swappable WhatsApp engines (`whatsapp-web.js`: ~300-500MB RAM/session, lower ban risk; `baileys`: ~30-80MB/session, higher ban risk), API-key auth scoped admin/operator/viewer.
- **How resellers actually use bots like this in practice** (founder, confirmed against the reference screenshots): a reseller adds the platform's one bot number into the WhatsApp group(s) they manage; every order command sent inside that group is attributed to whichever `Reseller` account the group is linked to. The trust boundary is **group membership**, not individual sender phone number — the reseller controls who is in their own group.
- Production infra (ADR-020/066 provisioning addendum): one DigitalOcean droplet, **4 GiB RAM / 2 vCPU**, currently running nginx + php-fpm + Redis + Horizon + Reverb at an estimated ~2.6 GiB peak — roughly 1.4 GiB of headroom before ADR-020's own named alert trigger (sustained RAM > 70%).

**Decision:**

1. **One shared OpenWA session/WhatsApp number for all `Reseller` (wallet) Bot-channel accounts**, not a dedicated number per reseller. No whitelabel/branding need exists on this channel (unlike `Affiliate`), so there is no product reason for a reseller-specific bot identity in v1; OpenWA's multi-session support means this can be revisited if a real per-reseller-number ask ever surfaces.
2. **New table `reseller_whatsapp_groups`** — `whatsapp_group_id`, `reseller_id`, `is_active`. This mapping *is* the per-account identifier for this channel, replacing what would otherwise be an individual-phone-number lookup. A message from any member of a mapped, active group is treated as an order attempt from that `Reseller` account.
3. **Group membership is the trust boundary for v1 — no per-sender allow-list within a group.** Matches the observed real-world pattern (the reference bots show no evidence of gating by individual number inside a trusted group) and keeps the reseller, who already controls their own group's membership, responsible for who can spend their wallet. A phone-number allow-list inside a group is a clean later addition if abuse is ever observed — not built speculatively now.
4. **Authentication between OpenWA and the backend is a shared, service-level HMAC webhook secret, plus a network-level restriction the Digiflazz precedent doesn't have.** The HMAC half mirrors `DigiflazzWebhookController` exactly: `X-Hub-Signature`-style HMAC over the raw body, secret stored the same way `Supplier.api_config['webhook_secret']` is (`encrypted:array`, never exposed via any API response) — no per-reseller secret on this channel (the group-id mapping, decision 2, identifies the individual reseller; the webhook secret only proves the inbound event genuinely came from the platform's own OpenWA instance). **Unlike Digiflazz's IP check (deliberately soft/log-only there, because that traffic crosses the public internet through an unreliable proxy chain), this webhook is co-located on the same droplet as OpenWA (decision 6)** — so nginx additionally **hard-restricts the route to `127.0.0.1`** on top of the HMAC check, a strictly stronger posture the Digiflazz pattern was never designed for and shouldn't be copied verbatim past.
5. **The webhook receiver and command parser are a new, small, dedicated module** — not bolted onto `CheckoutController` or any existing controller. It translates a parsed WhatsApp command into a call against ADR-073 decision 4's same internal order-placement service ADR-074's HTTP endpoint calls (including that contract's idempotency requirement — this channel's key is derived from `(whatsapp_message_id, group_id)`, since a chat command carries no client-generated key of its own and OpenWA's webhook can redeliver the same inbound message), and replies via OpenWA's own send-text REST endpoint using the platform's OpenWA API key (decision 6). **Per-`Reseller`-account rate limiting (ADR-073 decision 9) applies here too**, keyed on the `reseller_id` resolved from the group mapping (decision 2) rather than an API key or IP — the same requirement ADR-074 decision 4 states for the API channel, restated here because it doesn't automatically carry over between two differently-shaped ADRs. Minimum viable v1 command set (order placement, price-list, balance/status check) is a build-time detail, not decided further here.
6. **OpenWA runs on the existing production droplet, as its own Forge background process** (the same pattern already proven for Reverb — a persistent Node daemon + a dedicated nginx location block), not a separately-provisioned server. **Engine: `whatsapp-web.js`, not `baileys`** — despite the larger RAM footprint (~300-500MB vs. ~30-80MB for one session), the lower ban-detection risk is decisive because this channel *is* a reseller's live paid ordering path; a ban is an outage of their business, not a cosmetic degradation. **The droplet is proactively resized 4 → 8 GiB when this ships** (a single reboot, no data loss — the same "start small, resize live" mechanism ADR-020's own provisioning addendum already established and priced, ~$28 → ~$48/mo), rather than fitting OpenWA into the existing ~1.4 GiB headroom and risking crossing ADR-020's own 70%-RAM alert trigger. This matches the founder's own stated reliability-over-cost priority (ADR-020's governing rationale) for a newly-added, money-adjacent persistent process.

**Rationale:** Decision 2/3 (group-id as the identity key, group membership as the trust boundary) is the single structural insight this ADR turns on — it correctly models how these bots are actually used in the market the founder is targeting (one bot serving many resellers' groups) rather than the individual-phone-number model this assistant initially assumed before the founder corrected it. Decision 6's engine choice trades RAM for reliability deliberately, consistent with every other production-infra decision this codebase has made (ADR-020's Managed MySQL over self-hosted, Redis provisioned early, etc.) — this channel is new revenue infrastructure, not a nice-to-have.

**Consequence to track:**
- Decision 6's droplet resize is a cost commitment (+$20/mo) that should happen *when this channel actually ships*, not speculatively ahead of it — tie the resize to this ADR's own build addendum, not to ADR-020's general capacity monitoring.
- OpenWA itself needs its own DigitalOcean Droplet Backups/monitoring coverage once running in production (it now holds a WhatsApp session's auth state) — fold into the existing droplet-level backup/monitoring ADR-020 already has, don't stand up a parallel mechanism.
- Decision 3 (group-membership trust) is an explicit, named revisit trigger: if abuse or an unauthorized-order dispute is ever observed, that is the trigger to add the per-sender allow-list, not a hardening pass done preemptively.
- `foundation-security.md` should gain a line for this channel's specific fraud surface (a compromised or shared WhatsApp group could place unauthorized orders against a real balance) alongside the existing MFA-debt note for admin/reseller/portal auth.

**Addendum — 2026-09-04 (grilled separately, same day, three rounds via `/mattpocock-skills:grilling`): Reseller catalog code scheme (PR-E0), shared by ADR-074 decision 3 and ADR-075 decision 5.**

Both ADR-074 decision 3 and ADR-075 decision 5 deliberately deferred "exact payload/command shape" as a build-time detail. Getting there surfaced a real design question neither ADR had actually settled: given the storefront already carries multiple `Package` rows per `(game_id, denomination)` (one per supplier, ADR-034), what does a reseller's price list actually show, and what identifier do they order against? This addendum resolves it — for both channels identically, since PR-E and PR-F consume the same catalog.

**Context:**
- Naively exposing `Package.id` as the order-time identifier is what the storefront already does (`CatalogController::packages()`), but it's unstable across a supplier swap (ADR-031's bulk-deactivation remediation, or SYNC-5/6 reactivation, can change which `Package` row is the active cheapest at any (game, denomination) at any time) — unacceptable for an external reseller expected to hardcode a product catalog into their own system.
- First draft considered writing a synthetic value into `packages.denomination` for bundle/pass items (which stay `null` forever per ADR-034's own migration comment) so they'd get a code too. Checked against real code before accepting: `CatalogController::dedupByDenomination()` groups strictly by `(game_id, denomination)` and treats every row in a group as an interchangeable substitute, picking the cheapest — the exact mechanism that lets 2-3 suppliers' equivalent "14 Diamond" packages coexist active and dedup correctly today. A synthetic bundle/pass number sharing that same numeric space risks a false-equivalence bug (a pass silently deduped against an unrelated real-value package that happens to get the same number later) — this is not a hypothetical, it directly contradicts what the dedup mechanism assumes. Rejected.

**Decision:**

1. **New column `games.reseller_code`** — string, nullable, `[A-Z]{2,10}`, unique globally (not per-game), admin-set once in `EditGameModal.tsx`. A `Game` with no `reseller_code` is simply excluded from both reseller channels' catalog — no effect on the storefront.
2. **New column `packages.catalog_code`** — string, nullable, must contain at least one non-digit character (never a bare numeric string), normalized to uppercase on both save and lookup. **Mutually exclusive with `denomination`** at the `FormRequest` layer (`prohibits` each other) — a `Package` carries exactly one of the two, or neither (not yet curated).
3. **`packages.denomination` and ADR-034's existing dedup are entirely unmodified** — no addendum to ADR-034 itself, no behavior change for any package that already has a `denomination`. Bundle/pass packages get their own identifier via `catalog_code` instead of overloading `denomination`.
4. **Dedup runs over two independent key spaces, extended (not replaced) from ADR-034's query:** `(game_id, denomination)` exactly as before, and a new parallel `(game_id, catalog_code)` group for packages where `denomination` is null. A pass numbered via `catalog_code` can never collide with a real-value package, by construction — they occupy different columns of different types, not just different values of the same column. Multiple active packages sharing the same value in *either* space is intentional (multi-supplier equivalence, admin-curated) — this addendum adds **no new DB uniqueness constraint**; the only collision risk it set out to prevent (cross-space false-equivalence) is now structurally impossible rather than something to police at write time.
5. **The storefront gains the same `catalog_code` dedup for bundle/pass items** as a direct consequence of decision 4 extending the shared query (see decision 7) — previously every supplier's bundle/pass showed individually with no best-price selection; this closes that gap for free rather than scoping the extension to the reseller channels only.
6. **Public reseller product code = `{reseller_code}-{denomination-or-catalog_code}`** (e.g. `MLMY-14`, `MLMY-P1`). Lookup parses the trailing segment after the game's `reseller_code`: an all-digit remainder resolves via `denomination`, anything containing a letter resolves via `catalog_code` — unambiguous given decision 2's charset rule. `Package.id` and `supplier_package_ref` are never present in either channel's response, matching the storefront's existing narrow-response-shape discipline (`backend/AGENTS.md`).
7. **Shared resolution logic, one seam, two callers:** `Package::cheapestActiveFor(int $gameId, ?int $denomination, ?string $catalogCode): ?Package` — extracted from `CatalogController`'s existing private `dedupByDenomination()` — is called by both `CatalogController` (storefront) and the new `App\Services\Reseller\ResellerCatalogService::resolveByCode(string $code): ?Package` (reseller channels), which handles the `reseller_code`/code parsing (decision 6) before delegating. `ResellerCatalogService` sits alongside the already-shipped `ResellerOrderPlacementService` (PR-D, same namespace) and returns the raw `Package` — pricing (`PricingService::calculateForAffiliate()`, same rounding convention `ResellerOrderPlacementService` already uses: `(int) round()`, no separate helper exists in this codebase) is resolved by the caller (the API controller for a listing response, the Bot command handler for a quote), mirroring `ResellerOrderPlacementService`'s own DTO contract where the caller — not the service — resolves price inputs before calling in.
8. **A code with zero active packages behind it (all deactivated — the ADR-031 bulk-remediation scenario) is an explicit "unavailable" state, not a silent 404/empty response**, for both channels: the API's listing marks it `available: false` and rejects an order attempt against it with 422/409; the Bot replies with explicit text rather than failing silently.
9. **Listing price and order-time charge price are each freshly computed, with no consistency guarantee held between the two calls** — a price sync running between a reseller's list-call and their order-call can shift which `Package` wins decision 7's dedup. Accepted as-is: this is the same invariant this codebase already applies everywhere money is involved (ORD-9 — price is never trusted from the client, always server-computed at the moment of use), not a new risk class introduced by this channel.

**Rationale:** The core insight (decision 2-4) is that the actual risk was never "duplicate values" — active packages sharing a denomination across suppliers is the correct, intended shape of ADR-034's own dedup — the risk was two *semantically different* products colliding in one shared numeric space. Splitting into a second, differently-typed column removes that risk structurally instead of policing it with a DB constraint that would have also broken the legitimate multi-supplier case a first draft of this addendum incorrectly proposed. Decision 7 follows this codebase's established "deep module, stable seam" convention (`AGENTS.md`) — extending `ResellerOrderPlacementService`'s existing shape and extracting the storefront's existing dedup query, rather than standing up parallel logic for the new channels.

**Consequence to track:**
- `EditGameModal.tsx` and `EditPackageModal.tsx` are both touched to add decision 1/2's fields — if either still uses a hand-rolled TailAdmin primitive at that point, ADR-038's opportunistic-migration rule applies (swap to PrimeReact-Tailwind as part of this same change, not a follow-up pass).
- PRD §13 Glossary gains `reseller_code` and `catalog_code` as pinned terms once this ships.
- This ships as its own PR (**PR-E0**, inserted between PR-D and PR-E/PR-F in the phasing table below) — PR-E and PR-F both gain PR-E0 as a dependency, in addition to PR-D.

**Addendum — 2026-10-02 (grilled, two rounds via `/mattpocock-skills:grilling`): OpenWA chat-list rehydration on process restart.**

**Status:** Accepted (design) — build not started.

**Context:**
- Live-production investigation (SSH, 2026-10-01/02) against `pekangame-prod-lwf`'s real OpenWA instance found that OpenWA's dashboard "Chats" list (and the per-chat message view it gates — a chat missing from this list cannot be opened even via the dashboard's own full-text message search, confirmed by reading `Chats.tsx`'s search-hit handler) is built **entirely in-memory** (`BaileysSessionStore`), fed only by live Baileys events. It has no persistence and no rehydration-from-DB step at boot.
- A routine Baileys socket reconnect (statusCode 428/503 — confirmed ~70 occurrences across both sessions in a 2-day log sample) does **not** touch this: the OpenWA Node process stays alive, so the in-memory store is untouched and auto-reconnect is already transparent. Only a full OpenWA **process restart** (crash, manual restart, future redeploy) wipes it — confirmed 2 such restarts in the same 2-day window, from Forge daemon log rotation. Zero `loggedOut`/401 events and zero new QR generations have occurred since the one-time pairing on 2026-09-25 (decision not re-litigated by this addendum — session auth itself is stable).
- WhatsApp does not resend chat/message history to an already-paired device on reconnect (`messaging-history.set` only fires on first pairing, per this codebase's own `baileys-history.ts` comments) — so the in-memory list has no way to repopulate itself except from new live traffic, one chat at a time.
- The underlying messages are durably stored in OpenWA's own `data/openwa.sqlite` (`messages` table, indexed on `chatId` and `(sessionId, createdAt)`) — **no data is actually lost**, but it becomes unreachable from the dashboard UI for any chat that goes quiet across a restart. This is a real operational risk specifically for the `customer-support` session (ADR-116) during an active order-support conversation; founder has explicitly deprioritized `reseller-bot` group-chat visibility (does not care if lost) but does want `reseller-bot` DMs covered.
- Confirmed facts that shaped the decision: `rmyndharis/OpenWA` is a genuine unrelated third-party maintainer (Yudhi Armyndharis), not a founder-controlled account — any patch here is a real fork-and-maintain commitment, not a formality. `.env`'s `ENGINE_TYPE=baileys` is a single global setting, so both sessions run Baileys in production today, **contradicting this ADR's own decision 6** (which specified `whatsapp-web.js` for the reseller-bot channel specifically, for lower ban risk on a live paid-ordering path) — flagged here as a found discrepancy, not resolved by this addendum. Real message volume is tiny (286 messages / 4 chats on `customer-support`, 57 messages / 6 chats on `reseller-bot`, as of 2026-10-01) and there is no staging OpenWA instance — only the single production one.

**Decision:**
1. **Patch at the engine-agnostic `session.service.ts` layer** (`listChats()` unions the live in-memory result with a DB-derived fallback for any `chatId` the DB has that the in-memory store doesn't), not inside the Baileys-specific `baileys-lifecycle.ts` adapter — so the fix keeps working if the engine is ever switched back to `whatsapp-web.js` per this ADR's original decision 6.
2. **Fork `github.com/rmyndharis/OpenWA` and deploy from the fork**, rather than patching the server's checked-out code directly. A direct-server patch is silently lost on the next upstream `git pull`/update with no CI, test, or review gate catching it; a fork survives that and keeps the patch under version control. The fork does **not** track upstream automatically — upstream changes are merged in manually, at the founder's discretion, whenever a release looks worth taking (e.g. security/stability fixes); this patch's own diff is kept small and isolated specifically so a future merge-conflict is cheap to resolve.
3. **Rehydrate chat SUMMARIES only** (one row per `chatId`, derived from a `GROUP BY chatId` / `MAX(createdAt)` read of `openwa.sqlite`'s `messages` table — id, last-message preview, timestamp), not full message bodies. Opening a chat already queries the DB directly (`getChatMessages`) regardless of what's in memory, so backfilling full history into the in-memory store would be pure duplication for zero benefit.
4. **Applies uniformly to every chat on both sessions, including groups** — no special-casing to exclude `reseller-bot` groups. The cost of including them is effectively zero at this volume, and a uniform code path is simpler than a per-session filter for a dimension the founder is merely indifferent to (not asking to actively suppress).
5. **Validated directly against the single production instance** (no staging OpenWA exists) — scheduled for a moment the founder is actively standing by, not an unattended/overnight change. The pre-patch commit is kept on hand as an immediate rollback: if the patched OpenWA fails to boot cleanly after a test restart, Forge redeploys the prior commit directly, accepting a few minutes of WhatsApp-bot downtime over a longer unattended failure.

**Rationale:** The chat-summary gap is not a foreign architecture bolt-on — this same OpenWA codebase already applies the identical "evicted/restarted in-memory cache falls back to a DB-backed read" pattern to two other maps (`lidToPn` lid-mapping, chat mute/pin/archive state), confirmed by reading `.env.example`'s own documentation of those caps. This addendum extends that already-proven, already-idiomatic pattern to the one in-memory map that never received it, rather than inventing new persistence machinery.

**Consequence to track:**
- The `ENGINE_TYPE=baileys`-for-both-sessions discrepancy against this ADR's original decision 6 is a separate, unresolved finding — worth its own revisit (re-litigate the ban-risk trade-off, or correct the ADR to match reality) but explicitly out of scope for this addendum.
- The separate `openwa.sqlite` → Cloudflare R2 backup gap (PRD §16 item 56, extending ADR-095) is being tracked and built independently of this addendum — the two are related (both stem from OpenWA's own storage being outside this project's normal durability guarantees) but are not the same fix.
- Once built, `foundation-security.md`'s existing OpenWA fraud-surface note should gain a line noting the fork now carries platform-authored patches, so a future "redeploy clean from upstream" instinct doesn't silently drop this fix.

### 2026-10-10 addendum — decision 6's engine: Baileys stays until the droplet is upgraded

**Status:** Accepted (founder, 2026-10-10). Resolves the discrepancy flagged in the 2026-10-02 addendum (§16 item 59). Overrides decision 6's engine choice for now.

- **What is true.** Both OpenWA sessions (`reseller-bot`, `customer-support`) run `baileys`, because `ENGINE_TYPE` is one global setting. Decision 6 asked for `whatsapp-web.js` on the bot, for lower ban risk, with the droplet resized 4 → 8 GiB first.
- **Decision.** Keep Baileys on both sessions. Decision 6's engine choice is parked, not abandoned: it comes back with the host resize (§16 item 4).
- **Why, checked on prod 2026-10-10.**
  - The box has 3.9 GB RAM, 2.1 GB used, 1.8 GB available. The resize decision 6 assumed never happened.
  - OpenWA on Baileys uses about 230 MB for both sessions. `whatsapp-web.js` runs Chromium, about 300-500 MB per session (decision 6's own figure), so about 1 GB for two, which crosses ADR-020's 70% RAM alert.
  - Switching re-pairs both numbers by QR scan, and the bot and customer notifications are down until each is done.
  - Baileys has been stable: no `loggedOut` and no new QR since pairing on 2026-09-25, and 428/503 reconnects recover on their own. Volume is small (2026-10-01: 286 messages / 4 chats on `customer-support`, 57 / 6 on `reseller-bot`). Send pacing, typing simulation and the one-worker `whatsapp` lane (ADR-116) are the ban mitigation.
- **Triggers to revisit** (any one):
  - the droplet is upgraded (§16 item 4), so the RAM objection is gone;
  - WhatsApp warns about or bans either number;
  - `reseller-bot` volume grows until one ban costs more than the resize.
- **Not checked.** Whether OpenWA can set the engine per session. Settle that before any switch, since a global switch would also move `customer-support`.
