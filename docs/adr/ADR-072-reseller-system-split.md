# ADR-072: Reseller-system split — `Affiliate` (whitelabel) vs `Reseller` (prepaid wallet), full rename, shared portal architecture

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** BUILT + LIVE + PROD-VERIFIED end-to-end 2026-09-06 (the whole 072..076 family — rename, wallet, API channel, Bot channel — is code-complete and verified against real OpenWA + real CHIP; release PR #110). Original: Accepted (design) — 2026-09-04, grilled with the founder over six rounds via `/mattpocock-skills:grilling` before any code was written. First of a four-ADR family (072-075) from one grilled design, split by natural boundary — same convention as ADR-056..061. The "Build addendum" sections land as each PR in the phasing note (end of ADR-075) ships.

**Context:**
- ADR-056..061 built a single `Reseller` model shaped entirely around one business relationship: a whitelabel storefront partner who subscribes to a paid wholesale tier, sets their own markup, and earns margin credited to a ledger account after each sale. ADR-060 (branded storefront + Cloudflare custom domains) is designed against this same shape and remains unbuilt.
- The founder is opening two more delivery channels that do **not** fit that shape: **Reseller API** (an external system connects directly to a documented HTTP API to place orders) and **Reseller Bot** (the same underlying flow, but the reseller places orders by WhatsApp command instead of code — self-hosted via [OpenWA](https://github.com/rmyndharis/OpenWA), a NestJS/TypeScript multi-session WhatsApp API gateway with its own REST API + HMAC-signed webhooks). Both are a **prepaid-wallet** model — the reseller deposits MYR sen first, then every order debits that balance at an admin-assigned tier's rate over `cost_price` — structurally the mirror of PekanGame's own relationship with Digiflazz/Gamevion, not the retail-collect-then-split-ledger model the existing `Reseller`/ADR-060 shape assumes.
- Forcing all three business relationships onto one `Reseller` table (with a `channel` discriminator and a growing set of conditionally-relevant columns — `domains`, `reseller_branding`, `membership_enabled`, a subscription-fee tier vs. a fee-less wallet tier, a human-login portal token vs. a machine API key) is exactly the tangled shape the founder flagged as hard to debug/maintain/scale — none of the whitelabel-specific machinery (branding, custom domain, portal-login-only auth) is meaningful for a wallet reseller, and none of the wallet-specific machinery (deposit balance, API key, WhatsApp group mapping) is meaningful for a whitelabel affiliate.
- No wallet/deposit table, no reseller-facing order-CREATE endpoint, and no machine-facing (API-key/webhook) auth exists anywhere in the codebase today (confirmed by direct grep before this ADR was drafted).

**Decision:**

1. **Two entities, not one table with a discriminator, and not three fully separate tables.** The existing `Reseller`/`resellers` (branding, `domains`, `reseller_users` portal login, ADR-056..061's subscription-tier + earnings-ledger machinery) is renamed to **`Affiliate`/`affiliates`** — its shape is unchanged, only the name. A new entity, **`Reseller`/`resellers`** (reclaiming the vacated name — "reseller" is the more accurate term for a wholesale buyer than for a whitelabel storefront partner), holds the prepaid-wallet model shared by the API and Bot channels — they are **one entity with an `interface` capability**, not two tables, because their money/tier logic is byte-for-byte identical and only the ordering transport differs (Reseller API vs Reseller Bot channel presence, decision 5).
2. **Full rename, not a cosmetic/UI-only relabel.** The founder's explicit call, overriding this assistant's initial "defer it, it's just churn" recommendation (the `AGENTS.md` `kedairuncitsoloz`/`topup-website` precedent doesn't apply here — that internal name has zero user-visible collision risk; `Reseller` colliding with the *new* wallet entity's own natural name does): every reference — model class, table name, all ~28+ non-test call sites, the `admin/`/`reseller/` frontend TypeScript types, route segments, PRD `RES-1..6` IDs, glossary — is mechanically renamed. Justified because the refactor is happening anyway and doing it now means every later PR (073-075) is written against the correct final names, not against a name that gets swapped out from under it.
3. **One shared portal app.** `Affiliate` and `Reseller` accounts both log into the existing `reseller/` Next.js app to view their own dashboard/performance — no fourth Next.js app. Rejected splitting into separate apps: the actual security boundary is the backend's tenant-scoping (`BelongsToReseller`/`ResellerScope`, ADR-057 — guard-keyed, deny-by-default, unaffected by how many frontend apps exist), not the app count; a fourth app repeats the CI/deploy/env-surface cost ADR-059 already flagged for the third app, for security the backend already provides.
4. **Backend `owner_type` authorization gate is mandatory on every reseller-guard endpoint, not just conditional frontend rendering.** The portal must never rely on hiding a nav tab as its only defense against, e.g., a `Reseller` (wallet) account calling an `Affiliate`-only endpoint (Withdrawal, Subscription) or vice versa. A small `EnsureAccountType(affiliate|reseller)` middleware/policy, applied per-endpoint and covered by a test per endpoint, is the actual control — added to this refactor's review checklist the same way ADR-059 added "grep for `DB::table(` in reseller-context code" to its own.
5. **`reseller_users` (portal login credential table) becomes polymorphic** — `owner_type` (`affiliate` | `reseller`) + `owner_id`, replacing its current implicit single-`Reseller`-FK shape. This mirrors the `LedgerOwnerType` idiom already established in this codebase (ADR-059) rather than inventing a new "which kind of tenant" pattern. Portal screens branch on `owner_type`: an `Affiliate` account keeps today's seven screens (Dashboard/Orders/Earnings/Subscription/Withdrawal/Profile/Impersonation) unchanged; a `Reseller` (wallet) account gets Dashboard/Orders/Wallet(balance + topup + ledger)/Profile/API-key management — no Withdrawal (a wallet reseller only spends, never earns) and no Subscription-fee screen (the wallet tier carries no fee — ADR-073 decision 1).
6. **Registration stays admin-created for both, no self-serve signup** — consistent with the existing `Affiliate` policy (ADR-058 decision 2) and, for `Reseller`, load-bearing given real prepaid deposits are involved (KYC/fraud control stays with the admin, not an open signup form).
9. **`resellers.is_active` (boolean, default true)** — the wallet-account equivalent of `Affiliate`'s RES-5 activate/deactivate. Checked at the top of ADR-073 decision 4's order-placement contract (both channels go through this one choke point); a deactivated `Reseller` cannot place new orders on either channel, but deactivation does **not** freeze the remaining wallet balance — that stays refundable by the admin (ADR-073 decision 3's manual-credit path, run in reverse) if the relationship is ending, exactly mirroring how `Affiliate` deactivation leaves existing earnings withdrawable.
7. **`Reseller` (wallet) never gets consumer Membership**, same as a third-party `Affiliate`. Only `pekangame.space` itself and the founder's own `is_owned` `Affiliate` brand(s) do (ADR-061, unchanged by this rename).
8. **The Cloudflare-fronted branded-storefront work (ADR-060) is explicitly out of scope for this ADR family**, even though it is conceptually "Affiliate" work. It has its own unresolved open questions (logo upload, per-reseller hero slides, the Cloudflare domain-transfer timing) that need their own dedicated grill, and it touches an entirely different risk surface (`storefront/`'s `Host`-resolution + `CheckoutService`'s pricing resolver) than this family's backend/portal/OpenWA surface. **Sequencing dependency, not a scope merge:** ADR-060, whenever it is picked up, must be built *after* this family's rename PR (decision 2 / PR-A in the phasing note) lands — its own text already assumes `Host` resolution replaces `Affiliate::primary()` (né `Reseller::primary()`), so building it before the rename means redoing that swap.

**Rationale:** Decision 1 (two entities, not one table or three) is the load-bearing call — it directly answers the founder's own diagnosis that the current single-table shape is what makes the codebase hard to reason about. Splitting exactly where the *business relationship* splits (storefront-and-earn vs. wallet-and-spend) rather than where a superficial "reseller" label splits (API vs. Bot) keeps every table's columns 100% relevant to what it models, and keeps the two genuinely-identical-underneath channels (API, Bot) sharing one implementation instead of duplicating tier/wallet/order logic across two tables. Decision 3/4 (one portal, backend-enforced boundary) is deliberately the *opposite* instinct from decision 1 — money-critical multi-tenancy is a backend concern already solved by ADR-057, and re-solving it at the frontend-app-count layer would be spending real CI/ops cost on a boundary the backend already guarantees.

**Consequence to track:**
- The rename (decision 2) touches every file that references `Reseller` today — it ships as its own PR (PR-A in the phasing note), zero behavior change, verified by the full existing test suite passing unchanged (the same verification method ADR-061 PR-A used for its own zero-behavior-change refactor). No feature code lands in that PR.
- `docs/prd.md` §6.7 (`RES-1..6`), §13 Glossary, and §8 data-model rows all need updating to the new names once the rename PR ships — don't let the PRD drift to describe a class name that no longer exists.
- ADR-060's own text (written against the old `Reseller` name) needs a terminology-only addendum once the rename ships, mirroring how ADR-013 was marked superseded by ADR-061 rather than rewritten in place.
- Decision 5's polymorphic `reseller_users` is a schema change on a table with real production rows (the founder's own primary `Affiliate` portal users) — the migration must backfill `owner_type = 'affiliate'` for every existing row before making the column non-nullable, same discipline as every other polymorphic-owner migration in this codebase (`LedgerOwnerType`'s own rollout, ADR-059).
- Decision 4's `EnsureAccountType` gate needs a test per existing + new reseller-guard endpoint before this family is considered done — tracked explicitly so it isn't silently skipped under time pressure.

**Build addendum — PR-A shipped 2026-09-04** (`feature/adr-072-pr-a-rename-affiliate`, backend only — `admin/`/`reseller/` frontend types handled by a separate agent/PR). Pure rename, zero behaviour change, verified by the full existing test suite passing with the same pass count as before: **1259/1259** fast (sqlite) + **11/11** concurrency (real MySQL via `docker compose`), Pint clean on every file this PR touched.

- **Models/files renamed (`git mv`).** `Reseller`→`Affiliate`, `ResellerBranding`→`AffiliateBranding`, `ResellerFooterSettings`→`AffiliateFooterSettings`, `ResellerSeoSettings`→`AffiliateSeoSettings`, `ResellerImpersonationSession`→`AffiliateImpersonationSession`, `ResellerMembershipTier`→`AffiliateMembershipTier`, `ResellerSubscription`→`AffiliateSubscription`, `ResellerTierChange`→`AffiliateTierChange`, `ResellerUser`→`AffiliateUser`; `Concerns\BelongsToReseller`→`BelongsToAffiliate`, `Scopes\ResellerScope`→`AffiliateScope`, `Support\CurrentReseller`→`CurrentAffiliate`, `Http\Middleware\SetResellerContext`→`SetAffiliateContext`. Namespace directories renamed: `Http\Controllers\Reseller`→`Http\Controllers\Affiliate` (incl. `ResellerAuthController`→`AffiliateAuthController`), `Http\Requests\Reseller`→`Http\Requests\Affiliate`, `Services\Reseller`→`Services\Affiliate` (`ResellerInviteService`→`AffiliateInviteService`, `ResellerEarningsService`→`AffiliateEarningsService`, `ResellerSubscriptionService`→`AffiliateSubscriptionService`, `ResellerTierFeeService`→`AffiliateTierFeeService`, `ResellerSubscriptionStatus`→`AffiliateSubscriptionStatus`), `Console\Commands\Reseller`→`Console\Commands\Affiliate` (`ChargeResellerTierFeesCommand`→`ChargeAffiliateTierFeesCommand`, plus the test-only `ResellerTestChargeTierFee`→`AffiliateTestChargeTierFee`). - **Migration** `2026_09_04_010000_rename_reseller_tables_to_affiliate` — one new migration, no historical migration edited. Renames 10 tables (`resellers`→`affiliates`, `reseller_branding`→`affiliate_branding`, `reseller_footer_settings`→`affiliate_footer_settings`, `reseller_seo_settings`→`affiliate_seo_settings`, `reseller_membership_tiers`→`affiliate_membership_tiers`, `reseller_subscriptions`→`affiliate_subscriptions`, `reseller_tier_changes`→`affiliate_tier_changes`, `reseller_impersonation_sessions`→`affiliate_impersonation_sessions`, `reseller_users`→`affiliate_users`, `reseller_password_reset_tokens`→`affiliate_password_reset_tokens` — the last two per the resolved decision below, not deferred to PR-G) and every `reseller_id`/`reseller_user_id`/`reseller_membership_tier_id` FK column on them plus `orders`, `memberships`, `membership_otp_codes`, `membership_checkout_attempts`, `redirects`, `seo_scripts`, and `withdrawals` → `affiliate_id`/`affiliate_user_id`/`affiliate_membership_tier_id`. Every FK/unique/index dropped and re-added under an explicit, clean new name (drop uses the *pre*-rename auto-generated name — a table rename doesn't rename its constraints' stored names, so the drop must run before or reference the original identifier).
- **`orders.reseller_markup_pct`/`reseller_profit` also renamed** (→ `affiliate_markup_pct`/`affiliate_profit`), even though these aren't `*_reseller_id`-shaped FK columns and so aren't literally covered by this PR's FK-column instruction — every app call site (`Order::$fillable`, `OrderFulfillmentService::creditProfit()`, `CheckoutService`, `OrderResendService`) was already renamed by the code-level sweep, so leaving the DB columns at the old names would have broken checkout at runtime (`orders has no column named affiliate_markup_pct` — caught by the fast suite). Kept in scope on the same "schema must match the code it's already been renamed to" logic.
- **`ledger_accounts`/`ledger_entries`/`withdrawals.owner_type` data rows** — `LedgerOwnerType::Reseller = 'reseller'` became `LedgerOwnerType::Affiliate = 'affiliate'` (app/Services/Ledger/LedgerOwnerType.php), so the migration also `UPDATE`s every existing persisted `owner_type = 'reseller'` row to `'affiliate'` on all three tables. Missing this would have silently orphaned every real affiliate earnings/withdrawal ledger row in production the moment this PR deployed (every read path now filters on `'affiliate'`) — a real money-visibility bug caught only by tracing `LedgerOwnerType::coerce()`'s `\ValueError` path, not by any test (the fast suite's sqlite DB starts empty).
- **MySQL vs. SQLite index discrepancy (`orders.reseller_id`/`affiliate_id`).** Migration `2026_08_30_110000_add_reseller_id_index_and_backfill_orders` only added a standalone `orders_reseller_id_index` when nothing already covered the column — on real MySQL the earlier FK (`2026_07_25_150100`) had already left its own auto-created `orders_reseller_id_foreign` covering index, so that explicit index was in fact never created there (confirmed via `SHOW INDEX FROM orders` against the project's `docker compose` MySQL); SQLite never auto-indexes FKs, so on the sqlite test DB it *was* created. A first draft of this migration hardcoded `dropIndex('orders_reseller_id_index')` and passed the full sqlite suite but failed on real MySQL (`Can't DROP 'orders_reseller_id_index'; check that column/key exists`) — caught only by running the concurrency suite against real MySQL per this file's own gotcha about verifying FK/index behavior live. Fixed by detecting the actual index name dynamically (`Schema::getIndexes('orders')`) rather than assuming one; the fix mirrors both directions (up/down) and both column names (reseller_id/affiliate_id).
- **`reseller_users`/`reseller_password_reset_tokens` — resolved decision, not deferred.** ADR-072 decision 5 describes `reseller_users` going polymorphic (`owner_type`/`owner_id`) in a *later* PR (PR-G); this PR only renames the table/model/guard now, PR-G's polymorphic conversion is unaffected by that ordering. `reseller_password_reset_tokens` (config/auth.php's `passwords.affiliate_users.table`) was renamed to `affiliate_password_reset_tokens` alongside it for the same reason — leaving it old-named while everything else moved would have been the one visibly inconsistent leftover.
- **`config/auth.php`**: `reseller` guard → `affiliate`, `reseller_users` provider → `affiliate_users`, `passwords.reseller_users` → `passwords.affiliate_users` (table `affiliate_password_reset_tokens`). Every `auth('reseller')`/`auth:reseller`/`Auth::guard('reseller')` call site swept to `affiliate`; `bootstrap/app.php`'s `reseller.context` middleware alias → `affiliate.context`.
- **Routes.** `/api/reseller/*` (portal) → `/api/affiliate/*`; `/api/admin/resellers*` → `/api/admin/affiliates*`. `routes/console.php` scheduled-command references updated to match.
- **Judgment call — `config/services.php`'s `reseller_portal` key and `RESELLER_PORTAL_URL` env var were deliberately NOT renamed**, nor was the `reseller/` frontend directory/deploy target. ADR-072 decision 3 is explicit that the *portal app* stays one shared Next.js app that will host both `Affiliate` and the future wallet `Reseller` accounts (PR-G) — renaming the portal's own config key to "affiliate_portal" now would have to be un-renamed (or made misleading) the moment PR-G ships. Only the class-symbol references inside that config file's comments (`ResellerInviteService` → `AffiliateInviteService`) were updated; `config/cors.php`'s comment referencing the old `/api/reseller/*` route path was corrected to `/api/affiliate/*`.
- **Judgment call — cosmetic constraint/index names on FK columns that were *not* renamed were left as-is** (e.g. `resellers_is_primary_unique` → still that string on the renamed `affiliates` table; `reseller_impersonation_sessions_admin_user_id_foreign`/`_personal_access_token_id_foreign` unchanged). MySQL/SQLite both transparently repoint a FK's target when the referenced table is renamed via `Schema::rename()`, so these keep working under stale-looking names — purely cosmetic, out of scope for a pure-rename PR. One of these, `reseller_impersonation_sessions_personal_access_token_id_foreign`, is exactly 64 characters today (MySQL's identifier limit); renaming it under the one-character-longer `affiliate_impersonation_sessions_` prefix would have pushed it to 65 and failed on real MySQL — leaving it untouched was the correct call, not an oversight.
- **Pint** was run only against the 63 files this PR's rename touched (not the ~67 other files already flagged by `pint --test` before this PR started, which are pre-existing repo drift unrelated to this change) — scoped deliberately per the founder's own "don't touch unrelated files" instruction for this refactor.
