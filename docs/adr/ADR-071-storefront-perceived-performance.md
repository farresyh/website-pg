# ADR-071: Storefront perceived-performance — loading states, prefetchable routes, tag-based revalidation, and mobile buy-flow layout fixes

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-09-03 (grilled with the founder over four rounds via `/mattpocock-skills:grilling` before any code was written; this entry is that shared understanding). Built across PR0–PR3 off `staging`.

**Context:**

The founder reports that the storefront's purchase flow feels laggy and "stuck" on mobile — where ~80% of buyers are — with page transitions that show 1–2s of nothing after a tap and then snap in, a checkout review card and footer text that are clipped, and no skeleton or motion before content appears. A live audit (production, 390px viewport driven through a same-origin iframe harness — the Chrome window would not resize below ~769px) plus a code read established the causes. **None of them are backend throughput** — the backend list the founder wondered about (route/config/view cache, DB indexing, connection pooling, load balancing, read/write splitting, reverse-proxy and process-manager tuning) addresses a scale problem this low-traffic guest-checkout storefront with a tiny catalog does not have.

1. **Zero `loading.tsx` / `error.tsx`** anywhere in `storefront/` — every App Router navigation blocks on the server render with no pending UI. Measured: `/` → `/order/[slug]` = 1867ms of frozen screen; `/order/[slug]` → `/track-order` = 1093ms; a repeat visit to `/order/[slug]` = 2082ms (slower — nothing is cached).
2. **`app/layout.tsx` and every `app/**/page.tsx` carry `export const dynamic = "force-dynamic"`** — a blanket opt-out of static rendering, RSC prefetch, and the Data Cache for the whole app. The stated reason is a build-time concern (`/_not-found` prerendering through the layout needs a reachable backend in CI/Docker), not runtime correctness.
3. **`lib/api-client.ts::apiFetch` uses bare `fetch` with no `next` cache directives** → Next 15/16 default `no-store` → every SSR render makes a live round-trip to `api.pekangame.space` for every endpoint. The "60s TTL" the code comments cite is Laravel's `Cache::remember`, which saves Laravel's DB query but not the Vercel→DigitalOcean network hop.
4. **`app/order/[slug]/page.tsx` awaits four data calls in series** — `[getGame, getSeoSettings]` in parallel, then `getGamePackages`, then `listPaymentChannels`, then `listPlans` — a four-wave waterfall, ~1.6s total (measured RSC fetch: 1577ms).
5. **`listPlans()` is fetched twice per navigation** — once server-side (passed as a prop to `OrderForm`) and again client-side in `BottomNav`'s `useEffect`, which runs on every page.
6. **A logged-in member triggers a second client-side data wave** — `OrderForm`'s `useEffect` re-fetches `getGamePackages(slug, token)` + `getMe(token)` because the membership session token lives in `localStorage` and is unreadable during SSR.
7. **`ReviewModal` (`z-50`) and `BottomNav` (`z-50`) share a z-index**, and `BottomNav` renders later in the DOM, so the fixed bottom nav paints over the bottom of the checkout sheet — the "Confirm & Pay" button is occluded even after scrolling the sheet to its end. The modal also has no `role="dialog"`, focus trap, body scroll lock, or Esc handler.
8. **`<main className="pb-10 …">`** (40px) is shorter than `BottomNav`'s ~56–62px, so the last footer line ("Made for Gamers. By Gamers.") and the bottoms of the last content cards sit behind the fixed nav on every page.
9. **`OrderSummarySidebar` is `lg:sticky` only** — on mobile it sits in the DOM after the 60+ package cards, so selecting a package produces no visible change and the "Review & Pay" CTA is ~5000px down the page.
10. **`PromotionsSection` renders `PROMOTIONS` from `placeholder-data.ts`** — hardcoded, with "Ends: Jul 2026" dates, still live in production in September.
11. **`BottomNav` hardcodes `https://wa.me/60000000000`** for its Support link and `SiteFooter`'s WhatsApp social link is empty — even though `/admin/settings` → Store Branding already has editable "Support WhatsApp number" (`support_phone`) and "WhatsApp URL" (`social_links.whatsapp`) fields that `SiteFooter` already reads.
12. **Reverb (ADR-047) is Accepted and its code is built** (`OrderStatusUpdated`, the unified push+poll `OrderStatusTracker`, the `docker-compose.prod.yml` service) **but was deferred at the Forge production cutover (ADR-066)** and never wired. The live storefront runs only the poll fallback — which ADR-047 decision 4 deliberately slowed from 5s to 20s on the assumption Reverb would carry real-time. Net effect: the "your diamonds were delivered" transition can lag up to 20s, a regression against the pre-ADR-047 5s.

**Performance budget** (replaces the founder's initial "every page < 100ms", which is not physically achievable for a cross-network dynamic render — the floor for an uncached SSR render Vercel-SG → DO-SG is ~200–400ms). `< 100ms` is the right budget for *feedback*, not for content settling:

| Stage | Target | Metric |
| --- | --- | --- |
| Tap → visible feedback (skeleton / progress) | < 100ms | RAIL |
| Interaction → Next Paint | < 200ms | INP ("good") |
| Prefetched navigation → content settled | < 200ms | — |
| Warm navigation (edge Data Cache hit) | < 500ms | — |
| Cold navigation (cache miss) | < 1200ms; LCP < 2.5s | LCP |
| Checkout submit → CHIP redirect | < 1s, covered by a blocking overlay | — |

**Decision:**

1. **Add matched-layout `loading.tsx` skeletons** to `/`, `/order/[slug]`, `/order/status/[orderNumber]`, and `/track-order` — each mirroring its route's real structure so there is no layout shift when content lands. `/about-us`, `/terms`, `/privacy` are made genuinely static instead (no skeleton needed). A global top progress bar covers App Router navigations as a catch-all.
2. **Remove `force-dynamic` from the root layout and every page** (keeping it only on the `robots.ts`/`sitemap.ts`/`llms.txt` route handlers). The build-time `/_not-found` concern is solved properly instead: every `lib/*` server fetch gets a graceful `try/catch` fallback returning sane defaults, plus a static `app/not-found.tsx`, so a prerender with no backend succeeds. Catalog/SEO/branding/hero/payment fetches move to `next: { tags: ['catalog'], revalidate: 3600 }` — the 1-hour TTL is a failure backstop, not the freshness mechanism.
3. **Freshness is tag-based revalidation, mirroring the backend's existing `forgetCache()` discipline one layer up.** A new Next route `POST /api/revalidate` (guarded by a shared secret header `REVALIDATE_SECRET`) calls `revalidateTag('catalog')`. On the Laravel side, a queued `NextRevalidation::purge()` job (3 retries, then log) fires next to every existing `Cache::forget()`/`forgetCache()` call site — `CatalogController`, `GameController`, `SeoController`, `BrandingController`, `HeroSlideController`, `PaymentMethodCatalogController`, and the middleware pending-price-change / reactivation controllers. A single coarse `catalog` tag (purge-all on any of these mutations) is chosen over granular tags: over-revalidation costs one edge re-fetch, and granular tagging adds wiring for marginal benefit. Price *display* can lag by the revalidation round-trip, but the payable total is always recomputed server-side at checkout (ORD-9) — display staleness is never a mischarge. If the webhook wiring slips, `revalidate: 60` is the interim.
4. **Parallelize the `/order/[slug]` RSC waterfall** — all four data calls in one `Promise.all`. Wrap the package grid + payment channels in a single `<Suspense fallback={<PackageGridSkeleton/>}>` so the product header and stepper shell paint immediately even on a cold cache miss ("poor man's PPR"). Full Partial Prerendering is deferred until measurement shows the shell itself exceeding the 100ms budget.
5. **Kill the duplicate `listPlans()`** by lifting the "membership enabled" flag and branding into a single `SiteConfigProvider` in the root layout (which already fetches branding), consumed by `BottomNav` and `SiteHeader` — removing `BottomNav`'s per-page `useEffect` fetch.
6. **Migrate the membership session token from `localStorage` to a cookie** (a scoped addendum to ADR-027). This lets SSR read it and personalize member pricing in the single RSC pass, deleting `OrderForm`'s entire second client-side data wave (`getGamePackages(token)` + `getMe(token)`). The token is already a lightweight, unguessable value — a normal same-site cookie is sufficient.
7. **Fix the mobile buy-flow layout.** Page bottom padding becomes `BottomNav` height + `env(safe-area-inset-bottom)` on mobile, clearing the footer and card clipping. `ReviewModal` is hardened: `role="dialog"` + `aria-modal`, focus trap, Esc-to-close, body scroll lock, raised to `z-[60]` above the nav, and its "Confirm & Pay" button moves into a sticky footer inside the scrollable sheet so it is always reachable and visible — checkout is the money-critical path, so dialog discipline matters most here. A sticky "Review & Pay" bar (mobile only) is added to `/order/[slug]`, showing the live total and CTA the moment a package is selected, above `BottomNav`. The 60+ package list is grouped into tabs/segments (Diamonds / Weekly Pass / First-Topup, etc.) — designed via `impeccable` — which also structurally removes the "scroll 5000px to find the summary" problem. The hero heading gets a scrim over its background image.
8. **`/order/status` becomes an explicit state machine** — pending → paid → delivering → delivered / failed — with clear animated transitions and a satisfying "delivered" moment (a CSS checkmark draw + subtle celebration). Motion is CSS-only plus the native View Transitions API (route-level cross-fade + directional slide, `prefers-reduced-motion` respected); no motion library, no shared-element transitions.
9. **The status tracker's fallback poll becomes adaptive** — 2s for the first 60s after landing on a pending order, backing off to 10s, then 20s after ~3 minutes (total watch window unchanged at ~6 minutes). This brings the "delivered" lag from ≤20s to ≤2s with no infrastructure.
10. **Finish the Reverb deployment**, executing ADR-047's remaining last-mile which ADR-066 left undone (this ADR does not re-decide Reverb): a Forge daemon running `php artisan reverb:start`, an nginx `location /app` WebSocket-upgrade block, `REVERB_*` backend env + `NEXT_PUBLIC_REVERB_*` on the storefront and reseller Vercel projects, and Cloudflare WebSocket proxying for the domains. The adaptive poll from decision 9 stays as the permanent fallback tier (per ADR-047 decision 4).
11. **Checkout submit shows a blocking, branded "Taking you to payment…" overlay** for the ~1s between "Confirm & Pay" and the CHIP redirect, so the redirect never reads as a hang.
12. **Add Web Vitals RUM** — `@vercel/speed-insights` (if the plan supports it) plus `useReportWebVitals` posting to a lightweight `/api/vitals` route backed by a small `web_vitals` table — so the budget above is measured continuously and regressions are caught, not eyeballed once.
13. **PR0 content fixes, shipped first as their own PR**: wire `BottomNav`'s Support link to `branding.socialLinks.whatsapp` (falling back to `supportPhone`) and drop the hardcoded `wa.me/60000000000`; remove `PromotionsSection` and its `PROMOTIONS` placeholder data entirely (re-wiring promotions to admin-editable data is a separate future ADR); add the hero scrim; fix the dead "Read More" `href="#"`. The founder sets the real Support WhatsApp number in `/admin/settings` → Store Branding after deploy — it is never hardcoded.
14. **Deploy-time backend caches** (`config:cache`, `route:cache`, `view:cache`, `composer dump-autoload -o`, an opcache config check) are set once as part of PR3. These do not move the perceived-latency needle — they are free hygiene, not the fix.

**Explicitly out of scope** (and why): full Partial Prerendering (deferred to a measurement trigger); shared-element view transitions and any motion library (a later "delight pass"); load balancing, read/write splitting, DB connection pooling, reverse-proxy tuning, speculative DB indexing (no scale problem to solve — the founder's instinct to check whether these were needed first was right, but the answer is no); re-wiring the promotions section to real data (own ADR); Cloudflare edge-caching in front of `api.pekangame.space` (PR3 evaluates it only — it may become its own ADR); an INP-by-route dashboard beyond the raw `web_vitals` table.

**Delivery:** PRs off `staging`, each independently shippable and CI-verified, then a `staging`→`main` release PR (merge commit, `--no-ff`) per push.

**The original PR1/PR2 split was revised during PR1 build (2026-09-03).** `loading.tsx` (decision 1) and removing `force-dynamic` + Data-Cache-ing the reads (decision 2) turned out to be inseparable: a `loading.tsx` fallback cannot reveal while the root layout blocks on an uncached `await` (Next's own `loading.js` docs), so a skeleton-only PR that leaves `force-dynamic` in place ships a permanently-stuck skeleton. A second discovery, folded in: a **root** `app/loading.tsx` wrapping the whole app in one Suspense boundary never revealed on a streamed load in this Next 16.3.1 / React 19.2 / Turbopack stack (reproduced local `next dev` + `next build`, static and dynamic routes) — but this was a **local-only** artifact (the dev box's browser could not reach the API over TLS); the Vercel preview reveals cleanly. The fix that ships regardless: **route-scoped** `loading.tsx` only, no root one (`/` is static/ISR and needs none).

**Rationale:**

- The founder's symptoms are entirely perceived-latency and layout, not server throughput. The single highest-leverage change is making routes prefetchable (remove `force-dynamic` + tag-based Data Cache) and adding `loading.tsx` — together they turn "tap → 2s frozen screen" into "tap → instant skeleton → content from warm cache". Everything else refines on top of that.
- `< 100ms` for a full navigation that must fetch dynamic data across the internet is not physically possible; the way to make the flow *feel* instant is to remove the wait from the customer's perceived critical path — immediate feedback, prefetch the next route before the tap, serve from edge cache — not to beat network physics per request.
- Tag-based revalidation over a short blanket TTL is the "solid / maintainable / reliable" choice the founder asked for: display staleness stays near-zero in practice (busted on write, exactly like the backend's own `forgetCache()`), a 1-hour TTL remains as a failure backstop, and the existing centralized `forgetCache()` methods mean the wiring is ~7 known call sites, not a hunt.
- Moving the membership token to a cookie (decision 6) is worth touching ADR-027 for: it deletes an entire client-side data wave every logged-in member currently pays on every order-page load, in a small, well-contained change.
- Reverb (decision 10) is not a new decision — ADR-047 made it, the code is written, and the deferral at the Forge cutover created a real regression on exactly the moment the founder cares about. The adaptive poll (decision 9) is the zero-infrastructure fix that lands first; finishing the Reverb wiring is the proper fix that removes the poll load.
- Recording this ADR before PR0, with the full four-round grill captured, follows the project's "record decisions, don't just make them" practice — a future reader touching the storefront's caching or the checkout modal needs the *why*, especially the deliberate `force-dynamic` removal and the "display staleness is acceptable because ORD-9" reasoning.

**Addendum — track-order poll/throttle mismatch, 2026-09-23 (founder-grilled; fix branch).** This explicitly revises decision 9's first-minute `2s` fallback cadence to `4s`: the former can make ~30 requests/minute against ADR-065's unchanged `throttle:20,1,track-order`, so a normal long-running delivery self-triggers 429 even without refreshing. One active tab at 4s stays below that cap while Reverb still supplies immediate pushes. A 429 is treated as recoverable using the server's `Retry-After` header (exposed through CORS), not as a permanent customer-facing error; a safe fallback delay applies when the header is unavailable. Multiple tabs or customers behind one IP can still share the throttle bucket, so this is not a promise of zero 429. The backend limit and order-number trust model are unchanged.

**Addendum — the real dominant cause of perceived slowness was never diagnosed here, 2026-09-24 (production infra fix, no code change).** This ADR's own Context opens with "**None of them are backend throughput**" and correctly ruled out the database/PHP side — but never checked *where the Vercel Function itself runs*. Founder reported the storefront feeling slow again; live investigation (Vercel Observability + a browser network trace against production) found all 3 Vercel Function projects (`pekangame-storefront`, `pekangame-admin`, `pekangame-reseller`) had been running in `iad1` (Washington DC, US East) — the Vercel account default, never explicitly set — while the backend origin (Forge on DigitalOcean) is physically in Singapore (confirmed via IP geolocation). Every SSR render paid a cross-Pacific round trip on every backend `fetch()`, cache hit or miss: `/order/[slug]`'s measured duration was 3.9s average, 4.38s P75, 6s P95, occasionally bursting past 40s under concurrent prefetch load — while the backend itself answers in ~100-200ms measured directly. Two `[catalog] listHeroSlides failed`/`listGames failed` errors on `fixfastapp.com` in the preceding week (Cloudflare 520/522/525 origin-connection failures, one with a 44.8s stalled external API call before failing) were downstream symptoms of the same pathology, not a separate bug — Cloudflare gives up on an origin connection outright under bad enough latency instead of merely being slow.

Fix: Project Settings → Functions → Function Region on all 3 projects, unchecked `iad1`, checked `sin1` (Singapore — offered under Vercel's Asia Pacific region list despite the collapsed UI only initially previewing Hong Kong/Tokyo), redeployed. All 3 on Vercel Pro with Fluid Compute already enabled — this was pure misconfiguration, not a capacity/plan limitation, and self-hosting off Vercel was considered and rejected for that reason (a single fixed-capacity VPS handles a real burst of concurrent users worse than Vercel's already-enabled auto-scaling would, once pointed at the right region). Verified live immediately after redeploy, no rollout wait needed: `/order/[slug]` steady-state dropped to 0.15-0.45s across multiple games; admin/reseller login pages both ~0.35-0.4s. `pekangame-docs` (Astro/Starlight, zero Vercel Functions) was never affected.

**Consequence to track:** if a future Vercel project is created for this platform (a new frontend, a preview/staging-only deploy target, etc.), its Function Region must be set to `sin1` explicitly at creation — Vercel's own account default is `iad1` and nothing in this stack catches a silent region drift automatically. Worth a periodic manual check (Project Settings → Functions) rather than assuming it inherits correctly.
