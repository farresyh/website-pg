# ADR-105: Order resend profit-recompute correctness — reconcile against the order's own frozen snapshot, not the target package's live pricing

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`) 2026-09-17, sparked by the founder walking a real order (`PG-KWKBUHNDMKQT`, order id 15) end-to-end and noticing the reported profit didn't move the way the resend's own "platform absorbs RM0.09" note implied. **Built same day** (`fix/adr-105-resend-profit-recompute` off `staging`), **then extended same day by a founder-discovered addendum** (decision 8 below — a second, distinct money-conservation bug in decision 2's own formula, found while explaining decision 2 to the founder) — see `docs/build-log.md`'s matching entries for the full file list and test coverage. Order 15's own RM0.10 ledger correction (via ADR-083's Adjust mechanism) is still founder-owed, not part of this PR.

**Context:** `OrderResendService::resend()` (ADR-017 decision #3/#5) recomputes `platform_profit`/`affiliate_profit` on every resend by calling `PricingService::calculate()`/`calculateForAffiliate()` with the **target Package's own live** `cost_price` *and* `standard_selling_price` (`$liveCostPrice`/`$liveStandardSellingPrice` in the code, both read straight off `$targetPackage`). Using live cost is correct and intentional — it's the whole point of decision #3's "live cost reconciliation." Using the target package's live `standard_selling_price` is not: that field drifts independently of this resend, via routine `SyncSupplierPricesJob` runs (`price_change_logs` shows near-daily moves on real packages), so `PricingService::calculate()`'s `platformProfit = standardSellingPrice - costPrice` ends up computed against a number that has nothing to do with what the customer actually paid.

Traced live on order 15: customer paid `selling_price=392` sen, frozen at checkout (ADR-017 decision #2 — `final_amount`/`selling_price`/`transaction_fee` are never touched by a resend, confirmed still true). The order's original package cost was 356 sen (~36 sen naive margin). The admin resent to package 122 (Digiflazz `PUBGG_60_PG1`), whose live cost was 365 sen — a real +9 sen the platform knowingly absorbed, correctly captured in `order_resend_attempts.price_diff_sen=9`. But that same package's `standard_selling_price` had *also* independently moved that same morning, 398→402, via an unrelated scheduled price-sync (`price_change_logs` id 11882, 05:00:26, hours before the 10:05 resend). `calculate()` computed `platformProfit = 402 - 365 = 37` — profit went **up** by 1 sen in the stored `Order.platform_profit` (and in every Report reading off it) despite the platform absorbing +9 sen of extra cost that same resend. The mathematically correct realized profit is `order.selling_price` (392, what was actually charged) `- liveCost` (365) `= 27` — a real 9-sen *decrease*, matching the absorbed amount 1:1. The formula's error direction is pure coincidence (a package's price could just as easily have drifted the other way, understating profit instead) — it's structurally wrong for *any* resend that swaps to (or retries) a package whose own pricing has moved since the order's original checkout, which routine price-sync cadence makes common, not rare.

Confirmed via prod query that the actual blast radius today is small: 7 `order_resend_attempts` rows across 5 orders total exist in prod; only order 15's resend actually succeeded (`Delivered`, the other 4 orders' resends are all still `failed`) — `creditProfit()` (which posts `order.platform_profit` to `ledger_entries` as an `order_profit` credit) only fires on a successful delivery, so order 15 is the only order with a live, wrong figure already sitting in the ledger (RM0.10 overstated). One resend (order 9) was on a `pricing_basis=member` order but also failed, so the parallel Member-basis gap below has not yet touched real money.

**Decision:**

1. **Standard / lapsed-affiliate basis** (`tierMarkupPct === null`, i.e. `calculateForAffiliate()` delegates straight to `calculate()`): `OrderResendService::resend()` passes the **order's own frozen `standard_selling_price`** as `calculate()`'s second argument, not `$targetPackage->standard_selling_price`. `$liveCostPrice` (still read from `$targetPackage`) is unchanged — only the revenue side of the formula moves from "live package" to "frozen order." This is a one-line source change (swap which variable is read); no schema change, no behavior change for `selling_price`/`final_amount` (still never touched, per ADR-017 decision #2).

2. **Tier-affiliate / Reseller-wallet basis** (`tierMarkupPct` non-null): **kept exactly as-is, on purpose.** This formula (`wholesaleBase = liveCost × (1 + frozen tierMarkupPct)`, `platformProfit = wholesaleBase − liveCost`, `affiliateProfit = wholesaleBase × frozen affiliateMarkupPct`) is architecturally a proportional-margin-over-cost scheme, not an absolute-price one — the tier markup percentage is already frozen off the order (`order->wholesale_markup_pct`), and re-deriving the wholesale base from *live* cost on every resend is the intended behavior of a percentage-based wholesale deal, not the same failure mode as decision 1. Explicitly noted here so it is never mistaken for the same bug: a resend that swaps to a costlier package under this basis *will* move both the platform's and the affiliate's own recorded profit share proportionally, and that is correct, not a regression. (Founder confirmed 2026-09-17: keep proportional.)

3. **Member basis:** structurally the same proportional-margin-over-cost family as decision 2 (`MembershipPricingService::calculateMemberPrice()` = `cost × (1 + effectiveMarkupPercent)`), but with a real asymmetry the tier basis doesn't have — `OrderResendService::resend()` reads `$targetPackage->markup_percent` (**live**, the package's current admin-set markup) instead of a frozen value, because no frozen equivalent of `wholesale_markup_pct` exists for Member orders today. Fix: add a new nullable `orders.markup_percent` column (`decimal`, matching `packages.markup_percent`'s precision), populated once at checkout time by `OrderPricingResolver::resolveMember()` (alongside the existing `member_discount_percent`/`membership_id` capture) from the package's markup_percent *at that moment*. `OrderResendService`'s Member branch then reads `$order->markup_percent` (frozen) instead of `$targetPackage->markup_percent` (live). Rejected alternative: back-deriving an implied original markup percent from the two already-frozen `cost_price`/`standard_selling_price` columns (`(standard_selling_price − cost_price) / cost_price`) avoids a migration, but reintroduces sub-cent rounding drift on top of values that were already rounded once into sen integers, and treats Member asymmetrically from how tier's `wholesale_markup_pct` is handled (stored directly, not reconstructed) for no real savings — one nullable column is cheaper to reason about long-term than a lossy reconstruction formula. One historical Member-basis resend exists in prod (order 9) but its resend attempt failed, so no real money is affected; its `orders.markup_percent` backfills via the rejected-alternative formula anyway (one-off, approximate, documented, no live financial consequence since it was never delivered/credited).

4. **Negative-profit resends** (live cost now exceeds the order's frozen revenue figure — the resend would show the platform taking a genuine loss on top of the money already absorbed): `PricingService::calculate()`/`calculateForAffiliate()` keep their existing `InvalidPricingConfigException` guard unchanged — checkout and any other caller of these methods still must never construct a priced object that undersells cost. `OrderResendService`'s manual-admin-resend path is the one place this now needs a deliberate escape hatch: it reuses ADR-102 decision 3's existing `override_reason` gate (already wired through `ResendDeliveryModal`'s required-reason field and `OrderController::guardResendUnsafeOverride()`) rather than inventing a second override mechanism — a resend that would otherwise throw the pricing guard is allowed through only when a non-empty override reason is supplied, at which point the negative `platformProfit`/`affiliateProfit` is stored and logged as-is (never silently clamped to zero). No change to the automatic/system-triggered resend path (`ResendOrderDeliveryJob`'s own retry), which keeps hard-failing on this guard.

5. **Resend package-picker SKU visibility** (found during the same walkthrough, bundled into this PR as a trivial, unrelated-but-adjacent fix): `ResendDeliveryModal.tsx`'s package `<select>` options render as `${package.name} — RM${cost}` only — two active packages for the same game with the same display `name` but different supplier refs (exactly `PUBGG_60_PG1` vs `PUBGG_60_PG2` on order 15) are visually indistinguishable except by cost, forcing the admin to guess. Fix: append the package's `supplier_package_ref` to the option label.

6. **Retroactive correction for order 15's already-wrong ledger entry:** corrected via the existing ADR-083 Adjust/Void mechanism (built and live in prod since that ADR's 2026-09-15 addendum, already used once by the founder for a real Wise-transfer correction) — a manual RM0.10 debit adjustment against the order's `order_profit` ledger credit, not a bulk backfill script. Confirmed blast radius is exactly this one order (see Context above), so a dedicated backfill command would be pure overhead.

**Rationale:** The bug is a variable-selection mistake, not a design flaw in ADR-017's original architecture — decision #3's own stated intent ("reconciles that package's live cost against what the customer actually paid") already describes the correct behavior; the implementation just read the wrong field off the wrong model. Fixing it by principle ("only `cost_price` is ever read live off the target Package during a resend; every revenue/markup input comes from the order's own frozen snapshot") rather than patching the one observed instance keeps Member basis from developing the identical bug the moment a Member order's package happens to get its `markup_percent` edited between checkout and a resend — which, unlike Digiflazz's automatic price-sync cadence, is rarer but not implausible (an admin manually retuning a package's margin).

**Addendum, 2026-09-17 (same session, before this PR merged) — decision 8, a second money-conservation bug in decision 2's own formula.** Found while walking the founder through *why* decision 2 keeps the tier-affiliate/ResellerWallet basis's formula unchanged: that formula computes `platformProfit = wholesaleBase - liveCostPrice` independently of `affiliateProfit`, and independently of what the order's own frozen `selling_price` says was ever actually collected. `wholesaleBase >= liveCostPrice` always holds by construction for a non-negative tier% — the only invariant decision 2's own reasoning checked — but nothing ever checked that `liveCostPrice + affiliateProfit + platformProfit` (everything paid out) stays within `order.selling_price` (everything ever collected). Concretely, worked through with the founder using order 15's own numbers re-purposed for a tier-affiliate order (cost 356, tier 20%, affiliate markup 5% → wholesaleBase 427, affiliateProfit 21, frozen `selling_price` 448): a resend to a package whose live cost rises to 400 recomputed, pre-addendum, `platformProfit = 480 - 400 = 80` and `affiliateProfit = 480 × 5% = 24` — a combined 504 against a `selling_price` that only ever collected 448, a **56-sen phantom credit** to platform+affiliate combined that no guard caught, since the formula never referenced `selling_price` at all. Zero real tier-affiliate/ResellerWallet resends exist in prod (confirmed by query — only `standard` and one failed `member` resend exist today), so this was caught before it ever touched real money.

8. **`platformProfit` for every non-Member basis is now derived as one money-conservation residual: `order.selling_price (frozen) − liveCostPrice − affiliateProfit`**, computed *after* `affiliateProfit` (which keeps its existing per-basis formula — decision 1's frozen-anchored calculation for Standard/lapsed-affiliate, decision 2's live-cost-proportional one for tier-affiliate/ResellerWallet, both **unchanged**) — never read directly off `calculateForAffiliate()`'s own `platformProfit` field for the tier branch anymore. This one identity replaces the two independent formulas the original PR-1 code used (`standardSellingPrice - liveCost` for Standard, `wholesaleBase - liveCost` for tier) with a single rule that structurally cannot let the three pieces (cost paid, affiliate's cut, platform's cut) sum to more than what the order ever actually collected — proven algebraically equivalent to decision 1's original Standard-basis formula (so no behavior change there) and a genuine fix for the tier branch. Decision 4's negative-profit override-reason gate now checks this unified `platformProfit < 0` condition for every non-Member basis, not just Standard — same mechanism, same UI, wider trigger. Frontend: `ResendDeliveryModal`'s "Platform absorbs" preview (which was a raw cost-diff, only ever accurate for the Standard basis) is replaced with a `computeResendImpact()` helper mirroring this exact formula per basis, so the modal shows the real projected `platformProfit`/`affiliateProfit` before the admin submits, not an approximation; `OrderDetailCards.tsx`'s "Platform Profit" row — previously a hardcoded `+` prefix assuming profit is always positive — now renders a real negative correctly (`-RM1.00`, error tone) instead of a double-signed `+RM -1.00`.

Grilled 2026-10-06 (Q1–Q13) after a code-trace pass against real code and a read-only prod check. *Context — what is wrong today (verified 2026-10-06 against `staging` = `664fba6`).*

1. **Member resend re-prices the order.** `OrderResendService::resend()` (lines 164–171) computes a *new* member price for the target package and records `platform_profit = newMemberPrice − liveCost`. Every other basis records the residual `selling_price − liveCost − affiliate_profit` (decision 8). Example from the existing test (`OrderResendServiceTest.php:691`): customer paid 1000 sen, swap package costs 1200 → recorded **+36**, real **−200**, and no loss prompt (the gate at line 225 skips Member). Tests :691 and :724 assert the bug as correct; :755 tests a fallback of the same formula. Root of the miss: decision 3 grouped Member with tier "proportional margin", but for tier only the *affiliate* share is proportional; decision 8 then wrote its residual for "every non-Member basis" and Member was never re-checked. ADR-111 (`OrderFulfillmentService::reconcileRealCostProfit()`, flag on in prod) already applies the residual to every basis at delivery, so today the wrong figure usually lives only until delivery — but the loss prompt is missing, and it is credited as-is whenever real cost is unavailable.
2. **The affiliate share grows when the platform swaps to a dearer package** (decision 2). Tier 10 %, affiliate markup 5 %: paid RM 10.40, cost RM 9.00, affiliate RM 0.50. Swap to cost RM 12.00 → affiliate RM 0.66, platform −RM 2.26 instead of −RM 2.10. Decision 8 moved the platform share to the residual, so the platform alone now pays for the affiliate's increase.
3. **`orders.cost_price` keeps the old package's cost after a swap.** `resend()` updates `package_id`, `supplier_id`, `supplier_product_ref` and profit, never `cost_price` (ADR-017 decision 2). Every reader that treats it as the delivered order's cost is then wrong: `Order::costReconciliation()` "estimated" branch (Order Detail Cost Price, `OrdersWorkbook` export), `TransactionRegisterService` `cost_sen`, `MonthlyAccountingSummaryService::cogs()` (and so the FX variance true-up, `cogs − drawn`, which absorbs the swap cost as fake "FX"), `CustomerAnalyticsService` `supplier_cost`, and `recordFulfillmentAttempt()` / manual-confirm attempt rows (`cost_price_sen = $locked->cost_price`). Prod: order 19 (reseller-wallet) shows selling 367, cost 356, profit 2 → `selling − cost − affiliate` = 11 ≠ 2; real cost was 365. Order 15 (standard) same shape, cost 356 vs 365.
4. **The resend rules live in three copies that already drifted.**
   - `OrderResendService::resend()` — the real write.
   - `Admin/OrderController::resend()` + `guardResendUnsafeOverride()` (lines 396–431) — re-implements status / compensated / same-game / swap-block checks, and its loss check covers only `wholesale_markup_pct === null` (Standard). A loss on a tier-affiliate or ResellerWallet order passes the controller.
   - `admin/src/components/orders/ResendDeliveryModal.tsx` `computeResendImpact()` (lines 61–93) + `wouldSellBelowCost` (line 187) — a TypeScript copy. Its Standard branch uses `standard_selling_price` where the backend uses `selling_price`, so a lapsed-affiliate preview understates platform profit by the affiliate share (0 such orders in prod).
5. **A rejected resend is silent.** `ResendOrderDeliveryJob::handle()` (lines 74–82) catches the `ValidationException` and writes `Log::info` only. The admin already saw "Resend queued." — e.g. a tier-order loss the controller missed (point 4) is refused with no trace in the admin.
6. **Two overlapping resends.** `resend()` writes package / profit with no row lock (line 242); only `fulfill()` locks. `supervisor-orders` runs up to 4 workers, so two resend jobs for one order can interleave: both pass the unlocked checks, B's write lands after A's, A's `fulfill()` reads the locked row and delivers B's package (order and ledger stay consistent), but A's attempt row records A's package. With a narrower interleaving B can overwrite an already-Delivered order's package and profit.

*Prod scale (read-only, 2026-10-06).* Orders by basis: standard 22, reseller-wallet 7, affiliate 5, member 1. Resend attempts: member order 1 — 3 same-package, all failed (profit 2 = 94 − 92, correct). Successful resends: orders 15, 18 (standard), 19 (reseller-wallet, cost +9), 34 (affiliate tier, same cost — affiliate share unchanged). Ledger is correct for all four (order 15 = 37 − 10 adjustment = 27, per decision 6). Deliveries since 2026-09-22 with no real cost: 0. No customer money affected; the visible damage is `cost_price` on orders 15 and 19 (RM 0.18 total) and order 15's `platform_profit` column (37 vs ledger 27).

*Trace — what is already correct and stays untouched.* `selling_price` is written once, at checkout (`OrderFactory.php:68`), and is pre-voucher (`voucher_discount` is separate), so it is a safe anchor. Checkout, ADR-111 real-cost reconciliation, `OrderSettlementService` (partial combo), ADR-107 combo profit, Retry Delivery, the ledger, and every report reading the ledger (`Order::earnedProfit()`, `ReportService`) already use the residual or the ledger. Member quota is debited from the frozen price and is unaffected by a resend. Combo orders cannot be package-swapped (ADR-094 decision 10).

*Decisions (continuing this ADR's numbering):*

9. **One profit rule for every basis.** On every resend (same or different package): `affiliate_profit` = the order's current value (frozen — decision 10); `platform_profit = selling_price − liveCost − affiliate_profit`. Standard, lapsed-affiliate, tier Affiliate, ResellerWallet and Member all take this path. The Member branch and `MembershipPricingService` / `PricingService::calculateForAffiliate()` calls in `resend()`, plus the `InvalidPricingConfigException` catch (lines 191–208), are deleted, not repaired. This is the same identity as decision 8, ADR-111 decision 3 and `OrderSettlementService`. **Reverses decision 3.**
10. **The affiliate share is frozen at its checkout value on a resend.** An affiliate earns from the sale they made, not from the platform's delivery choice; the platform absorbs every cost change in either direction. Matches ADR-111, which already freezes it against real-cost drift. **Reverses decision 2** (founder, 2026-10-06). No historical data is affected (prod order 34's resend had no cost change).
11. **The loss gate covers every basis.** `platform_profit < 0` on a resend needs a non-empty `override_reason` for Member too; the "Member can never sell below cost" comments (service lines 222–224, modal lines 184–186) go. The gate is evaluated on **catalog** cost: real cost is known only at delivery, and a loss that appears then is caught by ADR-111's existing `profit_reconciled_flagged`. The gate is a prompt, not a guarantee; this is accepted.
12. **One seam owns every resend rule — `OrderResendService::preflight(Order, Package, ?overrideReason)`.** It runs every guard (resendable status, already compensated, same game, active, not combo, `blocksPackageSwapTo`, player-ID contract and validation window where applicable, loss → override) and returns the impact: `affiliate_profit`, `platform_profit`, `cost_diff_sen`, `override_required` + reasons, or a `blocked_reason`. Three callers, no copies:
    - `Admin/OrderController::resend()` calls it synchronously; its duplicated status / compensated / same-game / swap-block checks and the loss half of `guardResendUnsafeOverride()` are deleted (the `resendUnsafeToOverride()` reference guard stays, it is shared with `retryDelivery()`).
    - `resend()` calls it again under the row lock (decision 14) — the attempt-time re-check.
    - A read-only preview endpoint (decision 15).
    `computeResendImpact()` and `wouldSellBelowCost` are deleted from the modal; it only renders what the backend returns.
13. **`orders.cost_price` follows the package actually assigned.** A resend writes `cost_price = liveCost` of the target package alongside `package_id` / `supplier_product_ref`, so every cost reader in Context point 3 becomes correct with no change of its own. The checkout cost stays on record in the `initial` attempt row (ADR-106) and in the first resend's `price_diff_sen`. **Revises ADR-017 decision 2** for `cost_price` only — `selling_price`, `final_amount`, `transaction_fee`, `voucher_discount` stay immutable. **Revises ADR-017 decision 4:** `price_diff_sen` now means "this attempt's live cost − the cost assigned before it" (identical to before for a first resend; for a second resend it is relative to the first). The UI already shows real profit, not this diff, so no label changes.
14. **The resend write happens under the row lock.** Inside `DB::transaction` + `lockForUpdate()`: re-read the order, re-run `preflight()` (status must still be Failed or NeedsReview), then write package / supplier / ref / player IDs / `cost_price` / profits; commit; then `fulfill()`. A second overlapping resend is refused at its own locked re-check once the first has moved the order to Processing. The attempt row records the package `fulfill()` actually used (`$result->package_id` / `$result->cost_price`), never the requested one. Rejected alternatives: moving the write into `fulfill()`'s phase-1 lock (changes the `OrderFulfillmentService` seam), `ShouldBeUnique` on the job (does not cover resend vs Retry / webhook).
15. **Preview endpoint.** `GET /admin/orders/{order}/resend-options` returns the game's active packages, each with decision 12's impact or `blocked_reason`; sandbox twin `GET /middleware/sandbox/orders/{order}/resend-options` for `is_test` orders. `ResendDeliveryModal` takes its fetcher as a prop (as it already does for sandbox vs admin submit) and stops calling `listGamePackages`. Admin-only response, so cost and profit may appear; nothing reaches the portal, Reseller API or Bot.
16. **A rejected resend leaves a row.** `ResendOrderDeliveryJob` records an `order_resend_attempts` row with `attempt_type = resend`, `outcome = rejected`, the reason in `note`, `triggered_by` as given. `outcome` is a string column — no migration. `DeliveryLogsTable.tsx` `getOutcomeSeverity()` gets a `rejected` case. No new broadcast: Reverb pushes only on an `Order` row change (`OrderObserver`), so the row shows on the next refresh / reopen. Accepted.
17. **`orders.markup_percent` and `member_discount_percent` stay, unread by resend.** Checkout (`OrderPricingResolver`) keeps filling them as the checkout audit record. No migration. Test :755 (null-markup fallback) is deleted with the branch.
18. **Historical data fixed by a data migration, ruled not hand-picked.** Target: non-combo orders that are Delivered, have a `resend` attempt with `outcome = success`, and `real_cost_price_sen IS NULL`. For each: `cost_price` = the latest successful resend's `cost_price_sen`; `platform_profit = selling_price − cost_price − affiliate_profit`; **write only if that equals the order's platform `order_profit` ledger sum** (adjustments included), otherwise log and skip. Never touches the ledger. Idempotent — a second run changes nothing. Expected: order 19 cost 356 → 365; order 15 cost 356 → 365 and profit 37 → 27; order 18 unchanged.
19. **September's accounting summary moves, and that is accepted** (Q13, the model's call at the founder's request). Orders 15 and 19 were paid in September (already seen by the external reviewer, 2026-09-30). After decision 18: COGS +RM 0.18 and the FX variance true-up +RM 0.18 (`variance = cogs − drawn`) — the 0.18 was swap cost misreported as FX gap; the summary has no net line, so nothing else moves. Record the September summary before/after (read-only) in `docs/build-log.md` and tell the reviewer if they kept the old figures. Rejected: limiting decision 18 to orders after the last reviewed month, which leaves two orders permanently inconsistent.

*Build-time corrections (2026-10-06, founder-approved, no re-grill).* Found on the pre-build code-trace; they change three decisions above.
- **Decision 18 becomes a two-part rule.** `MonthlyAccountingSummaryService::cogs()` sums `cost_price` whether or not real cost exists, so filtering on `real_cost_price_sen IS NULL` would leave a resent order's stale `cost_price` in COGS. The target is every non-combo Delivered order with a `resend` attempt at `outcome = success`, with `new_cost` = the latest successful resend's `cost_price_sen`:
