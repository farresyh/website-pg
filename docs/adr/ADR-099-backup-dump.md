# ADR-099: Backup dump `useSingleTransaction` — stop the daily backup from locking the whole live schema

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled + built 2026-09-16 (`/mattpocock-skills:grilling`, `feature/adr-099-backup-single-transaction` → `fix/backup-single-transaction-dump`).

**Context:** A routine founder-requested Pulse/Horizon health-check session (no prior incident report) surfaced two slow writes in Pulse's own slow-query log: `UPDATE supplier_products ... where id=?` (42 occurrences, slowest 6,455ms) and `INSERT INTO supplier_request_logs (...)` (18 occurrences, slowest 4,926ms) — both far outside normal single-row-by-key latency. Traced to `routes/console.php`: the daily backup (`Schedule::command('app:run-backup', ...)->dailyAt('02:00')`) and price-sync (`Schedule::call(...)->cron("*/{$priceSyncIntervalMinutes} * * * *")`, `PRICE_SYNC_INTERVAL_MINUTES=60`, so it also fires exactly on `:00`) collide every day at 02:00.

**Root cause, confirmed against prod, not assumed:** `config/database.php`'s mysql `dump` config had `exclude_tables` and `mysql_gtid_purged` set (the 2026-09-14 GTID fix) but never `useSingleTransaction`. spatie/laravel-backup's dumper (`spatie/db-dumper`) only adds mysqldump's `--single-transaction` flag when that option is explicitly set — without it, mysqldump's own default behaviour issues `LOCK TABLES <every table> READ LOCAL` across the *entire* live schema before reading anything, to get a consistent dump without a transaction. Queried directly against prod's `performance_schema.events_statements_summary_by_digest`: the `LOCK TABLES ... READ LOCAL` digest (covering the whole schema in one statement) shows a max lock-*acquire* wait of **806.5ms / 691.5ms / 529.3ms / 405.5ms / 205.6ms** across 5 sampled daily occurrences — the writers on the other side of that acquire wait are exactly what Pulse's slow-query log caught.

**Ruled out, also against real prod data:** this does **not** cause price-sync job failures or data loss. Every `price_sync_runs` row from the last 7 days is `status='success'`, running 15-26 seconds — nowhere near `config/horizon.php`'s `supervisor-price-sync` 60s timeout, including every run that started at 02:00 and directly overlapped the backup. The only confirmed symptom is write-latency during a low-traffic window, not a functional bug.

**Ruled out as a separate hypothesis during the same session:** the founder independently asked whether this same lock collision explains the near-daily "Pending Reactivation" packages in `/middleware/price-sync`. Checked against real data: `price_sync_runs.stats->deactivated` shows a small (1-4/day) trickle on every single day in a 14-day window regardless of backup timing, plus two real outlier spikes (82 on 2026-09-12, 13 on 2026-09-13) that traced to Digiflazz reporting many SKUs across 11+ unrelated games as inactive in a single sync (`catalog_created=0`, `catalog_pruned=0` — nothing vanished, Digiflazz's own `status_raw` flipped) — a genuine, supplier-side platform blip, unrelated to this ADR's lock issue. Recorded here only so a future reader doesn't re-open the same already-ruled-out hypothesis; the Pending Reactivation auto-approve question itself is tracked separately, not decided by this ADR.

**Decision:**

1. **`'useSingleTransaction' => true`** added to `config/database.php`'s mysql connection `dump` array, alongside the existing `exclude_tables`/`mysql_gtid_purged`. mysqldump takes an InnoDB consistent snapshot (`START TRANSACTION WITH CONSISTENT SNAPSHOT`) instead of locking tables — confirmed safe: every real table in the live schema is InnoDB (`information_schema.tables` queried directly against prod — 82 InnoDB, the other 3 rows are views with `ENGINE=NULL`, not MyISAM). `--single-transaction` and `--skip-lock-tables` are independent dumper flags, but mysqldump itself turns off its default lock-tables behaviour whenever `--single-transaction` is present — no second flag needed.
2. **No schedule stagger.** Considered (moving the backup off the `:00` boundary so it stops colliding with every hourly-aligned job by construction, not just price-sync) and deliberately not done — decision 1 removes the actual lock, so there is nothing left for a stagger to avoid from a correctness standpoint. Noted, not acted on: **every** `->daily()` schedule in `routes/console.php` defaults to midnight, so 00:00 (not 02:00) is this codebase's real scheduling pile-up point — a separate observation, tracked as a backlog note, not this ADR's scope.
3. **Built despite zero customer-facing incident**, on the founder's own call during the grill: the fix is a one-line, fully-verified-safe config change, and ADR-077 PR-3's build-log entry (2026-09-07) had already flagged this exact class of concern ("DB-backup duration grows... captured in backlog for a proper look") without a session ever coming back to look — this session is that look.

**Rationale:** Matches this project's existing "verify against real database/production behavior, not an idealized one" discipline (ADR-014's cache-serialization addendum, ADR-015's `last_synced_at` truncation fix) — every claim in this ADR (the lock, its duration, the InnoDB-only schema, the ruled-out timeout theory, the ruled-out Pending Reactivation theory) was checked directly against prod (`performance_schema`, `price_sync_runs`, `deactivation_logs`) before being written down, not inferred from the code alone.

**Consequence to track:** none open — this is a self-contained config fix with no follow-on decision. The Pending Reactivation "should reactivation ever auto-approve" question raised during the same session is a separate, not-yet-decided design question (would reverse ADR-015 decision #3's deliberate manual-approval gate) — tracked in `docs/prd.md` §16, not this ADR.
