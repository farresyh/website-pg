# ADR-101: Security hardening — external pentest response (SPF/DMARC, CSP, OTP throttle, admin script-injection reversal)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`) 2026-09-16. Build pending, `fix/security-hardening-2026-09-16` off `staging`.

**Context:** the founder had an external AI pair (Hermes + DeepSeek) run a black-box security assessment against production and brought its findings in for a grill. Every claim was verified live before being trusted — against real DNS (`dig`), real response headers (`curl`), the real Cloudflare and Vercel dashboards (founder's own logged-in Chrome session), the real codebase, and the real Plunk dashboard — rather than accepted at face value, per this project's own "reference vs. project data" discipline applied to an external report instead of a reference codebase.

**Evidence gathered, all against the real system:**

1. **Confirmed real:** no SPF/DMARC/MX TXT records for `pekangame.space` (Cloudflare's own DNS dashboard flags this itself, unprompted). No CSP or `X-Frame-Options` on any of the three Vercel-hosted frontends (`storefront`/`admin`/`reseller`) or `docs-site` — `grep`-confirmed genuinely absent from every `next.config.*`/`middleware.ts`/`vercel.json`/Astro config in the repo, not just missing from the live response. Public POST endpoints (`validate-player`, `voucher-preview`, `membership/otp/send`) throttle per-IP only, proxy-rotation-bypassable — real for OTP email-bombing and player-ID enumeration; voucher brute-force specifically is not (`VC-`+`Str::random(8)` = 62^8 keyspace).
2. **Found false in the report:** no `googletagmanager.com`/`gtag.js`/any third-party script tag exists anywhere in `storefront/`, `admin/`, or `reseller/` source or the live homepage HTML — Web Vitals is self-hosted via the app's own `/api/vitals` route (ADR-071 decision 12), not `va.vercel-scripts.com`. (`storefront/src/app/layout.tsx` does contain an *admin-configurable, currently-unset* GA/FB-Pixel/TikTok-Pixel integration point — dormant, not what the report described, but relevant to decision 9 below.) "Cloudflare protects every host" is also false: DNS + live `server:` headers confirm only `api.pekangame.space` and `cdn.pekangame.space` (R2) are Cloudflare-proxied — `pekangame.space`, `admin.`, `reseller.`, `docs.`, `connect.` are all "DNS only" CNAMEs straight to Vercel, which has its own separate (and, per its Firewall traffic log, actually-working) DDoS/bot mitigation.
3. **The session's own most severe finding turned out to be a false alarm.** `bot.pekangame.space`'s unproxied A record reveals the real origin IP (`137.184.250.200` — DigitalOcean's Reserved IP for the Forge droplet, confirmed the same box as the `157.245.203.250` base IP in `reference_forge_box_ssh`, per `docs/adr.md`'s own ADR-066 cutover entry, not two servers). A direct request to that IP for `api.pekangame.space` was initially read as a total Cloudflare-WAF bypass — until cross-checked against this very log: the 2026-09-06 Cloudflare cutover entry above already records "Authenticated Origin Pulls" (mTLS: the origin rejects any TLS connection that doesn't present Cloudflare's own client certificate) as configured and verified, closing ADR-020 decision 8. Re-tested directly this session: `curl -k --resolve api.pekangame.space:443:137.184.250.200 https://api.pekangame.space/api/health` → `400 No required SSL certificate was sent` — the protection is live and correctly rejecting the request, not bypassed. `api.pekangame.space` was never actually exposed by this DNS record.
4. **What was real about the same finding:** `bot.pekangame.space` itself is not mTLS-covered (it was never flipped to Cloudflare-proxied the way `api` was — `docs/adr.md`'s cutover entry only mentions `api`). Confirmed by direct request: `bot.pekangame.space` answers with only `401 Basic Auth` protection, no Cloudflare in front, no mTLS. Nothing in ADR-075 requires it to be internet-reachable at all (OpenWA holds an outbound WhatsApp session; the Laravel↔OpenWA webhook traffic is loopback/nginx-restricted to `127.0.0.1`) — it's a founder-only management endpoint that happens to sit on the same droplet as the money-critical API.
5. **The Cloudflare zone is on the Free plan** — `security/security-rules` shows Custom rules 0/5, Rate-limiting rules 0/1, and the Managed WAF ruleset is locked behind "Upgrade plan." Only automatic L3/4 + TLS DDoS mitigation is active (confirmed still active and free). No actual signature-based L7 WAF has ever been configured, contrary to what "Cloudflare sits in front of the API" implies on its own.
6. **Vercel's own posture is solid and already working**, unprompted: Pro plan, system DDoS mitigation observed actually challenging real scanner-looking IPs in `pekangame-storefront`'s Firewall traffic log in the 24h before this audit. Zero custom firewall rules configured, and Bot Protection is toggled Off.
7. **Plunk (the actual OTP sender) checked directly in its own dashboard**, not inferred from `.env.example`: `pekangame.space` shows **Verified**, and its 3 required DKIM CNAMEs are exactly the 3 `_domainkey` records already present in Cloudflare DNS (Plunk runs on AWS SES infrastructure under the hood — these are not unrelated SES leftovers, as first misread). DKIM alignment alone already satisfies DMARC — the OTP path is not currently unauthenticated. Plunk's own optional "Custom MAIL FROM" bounce-alignment feature (not yet enabled) shows the exact SPF mechanism its real sends need: `v=spf1 include:amazonses.com`, scoped to a `plunk.<domain>` subdomain for that specific feature — informing decision 1 below for the root domain's own SPF.
8. **Production mail is not what the report assumed.** `MAIL_MAILER=log` in production (mail silently dropped) for Laravel's native mail path — a pre-existing, already-known gap (`docs/build-log.md`'s 2026-09-14 backup-alert incident). OTP mail bypasses that path entirely via `PlunkMailer`'s direct HTTP call to Plunk's API. No MX record exists for `pekangame.space` at all — by design so far, since no mailbox has ever existed at that domain.

**Decision:**

1. **SPF at the root domain:** `v=spf1 include:amazonses.com -all` — authorizes exactly Plunk's real sending path (evidence point 7) and hard-fails everything else. Safe as a hard fail because no other legitimate sender was found anywhere in the codebase or either vendor dashboard.
2. **DMARC at `_dmarc.pekangame.space`:** starts at `p=quarantine` (not the usual cautious `p=none` monitor-first rollout) with `rua=mailto:` a founder-chosen report address, moving to `p=reject` after a short observation window. Justified by evidence point 7 — DKIM alignment is already live and verified working, so the one real sender passes regardless of the SPF change, making the usual monitor-first caution unnecessary here.
3. **Plunk's optional "Custom MAIL FROM" bounce-alignment records added too** (the `plunk.pekangame.space` MX + SPF TXT Plunk's own dashboard supplies) — zero risk to the root domain's policy, marginal deliverability improvement, effectively free while already in the DNS zone making changes.
4. **A human-reachable `support@pekangame.space` mailbox is provisioned via Zoho Mail's free tier** (1 custom domain, 5 users, web-based send+receive, genuinely $0/mo) rather than Google Workspace or a Cloudflare-Email-Routing-plus-relay DIY setup — simplest zero-dev path that satisfies "receive *and* reply from the same address," the founder's own stated requirement. Its own MX sits at the root, alongside (not instead of) Plunk's separate bounce-handling MX on the `plunk.` subdomain.
5. **`bot.pekangame.space` is flipped to Cloudflare-proxied**, matching `api.pekangame.space`'s posture — closes evidence point 4 (gains WAF/DDoS coverage, hides the origin IP) with a single DNS toggle; Basic Auth stays as a second layer, unchanged.
6. **The Cloudflare zone stays on the Free plan** — the Pro-tier Managed WAF ruleset's main value-add here (blocking direct-to-origin bypass) was already delivered for free by the mTLS Authenticated Origin Pulls protection that predates this ADR (evidence point 3); the app layer already throttles the sensitive endpoints (evidence point 1) and uses parameterized Eloquent queries with no identified raw-SQL surface. Revisit only if Cloudflare's own (free-tier) Security Events analytics ever show real attack volume against this zone.
7. **`membership/otp/send` gains a second throttle key, per-email, alongside the existing per-IP 3/min limiter** — closes the actual abuse case (one victim's email bombed via rotating IPs) without adding friction (no Turnstile/CAPTCHA) to a signup flow, consistent with this project's standing bias toward not adding checkout/signup friction unless a real abuse case demands it.
8. **CSP is added to `storefront`, `admin`, `reseller`, and `docs-site`**, nonce-based (Next.js's own injected inline scripts need a per-request nonce to keep working under a strict `script-src`), rather than left unenforced or shipped as a loose `unsafe-inline` allowlist that would defeat the point.
9. **Reverses ADR-029 decision 13.** The admin SEO settings' free-text `headScripts`/`bodyEndScripts` fields (rendered via `dangerouslySetInnerHTML`, i.e. any external domain an admin pastes becomes a live script source) are replaced with three named-provider ID-only fields — Google Analytics measurement ID, Facebook Pixel ID, TikTok Pixel ID — the only three the fields have ever actually been used for (evidence point 2). Those three vendor domains become the storefront's only `script-src` entries beyond `'self'` and the per-request nonce.
10. **Vercel Bot Protection is toggled on for `pekangame-storefront`** — closes evidence point 6's gap; the system DDoS mitigation it already runs alongside stays unchanged.

**Rationale:** the report's own framing conflated three genuinely different things this grill had to pull apart before deciding anything — "Cloudflare is in front of a host" (true only for `api`/`cdn`), "Cloudflare's WAF is protecting a host" (true for neither, on the Free plan), and "the origin is directly reachable" (false for `api`, true for `bot`). Acting on the report's own conclusion ("Cloudflare = WAF everywhere, upgrade for more") would have spent money upgrading a layer that was never the actual gap, while leaving `bot.pekangame.space`'s real exposure and the CSP/admin-script structural conflict (evidence point 2's dormant tracking-pixel wiring plus decision 13's arbitrary-script field) untouched. Decision 9 specifically exists because a CSP allowlist is not meaningfully enforceable next to a feature that lets an admin inject any script by design — closing that gap was a precondition for decision 8 to mean anything, not an independent tidy-up.

**Consequence to track:**

- Decisions 1-7 and 10 are dashboard/DNS-only — no code, no branch, logged to `docs/build-log.md` once done rather than tracked as a PR.
- Decisions 8 and 9 are real code changes (nonce plumbing through each app's root layout + a new middleware/`headers()` config per app; the admin SEO form + its storefront consumer lose the free-text fields and gain three ID inputs) — built on `fix/security-hardening-2026-09-16`, test-first for the admin-field migration (existing brands with `headScripts`/`bodyEndScripts` set need a real migration decision, not a silent drop — build-time detail, not decided further here).
- The DMARC `p=quarantine`-not-`p=none` call (decision 2) carries slightly more risk than the cautious default if evidence point 7's Plunk-DKIM read is ever wrong — worth a quick spot-check of the first real DMARC aggregate report once `rua` reports start arriving, before moving to `p=reject`.
- Decision 6 (stay Free) is a revisit-triggered decision, not a permanent one — no monitoring was set up by this ADR to actually notice when the trigger condition (real attack volume) occurs; Cloudflare's Security Events tab would need a founder or scheduled check, not an automatic alert.

**Addendum, 2026-09-16 (same session, before any build):** decision 4 (Zoho Mail Free for `support@`) was wrong on cost — the founder confirmed Zoho's free tier no longer covers a custom domain; using `@pekangame.space` needs a paid Zoho plan. **Decision 4 is deferred** — no `support@` mailbox is provisioned by this ADR. Decisions 1-3 and 5-10 are unaffected (none depend on 4): decision 1's SPF `-all` still authorizes only Plunk, decision 2's DMARC still targets Plunk's DKIM-aligned mail, and no MX is added at the root for now — `pekangame.space` remains sending-only until a `support@` provider is actually chosen. Build order this session: 1, 2, 3, 5, 6, 10 (dashboard/DNS-only, no code) first; 7-9 (code) follow on the `fix/security-hardening-2026-09-16` branch; 4 stays parked.

**Addendum 2, 2026-09-16 (starting the code half, decision 7 retracted before writing any code):** re-reading `MembershipOtpController`/`routes/api.php` before touching it found decision 7 already built — `/membership/otp/send` is `throttle:otp-request`, a **named** limiter (`AppServiceProvider`) keyed on `(string) $request->input('email')`, `Limit::perHour(3)`, with its own comment (ADR-027's 2026-08-29 addendum, decision 26) explicitly citing the exact abuse case decision 7 was written to close ("unlike every other `throttle:` route in this app... spamming one target inbox... an IP-only bucket wouldn't catch"). The evidence-gathering pass for this ADR read the report's "per-IP-only" claim as true without checking the named-limiter definition itself — an error in this ADR's own verification, not a new fact. **Decision 7 is retracted, not built** — no second throttle key is added; the existing one already is the fix. Decisions 8 and 9 are unaffected and proceed as written.

**Addendum 3, 2026-09-16 (decision 9 built; decision 8 paused mid-build on a real conflict with ADR-071):** decision 9 shipped as designed — `SeoScript` (ADR-029 addendum 2 decision 13: admin free-text `head`/`body_end` `<script>` CRUD + its public `/seo/scripts` feed + the storefront's `dangerouslySetInnerHTML` rendering of it) is fully removed (admin routes/controller/FormRequest/nav/UI, public route, storefront consumer); `ga_measurement_id`/`fb_pixel_id`/`tiktok_pixel_id` (already-existing named fields, confirmed untouched) are the only script-injection paths left. The `seo_scripts` table/model are left in place, not dropped — dead data, nothing reads it now, no destructive migration needed.

Decision 8's "nonce-based" framing turned out to understate a real cost, found reading this Next.js version's own bundled CSP guide (`node_modules/next/dist/docs/.../content-security-policy.md`, per `storefront/AGENTS.md`'s standing instruction to check it before writing CSP/proxy code) before touching `proxy.ts`: **a nonce is generated per-request in `proxy`/middleware, which requires every page to render dynamically — the doc's own words, "all pages must be dynamically rendered... static optimization and ISR are disabled... slower initial page loads... higher hosting costs."** That is a direct reversal of ADR-071's own decision (PR1: removing `force-dynamic` from this exact root layout specifically to let pages stay static/ISR-cached) — the two ADRs pull in opposite directions and this session found that only by reading the framework doc, not by reasoning about it in the abstract.

Re-examined against what decision 9 already bought: the report's real fear (Magecart/skimmer — an attacker's script loading from an unauthorized domain) is blocked by a `script-src` **allowlist** on its own, nonce or not; a nonce's marginal value on top of the allowlist is stopping an attacker who can already inject raw inline `<script>` content into the page — and decision 9 just closed the one *known, admin-facing* path that would have made that possible (the free-text field). No other inline-script-injection vector was found anywhere in this codebase's own code (React's auto-escaping, no other `dangerouslySetInnerHTML` of unsanitized input). So for `storefront/` specifically, a `script-src` allowlist with `'unsafe-inline'` (Next.js's own documented "Without Nonces" pattern — a plain `headers()` block in `next.config.ts`, zero rendering-mode impact) delivers the report's actual ask (block unauthorized script *sources*) without paying ADR-071's performance cost to stop a threat that no longer has a live path in on this app.

**Decision 8 is narrowed, not retracted: CSP ships without nonces**, `next.config.ts` `headers()` (or `astro.config.mjs`'s own headers equivalent for `docs-site/`) in all four apps, `script-src` restricted to `'self'` + the exact external hosts each app actually loads (per this ADR's own evidence-point-4 inventory — `www.googletagmanager.com`/`connect.facebook.net`/`analytics.tiktok.com` for `storefront/` only; `admin/`/`reseller/`/`docs-site/` load no external script host at all, so `script-src 'self'` with no allowlist entries and no `unsafe-inline` is achievable there). Revisit nonces only if a real inline-injection vector is ever found that an allowlist alone can't stop — not preemptively, against ADR-071's own measured cost.
