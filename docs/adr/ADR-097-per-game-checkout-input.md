# ADR-097: Per-game checkout input — Digiflazz `customer_no` separator moves from per-supplier to per-game, and a Zone ID picklist replaces free text, with matching validation added to every channel

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled 2026-09-15, stress-tested against real code 2026-09-16 (see this entry's own addendum below). **PR-1 (Topic 1, separator) merged to `staging` 2026-09-15 — see `docs/build-log.md`. PR-2 (Topic 2, zone picklist) built 2026-09-16 on `feature/adr-097-zone-id-picklist`, PR open, not yet merged.**

**Context:**

Two related but independent findings from the founder's own real usage, both landing on the same admin surface (`/middleware/product-manager`'s per-game "Checkout Input" concept, `Game.validation_rules`):

**Finding 1 — the Digiflazz `customer_no` separator is wrongly scoped to the whole supplier, not per-game.** `Supplier.api_config['customer_no_separator']` is resolved once per-supplier (`SupplierAdapterFactory` binds one `DigiflazzAdapter` instance per slug), and `normalizeCustomerNo()` concatenates `{playerId}{separator}{serverId}` identically for every game on Digiflazz. But Digiflazz itself doesn't publish the real per-game `customer_no` wire format — different games the seller (Digiflazz) forwards orders to expect different shapes: concatenated (`510496072005`), space-joined (`51049607 2005`), or pipe-joined (`51049607|2005`), confirmed from the founder's own real order failures/successes. Changing the one supplier-level value moves every game's format at once, which is wrong.

**Correction found mid-grill, worth recording precisely (the founder caught this, not assumed):** `AppServiceProvider.php`'s `digiflazz` binding passes `customerNoSeparator: (string) $apiConfig['customer_no_separator']` with **no `??` fallback** — so `DigiflazzAdapter`'s own constructor default (`'|'`) is dead code, never reached. Production's real `Supplier.api_config` has no `customer_no_separator` key set at all (confirmed via SSH), so `(string) null` casts to `""` — **the real effective behavior in production today is concatenation, not pipe.** The class-level default was a red herring in this grill's first pass.

**Finding 2 (unrelated cause, same admin surface) — Zone ID has no allowed-value list anywhere.** `Game.validation_rules.extra_field` is a bare flag (`null`/`'server_id'`/`'zone_id'`) — no list of valid values exists. The storefront checkout wizard (`Step1AccountInfo.tsx`) renders whichever extra field as free text. A zone-requiring game's real values often carry wording (e.g. "SouthEastAsia", "MENA") rather than digits, and a customer typing an abbreviation ("SEA") causes a real order failure at the supplier — Digiflazz doesn't correct or fuzzy-match this for us; whatever string we send is exactly what's forwarded.

**Facts checked against real code before deciding:**

- `SupplierOrderRequest`/`SupplierStatusCheckRequest` carry no game/package context today (`productRef`, `referenceNumber`/`supplierRef`, `playerId`, `serverId`, `customerPhone`, `callbackUrl`, `orderId` only) — an additive per-call separator field widens these DTOs without reshaping the `SupplierAdapter` interface (this project's "deep modules, stable seams" convention). `OrderFulfillmentService` already has the Game/Package in scope everywhere it builds these requests.
- **Gamevion has the identical concatenation quirk, hardcoded, no config at all** (`GamevionAdapter::createOrder()`: `"{$request->playerId}|{$request->serverId}"`, always `|`, never configurable). No reported issue there — founder's own call: leave Gamevion untouched, Digiflazz-only scope for now.
- `Game.validation_rules` is an existing nullable JSON array column, today used for exactly one key (`extra_field`) — sibling keys need no migration.
- Presence/value enforcement today, per channel — checked directly, not assumed: Storefront's `CheckoutController::store()` enforces **presence** of the extra field when required (422 otherwise), no value check (no list exists to check against). Reseller Bot's `ResellerBotService::handleOrder()` also enforces **presence only** (`missing_server_id`). **Reseller API's `PlaceOrderRequest`/`ResellerOrderPlacementService` enforce neither** — `server_id` is bare `['nullable','string','max:64']`, a pre-existing gap independent of this ADR.
- The Reseller API's request/response shapes are the public contract behind ADR-084's Scramble-generated spec (`docs.pekangame.space`) — any change to `PlaceOrderRequest`'s validation becomes publicly documented surface, not internal-only.
- The Reseller Bot is WhatsApp free-text only — no native picklist UI is possible there; enforcement can only be "exact match against the allowed list, else reply naming the valid values" (the same shape ADR-093's fat-finger safety net already established).
- **The ongoing edit surface for `validation_rules` already exists** — `CheckoutInputEditor` (`/middleware/product-manager`'s linked-group detail view), built specifically because `LinkCategoryModal`'s one-time link-time setting had no way to be corrected afterward. `EditGameModal` (`/admin/games`) explicitly and deliberately excludes `validation_rules` in its own doc comment — "a supplier-integration decision, not a catalog-display one" (this project's established catalog-vs-supplier-integration split, `[[feedback_middleware_vs_admin_config_placement]]`). Extending `CheckoutInputEditor` is the correct continuation of an already-drawn line, not a new one.
- The Reseller API's catalog endpoint (`GET /v1/catalog`, `ResellerApi\CatalogController::index()`) returns `{code, name, packages}` per game today — no checkout-input metadata at all. A reseller/bot integrator has no programmatic way to learn what a game needs or how to format it.

**Decision — Topic 1 (customer_no separator):**

1. **Digiflazz-only, not generalized to every supplier.** Matches the real, reported pain point; Gamevion's hardcoded `|` stays untouched. A future supplier needing this extends the same mechanism, not a reason to build it generically now.
2. **Stored as a named enum in `Game.validation_rules['customer_no_separator']`: `'concat' | 'space' | 'pipe' | null`.** Self-documenting over a literal character (`''`/`' '`/`'|'`), which risks silent whitespace/escaping confusion in JSON. `DigiflazzAdapter`'s `normalizeCustomerNo()` (or its caller) maps the name to the real wire character.
3. **`null` (unset) means "inherit whatever `Supplier.api_config['customer_no_separator']` currently resolves to"** — today, concatenation (Finding 1's correction). No backfill/migration: every existing game keeps behaving exactly as it does today until an admin explicitly opts a game into `'space'`/`'pipe'`.
4. **The caller supplies the separator, the adapter never looks it up itself.** `OrderFulfillmentService` (which already has the Game in scope wherever it builds a `SupplierOrderRequest`/`SupplierStatusCheckRequest`) resolves the effective separator (game override, else the supplier default) and passes it as a new optional field on those DTOs. `DigiflazzAdapter` gets strictly more explicit about what it's given, never reaches into a repository — matches this project's "deep modules" convention over the alternative (adapter resolving a game_id itself).
5. **Editing surface: `CheckoutInputEditor`** (`/middleware/product-manager`, Finding above) gains this as a second control alongside the existing `extra_field` select — not `LinkCategoryModal` (link-time only), not `EditGameModal` (wrong split).

**Decision — Topic 2 (Zone ID picklist):**

6. **Plain string array, not label+value pairs** (`Game.validation_rules['zone_options']: string[] | null`) — founder's own reasoning: Digiflazz doesn't reinterpret or correct the value we send, whatever string the admin picks as an option IS the literal wire value forwarded verbatim. No evidence today of a real game needing a friendlier display label distinct from the wire value; add label+value later only if a real case demands it.
7. **`null`/empty `zone_options` preserves today's free-text behavior exactly** — a `zone_id`-requiring game with no defined list yet is unaffected; the storefront only switches to a `<select>` once a real list exists for that game. No game is forced to migrate.
8. **Editing surface: the same extended `CheckoutInputEditor`**, a simple add/remove list editor for `zone_options`, shown only when `extra_field === 'zone_id'`.
9. **Storefront (`Step1AccountInfo.tsx`):** renders a `<select>` from `game.validation_rules.zone_options` when present and `extra_field === 'zone_id'`; unchanged free-text `<input>` otherwise (server_id, or a zone_id game with no list yet).
10. **Value-parity across every channel — the founder's own explicit call, not left ambiguous.** Reseller API and Bot get the SAME value-restriction the storefront's `<select>` enforces, not a looser "trusted B2B caller" carve-out:
    - **Reseller Bot** (`ResellerBotService::handleOrder()`): on top of its existing presence check, reject a `zone_id` value not in `zone_options` with a reply naming the valid options — same shape as ADR-093's fat-finger safety net. No fail-open concept applies here (unlike ADR-093's third-party-validator outage case) — this is a pure local DB read with no external dependency, so a wrong value is always a hard, immediate reject.
    - **Reseller API** (`PlaceOrderRequest`/`ResellerOrderPlacementService`): gains BOTH the presence-when-required check it's missing today AND the value-restriction check, in the same change — the founder's own call (decision 11 below explains why folding the pre-existing gap in here, rather than filing it separately, is the right scope).
11. **The pre-existing Reseller API presence-validation gap is fixed as part of this ADR, not filed separately.** Value-validation necessarily has to check presence first (the same `if` chain) — building the value check without also closing the presence gap it sits directly on top of would be artificial scope-splitting of one natural piece of logic.
12. **Reseller API gains a genuinely new capability, not just a validation fix: `GET /v1/catalog` (`ResellerApi\CatalogController::index()`) exposes each game's checkout-input requirement** — founder's own extension of the original ask ("supaya reseller boleh tahu field dia apa dan macam mana nak hantar"). Each game row gains e.g. `"checkout_input": {"field": "zone_id"|"server_id"|null, "options": string[]|null}` — an integrator (developer or the Bot's own `.listharga`/`.list` reply) can now discover the requirement programmatically instead of guessing or hardcoding.
13. **`docs.pekangame.space`'s public spec documents the *behavior* (a per-game-validated field, with the new `checkout_input` catalog descriptor telling the caller how), not a static enum of every game's actual zone values baked into the OpenAPI schema** — the real list is admin-editable, per-game data, not a fixed contract shape. Nothing about this needs the ADR-084 wording-scrub loop revisited; it's new documented surface, not internal-term leakage.

**Rationale:**

- Separator (Topic 1) and zone list (Topic 2) share the identical config location and editing surface (`Game.validation_rules`, `CheckoutInputEditor`) but are otherwise fully independent — Topic 1 never touches customer-facing UI or other channels' validation at all; Topic 2 never touches `DigiflazzAdapter`'s wire-format assembly. Building on the *existing* `CheckoutInputEditor` rather than a new screen respects this project's own already-drawn catalog-vs-supplier-integration line (`EditGameModal`'s own doc comment) instead of quietly redrawing it.
- Value-parity (decision 10) closes the exact class of failure the founder is trying to prevent — a fat-finger zone typo — for the channel it's arguably MORE likely on (a reseller/bot user typing manually, same as a storefront customer) rather than only fixing the surface with the nicest UI and leaving the other two exposed.
- Folding the Reseller API presence-gap fix into this ADR (decision 11) rather than a separate ticket keeps one logical validation change in one PR — splitting it would mean touching the exact same `if` chain twice, in two separate reviews, for no real isolation benefit.
- Decision 3's "null inherits the supplier default, no backfill" and decision 7's "null preserves free text" are the same underlying discipline applied twice: a new admin capability should never silently change behavior for a game/game-set that hasn't opted in.

**Consequence to track:**

- If a future supplier other than Digiflazz needs a configurable `customer_no`-shaped separator, decision 1's Digiflazz-only scope is the thing to revisit — the mechanism (per-game override, caller-supplies-to-adapter) generalizes cleanly; only the wiring is Digiflazz-specific today.
- If Gamevion's hardcoded `|` ever becomes a real reported problem, it's the same shape of fix as this ADR, not a new design.
- `docs.pekangame.space`'s spec (decision 13) should be spot-checked once built to confirm the new `checkout_input` catalog field reads clearly to an external integrator, not just internally.

**Addendum, 2026-09-16 — stress-tested against real code (`/mattpocock-skills:grilling`, 4 rounds) before any build, at the founder's own request given the feature's reach (storefront + Reseller API + Bot). One real bug and two unexposed-surface gaps found; everything below is settled, continuing this ADR's own decision numbering. Staged into two PRs (decision 25) — PR-1 not yet started.**

14. **Decision 4's separator-resolution fix is wired at all FOUR real call sites, not the two implied by "`OrderFulfillmentService`."** Real-code check found `SupplierDeliveryCheckService` (`checkOrder()` + `checkComboLegs()` — ADR-096's scheduled reconcile poll AND the admin manual "Check from Supplier" button) builds its own `SupplierStatusCheckRequest` completely independently of `OrderFulfillmentService`. Left unfixed, a Digiflazz game set to `'space'`/`'pipe'` would get the correct `customer_no` on `createOrder()` but the WRONG one on every `checkStatus()` re-submit — and Digiflazz's `checkStatus` is a literal re-submit of the same customer_no (ADR-030 decision 1), so a mismatch risks the poll never recognizing the original order. Fixed at: `OrderFulfillmentService::fulfill()`, `::fulfillCombo()`'s leg loop, `SupplierDeliveryCheckService::checkOrder()`, `::checkComboLegs()`. Combo legs verified safe to resolve against `$order->game` directly — `StoreComboPackageRequest` hard-enforces same-game components at save time, confirmed in code, so there's no per-leg game divergence to worry about.
15. **DTO field carries the raw Game-level override only; `DigiflazzAdapter` owns 100% of name→wire-char translation and the supplier-default fallback.** `SupplierOrderRequest`/`SupplierStatusCheckRequest` gain one nullable field (`'concat'|'space'|'pipe'|null` — the Game override, nothing else). The adapter maps it and falls back to its own constructor-injected supplier default internally when null — no caller ever computes or knows the literal wire character, and no caller duplicates the adapter's own default logic. Matches decision 4's own "adapter never reaches into a repository" reasoning and keeps decision 14's four call sites to a one-line read each. To avoid four copies of the same raw `$game?->validation_rules['customer_no_separator'] ?? null` array-key literal (typo-drift risk across 4 sites), that read is a single small `Game` model accessor, called identically everywhere.
16. **`CheckoutInputEditor`'s existing save path is a full-column REPLACE, not a merge — a real, live silent-data-loss trap for this ADR's own build.** `Middleware\SupplierProductController::linkCategory()` does `$game->update(['validation_rules' => $data['validation_rules'] ?? null])`. The editor's existing "Update" button (decision 5's continuation point) already sends only `{extra_field: X}`. This ADR adds TWO more sibling keys (`customer_no_separator`, `zone_options`) as separate controls on the same editor — unless the editor sends the FULL merged object on every save, clicking Update on any one control silently wipes the other two. Fix: the editor holds and sends the whole `validation_rules` object (spread existing + override the one changed key) on every save, from the first commit that adds a second control — not patched in afterward.
17. **Two response surfaces don't expose what decisions 9/12 assume they already do — both are real, in-scope gaps, not implementation afterthoughts.** Storefront's `CatalogController::publicGameDetail()` (the endpoint `Step1AccountInfo.tsx` actually calls, via `show()`) flattens only `extra_field` today — no `zone_options` at all; fix adds it as a flat sibling key (decision 21 explains why flat, not nested). Reseller API's `CatalogController::pricedCatalogForTier()` explicitly column-selects `Game::query()->get(['id', 'reseller_code', 'name'])` — `validation_rules` is absent from that list, so decision 12's `checkout_input` descriptor would silently resolve to null for every row unless that select list is also touched.
18. **Reseller API's presence+value check lives in `ResellerApi\OrderController::store()`, not in `PlaceOrderRequest` or inside `ResellerOrderPlacementService::placeOrder()` — this ADR's own "PlaceOrderRequest/ResellerOrderPlacementService" phrasing was imprecise, corrected here.** Real-code check: `PlaceOrderRequest` genuinely cannot do it — `product_code` only resolves to a `Package`/`Game` inside `store()`, after FormRequest validation runs (the FormRequest's own doc comment says so). `ResellerOrderPlacementService::placeOrder()` receives an ALREADY-resolved `gameId` — the exact same shape `ResellerBotService::handleOrder()` already uses today (resolve product → resolve Game → check extra_field presence → THEN call the shared placement service). So `store()` gains the same check `handleOrder()` has, in the same relative position in its own flow — not a new shape, the existing Bot precedent extended to the second caller.
19. **One shared validator, not three independent copies of the same if-chain — including refactoring the storefront's pre-existing check, not just the two new callers.** New `CheckoutInputValidator::validate(Game $game, ?string $value): ?array{field: string, message: string}` (null = valid), covering both presence (any `extra_field`) and zone-value-restriction (`extra_field==='zone_id'` with a non-empty `zone_options`). Called from storefront `CheckoutController` (replacing its existing inline presence-only check), `ResellerApi\OrderController::store()`, and `ResellerBotService::handleOrder()`. Each caller still shapes its OWN response from the returned `{field, message}` — storefront maps `.field` onto its existing form-error array, the Reseller API wraps it into `ResellerApiException::validationFailed(['...' => [...]])` (decision 22 — no new error code), the Bot uses `.message` as the WhatsApp reply text. One rule, three channel-native response shapes — never three copies of the rule itself.
20. **Admin `LinkSupplierProductCategoryRequest` enforces relevance server-side, not just UI-hidden.** `customer_no_separator` is rejected unless the linked category's supplier is actually Digiflazz (decision 1's own scope); `zone_options` is rejected unless `extra_field==='zone_id'` (decision 8's own scope). A silently-set-but-never-read field is exactly the class of stale-config trap this ADR's own Finding 1 already burned the project on once (the dead adapter-constructor default) — not repeating that with two brand-new fields.
21. **`zone_options` is trimmed, empty-dropped, and deduped server-side on save** (same `LinkSupplierProductCategoryRequest` pass as decision 20) — mirrors this codebase's existing `list`-type field coercion pattern (`SupplierConfigSchema`'s comment on its own list fields: "Trims entries, drops blanks"). Digiflazz forwards whatever string is sent verbatim (decision 6), so a stray leading/trailing space or a duplicate entry is a silent real-order failure risk, not a cosmetic one. **No length cap** on `zone_options` — unlike combo's `MAX_TOTAL_LEGS` (which had a real usage number to size against), no real per-game zone-list size is known yet; parked per this ADR's own "revisit against real usage, not speculatively" discipline (decision 1, decision 17).
22. **Storefront's new `zone_options` field stays a flat sibling of `extra_field`; the Reseller API's new `checkout_input` object (decision 12) stays nested — deliberately different shapes for deliberately different audiences, not an inconsistency to fix.** Storefront is a first-party frontend this project controls both ends of — minimal diff to `Step1AccountInfo.tsx`'s existing `extra_field` read wins. The Reseller API's `checkout_input: {field, options}` is a freshly-designed PUBLIC contract (ADR-084's spec) with no existing shape to match against — nesting it is the better design there, on its own merits, independent of what storefront does internally.
23. **Reseller API reuses the existing generic `ResellerApiException::validationFailed(array $details)` (already used elsewhere in this same controller) for a bad/missing checkout-input value — no new error code minted.** `store()`'s own doc comment already documents `VALIDATION_FAILED` as a 422 cause. Matches decision 13's "document the behavior, not a bespoke enum" framing, and is exactly why decision 19's shared validator returns a structured `{field, message}` rather than a bare string — `store()` wraps it straight into `validationFailed(['<field>' => [message]])`.
24. **Staged as two PRs, not one combined diff.** PR-1 = Topic 1 (decisions 1-5 + 14-16) — backend + admin only, zero customer-facing surface, smallest/safest cut, ships first. **Decision 16 (the CheckoutInputEditor merge-on-save fix) belongs in PR-1, not PR-2**, despite living in Topic 2's numbering above — PR-1 is what actually adds the editor's 2nd control (decision 5), which is the exact moment the clobber risk first exists; shipping decision 5 without decision 16 would reintroduce the bug within PR-1 itself, not defer it. PR-2 = Topic 2's remaining, genuinely-Topic-2 decisions (6-13 + 17-23) — the larger storefront + Reseller API + Bot cut. Matches this repo's granular-commit convention over one large mixed diff; the Rationale section already called the two topics "otherwise fully independent" — that independence is about customer-facing surface, not about which PR the shared editor's save-safety belongs to.
25. **Dev-only tooling (`DeveloperToolController`'s probe endpoint, `OrderFulfillmentTestFulfill`, `ResellerOrderPlacementTestPlaceOrder`) is left as a known, non-blocking gap.** None of the three has a real `Game` in scope — they build DTOs from raw admin-typed payloads. Left as-is, a dev probing a `'space'`/`'pipe'` game through these tools gets decision 15's null-fallback behavior (supplier default), not the game-accurate result. No real money/customer path touches them; not worth build effort against.
26. **Two things checked and found to be non-issues, recorded so they aren't re-litigated later:** (a) a suspected live bug — `SupplierConfigSchema::REQUIRED['digiflazz']` still lists `customer_no_separator` as required, and this ADR's own Finding 1 already confirmed prod's `api_config` lacks a real value for it, raising the question of whether `RefreshSupplierBalancesCommand`'s daily sweep silently skips Digiflazz — verified FALSE via a live prod check (`ssh pekangame-prod`, `php artisan tinker`): the key is PRESENT with a `null` value, and `SupplierConfigSchema::missingKeys()` only checks `array_keys()` presence, never null-ness, so nothing is skipped. (b) storefront's `show()` endpoint (the one `Step1AccountInfo.tsx` calls, decision 17) is verified UNCACHED — a `zone_options` edit via `CheckoutInputEditor` is visible on the real checkout page immediately, no cache-invalidation work needed for the critical path. (The Reseller API's 60s-TTL priced-catalog cache and the storefront's separately-cached catalog *list* endpoint both inherit the same lag `extra_field` already has today — pre-existing, unrelated to this ADR, not a new gap.)

**Addendum, 2026-10-05 — per-game player-input contract (pre-launch money audit item 63, the Bot multi-line bullet). Grilled 2026-10-05 (Q1–Q13). Revises decision 19: the shared validator checks the player ID's format and the extra field's format, not just the extra field's presence and zone value.**

*Context.* The audit bullet was "Bot: several `.order` lines in one message place only the first." The trace found the real gap is wider and sits in the shared seam:
- `ResellerBotCommandParser` splits on all whitespace (newline included) and drops every token past the ones it needs, silently. A second line's `.order` becomes the first order's `server_id`.
- `CheckoutInputValidator::validate()` returns valid for a game with no `extra_field` whatever `server_id` holds, and `DigiflazzAdapter::normalizeCustomerNo()` appends any non-null `server_id`. So `.order X-10 123456 tq` on a User-ID-only game (17 of 30 reseller games) sends `customer_no = 123456tq`, after the wallet is debited. The Reseller API (`server_id` nullable) has the same path.
- No format check on `player_id` or on a `server_id`-type value anywhere: `12345678 (2001)` reaches the supplier as-is.
- The founder confirmed resellers send one order per message, so multi-line itself is rare; the single-line cases above are not.
- Prod 2026-10-05: 0 orders anywhere with a `server_id` on a no-field game, 0 non-digit `player_id`s, the only non-digit `server_id` is a valid Gangstar zone. Nothing to remediate.

*Pre-existing bug found in the trace.* `LinkCategoryModal` sends `validation_rules: {extra_field}` only, and `SupplierProductController::linkCategory()` replaces the column. Linking a second supplier category to an existing game silently wiped its `zone_options` and `customer_no_separator` (decision 16 fixed this for `CheckoutInputEditor` only).

*Decisions (continuing this ADR's numbering):*

27. **Each game's contract, enforced in `CheckoutInputValidator` for every channel.** `player_id`:
    - `numeric` (default when the key is unset): digits only.
    - `text`: letters, digits and `# . _ -`, no spaces (Riot ID `JettMain#1234`).
    `server_id` by `extra_field`:
    - `null`: must be absent/empty — a value is rejected, never silently dropped.
    - `server_id`: required, digits only.
    - `zone_id`: required, must be in `zone_options`; a zone game with no list (Wuthering Waves, Aniimo) still accepts any value (decision 7 unchanged).
    Both fields: leading/trailing whitespace trimmed, inner whitespace rejected, max 64 characters (Reseller API's existing cap, now uniform).
28. **Reject with a field-specific reason; never auto-correct.** Order not created, wallet untouched. Each channel shapes its own reply from `{field, message}` as decision 19 already set (storefront 422 form error; Reseller API `VALIDATION_FAILED`; Bot reply text in BM).
29. **Stored as `Game.validation_rules['player_id_format']: 'numeric' | 'text' | null`** (null = numeric), edited in `CheckoutInputEditor` (decision 5's surface, not `EditGameModal`). No data migration: every game is numeric until an admin opts it into `text`. Founder's call: they set Valorant (×5) and any other non-numeric game themselves after deploy; those games' orders are rejected until then.
30. **`linkCategory()` merges `validation_rules` instead of replacing it.** Keys the request sends overwrite (an explicit null still clears); keys it omits are kept. Closes the `LinkCategoryModal` wipe above and protects the new key the same way.
31. **Same rule on every path that sends a player ID to a supplier or a paid validator:** storefront checkout, Reseller API, Bot `.order`/`.checkid`, admin Resend with an ID correction (decision 10 of ADR-102), and the storefront "Check ID" endpoint (`PlayerValidationController` — rejects before the paid provider call). Exempt: Middleware sandbox order and Developer Tool (admin test tools, decision 25's precedent).
32. **Bot: extra tokens on `.order`/`.checkid` are rejected, not dropped** — this also covers a multi-line message without a multi-line-specific rule. Replies show the game's real format built from its `validation_rules` (`{userId}`, `{serverId}`, or the zone list), never hardcoded per game; the `.list` footer does the same.
33. **Reseller API: `checkout_input` gains `player_id_format`** (`numeric` | `text`). Same `VALIDATION_FAILED` 422 envelope, field-specific `details` messages. Input that used to be accepted can now be rejected, so the API docs bump to **v1.3.0** with that note.
34. **Storefront:** the catalog detail exposes `player_id_format` (flat, decision 22). A `numeric` field gets `inputMode="numeric"`, blocks non-digit keystrokes, and a paste containing non-digits is left as-is with an inline error — never stripped, because `12345678 (2001)` stripped becomes `123456782001`, a plausible wrong ID the backend would accept. A `text` field gets a normal keyboard (today every game gets the numeric keypad, which made a Riot ID hard to type on a phone). The backend stays the authority.
35. **Out of scope, recorded:** Zenless Zone Zero is configured User-ID-only though it likely needs a server like Genshin/HSR — a data fix the founder makes in Product Manager, not code. No `ID (Server)` auto-split on paste (add if customers complain).
