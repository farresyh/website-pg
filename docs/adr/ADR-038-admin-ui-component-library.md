# ADR-038: Admin UI component library — adopt PrimeReact (Tailwind mode), opportunistic migration off hand-rolled TailAdmin primitives (design only, 2026-08-26; testbed built 2026-08-26)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled 2026-08-26. Decision 3's testbed (the Backups screen, ADR-039) built same-day.

**Build addendum, 2026-08-26 (Backups testbed):** live-testing the Backups screen surfaced a fact this ADR's research missed — PrimeReact v11's Tailwind/"primitive" architecture (`@primereact/core`'s `PrimeReactProvider`) is a **different, newer commercial product line ("PrimeUI")** than classic PrimeReact, and calls a real license check (`@primeui/license-manager`) on every mount: with no `license` prop, every admin page shows a permanent "Invalid PrimeUI License" red banner. This ADR's "open-source, ~340K weekly downloads" framing was true of classic PrimeReact's older API, not of the Tailwind-mode rewrite Decision 1 actually adopts. Resolved, not re-litigated: PrimeUI has a free "Community" tier (individuals/solo founders/orgs under $1M revenue, <5 developers, <10 employees, no material VC funding — this project qualifies); the founder registered at primeui.dev and supplied a Community-tier key, wired into `admin/src/components/prime-provider.tsx` via `NEXT_PUBLIC_PRIMEUI_LICENSE_KEY` (`admin/.env.local`, not committed). Flag this dependency for anyone else standing up a PrimeReact-Tailwind screen — the license check is unconditional, not gated on which components are actually used.

**Context:** `admin/` renders every screen with 7 hand-rolled UI primitives (`Table`, `Modal`, `Dropdown`/`DropdownItem`, `Badge`, `Button`, `RichTextEditor`, basic form inputs) living in `admin/src/components/ui` and `components/form` — not an npm dependency, fully custom-built/copied from the TailAdmin template. A read-only audit this session found two real gaps: no pagination component exists anywhere in `admin/` despite 15+ list screens (`orders`, `vouchers`, `withdrawals`, `blacklist`, `users`, `games`, SEO screens, etc. all render unpaginated), and no unit/component test framework exists in `admin/` at all — only the repo-level Playwright e2e suite's 3 golden-path specs (ADR-023).

The same session's investigation into `react-hooks/set-state-in-effect` CI failures (a new rule shipped in `eslint-plugin-react-hooks@7.1.1`, bundled via `eslint-config-next@16.2.11`) found the doc's earlier "9 files" estimate stale — a real lint run found **27 files, 33 errors** across `admin/`+`storefront/`, two distinct pre-existing patterns: (a) ~24 files copy `UserDropdown.tsx`'s SSR-hydration-safety session-read shape (`useEffect` reading `getClientSession()` then calling `setSession(s)` synchronously — deliberate, to avoid the server/client text-mismatch bug fixed 2026-07-25, but now flagged by the new rule), and (b) a handful of modals (`SyncDetailsModal.tsx` and similar) reset internal state via `setState(null)` inside an effect keyed on a changing prop (`isOpen`/`runId`) — React's own documented "resetting state when a prop changes" anti-pattern, unrelated to (a).

The founder wants to adopt **PrimeReact** (`primereact.dev`, open-source, ~340K weekly npm downloads) — a real component library shipping most of what `admin/` currently hand-builds, already documented, rather than continuing to build every primitive from scratch. Live research this session confirmed: PrimeReact 11.1.0's real catalog is 78 components across 10 categories (Form/Button/Data/Panel/Overlay/File/Menu/Messages/Media/Misc), it requires `react >=19.0.0` (project runs `19.2.4` — compatible), and it ships **four** integration modes — Headless, Primitive, Styled, and **Tailwind**. Tailwind mode is confirmed (via `primereact.dev/docs/tailwind/guides/introduction`) to copy component source directly into the consuming repo via a CLI, styled purely with Tailwind utility classes, with "no theme file, no runtime dependency" — closer to shadcn's code-ownership model than a conventional npm-dependency UI kit. Styled mode, by contrast, ships its own separate PrimeOne CSS theme/passthrough system, which would run a second, competing visual system alongside `admin/`'s existing hand-styled Tailwind v4 design.

**Decision:**

1. **Adopt PrimeReact in Tailwind mode only, never Styled mode.** Styled mode's separate PrimeOne CSS theme would introduce a second visual system alongside the existing hand-rolled Tailwind design; Tailwind mode copies component source into the repo and styles it with the same Tailwind utilities `admin/` already uses, so there is only ever one visual system to maintain.
2. **End-state target is full replacement of all 7 hand-rolled TailAdmin primitives with PrimeReact-Tailwind equivalents — not permanent coexistence.** One component system long-term is less maintenance than two running side by side indefinitely. `RichTextEditor` is the one exception: PrimeReact's current catalog has no rich-text-editor component, so the existing Tiptap-based wrapper stays untouched.
3. **Rollout starts on the next not-yet-built admin screen (the Backups feature, BAK-1..5, once its own ADR is grilled and built) as the first real testbed** — zero existing UI or tests to regress there, proving the migration pattern before touching money-critical, already-live screens (orders, vouchers, withdrawals, blacklist).
4. **Already-built, already-tested screens migrate opportunistically only** — when a file already needs to be opened for unrelated work (a bug fix, a feature change), not as a scheduled forced-migration pass. Rewriting a working, tested, live screen purely to swap its component library carries real regression risk for no matching benefit today.
5. **Opportunistic migration is enforced by three concrete, low-cost mechanisms, not left to memory:**
   a. `AGENTS.md` (root) gains a standing rule: any session that opens a file still using a hand-rolled TailAdmin primitive swaps it for the PrimeReact-Tailwind equivalent as part of that same change, referencing this ADR.
   b. `docs/prd.md` gains a migration-status tracker (mirrors §15's existing per-area table format) listing every admin screen and its migrated/not-migrated status.
   c. Every still-unmigrated primitive file gets a short inline comment flagging it for migration on next touch, referencing this ADR.
6. **The Backups testbed screen uses PrimeReact-Tailwind components exclusively — no mixing with old TailAdmin primitives within that one screen.** Keeps it a clean reference template for every later migration rather than an inconsistent hybrid the next migration has to interpret.
7. **Verification bar per migrated screen is manual live browser verification, matching this project's established habit — no new unit/component test framework is introduced as a prerequisite.** The 2 existing Playwright admin e2e specs (login → Resend Delivery, login → Issue Voucher) remain the only automated regression guard for now; revisit if migration scope grows large enough to justify a dedicated frontend test framework.
8. **The `react-hooks/set-state-in-effect` lint fix is decoupled from this migration — its own fix, its own timeline, not bundled into whichever future session does a PrimeReact swap.** Fix: centralize the SSR-safe session-read pattern into one `useClientSession()` hook (built on `useSyncExternalStore`, React's own designed solution for a value that must differ between server and client snapshots, which resolves the real value without a raw `setState` call inside `useEffect`) used by all ~24 sites; separately, give the "reset state on prop change" modals a `key`-based remount instead of a manual `setState(null)` effect. CI is red today; a multi-session UI migration is not an acceptable timeline to leave that unresolved.
9. **This session is decision-only.** This session's earlier-agreed priorities (SEO backend test coverage, the Backups feature's own ADR) proceed unaffected — SEO test coverage is backend-only and touches no admin UI. If the Backups ADR turns out to need a new or changed admin screen, that screen is built with PrimeReact-Tailwind per Decision 3, not TailAdmin.

**Rationale:** "PrimeReact has better docs" is not, by itself, sufficient reason to add a second UI dependency to a project that already has one working (if hand-rolled) design system — the real justification is narrower and load-bearing: `admin/` is missing real capability (pagination, nowhere in 15+ list screens) that hand-building would cost real time to add correctly, and PrimeReact's Tailwind mode specifically avoids the two-design-system maintenance cost the founder's "easier since documented" framing could otherwise hide, because the code becomes this repo's own code the moment it's copied in — not a black-box dependency to keep in sync. Starting on a not-yet-built screen and migrating live screens only opportunistically matches this project's own established risk posture (ADR-018's sandbox-first pattern, ADR-032's "generic mechanism only, not yet reachable in practice" sequencing): prove a new mechanism somewhere safe before it touches money-critical, live-traffic code. Decoupling the lint fix from the migration timeline avoids the exact failure mode a stalled or slow multi-session UI migration would otherwise create — CI staying red for however long full adoption takes.

**Consequence to track:**
- Decision 8 (the `useClientSession()` hook + modal `key`-remount fix) still needs its own build session — tracked independently of this ADR, not gated on Backups or PrimeReact.
- The Backups feature's own ADR (not yet grilled) is now the designated first PrimeReact testbed per Decision 3 — flag this dependency when that ADR is grilled and built.
- Decision 5's three enforcement artifacts (AGENTS.md rule, prd.md tracker, inline comments) must all actually land before the opportunistic-migration policy is self-enforcing — landed together with this ADR in the same session, not deferred.
- A first-pass component mapping was researched this session (`Table`→`DataTable`, `Modal`→`Dialog`, `Dropdown`→`Menu`/`Popover`, `Badge`→`Tag`, `Button`→`Button`/`ButtonGroup`, Gallery's upload UI→`FileUpload`) but isn't re-decided here — feed it into the Backups testbed build once that ADR is grilled.
- `admin/src/components/ui/*`'s TailAdmin primitive files get deleted only once nothing references them anymore — no scheduled deletion date; tracked implicitly by Decision 2's full-replacement end-state.
