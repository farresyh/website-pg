# ADR-036: Voucher Merge — admin-triggered consolidation into a new code, no ledger write (built 2026-08-26)

> **Standing (2026-11-07):** In force; decision 4 narrowed: a no-expiry source keeps the merged voucher without one (2026-11-07 addendum). Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled 2026-08-25, built 2026-08-26, no scope changes on contact with code

**Context:** A real, recurring scenario: Order 1 (RM10) fails, refunded as Voucher A (RM10). Customer places Order 2 (RM15), applies Voucher A at checkout — RM10 covered by the voucher, RM5 paid in cash (ADR-024's partial-cover wallet model). Order 2 itself then also fails. Per ADR-024 decision #6/#7, `VoucherController::storeFromOrder()` restores Voucher A's balance back to RM10 **and** mints a **separate** new Voucher B for the RM5 cash portion, in one transaction — the customer now holds two active vouchers (RM10 + RM5) instead of one RM15 voucher.

ADR-024 decision #7 explicitly considered and rejected merging these automatically at the time, reasoning: *"no functional benefit — a customer can already hold multiple simultaneously-active vouchers... merging would add real bookkeeping... for a purely cosmetic 'one code instead of two.'"* That reasoning assumed holding two vouchers is functionally equivalent to holding one combined voucher. **It is not:** `CreateCheckoutRequest.php:101` accepts exactly one `voucher_code` per order (verified this session, not assumed) — checkout cannot stack multiple codes. A customer holding Voucher A (RM10) and Voucher B (RM5) genuinely cannot combine them to fully cover a RM15 order in one checkout; they can only ever apply one, paying the difference, leaving the other voucher stranded for some future, unrelated order. This is a real functional gap, not the cosmetic one decision #7 dismissed — this ADR reopens that one clause of ADR-024, nothing else in it.

Two other directions were considered and rejected this session before landing on the one below:
- **Automatic top-up** (any time a voucher would be issued to a customer who already holds an active one, top it up instead of minting a new code) — rejected: no admin visibility or control over *when* a merge happens, and risks silently combining vouchers from genuinely unrelated origins (different campaigns, different expiries) that a human would not have chosen to combine.
- **Multi-voucher checkout stacking** (keep vouchers separate, let checkout accept and sum several codes) — rejected: a much larger blast radius (`CreateCheckoutRequest`, `CheckoutTotalService`, `VoucherService::redeem()`/`restore()` all become 1:N instead of 1:1, plus a storefront UI rework) for the same customer-facing outcome a much smaller change achieves.

**Decision:**

1. **New admin action at `/admin/vouchers`: select two or more active vouchers belonging to the same customer, merge into one.** Same-customer ownership check reuses `VoucherService::assertUsable()`'s existing email/phone match, not a new guard. Manual and opt-in — the default behavior on order failure (decision 6/7 above) is **unchanged**; a customer who is fine holding two vouchers (founder's own observation: this is common) simply never gets merged.
2. **Mints a brand-new voucher code; both sources are voided, never reused.** Source vouchers get `remaining = 0` and a new status value, `'merged'` — not deleted (this codebase never deletes audit-relevant rows). Chosen over keeping one source's code as the "survivor": avoids ambiguity about which of two codes a customer may already have been told wins, at the cost of one more code the admin must relay — accepted since merges are expected to be infrequent (founder: "case ni tak selalu terjadi").
3. **New voucher's `amount`/`remaining` = sum of the sources' `remaining` at merge time, not their original `amount`.** Already-spent portions of a source voucher are not part of what is being consolidated — only the money still genuinely available moves.
4. **`expires_at` is set explicitly by the admin at merge time** — never auto-derived (later-of / earlier-of) from the sources' own expiries; avoids a business rule with no clear right answer.
5. **No ledger entry is written by a merge — verified against the real code, not assumed.** `VoucherService::issue()` (`VoucherService.php:60`) always writes a `voucher_issued` ledger debit; using it unchanged for the new merged voucher would book the combined liability a **third** time, on top of the two `voucher_issued` debits the source vouchers' own original issuance already wrote — a real ledger-correctness bug, not a style question. `VoucherService` gains a new method (mirroring `restore()`'s own existing no-ledger-write shape, `VoucherService.php:189-214`) that creates the merged `Voucher` row directly, bypassing `issue()`'s ledger call entirely. The liability already sits correctly in the ledger via the two sources' original entries; it is not being reversed, only re-represented under a different code.
6. **New `voucher_merges` audit table** (`source_voucher_id`, `target_voucher_id`, `reason`, `merged_by`, `merged_at` — one row per source, not a JSON array) — surfaced on the existing voucher detail page (`/admin/vouchers`, shipped 2026-08-13) so an admin can see which vouchers/orders a merged code traces back to. This is the real answer to "where did this voucher come from" for a merged code — `Voucher.order_id` stays a single `belongsTo` and cannot represent two-or-more source orders, so a merged voucher's own `order_id` is `null`, deliberately.
7. **Any admin can trigger a merge — not maker-checker-gated like large voucher issuance.** A merge creates zero new liability (net-zero risk to the platform ledger, per decision 5) — a materially different risk profile than issuing a genuinely new voucher. A mandatory `reason` field is the audit control, not a second approver.

**Rationale:** Manual/admin-triggered avoids guessing when an automatic merge is appropriate — the same reasoning this codebase already applies to every other special-case order/voucher action (Resend Delivery, Mark as Delivered, Issue Voucher are all admin-triggered, never automatic). Minting a new code rather than reusing a source's is the simpler mental model (a merge is its own event, not "voucher A absorbed voucher B"). No ledger write is the only financially-correct option once decision 5's math is worked through — the alternative silently double-counts real liability.

### 2026-10-12 addendum — an expired voucher cannot be merged (§16 item 80)

**Gap.** Expiry is decided by `expires_at` alone: nothing ever sets a voucher's `status` to `expired`, so an expired voucher still reads `active`. `merge()` checked only `status = active`, so an expired voucher could be merged and come back under the admin's new expiry (or none). A closed month may already have booked that credit as breakage (ADR-083 item 78), so this gave lost credit back. Found by the item 78 code-trace; production had 0 merges on 2026-10-10.

**Decision.** `merge()` rejects the whole merge if any source has `expires_at` in the past, with the same `InvalidVoucherException` → 422 path as a non-active source. Decision 4 is unchanged: the admin still sets the new expiry freely for unexpired sources, including extending it, since that is a deliberate choice on credit that is still live.

**Not changed.** No status backfill to `expired` (the admin index's "Expired" count reads `status = 'expired'` and so stays 0; a separate display issue). The admin selection checkbox still offers an expired-but-`active` voucher; the server rejects it.

### Cross-reference (2026-10-12) — decision 5's ledger premise is narrower now

Decision 5 says each source's liability "already sits correctly in the ledger via the sources' own original `voucher_issued` debits". Since ADR-024's 2026-10-12 addendum (PRD §16 item 79), only an admin-issued source has that debit. A compensation source never had a cost to book, so it has none. Decision 5's conclusion is unchanged: a merge writes no ledger row, and the platform ledger stays right for any mix of sources.

### 2026-11-07 addendum — a voucher in use can't be closed, and customer credit never gains an expiry (PRD §16 item 168; revises decision 4)

**Status:** Accepted 2026-11-07. Grilled with the founder (Q1 to Q5), code-traced, stress-tested by two read-only forks whose top findings were re-read or re-run. Item 163's seam D.

**Context.** A redemption stays `reserved` from checkout until the order delivers or gives the value back; one on production stayed open 489 minutes. `merge()` only moved `remaining`, so a reserved amount stayed behind on the source. `restore()` then added it to a voucher nobody can spend, and `balanceAsOf()` reads a merged-away or revoked voucher as 0, so the books lost it too. Proven with a RM100 voucher and RM40 reserved: after a merge or a revoke, the customer has no RM40 and neither Cash Position nor breakage shows it. Nothing on production was hit: 12 vouchers, 0 reserved, one merge, 0 revokes, none with an expiry.

**Decisions.**

1. **A voucher an order is using can't be merged or revoked.** `merge()` and `revoke()` are the only two closers, so one check in `VoucherService` covers both, and the refusal names the order and the voucher. The admin waits, or resolves the order. An order may not be paid yet, so the message doesn't say "settle".
2. **The check is a plain read taken after the voucher lock, never a locking read.** `restore()` locks the redemption and then the voucher, so a locking read deadlocks with it (proven: `ERROR 1213` with `restore` the victim, on MySQL with replica tables). Plain is enough: every reservation takes the voucher lock, so it committed before ours, and this is the transaction's first plain read, so its snapshot starts after that lock. A stale `reserved` can only refuse, the safe side.
3. **Refusing a revoke has a cost, accepted (founder, Q4).** The unreserved balance stays spendable until the order closes, so a voucher can't be stopped on the spot. Production has never revoked one. A "frozen" status was rejected: a new state on every voucher path for a case that hasn't happened.
4. **What each tool is for.**

   | Need | Tool | Expiry |
   | --- | --- | --- |
   | The customer's own money (a failed order) | Compensation voucher | Never |
   | A gift to a named person (giveaway, goodwill) | Admin-issued voucher (Path A) | Optional |
   | A public discount | Campaign, [ADR-118](./ADR-118-marketing-campaigns.md) | The code's `ends_at` |

   Expiry stays on vouchers for gifts. A Campaign can't replace it: it is percent only, new customers only, and for the primary brand only.
5. **Revises decision 4: if any source has no expiry, the merged voucher can't have one.** Settlement never sets an expiry, so a compensation voucher has none, and this rule keeps it that way through any chain of merges, with no new column. The admin can still date a merge of vouchers that all expire. The panel hides "Valid until" when the rule applies, and the server refuses it regardless.
6. **ADR-127's rule on expiry stands.** A restore onto an expired voucher is breakage of the restore month. Under decision 5 only gift value can expire, so this never takes a customer's own money. A cash share of the same order still comes back as a new voucher.
7. **The `/admin/vouchers` stats count a merge once.** A merge target re-represents its sources, so Total Issued leaves it out. Total Used reads redemptions, net of what was restored, because a merge zeroes a source without spending it. Both had been overstated by RM460.42 since the first merge. Display only: the ledger and Cash Position read neither.

**Rejected.**
- *Restore follows the merge to its target.* The target may be spent, expired or revoked by then, which is more cases, not fewer.
- *Issue a new voucher at restore.* It collides with what "compensated" means, and with the admin-issued expense line.
- *Remove expiry from vouchers and move giveaways to Campaign.* It would rebuild a fixed-RM, named-person voucher inside Campaign, which ADR-118 keeps separate on purpose.

**Consequence to track.**
- Re-check at release that no reservation sits on a merged or revoked voucher: this rule stops new ones, it doesn't repair old ones. 0 on 2026-11-06.
- A reservation whose payment lookup never answers keeps its voucher open with no admin exit. Correct, since that order could still be paid, and the value is held today regardless. 0 pending on 2026-11-06.
- A promo on OhahaStore, or for existing customers, needs an ADR-118 addendum first (PRD §16 item 171). OhahaStore is the busier brand: 51 paid retail orders against PekanGame's 27 on 2026-11-06.
