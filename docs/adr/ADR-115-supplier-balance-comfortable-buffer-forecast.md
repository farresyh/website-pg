# ADR-115: Supplier balance comfortable-buffer forecast — learned, per-supplier top-up threshold (design only, build parked)

> **Standing (2026-10-09):** Parked (designed, build deferred by founder). Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Parked — grilled 2026-09-28 (`/mattpocock-skills:grilling`, 3 rounds), fully designed and decided below, **build deliberately deferred**. No automatic trigger to start building (decision 10) — the founder will say when.

**Context:**

Companion to the new `/admin/balance` page (built same day, no ADR — pure composition of ADR-046/073, see `docs/build-log.md`). While discussing that page, the founder raised a broader question: today the "comfortable" Digiflazz balance to keep topped up (currently a static, eyeballed RM15k-in/RM5k-reorder rule) is a guess, not a measured figure — and topping up via bank transfer/Airwallex has a real 1-2 day settlement lag. If real spend across all three order channels (direct storefront, Affiliate storefronts, Reseller wallet) ever runs meaningfully hotter than that guess, a top-up started too late could land after the balance already hit zero, breaking checkout for every channel drawing on Digiflazz.

Two facts, checked against real code before grilling further:

- `Supplier.balance` already **auto-polls daily**, not just on manual click — `app:refresh-supplier-balances` (`routes/console.php`, `->daily()`, ADR-069 decision 12). That same command already checks a per-supplier `api_config['low_balance_threshold']` and `Supplier::fundingDrift()` (ADR-083 decision 6, ledger-vs-polled-balance variance) — both **`Log::warning()` only**, no UI surface, no admin sees either unless they read log files directly. Part B's real starting point is "surface an existing static threshold + silent warning," not a blank slate.
- `supplier_ledger_entries` (ADR-083) already records one `ORDER_DRAWDOWN` row per order (per leg, for combo) in the supplier's own native currency, append-only, with a timestamp — a clean, ready-to-aggregate daily-spend data source, provided `REFUND` rows are netted against it (otherwise any day with a refund overstates real net spend).

**Critical constraint driving the "parked" status**: PekanGame has **zero real external customers** as of this ADR (2026-09-28) — every order to date is the founder's own manual testing. A statistical model trained on that data now would learn testing noise, not real demand. Building the mechanism now would produce a confidently-wrong number.

**Decision:**

1. **Design now, build later — no automatic trigger.** The founder will explicitly say when to start building (typically once real customer orders exist). There is currently no `is_test_order` flag distinguishing founder-testing orders from real ones, so this trigger is a manual founder call, not something the system can detect on its own — adding that flag is out of scope here (a candidate for its own future decision if it turns out useful for Reports/Analytics too, not just this).
2. **Scope: Digiflazz only.** Gamevion's launch gate was retired 2026-09-24 (founder decision, `docs/prd.md` §16) — integrated but deliberately unfunded/deprioritized, effectively zero real spend. One supplier to model.
3. **One blended buffer, not per-channel.** Direct storefront, Affiliate, and Reseller-wallet orders all eventually draw down the same single Digiflazz balance pool at fulfillment time — the question "how much buffer do I need" is inherently about combined drain on one shared pot. A per-channel breakdown is a legitimate analytics view but not what sizes the buffer.
4. **Formula: rolling lead-time-window-sum, high percentile — not a flat daily rate.** Rejected the naive "average daily spend × lead-time days," because it assumes every day inside the lead-time window is typical — if a top-up lands right after a recurring high-volume day (the founder's own example: MLBB in-game events cluster Friday afternoons, materially higher volume than an ordinary day), that assumption underestimates. Instead: over a trailing window (default 60 days, giving ~8 weekly cycles of signal), compute the sum of `ORDER_DRAWDOWN` net `REFUND` inside **every rolling window equal to the lead-time length** (2 days, per decision 5), then take a high percentile (p90) of those window-sums. Because any historical 2-day window that happened to include a Friday spike is already inside that distribution, the recurring pattern is captured automatically — no day-of-week special-casing, no hardcoded event calendar to maintain.
5. **Lead time: 2 days, one global config value, not per top-up method.** The founder confirmed today's real worst case (topup today, funds land tomorrow) is 2 days across both bank transfer and Airwallex. A single admin-configurable number per supplier, set to the worse-case of whichever methods are actually used — not a per-method model, which would be complexity with no evidence it's needed.
6. **Cold-start: fall back to the founder's own manual number, admin-editable, until the trailing window has enough history.** Never show a percentile-derived figure computed from under ~2 weeks of data as if it were confident — it isn't. The existing static rule (currently RM15k/RM5k, held as `api_config['low_balance_threshold']`) stays the operative figure until the computed suggestion has enough trailing data to be trustworthy.
7. **Currency: show both IDR (native, Digiflazz's own denomination) and MYR side by side — never a silent single-currency conversion.** Reuses the existing FX-conversion mechanism ADR-033 already established for pricing, applied here only to the final display figure (the underlying spend computation stays in native IDR throughout, per the ledger's own native-currency storage). Showing both, rather than picking one, keeps the FX assumption visible and checkable rather than hidden inside one number — the founder tops up in MYR (Malaysia-based), so MYR is the actionable figure, but IDR stays alongside it as the ground truth.
8. **Output is informational only — no auto-action.** A suggested-buffer figure plus a visible UI warning when the live balance actually crosses it. No automatic top-up, no blocking of checkout, no external push (email/WhatsApp) — the existing `MAIL_MAILER=log` / silent-alert history (`docs/build-log.md`'s 2026-09-14 backup-alert incident) argues against adding a second alert channel with no proven delivery path yet.
9. **Surfaces in two places, reusing an existing pattern, not inventing a new one.** Full detail (IDR + MYR figures, last-computed time) on `/admin/balance`. A short amber chip on the Dashboard — mirroring the funding-ledger-drift chip ADR-083 decision 6 already put there — links through to the Balance page, so the founder doesn't have to remember to check a page proactively; Dashboard is what they land on.
10. **Implementation shape (recorded for whoever builds this, not re-litigated at build time unless the founder wants to)**: extend the existing `app:refresh-supplier-balances` daily command (natural home — it already runs daily, already touches this exact `Supplier` row, already computes the low-balance and drift warnings) rather than a new scheduled job; store the computed suggestion as new columns on `suppliers` (native-currency amount + computed-at timestamp), separate from `api_config['low_balance_threshold']` — the computed value is a recommendation the admin can choose to copy into the operative threshold, never a silent auto-overwrite of an admin-set safety number.

**Rationale:**

- Every design decision above traces to a real, already-observed constraint (the zero-real-customer state, the Friday-spike pattern, the 2-day lead time, the existing silent-warning gap) rather than a generic best-practice guess — consistent with this project's own "data-driven pricing/threshold modeling" discipline.
- Reusing existing seams throughout (the daily scheduled command, the ADR-033 FX mechanism, the ADR-083 Dashboard-chip pattern, the `supplier_ledger_entries` data source) means Part B is additive to already-decided architecture, not a new subsystem — smaller blast radius whenever it does get built.
- Recording the full design now, while explicitly deferring the build, follows this project's own practice for gated/future features: the *decisions* are settled and challengeable again at build time if circumstances changed, but nothing here is silently assumed or left to be re-derived from scratch by a future session.

**Consequence to track:**

- **Do not build this until the founder explicitly triggers it** (decision 1). A future session should not interpret "we have some real orders now" as sufficient on its own — confirm with the founder first, since there is no automatic real-vs-test order signal yet.
- If an `is_test_order` flag (or equivalent) is ever built for other reasons, revisit decision 1 — an automatic trigger (e.g. "N real orders in the last 30 days") becomes possible and may be preferable to a manual call.
- The 60-day trailing window and p90 percentile (decision 4) are defaults recorded here, not proven against real data (none exists yet) — treat them, like the rest of this design, as fully re-arguable once real spend data actually exists to tune against, not just numbers to tweak in isolation.
- If Gamevion is ever re-funded/re-activated (reversing the 2026-09-24 launch-gate retirement this ADR's scope decision 2 relies on), this ADR's single-supplier scope needs revisiting.
