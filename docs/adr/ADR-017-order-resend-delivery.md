# ADR-017: Order Resend Delivery — same-game package swap + live price reconciliation (built 2026-07-27)

> **Standing (2026-10-09):** In force; decisions 2/4 revised by ADR-105 (2026-10-06). Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-07-27 (grilled with the founder one decision at a time, informed by direct review of the legacy KeroxShop admin's own "Resend Delivery" modal and Order Details screen — real screenshots, not recalled from memory — per this project's long-standing rule that the legacy system is UI/UX reference only, never a source of product facts, [`legacy-reference-notes.md`](../legacy-reference-notes.md))

**Context:** ORD-7's currently-shipped `retryDelivery()` (`OrderController::retryDelivery()` → `FulfillOrderJob` → `OrderFulfillmentService::fulfill()`) is a purely **idempotent resend**: it re-submits the exact same `supplier_product_ref`/`player_id`/`server_id` already snapshotted on the `Order` row, reusing the same `reference_number` (ORD-8, unchanged), and only ever runs while `delivery_status=failed`. It cannot change what's being delivered. A founder audit of the legacy KeroxShop admin's own Resend Delivery flow surfaced a materially richer feature: the admin can swap to a **different package**, sees a live price comparison against what the customer actually paid, re-validates the Player ID before resending, and the order detail page keeps a **full history** of every attempt (not just the latest). This ADR designs that richer flow for this codebase — grilled one decision at a time, since it touches money/ledger correctness (`ADR-002`), not just UI.

**Decision (per sub-area, each grilled with the founder one at a time before being accepted):**

1. **Scope: same-game package swap only.** Admin may resend against a *different* `Package`, but only one belonging to the **same `Game`** as the original order. Swapping the game itself is explicitly **deferred, not abandoned** (see decision #9) — this phase ships the lower-risk half first.
2. **Checkout snapshot stays immutable — ORD-9 is unchanged.** `Order.cost_price`/`reseller_cost_price`/`selling_price`/`final_amount`/`transaction_fee` are the historical record of what the customer was actually charged at checkout time and are **never rewritten** by a resend. A resend is a new financial event layered on top of that record, not a retroactive edit of it.
3. **Live price is a reconciliation check, not a replacement for the snapshot.** At resend time, the selected package's *current* `cost_price`/`reseller_cost_price` (already kept live by Price Sync's Price Propagation, `ADR-015`) is compared against the original order's snapshotted values, purely to answer "has this gotten more/less expensive since checkout." The platform always **absorbs** the difference in either direction — never re-charges the customer, never blocks a resend over a price increase — but "absorb" must never mean "don't record." Per the founder: failing to record a 1-sen loss is worse than the loss itself.
4. **New audit table, `order_resend_attempts` — one row per resend attempt**, mirroring this codebase's existing `price_change_logs`/`deactivation_logs` discipline (insert-only, no `updated_at`): `order_id` (cascade), `package_id` (the package actually used *this* attempt — may differ from `Order.package_id`), `cost_price_sen`/`reseller_cost_price_sen` (live values read at attempt time), `price_diff_sen` (this attempt's cost vs. the order's original snapshot), `outcome` (success/failed), `supplier_response` (raw JSON), `note` (nullable, admin's own free-text — matches the legacy modal's "Note (Optional)" field), `triggered_by` (admin, nullable). This is what the Admin Orders detail page renders as a "Delivery Logs" history table — today's schema only ever has `Order.supplier_response`, overwritten on every attempt, so no history survives past the latest try.
5. **`final_amount`/`selling_price`/`transaction_fee` stay immutable — never touched by a resend, no exception.** These are the customer-facing record of what was actually charged, and are also the source of truth for total-sales analytics/reporting — a resend, or any package swap, must never retroactively change what a sales report says the customer paid. **`platform_profit`/`reseller_profit`, by contrast, are updated at the moment delivery finally succeeds** (whichever attempt that is — original or resent) to mirror whatever was actually credited to the ledger for that order. Reasoning: `creditProfit()` only ever fires once, on the attempt that actually succeeds (no earlier attempt ever credits the ledger — confirmed in `OrderFulfillmentService::fulfill()`), so there's no double-credit risk either way — but if these two fields stayed frozen at the checkout-time estimate while a resend's `LedgerEntry` credits a *different*, recomputed figure, `Order` would permanently disagree with its own ledger entry for the same order. These fields exist to mirror the ledger, not to preserve a pre-delivery estimate — same discipline as Price Propagation updating `Package.cost_price` to live truth, applied here to `Order`'s own profit fields, with `order_resend_attempts` (#4) as the audit trail for every intermediate figure along the way. Confirmed with the founder, 2026-07-27: total-sales analytics must key off the immutable customer-charged fields above, never off profit, which is exactly why this split is safe.
6. **Player-ID re-validation is conditional on `Game.player_validator_enabled`** (the toggle already shipped in `/admin/games`, `ADR-005`'s newest addendum). If enabled, the resend flow must run a validate-ID step (reusing the existing `PlayerValidationController`/`PlayerValidator` chain) before the resend button is actionable. If the game has no validation configured, the resend proceeds directly — no new schema, this reuses an existing mechanism end to end.
7. **Supplier reference handling — no change from today's already-correct behavior.** `Order.reference_number` (ours) is reused unchanged across every resend attempt (ORD-8, unaffected by this ADR). `Order.supplier_ref` (the supplier's own returned ID) already gets overwritten to the latest value on a successful `fulfill()` call — confirmed in the current `OrderFulfillmentService::fulfill()` implementation, nothing to build here.
8. **No new `DeliveryStatus` value for a supplier-side post-success reversal ("refunded by supplier").** `delivery_status` stays binary (delivered/failed) — a supplier that reports a refund/reversal reason does so inside its own raw response body, which this codebase already stores verbatim (`Order.supplier_response`). Any "refunded (Supplier)" badge is purely a UI-level read of that existing raw field when a supplier happens to populate it — some suppliers give a reason, some don't (a bare "failed" the admin must manually confirm with the supplier directly), and that variability is inherent to the data, not something to model as a state machine.
9. **Cross-game package swap — explicitly deferred, not abandoned.** The legacy system itself never built this either; it was previously deprioritized on the reasoning that Voucher issuance already lets a customer choose a different game themselves, so an admin-side cross-game swap was judged redundant complexity for the same outcome. The founder still wants it eventually. Tracked for its own dedicated future grill session, which must cover at minimum: (a) Player-ID re-validation is **not optional** when the target game differs from the original — a validated ID for one game carries zero meaning for another, this is a different player account, not just a different SKU; (b) a package-discovery/equivalence UX across unrelated games (no schema for this exists today); (c) whether Voucher's existing self-service path still makes this not worth the complexity, or whether the founder's motivation (reducing customer friction/drop-off after a failure) justifies it anyway.

**Rationale:** Every sub-area above changes `OrderFulfillmentService`'s *implementation* around a resend, not the money-computation contracts `PricingService`/`CheckoutTotalService` already own — the same "deepen the module, don't reshape the seam" discipline this codebase has followed since `ADR-001`/`ADR-006`/`ADR-014`. Decision #3's "always absorb, always record" directly extends `ADR-002`'s ledger philosophy (full audit trail over a clean number) into a new scenario the ledger design didn't originally anticipate.

**Consequence to track:** this ADR records *design intent only* — no code exists yet, matching this project's own established practice of designing and grilling before building (`ADR-013`/`ADR-015`/`ADR-016`). All 9 decisions above are founder-confirmed, including #5's profit-field-vs-customer-charged-field split. Decision #9 (cross-game) is out of scope for whatever ships from this ADR — do not build it opportunistically alongside decisions #1–8 just because the code is nearby. Update `prd.md` §14/§15 once this actually ships.

**Addendum, 2026-07-27 (build session) — decisions #1–8 shipped, #9 still deferred:** `order_resend_attempts` (decision #4) now exists, same insert-audit discipline as `price_change_logs`/`deactivation_logs`. `OrderResendService` (`app/Services/Fulfillment/`) enforces, in order: the order is currently `delivery_status=failed` (decision #8's own state machine, unchanged — resend doesn't loosen the guard `retryDelivery()` already had), the target `Package.game_id` matches the order's own `game_id` and is active (decision #1), and — only when `Game.player_validator_enabled` and a profile is assigned — a recent `player_validations` row exists for the order's own player_id/server_id (decision #6, reusing `CheckoutController::assertPlayerIdIsValidated()`'s exact data-tuple-match discipline, not a new mechanism). `OrderController::resend()` pre-checks the same two guards synchronously for fast admin feedback, then dispatches `ResendOrderDeliveryJob` (ADR-014's async discipline — the admin panel never blocks on a live Gamevion call); the job re-derives live package values at actual attempt time and delegates to `OrderFulfillmentService::fulfill()` unchanged.

One concrete formula decision this ADR's own text left open, resolved during implementation: decision #5 says platform_profit/reseller_profit are "recomputed... to mirror whatever was actually credited," but doesn't specify the formula. Implemented by reusing `PricingService::calculate()` — the exact same function `CheckoutService::initiate()` already calls — against the *live* `cost_price`/`reseller_cost_price` of the package actually being resent, at the order's original `reseller_markup_pct`. This mirrors decision #5's own analogy ("same discipline as Price Propagation... applied here") rather than inventing a bespoke absorption formula: `Order.cost_price`/`reseller_cost_price`/`selling_price`/`final_amount`/`transaction_fee` stay exactly as decision #2 requires (never touched), while `platform_profit`/`reseller_profit` are set to this recomputed breakdown *before* `fulfill()` runs, so `creditProfit()`'s existing "fires exactly once, on success" guarantee credits the ledger with these figures — and if the attempt fails, nothing was credited, matching the checkout-time flow's own existing "stored figure is an estimate until delivery actually succeeds" behavior (not a new invariant introduced by this ADR).

Admin UI: `/admin/orders`' existing order-detail view (not a separate route) gained a "Resend Delivery…" button (gated on `delivery_status=failed`, matching the backend exactly) opening a modal — same-game active-package picker with a live cost-price reconciliation preview, an inline "Verify Player ID" step that only renders when the game requires it, and an optional note — plus a "Delivery Logs" table below the existing detail cards rendering every `order_resend_attempts` row, most recent first. 21 new backend tests (`OrderResendServiceTest` 12, `ResendOrderDeliveryJobTest` 4, `OrderControllerTest` +5 resend cases); full suite 396, all green. `npx tsc --noEmit`/`next build`/`eslint` all clean. Verified live against a real running `php artisan serve` + real Sanctum token: `GET /api/orders/{id}` returns the new `resend_attempts` relation, `POST .../resend` correctly 422s a cross-game package and 200s + queues a same-game one. **Not verified live**: an actual queued `ResendOrderDeliveryJob` run against the real Gamevion adapter — deliberately not attempted, since `GAMEVION_SANDBOX`'s real value wasn't checked first and ADR-006's own sandbox `500` limitation (or worse, an accidental real production call) makes that an action to take deliberately, not as a side effect of testing this feature. Decision #9 (cross-game swap) remains explicitly out of scope, not built.

**Addendum, 2026-07-27 (same session) — UI merged, one button instead of two:** first cut shipped "Resend Delivery…" as a *second* button next to ORD-7's original "Retry Delivery" (both gated on `delivery_status=failed`). Founder feedback: two buttons for "fix a failed delivery" was more confusing than useful — an admin shouldn't have to know in advance whether they want the plain-retry or package-swap variant before clicking. Consolidated to a single "Resend Delivery…" button whose modal **defaults the package picker to the order's own package** — submitting with no change reproduces the old "Retry Delivery" behavior exactly (the submit button itself even relabels to "Retry Delivery" when the selection is unchanged, "Resend Delivery" when it differs), routed entirely through the one resend flow (`OrderResendService`/`ResendOrderDeliveryJob`/`POST .../resend`) rather than two separate code paths. If the order's original package was deactivated since it failed (decision #1's own active-package guard would reject resubmitting to it), the modal leaves the picker empty and shows an explicit "original package no longer active — choose a replacement" notice instead of silently failing. The plain `POST /api/orders/{order}/retry-delivery` endpoint (ADR-014, `OrderController::retryDelivery()`) is unchanged and still exists on the backend — no reason to remove a working, tested primitive — it's simply no longer called from this UI; `admin/src/lib/orders.ts`'s `retryOrderDelivery()` helper was removed as genuinely dead frontend code once nothing called it. No backend logic changed, so no test/behavior impact beyond the admin UI itself.

**Addendum, 2026-10-06 — decisions 2 and 4 revised for `cost_price` (see ADR-105's 2026-10-06 addendum, decision 13).** A resend now writes `orders.cost_price` = the target package's live cost, so every COGS / cost reader matches the package actually delivered. `selling_price`, `final_amount`, `transaction_fee` and `voucher_discount` stay immutable as before. `price_diff_sen` now compares against the cost assigned before this attempt, not always the checkout cost; the checkout cost stays on the `initial` attempt row (ADR-106).
