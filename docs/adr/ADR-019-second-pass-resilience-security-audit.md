# ADR-019: Second-pass resilience & security audit — reconciling ADR-014 against real code, docs restructure

> **Standing (2026-10-09):** In force; cache deferral closed by ADR-077. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-07-27 (findings and sequencing discussed with the founder in a dedicated audit session; grilled on the "fix now vs. wait for deploy" split specifically, not per-item). **Partly revised:** the "no Redis, `database` cache driver" deferral was closed by [ADR-077](./ADR-077-storefront-read-path.md) (2026-09-07).

> **Extended by ADR-077 (2026-09-07):** the `database` cache-store decision this audit confirmed as correctly-built has since been reversed to Redis — the reasoning that held in 2026-07 (no production infra, Redis not worth the ops burden) stopped holding once ADR-048 put Redis in the stack and production Pulse data showed the `database` `cache` table causing multi-second lock stalls.

**Context:** ADR-014 (2026-07-26) recorded a 24/7 burst-resilience baseline — queue, retry, indexing, caching, rate-limiting, observability — as design intent, later confirmed built the same day (`prd.md` §14, 2026-07-26 entry). A full read-only re-audit was run 2026-07-27 (four scoped reviews: DB indexing + caching, queue/retry/load-balancing, observability, and OWASP-adjacent security — mass assignment, validation, CSRF, XSS, SQL injection) to verify ADR-014 against the actual code rather than trust the design doc, and to check the security surface ADR-014 didn't scope at all.

Result: all six of ADR-014's decisions are genuinely shipped as designed. Two things that looked like gaps on first read are not — they're the founder's own already-recorded deferrals: Redis (ADR-014 decision #1, deferred until real traffic justifies the infra) and Sentry/external error-tracking (ADR-014 decision #6, explicitly declined for cost/data-residency before real production traffic exists). What the audit did find genuinely new: a handful of code-level gaps ADR-014 never scoped (mostly on the auth/payment edges), one correction to an existing docs claim, and a confirmation that the project's production-infra gap (no queue worker, no Redis/S3 provisioned anywhere — `docker-compose.yml` still defines MySQL only) is real and unaddressed, consistent with `prd.md`'s own repeated note that this project is still 100% local Herd, no production host chosen (ADR-010).

**Decision — sequenced by what's actionable now vs. genuinely blocked on a production-host decision, not by raw severity:**

1. **Fix now — pure code/migration, no infra dependency, testable on local Herd:**
   - Add an index on `orders.created_at` (the default, unfiltered Admin Orders listing sorts by it with nothing backing that sort) and replace the "today" filter's `whereDate('created_at', ...)` with `whereBetween()` — `whereDate()` wraps the column in a function, which defeats any index on it regardless.
   - Verify the 7 tables using `foreignId()->constrained()` without a confirmed standalone index (`player_region_mappings`, `player_validations`, `price_change_logs`, `deactivation_logs`, `order_resend_attempts`, `games.player_validator_profile_id`, `gallery_images.uploaded_by`) via `SHOW INDEX` against real MySQL — the same gotcha already hit and fixed once, on `packages.supplier_id` (see ADR-006's neighboring migration note).
   - Add an idempotency key to `XenditGateway::createPayment()` — the shared `TransientFailureRetryPolicy` (ADR-014 #2) can retry a request that Xendit actually processed but whose response was lost, creating a second live payment request for the same order. This is a real double-charge risk distinct from order-fulfillment idempotency (PAY-2), which is already handled.
   - Add the same explicit short HTTP timeout to `XenditGateway::client()` that `GamevionAdapter` already has (with its own documented reasoning) — without it, a slow Xendit response can hold a request thread for the HTTP client's much longer default, compounded across retry attempts, on what is a customer-facing checkout path.
   - Log checkout failures (`CheckoutController`'s `catch (CheckoutFailedException $e)`, currently silent — no record anywhere of *why* a checkout failed) and admin login attempts, success and failure (`AuthController::login()`, currently unlogged — no audit trail for a brute-force attempt or a compromised account).
   - Rate-limit `POST /api/login` — the only mutating auth-adjacent route with no `throttle`, unlike `/checkout` (ADR-014 #4) and `/validate-player`.
   - Decide and either enforce or explicitly descope the existing `mfa_secret`/`mfa_enabled` columns on `AdminUser` — the schema exists (added ahead of this feature being built) but `AuthController::login()` never checks either, despite `foundation-security.md` mandating MFA ahead of withdrawal/voucher actions.
   - Fix `Admin\GalleryImageController` to read the upload disk from config (`FILESYSTEM_DISK`) instead of the hardcoded `'public'` string. This corrects `prd.md` §15's Image Gallery note ("a later swap to a real bucket costs a disk-config change, not a rewrite") — that's only true once this lands; today the disk is hardcoded, so an env-only swap wouldn't actually take effect.
2. **Defer until a production host is chosen — Redis/S3/worker specifics genuinely depend on the target, config now would be guesswork:**
   - Provision a real queue-worker process. `docker-compose.yml` defines `mysql` only — no worker container, no app container at all. This isn't hypothetical: the founder's own 2026-07-27 live-testing pass (`prd.md` §14) already hit the local-equivalent of this exact gap — Herd doesn't run a worker on its own either.
   - Move `CACHE_STORE`/`QUEUE_CONNECTION` off `database` to Redis once there's ops budget for the extra infra — reaffirming, not overriding, ADR-014 decision #1's own deferral reasoning.
   - Move gallery/hero-slide uploads to the already-configured (but unused) `s3` filesystem disk once a bucket exists — blocked on item 1's disk-config fix first.
   - Wire centralized log shipping — a Papertrail-shaped channel template already exists in `config/logging.php`, unused — once there's a production target to ship to.
3. **Revisit once there's real production traffic to learn from:**
   - Thread a request-correlation ID from inbound HTTP requests into the jobs they dispatch (each job already logs with good internal context via `Log::withContext()`; there's just no link from "this customer's request" to "the job it triggered" today).
   - Basic metrics — queue depth, job failure rate, checkout error rate. Extend `HealthController` with a threshold check first; a full metrics exporter is a later, bigger lift.
   - Schedule the existing `Smoke\{Xendit,Gamevion}SmokeTest` console commands as synthetic monitoring instead of leaving them dev/manual-only.
   - Add client-side error tracking to `admin/` and `storefront/` (neither has an `error.tsx` boundary or a reporting client today — a crashed component or failed fetch on the storefront is currently invisible until a customer complains).
   - FRAUD-1..4 (blacklist) — already tracked "Not started" in `prd.md` §15, reaffirmed here as a real, stated requirement in `foundation-security.md` with zero implementation, not a silent gap.
   - The small `lockForUpdate()` gap in `Admin\WithdrawalController::reject()`/`complete()` (unlike `approve()`, which already locks) — an audit-trail race only, no double financial movement, since the ledger is only touched in `approve()`.
4. **Docs restructure, done alongside this ADR:** root `CLAUDE.md`/`AGENTS.md` were auto-generated multi-agent-swarm tooling boilerplate with zero project-specific content — confirmed unused in practice (this audit session used none of it). Replaced with project-specific orientation (stack, layout, working conventions, ADR-driven-decision discipline) in `AGENTS.md`, with `CLAUDE.md` now a one-line `@AGENTS.md` import, matching the pattern `admin/`/`storefront/` already used. Added `backend/CLAUDE.md` (Laravel-specific conventions, loaded only when working in `backend/`, per how nested `CLAUDE.md` files are actually resolved) and a root `README.md` for onboarding/handoff. `mattpocock-skills` (grilling, codebase-design, domain-modeling) are named explicitly in `AGENTS.md` as the project's house style, since their vocabulary was already showing up unattributed in this very ADR log (`ADR-014`'s "each grilled with the founder," this doc's repeated "deepen the module, don't reshape the seam") — making the practice explicit rather than leaving it implicit.

**Rationale:** Same interface-vs-implementation discipline as every prior resilience/security ADR — nothing in Decision-1 or Decision-2 changes a public contract (`PaymentGateway`, `SupplierAdapter`, `OrderFulfillmentService` are all untouched). Sequencing by deploy-dependency rather than raw severity matches this project's actual state: the code-level fixes cost nothing to do now and mean deploy day is infra wiring only, not a second security pass rushed under launch pressure; the infra-dependent items would just be guesswork before a host is chosen, and revisiting them then is not a delay, it's the correct order of operations.

**Consequence to track:** update `prd.md` §14/§15 as each Decision-1 item ships — this is exactly the kind of finding `AGENTS.md`'s new "keep §14/§15 current" convention exists for. Decisions 2 and 3 are sequencing intent, not scope reduction — each has an explicit trigger condition (production host chosen / real traffic exists) to re-open it; don't let "deferred" quietly become "forgotten." **Addendum — self-review before committing this session's docs changes, 2026-07-27 (same session, not a new audit round):**

1. **Missed finding: per-supplier circuit breaker.** `foundation-security.md` §6 and `prd.md` (DASH-2, §9 Non-Functional Requirements) both state this as an explicit **MVP** requirement — unchecked in the checklist, not implemented in code, and this ADR's Decision-1/2/3 lists above do not cover it. What exists today (`TransientFailureRetryPolicy`) is a different mechanism: it retries *within* one request; a circuit breaker trips *across* requests after repeated failures and stops attempting calls to a down supplier for a cooldown window, preventing a retry storm across many concurrent orders when a supplier has a sustained outage. This is pure code with no infra dependency (belongs conceptually with Decision-1), but is a larger unit of work than that list's other items (a new stateful component, not a one-line fix or single migration) — recorded here as its own explicitly tracked item rather than silently folded into either list: **build a `SupplierCircuitBreaker` (or equivalent) wrapping the `GamevionAdapter`/`XenditGateway` call sites, before treating ADR-019's fix-now list as complete.**

**Addendum — fix-now list shipped, 2026-07-29 (new session, read-only audit converted into an implementation pass at the founder's direction):** every Decision-1 item is now built and tested (416 tests passing on the fast suite, 4 on the concurrency suite against real MySQL), except MFA, which the founder explicitly chose to descope rather than build this session (see its own line below). What shipped:
- `orders.created_at` index + `OrderController`'s `today` filter switched from `whereDate()` to `whereBetween()` (the former defeats any index on the column regardless of whether one exists).
- The 7 tables flagged as "unverified FK indexes" were checked directly against real MySQL (`SHOW INDEX FROM`, per `backend/CLAUDE.md`'s own standing instruction) and all 7 already had one — `foreignId()->constrained()` does reliably index itself on this schema. **What that verification pass found instead, previously unknown:** two migrations (`player_region_mappings`'s `unique(['player_validator_profile_id','country_code'])`, `player_validations`'s 4-column `index([...])`) have Laravel-auto-generated index names exceeding MySQL's 64-character identifier limit — `php artisan migrate:fresh` against real MySQL failed outright on both, a bug sqlite's default test suite can never surface (no such limit). Both fixed with explicit short names. This is a genuine, previously-undetected production-deploy blocker directly relevant to ADR-020 (real MySQL, not sqlite) — worth a full migration-file sweep for the same pattern before the first production deploy, not assumed fixed just because these two are.
- `XenditGateway`: explicit HTTP timeout (10s/5s, config-driven, mirrors `GamevionAdapter`'s own pattern) — the actual idempotency-key research (below) landed here too, as a doc comment on `CheckoutService::initiate()`'s `createPayment()` call.
- **Idempotency-key research, verified directly against docs.xendit.co (not assumed):** Xendit's Payment Request v3 API has **no client-supplied idempotency-key header** — its OpenAPI spec documents exactly 3 request headers (`api-version`/`for-user-id`/`with-split-rule`), none of them idempotency-related. Its real dedupe mechanism is server-side `reference_id` uniqueness: a second `POST` with the same `reference_id` (this codebase already sends `order.order_number`, stable per Order) gets a clean `409 DATA_NOT_FOUND` "Duplication is not allowed," never a second live payment request. This means a `TransientFailureRetryPolicy` retry *within* one `createPayment()` call was already safe against double-charging before this session — the real, still-open gap is different from what this ADR's fix-now list assumed: a **retried `POST /api/checkout` HTTP request** (customer double-click, client-side timeout retry) calls `CheckoutService::initiate()` again from scratch with a **brand-new** `order_number` each time, which Xendit's `reference_id` check can't catch at all. Closing that needs a client-supplied checkout-level idempotency key — a request-contract change touching `storefront/` too, not built this session (flagged, not silently dropped — see `prd.md` §14's newest NEXT SESSION pointer).
- `AuthController::login()` and `CheckoutController`'s `CheckoutFailedException` catch now log every attempt/failure (`Log::info`/`Log::warning`, admin_id/email/ip for login, game_id/package_id/channel_code for checkout — never a password or full customer PII).
- `POST /api/login` now rate-limited (`throttle:5,1` — tighter than checkout/validate-player's `10,1`, since this is a brute-force target, not a genuine-retry-tolerant customer action).
- **MFA — explicitly descoped, founder decision, 2026-07-29:** `mfa_secret`/`mfa_enabled` columns remain unchecked by `AuthController::login()`. Founder chose not to build the full TOTP enrollment+verify flow this session (a real feature — QR-secret generation, verify-and-enable endpoint, login-time code check, recovery codes, plus `admin/` UI — not a one-line patch). Recorded here per this doc's own no-silently-forgotten discipline: still a real, stated `foundation-security.md` §1 requirement, zero implementation, deliberately deferred rather than built partially or assumed done.
- `Admin\GalleryImageController`'s disk moved off the hardcoded `'public'` string. **Not** wired to the app-wide `FILESYSTEM_DISK`/`filesystems.default` — that env is already set to `local` in this project's own `.env` for unrelated reasons, and reusing it would have silently broken gallery's public-URL requirement (`local` has none). Given its own dedicated `filesystems.gallery_disk` (`GALLERY_DISK` env, defaults `public`) instead — corrects `prd.md` §15's Image Gallery note, which assumed the app-wide disk setting was the right lever.
- **`SupplierCircuitBreaker` built** — `App\Services\CircuitBreaker\CircuitBreaker` (cache-backed via the `database` store per ADR-014, so state is visible across queue-worker processes; simplified two-state closed/open, not a textbook three-state breaker — see its own doc comment for why that's an acceptable trade for this system's actual concurrency profile) wrapping `GamevionAdapter` via a new `App\Services\Supplier\CircuitBreakingSupplierAdapter` decorator (ADAPT-3: any future second `SupplierAdapter` gets the same protection just by being wrapped the same way, no interface change). **One correctness fix beyond the ADR's original one-line description:** the breaker only trips on `SupplierResponse::isServerError` (a new field, HTTP 5xx) — an ordinary 4xx business rejection (invalid product, insufficient balance) now resets the failure count as a health signal instead of counting toward tripping. Without this split, three unrelated "insufficient balance" orders in a row would have wrongly blocked every other order/game on a perfectly healthy supplier — the literal wording in this ADR's addendum above didn't anticipate that distinction, but `foundation-security.md` §6's actual requirement ("a down supplier must not be able to cascade into blocking the whole delivery queue") implies it. Deliberately scoped to suppliers only (not `XenditGateway`, despite this ADR's addendum text naming both) — `foundation-security.md` §6 and DASH-2 both scope the *stated* MVP requirement to per-supplier only; `CircuitBreaker` itself is generic enough to wrap `XenditGateway` later if that's ever decided, without rework. ~~No dashboard UI yet (`CircuitBreaker::state()` exists for whenever DASH-2's Dashboard screen gets built — still "Not started" per `prd.md` §15).~~ **Dashboard screen built 2026-08-27 — see [ADR-045](../adr.md), `CircuitBreaker::state()` now wired to `/admin`'s System Health section.**

**Addendum — correction, 2026-08-27: this ADR's `throttle:5,1` login rate limit (and every other bare `throttle:N,1` route added since, including the webhook `throttle:120,1` pair below) was never actually isolated per-route.** Found live while diagnosing the playwright E2E job (`docs/prd.md` §14's 2026-08-27 entry has the full root-cause story): `Illuminate\Routing\Middleware\ThrottleRequests::resolveRequestSignature()` keys a throttle bucket as `sha1($route->getDomain().'|'.$request->ip())` — the route path is never part of the key. Every `throttle:N,1` middleware call in `routes/api.php` that didn't pass the class's own optional 3rd `prefix` argument shared one counter per IP, regardless of each route's own configured `maxAttempts` — a guest hitting `/checkout`/`/client-errors`/etc. from one IP was silently spending `/login`'s 5/minute budget too, and vice versa. This directly contradicts this ADR's own framing above ("Rate-limit `POST /api/login`") and `foundation-security.md` §5's claim that the Xendit/CHIP webhook routes "have their own rate limit" — neither was true in the sense either doc meant. Fixed same session: every `throttle:` route in `routes/api.php` now carries an explicit unique prefix (`throttle:5,1,login`, `throttle:120,1,webhook-xendit`, etc.), isolating each route's bucket for real. New regression test: `AuthControllerTest::test_login_rate_limit_is_not_shared_with_other_throttled_routes`. `foundation-security.md` §5's webhook line updated to reflect the correction, not just this entry.

**Addendum — per-account and per-IP abuse limits, 2026-09-29 (Wave 3 PR-B; numbers proposed by the model, accepted by the founder without a grill).** The 2026-09-28 audit found four gaps that per-IP `throttle:` alone can't cover:
1. **Per-account login lockout** (`App\Support\AccountLoginThrottle`), used by both `POST /api/login` and `POST /api/affiliate/login`, with separate buckets per guard. After **10 failures within 15 minutes, from any mix of IPs**, the account is locked for **15 minutes**. The lock check runs *before* the password check, so even a correct password gets a 429 while locked. A success clears the count. The per-IP `throttle:5,1,*` stays as it is. **Trade-off, accepted:** anyone who knows an admin's email can trip the lock. That is why the window is short and never permanent: the worst case is a 15-minute wait. MFA is still the real fix (the descoped item above, and `prd.md` item 10).
2. **OTP send: 10/hour per IP**, added alongside the existing 3/hour per email (ADR-027 decision 26). Without it, one IP could mail-bomb any number of different inboxes. 10 leaves room for several people behind one NAT.
3. **OTP attempt counter is now atomic.** `OtpService::verify()` claims an attempt slot with a conditional `UPDATE ... WHERE attempts < 5` and consumes the code the same way (`WHERE consumed_at IS NULL`). Previously it read then incremented, so N parallel guesses against a code at 4 attempts each got a try.
4. **Reseller API failed-auth counter:** 20 failures/min per IP in `EnsureResellerApiKey`, then 429 `RATE_LIMITED` with `Retry-After`. The `reseller-api` limiter keys on the raw bearer token (ADR-074 decision 4, kept so shared-infra resellers don't starve each other), which gave every made-up key its own fresh bucket.
