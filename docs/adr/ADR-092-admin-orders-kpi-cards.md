# ADR-092: Admin Orders KPI cards — persistent, clickable status counts, closing the reseller-family audit's "no admin alert" gap without reopening ADR-073's manual-refund policy

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted & built — grilled 2026-09-12, built 2026-09-13 on `feature/adr-092-orders-kpi-cards`. `GET /api/orders/summary` (one grouped-aggregate query, `is_test=false` scope) + `OrderSummaryCards` above the existing `STATUS_FILTERS` pills on `/admin/orders`, polling every 60s. Zero touch to `ResellerOrderPlacementService`/`OrderFulfillmentService`/`refundToWallet`/locking, per decision.

**Context:**

The 2026-09-10 reseller-family audit (see `docs/build-log.md`) flagged "failed reseller-wallet order refund is admin-manual only… no admin alert" as item C, citing `ResellerWalletService`'s own docblock naming a "retry-then-refund terminal action" it implied was meant to become automatic.

Re-reading ADR-073 decision 7 in full before grilling corrected that framing: **manual-only was always the deliberate design**, not an unbuilt promise — *"Only when an admin decides not to retry further does the debited amount get refunded back to the reseller's own wallet balance… as a new terminal admin action."* Automating the refund itself would remove exactly the judgment call ADR-073 built this for: a `Failed` delivery is sometimes a wrong player ID or package the admin should fix and retry (via the existing Resend Delivery flow), not always a genuine terminal failure that should refund. The founder confirmed at the start of this grill: **keep the manual-refund policy unchanged, fix the visibility gap only.**

Two further facts, checked against real code before grilling further:
- A wallet-order `Reseller` is already notified **immediately** on delivery failure via WhatsApp (`SendResellerBotOrderNotification`, queued off `OrderStatusUpdated`) — the reseller already knows before the admin does. Neither the Bot (`.order`/`.trackorder`/`.baki`/`.topupbaki`/`.listharga` — no `.retry`/`.refund`) nor the API give a reseller any self-serve resolution path; only an admin, via the panel, can retry or refund.
- `Admin\OrderController::index()`'s `status` query param **already implements** every bucket this ADR needs — `need_action` (`payment_status=Paid AND delivery_status=Failed`, exactly item C's condition), `needs_review`, `pending_delivery`, `processing`, `completed`, `awaiting_payment`, `today` — rendered today as unlabeled filter pills with **no count shown**, so an admin must click one to learn whether anything is even in it. The gap is narrower than the audit's "no alert" framing suggested: it's not invisible, it's not *counted at a glance*.

The founder's own counter-proposal (with a reference screenshot from a different admin system — read as a **UI pattern reference only**, its numbers are that other system's data, not this platform's, per this project's own "reference vs. project data" discipline) was KPI number-cards above the existing filter pills, each clickable to apply that filter — a persistent, always-visible surface an admin doesn't have to remember to check, in place of a push notification (WhatsApp/email) that can scroll out of view in a busy chat.

**Decision:**

1. **No WhatsApp/email alert.** Considered and dropped in favour of the KPI-card approach below — a push notification into an already-busy WhatsApp surface is easier to miss forever than a number sitting at the top of the one screen an admin uses to work orders; it would also have needed a brand-new "admin/founder WhatsApp target" config that doesn't exist anywhere in this codebase today (`OpenWaClient::sendText()`'s `chatId` is currently only ever a reseller's own group id).
2. **Six KPI cards, each mapped to an existing (or lightly combined) `delivery_status`/`payment_status` bucket — no new bucket invented:**
   - **Need Action** = `need_action` as it exists today (`payment_status=Paid AND delivery_status=Failed`) — deliberately **not** merged with Needs Review or Pending Delivery. `needs_review` has its own distinct resolution actions (Mark Delivered / Resend — never Issue Voucher, ADR-026 decision 4c) and `pending_delivery` needs **no** admin action at all (an async supplier's own webhook or `ReconcilePendingDeliveriesCommand`'s poll resolves it) — folding either into "Need Action" would train the admin to click into a card and find nothing actually needing them, defeating the card's own purpose.
   - **Needs Review** = `needs_review`, its own card, for the reason immediately above.
   - **Processing** = `processing` **and** `pending_delivery` combined into one count — founder's own call: both mean "paid, accepted, being worked on" from an admin's-eye view, even though they're structurally different states for different reasons (a synchronous in-flight attempt vs. an async supplier awaiting confirmation). The two underlying filter pills stay separately clickable below the cards for anyone who needs the distinction; only the top-level count merges them.
   - **Completed** = `completed` (delivered).
   - **Today** = `today` — orthogonal to delivery status (cuts across every bucket by `created_at`), kept as its own card exactly as today's pill already is.
   - **All Orders** = total (`is_test=false`, matching `index()`'s existing permanent scope).
   - **Awaiting Payment stays a pill only, not promoted to a card** — it's `ReconcilePendingPaymentsCommand`'s own payment-side visibility gap (a webhook that never arrived), a different problem from "delivery needs an admin decision."
3. **New lightweight counts source, decoupled from the paginated list fetch.** A lean `GET /api/admin/orders/summary`-shaped read (single grouped/aggregated query, not six separate `COUNT(*)` round-trips) returns all six numbers at once. Deliberately **not** piggybacked onto `index()`'s existing paginated response — search-as-you-type and filter changes already re-call `index()` on every keystroke/click; recomputing all six counts on every one of those calls would be wasted work the cards don't need (a card's own count only needs to reflect reality, not the currently-typed search text).
4. **Cards poll every ~60s while the page is open** — the one piece of "proactive" behaviour this design keeps from the dropped WhatsApp-alert idea: an admin who leaves `/admin/orders` open through the day sees **Need Action** climb on its own when a new delivery fails, without a manual refresh. A single small grouped-count query on a 60s interval is cheap; this is not the same cost shape as polling the full paginated list.
5. **Clicking a card applies the same `status` filter its matching pill already sets** — cards are a second, larger-target entry point onto the exact filter mechanism that exists today (`STATUS_FILTERS`/`setStatus()` in `admin/src/app/admin/orders/page.tsx`), not a parallel filtering system.

**Rationale:**

- This closes the real gap (a number an admin can act on without first clicking into a filter to check) while touching zero money-critical code — no change to `ResellerOrderPlacementService`, `OrderFulfillmentService`, `refundToWallet()`, or any locking/ledger path. The entire build is a read-only summary endpoint plus a frontend layout change.
- Keeping "Need Action" scoped to exactly today's `need_action` semantics (rather than the reference screenshot's broader grouping) preserves an already-load-bearing distinction this codebase's own `OrderController::index()` docblock draws between "needs an admin decision" and "resolves itself" — collapsing that distinction into one number would be a real regression in what the card actually communicates, even though it reads as "more complete" at a glance.
- A dedicated summary endpoint over reusing `index()`'s response keeps the two query shapes independently cheap: the list query already varies per search/filter/page and shouldn't also carry six aggregate counts on every keystroke; the counts query never needs `search`/pagination params and shouldn't be recomputed by typing.

**Consequence to track:**

- This ADR fully resolves the reseller-family audit's item C **visibility** half. The **policy** half (manual-only refund) is explicitly reaffirmed, not reopened — if reseller order volume grows enough that manual review becomes an operational bottleneck, that is a **separate, future decision**, not a silent scope creep of this one.
- If a genuinely proactive push (not just an always-visible dashboard) is ever wanted later — e.g. once there's real order volume and an admin can no longer realistically have `/admin/orders` open all day — revisit the WhatsApp-alert idea dropped here decision 1, including provisioning a real admin/founder OpenWA target config, which does not exist yet.
- `needs_review`/`pending_delivery` stay separately clickable pills even after the Processing-card merge (decision 2) — if a future admin workflow needs a "Needs Review only" or "Pending only" count *card*, that's an additive change to decision 2's mapping, not a reason to re-litigate the merge itself.
