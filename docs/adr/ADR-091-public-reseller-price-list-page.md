# ADR-091: Public Reseller Price List page — a sales/acquisition surface on `is_owned` storefronts, admin-selected tiers

> **Standing (2026-11-01):** In force; decisions 5 and 9 are revised by the 2026-11-01 addendum (Accepted, built, not released). Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Context:**

Founder wanted a public price-list page like competitor sites (`synnmlbb.com/price-list`, `topagentgames.com/my/services`) — prospective resellers see tiered wholesale top-up rates before approaching the platform to sign up. His own proposal: shown only on the primary storefront or an affiliate brand categorized as "owned brand"; a checkbox on each `reseller_tiers` row to opt it into the page; minimum 1, maximum 3 tiers shown; near-real-time pricing linked to price sync. He explicitly asked for this to be checked/improved from a code-maintainability angle before building, not taken as final.

Grilled over 3 rounds (`/mattpocock-skills:grilling`) plus a visual wireframe artifact reviewed before build. Codebase check up front found most of the plumbing already exists: `Affiliate.is_owned` (ADR-061 PR-A) is the exact "owned brand" concept; `ResellerCatalogService::listAvailable()` (ADR-077 PR-5) is already the cached, deduped, reseller-eligible package listing the Reseller API/Bot channels use; `reseller_tiers.sort_order` already exists for admin-table ordering. `reseller_tiers.markup_percent` is platform's own margin over `cost_price` (no second retail-markup layer like Affiliate has) — publishing it as a tier's price is a real margin-exposure decision, not a formality, though it matches how both reference competitor sites already operate.

**Decision:**

1. **Gating: automatic on every `Affiliate.is_owned = true` brand**, no separate per-brand opt-in toggle — `is_owned` already means "this is our own brand," a second toggle for the same distinction would be pure admin-surface overhead. Content is **platform-wide, identical on every `is_owned` brand** (`reseller_tiers` isn't an affiliate concept) — the brand only changes the page's skin (logo/theme), never its data.
2. **Tier selection: `reseller_tiers.show_on_price_list` (boolean), capped at 3 `true` rows at once**, enforced in `Store`/`UpdateResellerTierRequest` (`withValidator`, DB count check — not a DB constraint). Explicitly **not** "auto-show the N lowest-markup active tiers" — the founder's own real ladder has a 0%-markup "SSS" tier for special/negotiated resellers that must stay excludable regardless of how cheap it is; inclusion is always an admin choice. Display order reuses the **existing** `sort_order` column — no new rank/order field.
3. **Zero tiers marked `show_on_price_list` → the page and its footer link auto-hide**, no validation forcing at least 1 — same "empty array means off" contract `MembershipController::plans()` already established for its own kill switch (`GET /catalog/reseller-price-list` returns `{tiers: [], games: []}`), so `/price-list` calls Next's `notFound()` and `SiteFooter`/`sitemap.ts` skip the link, with no separate `enabled` flag to keep in sync.
4. **Price display: absolute price per tier column only — no computed "save X%" between tiers.** The founder was explicit: a clean percentage between two public prices is a number a viewer can screenshot and use to back out the tier-to-tier markup delta directly; tier names + naturally-lower numbers left-to-right already carry the upsell signal without handing over a computed comparison.
5. **Data scope: one page, client-side search/filter over the full list** — not a per-game picker, not server pagination. The reseller-eligible catalogue (hundreds of packages) is small enough to ship as one JSON payload and filter in the browser, matching how both reference competitor sites present their own price lists (land on the page, search, see it instantly).
6. **Pricing formula: `PricingService::calculateForAffiliate(cost_price, standard_selling_price, tier.markup_percent, 0.0)->sellingPrice`** — the exact same call `OrderPricingResolver::resolveResellerWallet()` uses at real order time, so a displayed price can never drift from what a reseller in that tier is actually charged. No separate formula, no rounding drift risk.
7. **Freshness: reuse `listAvailable()`'s existing 60s cache** for "which games/packages," compute the per-tier price arithmetic fresh on every request (cheap — a few hundred packages × ≤3 tiers, no DB query beyond one small `reseller_tiers` read and one `Game` name pluck). **No new cache key or invalidation choke point** — a second cache layer keyed on `reseller_tiers` state would need its own invalidation wired into `ResellerTierController`, for a computation cheap enough not to need caching at all. `ResellerTierController::store()`/`update()` do call `NextRevalidation::purge()` (the storefront's own Next Data Cache `catalog` tag, 30s TTL backstop either way) so a tier toggle reaches the live page promptly rather than waiting out the full backstop window.
8. **Tier label: reuse the internal admin tier `name` field directly as the public label** ("Tier SS", "Tier S", "Tier A") — no separate customer-facing display-name column. The founder's own examples used the admin names as-is.
9. **CTA: "Contact us" (WhatsApp), reusing the existing branding-driven contact resolution (`resolveWhatsappHref`)** — no new signup form or endpoint. Matches the current admin-invite-only reseller onboarding (ADR-074); a self-serve form would imply a signup flow that doesn't exist yet (see Consequence).
10. **SEO: a real `generateMetadata()` entry** (title + description, same lightweight per-page pattern `/about-us` and `/track-order` already use — not the admin-editable SEO Templates screen, which is game-PDP-specific) **and a conditional `sitemap.ts` entry**, both gated on the same "tiers non-empty" signal.

**Rationale:**

- Reusing `listAvailable()`, `PricingService::calculateForAffiliate()`, `sort_order`, and the `MembershipController::plans()` "empty means off" contract means this feature adds almost no new deep-module surface — it recombines four already-proven, already-tested seams rather than inventing parallel versions of any of them (`AGENTS.md`'s "deep modules, stable seams" principle in practice).
- A boolean + reused `sort_order` is simpler than a dedicated rank/priority column and still fully answers "which 3, in what order" — a new rank field would have solved a problem (stable ordering) that `sort_order` already solves.
- No second cache layer is the more solid choice, not just the simpler one: a cache keyed on `reseller_tiers` state left unwired to `ResellerTierController` would have been a real staleness bug waiting to happen the first time someone forgot the invalidation call existed.

**Consequence to track:**

- If self-serve reseller signup ever ships (ADR-085 candidate, not started), this page's CTA is the natural place to switch from "Contact us" to a real signup flow — revisit decision 9 then, not before.
- `reseller_tiers` gained its first field (`show_on_price_list`) that is genuinely public-facing rather than admin/billing-internal — any future `reseller_tiers` column should ask the same "does this leak to `/price-list`?" question decision 4 already settled for markup framing.
- The margin-exposure trade-off in decision 1/6 (a tier's public price is `cost_price × (1 + markup%)`, unlike Affiliate's portal which never shows platform's own markup) was a deliberate, eyes-open founder call, matching how both reference competitor sites already operate — not an oversight to "fix" later.

**Addendum, 2026-09-13 (founder feedback, live mobile testing):** two display-only overrides on top of decisions 2 and 3, neither a change to the underlying data contract:
- **Decision 2's column order is now rendered in reverse of `sort_order`** — `PublicResellerPriceListService::build()` orders `orderByDesc('sort_order')->orderByDesc('id')` instead of ascending, so the cheapest tier sits rightmost (a "price rises as you scroll left" reading) rather than leftmost. `sort_order` itself is untouched and still governs every other tier-ordering surface (Wallet tiers table, portal picker) ascending, as before — this is a display-order flip on this one page's output, not a reinterpretation of the field.
- **Decision 3's footer link is hidden** (`SiteFooter` no longer fetches/renders it) while the page itself stays fully live at `/price-list` — the "empty tiers = no page" auto-hide contract (`notFound()`, `sitemap.ts`) is unchanged, this only removes the on-site nav discovery path. Not gated on a new admin toggle; a straight code-level hide, reversible by restoring the removed block if the founder wants it back in nav.
- Also fixed the same session: the table's mobile scroll affordance — a 3rd tier column could clip flush against the bordered scrollport with zero visual cue more existed. `ResellerPriceListTable` now shows a "swipe to see all N tiers" hint below the table on narrow viewports whenever more than 2 tiers are shown.

### 2026-11-01 addendum: browse by game and region, an apply button, and a light "enabled" signal (revises decisions 5 and 9)

> **Status: Accepted, built 2026-11-01 (on `staging` once its PR merges, not released).** Design approved by the founder against a local mockup; grilled the same day (answers recorded below). Build status: [`prd.md` §15](../prd.md), item 154.

**Context:**

- Prospective resellers complained the page is hard to read. Prod today (2026-11-01): 674 package rows, 36 game entries, 3 tiers. Mobile Legends alone is 10 regions and about 360 rows, over half the page. Every row repeats the game name, and the only control is a search box.
- Decision 5 chose "one page, search only, not a per-game picker". With the catalogue at this size that no longer reads well; the competitor pages the founder named group by game.
- **The data has no usable grouping.** about 35 games; only three families span regions (Mobile Legends 10, Free Fire 6, Valorant 5), the rest stand alone. `games.category` is a genre (MOBA, Battle Royale, FPS), the wrong axis. `reseller_code` has no convention (`MLMY`, `FFG`, `PUBGG`, `RM`, `HSR`). Names are inconsistent ("Mobile legends Global", "Racing Master (SEA)"). Parsing any of them is the patchwork this addendum avoids.

**Decision:**

1. **Browse by game, then region** (revises decision 5). Game tiles with the game's image, then region pills for a multi-region family, then one table for the chosen region (5 to 83 rows). The first family and its first region are selected by default, so the page is never empty. State lives in the client: no `searchParams`, so the page stays cached, and the one fetch is unchanged. Nothing is paginated server-side.
2. **Search stays**, across every group: it hides the tiles and shows matches grouped by game. It starts at 2 characters and uses React's `useDeferredValue` (no debounce timer, no network call per keystroke: the data is already in the browser). A one-letter query matches about 545 rows and was measured at 11 ms on desktop; the deferral protects older phones.
3. **Grouping is two nullable display columns on `games`:** `family` (text, max 60) and `region_label` (text, max 40). Not a `game_families` table: three families do not justify a model, a migration and an admin screen, and the string columns can be promoted to a table later without losing anything. Rules: values are trimmed and single-spaced; families are matched case-insensitively; `region_label` is refused without a `family`; `(family, region_label)` is unique among games, so two "Malaysia" tabs cannot exist. A game with no family is its own group, named after the game; a family with no region label falls back to the game name. The admin sets both in `EditGameModal` beside Reseller Code, with an editable dropdown of the families that already exist (so "Mobile legends" cannot drift from "Mobile Legends"), and warns on a region without a family.
4. **Order and image are derived, not stored:** families ordered by the lowest `sort_order` among their members, regions by `sort_order`, the tile image is the first member's `image_url`. No new ordering or image column.
5. **Wire shape.** `tiers` unchanged (still reversed per the 2026-09-13 addendum), the flat `games` list replaced by `groups[] { family, image_url, games[] { name, region, packages[] { name, prices[] } } }`, and a new `apply_url`. The game name is sent once per game instead of once per row. The flat shape had one reader (the storefront, plus its tests); both change in the same PR. During the minutes between the backend deploy and the Vercel build, `/price-list` can answer not-found through `safeRead`'s fallback; nothing else reads `groups`.
6. **A light "enabled" signal (found in the trace).** The root layout (`app/layout.tsx`) and `sitemap.ts` both call `getResellerPriceList()` and parse all 674 rows through Zod, on every root-layout render, only to compute `tiers.length > 0` for the bottom nav. Adding images and regions would make that heavier on every storefront page. Decision: `GET /api/catalog/reseller-price-list?summary=1` returns `tiers` only (the service skips `listAvailable()` and the per-row pricing), the layout and sitemap use a small `getResellerPriceListEnabled()`, and only `/price-list` fetches the full list. Same endpoint, same 30-second Next cache and `catalog` tag purge, no new cache key (decision 7 holds).
7. **The call to action becomes the application** (revises decision 9). The WhatsApp button is replaced by "Apply to become a reseller", linking to `apply_url`: the backend builds it from `services.onboarding.url` (`ONBOARDING_URL`, already set on Forge for the applicant emails) plus `/apply`, so the storefront hardcodes no host and local dev works. The copy says accounts are approved by the team and the applicant gets an email. When "Public applications open" is off the button still shows and `/apply` explains the closure (the price list is cached; reading the switch there would add an invalidation path). `price-list/page.tsx` drops `resolveWhatsappHref`; the footer, the Joki page and `SiteConfigContext` still use it.
8. **Phone layout.** One swipeable row of game tiles and one of region pills (a half-visible tile is the cue; the first mockup's 4-column grid pushed the first price two screens down), each package as a card with the three tier prices side by side, the table's header sticky on desktop. Desktop keeps a wrapping tile grid and wrapping pills.

**Unchanged:** decision 1 (gating on `is_owned`), 2 and 3 (tier selection, empty means off), 4 (absolute prices only, no "save X%"), 6 (the price formula, so a displayed price still cannot drift from the charged one), 7 (no new cache layer), 8 (tier labels), 10 (page-level SEO, the sitemap entry). No price, cost or margin path is touched.

**Trace (2026-11-01):**

- **Readers of the endpoint:** `PublicResellerPriceListController` (via `StorefrontBrand::is_owned`), the storefront's `layout.tsx` (once per root layout render), `sitemap.ts`, `price-list/page.tsx`, `ResellerPriceListTable.tsx`, the backend test `PublicResellerPriceListControllerTest` and `RouteAccessTest`. No admin, portal, bot or docs-site reader.
- **Writers of `games`:** `GameController::store` and `update` (through `UpdateGameRequest`), `SupplierProductController` (creates a game from a supplier product) and `JokiCatalog`. The new columns are nullable, so none of the creators must set them and a new game simply lands as its own group.
- **Cache:** `GameController::update` already calls `forgetIndexCache()`, which clears `listAvailable()`'s 60-second key. `PublicResellerPriceListService` reads the game's `name`, `image_url` and the new columns from a fresh `Game` query, outside that cached listing, so an admin edit needs no new invalidation; the Next 30-second cache is the only delay.
- **SEO** is per game (`/order/{slug}`, `GameSeoController`, ADR-029/042), not per title, and stays so. A per-title page would be a new ADR and is the trigger to promote `family` into a `game_families` table.

**Consequence to track:**

- Mockup: the founder-approved design lives outside the repo; the build must be compared against it at 390px and desktop with a live screenshot before it is called done (root `AGENTS.md`, step 6).
- Production has no `family` yet: after the release the page shows every game as its own group until the founder fills the families (about 24 games, PRD item 154).
- A future `games` column that is public-facing should ask the same "does this leak to `/price-list`?" question as `reseller_tiers` (see the consequence list above).

**Grill answers (founder, 2026-11-01):** (1) no backfill migration: the founder fills Family and Region by hand in the admin, to learn the process; (2) the family and region names are the short ones in PRD item 154 ("Mobile Legends", "Free Fire", "Valorant", "Genshin Impact", "Honkai Star Rail", "Rainbow Six Mobile"; Genshin, HSR and Rainbow Six get region "Malaysia" so another region can be added later); (3) tile order is the games' own order, changed with Reorder Games on `/admin/games`, no code; (4) the few minutes in which `/price-list` can answer not-found between the backend deploy and the Vercel build are accepted, no dual-shape release.

**Built (2026-11-01), where it differs from or adds to the text above:**

- `UpdateGameRequest` normalises both fields (trim, single spaces, blank to null), reuses the spelling an existing game already has for the same family (ignoring case; a game's own family can still be re-cased), refuses a region without a family and a second game with the same `(family, region)`. Test: `Adr091GameFamilyTest` (14 tests) plus the updated `PublicResellerPriceListControllerTest`.
- The admin modal's "Price List Family" field is two inputs; the family input is a native `<input list>` with a `<datalist>` of the families already in use (no new component), and a region typed without a family shows a warning before saving.
- The table header sticks at `top-[70px]`, the measured height of the site header; if that header changes height, change it with it (comment in `PriceRows.tsx`).
- Checked in a browser against a throwaway backend seeded with the 674 real rows (not production): desktop and 390px, choosing, region pills, sticky header, search, no-match message, no horizontal overflow, the apply link, and the admin modal's prefill, suggestions and warning.
- Not measured: the CPU saved by the layout no longer parsing the full list (a conclusion from the code, as stated in decision 6).
