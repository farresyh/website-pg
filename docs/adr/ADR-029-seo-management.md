# ADR-029: SEO Management — reseller-scoped SEO settings, redirects, and per-game wiring (built 2026-08-22)

> **Standing (2026-10-09):** In force; decision 8 revised by ADR-120. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-21 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, companion to and sequenced immediately after `ADR-028`, before any code touched)

**Context:** `prd.md` §6.16 (SEO-1..7) is 100% ⬜ not started per §15, all MVP-priority except SEO-3/SEO-5 ("Important"). One piece already exists: `Game` (`app/Models/Game.php`) already carries `seo_title`/`seo_title_local`/`seo_description`/`seo_description_local`/`seo_keywords`/`seo_og_image` columns — schema-complete, but never wired into `EditGameModal` (§15's own "GAME-12/SEO fields still unbuilt" note). `ADR-028`'s own Consequence to track named two open questions for this ADR to resolve: whether `reseller_branding` also carries SEO defaults, and whether `Game.seo_*` needs any schema change.

**Decision:**

1. **Per-game SEO (SEO-4) stays exactly where it already is — `Game.seo_*` columns, wired into the existing `/admin/games` `EditGameModal` — not folded into any new reseller-scoped table.** This resolves `ADR-028`'s first open question: a product page's own SEO (a specific game's title/description/keywords) is about that *product*, not about which reseller happens to be selling it — a different axis entirely from SEO-2/3/5/6/7 below, which are about the *storefront itself*. Games are global per `ADR-013`'s own established model (no per-reseller `Game` rows), so per-game SEO staying global too is the consistent choice, not a new one.

2. **SEO-2/3/6/7 — new table `reseller_seo_settings`, 1:1 with `Reseller`, kept separate from `ADR-028`'s `reseller_branding` despite both being per-reseller.** Resolves `ADR-028`'s second open question: `reseller_branding` is "how the store presents itself to a human visitor" (name, contact, footer); this table is "how the store presents itself to a search engine or tracking script" — a genuinely different concern that happens to share the same 1:1-with-`Reseller` shape, matching this codebase's existing convention of a separate table per distinct concern rather than one growing model. Holds: default meta title/description/OG image (SEO-2, used as the storefront's fallback wherever a specific `Game.seo_*` field is empty); meta title/description template *patterns* per page type with placeholder substitution, e.g. `{game_name} Top Up — {store_name}` (SEO-3); typed pixel-ID columns `ga_measurement_id`, `fb_pixel_id`, `tiktok_pixel_id` (SEO-7); a generic `custom_head_script`/`custom_body_end_script` fallback pair for anything not covered by the three named integrations (SEO-6).

3. **Redirects (SEO-5) — new table `redirects`, reseller-scoped (`reseller_id` FK), `from_path`/`to_path`/`status_code` (301/302).** Consistent with every other table in this ADR and `ADR-028`: a redirect is a path on a specific storefront's URL space, and a Phase 2 reseller with their own domain would need their own redirect set, not a shared global one.

4. **SEO-1 (Overview dashboard) needs no new storage at all — a computed, read-only view aggregating existing data (`Game.seo_*` completeness, `redirects` count) into a coverage checklist, never a single weighted "score."** A bespoke scoring formula would be a vanity metric invented without real basis; a checklist ("12/20 games have an SEO title", "3 games missing an OG image") is directly actionable without needing one.

5. **Implementation approach — verified against this project's own installed Next.js 16 docs (`admin/node_modules/next/dist/docs/`), not assumed from training data, per `admin/AGENTS.md`'s own warning that this Next.js version can differ from training-data assumptions.** No SEO framework needed:
   - **Meta tags/OG (SEO-2/3/4):** Next.js App Router's native `generateMetadata()` — already sufficient; deliberately not adding `next-seo` (a Pages-Router-era package whose core purpose App Router's native API already covers, confirmed by reading the bundled docs directly rather than assumed).
   - **Google Analytics/Tag Manager (part of SEO-7):** `@next/third-parties/google`'s `<GoogleAnalytics gaId="G-XYZ">`/`<GoogleTagManager gtmId="GTM-XYZ">` components — an official Vercel-maintained package (confirmed present in this project's own bundled Next.js docs), not currently installed, a genuine new dependency worth adding rather than hand-rolling Google's own script-loading optimizations.
   - **Facebook Pixel/TikTok Pixel + the SEO-6 custom-script fallback:** `next/script` — already built into Next.js core, zero new dependency, no official or compelling third-party package exists for either platform since they're just a standard init snippet with a dynamic ID, which `next/script`'s own loading-strategy options already handle correctly.
   - **Redirects (SEO-5) execution:** a custom lookup against the `redirects` table (via `proxy.ts`/middleware or an equivalent storefront-side check) — no existing package fits a schema-specific, admin-editable, per-reseller redirect set; this is genuinely bespoke, not reinventing something that already exists.

6. **Access model: the Admin Panel edits these settings on behalf of a reseller — today always `Reseller::platformOwner()` — there is no reseller self-service portal (RES-1..6, Phase 2, not built).** Both this ADR's tables and `ADR-028`'s carry a `reseller_id` FK so the data model is ready, but the *editor* today is exactly the same admin who already manages Games/Packages/Vouchers for the whole platform, not a distinct reseller identity. Mirrors `ADR-013`'s own "same code path, more rows" philosophy: when Phase 2 eventually builds a real reseller self-service portal, it reuses these same tables and endpoints, scoped to the logged-in reseller's own `reseller_id` instead of full admin access — no schema change needed at that point, only a new UI surface and an auth-scoping layer.

7. **Sequencing: design-only, same as `ADR-028` — building either ADR is a future session's work, one item at a time, not authorized to start from this grilling session alone.**

**Rationale:** The one real insight this session turned up is decision 1's axis distinction — per-game SEO and per-storefront SEO look similar (both are "SEO settings") but vary along completely different dimensions (which product vs. which reseller), and conflating them into one table would have been the wrong shape the moment a second reseller or a second game both needed SEO data simultaneously. Decision 5's research (reading this project's own bundled Next.js docs rather than assuming) closes out a real, previously-open question — the founder asked directly whether an existing library could help — with a concrete, low-dependency answer: exactly one new package (`@next/third-parties`, official) is worth adding, everything else is already native to the Next.js version this project runs.

**Addendum, 2026-08-22 — the three deliberately-deferred items above resolved before build (quick follow-up round, same pattern as `ADR-025`'s own addendum), no scope changes to the 7 main decisions.**

8. **SEO-3's template placeholder syntax reuses `ADR-028` addendum decision 13's exact convention, not a new one invented for this ADR.** `{game_name}`/`{store_name}` tokens are substituted at storefront render time only (never at save time); any other brace sequence (a typo, an unrecognized token) is left verbatim, no error. One consistent templating rule across the whole app rather than two subtly different ones a future reader would have to keep straight.

9. **Redirects (decision 3) execute via Next.js's native `middleware.ts` — framework middleware, not a Vercel-specific product — checking each request's pathname against an in-memory cache of the `redirects` table, not a DB round-trip per request.** Chosen over a backend 404-fallback because this project's own deployment target (`ADR-020`) is a self-hosted droplet running `next start`, not Vercel's platform — `middleware.ts` runs identically there, it isn't an Edge-only or Vercel-only mechanism. The cache is populated from the storefront's own `getBranding()`-style backend fetch (`ADR-028` addendum precedent) and invalidated the same way `BrandingController::forgetCache()` already does on save — a `RedirectsController::forgetCache()` sibling, not a new invalidation pattern. A cache-miss (cold start, or the TTL just expired) costs one lookup; every other request in that window costs nothing beyond an in-memory array scan.

10. **UI placement: a new top-level admin nav item, "SEO"** (`/admin/seo`), not a fourth tab folded into `ADR-028`'s `/admin/settings`. Matches `prd.md`'s own §6.16/§6.17 split (SEO Management and Settings are two separate functional areas in the spec, not one) and keeps the Settings page from growing a fourth tab on top of its existing three plus the bulk-markup tool. Three sections on this one page: SEO Overview (decision 4's coverage checklist, read-only), Reseller SEO Settings (decision 2's `reseller_seo_settings` form — default meta/OG, template patterns, GA/FB/TikTok pixel IDs, custom scripts), Redirects (decision 3's table — add/edit/delete `from_path`/`to_path`/`status_code`). Per-game SEO (decision 1) stays exactly where decision 1 already put it — `EditGameModal` — this new page does not duplicate it.

**Consequence to track (addendum):** ~~`@next/third-parties`'s experimental status... still needs a fresh check at the actual build session~~ **done, see the main Consequence to track above.** ~~`RedirectsController::forgetCache()` (decision 9) needs the same discipline...~~ **Built as `SeoController::forgetCache()` (public controller, mirrors `BrandingController::forgetCache()` exactly), called from every admin write in `Admin\RedirectController`/`Admin\SeoScriptController`.
