# ADR-020: Production host — DigitalOcean Basic Droplet + Managed MySQL, Docker Compose, Cloudflare-fronted (Phase 1 built 2026-07-30 — deploy mechanism superseded by ADR-066)

> **Standing (2026-10-09):** Partly superseded by ADR-066 (Forge deploy, Vercel frontends). Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-07-29 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`). **Tier/placement decisions revised at the 2026-09-01 provisioning session — see the final addendum: frontends → Vercel (reverses decision 4), droplet 8→4 GiB (decision 1), Managed MySQL 2→1 GiB single-node (decision 2), each with a named upgrade trigger. The reliability core is unchanged.** **The deploy *mechanism* (decisions 4/5 + decision 9's image-pipeline/SSH half) is superseded by [ADR-066](./ADR-066-production-deploy-via-laravel-forge.md) — executed 2026-09-02, production is now LIVE on Laravel Forge (native PHP-FPM/nginx/Redis/Horizon), not Docker. Every reliability decision here — Managed MySQL off-box, backups, Cloud Firewall + key-only SSH + `fail2ban`, monitoring, the Cloudflare-fronting plan, the Vercel frontends, the 4 GiB/1 GiB tiers + upgrade triggers — is unchanged and carried forward verbatim by ADR-066.**

**Context:** Every prior ADR that touched production infrastructure (`ADR-015` decision #6, `ADR-016`, `ADR-019` decision #2) recorded the same genuine blocker: no production host had been chosen, so Redis/S3/queue-worker/log-shipping specifics would have been guesswork. This ADR resolves that blocker. The founder had already researched a concrete shape before this session — a single DigitalOcean Droplet running Laravel, both Next.js apps, MySQL, Redis, a queue worker, and a backup script, plus DigitalOcean Spaces for media and private MySQL backups — priced against DigitalOcean's own calculator (Basic Droplet, Regular CPU, 8 GiB/4 vCPU/160 GiB SSD/5,000 GiB transfer, $48/mo, with the "Enable backups" add-on checked, daily/7-30-day retention).

**One founder-stated priority governs every decision below, and reverses a default assumption several earlier ADRs made under a different constraint:** cost is explicitly *not* the optimization target. The founder's own words: money spent to keep the system from crashing, easy to maintain, and scalable for traffic that may exceed what's typical for a Malaysia-only top-up store — including a real plan to expand beyond Malaysia — is money the founder is willing to spend. This is the opposite starting position from, e.g., `ADR-001`'s "no second gateway is confirmed, building one now would be guessing" caution or `ADR-015`'s cost-conscious scoping — those were right for their own context (unconfirmed future need), but production infrastructure now has a confirmed, present need (a real host is being provisioned this session), so several sub-decisions below deliberately spend more than the founder's own initial research proposed, where a stronger reliability/scalability case existed.

**Decision (per sub-area, each grilled with the founder one at a time before being accepted):**

1. **Compute — one DigitalOcean Basic Droplet, 8 GiB RAM / 4 vCPU / 160 GiB SSD, Singapore region, with DigitalOcean's own Droplet Backups add-on enabled (daily, 7–30 day retention).** One droplet, one region, for now — a second droplet, a second region, and a DigitalOcean Load Balancer ($12/mo minimum) are **explicitly deferred, not provisioned speculatively**, despite the founder's stated appetite for spending on reliability. Rationale for deferring specifically this item, grilled and confirmed: the system has **zero production traffic today** (checkout is still sandbox-only per `prd.md` §14) — provisioning multi-region/load-balanced infrastructure now would be a different flavor of the same mistake `ADR-015`/`ADR-016` were built to avoid (designing against a shape with no real signal yet), not a cost-saving compromise. The trigger to revisit is concrete, not vague: sustained high CPU/RAM on this droplet, or a confirmed launch date for a second country. Droplet Backups (whole-disk snapshot) is deliberately **separate from, and complementary to**, the DB-level backup mechanism in Decision 2 — one recovers the whole box, the other recovers just the database from an independent, queryable source.
2. **Database — DigitalOcean Managed MySQL, not self-hosted on the droplet.** This reverses the founder's own initial research (which had MySQL living on the same droplet as everything else). Starter tier confirmed against DigitalOcean's own pricing page: 2 GiB RAM / 1 vCPU / 30–60 GiB storage, $30.45/mo, upgradeable to a standby node (automatic failover) once justified. **Rationale, grilled specifically against the founder's "don't fear cost" instruction:** `orders`, `ledger_entries`, `withdrawals`, and `vouchers` are the platform's money-critical tables (`backend/CLAUDE.md`'s own stated invariants). Self-hosted MySQL on the same droplet as the app means a droplet-level fault (OOM kill from the Next.js/PHP-FPM processes sharing the box, kernel panic, disk exhaustion) takes the database down with everything else, and recovery means restoring from the last `mysqldump` — losing every transaction between that dump and the crash. Managed MySQL's optional standby-node failover closes exactly this gap (automatic switch in seconds, not a restore-and-lose-data event), and DigitalOcean handles patching/point-in-time recovery instead of the founder. This is the single highest-value place to spend beyond the founder's own original research, given the explicit no-crash priority.
3. **Cache — Redis, self-hosted in a Docker container on the droplet, cache-only.** Redis is **not** used as the queue driver — the queue stays on the `database` driver (`ADR-014` decision #1's original choice), now backed by Managed MySQL. **This decision explicitly supersedes `ADR-014` decision #1's Redis deferral** (per this doc's own no-silent-rewrite convention — recorded as a new entry, not an edit to that one): Redis is being provisioned from day one of production, reversing "deferred until real traffic justifies it." What does *not* change is the reasoning for why self-hosted (not Managed Redis/Valkey, $15/mo+) is still correct here, even under a spend-for-reliability mandate: everything Redis holds in this system is regenerable cache (`Games`/`Packages`/`Payment Methods` listings, 60s TTL, per `ADR-014` decision #5) — a crash loses nothing that a fresh read from Managed MySQL can't immediately replace. Spending on managed HA for data that carries zero loss-of-data risk would be spending on the wrong thing. **Explicit revisit triggers** (so "self-hosted for now" doesn't quietly become "self-hosted forever" without anyone noticing the context changed): (a) the queue driver ever moves off `database` onto Redis — at that point Redis starts holding money-relevant, non-regenerable job state, changing this calculus entirely; (b) Redis downtime is observed to visibly degrade the customer-facing checkout path; (c) a second droplet/region (Decision 1's deferred trigger) needs a Redis instance shared across boxes, which self-hosted-per-droplet can't do.
4. **Containerization — Docker Compose, not a native LEMP-style install directly on the droplet's OS.** Chosen specifically because the founder's stated priority is ease of horizontal scaling and eventual multi-country expansion, not minimizing today's RAM footprint on one box — a reversal of this assistant's own initial lean toward native, revised once that priority was made explicit. This does **not** reopen `ADR-010` (Docker for MySQL-only, no full Sail stack) — that decision was scoped to *local development*, where Herd already worked and full containerization added no benefit; this decision is scoped to *production*, a materially different context (multi-box scaling, reproducible deploys, CI/CD image pipelines are real needs there that don't exist for one developer's local machine).
5. **Process supervision — Docker-native (`restart: unless-stopped`) plus Laravel's own `--max-jobs`/`--max-time` worker-recycling flags. No Supervisor.** Queue workers are split into separate named Docker Compose services by queue (e.g. `queue-worker-orders`, `queue-worker-pricesync`), not one worker consuming every queue — so a slow, non-urgent `SyncSupplierPricesJob` run can never head-of-line-block an urgent, money-touching `FulfillOrderJob`. **Rationale:** Supervisor's three real jobs — auto-restart on crash, N-way concurrent workers, and managing several distinct worker programs from one tool — are each already covered natively once Docker is the runtime (restart policy, `--scale`, and multiple Compose services, respectively). Supervisor is the correct, arguably only, choice on a bare VPS with no container runtime (which is why most Laravel deployment tutorials and Laravel Forge itself default to it) — but nesting Supervisor inside a container on top of Docker's own restart policy stacks two process managers solving the identical problem, for this codebase's actual (containerized) deployment shape.
6. **Load balancing / multi-region — deferred (see Decision 1), but the chosen shape is already positioned for it.** Docker images, Managed MySQL external to any one droplet, and DigitalOcean Spaces for all file storage mean the application layer holds no droplet-local state that would block adding a second droplet — the same "already positioned for it" discipline `ADR-014` decision #7 recorded for load balancing generally, now concretely true for this system: a second droplet/region is "add capacity," not "redesign for statelessness first."
7. **Network/security — DigitalOcean Cloud Firewall restricting inbound to 80/443/22 only.** MySQL is off-box entirely (Decision 2); Redis never needs a public port, only Docker's internal network. SSH is hardened to **key-only auth + `fail2ban`** — a non-standard SSH port was considered and rejected (grilled explicitly): it's security-through-obscurity, not real additional protection, and costs real operational friction (remembering a non-default port) for no measurable safety gain.
8. **Domain/DNS/SSL — DNS stays at Cloudflare (the founder's existing domain registrar), not migrated to DigitalOcean's DNS.** Cloudflare Proxy ("orange cloud") is enabled, giving free DDoS protection, edge CDN caching, and origin-IP concealment — the CDN caching in particular directly serves the founder's stated international-expansion plan, since Cloudflare's edge network serves static assets from a point of presence closer to a non-Malaysia customer than a single Singapore droplet ever could alone. SSL is terminated via a **Cloudflare Origin CA certificate** installed on the droplet's Nginx (15-year validity — no Let's Encrypt renewal cron needed at all, simpler than this assistant's original suggestion), Cloudflare's own SSL mode set to **Full (Strict)**. A DigitalOcean **Reserved IP** is attached to the droplet, and Cloudflare's DNS A record points at that Reserved IP, not the droplet's own ephemeral IP — a future droplet rebuild/resize only requires re-attaching the Reserved IP, never touching DNS.
9. **CI/CD — GitHub Actions, two phases, fully automated (no manual approval gate).** Confirmed by inspection, not assumed, before deciding: this repo has **zero CI/CD and zero E2E test infrastructure today** (`.github/` doesn't exist; no Playwright anywhere in `admin/`/`storefront/`).
   - **Phase 1 (build now, this session or the next):** backend fast test suite (sqlite) → backend concurrency suite (`phpunit.concurrency.xml`, against a MySQL service container inside the Actions runner itself, not the production Managed DB) → admin/storefront `tsc --noEmit` / `next build` / `eslint` → build three Docker images (backend, storefront, admin — queue workers reuse the backend image with a different command) → push to DigitalOcean Container Registry (Basic tier, $5/mo, 5 repos/5 GiB, confirmed sufficient) → SSH deploy (`docker compose pull && up -d`, then `php artisan migrate`) → a post-deploy `GET /api/health` check with automatic rollback to the previous image tag on failure. Deliberately **no manual approval click** — the safety net is the test stages themselves, which are already strong (396+ backend tests including the concurrency proofs on `Ledger`/`Voucher`/`OrderFulfillmentService`), not a human glancing at a button before deploying.
   - **Phase 2 (decision recorded now, build explicitly deferred, not abandoned — matching this doc's own established pattern, e.g. `ADR-017` decision #9):** Playwright E2E covering the golden paths — guest checkout → payment → order status; admin login → view order → Resend Delivery. Not required to gate the first production deploy (Phase 1's existing test gate is already strong), but tracked as the **immediate next priority** once this ADR itself is settled, given this is a money-moving system with currently zero UI-level regression coverage.
10. **Build sequencing — everything except the final SSH-deploy step can be built and proven before the droplet is purchased.** Dockerfiles, `docker-compose.yml`, and every GitHub Actions stage up through pushing images to the Container Registry depend on nothing that requires real infrastructure to exist yet — they can be built and validated now (a local Docker Compose stack, a CI-only MySQL service container). Only the SSH-deploy step needs a real target (droplet IP, SSH key). Building the rest now means the first real production deploy of a money-critical system is "run an already-proven pipeline against a new target," not "build and debug the pipeline for the first time under launch pressure."

**Rationale:** Every decision above traces back to the founder's single explicit governing priority for this ADR — reliability/no-crash and future scalability outrank minimizing spend — and each sub-decision was grilled individually against that priority rather than assumed to follow automatically from it (Decision 1's single-droplet-for-now and Decision 3's self-hosted-Redis are both deliberate *exceptions* to "spend more," grilled and justified on their own terms: no signal yet, and zero data-loss risk, respectively — spending for reliability everywhere indiscriminately would itself be a mistake, just the opposite one from under-spending).

**Consequence to track:** this ADR records *design intent only* — nothing here is built, purchased, or provisioned yet (matching `ADR-015`/`ADR-016`/`ADR-017`/`ADR-018`'s own established practice). Update `prd.md` §14/§15 as each piece of Phase 1 actually ships. Specifically still open, tracked here so none of it is silently lost:

**Addendum — Phase 1 shipped (Dockerfiles, `docker-compose.prod.yml`, CI), 2026-07-30 (same session, later, per ADR-021 item 3):** everything decision #10 said was buildable without the droplet is now built and locally proven — the SSH-deploy job and the git-remote creation are the only pieces still deferred (see below), exactly as scoped.

**Prerequisite found and fixed first, before any Docker/CI file:** this session's own queue-worker-sizing research (Laravel's official docs, cross-checked against the 8 GiB/4 vCPU droplet spec) confirmed decision #5's `queue-worker-orders`/`queue-worker-pricesync` split was still just a name on paper — no job actually declared a queue. Fixed via `$this->onQueue(...)` in each job's constructor (`FulfillOrderJob`/`ResendOrderDeliveryJob` → `orders`, `SyncSupplierPricesJob` → `price-sync`) — **not** a redeclared `public $queue` property, which PHP rejects as an incompatible redefinition of `Illuminate\Bus\Queueable`'s own property of the same name (a real, reproducible fatal error hit and fixed live, not assumed). Recommended sizing: 2 queues, 1 worker process each for now (zero real traffic today per ADR-021's own framing) — scale `queue-worker-orders` via `docker compose up -d --scale queue-worker-orders=2` once real order volume justifies it, no code change needed to do that.

**Built and locally verified** (`docker compose -f docker-compose.prod.yml build` + `up`, all before any droplet exists):
- `backend/Dockerfile` — multi-stage (composer deps → vite asset build for the unrelated default `welcome.blade.php` scaffold page → `php-fpm` runtime), reused unmodified by both queue-worker services (only the container `command:` differs).
- `admin/Dockerfile`, `storefront/Dockerfile` — standard Next.js `output: "standalone"` multi-stage build (added to both `next.config.ts` files — neither set this before). `NEXT_PUBLIC_API_URL` (the one env var either app reads) is passed as a Docker build arg, not just an env_file — confirmed this matters: Next.js inlines `NEXT_PUBLIC_*` into the client bundle at build time, a runtime-only env var would silently not apply.
- `backend/docker/nginx/default.conf` + a `nginx` compose service — standard two-container `nginx` + `php-fpm` split (fastcgi_pass over the compose network), not bundled into one image, keeping one-process-per-container. Host-level Nginx (Cloudflare Origin CA/SSL, decision #8) stays out of scope — it needs the real droplet's filesystem to configure, reverse-proxies to this stack's one published port.
- `docker-compose.prod.yml` (repo root) — 7 services (`nginx`, `php-fpm`, `queue-worker-orders`, `queue-worker-price-sync`, `admin`, `storefront`, `redis`), no `mysql`/Spaces service (both off-box per decisions #2/nothing self-hosted). Distinct from, and doesn't touch, `backend/docker-compose.yml` (ADR-010's own local-only file).
- `.github/workflows/ci.yml` — 4 real jobs (backend sqlite suite, backend concurrency suite against a `mysql:8.4` GitHub Actions service container, `admin`/`storefront` tsc+build+eslint) plus a `build-and-push` job gated on all four, pushing to DigitalOcean Container Registry. **Confirmed, not glossed over:** this last job needs `DIGITALOCEAN_ACCESS_TOKEN` (repo secret) and an actual DO Container Registry resource, neither provisioned — a real requirement beyond decision #10's "only the SSH-deploy step needs a real target." The SSH-deploy job itself is deliberately not written at all yet (a disabled stub is worse than no job).
- `predis/predis` added to `backend/composer.json` — decision #3 provisions Redis for cache, and there was no PHP Redis client installed at all until now (checked directly, not assumed).

**Two real bugs found and fixed only by actually building and running the stack locally, not by reading the Dockerfile and assuming it works:**
1. `mbstring`'s configure step failed on `php:8.3(/8.4)-fpm-alpine` for a missing `oniguruma-dev` Alpine package — added.
2. **PHP version mismatch:** `composer.json` declares `"php": "^8.3"`, but `composer.lock` — generated against this machine's actual local PHP 8.4.23 — locked at least one dependency to a floor of `>=8.4.1`. `php:8.3-fpm-alpine` failed outright at Composer's own `platform_check.php`. Switched the Dockerfile (and the CI workflow's `setup-php` step) to `8.4`, matching what's actually required. `composer.json`'s own declared constraint is left as-is (not edited this pass, out of this plan's scope) — worth a future one-line correction so it stops claiming `^8.3` when the lock file already requires `^8.4`.
3. **Stale local `bootstrap/cache/{packages,services}.php`** (Laravel's compiled provider-discovery cache, generated locally with dev dependencies present) were being copied into the image by the final stage's `COPY . .`, clobbering whatever `composer dump-autoload --no-dev` had freshly regenerated one stage earlier — surfaced as `Class "Laravel\Pail\PailServiceProvider" not found` (a dev-only package correctly absent from the `--no-dev` image, but still referenced by the stale cache). Fixed by adding `bootstrap/cache/*.php` to `backend/.dockerignore` — the image now regenerates this cache itself from its own (no-dev) `vendor/`, never inherits the host's.

After both fixes: `GET /api/health` through the `nginx`→`php-fpm` stack returned a real, correctly-structured `503 {"status":"degraded","checks":{"database":false,"queue":false}}` — not a crash. This is the *expected* result for this local check (no real `.env`/DB is wired into this verification, by design — production secrets aren't baked into the image or committed), and it directly confirms the mechanism CI's future SSH-deploy rollback step depends on actually works: a broken/unconfigured deploy reports `503`, not a silent `200`.

**Consequence to track:**
- `composer.json`'s `"php": "^8.3"` constraint is stale (should say `^8.4`) — a small, safe follow-up, not done this pass to keep this plan's scope to infra files only.
- Still genuinely not done: the SSH-deploy CI job, the actual droplet/Managed MySQL/Spaces/Reserved IP/Cloudflare Origin cert, the DO Container Registry + its access-token secret, and git-remote creation (ADR-021 item 4) — none of Phase 1's local build/proof work substitutes for any of these.
- **Local-dev regression caught and fixed same session, not left for a future session to discover as a "stuck job" mystery:** now that all 3 jobs declare a real queue name (`orders`/`price-sync`, not the implicit `default`), `composer run dev`'s own `queue:listen` call (previously no `--queue=` flag, which per `WorkCommand::getQueue()`'s own source falls back to the connection's configured default queue) would have silently stopped processing every one of them. Fixed in the same pass: `backend/composer.json`'s `dev` script now runs `queue:listen --queue=orders,price-sync ...`. `docs/prd.md`'s own "known gotchas" note (queue-worker-not-running) updated to match — any other manual `queue:work`/`queue:listen` invocation (e.g. alongside Herd) must include the same `--queue=orders,price-sync` or it processes nothing.

**Investigation notes (reference only, not part of the Decision above) — capacity analysis against real order history, 2026-08-14 (discussion only, nothing provisioned/changed).** Founder supplied `docs/orders.csv` — the current live topup site's real order export, 28,848 rows, 2025-12-28 to 2026-08-14 (230 days) — to sanity-check whether Decision 1's droplet (8 GiB/4 vCPU) and Decision 2's Managed MySQL tier (2 GiB/1 vCPU) can actually carry this business's real transaction shape, not just a guessed one. Findings, derived by direct analysis of the CSV (not assumed):

- **Volume:** ~125 orders/day average (~4,008/month over full months), confirming the founder's own recollection of ~RM100k–200k/month (paid-only monthly revenue ranged RM66.5k–244k across Jan–Jul 2026, avg RM136.6k, avg order value RM43.78).
- **Burst is very light relative to the chosen compute:** busiest single minute ever recorded was 9 orders; busiest 5-minute window was 28 orders (~0.09 orders/sec); the highest number of orders sharing the exact same second, across the entire 230-day history, was 3. This is nowhere near saturating a single php-fpm worker pool on a 4 vCPU box, even accounting for `CheckoutController::store()`'s synchronous payment-gateway call (fulfillment itself is already queued, per Decision on ADR-014).
- **Linear extrapolation to 5x/10x/20x today's volume** (RM1–2 million/month lands around x7–x15 of the current ~RM136.6k/month baseline) still projects peak concurrency in the tens of orders/minute, single digits/sec sustained — comfortably within Decision 1's droplet, with the explicit caveat that this is a **linear scaling of today's organic pattern**, not a model of sharper, campaign-driven bursts a real 10–20x growth push might actually produce; a genuine flash-sale-shaped spike could cluster far more tightly than this extrapolation assumes.
- **Managed MySQL connection ceiling checked directly against DigitalOcean's own published limits** (`docs.digitalocean.com/products/databases/mysql/details/limits/`): Decision 2's chosen 2 GiB/1 vCPU tier allows **150 backend connections** (1 GiB → 75, 4 GiB → 400, 8 GiB → 800). Estimated worst-case concurrent connection demand at 10–20x volume (~30–50 php-fpm workers plus the `orders`/`price-sync` queue workers plus the 15-minute reconciliation commands) sits well under that ceiling — connection *count* is not expected to be the constraint even at 20x.
- **Genuinely still unverified, not resolvable from documentation or the CSV alone — needs a real load test once the droplet/DB actually exist:** sustained write-throughput/IOPS under real concurrent load, actual droplet↔Managed-MySQL network latency, and `pm.max_children`/queue-worker-count tuning (none of this is configured yet — Phase 1 only proved the images build and run, not real production concurrency).
- **One risk this analysis surfaced is independent of order volume entirely, present even at 1x:** Decision 1's single-droplet/single-region choice remains this ADR's own explicitly named revisit trigger (sustained high CPU/RAM, or a confirmed second-country launch) — a serious growth push toward the RM1–2m/month range is a reasonable point to re-open that trigger deliberately, not because compute runs out, but because a single box stays a single point of failure regardless of how much headroom it has.

**Consequence to track:** no infrastructure decision changed by this analysis — Decision 1 (droplet size) and Decision 2 (Managed MySQL tier) both hold up against real historical data through the 10–20x range discussed. Revisit this addendum at the start of the actual deployment session (Decision 10's "build sequencing" — droplet/Managed MySQL not yet purchased) to decide, with real numbers from a load test, whether either tier needs adjusting before go-live, and to weigh whether the redundancy trigger above is worth acting on proactively given the founder's stated growth target.

**Investigation notes (reference only, not part of the Decision above) — availability-under-load and detection/alerting discussion, 2026-08-14 (same day, discussion only, nothing built/changed).** Founder asked two related questions ahead of the deployment session: (1) under heavy request load, can the site actually go down; (2) as a non-technical ("vibe coder") operator, how would a problem or an attack attempt even be noticed. Both answered against what's actually decided/built today, not assumed:

1. **Availability under load — real, accepted risk, not a new gap.** What already protects: Cloudflare Proxy in front of the droplet (Decision 8, absorbs volumetric DDoS at the edge before it reaches the box), per-route rate limiting (`throttle:10,1` checkout, `5,1` login, `120,1` on both webhook routes — `ADR-014`/foundation-security.md §5), the Cloud Firewall's minimal 80/443/22 surface (Decision 7), and the per-supplier circuit breaker (keeps a down Gamevion from cascading into the whole delivery queue). What does **not** protect, by deliberate, already-recorded design: Decision 1's single-droplet/single-region choice — no load balancer, no auto-scaling. Organic growth, including the 10–20x range in the capacity addendum above, stays within the droplet's headroom. A genuine sustained L7 flood or an extreme, attack-shaped spike is a different failure mode from organic burst and is **not** fully covered by today's design — this is Decision 1's own named revisit trigger, not a newly discovered hole.
2. **Detection/alerting for a non-technical operator — a real, currently-open gap.** `ADR-014` decision #6 explicitly declined external error-tracking (Sentry etc., cost/data-residency, before real production traffic existed) — that reasoning was sound at the time but was never revisited against an actual imminent deployment. Today: `GET /api/health` exists but nothing polls it; admin login attempts are logged (`prd.md`'s 2026-07-29 entry) but nothing alerts on a suspicious pattern; the blacklist/velocity guard blocks known-bad actors automatically but is reactive (an admin must add the entry after noticing); admin MFA remains descoped (`foundation-security.md` §1). A founder without deep security background has, today, no push notification of either an outage or a suspicious pattern — only a manual SSH-and-read-the-log path.

**Consequence to track — concrete, low-effort items to decide (not silently re-defer) at the actual deployment session, none requiring new application code:**
- An external uptime monitor (e.g. UptimeRobot/Better Uptime free tier) polling `GET /api/health`, notifying by email/SMS/WhatsApp on failure — closes the "nobody is watching health-check" gap directly.
- DigitalOcean's built-in droplet monitoring + alert policies (CPU/RAM/disk thresholds) — free, a checkbox at provisioning time, not built yet.
- Review Cloudflare's dashboard security settings once the domain is live (manual "Under Attack Mode" toggle, managed WAF rules on the free tier) — not yet configured, since there's no live domain to configure it against.
- **Re-open `ADR-014` decision #6's Sentry/error-tracking deferral deliberately**, now that a real deployment is imminent rather than hypothetical — its original justification ("before real production traffic exists") is the exact condition about to change, and this ADR's own governing priority (Decision statement: "money spent to keep the system from crashing... is money the founder is willing to spend") plausibly extends to observability, not just compute/DB tier.
- Reconsider admin MFA (`foundation-security.md` §1, AUTH-7) given it's the single-factor weak point on the two account types (withdrawal approval, blacklist management) with the most damage potential if compromised — still a founder call to make, not decided here.

1. **Frontends (`storefront/`, `admin/`, `reseller/`) move to Vercel — this reverses decision 4's "admin + storefront as Docker containers on the droplet".** The founder already has a paid Vercel Pro team (`JW Brothers`) with large unused headroom (checked live: $4.22 of $20 included credit used, one small project); three low-traffic Next.js 16 apps at this volume are expected to stay within the included credit → ~$0 incremental. Reasoning this is a *reliability* move, not just a cost one: 3 SSR Next.js processes competing with `php-fpm` + Horizon workers for RAM on one box is exactly the OOM-a-money-critical-process risk decision 5's queue-split was written to avoid, one layer up; `next build` (1–2 GiB spikes ×3) on the box that serves checkout traffic is worse still. Vercel isolates all three, builds them off-box, and gives zero-downtime deploys and edge CDN for the storefront (the same international-reach goal decision 8 cited Cloudflare for). **Consequence:** `storefront/Dockerfile`, `admin/Dockerfile`, their `output: "standalone"` config, the `admin`/`storefront` services in `docker-compose.prod.yml`, and the `admin`/`storefront` tsc/build/eslint + image-build steps in `.github/workflows/ci.yml` are now dead weight — remove them in the deploy-wiring pass (not this session). `reseller/` needs a Vercel project too, never got a Dockerfile. The Vercel projects can be transferred to a dedicated team later if billing separation is wanted (kedairuncitsoloz is a separate business) — no lock-in.

2. **Droplet drops from 8 GiB / 4 vCPU to 4 GiB / 2 vCPU** ($48→$28). With the three Next.js apps gone (decision 1 of this addendum), the droplet runs only `nginx` + `php-fpm` + `redis` + Horizon/queue workers. Measured-estimate against the 2026-08-14 capacity addendum's *real* numbers (busiest minute ever = 9 orders, busiest single second = 3, over 230 days): `pm.max_children≈30` (~1.8 GiB) + Horizon/workers (~0.6 GiB) + Redis `maxmemory 512mb` + OS ≈ 3–4 GiB peak. `throttle:10,1` on checkout + Cloudflare rate-limiting cap the real rate hitting PHP. **DO droplet resize is a single reboot (~1 min), no data loss (DB is off-box)** — so this is genuinely "start small, resize live", not a bet. **Upgrade trigger (named, not vague):** sustained droplet RAM > 70% or CPU > 60% in DO monitoring, OR a campaign / second-country launch is confirmed → resize to 8 GiB before it's needed.

3. **Managed MySQL drops from the 2 GiB Starter to the 1 GiB single-node tier** ($30.45→~$15). Decision 2's *load-bearing* choice — Managed, not self-hosted on the droplet, so a droplet fault can't take the DB with it and DO handles patching + 7-day point-in-time recovery — is **kept**. Only the tier changes. The 2026-08-14 capacity addendum validated 2 GiB against the *10–20× growth* connection ceiling (150 conns), not launch: at launch volume real concurrent connection demand is ~5–15, far under the 1 GiB tier's 75-connection ceiling, and a ~28k-row `orders` table fits the 1 GiB buffer pool comfortably for a long time. **Accepted trade-off, explicit:** 1 GiB single-node has **no automatic failover** — a node hardware fault means minutes-to-~1h of downtime while DO replaces it, though PITR means **no transactions are lost** (restore to seconds-before-fault; the cost is outage duration, not data). **Two independent upgrade triggers, named:** (a) DB connection count sustained > 50, or DB RAM > 75%, or storage > 70% → resize the tier (a few-minutes cutover window, done at a low-traffic hour); (b) revenue reaches a level worth protecting against the failover-gap outage → **add a standby node** (automatic sub-second failover, roughly doubles the DB line) — this is the higher-value upgrade and closes the exact gap decision 2's reliability argument was partly about. Both are checked in DO monitoring, not left to be noticed by accident.

**Net monthly cost:** ~$59 DO (droplet $28 + droplet backups ~$6 + Managed MySQL 1 GiB ~$15 + Spaces $5 + Container Registry Basic $5; Reserved IP free) + ~$0 incremental Vercel. Down from ADR-020-as-written's ~$95–105.

**The full real-client-IP checklist** (grep'd this session, not just the one Digiflazz webhook ADR-069's own consequence-to-track already flagged):
- `bootstrap/app.php` currently sets `trustProxies(at: '*')` — trusts **any** proxy, unconditionally. This is the actual fix point: once Cloudflare fronts every request, this should narrow to Cloudflare's published IP ranges and read the real visitor IP the way Cloudflare's edge presents it (`CF-Connecting-IP`) — configuring Laravel's trusted-proxy header mapping correctly here fixes every consumer below **transparently**, rather than patching each call site to read `CF-Connecting-IP` by hand.
- **Consumers of `$request->ip()` found**, each silently wrong today (or post-cutover, without the fix) in a different way:
  - `AppServiceProvider.php` (2 rate-limiter definitions, IP-keyed fallback when no bearer token) — post-cutover-without-the-fix, every unauthenticated caller behind Cloudflare would collapse onto one shared rate-limit bucket (Cloudflare's edge IP), defeating the limit entirely — a real abuse-surface regression, not cosmetic.
  - `CheckoutController::assertNotBlacklisted()` (FRAUD-4's per-IP velocity guard, `CheckoutVelocityGuard`) — same collapse risk: a real carding-probe attacker becomes indistinguishable from every other guest checkout, silently neutering the one fraud signal this guard exists for.
  - `AuthController` / `AffiliateAuthController` login audit logs, `AffiliateImpersonationController`'s impersonation audit log — all record the wrong (Cloudflare edge) IP post-cutover without the fix, degrading a security audit trail's evidentiary value.
  - `DigiflazzWebhookController` — already known (ADR-069), already soft/log-only, lowest severity of the five.
- **Fix is one place, not five**: correct `trustProxies`/header-mapping configuration (Cloudflare's IP ranges as trusted proxies, `CF-Connecting-IP` recognized as the real-IP header) makes `$request->ip()` return the correct value everywhere above with no per-call-site change — confirm this at build time against the installed Laravel version's `TrustProxies` API rather than assuming the exact method names.
- Also folds in decision 8's already-known steps: move DNS to Cloudflare, swap the droplet's Let's Encrypt cert for Cloudflare Origin CA, enable Proxy + Full (Strict) SSL mode.
- **Verification domain**: the founder has one real domain available to test the eventual custom-hostname flow end-to-end (ADR-060 decision 3/4) once this cutover and ADR-060's own build are both done — not needed for the cutover itself, but reserved for that later live-verification step.

**Phase 2 — `trustProxies` fix + origin hardening. ALL DONE + VERIFIED 2026-09-06** (same browser session; PR #112 → staging, release PR #113 → `main`, Forge auto-deploy; then Forge + Cloudflare dashboard steps with the founder doing the mutating clicks — the auto-mode classifier blocks Claude from editing prod nginx / prod DNS / prod SSL directly, and the credential rules keep Claude out of the Origin CA private-key copy-paste).

- **`trustProxies` code (PR #112):** `bootstrap/app.php` `trustProxies(at: '*')` → the explicit **Cloudflare published ranges** (`https://www.cloudflare.com/ips/`, 15 IPv4 + 7 IPv6 CIDRs, plus loopback), with the standard `X-Forwarded-*` header set. Confirmed against Laravel 13's `Middleware::trustProxies(array|string|null $at, ?int $headers)` API. **Not** a `CF-Connecting-IP` custom header: Cloudflare always appends the true connecting IP as the right-most `X-Forwarded-For` entry, so Symfony's right-to-left walk past trusted proxies already lands on the real client, and a spoofed client-sent `X-Forwarded-For` sits to the *left* of Cloudflare's appended value and is never reached. One change, all five `$request->ip()` consumers fixed. **Inert while `api` is grey**, so shipped ahead of the proxy flip. `tests/Feature/Http/TrustedProxiesTest.php` (3). **Verified in prod after the flip:** `php artisan tinker` booting the HTTP kernel with `REMOTE_ADDR` = a Cloudflare IP + `X-Forwarded-For: 203.0.113.99` → `$request->ip()` returned `203.0.113.99`.
- **openwa webhook nginx block:** `location = /api/webhooks/openwa` carried `allow 127.0.0.1; allow 137.184.250.200; allow 10.15.0.2; deny all;` (ADR-075 decision 4). Once `api` is Cloudflare-proxied every request arrives from a Cloudflare edge IP, so that block would 403 OpenWA's own webhook. The `allow`/`deny` lines were **deleted** — the endpoint is now HMAC-only, the same posture CHIP and Digiflazz already carry (founder confirmed). Post-edit it returns 401 to an unsigned request (was 403), i.e. it now reaches Laravel.
- **`api.pekangame.space` flipped to proxied (orange)** — the three Vercel frontends stay grey / Vercel-direct. `api` resolves to Cloudflare edge IPs; `api /up` returns `200` with `server: cloudflare`.
- **Origin CA certificate** (`api.` + `*.pekangame.space`, RSA 2048, 15-year) created in Cloudflare, installed on the droplet via **Forge → Domains → Certificates → "Existing certificate"**, activated (replaces the Let's Encrypt cert — no more 90-day HTTP-01 renewal to worry about now that `:80` is behind Cloudflare). Origin now presents `issuer=CloudFlare Origin SSL Certificate Authority`, valid to **2041-09-02**.
- **SSL/TLS encryption mode → Full (Strict).** (The Configure page needs its own **Save** button — selecting the radio alone does not persist.)
- **Authenticated Origin Pulls → Global toggle ON** (Cloudflare presents its shared `origin-pull.cloudflare.net` client cert on every origin pull). The matching CA — `https://developers.cloudflare.com/ssl/static/authenticated_origin_pull_ca.pem` (`CN=origin-pull.cloudflare.net`, valid to **2029-11-01** — a ~3-year rotation Cloudflare announces ahead of) — was pulled onto the droplet at `/home/forge/api.pekangame.space/cloudflare-aop-ca.pem` via a Forge command. **nginx workers run as user `forge`** on this box (`ps -o user= -C nginx`), so anything under `/home/forge/api.pekangame.space/` is nginx-readable — no permission dance needed.
- **nginx `site.conf` (Forge Monaco editor)** gained, right after `ssl_dhparam`:

  ```
  ssl_client_certificate /home/forge/api.pekangame.space/cloudflare-aop-ca.pem;
  ssl_verify_client on;
  ```
  → the origin now **rejects any TLS connection that does not present Cloudflare's client cert**. A direct `curl -k https://137.184.250.200/up -H 'Host: api.pekangame.space'` (and the same against the base droplet IP `157.245.203.250`) fails the handshake (`000`). **The droplet can no longer be reached bypassing Cloudflare's edge — ADR-020 decision 8 is now satisfied in full.**

**Free security hardening applied the same session** (SSL/TLS → Edge Certificates, zone-wide but only bites the one proxied hostname `api`): **Always Use HTTPS** on (verified: `http://api…` → one 301 → `https`, no loop — safe because the mode is Full (Strict), so Cloudflare→origin is always HTTPS and the edge redirect happens before the origin's own `:80`→`:443` redirect); **Minimum TLS Version → 1.2** (verified: a TLS 1.1 handshake now fails, 1.2 connects); **TLS 1.3** and **Automatic HTTPS Rewrites** were already on. **HSTS deliberately skipped** — low value on an API-only host (server-to-server callers ignore it; the browser-facing frontends are on Vercel, which already sends `Strict-Transport-Security: max-age=63072000`), and its "hard to undo" commitment isn't worth it here; revisit when the storefront moves behind Cloudflare for ADR-060.
