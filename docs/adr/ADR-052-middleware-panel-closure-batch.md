# ADR-052: Middleware Panel closure batch — MUI-7 merged into Validators, MUI-1 as a thin `/middleware` landing page, MUI-4 dropped

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-28 (grilled via `/mattpocock-skills:grilling`, four rounds, before any code touched)

**Context:** `docs/prd.md` §15's Middleware Panel row listed three remaining real gaps after ADR-051 (Request Logs) closed MID-10/11/MUI-9: **MUI-7** (standalone Validate Player tool), **MUI-4** (Games full catalog+export inside `/middleware`), and **MUI-1** (unified Dashboard: supplier cards, quick actions, recent API calls, circuit-breaker state). The founder no longer clearly remembered why these three were originally scoped as separate screens and asked for a genuine build-or-drop grilling rather than taking the backlog wording at face value.

Investigation before grilling found each item already overlaps existing, shipped screens:
- **MUI-7** ("Validate Player: game selector, player ID input, validation result, 'not supported for this game' state") overlaps the per-validator raw connectivity test already on `/middleware/validators` (MUI-5) — but that test calls `PlayerValidatorRegistry::resolve($key)->validate()` directly, bypassing the game→region-mapping resolution a real customer's checkout hits. The real customer-facing logic already exists and is already called from two other places: `storefront/src/lib/checkout.ts` (the wizard) and `admin/src/lib/orders.ts`'s `validatePlayerForResend()` (ORD-7 resend flow) — both hit the same public, no-auth `POST /api/games/{game}/validate-player` (`PlayerValidationController::store`).
- **MUI-4** ("Games: full game catalog with edit and export") overlaps `/admin/games` (catalog+edit, GAME-1..5/7, already built) and `/middleware/product-manager` (raw supplier catalog staging/promote flow) — no concrete export use-case (accounting, handoff, audit) was ever recorded, and reproducing an entire catalog+edit screen a second time inside `/middleware` just to add an unspecified export button has no clear justification.
- **MUI-1** ("Dashboard: supplier status cards, quick actions, recent API calls, circuit-breaker state") overlaps `DashboardService::health()` (ADR-045's Admin Dashboard System Health section — already renders per-supplier `name`/`balance`/`circuit_state` from `CircuitBreaker::state()`), `/middleware/request-logs` (ADR-051 — the "recent API calls" feed), and `/middleware/suppliers` (ADR-046 — the "quick actions": refresh balance, activate/deactivate). ADR-051 decision 10 had already flagged `supplier_request_logs` as MUI-1's anticipated future data source. `admin/src/app/middleware/page.tsx` itself already existed as a stale placeholder (`TODO: MUI-1 ... Placeholder until the Adapter layer exists` — the Adapter layer has been built since ADR-006).

**Decision:**

1. **MUI-7: merged onto `/middleware/validators`, not a standalone screen.** A new "Validate Player (by Game)" panel (`ValidateByGamePanel.tsx`) sits below the existing Validators list, reusing `validatePlayerForResend()` (widened to surface `country_code`/`redirect_game`, both already returned by the backend but previously untyped on this narrower caller) — zero new backend. The founder accepted the one real side-effect this reuse carries: `PlayerValidationController::store` writes a real `player_validations` row on every call, and `CheckoutController::assertPlayerIdIsValidated()` gates checkout purely on `game_id`+`player_id`+`server_id`+`status=valid` within a rolling window (default 30 min) — **not** session-bound (a deliberate, already-accepted design per the 2026-07-27 audit). An admin's test call therefore pre-clears checkout for that exact combo for the window, identical in kind to what any guest calling the same public endpoint could already do — not a new attack surface, so no `is_admin_test` flag or separate non-persisting endpoint was built for it.
2. **MUI-4: dropped entirely.** No screen, no export button, anywhere. `/admin/games` and `/middleware/product-manager` already cover the real workflow (promote → manage); no concrete demand for a duplicate view or an export was ever established.
3. **MUI-1: built as a thin, manual-refresh landing page at `/middleware`** (replacing the stale placeholder), not a new data source:
   - Suppliers section: reuses `getDashboardHealth()` (the exact endpoint Admin Dashboard's System Health already calls), rendering only `suppliers` (name/balance/circuit_state) — `stuck_orders`/`pending_payments` are intentionally omitted as out of this screen's scope.
   - Quick actions: a single "Manage Suppliers →" link to `/middleware/suppliers`, no inline mutation — action logic stays owned by that one screen.
   - Recent API calls: last 5 rows from `listRequestLogs(token, { per_page: 5 })` (the `RequestLogFilters` type gained an optional `per_page`, mirroring a parameter the backend controller already accepted but the admin client never declared) + a "View all →" link to `/middleware/request-logs`.
   - Manual "Refresh" button, no auto-poll — this is a glance-and-leave page, not a monitoring surface someone sits on the way Admin Dashboard's own 60s-polling System Health is.
   - No shared component extracted with Admin Dashboard's System Health section — the two screens' scopes differ (order-metrics vs. supplier-only) and the founder agreed sharing would be premature abstraction for a two-consumer, small-each case.

**Rationale:** Decision 1 is the load-bearing call — it gets MUI-7's real requirement (simulate what a customer actually experiences, not just poke a validator's provider) without adding a second screen or any backend, by recognizing the exact resolution logic already exists and is already called from two other places in the codebase. Decision 2 avoids building a screen and a feature (export) that nothing in the system or the founder's own memory could justify — the honest answer to "what's this for" was "not sure," which is a drop, not a build. Decision 3 keeps MUI-1 to what's actually missing (a `/middleware`-scoped at-a-glance view) rather than re-deriving data three other screens already serve correctly.

**Consequence to track:** if a future feature needs `player_validations` rows to exclude admin-originated test calls (e.g., a fraud/analytics feature starts reading that table), decision 1's accepted side-effect should be revisited then, not preemptively engineered around now. If MUI-1's landing page later grows real scope-specific data needs beyond the three reused sources, evaluate a dedicated backend view at that point rather than stretching `DashboardService::health()` to serve two different screens' evolving needs.
