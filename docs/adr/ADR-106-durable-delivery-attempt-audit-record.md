# ADR-106: Durable delivery-attempt audit record — every fulfillment attempt gets its own immutable row, not just resends

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — grilled (`/mattpocock-skills:grilling`) 2026-09-17, same session and same order (`PG-KWKBUHNDMKQT`/order 15) as ADR-105, at the founder's explicit request to grill it immediately rather than defer, so the investigation's context wouldn't be lost. **Built 2026-09-18, merged to `staging`** (PR #237, bundled with ADR-107, after ADR-107) — every decision built exactly as accepted, no revisions. See the build addendum at the end of this entry.

**Context:** `order_resend_attempts` (ADR-017 decision #4, "record every attempt, not just the latest") only ever gets a row from one of its two write sites — `OrderResendService::resend()`, called on every admin-triggered resend. `OrderFulfillmentService::fulfill()` has exactly one other caller, `FulfillOrderJob::handle()` (the real first attempt, dispatched once the payment webhook confirms `Paid`), and that path writes no row at all — explicitly documented as a no-op case in `OrderFulfillmentService::resolvePendingResendAttempt()`'s own docblock. The admin's "Initial Delivery" row in `DeliveryLogsTable.tsx` is therefore synthesized live from `Order.supplier_response`/`supplier_product_ref`/`delivery_status` — single mutable columns that get overwritten by every later resend. That's accurate for an order that's never been resent, but the moment it has, the true initial attempt's SKU, response JSON, and outcome are permanently gone — confirmed live on order 15: the real initial attempt used `PUBGG_60_PG2`, but the admin UI's "Initial Delivery" row shows `PG1` because that's what the PG1 resend left sitting in the mutable columns. The 2026-09-15 bugfix (`docs/build-log.md`) already stopped this row from *lying* (it used to show a hardcoded `failed` label under a genuinely-`Sukses` response) by falling back to an honest `outcome="unknown"`/hidden-JSON placeholder once any resend exists — but the underlying gap, no durable row for the first attempt, was explicitly deferred there pending "its own ADR + grill" (`docs/prd.md` §16 item 15).

A third gap in the same family, found while grilling this one: `markDeliveredManually()` (ADR-026 decision 4a — an admin manually confirms delivery after cross-referencing a supplier's own dashboard for a `needs_review` order) *also* overwrites `Order.supplier_response`/`delivery_status` directly, exactly like `fulfill()` does, but is a third code path entirely (not `fulfill()`, no `order_resend_attempts` row today). If this fires after a prior resend, it becomes the new latest mutable-state overwrite — the durable log this ADR builds would otherwise show initial+resend history ending in a dangling `pending`/`failed` row with no record of how the order actually reached `Delivered`.

**Decision:**

1. **Non-combo only, for now.** Combo orders' `order_delivery_legs` table has the structurally identical symptom (`status`/`supplier_reference`/`failure_reason` are current-state columns with no attempt history of their own), but zero live incidents exist to fix (ADR-103's own finding: production has exactly one combo order ever, both legs delivered clean, neither ever sat ambiguous), and `OrderResendService::assertSameGamePackage()` already blocks combo orders from the package-swap resend path entirely (ADR-094 decision 10). Deferred, matching the same non-combo-first split ADR-094/102/103 already established — revisit once real combo volume exists.

2. **Reuse the existing `order_resend_attempts` table/`OrderResendAttempt` model — no rename, no new table.** Add a new `attempt_type` enum column (`initial` / `resend` / `manual_confirm`), backfilled to `'resend'` for the 7 rows that already exist (every one of them genuinely is a resend). A rename to something like `order_delivery_attempts` would be more accurate but touches ADR-017/094/102/103's code, comments, tests, and the frontend's `OrderResendAttempt` TS type for zero functional gain — this repo's own `AGENTS.md` header already sets the precedent for keeping a technically-stale name over pure-accuracy churn (the repo dir/git remote/DB name still read `kedairuncitsoloz`/`topup-website` "by deliberate choice... churn with no user-visible benefit"). A second table was also rejected: `resolvePendingResendAttempt()`'s "find the latest pending attempt for this order" query would otherwise need to `UNION` two tables for no real benefit — it stays a single, entirely type-agnostic query (`where order_id = ? and outcome = 'pending'`) that keeps working unchanged once `initial`/`manual_confirm` rows exist in the same table alongside `resend` ones.

3. **The initial-attempt row is written from inside `OrderFulfillmentService::fulfill()` itself, not its caller.** `fulfill()` already re-reads and locks the Order at the top of its transaction — it checks whether `$locked->delivery_status` was `DeliveryStatus::NotStarted` *before* this call advances it, and if so, writes an `attempt_type=initial` row in the same transaction as the rest of the attempt (so it only ever commits alongside a real outcome, never orphaned by a mid-flight exception — `FulfillOrderJob`'s own `$tries=3` retry can safely re-run `fulfill()` without risking a double row, since a connection failure that throws before the transaction's outcome branches run writes nothing at all). This keeps the audit trail inside the deep module that owns delivery state (`AGENTS.md`'s "Deep modules, stable seams" — `OrderFulfillmentService` is one of the three named seams) rather than something every future caller has to remember to do separately; `fulfill(Order $order)`'s own signature is untouched. `markDeliveredManually()` gets the matching treatment — one new call writing an `attempt_type=manual_confirm` row (package_id/cost_price_sen off the order as it stands, outcome `success`, the same synthetic `supplier_response` payload it already builds, `note`/`triggered_by` from its own existing parameters) — closing the third gap found above and narrowing Gap D's remaining scope down to just the two genuinely different event types (Issue Voucher, wallet refund), which stay parked.

4. **`price_diff_sen` for an `initial`/`manual_confirm` row is `null`, not `0`** — matching the *meaning* the frontend already gives a `null` value for the synthesized initial row today ("no comparison was made"), which is different from a real `0` diff a resend-to-the-same-package would produce ("a comparison was made and found no difference"). `cost_price_sen`/`standard_selling_price_sen` are simply the order's own values at that moment (for `initial`, this literally is the checkout snapshot — no live reconciliation happens on a first attempt by definition).

5. **`DeliveryLogsTable` (and whatever backend endpoint feeds it) switches its "Initial Delivery" row to read the real `attempt_type=initial` row once one exists for that order** — dropping the current live-synthesis entirely for any order that has one. For an order created before this ships (no `initial` row exists, and never will — the true data is already unrecoverably overwritten), the existing 2026-09-15 honest-fallback behavior (`outcome="unknown"`, hidden JSON) is kept exactly as-is; **no backfill is attempted**, since there is nothing left to backfill it from. The switch is a presence check ("does an `initial`-type row exist for this order?"), not a ship-date/`created_at` cutoff, so it behaves correctly regardless of when a given order happens to be viewed.

6. **Ships as its own PR, sequenced after ADR-105 but not blocked on it merging first** — ADR-105 is the money-critical, ledger-affecting fix and takes priority; ADR-106 is an audit-trail correctness fix with no financial-figure impact, so it doesn't need to wait for ADR-105's review/merge, just its own branch off `staging`.

**Rationale:** Same underlying lesson as ADR-105 — resend/manual-confirm code across this order lifecycle has repeatedly treated single mutable "current state" columns on `Order` as if they were also a durable history, when they were only ever designed to answer "what is the delivery state *right now*." The fix in both ADRs is the same shape: stop asking a mutable column to also serve as an immutable log, and instead give every attempt (however it's triggered) its own row in a table built for exactly that. Doing this from inside `fulfill()`'s own transaction, rather than at each call site, means the guarantee holds for every future caller without relying on anyone remembering to add a write call.

**Consequence to track:**

- Once this ships, verify the very first order that gets both a real `initial` row AND a later resend renders its full history correctly end-to-end in `DeliveryLogsTable` (SKU, outcome, and JSON all present and correct for both rows) — the kind of live re-check ADR-104's own build already demonstrated is worth doing over trusting the code reading alone.
- `resolvePendingResendAttempt()`'s type-agnostic query was verified, not just assumed, to keep working once `initial` rows exist — but add an explicit test case for "an initial attempt lands on Digiflazz `Pending`, then a webhook resolves it" alongside the existing resend-Pending test, since this is a genuinely new code path (the initial call has never written a `pending`-outcome row before).
- Combo-leg attempt durability (decision 1's deferral) should be revisited together with any future combo-volume-driven work, not on its own — likely the same session that finally gives `order_delivery_legs` real usage data worth designing against.
- Gap D's remaining scope (Issue Voucher, wallet refund not appearing in the admin's delivery/activity log) is now narrower than originally scoped in ADR-105's own Consequence-to-track — re-word that backlog item to exclude `markDeliveredManually()`, which this ADR covers.

**Addendum, 2026-09-21 — closes decision 1's own "non-combo only for now" deferral, plus its cousin gap on plain orders.** A founder-requested combo-lifecycle audit (real reseller volume ramping up — the same trigger as ADR-094's same-day reliability addendum) confirmed decision 1's deferred symptom was still live: `order_delivery_legs`' mutable `status`/`failure_reason`/`supplier_reference` columns still get silently overwritten on every leg attempt, with no durable row of their own. A second, previously-unnoticed gap surfaced in the same audit: `OrderController::retryDelivery()`'s backend route has no `is_combo` guard at all, and dispatches the bare `FulfillOrderJob` directly — so a PLAIN (non-combo) order retried through any of that job's 6 dispatch sites (the CHIP webhook, checkout, reseller placement, both reconciliation commands, `retryDelivery()` itself) hit the identical silent gap `fulfill()`'s own `$wasNotStarted`-gated write never covered for a retry, either. Grilled (`/mattpocock-skills:grilling`, 2 rounds, 8 questions) before any code.

1. **Reuse this same table for a combo leg's own attempt history — a nullable `order_delivery_leg_id` FK, no new table.** Directly extends decision 2's own "one table, discriminator column" precedent rather than contradicting it — a candidate parallel `order_delivery_leg_attempts` table was considered and rejected for exactly that reason. `order_id` stays populated on every row (a leg belongs to an order); `order_delivery_leg_id` is null for an order-level row, set for a leg-scoped one. `package_id` on a leg row is the leg's own component package (the order's own `package_id` is the combo SKU itself, meaningless per-leg); `standard_selling_price_sen` reads the leg's own frozen `selling_price_sen` (ADR-107 decision 1); `cost_price_sen` reads the component's LIVE cost (no frozen snapshot exists for it, same reason `resolveComboOutcome()`'s own profit reconciliation reads it live). Bonus, not the deciding factor: `Order::resendAttempts()` already eager-loads this table in the admin API response, so a leg row surfaces there with zero new endpoint.

2. **`attempt_type=retry` is new; both `initial` and `retry` are now written for EVERY attempt, not gated to "only if this is genuinely the first."** Widens decision 3's own `$wasNotStarted`-gated write (which only ever fired for `initial`, silently skipping every retry) to always write, discriminating `initial` vs `retry` off the same flag. Applies to both the leg-scoped write (a new `recordLegAttempt()`, called from all 4 of `attemptLeg()`'s write sites — Pending/Failure/Success inside its transaction, plus the Throwable-catch fallback that writes to a separate, already-committed transaction) and the plain order-level write (`recordInitialAttemptIfFirst()` renamed `recordFulfillmentAttempt()`, same 3 call sites unchanged). Confirmed live during the audit, not assumed: `ReconcilePendingDeliveriesCommand::retryStuckProcessing()` genuinely re-dispatches an order stuck at `Processing` — a real, already-running system-triggered retry path with this exact gap for combo and plain orders alike.

3. **`triggered_by`/`note` threaded end-to-end from `retryDelivery()` through `FulfillOrderJob` to the write.** `FulfillOrderJob`'s constructor gains two new nullable params (`?string $triggeredBy = null, ?string $note = null`) — every one of its 6 dispatch sites keeps its null defaults except `OrderController::retryDelivery()`, which now passes `$request->user()->name` and `override_reason` (this action's only free-text field, since it has no separate `note` input like `resend()` does). A system-triggered retry is therefore distinguishable from an admin-clicked one by `triggered_by` alone, with no separate boolean needed.

4. **`override_reason` now persists into the row's `note` column — retrofitted onto `OrderResendService::resend()` too, not just the new retry rows.** It used to only ever reach `Log::warning()` (found while implementing decision 3) — the exact reason an admin decided to accept a loss and force a resend/retry, previously unqueryable outside a log line. Falls back only when no separate `note` was given (`$note ?: $overrideReason`); a real `note` is never clobbered. Deliberately a small, explicit retrofit rather than leaving `resend()`'s and the new retry rows' conventions inconsistent for the same field.

5. **Leg-level `price_diff_sen` cost-drift reconciliation is explicitly out of scope — a future decision, not this one's to make.** This addendum closes a missing-audit-trail gap; a leg's component package drifting price between attempts is ADR-107's own domain (which already reconciles `platform_profit` as a money-conservation residual at final resolution). Conflating the two would have widened this addendum's blast radius for no requested benefit.

6. **Admin-facing "Leg History" UI is deferred, not committed here.** The data is durable and queryable the moment this ships (via `OrderDeliveryLeg::attempts()` / `Order::resendAttempts()`), but `ComboLegBreakdown.tsx` keeps showing live per-leg state only for now — building a history view is its own, separately-scoped follow-up so this addendum's diff stays backend-and-data-model only.

**Rationale:** Same lesson as this ADR's own original decision 2/3 — a mutable "current state" column was never designed to double as a durable log, and the fix is always the same shape (give every attempt its own row, written from inside the service layer that owns the transition, not each call site). Reusing this table rather than forking a parallel one for the leg case keeps that lesson from fragmenting into two separately-evolving audit trails with the same purpose.

**Build addendum, 2026-09-21.** Built exactly as accepted. One real bug found and fixed mid-build, not anticipated by the grill: `OrderResendService::resend()` calls `fulfill()` internally *after* already writing its own richer `attempt_type=resend` row (package swap, live-cost reconciliation) — decision 2's "write unconditionally" would have silently double-booked every single resend with a spurious extra `retry` row. Fixed with an explicit `bool $recordAttempt = true` parameter on `fulfill()` (`resend()` passes `false`) rather than trying to infer "did the caller already write one" implicitly from context. A second, smaller gap surfaced from the same review: a combo leg that goes `Pending` (Digiflazz async) and is later resolved via `finalizePendingDeliveryLeg()` (webhook/poll) needed its own leg-scoped twin of `resolvePendingResendAttempt()` — added as `resolvePendingLegAttempt()` — so a leg's `pending`-outcome attempt row self-corrects to `success`/`failed` once the real answer arrives, instead of staying stuck at `pending` forever. 12 new/revised tests across 4 files. Full backend suite **2202/2202 green**, concurrency suite **17/17 green** (real MySQL), Pint clean on every file actually touched. Full detail: `docs/build-log.md`'s matching entry.
