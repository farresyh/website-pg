# ADR-040: Gamevion sandbox integration — investigation saga, `telp` normalization, `callback_url` fix (2026-07-25 – 2026-08-14)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Resolved — investigation and fixes spanning 2026-07-25 through 2026-08-14. Split out from ADR-006's addenda chain (2026-08-27 docs refactor) for readability — see ADR-006's cross-reference.

**Context:** ADR-006 established the Supplier Adapter pattern; `GamevionAdapter` was the one real implementation that needed to be proven against Gamevion's actual sandbox and production environments before the platform's first real checkout→payment→fulfillment chain could be trusted. This entry is the resulting investigation trail — a chronological record of every sandbox/production issue found and the concrete fix each one produced.

**Decision:** Two adapter-level code fixes shipped as a direct result of this investigation:
1. `GamevionAdapter::normalizePhone()` now strips every non-digit character before sending `telp` — Gamevion's own validator rejects a leading `+` despite counting only digits toward its 9–13 digit rule.
2. `SupplierOrderRequest`'s `callback_url` is now always included in the request body (`'callback_url' => $request->callbackUrl ?? ''`) in `GamevionAdapter::createOrder()` — Gamevion's real API requires the key present even when empty, and silently returned a generic `500 Server error` when it was absent, which is why every real order sent before this fix failed with that same generic error.

**Rationale / investigation trail (chronological, moved verbatim from ADR-006's original addenda):**

**Addendum — first real end-to-end order + two live findings, 2026-07-25 (same session as the payment `customer` fix):** ran the platform's first-ever real checkout → payment → webhook → Gamevion fulfillment chain for a real order (MLBB Malaysia, "13 + 1 Diamonds", real User ID/Server ID supplied by the founder), Xendit in real sandbox mode, Gamevion with `GAMEVION_SANDBOX=true`. Found and fixed one real adapter bug, and isolated (but did not fix — not ours to fix) one real Gamevion-side sandbox limitation:
1. **[Fixed] `GamevionAdapter`'s `telp` field rejects a leading `+`.** Gamevion's own error — `"telp field must be between 9 and 13 digits"` — was returned for `"+60123456789"`, which *is* 11 digits; their validator fails entirely on the non-digit `+` character rather than counting digits only. `GamevionAdapter::normalizePhone()` now strips every non-digit character before sending `telp`, matching ADAPT-4's existing principle (the Adapter absorbs a supplier's specific format quirks, business logic never needs to know). Confirmed fixed live: same order retried post-fix produced no `telp` error at all.
2. **[Isolated, not ours to fix] Gamevion's sandbox `/api/order` returns a generic `{"error":true,"code":500,"message":"Server error"}` for any real, valid `product_code` — while the exact same request against Gamevion's real docs example values (`referenceNumber` formatted `GV-...`, a placeholder `product_code`) correctly returns `422` "product code invalid".** Ruled out, methodically, before concluding this: not `telp` format (fixed and confirmed working), not `referenceNumber` format (`GV-` prefix vs. our own `REF-` prefix made no difference), not product-specific (both a Free Fire item and an MLBB item — two different products — hit the identical `500`). **Conclusively isolated by switching the same adapter to `sandbox: false` (production) with the same real product code and request shape**: production returned a clean `400 Insufficient balance` (the account's real production balance is confirmed `0`, so this is the correct, expected response, not a lucky success) — proving the request itself is well-formed and Gamevion's production order-processing pipeline handles it correctly. The sandbox-mode failure is therefore Gamevion's own sandbox environment, not our adapter or request shape. **Action:** report this to Gamevion support with the diagnostic evidence above (fake product → clean `422`; real product → `500` in sandbox only, `400` in production) — not a code task for this codebase.

**Consequence to track:** the platform's checkout→payment→fulfillment chain is now proven correct end-to-end for the payment half (real `201` from Xendit, real webhook processed, `payment_status` correctly reaches `paid`). The delivery half is blocked purely on Gamevion's sandbox environment being unable to complete a real order right now — re-attempt once Gamevion support resolves it, or accept `GAMEVION_SANDBOX=false` for real fulfillment testing once the account has real balance (not recommended casually, since that spends real money and delivers to a real player account).

**Addendum — no sandbox `product_code` exists that can successfully order, 2026-07-25 (follow-up same day):** re-verified the sandbox `500` above is still live today, and closed out the obvious next question — "is there a sandbox-specific product code that avoids it?" Checked directly against the local copy of Gamevion's OAS spec (`gamevion-api.json`, v1.0.10): `/api/order`'s `product_code` schema has no relationship to `/api/product`'s `sandbox` body flag — they're two independent mechanisms that only *look* connected. Confirmed live with raw request/response evidence:
1. `POST /api/product` with `{"sandbox": true}` returns `{"error":false,"code":200,"message":"Products Simulation (Sandbox)","data":[{"sandbox_code":"234","sandbox_serviceName":"mlbb5","sandbox_category":"Mobile Legends","sandbox_price":"1000.00","sandbox_status":"active"}]}` — Gamevion's own `message` field literally calls this "Simulation," and it's a single hardcoded entry, not a real catalog.
2. Feeding that `sandbox_code` (`234`) into `POST /api/order` as `product_code` (with the founder-supplied test IDs, `data: "51049607|2005"`) returns a clean `{"error":true,"code":422,"message":"The selected product code is invalid."}` — Gamevion's order endpoint validates `product_code` against the **real production catalog**, not the sandbox-simulation list, so a `sandbox_code` value is never valid there.
3. Re-tested a real production code (`GV572`, "13 + 1 Diamonds," the same MLBB item from the addendum above) under `X-ENVIRONMENT: sandbox` with the same test IDs — reproduced the identical `{"error":true,"code":500,"message":"Server error"}`, confirming the bug is still present, not a one-off.

**Net conclusion: there is currently no `product_code` — sandbox-simulation or real — that can complete a successful order through Gamevion's sandbox mode.** Simulation codes are rejected as invalid (`422`); real codes hit Gamevion's server bug (`500`). This doesn't change the action from the addendum above (report to Gamevion support; the `422`/`500`/`400` evidence trail across sandbox and production is the diagnostic package to send them).

**Open question surfaced, not yet investigated:** Gamevion has no player-validation endpoint (ADR-005) — player/server ID correctness is only checked implicitly, inside order processing itself. Every real-product order attempt so far has been stopped earlier (by the sandbox `500` here, or by `400 Insufficient balance` in production) before reaching that implicit check, so it's still unconfirmed whether a given `playerId`/`serverId` pair (e.g. the founder-supplied `51049607`/`2005`) is actually valid from Gamevion's side. Tracked for a follow-up session — needs its own investigation into what "player ID validation" can mean with no dedicated endpoint (e.g. whether topping up production balance and letting a real order run is the only way to observe it).

**Addendum, 2026-07-27 — the same sandbox-simulation catalog also corrupts Price Sync's Deactivation Detection, not just order creation:** while founder-testing the freshly-shipped Price Sync Center (ADR-016) for real against `kedairuncit-backend.test` (`GAMEVION_SANDBOX=true`), a real "Sync All Prices Now" run's Stage 1 catalog fetch returned exactly the one hardcoded simulation product already documented above (`external_ref: 234`, `mlbb5`, `"Products Simulation (Sandbox)"`) — confirmed live via `SupplierProduct::orderBy('last_synced_at','desc')->first()`. This addendum previously only connected that limitation to order creation (`POST /api/order` rejecting or 500ing on any real `product_code`); nobody had connected it to ADR-015's Deactivation Detection until this session. The mechanism: since the sandbox catalog never contains any real `supplier_package_ref`, every real promoted `Package` looks "vanished from the latest sync" to `PackagePriceSyncService`, which treats that identically to an explicit supplier deactivation (this ADR's own decision #3 discipline, working exactly as designed — the bug is Gamevion's sandbox data, not this codebase's logic). Confirmed this happened for real: 3 packages (100 Diamonds, 210 Diamonds, 13 + 1 Diamonds) were auto-deactivated in that run, `deactivated_at` matching the run's `finished_at` to the second — manually reactivated immediately once the root cause was confirmed false, rather than routed through the normal Pending Reactivation review (that queue exists for genuine ambiguity; this case had none).

**Consequence to track:** do not trigger a real Price Sync run while `GAMEVION_SANDBOX=true` — it will falsely deactivate every real promoted Package, every time, for as long as this sandbox limitation stands. Price Sync itself has no sandbox-awareness and none is scoped — the practical mitigation today is operational (don't run it in sandbox mode), not a code fix.

**Addendum, 2026-07-29 — the founder's first deliberate real end-to-end purchase-workflow test (Xendit test-mode + `GAMEVION_SANDBOX=false`, grilled and planned via `/mattpocock-skills:grilling` before running — see the checkout-idempotency addendum above for that planning session) reached all the way to a real `POST /api/order` call against Gamevion **production**, and hit a new, previously-unseen failure mode there too — not the sandbox-only bug this ADR already tracks.** Full setup: real storefront checkout (`http://localhost:3001`), a Cloudflare quick tunnel exposing the local backend's webhook endpoint to the real internet for the first time ever in this project (previous sessions only ever simulated the webhook), real Xendit test-mode payment completed through Xendit's own mock-bank redirect flow. Two real orders reached Gamevion production:

1. First order (`KRS-01KYPBXV4YNP3V66NDE5X09BKW`, `GV572` "13 + 1 Diamonds"): `payment_status` correctly reached `paid` via a **real webhook delivered over the real network** (not simulated) — the payment half of the pipeline is now proven end-to-end for the first time. Delivery failed with a real, meaningful Gamevion response: `{"error_code":"404","error_message":"Phone number required"}` — the storefront's checkout form marks `customer_phone` optional, but Gamevion's real order endpoint requires it. A genuine, previously-unknown gap (not yet fixed — tracked as a follow-up, see `prd.md` §14's newest NEXT SESSION pointer).
2. Second order (`KRS-01KYPCA72S2MHH9W4XNX2NBHBB`, same product, phone number supplied this time): `payment_status` reached `paid` again (2/2 real webhook deliveries succeeded). Delivery failed again, this time with `{"error_code":"500","error_message":"Server error"}` — Gamevion's own generic server-error shape, but from **production**, not sandbox.

**Isolated methodically before concluding this is Gamevion's own production-side issue, not a code regression:** ran two direct diagnostic `POST /api/order` calls straight against the real Gamevion production API (bypassing the storefront/checkout entirely), each with a fresh, never-used `referenceNumber` (ruling out ADR-006's own duplicate-reference mechanism) and a different `product_code` each time (`GV572` again, then `GV733` "10 + 1 Diamonds" — ruling out a single-product bug):

```
POST /api/order {"product_code":"GV572","referenceNumber":"REF-DIAG-...","data":"51049607|2005","telp":"01118884011"}
→ HTTP 200, body: {"error":true,"code":500,"message":"Server error"}

POST /api/order {"product_code":"GV733","referenceNumber":"REF-DIAG2-...","data":"51049607|2005","telp":"01118884011"}
→ HTTP 200, body: {"error":true,"code":500,"message":"Server error"}
```

Both diagnostic calls reproduced the identical generic 500 — confirming this isn't product-specific, isn't the duplicate-reference `409` case, and isn't a code-side request-shape problem (the exact same shape worked correctly in this ADR's own 2026-07-25 addendum, which got a clean `400 Insufficient balance` from production back then). `check-balance` on the same account/credentials still succeeds normally (real balance confirmed, RM5.00) — so auth/connectivity is fine; only `/api/order` itself is affected, right now, in production. Founder drafted a support message to Gamevion with this exact request/response evidence, same diagnostic-package discipline this ADR's addendum above already established for the sandbox bug.

**Consequence to track:** the purchase workflow is now proven correct end-to-end on our side — checkout, payment, real webhook delivery, and reaching Gamevion production with a well-formed request are all confirmed working. The one remaining unconfirmed piece (an actual successful delivery, diamonds really credited) is blocked purely on Gamevion's production API's own current state, not on anything in this codebase. Do not re-attempt a real production order as a way to "test" this further until Gamevion support responds — the diagnostic evidence is already conclusive. Separately, unrelated to Gamevion's own issue: `customer_phone` should probably become a required checkout field (not nullable) given finding #1 above — not yet decided or built, flagged for a future session.

**Resolved, same day — root cause was ours, not Gamevion's: `callback_url` was silently missing from every real order request this codebase has ever sent.** Gamevion support replied fast (same-day) and, instead of finding anything in their own logs, pointed out their own `curl` example always includes `callback_url` (empty string when there's no real callback) — ours omitted the key entirely. Root cause, once pointed at it: `App\Services\Supplier\SupplierOrderRequest::$callbackUrl` defaults to `null` and **nothing in this codebase has ever set it to anything else** — `GamevionAdapter::createOrder()`'s own `array_filter(..., fn ($value) => $value !== null)` then silently dropped the key from the JSON body whenever it was null, which was always. Gamevion's real API apparently requires the key present (even empty) and fails the whole request with a generic `{"error":true,"code":500,"message":"Server error"}` when it's absent — explaining both the 500 itself and why their support found no matching entry in whatever log they checked: a request missing a required field this fundamentally likely never reaches their real order-processing/logging layer at all.

**Fix:** `'callback_url' => $request->callbackUrl ?? ''` — the key is now always present in the request body, matching Gamevion's own documented shape exactly. One line, `GamevionAdapter::createOrder()` only. All 17 existing `GamevionAdapterTest` cases still pass unchanged (none asserted on `callback_url`'s presence/absence).

**Verified live, twice, after the fix:** (1) a raw diagnostic `POST /api/order` (bypassing this codebase's own checkout/fulfillment path entirely) returned a clean `{"error":false,"code":200,"message":"Order Created",...}` — real money spent (RM0.61, "10 + 1 Diamonds"), real delivery attempted, then auto-refunded by Gamevion itself since the diagnostic call used a Malaysia-region player ID against a Global-region product code (`GV733`) — a genuine region mismatch, not a bug, and further proof the fix works (Gamevion's own business logic correctly caught and reversed it). (2) The real stuck order from this ADR's own live-test addendum above (`KRS-01KYPCA72S2MHH9W4XNX2NBHBB`, correct region this time — `GV572`, MLBB Malaysia) was resent via the real `/admin/orders` → **Resend Delivery** UI (`ResendOrderDeliveryJob`, the real production code path, not a diagnostic script) and came back `delivery_status: delivered`, `supplier_ref: GV-RAPI-AF12EF29DBEE`, with both ledger entries (`platform_profit`/`reseller_profit`, 14 sen/0 sen) correctly written. **This closes the loop this ADR's own live-test addendum left open — the full purchase pipeline (checkout → payment → real webhook → Gamevion production delivery → ledger) is now proven correct end-to-end, for real, not simulated, for the first time in this project.**

**Addendum, 2026-08-13/14 (new session) — Gamevion's sandbox `/api/order` `500` bug (this ADR's 2026-07-25 addendum, "no `product_code` — sandbox-simulation or real — that can complete a successful order through Gamevion's sandbox mode") appears fixed on Gamevion's side. Surfaced by accident, not a deliberate retest**: a real storefront checkout during ADR-024 (voucher-at-checkout) testing reached `delivered` in sandbox mode, which shouldn't have been possible per this ADR's own prior conclusion — prompted the founder to ask for a deliberate re-verification rather than assume a fluke.

Re-tested methodically, `sandbox: true`, via `app:gamevion-smoke-test` plus direct `GamevionAdapter::createOrder()` calls (bypassing checkout, same diagnostic discipline as this ADR's earlier addendums):
- `checkBalance()` — still works (`Sandbox User`, balance RM1000, unchanged from 2026-07-25).
- `listProducts({sandbox: true})` — **still returns only the one hardcoded simulation entry** (`sandbox_code: "234"`, `mlbb5`), unchanged from the 2026-07-25/27 addendums. This means the Price Sync/Deactivation-Detection corruption documented in the 2026-07-27 addendum above is **not** affected by this fix and its consequence-to-track (don't run a real Price Sync while `GAMEVION_SANDBOX=true`) **still stands** — only `/api/order` behavior changed, not `/api/product`.
- `POST /api/order` with the simulation code (`234`) — still **rejected**, `422 The selected product code is invalid.` (same as the 2026-07-25 addendum's finding #2 — simulation codes were never valid against the order endpoint, and still aren't).
- `POST /api/order` with a genuinely bogus code (`FAKE-CODE-...`, `BOGUS-XYZ-777`) — correctly rejected, `422 The selected product code is invalid.` — real validation is happening, not a blanket accept.
- `POST /api/order` with **real production `product_code`s, across two different games** — all **succeeded**, previously always `500` in sandbox: `31478`/`31496` (Free Fire, "100 Diamonds"/"210 Diamonds") and `GV572` (MLBB Malaysia, "13 + 1 Diamonds"), each returning accurate matching data (`service_name`, correct `game`, plausible `price`) and a `supplier_ref` prefixed `GV-SANDBOX-...` (distinct from production's own `GV-RAPI-...` prefix seen elsewhere in this ADR — confirms these really are two different environments, not production silently substituting).

**Net conclusion, updated from the 2026-07-25 addendum's own conclusion:** real production `product_code`s (the only kind this codebase ever actually sends — nothing reads from `/api/product`'s simulation catalog for real order creation) now complete successfully through Gamevion's sandbox. The sandbox `500` bug this ADR tracked for weeks appears to be resolved on Gamevion's side — no support ticket needed, no code change on ours (the `callback_url` fix already in place from the addendum above was sufficient; nothing new was changed here). Not confirmed: exactly when Gamevion fixed this, or whether it's stable going forward — no changelog/announcement checked, this was discovered by accident. The one remaining oddity (their own simulation code `234` still `422`s) is minor and doesn't block anything, since this codebase never uses it.

**Consequence to track:** `GAMEVION_SANDBOX=true` can likely be used for real day-to-day dev/testing again (real order creation now works, not just `checkBalance`), which was not true from 2026-07-25 through this addendum. Still **do not** run a real Price Sync while in sandbox mode — that specific gotcha (catalog fetch, not order creation) is confirmed unchanged. Worth a periodic spot-check (`app:gamevion-smoke-test` plus one real `createOrder()` call) in a future session rather than assuming this stays fixed indefinitely, since it was never confirmed *why* it started working.
