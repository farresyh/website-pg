# ADR-005 (D5): Player-ID pre-payment validation is not universal

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-07-23

**Decision:** The order flow must support two paths: validate-before-payment where the supplier/game supports a dedicated validation endpoint, and payment-then-validate-at-order-time as a fallback where it doesn't.

**Rationale:** Confirmed via direct research on real supplier APIs that dedicated validate-ID endpoints are typically only available for specific games (e.g. MLBB), not universally offered by every supplier for every game. This cannot be engineered around — for suppliers without pre-validation, "customer pays, then player ID turns out invalid" is a real scenario that must be handled by policy (ADR-004's voucher-only refund), not assumed away by code.

**Addendum, 2026-07-25 — Gamevion re-confirmed against the live spec, and a related gap surfaced:** re-checked directly against `docs.gamevion.com/gamevion-api` (v1.0.10, fetched live, not recalled from memory) in response to a founder question. Gamevion's entire API surface is exactly 4 endpoints — `check-balance`, `product`, `order`, `check-status` — **zero validation endpoints, for any game, not just "not universal."** `GamevionAdapter::validatePlayer()` throwing `ValidationNotSupportedException` unconditionally is confirmed correct, not a stale assumption.

The same check surfaced a related, previously-undocumented gap: `POST /api/order`'s `data` field is a single opaque **string** (e.g. `"123456|1234"`) — Gamevion's API has no concept of structured per-product input fields either (no schema telling us "this game needs player_id + server_id, this one needs only player_id"). That knowledge has to live entirely on our side. The schema already has a home for it (`Game.validation_rules`, JSON — see `prd.md` §8), but no admin UI to populate it and no `CheckoutService`/`OrderFulfillmentService` logic yet to assemble the `data` string from it. Not built as of this addendum — tracked in `prd.md` §14's NEXT SESSION pointer.

**Addendum, 2026-07-25 (new session) — independent third-party MLBB player-ID validators, built:** since Gamevion itself has zero validation endpoints (confirmed above), the founder separately researched **unofficial, reverse-engineered validate-ID endpoints from three existing MLBB top-up storefronts** — AcidGameShop, Nexone.ph, and MooGold — none of which are Gamevion or any of our own suppliers; this is a wholly independent signal source, not a supplier capability. All three were live-tested (valid and invalid cases) with a real MLBB Malaysia account before any code was written:

- **AcidGameShop** (`POST /api/validate-mlbb`) — cleanest: stateless JSON in/out, `400` + `{"error":...}` on invalid.
- **Nexone.ph** (`POST /pages/get_check_id`) — session-bound: requires first `GET /idchecker` to scrape a one-time `checkToken` tied to that request's cookies, replayed on the actual check. Always returns HTTP `200`; validity is `success: true/false` in the body.
- **MooGold** (a WooCommerce `id-validation-new` plugin endpoint) — most fragile: no structured fields, everything in a free-text `message` string; confirmed live that `icon` stays `"success"` even on a confirmed-invalid ID (`status` is the only real validity flag) and that the `Country` line is sometimes absent even for the identical valid account on a repeat call.

**Decision:** a fallback chain, priority **AcidGameShop → Nexone.ph → MooGold** (founder's own reliability ranking), each behind a common `PlayerValidator` interface (`app/Services/PlayerValidation/`) normalizing to `{valid, nickname, countryCode, provider}` — same normalizer discipline as `SupplierAdapter`/`SupplierResponse` (ADAPT-2). Country is canonicalized by **decoding the flag emoji into its ISO alpha-2 code algorithmically** (a flag emoji is exactly two Unicode Regional Indicator Symbols, one per letter) rather than a country-name lookup table, since it's the one signal both AcidGameShop and Nexone carry consistently; MooGold carries neither reliably, so `countryCode` normalizes to `null` there — a real, distinct "region unknown" outcome, never conflated with "invalid".

**Founder correction, same session — validator is a first-class admin entity, not a string tag:** the first cut put a raw, free-typed `validator_key` string directly on `Game`/`player_region_mappings`. The founder caught the real gap this leaves: nothing stops an admin typing a key with no real backend implementation, and nothing surfaces whether a configured key is actually working. Restructured to a real `PlayerValidatorProfile` model (`player_validator_profiles` table — `name`, `key`, `last_tested_at`, `last_test_result`), with `key` constrained (`Rule::in`) to `PlayerValidatorRegistry::AVAILABLE_KEYS` — the finite set of keys with a real container binding — so a profile can never be created pointing at nothing. A live **"Test this validator"** action (admin supplies a real Player ID/Server ID) runs the actual chain and reports `UnsupportedPlayerValidatorException` (key not bound at all) vs. a genuine result — proving the validator is plugged in, not just configured. `player_region_mappings` (MUI-5's "region-based game routing rules" — which of our own Game rows a given country must buy from, since no provider knows our catalog) now nests under `player_validator_profile_id`, not a loose string, and `games.player_validator_profile_id`/`player_validator_enabled` (nullable FK + kill-switch) replace the original string field. Built and shipped: the middleware Validators screen (MUI-5), the `PlayerValidator` chain + registry, all schema, 33+ tests.

**Addendum, 2026-07-26 (new session) — toggle, public endpoint, and storefront flow all built and live-verified:** the three items this addendum previously flagged as "not yet built" are now two-thirds done. `/admin/games` gained the "Requires Player Validation" toggle (profile picker + on/off, writing `player_validator_profile_id`/`player_validator_enabled` — `UpdateGameRequest` previously silently dropped both fields even if sent). `POST /api/games/{game}/validate-player` (public, no auth, per ADR-011) resolves the profile, runs the chain, maps country against `player_region_mappings`, and returns one of `invalid`/`region_unknown`/`wrong_region`/`valid` — the first thing that ever writes a `player_validations` row. The storefront (`storefront/`, scaffolded this same session — see ADR-009's own addendum) wires this into `/order/[slug]`'s wizard Step 1. **Still not built**: `CheckoutController` server-side enforcement — the storefront gates its own "Proceed to Payment" client-side, but nothing re-checks `player_validations` on the actual `POST /api/checkout` call yet, so a direct API call still bypasses it. See `prd.md` §14's newest NEXT SESSION pointer.

**Still separate, still unconfirmed:** this new validator layer answers "is this MLBB account's region known" — it does **not** resolve Gamevion's own still-open question (this ADR's first addendum, and ADR-006's newest addendum) of how an invalid player/server ID actually surfaces when Gamevion processes a real order. The two are unrelated mechanisms; don't conflate a "yes" on one as progress on the other.

**Addendum, 2026-07-27 — `CheckoutController` server-side enforcement built, closing the bypass flagged above:** surfaced by a full project audit as a real, exploitable gap — `POST /api/checkout` never checked `player_validations` at all, so any direct API call (skipping `POST /api/games/{game}/validate-player` entirely) reached a real Xendit charge and a real Gamevion order on an unconfirmed Player ID. Given ADR-004's no-cash-refund policy, the only resolution for a resulting misdelivery is retry or voucher — this made the bypass a genuine money/dispute risk, not just a spec gap.

`CheckoutController::assertPlayerIdIsValidated()` now runs whenever `game.player_validator_enabled` is true: it requires a `player_validations` row matching the exact `game_id`/`player_id`/`server_id` tuple, `status='valid'`, within a rolling window (`services.player_validation.checkout_window_minutes`, default 30, env `PLAYER_VALIDATION_CHECKOUT_WINDOW_MINUTES`) — otherwise rejects with a `422` on `player_id` before any Order/payment is created. Deliberately matched on the data tuple, not a per-session/per-request token: guest checkout (this ADR, ADR-011) has no session to bind a token to, and founder confirmed data-tuple matching is sufficient — it closes "checkout with an ID that was never validated," which is the actual risk, without adding a token-issuance mechanism to solve a session-binding problem this architecture doesn't have. 6 new tests in `CheckoutControllerTest` (expired validation, wrong player_id, wrong status, matching server_id); full suite 367 tests, all green.
