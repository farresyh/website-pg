# ADR-048: Queue driver migration to Redis, plus Horizon + Pulse — reverses ADR-014 decision #1 / ADR-020 decision #3's "queue stays on `database`"

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-27 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, same session as `ADR-047`, before any code touched)

> **Follow-on in ADR-077 (2026-09-07):** the *cache* store now also moves to Redis (this ADR moved only the queue and put Pulse's dashboard-render cache on Redis). ADR-077 also adds a dedicated `revalidation` Horizon queue/supervisor and re-tunes Pulse's ingest driver (`storage`→`redis`, dedicated DB) and slow-query thresholds.

**Context:** The queue driver has been `database` since `ADR-014` decision #1, and `ADR-020` decision #3 explicitly reaffirmed it when Redis was provisioned for production ("Redis is cache-only, never the queue driver... the queue stays on the `database` driver"). That same decision #3 already named its own revisit trigger in advance: *"the queue driver ever moves off `database` onto Redis — at that point Redis starts holding money-relevant, non-regenerable job state, changing this calculus entirely."* This ADR is that trigger firing, not a decision made in a vacuum.

Driving need: **Laravel Horizon** (a real-time queue dashboard — throughput, per-queue metrics, a failed-job retry UI) requires `QUEUE_CONNECTION=redis`; it does not support the `database` driver at all. Today's three named queues (`orders`, `price-sync`, `backups`, per `ADR-020`'s queue-worker split) run on bare `queue:listen` with no visibility beyond Pail's raw log tail — a real gap once queue volume matters.

**A real, newly-found risk surfaced while grilling this, not assumed away:** `docker-compose.prod.yml`'s `redis` service runs `redis-server --save "" --appendonly no` — persistence fully disabled, which was **correct** under `ADR-020` decision #3's own reasoning (a pure cache crash loses nothing a fresh Managed-MySQL read can't immediately replace). Moving the queue onto this same, still-unpersisted Redis instance would silently put **real, unprocessed jobs** — a queued `FulfillOrderJob` for a real, already-paid order — at risk of being lost on any Redis restart, crash, or OOM. This is new, money-adjacent risk that does not exist under the current database-backed queue (whose job rows live durably in Managed MySQL). It must be closed as part of this same decision, not discovered later during an incident.

**Decision:**

1. **Reverse `ADR-014` decision #1 / `ADR-020` decision #3's "queue stays on `database`" explicitly, recorded here as its own entry** — matching this doc's own no-silent-rewrite convention (the same way `ADR-020` decision #3 itself explicitly superseded `ADR-014` decision #1, rather than editing that entry in place). `QUEUE_CONNECTION` changes to `redis`.
2. **Redis persistence is enabled as a hard prerequisite of decision 1**, closing the risk found above: `docker-compose.prod.yml`'s `redis` service command changes from `--save "" --appendonly no` to `--appendonly yes` (AOF), trading a small, well-understood amount of disk I/O for job durability across restarts. This is the one technical addition this ADR makes beyond what was directly asked for — recorded explicitly rather than silently assumed safe, per this project's "money-critical infra gets caught before merge, not after" discipline (mirrors `ADR-046`'s backfill-before-cutover sequencing for the same reason).
3. **Horizon adopted.** Dashboard linked from the admin app's existing `/middleware` nav group — the same technical-ops-tooling category `Backups`/`Price Sync`/`Sandbox` already live in, not `/admin`'s business-ops group — and gated via `Horizon::auth()` against the same admin-role check every other admin-facing backend surface already uses. No new auth mechanism.
4. **Pulse adopted alongside Horizon** (general app-health telemetry — slow queries, exception rate, cache/queue metrics) — same `/middleware` placement and admin-role gate as decision 3. Ingest storage driver stays Pulse's own `database` default for now, deliberately not Redis — no reason to add Pulse's own write load onto the newly-Redis-backed queue path before real metric volume ever justifies it.
5. **Precognition and Pennant evaluated, not adopted.** Neither has a confirmed present trigger — no reported form-validation-duplication pain for Precognition, no gated-feature need beyond what plain env-var toggles already handle for Pennant. Tracked in `docs/prd.md`'s pointer list as a future candidate, same treatment as any other not-yet-triggered backlog item, not built here.

**Rationale:** Horizon's own Redis requirement is the actual forcing function for reversing `ADR-014`/`ADR-020`'s queue-stays-`database` choice — this ADR doesn't reopen that choice for its own sake, it fires the exact trigger `ADR-020` decision #3 already named in advance for exactly this situation. Fixing the persistence gap (decision 2) in the same pass, rather than as a follow-up ticket, matches the same discipline `ADR-046` used for its own money-adjacent cutover (backfill verified before the binding change, not after).

**Consequence to track:**
- Decision 2 (Redis persistence) must be verified locally before any real deploy — AOF rewrite/recovery behavior should be smoke-tested directly (e.g. `kill -9` the Redis container mid-queue-burst, confirm jobs survive the restart), not assumed correct from documentation alone, the same discipline `ADR-020`'s own addendum used to smoke-test `GET /api/health` by actually running the stack.
- `ADR-020` decision #3's other two revisit triggers — (b) Redis downtime visibly degrading the customer-facing checkout path, (c) a future second droplet/region needing a Redis instance shared across boxes — remain open and are **unaffected** by this ADR. Trigger (a) firing here does not make (b)/(c) moot; don't conflate them.
- Nothing is built yet — design only, matching `ADR-018`/`ADR-020`/`ADR-047`'s own established practice.
- Decision 5 (Precognition/Pennant not adopted) should be treated as closed for this round unless a real, concrete trigger surfaces later — not silently revisited without one, matching `ADR-046` decision 1's own precedent for SUPP-2/3/4.
- This ADR is independent of `ADR-047` (Reverb/Echo) but was grilled the same session because Reverb's own broadcasting can optionally use Redis for horizontal scaling later — nothing in `ADR-047` currently depends on this ADR shipping first, and vice versa; they can be built in either order.

No new decision needed on scope/shape — this is a correction to decision 8's own "live call" behavior, not a new mechanism.

**Build addendum, 2026-08-27 (same day, new session) — all 5 decisions shipped.** `composer require laravel/horizon laravel/pulse`; `config/horizon.php` gained `supervisor-orders`/`supervisor-price-sync`/`supervisor-backups` (one per queue, `balance: off`, tries/sleep matching each old `queue-worker-*` container's own flags exactly — orders `tries=3`, price-sync/backups `tries=1`, all three `sleep=3`); `docker-compose.prod.yml`'s three `queue-worker-*` containers replaced by one `horizon` service (`php artisan horizon`, `stop_grace_period: 90s` for `horizon:terminate`'s graceful drain); `redis`'s command flipped to `--appendonly yes` with a new named `redis-data` volume (decision 2's hard prerequisite, closing the money-adjacent risk the ADR itself found — not yet live-verified via the `kill -9` restart-survival test the ADR's own consequence-to-track calls for, since there's no real deploy yet to test against). `backend/composer.json`'s `dev` script swapped `queue:listen --queue=orders,price-sync,backups` for `php artisan horizon`, gaining the same dashboard locally.

**A second, real gap found and closed while building, not assumed away:** decision 3's "gated via `Horizon::auth()`... No new auth mechanism" undersold what building it actually required. This backend has no session-based login anywhere — `AuthController::login()` only ever issues a Sanctum bearer token, never calls `Auth::login()` — so a browser tab visiting `/horizon` directly has no way to authenticate against Horizon's own `web`-guard dashboard (confirmed live: `AdminUser` already `Authenticatable`, `config/auth.php`'s `web` guard/`admin_users` provider already fully wired, just never exercised). Explored with the founder (`/mattpocock-skills:grilling`-style, one decision at a time) against a real, freshly-found precedent this same day: `ADR-047` decision 3's own comment in `bootstrap/app.php` explicitly avoided the `web` session guard for broadcasting auth, calling it "session-based... which this API-only backend never otherwise uses." Building session-bootstrap for Horizon/Pulse is a deliberate, scoped exception to that precedent, not a silent reversal of it — recorded here rather than left implicit:

- **`OpsAccessController::mint()`** (`POST /api/middleware/ops/{target}/link`, Sanctum + `admin.role:super_admin`, same tier as every other `/middleware/*` route) issues a `URL::temporarySignedRoute()` good for 5 minutes, params bound into the signature (`admin_id`, `target`).
- **`OpsAccessController::enter()`** (`GET /ops/enter`, `web` + `signed` middleware, named `ops.enter`) is the *only* place this backend ever calls `Auth::guard('web')->login()`. The `signed` middleware rejects a tampered/expired link before the controller runs at all; the controller re-checks `is_active`/`role` itself (the signature only proves the link wasn't tampered with, not that the admin is still active/super_admin *now*), then redirects into `horizon.index` or `pulse` (Horizon/Pulse's own route names) with a real session established for every subsequent same-origin dashboard request.
- `HorizonServiceProvider::gate()`'s `viewHorizon` and a new `Gate::define('viewPulse', ...)` in `AppServiceProvider::boot()` (Pulse doesn't generate its own provider) both check the same thing: `$user !== null && $user->is_active && $user->role === 'super_admin'`.
- Admin UI: `/middleware`'s existing nav layout (`admin/src/app/middleware/layout.tsx`) gained an "Ops" section — "Horizon (Queues)"/"Pulse (App Health)" buttons, not `<Link>`s, since these are Laravel-rendered pages, not Next.js routes. Each opens a blank tab synchronously (avoids Safari/Chrome's popup-blocker triggering on the post-`await` `window.open`), mints the link, then sets the tab's `location.href`.
- Not a standing login form: the only way to reach `/ops/enter` at all is already being an authenticated Sanctum super_admin inside the SPA and clicking one of these two buttons — there is no page anywhere that accepts an email/password against the `web` guard.

**Local dev gained a real new prerequisite, found and closed the same session, not left as a silent gotcha:** `backend/docker-compose.yml` (the local, Docker-optional dev compose file, distinct from the root `docker-compose.prod.yml`) had no `redis` service at all — daily `composer run dev` never previously needed Docker running. Since `QUEUE_CONNECTION=redis` is now the default and Horizon has no `database`-driver fallback, local dev gained a `redis` service (published on `6379`, no AOF — a local dev Redis losing an in-flight test job on restart is a non-event, unlike production's) and a new documented prerequisite: `docker compose up -d redis` before `composer run dev`. `AGENTS.md`'s Build & Test section and its "Known gotcha" entry both updated with this as a third named cause of the same "queued job never runs" symptom.

**Founder live-testing, same day (2026-08-27/28) — real bug found, first diagnosis wrong, corrected same session.** `/pulse` 500'd on first real load: `Illuminate\Support\Collection` "incomplete object... unserialize()" error inside `vendor/laravel/pulse/resources/views/livewire/slow-requests.blade.php`.

*First fix attempt (incomplete):* assumed the app's own `database`-driver cache default (ADR-014/019) was the cause — the exact "`Cache::remember()` values must be plain arrays... the `database` cache driver silently corrupts nested objects on the next read" gotcha `backend/AGENTS.md` already documents for this app's own code. Changed `config/pulse.php`'s `'cache'` default to `redis`. **This did not fix it** — the same error recurred on a *different* card (`Queues.php:35`) after the change, and was reproduced in a plain `php artisan tinker` session (no Livewire/HTTP involved at all) using the Redis store directly, ruling out both Livewire and the store choice as the cause.

*Real root cause, found via `WebSearch` (a matching open upstream report, `laravel/pulse` "incomplete object" + PHP 8.4 + Laravel 13) then confirmed by reading `Illuminate\Cache\RedisStore::unserialize()` and `CacheManager::getSerializableClasses()`:* `config/cache.php`'s `'serializable_classes' => false` — a real Laravel security default ("no PHP classes will be unserialized from your cache to prevent gadget chain attacks if your APP_KEY is leaked") — makes `unserialize($value, ['allowed_classes' => false])` silently downgrade *every* cached object to `__PHP_Incomplete_Class` instead of erroring at write-time. It's a single global setting read for every store regardless of which one asked (`getSerializableClasses($config)` ignores its own `$config` argument), so switching Pulse's store doesn't touch it. `laravel/pulse` (first-party) doesn't account for this newer framework default at all — a real, currently-open upstream gap, not something specific to this app.

*Fix:* `config/cache.php`'s `'serializable_classes'` changed from `false` to an explicit allowlist — `Illuminate\Support\Collection`, `stdClass`, `Carbon\CarbonImmutable`, `Carbon\CarbonInterval` — the 4 exact types Pulse's Livewire card source actually caches (grepped, not guessed). Deliberately **not** `true` (blanket-allow, which would reopen the gadget-chain surface this setting exists to close) — a narrow allowlist stays consistent with this app's own existing discipline of never caching real objects from its *own* code, so the practical risk reduction from `false` is Pulse-only. `config/pulse.php`'s earlier `'cache' => 'redis'` change (first fix attempt) is kept — real infra reuse (ADR-020's `cache` Redis connection, DB index 1, distinct from Horizon's DB index 0), not wrong, just not sufficient alone. Verified live: `Cache::flexible()`-equivalent round-trip (write then a *separate* process read) succeeds for both `Collection` and `stdClass` after the fix; poisoned pre-fix entries purged (`cache:clear` + a `FLUSHDB` on the `cache` Redis connection). Backend suite still 901/901 green throughout both fix attempts.

**Addendum, 2026-09-29 — order lanes + worker scaling (audit Wave 4 K-1/K-5/K-7).** Grilled with the founder (`/mattpocock-skills:grilling`). This is the "scale once real volume justifies it" trigger from the original decision, pulled forward as burst prep before any promo push.

*Context:* `supervisor-orders` ran 1 worker for every channel, and the same queue also carried bot replies and every `OrderStatusUpdated` broadcast. At prod's measured Digiflazz `createOrder` latency (p50 0.16s, p95 6.3s, n=43), a 300-orders-in-5-minutes burst would back up for up to ~30 minutes. The founder asked about one worker per channel. Digiflazz CS confirmed topup has **no rate or concurrency limit** (the full price list is limited to 1 call per 5 min, `rc 83`), so the ceiling is our own box: 2 vCPU, 3.9 GB RAM, ~85 MB per Horizon worker, php-fpm `max_children 20` × ~65 MB.

*Decisions:*
1. **Two lanes, not one per channel.** The retail lane keeps the queue name `orders` (storefront + affiliate, `wallet_reseller_id` null). Keeping the name means jobs already queued or delayed on `orders` at deploy time still drain. A new `orders-reseller` lane takes portal, API and bot orders (`wallet_reseller_id` set). `FulfillOrderJob`, `ResendOrderDeliveryJob` and `CheckSupplierDeliveryJob` pick the lane from the order itself, so webhook, reconcile and admin-retry dispatches route correctly with no caller changes. One per channel was rejected: every channel would still have only 1 worker, idle workers would waste RAM, and the only real noisy neighbour is a reseller (API 60 orders/min/token) starving storefront customers.
2. **One supervisor, `balance: auto`**, min 1 process per lane, **max 4 total**. **Combo goes 1 → 2** (made safe by K-4's `redis-long` retry_after).
3. **Bot replies and `OrderStatusUpdated` broadcasts move off `orders` to the existing `default` supervisor.** No new process for them.
4. **K-5:** the CHIP, Digiflazz and OpenWA webhook throttles go from 120 to 600 per minute. Signatures are still verified, so the throttle remains only a flood guard. OpenWA traffic all arrives from one localhost IP.
5. **K-7 (ops, applied live 2026-09-29):** prod Redis was `noeviction`, `maxmemory 0`, AOF **off** on the ADR-114 droplet. ADR-048 decision 2's AOF prerequisite had not been carried over to the new box. It is now `maxmemory 256mb`, `volatile-lru`, `appendonly yes`, `appendfsync everysec`, persisted via `CONFIG REWRITE`. `volatile-lru` only evicts keys that have a TTL (cache, throttle counters), so queue payloads, which have no TTL, are never evicted. Port 6379 was confirmed filtered from the internet.
6. **RAM headroom:** the unused local `mysqld` (409 MB, zero connections, the app uses DO Managed MySQL) gets disabled before this ships. That covers the +4 workers (~340 MB).
7. **Lows bundled in:** Horizon LongWait notifications on, `horizon:snapshot` scheduled, and the dashboard "queue pending" KPI now reads Redis. Parallelising scheduler reconcile was deferred because it is not slow today.

*Consequence to track:* max 4 / combo 2 are starting numbers. Raise them from real Horizon wait-time data, not guesses. The next ceiling is php-fpm plus RAM: a burst that also fills fpm to 20 children would need the 8 GB droplet.
