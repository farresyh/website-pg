# ADR-073: Reseller wallet — fee-less tiers, prepaid-deposit ledger, order-placement contract, profit booking, delivery-failure handling

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-04, same grill session as ADR-072. Depends on ADR-072 (the `Reseller` entity must exist before its money mechanics do).

**Context:**
- ADR-056's `reseller_membership_tiers` (renamed `affiliate_membership_tiers` per ADR-072) is a **paid subscription** — a monthly fee, a `ResellerSubscription` state machine with a grace period and a lapse-to-fallback path. That model doesn't fit `Reseller` (wallet): the founder's explicit call is **no monthly fee, deposit only** — admin creates a tier (just a name + `markup_percent` over `cost_price`) ahead of time, then assigns a `Reseller` account to one at registration; there is nothing to lapse from.
- No wallet/deposit balance mechanism exists anywhere in this codebase. `LedgerService`'s `credit()`/`debit()`/`withdraw()` primitives (ADR-002) are proven, concurrency-tested (`lockForUpdate()` on the `ledger_accounts` mutex row), and already generic — `debit()` takes a free-text `$type`, so a new debit reason needs no new locking code, only a new `LedgerOwnerType` case.
- `VoucherService::redeem()` is this codebase's closest existing precedent for "debit a balance synchronously at the moment of purchase" (as opposed to `withdraw()`'s request-then-admin-approve two-step) — it locks the balance-holding row directly inside one transaction before creating anything downstream.
- The founder's own framing, stated directly: the wallet's business purpose is to fund PekanGame's own working capital so its own supplier balance (Digiflazz/Gamevion) doesn't run dry — a reseller's deposit is real cash landing in the one company CHIP account, same as every other sale.

**Decision:**

1. **New table `reseller_tiers`** (post-rename name) — `name`, `markup_percent` (over `cost_price`, same math as ADR-056 decision 2), `is_active`, `sort_order`. **No `monthly_fee_sen`, no lapse/grace state machine** — assignment is a direct FK swap by admin, effective immediately, no billing cycle. This is a deliberately separate table from `affiliate_membership_tiers`, not a shared/reused one — the two are different economic relationships (recurring SaaS-shaped fee vs. pure prepaid volume pricing) that happen to share the same percentage-over-cost math; forcing one table to serve both re-tangles what ADR-072 just untangled.
2. **Wallet balance reuses `ledger_entries`/`LedgerService`**, not a new balance-column system. New `LedgerOwnerType` case (e.g. `ResellerWallet = 'reseller_wallet'`) and new `ledger_entries.type` values: `wallet_topup` (credit), `wallet_debit` (spend on an order), `wallet_refund` (credit, decision 6). A `Reseller` (wallet) account never has an earnings-type balance — it only ever holds a spend balance, the structural opposite of an `Affiliate`'s earnings account.
3. **Top-up has two paths, both writing the same `wallet_topup` ledger entry type** so reporting never has a gap regardless of path: (a) **self-serve**, mirroring ADR-068's self-serve Membership subscription architecture exactly — a new `wallet_topup_attempts` table (`pending → paid/failed/expired`), the `Reseller` portal screen → CHIP checkout → `ChipWebhookController` gains a third reference-matched branch (order / membership / wallet-topup), CHIP's transaction fee added on top and borne by the reseller (same customer-borne-fee pattern as checkout today); (b) **admin manual-credit**, for a reseller who pays by direct bank transfer outside CHIP — an admin action that writes the same `wallet_topup` entry with an optional attached receipt/proof file for audit. **`LedgerService::openAccount('reseller_wallet', id)` is called at `Reseller` account creation (PR-B), not deferred until the first top-up** — `debit()`'s existing `lockForUpdate()->firstOrFail()` throws a hard "row not found" error (not a graceful insufficient-balance rejection) against a `ledger_accounts` row that was never opened, mirroring the same proactive-open precedent `Admin\ResellerController::create()` already follows for a new `Affiliate`.
4. **Order-placement contract (both API and Bot channels call the same internal service):** check `resellers.is_active` (decision 9's account-level gate, ADR-072) → authenticate (API key or WhatsApp-group resolution, ADR-074/075) → **check the request's idempotency key against existing orders before doing anything else** (API: a caller-supplied `idempotency_key`, same field/semantics `CheckoutController` already requires; Bot: derived from `(whatsapp_message_id, group_id)`, since a chat command carries no client-generated key of its own and OpenWA's webhook can redeliver the same inbound message) — a duplicate is a no-op returning the original order's result, never a second debit → resolve the tier price for the requested package → one `DB::transaction()`: lock the `('reseller_wallet', id)` `ledger_accounts` row, check balance ≥ price, `LedgerService::debit()` with type `wallet_debit` (reusing the existing generic primitive — no new locking code needed), create the `Order` row (`payment_status = Paid` immediately — the debit succeeding *is* the payment event, there is no CHIP/webhook round-trip to wait on; `payment_method = 'wallet'`, a new free-text value alongside `fpx` — `payment_method` has no fixed enum in code; `pricing_basis = 'reseller-wallet'`, a new value alongside `standard`/`member`, reusing the existing `selling_price`/`cost_price`/`platform_profit`/`reseller_profit` snapshot columns rather than new ones) — transaction closes here. **`FulfillOrderJob` is dispatched *after* this transaction commits, never from inside it** — confirmed against real code: `config/queue.php` sets `after_commit => false` on every connection including `redis` (the production queue driver, ADR-048), so a job dispatched inside the transaction risks a worker grabbing it before the commit is visible; `CheckoutService::settleWithVoucher()` already avoids exactly this by dispatching only once its own transaction has closed — this contract follows the same proven shape. **Insufficient balance rejects synchronously before any `Order` row is created** — no ghost/failed-payment order rows for a purchase that was never actually funded.
5. **Full reuse of `Order`/`OrderFulfillmentService`/the delivery-status and retry pipeline** — no parallel lighter-weight order entity. `orders.reseller_id` (renamed conceptually by ADR-072 to mean "which `Affiliate`/brand this order's storefront belongs to") stays as-is and defaults to the primary `Affiliate` for a wallet order (there is no branding/whitelabel involved — the reseller is buying directly from the platform's own catalog). A new nullable `orders.wallet_reseller_id` FK identifies which `Reseller` (wallet) account placed it, for their own order-history and for reporting — two columns for two different meanings, not one FK overloaded both ways.
6. **`platform_profit` is booked on delivery-confirmed** (not at debit time), by the same `OrderFulfillmentService::creditProfit()` seam every other order type uses: `platform_profit = wallet_debit_amount − cost_price` (snapshotted at order-creation time per the existing ORD-9 discipline), credited to `('platform', null)`. **No `reseller_profit` line for a wallet order** — the reseller's margin was already fully captured at the moment of the debit (they paid the tier price up front); there is no downstream earnings account for a `Reseller` (wallet) to credit, unlike an `Affiliate`.
7. **Delivery-failure handling diverges intentionally from ADR-004's Voucher policy.** A failed wallet order first gets the same **retry / Resend Delivery** path every order type already has (no new retry logic). Only when an admin decides not to retry further does the debited amount get **refunded back to the reseller's own wallet balance** (`wallet_refund` credit, decision 2) as a new terminal admin action — for a `wallet_reseller_id`-owned order, the admin's existing "Issue Voucher" action is **replaced entirely by "Refund to Wallet"** in that order's detail screen (not shown alongside it), since Voucher's email-keyed mechanism has no meaning for a B2B wallet account and a dual option only invites the wrong one being clicked. This is a deliberate, better-than-guest outcome (real automatic reversal of an internal balance we fully control) rather than a Voucher workaround — **not** a reopening of ADR-004's "no cash refund" policy, since no cash ever leaves the platform; it is an internal-credit reversal.
8. **No automated routing of top-up cash toward supplier funding.** Every top-up (self-serve or manual) lands in the same one company CHIP account as every other sale — commingled with `Affiliate`/main-storefront revenue, by design (ADR-059 decision 6's "one account" model, unchanged). The founder tops up Digiflazz/Gamevion's own balance manually from overall cash flow; the `wallet_topup` ledger type (decision 3) exists specifically so this can be reconciled from a report even though the bank balance itself is not separated. Automating supplier-funding-from-wallet-revenue is out of scope, a candidate for its own future ADR if the founder ever wants it.
9. **Rate limiting is mandatory on the order-placement endpoint from day one**, its own throttle bucket per-`Reseller` account (matching the shared-throttle-bucket bug class ADR-021's addendum already documents for this codebase) — exact thresholds are a build-time detail, not a design decision, but the requirement itself is not optional given the endpoint debits real money synchronously.

**Rationale:** Decision 2 (reuse `LedgerService`, don't reinvent) is the single highest-leverage call in this ADR — `debit()` already being a generic, concurrency-proven primitive with a free-text `$type` means the entire wallet-spend mechanism needs zero new locking code, only a new owner-type case and two new entry-type strings. Decision 7's divergence from ADR-004 is justified because the two refund mechanisms solve different problems: Voucher exists because there is no wallet to refund a guest into; a `Reseller` (wallet) account *is* a wallet, so refunding it is strictly simpler and safer than the workaround Voucher was built to be.

**Consequence to track:**
- Decision 4's synchronous debit-then-create flow needs a concurrency test in the same shape as `LedgerService::withdraw()`'s and `VoucherService::redeem()`'s existing subprocess-based proofs (`tests/Concurrency/*`) — two simultaneous orders against the same near-exhausted wallet balance must not double-spend past zero.
- Decision 6's "no `reseller_profit` line" must be grepped for at build time everywhere `creditProfit()` (or its future refactor) branches on order type, so a wallet order never accidentally gets a phantom earnings credit routed to a `('reseller', id)` earnings account it doesn't have.
- The `PricingResolution` value-object extraction ADR-060's own post-ADR-057 review already flagged (`CheckoutController::initiate()`'s inline ternaries not holding past a 2×2) is now a genuine prerequisite for this ADR's order-placement contract too, since wallet-debit pricing is a third dimension on top of standard/member × affiliate-tier/lapsed. Build it once, here, rather than duplicating ad-hoc branching in the API/Bot order-creation path.
- `docs/prd.md` §6/§8/§13 need a `Reseller Wallet Tier` / `Wallet Debit` / `Wallet Refund` glossary entry once this ships, distinct from the existing `Reseller Wholesale Tier` (which is now `Affiliate`'s).

### Cross-reference (2026-10-04) — decision 7's Refund to Wallet now goes through one shared settlement service
