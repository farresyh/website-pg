# ADR-051: Middleware Request Logs (MID-10/11, MUI-9) — HTTP-client-event hook, redact-then-queue write path, and split retention

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-28 (grilled via `/mattpocock-skills:grilling`, four rounds, before any code touched)

**Context:** `docs/prd.md` §15's 2026-08-28 reconciliation pass on the Middleware Panel row confirmed MID-10/11 (backend) and MUI-9 (admin UI) as the one genuinely unbuilt piece of that row — no `request_log`-equivalent table or model exists anywhere in the codebase (confirmed via grep), and `docs/foundation-security.md` §7 already carries an explicit, still-unchecked line naming exactly this feature: *"Request logs redact credentials and excess PII before being written (MID-10)"* — a standing requirement, not a new invention of this ADR.

Investigation before grilling found the real shape of the problem: `SupplierAdapter` (`app/Services/Supplier/SupplierAdapter.php`) has 5 methods (`checkBalance`, `listProducts`, `createOrder`, `checkStatus`, `validatePlayer`), and both real implementations (`GamevionAdapter`, `DigiflazzAdapter`) each build their own `Http::baseUrl()` client and call `->post()` independently at each method — there is no single existing choke point. `CircuitBreakingSupplierAdapter`'s `guarded()` helper wraps 4 of the 5 methods (not `validatePlayer`) but only sees the normalized `SupplierResponse`, not the raw HTTP request/response. Zero existing logging (`Log::` calls) exists in either adapter or the circuit breaker today. `player_validations` (ADR-021's 7-day-retained PII table) stores only the validation *outcome* (status/nickname/country/provider), not the raw call — no overlap with what this feature adds. `price_sync_runs`/`deactivation_logs` are per-sync-*run* granularity, not per-HTTP-*call* — also no overlap.

**Decision:**

1. **Scope: supplier-adapter calls only** — all 5 `SupplierAdapter` methods, for any adapter (today Gamevion/Digiflazz, automatically any future one). Payment gateway webhooks (Xendit/CHIP) are explicitly **out of scope** — a separate future item under §6.23 Payment & Webhook Integrity, not folded in here.
2. **Hook mechanism: Laravel's HTTP client `RequestSending`/`ResponseReceived` events, listened to globally** — not a new decorator, not per-adapter logging code. This touches neither the `SupplierAdapter` interface nor its implementations' method bodies (matches this project's "deep modules, stable seams" convention), and automatically covers `validatePlayer` too, which the existing circuit-breaker decorator doesn't wrap. Each adapter call site gains a small context tag (`supplier_id`, `call_type`, `order_id` where applicable) passed via HTTP client request options, so the generic event has enough to attribute a row without redesigning `SupplierResponse`.
3. **Circuit-breaker preemptive skips get a synthetic log row too** (`outcome = skipped_breaker_open`), distinct from a real HTTP failure — `guarded()` short-circuits before any request is sent, and losing that distinction would make the log unable to answer "did the supplier actually fail, or did we never even ask." ~~Same signal MUI-1's still-ungrilled Dashboard would eventually want to show.~~ **MUI-1 built 2026-08-28 — see [ADR-052](../adr.md)** — deliberately scoped thinner than this: a "recent calls" feed reusing `listRequestLogs()` as-is, not a dedicated breaker-skip-rate view.
4. **Write path is redact-then-queue-then-write, never inline-then-redact.** The event listener classifies and strips secret-tagged payload keys *before* the row ever reaches the queue or the database — directly implementing `foundation-security.md` §7's "redact... before being written" line, not a lesser after-the-fact scrub. The actual insert is dispatched as a queued job (Redis/Horizon, `ADR-048`), not written inline, so the one customer-facing synchronous call in this set (`validatePlayer`) never gets slower because of logging.
5. **Payload depth: full request+response body by default**, masked. This is the feature's real debugging value — a metadata-only log (status code, duration, nothing else) would not have surfaced the real `callback_url`-missing production bug (`ADR-006`'s 2026-07-29 addendum). One deliberate exception: `listProducts`' response (a full supplier catalog dump) is truncated to an item count + small sample, not stored in full — repetitive, large, and already covered at the right granularity by `price_sync_runs`/`deactivation_logs`.
6. **Rows from `createOrder`/`checkStatus` carry a nullable `order_id` FK** — cheap column, lets a future Order Detail view filter "every supplier call for this order" directly; same FK-to-originating-entity convention `deactivation_logs` already uses toward `price_sync_run_id`.
7. **Retention: 30-day default pruning, except `validatePlayer` rows follow `player_validations`' existing 7-day PII window (`ADR-021`)** rather than the blanket 30 — those rows carry the same player-account nickname/ID category that window already governs, and a debug log copy of PII shouldn't outlive the record the PII-retention decision was actually made for. A new pruning command mirrors `PrunePlayerValidationsCommand`'s shape rather than extending it (different table, different owning concern).
8. **Table name: `supplier_request_logs`**, not the more generic `request_logs` the PRD's own MID-10/11 wording might suggest — decision 1 already scopes this to supplier-adapter calls only, and a generic name would collide with (or force a rename around) a future payment-webhook logging table under §6.23.
9. **UI: standalone `/middleware/request-logs` screen (MUI-9)**, not folded into `/middleware/suppliers` or `/middleware/sandbox` — list + filter (supplier/call_type/outcome/date range) + a detail modal showing the (already-redacted) raw payload, same interaction shape as Price Sync's own Sync Details modal.
10. ~~**Forward reference, not a commitment:** this ADR notes `supplier_request_logs` as the eventual data source for MUI-1's still-ungrilled unified Dashboard (supplier cards, circuit-breaker state, a recent-API-call feed) — the same anticipatory note `ADR-019` left via `CircuitBreaker::state()` ahead of `DASH`'s own dashboard screen being built.~~ **Fulfilled 2026-08-28 — see [ADR-052](../adr.md).** MUI-1's landing page reads `supplier_request_logs` via `listRequestLogs()` exactly as anticipated here, alongside `getDashboardHealth()` (the same `CircuitBreaker::state()`-backed endpoint `ADR-019`'s own anticipatory note pointed at) for supplier cards/circuit state.

**Rationale:** Decision 2 is the load-bearing architectural call this ADR exists to record — a global HTTP-client-event listener achieves full coverage across all 5 methods (including the one the existing circuit-breaker decorator doesn't wrap) without reshaping the `SupplierAdapter` seam or touching either real adapter's method bodies. Decisions 4/5/7 together directly close the standing, previously-unchecked `foundation-security.md` §7 requirement rather than leaving it open through this build too. Decision 8 keeps the table's scope as precise as decision 1's own scope boundary, so a future webhook-logging feature never has to contend with (or rename around) this one.

**Consequence to track:** the secret-field classification this feature's redaction step relies on should reuse/extend the shared field-shape schema (see build addendum — `SupplierConfigSchema`) rather than invent a second classification scheme — if a new supplier adds a new secret-shaped config field, both places need to move together or redaction silently misses it. If a future payment-webhook request-logging feature gets built under §6.23, it gets its own table, never squeezed into `supplier_request_logs` (decision 8's boundary). ~~If MUI-1's Dashboard is eventually grilled and built, it should read `supplier_request_logs`, not stand up a second, parallel write path.~~ **Fulfilled 2026-08-28 — see [ADR-052](../adr.md)**, exactly as anticipated: no second write path was ever created.

**Build addendum, 2026-08-28 (same day) — shipped on `feature/adr-051-request-logs`, stacked on `fix/supplier-config-guard`.** All 10 decisions shipped; one implementation-level correction to decision 2, found while building, not a re-litigation of the decision's intent:

- **Decision 2 correction:** Laravel's `RequestSending`/`ResponseReceived` HTTP client events, as literally named in the decision text, turned out to carry only the PSR-7 request/response — no way to attach a call's business context (supplier slug/call_type/order_id), since Guzzle-level request *options* (where that context would ride) never make it onto the event's `Request` object. Used Guzzle's per-request `on_stats` option instead (`SupplierRequestLogger::attach()`) — set locally inside each adapter's `client()` builder, so the callback closes over the context directly. Achieves the same intent decision 2 actually asked for (no `SupplierAdapter` interface change, no decorator, automatic coverage of `validatePlayer` too) — same "generic client-level hook, not per-call-site logging code" shape, just a different Laravel/Guzzle primitive than the one named. `client()` methods on both adapters gained `string $callType`/`?int $orderId` parameters to supply that context; `SupplierOrderRequest`/`SupplierStatusCheckRequest` gained an `orderId` field (decision 6), populated at their two real construction sites (`OrderFulfillmentService`, `CheckSupplierDeliveryJob`).
- **`SupplierController::FIELD_DEFINITIONS`** (private, decision 8/redaction's stated reuse target) was extracted to a new shared `App\Services\Supplier\SupplierConfigSchema` on the prerequisite `fix/supplier-config-guard` branch this one stacks on — both `SupplierController` (masking/`visibleConfig()`) and this feature's `SupplierRequestPayloadRedactor` (body-key redaction) now read the same source, closing the exact drift risk this ADR's own Consequence section flagged before it could ever open.
- **Redaction, concretely:** `SupplierRequestPayloadRedactor` always strips `Authorization`/`X-API-KEY` headers case-insensitively (covers Gamevion's header-based auth), plus any body key `SupplierConfigSchema` marks `secret` for that slug, plus one extra per-slug list (`digiflazz.sign` — an MD5 derived from the api_key, not the raw secret, but replayable for that exact call so redacted with the same discipline). Digiflazz's auth lives entirely in the body (no secret headers), Gamevion's entirely in headers (no secret body keys) — both paths are real, not hypothetical, and both are covered.
- **Circuit-breaker skip logging (decision 3):** `CircuitBreaker` gained a `name()` getter (its constructor name already *is* the supplier slug every binding constructs it with); `CircuitBreakingSupplierAdapter::guarded()` takes a `$callType` (+ `$orderId` for the two order-related methods) and dispatches `LogSupplierRequestJob` directly with `outcome=skipped_breaker_open` on an open breaker — bypassing `SupplierRequestLogger` entirely since there's no real HTTP transfer to hook `on_stats` onto.
- **`listProducts` truncation (decision 5):** response sampled to `item_count`/`sample` (first 3 items)/`truncated` when the decoded body's `data` key holds a list; falls back to storing the (redacted) body as-is for any non-list shape rather than guessing.
- **Real gap found and fixed before this was considered done, not shipped silently:** Horizon's supervisors (`config/horizon.php`) explicitly list which queue each one processes (`supervisor-orders` → `orders`, etc.) — the new `LogSupplierRequestJob`'s `supplier-request-logs` queue had no supervisor at all, so every dispatched job would have sat forever unprocessed with zero error, discovered only by trying to verify a real log row appear in the UI (a `php artisan queue:work redis --queue=supplier-request-logs --stop-when-empty` foreground drain proved the write path worked before Horizon itself was restarted). Fixed with a new `supervisor-supplier-request-logs` (mirrors `supervisor-backups`' shape, `tries=1`) in both `defaults` and every `environments` entry, plus a `waits` threshold — this is a real, generalizable lesson: **a new queue name needs a Horizon supervisor entry, not just `ShouldQueue` on the job,** the same way a new migration needs a local `php artisan migrate` (AGENTS.md's own second gotcha) — nothing enforces this at write time, it only surfaces as a silently-stuck queue.
- **Second real bug, found live in the same verification pass:** the Request Logs detail modal's "View" button initially passed the `DataTable` row template's own `item` object straight into dialog state (`setDetailLog(row)`, mirroring `BackupsPage`'s working `setConfirmDeleteRun(run)` pattern) — every field came back `undefined` in the dialog despite the same row rendering correctly in the table one line above. Root cause not fully isolated (suspected PrimeReact `DataTable` row-template object not being safe to hold past its own render cycle for a *nested* field like `supplier`, where `BackupRun`'s equivalent case never nests). Fixed by having "View" call `GET /api/middleware/request-logs/{id}` (`RequestLogController::show()`, already built for decision 9) instead of reusing the table's own object — also the more correct design regardless, since it's the canonical single-row fetch rather than trusting whatever the last list response happened to include.
- Test-suite discipline: `GamevionAdapterTest`/`DigiflazzAdapterTest`/`CircuitBreakingSupplierAdapterTest` are deliberately DB-free unit tests (no `RefreshDatabase`) — `LogSupplierRequestJob implements ShouldQueue`, and the test environment's `QUEUE_CONNECTION=sync` (`phpunit.xml`) executes a queued job inline the instant it's dispatched, which broke all three suites the moment adapters started dispatching it (`no such table: suppliers`). Fixed with `Queue::fake()` in each suite's `setUp()` — keeps their DB-free scope intact while still letting new tests assert *that* the right job was pushed with the right shape (`Queue::assertPushed(...)`).
- 17 new backend tests (`SupplierRequestPayloadRedactorTest`, `LogSupplierRequestJobTest`, `RequestLogControllerTest`, `PruneSupplierRequestLogsCommandTest`, plus new cases in the three adapter-level suites above); full backend suite **948/948 green**. `npx tsc --noEmit`/`eslint`/`next build` clean on `admin/`. Browser-verified live end-to-end (not just typechecked): a real `Refresh Balance` click against the real local Gamevion connection → `on_stats` → redacted → queued → drained via `queue:work --once` → row appears in `/middleware/request-logs` → detail modal shows `Authorization`/`X-API-KEY` correctly redacted and the real (unredacted, non-secret) response body.

**Consequence to track:** any future money-panel on this project that shows a "Revenue − Costs = Profit"-shaped breakdown should default to asking which population question 2 asked here — does the reconciliation need to hold, and if so, every line must share one scope — before writing the query, not after a founder notices the numbers don't add up. The Order History table's `—`-for-undelivered convention (decision 5) is new precedent; a future per-order profit display elsewhere should match it rather than inventing a third convention (`RM 0.00` vs. `—` vs. omitting the column).
