# ADR-025: Supplier price-sync sanity guard — floor + swing checks on Gamevion's incoming price (built 2026-08-21)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-08-14 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any code touched)

**Context:** A security audit of the checkout/payment paths (same session) found that Gamevion's raw `price_sen` flows unvalidated into `Package.cost_price`/`reseller_cost_price` at two call sites — `PackagePriceSyncService::propagatePrice()` (the scheduled/manual "Sync All Prices Now" path, ADR-015) and `SupplierProductController::promote()` (the one-time manual admin-promote path) — both only check `price_sen !== null`, no floor or delta-sanity check. `PricingService::calculate()` reads `Package.cost_price`/`reseller_cost_price` directly at checkout time with no re-validation, so a malformed/glitched supplier response (`price_sen = 0`, or an absurd spike) would silently make a live package free, margin-negative, or display an absurd customer-facing price. `SupplierAdapter` is a generic interface — `GamevionAdapter` is the only real implementation today (per `AGENTS.md`), but the vulnerable call sites are supplier-agnostic (they operate on the normalized `SupplierProduct`/`Package` models, never call Gamevion-specific code directly), so this guard automatically covers any future supplier adapter without per-adapter duplication.

This is architecturally adjacent to ADR-015's own Deactivation Detection, which already established a precedent for "supplier data looks wrong, don't silently trust it" — but its mechanism (the Pending Reactivation queue, `PendingReactivationFinder`) is **live-computed**, reconstructed on every call from already-applied state (`is_active=false` + a live re-check against `supplier_products.status_raw`). That pattern doesn't transfer directly here: a price anomaly must be caught *before* it's ever applied, which means the proposed-but-rejected value has to be stored somewhere, not reconstructed after the fact — this ADR's queue is a new, real table, not a query over existing columns.

**Decision:**

1. **Floor check (`price_sen <= 0`) — hard auto-reject, no queue, applies to both call sites.** `cost_price` represents what *we* pay the supplier — it is never legitimately zero or negative (even a supplier promotional item still carries our own delivery/operational cost), so this is treated as an unconditional invariant, not a judgment call. On violation: skip the write entirely, package/package-creation keeps/gets no price change, `Log::error()`, plus a small counter surfaced on an existing Price Sync Center stat card (visibility without building a full audit table for a condition that should structurally never fire). `SupplierProductController::promote()` gains the same floor check it's currently missing (today it only rejects `price_sen === null`, not `=== 0`) — consistency across every write site to `Package.cost_price`, not reliance on the admin's own eyes catching it.

2. **Swing check (`|new - old| / old > threshold`) — new "Pending Price Change" queue, blocks the write until admin review. Threshold 50%, symmetric, config-driven (`PRICE_SWING_THRESHOLD_PERCENT`).** Only applies to `PackagePriceSyncService::propagatePrice()` — `promote()` has no prior `cost_price` to diff against on a first-time creation, so the swing check is structurally inapplicable there. On violation: the price is *not* applied (package's `cost_price` stays at its last-known-good value), a new `pending_price_changes` row is written (`package_id`, `price_sync_run_id`, `old_cost_price`, `proposed_cost_price`, `old_reseller_cost_price`, `proposed_reseller_cost_price`, `status`), and the package is deactivated with a new, distinct `deactivated_reason = 'price_anomaly'` — deliberately **not** `'supplier_sync'`, so `PendingReactivationFinder`'s existing query (which filters specifically on `'supplier_sync'`) never picks these up, keeping the two mechanisms independent.

3. **Symmetric threshold for v1.** A big price *increase* (customer-facing display risk — an absurd price, not a margin loss) and a big price *decrease* (direct margin/loss risk) get the same 50% tolerance rather than an asymmetric one. Simpler for a first cut; revisit with an asymmetric threshold only once real data shows the two directions actually need different tolerances.

4. **Deactivate while pending, not leave active at the old price.** Mirrors Deactivation Detection's own conservative bias ("stop losing margin silently" is that feature's explicit reason for existing, per its own code comment) over the alternative of leaving the package sellable at a possibly-stale price during the review window — especially since this project has no active alerting today (`ADR-019`'s recorded "no Sentry" deferral still holds), so an unreviewed queue item could otherwise sit unnoticed for an unbounded time while the platform keeps selling at what might be a real, unapplied cost increase.

5. **Idempotency — skip re-flagging a package with an unresolved pending item.** If a subsequent sync run re-evaluates a package that already has a `status=pending` row, it skips rather than writing a second pending row — mirrors `PackagePriceSyncService::deactivate()`'s own existing idempotency guard (`if (! $package->is_active) return false`), for the same reason: avoid duplicate/confusing queue entries for one still-unresolved anomaly.

6. **Approve — recompute `reseller_cost_price` from the package's live `markup_percent` at approval time, not whatever was frozen when the anomaly was first flagged.** Matches this codebase's existing precedent (`OrderResendService` recomputes profit from live package values at actual resend time, not request time, ADR-017) — an admin may have edited the markup between flag-time and review-time, and the applied price should reflect the package's real current configuration.

7. **Dismiss — auto-reactivates the package at the old (already-proven-safe) price, bundled into one action.** No separate manual trip to `/admin/games` to flip `is_active` back on required — a rejected anomaly means "the old price was fine all along," which is itself sufficient justification to resume selling immediately.

8. **Admin UI — sixth section on the existing Price Sync Center page**, alongside stat cards / Last Sync Details / Pending Reactivation / Manually Dismissed Packages / Sync History — not a new standalone page. Admins already check this page for sync-related review; a new location would just fragment where "things needing my attention" live.

**Rationale:** The floor and swing checks are deliberately two different mechanisms, not one, because they carry genuinely different risk shapes: a zero/negative price is (per decision 1) never legitimate under any circumstance, so there is no scenario where blocking it costs a real, wanted price change — auto-reject is strictly safe. A large swing, by contrast, *could* be a real, wanted repricing (currency shift, genuine supplier cost change), so silently discarding it the same way the floor check does would risk permanently missing a real cost increase — hence a review gate instead of a silent reject. Decision 4's "deactivate while pending" and decision 2's "new table, not the live-computed Pending Reactivation pattern" both trace back to the same root cause: unlike Deactivation Detection (which reacts to an already-happened, already-safe state — a package going missing from the catalog), a price anomaly must be intercepted *before* application, and this codebase has no active alerting to catch a silently-stale state quickly, so the conservative default (block + take offline) is preferred over the permissive one (apply or ignore + leave active).

**Consequence to track:**
- This ADR records design intent only — no code exists yet, matching this project's own established practice for design-only ADRs (`ADR-013`/`ADR-015`/`ADR-016`/`ADR-017`/`ADR-018`/`ADR-020`/`ADR-022`/`ADR-024`). Update `docs/prd.md` §14/§15 once this actually ships.
- `pending_price_changes` needs its own migration, model, and (per this codebase's existing append-only audit-table convention — `price_change_logs`/`deactivation_logs`/`order_resend_attempts`) rows are never deleted, only transitioned through `status` (`pending`→`approved`/`dismissed`) — a permanent audit trail of every anomaly ever flagged, not just the currently-open ones.
- Decision 5's idempotency guard needs to be verified against a genuinely concurrent scenario (two sync runs overlapping) the same way `VoucherRedeemConcurrencyTest`/`OrderFulfillmentService` tests real races, not just sequential-call unit tests — this project's own standing convention for anything touching money-adjacent state under possible concurrent access (`backend/CLAUDE.md`).
- `PRICE_SWING_THRESHOLD_PERCENT`'s 50% default is a first-cut guess, not data-derived — worth revisiting after a few real sync cycles' worth of legitimate price-change data exists.
- Decision 2's new `deactivated_reason = 'price_anomaly'` value means any code that already pattern-matches on `deactivated_reason` (currently just `PendingReactivationFinder`'s `'supplier_sync'` filter) should be audited at build time to confirm none of them accidentally treat the two reasons as equivalent.
- First real sync run after this ships could, in principle, flag several packages at once if Gamevion pushes a genuine batch repricing that happens to cross the 50% threshold on multiple items simultaneously — not a bug, but worth the founder knowing this is possible so a sudden non-zero Pending Price Change count isn't mistaken for a system fault on day one.

**Addendum — swing-check baseline and threshold shape, 2026-08-21 (grilled with the founder, before any code touched, closing the two questions the original grilling session left unaddressed).**

Two follow-up questions surfaced re-reading the original design: (1) does the swing check's "old" value in `|new - old| / old` ever risk being an admin-set price rather than a real prior supplier price, and (2) should the flat 50% threshold gain an absolute-sen floor so a cheap package's rounding-level noise doesn't get treated the same as a real anomaly on an expensive one.

Question 1 resolved by fact, not by decision — a targeted code check (not assumed) confirmed `Package.cost_price` has **no admin-facing write path at all**: `PackageController::update()` only touches `name`, `updateMarkup()` only accepts `markup_percent` and recomputes `reseller_cost_price` from the *existing* `cost_price` without ever letting it be set directly, and `updateStatus()`/`destroy()` don't touch pricing. The only two writers of `Package.cost_price` in the entire codebase are `PackagePriceSyncService::propagatePrice()` (this ADR's own sync path) and `SupplierProductController::promote()` (first-time creation from a `SupplierProduct`). So the swing check's "old" value is, by construction, always a previously-synced-or-promoted supplier price — never an admin override — and the false-positive/false-negative risk this question raised cannot occur. No design change needed; this is recorded here so a future reader doesn't re-raise the same question without checking first.

Question 2 — decided: **keep the threshold as a flat percentage, no absolute-sen floor added.** Same reasoning this ADR already applies to the 50% number itself (decision 3's "first cut, revisit once real data exists") extends to the threshold's *shape*: adding a second config value (a minimum-delta floor) now would be tuning against a guessed risk, not a measured one, before a single real sync cycle has run. If cheap-package noise turns out to be a real, observed problem once `pending_price_changes` has real rows to look at, revisit then — not preemptively.
