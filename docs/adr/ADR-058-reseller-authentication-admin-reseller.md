# ADR-058: Reseller authentication + admin Reseller Management (RES-1..6) — BUILT + LIVE (guard later renamed `reseller`→`affiliate` by ADR-072)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** BUILT + LIVE (58a/58b, merged + deployed; the `reseller` guard was renamed `affiliate` in ADR-072). Original: Accepted (design) — 2026-08-30 (grilled with the founder via `/mattpocock-skills:grilling`, same session as ADR-056)

**Context:**
- No non-admin authentication exists anywhere. `config/auth.php` has one guard (`web`, session, `admin_users` provider); `admin_users.role` is `super_admin | admin`; `admin/` uses Sanctum bearer tokens against that.
- RES-1..6 (PRD §6.7) specify admin reseller CRUD + impersonation, all Phase 2, all unbuilt.
- The reseller portal (ADR-059) needs its own login. Founder decision this session: a **separate reseller portal with its own auth**, and **`/admin` also gets a Reseller Management tab** to register resellers, view their details, and route their domain.
- `PlunkMailer` (`ADR-027`) exists and is wired for transactional email (sender-domain verification still `Pending`).

**Decision:**

1. **New guard `reseller` + provider `reseller_users`** in `config/auth.php`, Sanctum bearer tokens (same mechanism as admin, separate guard). New table `reseller_users` — `id`, `reseller_id` (FK), `name`, `email` (unique), `password`, `is_active`, `last_login_at`, timestamps. One reseller can have multiple staff users from day one — the schema supports it even if the first onboarding creates exactly one.

2. **Resellers never self-register.** An admin creates the `Reseller` row and its first `reseller_user` in `/admin`, and the system emails a **set-password invitation** (Plunk, signed expiring link, mirroring a standard password-reset token flow). Matches PRD's standing "no reseller self-service onboarding" Phase 2 deferral — onboarding is admin-driven; only the password step is the reseller's.

3. **Admin Reseller Management screen (`/admin`, `super_admin` only** — same tier as Settings / Price Sync / Membership config). Covers:
   - **RES-1**: reseller table — business name, contact, active tier + subscription status, earnings balance, orders count, domain status, status, actions.
   - **RES-2**: add reseller — business info, `markup_pct` + `max_markup_pct`, assign initial `reseller_membership_tier`, create first `reseller_user` (triggers decision 2's invite).
   - **RES-3**: edit reseller details, change `max_markup_pct`, change tier (writes a tier-change audit row).
   - **RES-5**: activate / deactivate — deactivate ⇒ the ADR-060 storefront returns 503 and the Cloudflare custom hostname is suspended; existing earnings stay withdrawable; no new orders.
   - **RES-6**: delete — **soft-delete only** (FK on `orders`; history must survive), allowed only when earnings balance = 0 and there is no pending withdrawal; the Cloudflare custom hostname is removed.
   - **`reseller_membership_tiers` CRUD** (ADR-056's admin surface) — its own section on this screen, same `super_admin` gate.
   - Record a manual tier-fee payment / trigger a tier charge (ADR-056 decisions 6/8).
4. **Impersonation (RES-4)** — an admin action that mints a short-lived `reseller`-guard Sanctum token scoped to the target reseller and opens the reseller portal (ADR-059) in an impersonation session. Every request in that session is tagged with the real admin identity + session start/end; the portal shows a persistent "Impersonating {reseller} — acting as {admin}" banner; an audit row is written on start and end. Because the session runs under the real `reseller` guard, `ADR-057`'s tenant scope applies automatically — an impersonating admin sees exactly what the reseller sees, nothing cross-tenant.

5. **No maker-checker on reseller CRUD** — solo-founder workflow (`AGENTS.md`); the `super_admin` gate + audit rows are sufficient. Withdrawals (ADR-059) keep the existing WTH maker-checker because that moves money out.

6. **Reseller-guard routes get their own throttle prefix from day one** (`throttle:*,*,reseller-login`, etc.) — `ADR-021`'s addendum documents the shared-throttle-bucket bug class this codebase has already hit twice.

7. **PrimeReact-Tailwind for every new admin screen** (`ADR-038`) — no hand-rolled TailAdmin primitives in Reseller Management.

**Rationale:** A fully separate guard + user table (decision 1) rather than a third `admin_users.role` keeps the money-critical admin surface and the reseller surface from sharing a session, a token namespace, or a component set where a role check could be missed — the security boundary is worth the extra table. Decision 2 (admin-created, invite to set password) keeps onboarding controlled without the admin ever handling a plaintext password.

**Consequence to track:**
- Design-only. Depends on ADR-057 (the reseller guard is what activates the tenant scope). No dependency on production deployment.
- Sanctum's guard/ability model needs checking at build time — token abilities may be a cleaner way to scope an impersonation token than guard config alone; resolve against the installed Sanctum version's docs, not assumption.
- `foundation-security.md` §1's MFA-before-money-actions mandate is already unmet for admins (`ADR-020` notes it); a reseller portal that can request withdrawals raises the same question for `reseller_users`. Flag it — founder call, not silently skipped.
- The set-password invite reuses Plunk, still pending sender-domain verification (`ADR-027`). Reseller onboarding email is blocked on the same external step as consumer OTP.

**Build addendum — 2026-08-30 (founder decisions):**
- **Split into two PRs.** ADR-058 is unusually large (a guard, `reseller_users`, two audit tables, ~8 admin endpoints, a full PrimeReact screen, impersonation, an invite email). **58a** = the auth foundation, backend only: the `reseller` guard + `reseller_users` + `ResellerUser` model + the `SetResellerContext` middleware that calls `CurrentReseller::activate()` (this is what actually switches on `ADR-057`'s scope in production) + reseller login / set-password / logout / me + reseller-route throttle buckets. **58b** = admin Reseller Management: RES-1..6 endpoints, `reseller_membership_tiers` CRUD, the manual tier-fee record/charge action, RES-4 impersonation (+ its audit table), the Plunk invite send, and the `admin/src/app/admin/resellers/` screen. `resellers.deleted_at` (soft-delete) + the tier-change audit table land in 58b with the features that use them.
- **MFA for `reseller_users`: deferred**, matching the already-unmet admin MFA gap (`ADR-020`, `foundation-security.md` §1). The portal withdrawal path keeps the existing WTH maker-checker (an admin approves every payout) as the compensating control. Recorded as known security debt — resolve alongside the admin MFA gap, not separately.
- **Sanctum guard mechanics:** 58a defines `reseller` as a `driver => 'sanctum'` guard with its own `reseller_users` provider; `auth:reseller` must reject an `admin_users` token (and vice versa). Verify the installed Sanctum v4 tokenable-provider check does this and pin it with a test — do not assume `auth:sanctum` alone separates the two surfaces.
- **`ResellerUser` does NOT use `BelongsToReseller`** (unlike every other reseller-owned table): it is only ever queried by email at login (no tenant context), by Sanctum as the token's `tokenable` (which must not be tenant-constrained or auth resolution breaks), and by the admin (cross-tenant). No reseller-facing "manage my team" query path exists yet. Revisit when ADR-059+ adds one, with a scope that is provably safe against the tokenable load.

The controller additionally **blocks** deleting a tier with an `active`/`grace` subscriber outright. Reseller delete is blocked unless earnings balance = 0 **and** no `pending`/`approved` withdrawal, and the `Platform Owner` row can never be deleted.

The session runs under the real `reseller` guard so ADR-057's tenant scope applies unchanged. Ending a session (or deactivating/deleting the reseller) deletes the `personal_access_tokens` row and closes the audit row. **Deferred to ADR-059:** the persistent "Impersonating {reseller} — acting as {admin}" banner and per-request admin tagging (the portal app doesn't exist yet — 58b's UI shows the minted token + portal URL inline as a stopgap).

**Build addendum — `/set-password` frontend page, grilled 2026-09-05 (gap found the day PR-G's invite links were fixed).** Decision 2's invite email always pointed at `/set-password?token=...&email=...` — a page that has never existed on the `reseller/` app, for either an `Affiliate` or a `Reseller` (wallet) account, since this ADR shipped. The backend half (`POST /api/affiliate/set-password`, `AffiliateAuthController::setPassword()`) was built and tested from day one; only the frontend acceptance page was missed, silently, until a real invite link was clicked. Grilled 1 round (all resolved, no new decision — this is completing an already-specified contract, not opening one):

1. **Error handling accepts the backend's actual granularity, no better.** Laravel's `PasswordBroker` collapses "wrong token", "expired token" (24h TTL, `config/auth.php`), and "already-used token" into one identical response (`422`, `passwords.token` on the `email` field) — there is no way to distinguish them server-side, and building a distinguishing UI would be fake precision. The page shows one generic message: "Link tidak sah atau sudah tamat tempoh. Sila hubungi admin untuk hantar invite baharu." for any `errors.email` response, and the field-level `errors.password` message (weak/mismatched) verbatim for that case.
2. **No Route Handler proxy** — unlike `/login` (which calls `/api/login` through a same-origin Next.js Route Handler because that call sets a session cookie), `set-password` has no server-side state to set. The page calls `POST /api/affiliate/set-password` directly via the portal's existing `apiFetch` helper.
3. **Success flow**: on `200`, redirect to `/login?message=Password+berjaya+ditetapkan` (no auto-login — the endpoint returns no token, and adding one would be new backend scope for a gap-closing PR).
4. **No `owner_type` branching** — confirmed the broker operates purely on `affiliate_users` rows by email/token, with zero visibility into that row's polymorphic `owner_type`/`owner_id` (ADR-072 decision 5). One page serves both an `Affiliate` and a `Reseller` (wallet) invite identically, mirroring `/login`'s existing shared-page precedent.

**Shape:** one `reseller/src/app/set-password/page.tsx` — reads `token`+`email` off the query string, a password + confirm-password form (client-side `min 8` + match check before submit, mirroring the backend's own `min:8|confirmed` rule so a doomed request never round-trips), submits via `apiFetch`, redirects per decision 3 on success. `reseller/src/proxy.ts`'s `isEntryPoint` check gains `pathname === "/set-password"` alongside `/login`/`/impersonate`. No backend change — `AffiliateAuthController::setPassword()` already works, confirmed by direct code read this session, not assumed. Pure build from here — no further grilling needed.

**Built + shipped 2026-09-06** (`feature/adr-058-set-password-page`, PR #108 → staging → prod via release PR #110). Built exactly as the Shape above; `ApiError` gained an optional `errors` field so the page can tell an `errors.email` (bad/expired token) response from an `errors.password` one; `/login` renders the `?message=` success banner then strips it from the address bar. No backend change, no `reseller/` unit-test infra (build + lint + tsc green). **Live-verified in production 2026-09-06**: a real `/admin/resellers` invite link set a password and redirected to `/login` with the success banner; login then worked.

**Addendum — invite acceptance with an old portal session, 2026-09-23 (founder-grilled; fix branch).** The original manual-login decision 3 stands. A different account's presence-only cookie can remain in the browser while the real bearer session is tab-scoped; `proxy.ts` then diverts the post-acceptance `/login` navigation back to `/dashboard`, where a null session used to select the Affiliate nav by default and hang. On a successful set-password call, explicitly end the old portal session (including the gate cookie and tab storage) *before* redirecting to `/login`; do not return/mint a new token. If old-session cleanup fails after the single-use invite succeeds, retry cleanup rather than re-posting the password. A null session must never choose the Affiliate shell or dashboard as its default. Consequence: clearing the shared cookie also ends the optimistic gate for other tabs, matching ordinary logout; each tab must log in again. No backend auth/owner-type semantics change.

**Addendum: RES-4 impersonation stays unrestricted (2026-09-29, founder decision, closed as won't-fix).** The 2026-09-28 audit found that the `impersonate` ability on an impersonation token is minted but never checked. An impersonating `super_admin` can therefore do everything the affiliate can, withdrawals and config changes included, and writes made during a session are logged as the affiliate user, not the real admin. The founder chose to keep this full-access behaviour, with no read-only mode and no per-action attribution. The reasons: `super_admin` is the founder alone, and impersonation is used precisely to act on an affiliate's behalf. The existing `affiliate_impersonation_sessions` audit row records who, when, why and from which IP, along with the 60-minute TTL and the portal banner, and that is judged sufficient. **Re-open trigger:** a second `super_admin` or staff account being given impersonation rights. At that point per-action attribution becomes a real accountability need.
