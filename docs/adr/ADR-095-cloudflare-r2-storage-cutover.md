# ADR-095: Cloudflare R2 storage cutover — gallery images + DB backups, WebP-at-upload, delete referential safety

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted & built — grilled and built same session, 2026-09-14, on `feature/adr-095-r2-storage-cutover`. Both buckets + custom domain + scoped tokens provisioned live via Claude's browser access to the founder's own Cloudflare account (decision "not decided here" below resolved that way, founder's call in the moment). See the build addendum after the Consequence section for what shipped vs. this entry's original decision list.

**Context:**

Both halves of this ADR were parked by founder decision 2026-09-09 ("Cloudflare R2 storage — code prepped, `ImageIngestService` seam + `GALLERY_DISK`; fold in WebP-at-upload") — see `docs/prd.md` §16 and `[[project_cloudflare_r2_storage_backlog]]`. Reopened 2026-09-14 at the founder's own initiative during a routine backlog audit: "sekarang pun kita tiada gambar lagi so bagus untuk kita buat" — i.e. do the cutover now, while real data is still small, not after it accumulates.

**Facts checked against real code/infra before deciding (this grill's own discipline):**

- `ImageIngestService::ingest()` (logo + hero uploads only) already writes/reads/deletes exclusively through `config('filesystems.gallery_disk')` — genuinely a config-only swap for those two paths, exactly as ADR-089's own comment claimed. **`Admin\GalleryImageController::store()` does not use it** — general Gallery uploads go through raw `Storage::store()`, no WebP conversion, no resize, no EXIF-orient. "WebP-at-upload" for Gallery is real new wiring, not a flag flip.
- `GalleryImage.disk` is a **per-row** column (default `'public'`), by original design ("a disk swap never invalidates already-uploaded rows" — the migration's own comment) — old rows were meant to stay on their original disk forever, only new uploads adopt a new one. `AffiliateBranding.logo_path`/`favicon_path` and `HeroSlide.image_path` have no per-row disk column at all — they always resolve via the current `gallery_disk` config, so flipping it moves *every* existing logo/hero URL atomically, with no DB update needed — but any physical file not also copied to the new disk 404s the instant the flip happens.
- No FK exists from `Game`/`HeroSlide`/`AffiliateBranding` to `gallery_images` — admin pastes a copied URL into a plain text field. `GalleryImageController::destroy()` deletes unconditionally today, confirmed by its own doc comment as a deliberate non-goal at build time, not a later-discovered oversight.
- `league/flysystem-aws-s3-v3` (needed for Laravel's `s3`-shaped disk driver, which R2 speaks) is **not installed** — a real composer dependency add, not config-only. An unused `s3` disk block already exists in `filesystems.php` but was never intended for R2 specifically (no R2 endpoint shape) — a new `r2`-named disk is added rather than repurposing it.
- Cost is negligible at this project's real scale: R2 storage $0.015/GB-month, **zero egress fee**, free tier covers 10GB + 1M write + 10M read ops/month. Confirmed live 2026-09-14.
- **R2 is already enabled on the founder's Cloudflare account** (an unrelated existing bucket, `nakhoda-recordings`, for a different project — not touched by this ADR), billing already active ($0.00, still inside the free tier). `pekangame.space` is a zone on the same account (Free plan) — a new custom subdomain (e.g. `cdn.pekangame.space`) is a same-account DNS + R2 custom-domain binding, not a new signup.
- **Architecture, confirmed via SSH against real production:** MySQL is a separate DigitalOcean Managed Database (`....db.ondigitalocean.com:25060`), not on the droplet. The app-level backup zip (ADR-039) is `mysqldump`'d *from* that managed DB but stored only on the droplet's own local disk (`storage/app/private`, `filesystems.backup_disk`, default `local`) — a real single point of failure distinct from (and not covered by) whatever redundancy DigitalOcean's managed-DB tier provides on its own side: if the managed DB has a *human-error* problem (bad migration, accidental delete), the droplet-local backup is the independent recovery copy; if the **droplet** is lost, that copy is lost with it, even though the managed DB itself might be fine. This is exactly the gap ADR-039's own "Consequence to track" flagged in 2026-08-26 and is folded into this ADR rather than raised separately.
- Discovered mid-grill (unrelated to the R2 decision itself, fixed separately — see `fix/backup-restore-test-gtid-privilege`, ADR-039's own 2026-09-14 addendum): the backup restore-test had in fact failed on every production run since go-live, and its failure alert was silently swallowed by `MAIL_MAILER=log`. Both fixed already; noted here only because it's what surfaced the backup-on-droplet risk this ADR now addresses structurally.
- Production gallery/branding data checked directly (read-only SSH), not assumed: **1** real `GalleryImage` row (a 3.9MB PNG) + **2** real `AffiliateBranding` logos (already WebP, via `ImageIngestService`) + **0** `Game`/`HeroSlide` images. Total **3.9MB across 5 files** — small enough that a real one-time migration costs almost nothing, versus accepting a permanent split between an old and a new disk.

**Decision:**

1. **Two separate R2 buckets, not one shared bucket with folder prefixes.** `pekangame-gallery` (public) and `pekangame-backups` (private) — gallery images are public-by-design storefront/catalog content (guest-checkout, ADR-011: every visitor's browser must load them directly, with no concept of an "authenticated" viewer to gate on); DB backups are the opposite, containing order/ledger/admin/wallet data with no legitimate reason for any public read path to exist at all. Splitting the bucket removes the failure mode where one misconfigured public-access setting exposes both; each bucket also gets its own scoped Cloudflare API token (least-privilege, matching this project's existing per-supplier-credential posture, ADR-046).
2. **`pekangame-gallery` is served through a custom domain on the existing `pekangame.space` Cloudflare zone** (`cdn.pekangame.space`), never R2's own `r2.dev` dev subdomain (Cloudflare's own docs mark `r2.dev` unfit for production). `pekangame-backups` gets **no public domain at all** — reachable only via the S3-compatible API using the app's own scoped credentials.
3. **New `r2` Laravel disk(s), not a repurposed `s3` block.** `league/flysystem-aws-s3-v3` is added via composer. Two disk entries (`r2_gallery`, `r2_backups`) so `GALLERY_DISK`/`BACKUP_DISK` can point at their own bucket/credential pair independently — local dev keeps defaulting to `public`/`local` (unset env), unchanged.
4. **Gallery WebP-at-upload reuses `ImageIngestService::ingest()`** (not a second, parallel implementation) — `GalleryImageController::store()` now calls it with `maxEdge=2000` (bigger than hero's 1600, since Gallery serves game art/promo banners that can legitimately need more resolution than a fixed hero slide). Existing input-side validation (`mimes:jpg,jpeg,png,webp,gif`, `dimensions:max_width=5000,max_height=5000`, `max:5120`KB) is unchanged — those bound decoder memory on the *raw upload*, unrelated to the resize target. Output is always static WebP q82, same as logo/hero — animated GIF preservation was considered and dropped (confirmed with the founder: not a real use case today), so an animated source silently becomes a static frame, matching `ImageIngestService`'s existing behaviour for every other path.
5. **Gallery-delete referential safety is warn-and-confirm, not a hard block.** No FK exists to build a real constraint on (decision context above) — `GalleryImageController::destroy()` gains a reverse string-match check against `Game.image_url`/`banner_url`/`seo_og_image`, `HeroSlide.image_url`/`image_path`, and `AffiliateBranding.logo_path`/`favicon_path`. A match surfaces a warning listing what still references the image, requiring explicit admin confirmation to proceed — never an outright block, since an admin legitimately replacing artwork should still be able to delete the old file.
6. **The 3 real existing files get a genuine one-time migration, not a permanent old-disk/new-disk split.** Reverses the letter (not the intent) of `GalleryImage.disk`'s original "never invalidate old rows" design — that design optimized for a world with real accumulated data, which this project doesn't have yet (decision context: 3.9MB/5 files total). The 1 `GalleryImage` row's `disk` column and the physical file are updated together; `AffiliateBranding`'s 2 logo files are copied to the same relative path on the new disk *before* `GALLERY_DISK` flips (no DB change needed there — those URLs are always derived from current config, not stored per-row).
7. **No backup-zip migration.** Existing local backup archives are left to age out under the existing 7d/4w/6m retention (`Spatie\Backup`'s own cleanup, disk-agnostic) rather than being backfilled onto R2 — only new backup runs, after `BACKUP_DISK` flips to `r2_backups`, land there. Cheaper and consistent with ADR-039's own retention design; nothing about an old, soon-to-rotate local zip needs preserving forever.
8. **`next.config.ts`'s `remotePatterns`** in `storefront/`, `admin/`, and `reseller/` (wherever each currently allowlists the backend's own host for images) gains `cdn.pekangame.space`.
9. **This ADR resolves, in one build:** `docs/prd.md` §16's "gallery→WebP + delete referential safety" and "Cloudflare R2 storage" backlog lines, and ADR-039's 2026-08-26 "Consequence to track" flag about the droplet-local single point of failure.

**Rationale:**

Every decision reuses an existing seam rather than inventing one — `ImageIngestService` for WebP (decision 4), the disk-config-per-feature pattern `GALLERY_DISK`/`BACKUP_DISK` already established (decision 3), the scoped-credential posture ADR-046 set for suppliers (decision 1). The public/private bucket split (decision 1-2) isn't a preference call between two similar options — gallery and backup data have fundamentally different, non-negotiable access requirements, and treating them as one bucket with folder-level trust would be a real security regression dressed up as convenience. Doing a real migration for the 3 existing files (decision 6) rather than relying on the original per-row-disk design's built-in tolerance for a permanent split is only correct *because* the real data size is still trivial — the original design remains the right one for a project with real accumulated volume, and this ADR doesn't change it, it just chooses not to lean on it while the cost of not doing so is nearly free.

**Consequence to track:**

- Bucket + scoped-API-token creation + custom-domain DNS binding are founder-facing Cloudflare dashboard steps (same shape as CHIP/Gemini credential provisioning) — confirm with the founder, at the actual build session, whether Claude does these live (browser access to the founder's logged-in Cloudflare was already used and permitted during this grill) or the founder does them via a generated wizard walkthrough. Not decided here — an execution question, not a design one.
- `MYSQL_ATTR_SSL_CA` and this ADR's own new `R2_*`/`GALLERY_DISK`/`BACKUP_DISK` env vars all still owe `.env.example` entries (matches the existing, already-tracked `.env.example` gap in `docs/prd.md` §16).
- No R2 bucket versioning and no Cache-Control tuning beyond Cloudflare's zone default were decided as separate line items — both considered during the grill and judged disproportionate for guest-checkout catalog imagery at this project's current scale; revisit only if a real incident (accidental overwrite, cache-staleness complaint) actually happens.
- Decision 6's migration and decision 4's `ImageIngestService` reuse both touch `GalleryImageController` — build them together, not as two separate PRs, since the second makes the first's "what does a migrated row look like going forward" question trivial (every future upload is already WebP on the new disk).

**Build addendum, 2026-09-14 (same session, `feature/adr-095-r2-storage-cutover` → `staging`).** Built exactly as designed, decisions 1-9 all shipped; three points worth recording where the build touched something the design list didn't spell out:

- **`Game`/hero upload validation gained the same `dimensions:max_width=5000,max_height=5000` guard logo/hero already had** (`UploadGalleryImageRequest`) — not in the original decision list, but a direct, low-risk consequence of decision 4's own reasoning (bounding decoder memory on the raw upload): Gallery's `UploadGalleryImageRequest` had no dimension cap at all before this, an inconsistency with the seam it now shares, closed in passing.
- **Decision 8's `next.config.ts` update confirmed reseller needs no change** — grepped first rather than assumed: `reseller/` renders every branding/hero image via a plain `<img>` tag (`BrandingTab.tsx`, `HeroTab.tsx`), never `next/image`, and its `next.config.ts` has no `remotePatterns` at all today. New `GalleryImageController::references()` (+ `GET /api/gallery/images/{gallery_image}/references`) implements decision 5 — the admin gallery page's existing delete-confirm dialog now fetches this when opened and lists real matches instead of a generic disclaimer; `destroy()` itself is unchanged, still never blocks.
