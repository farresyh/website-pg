**Context:**

The Reseller API (ADR-074, built PR-E, live in prod) is the first surface an external system integrates against. Its docs today are `dedoc/scramble`'s auto-generated OpenAPI reference at `/docs/api` (`viewApiDocs` gate fixed to be guest-reachable 2026-09-09, PR #153) — bare: no endpoint summaries or descriptions, no examples, `price_sen` typed as string in `/v1/catalog` but integer in the order responses, partial error coverage (`POST /v1/orders`'s 422 has no schema at all; no endpoint documents 401/403/429), and it is a *reference viewer*, not a docs *site* — there is nowhere for narrative guides (getting started, idempotency, webhook setup, an error catalog).

The founder's benchmark, from consuming three vendor APIs: **CHIP** (`docs.chip-in.asia` — published OpenAPI, `llms.txt`, sandbox, structured guides + conventions) is the standard to reach; **Digiflazz** (real bilingual docs site, but per-endpoint MD5 signature formulas — the friction that ranks it below CHIP); **Gamevion** (`Authorization: Bearer` **and** `X-API-KEY` — two secrets, thin OAS, no player-validation endpoint) is the standard to avoid. The founder explicitly wants CHIP-tier.

Current auth: a single bearer `reseller_api_keys` credential (`pgrk_<48>`, sha256 at rest, multiple named keys per reseller already supported, rotate/revoke from day one — ADR-074 decision 1). No external partner holds a key in production yet (pre-commercial-launch — suppliers unfunded), so a response-shape change now has zero blast radius.

Not decided here, recorded so it is not silently assumed: **self-serve reseller signup** stays out of scope (a separate, larger decision — payment risk, KYC, auto tier-assignment) → **ADR-085 candidate**. ADR-084 assumes invite-only; the docs carry a "Request access — contact us" page with no form.

**Decision:**

1. **API surface** — keep the four ADR-074 endpoints and add two:
   - **`GET /v1/orders`** — the caller's own order history, cursor-paginated (`?cursor=`, `?limit=` capped at 100, newest first), optional `?status=` (delivery status) and `?created_after=` (ISO 8601) filters, scoped to `wallet_reseller_id`. Returns `{ items: [<order>...], next_cursor: string|null }`. Cursor, not page-number, so a new order landing mid-pagination cannot shift the window.
   - **A delivery webhook** — see decision 4.
   - **Rejected: a player-ID validation endpoint.** It would expose supplier structure, and Gamevion has no such endpoint anyway — order-time validation (ADR-005) remains the answer.

2. **The reseller-private boundary is formalised.** These never appear in any response body or in the docs: `cost_price`, `platform_profit`, the platform's markup, the tier's `markup_percent`, any supplier name or identity, `supplier_package_ref`, `Package.id`, the internal order id, any other reseller's data. (Already the code's discipline — `ResellerApi\OrderController::publicOrder()` + `backend/AGENTS.md`; this pins it as an ADR invariant.) `price_sen` is always the caller's own tier-adjusted price.

3. **Error contract** — every 4xx response is `{ "error": "<STABLE_CODE>", "message": "<human text>" }`. `error` is a stable machine-readable code; `message` stays (an additive modification of ADR-074 decision 3's message-only shape — an external integrator must never parse English prose). HTTP status is used meaningfully:
   - `401` — `MISSING_API_KEY`, `INVALID_API_KEY`
   - `403` — `RESELLER_INACTIVE`
   - `404` — `ORDER_NOT_FOUND`
   - `409` — `IDEMPOTENCY_KEY_CONFLICT`
   - `422` — `VALIDATION_FAILED` (with `details: { <field>: [<message>...] }`), `UNKNOWN_PRODUCT_CODE`, `NO_TIER_ASSIGNED`, `INSUFFICIENT_BALANCE`
   - `429` — `RATE_LIMITED`, plus a `Retry-After` header

4. **Delivery webhook.**
   - `reseller_webhooks` (`reseller_id`, `url`, `secret_hash`, `is_active`) — one endpoint per `Reseller` account, `url` + `secret` self-managed from the portal (admin can also set/read for support). `secret` is generated, shown once, sha256 at rest — the same trust model as the API key.
   - Events: `order.delivered`, `order.failed`, `order.refunded` (a wallet refund on a failed-and-not-retried order).
   - Transport: `POST` JSON, header `X-Hub-Signature-256: sha256=<hmac(secret, rawBody)>` — mirrors `DigiflazzWebhookController`'s inbound scheme. Payload is the same public order shape plus `event`, `event_id` (for the receiver's own idempotency), and `occurred_at`.
   - Delivery: a Horizon job (`DeliverResellerWebhook`, Redis queue per ADR-048), exponential backoff, ~5 attempts over ~1 hour, then `exhausted`. `reseller_webhook_deliveries` records every attempt (`event`, `event_id`, `order_id`, `payload`, `attempts`, `status` pending/delivered/failed/exhausted, `last_response_code`, `next_retry_at`) — a dead-letter view in the portal. Polling `GET /v1/orders/{orderNumber}` stays the backstop.
   - Dispatched **after** the fulfillment DB transaction commits, from `OrderFulfillmentService` — never inside the money-critical transaction.

5. **Idempotency semantics, documented precisely** (the #1 integration foot-gun):
   - Same `idempotency_key` + same payload → the original order, **HTTP 200** (changed from the current 201) + header `Idempotent-Replayed: true`.
   - Same key + a *different* payload → **409 `IDEMPOTENCY_KEY_CONFLICT`**. A hash of the request payload is stored alongside the key (`orders.reseller_api_idempotency_payload_hash`) to detect this — currently undetected.
   - Keys are retained for the life of the order (indefinitely). The docs instruct: one fresh UUID per logical order.

6. **Auth stays a single bearer API key.** No request signing (the Digiflazz friction), no mandatory second secret (the Gamevion pattern — no security gain over one strong opaque token). Hardened around instead:
   - **Optional per-key IP allowlist** (`reseller_api_keys.allowed_ips`, JSON, empty = any IP). Recommended in the docs for server-to-server integrations; never mandatory, so a serverless / shared-infra reseller still works (the same reasoning ADR-074 decision 4 gave for rate-limiting on the token, not the IP).
   - **`reseller_api_keys.last_used_ip`** surfaced in the portal so a reseller spots anomalous use.
   - Blast radius is already bounded by the prepaid wallet (max loss = current balance) and the delivery webhook (fast notification of unexpected orders).

7. **Documentation stack — a Starlight (Astro) site, not the Scramble viewer.**
   - Scramble is kept **only as the spec generator**: `php artisan scramble:export` produces `api.json`, committed into the docs app. A CI job regenerates it and fails on any drift from the committed copy (the ADR-033 lesson).
   - A new `docs-site/` app (Astro + Starlight + `starlight-openapi`, nothing else) renders the committed `api.json` as the reference, alongside hand-written Markdown guides. Deploys on Vercel as the project's **fourth** frontend → **`docs.pekangame.space`**.
   - In production the Scramble route (`/docs/api`) **301-redirects** to `docs.pekangame.space`; the raw spec is served statically as `docs.pekangame.space/openapi.json`.
   - Guardrails for a solo-maintained app: pinned Astro + Starlight versions, dependency-minimal, the docs app builds in CI on every PR.

8. **Documentation content — 11 pages:** Introduction (what it is, invite-only, base URL, environments) · Authentication (bearer key, issue/rotate, IP allowlist, compromise → revoke + reissue) · Your first order (end-to-end: catalog → orders → poll/webhook) · Product codes (`{reseller_code}-{denomination}` / `{reseller_code}-{catalog_code}`, discovered via `/catalog`) · Idempotency & retries · Delivery notifications (webhook setup, signature verification, event shapes, retry, poll fallback) · Wallet & balance (prepaid model, insufficient-balance handling, top-up via portal/contact) · Errors (the full catalog — status + code + meaning + what to do) · Rate limits (60/min per key, `Retry-After`, 429) · Versioning & changelog · API Reference (auto from `api.json`).

9. **Versioning & deprecation policy** (in the ADR and on the docs site): the path carries `/v1`. Additive, backward-compatible changes (new endpoints, new optional fields, new error codes) ship without a version bump. A breaking change means `/v2`, with `/v1` supported for **at least 6 months** after `/v2` GA, a `Sunset` header on `/v1`, and a docs deprecation notice. `info.version` in the spec is the docs revision (semver), not the API version. A dated changelog page.

10. **Portal surface** — webhook URL/secret + the delivery-attempt log + per-key IP allowlist + `last_used_ip` all live in the `reseller/` portal (`:3002`), extending the existing "API Keys" area (ADR-074 PR-E). `/admin/resellers` gains read/set for support.

11. **Four PRs, in order:**
    - **PR-1 — API surface hardening** (the contract must be stable before it is documented): the error-code envelope on every 4xx path; `reseller_api_keys.allowed_ips` + `last_used_ip`; `orders.reseller_api_idempotency_payload_hash`; `price_sen` → integer in `/v1/catalog`; `#[Response]` / summary / description PHP attributes on every endpoint so Scramble emits the full 401/403/404/409/422/429 spec; `EnsureResellerApiKey` enforcing `allowed_ips` and writing `last_used_ip`; the 429 `Retry-After` header + body; the idempotency change (200 + `Idempotent-Replayed`, 409 on payload conflict) in `ResellerOrderPlacementService`. Two migrations. No new endpoints. No compat shim — no external consumer exists yet.
    - **PR-2 — `GET /v1/orders`** (order-list, cursor pagination + filters).
    - **PR-3 — the delivery webhook** (`reseller_webhooks` + `reseller_webhook_deliveries`, `DeliverResellerWebhook` job, the after-commit dispatch hook in `OrderFulfillmentService`, the portal + admin screens).
    - **PR-4 — the docs site** (`docs-site/` Starlight app, `scramble:export` + committed `api.json` + the CI drift-guard + the CI build gate, the 11 pages, the Vercel project + `docs.pekangame.space` DNS, the `/docs/api` → docs-site redirect).
    - PR-1 is mandatory first. PR-2 and PR-3 can run in parallel. PR-4 documents the finished contract.

**Rationale:**

- Documenting a still-loose contract produces docs that go stale immediately — hence PR-1 first, and a stable machine-readable `error` code (not an English `message`) is a hard integration requirement, not a nicety.
- A single bearer key is the modern standard (CHIP, Stripe) and the lowest-friction choice — which is the entire reason CHIP ranks first and the goal here. Signing and mandatory second secrets are the exact patterns that make Digiflazz and Gamevion worse to integrate. The optional IP allowlist adds real protection for the reseller who wants it, at zero cost to the one who can't use it.
- The webhook removes the poll burden and matches CHIP's `success_callback` model; reusing `DigiflazzWebhookController`'s signature scheme keeps one HMAC convention across the codebase.
- Starlight over Scramble's viewer is a deliberate, founder-made trade: it is the heavier option (a fourth Vercel app, a build pipeline, a committed spec that needs a drift-guard, hand-written guides that can go stale) but it is the only one that delivers the CHIP-shaped experience — multi-page guides plus reference plus changelog on an owned domain. The guardrails (pinned versions, minimal deps, CI build + drift gates) are what keep it maintainable by one person.

**Consequence to track:**

- After PR-1, `price_sen`'s type and the replay status code are a committed external contract — any later change is breaking and triggers the decision-9 policy.
- A leaked webhook `secret` lets an attacker spoof delivery events to the reseller's system → `secret` is rotatable, shown once, sha256 at rest.
- `docs-site/` is a fourth Vercel project and a new npm dependency surface for a solo founder — the CI build gate and pinned versions are mitigation, not optional.
- The `docs-site/` name avoids a clash with the existing `docs/` (ADR/PRD) directory.
- ADR-085 candidate: self-serve reseller signup.
- Update `docs/prd.md` §14/§15; retag the "ADR-084 candidate" pointer (§15 item 9) as ADR-084 accepted.
- `config/scramble.php`'s `api_path` already scopes the spec to `api/reseller` only (ADR-074 PR-E) — verify no admin/storefront route leaks after the annotation pass.

**PR-1 build addendum — API surface hardening, 2026-09-10 (`feature/adr-084-pr-1-api-hardening`, PR to `staging`).** Shipped exactly the decision-11 PR-1 list, plus the `/v1/catalog` game-grouping decided in the pre-build recap (a breaking reshape, and the last free moment for one — no external consumers).

- **Error envelope (decision 3).** New `App\Exceptions\ResellerApi\ResellerApiException` — one class, named constructors, each carrying a stable `errorCode` + HTTP status + optional `details`. A single `$exceptions->render()` closure in `bootstrap/app.php` renders it everywhere, and on the `api/reseller/*` path also maps the framework exceptions it can't throw itself: `ValidationException` → `422 VALIDATION_FAILED` with `details: {field: [msg]}`, `ThrottleRequestsException` → `429 RATE_LIMITED` **carrying the framework's own `Retry-After` header through** (`->withHeaders($e->getHeaders())`), `NotFoundHttpException`/`MethodNotAllowedHttpException` → `404 NOT_FOUND`/`405 METHOD_NOT_ALLOWED`. Controllers/middleware now `throw` instead of `response()->json([...], 4xx)`. Codes: `MISSING_API_KEY`/`INVALID_API_KEY` (401), `RESELLER_INACTIVE`/`IP_NOT_ALLOWED` (403), `ORDER_NOT_FOUND` (404), `IDEMPOTENCY_KEY_CONFLICT` (409), `VALIDATION_FAILED`/`UNKNOWN_PRODUCT_CODE`/`NO_TIER_ASSIGNED`/`INSUFFICIENT_BALANCE` (422), `RATE_LIMITED` (429).
- **Idempotency (decision 5).** Migration `orders.reseller_api_idempotency_payload_hash` (nullable — API only). `ResellerOrderPlacementService::placeOrder()` now returns `ResellerOrderPlacementResult { Order $order, bool $wasReplay }` (was a bare `Order`); the Bot caller reads `->order`, the dev/testing command too. A replay with the **same** key + payload → HTTP **200** + header `Idempotent-Replayed: true` (was 201); **same** key + **different** payload → **409** via the channel-neutral `IdempotencyKeyPayloadMismatchException` (the API controller maps it). Payload hash = `sha256(json_encode([product_code, player_id, server_id]))`, computed in `OrderController` and threaded through `ResellerOrderPlacementRequest` → `OrderDraft` → `OrderFactory`. `assertPayloadMatches()` is a no-op when either hash is null (Bot channel, or a pre-existing order), so it never affects the Bot path.
- **IP controls (decision 6).** Migration `reseller_api_keys.allowed_ips` (json, nullable/`[]` = any IP — opt-in) + `last_used_ip`. `EnsureResellerApiKey` resolves the key (stamping `last_used_at` + `last_used_ip` — the stamp lands even on a request the allowlist then rejects, which is the anomaly signal), checks `is_active`, then exact-match `allowed_ips` against `$request->ip()` (Cloudflare-trusted proxies already give the real client IP, `bootstrap/app.php`). CIDR ranges deferred — exact match covers the server-to-server case; note it in the docs.
- **`price_sen` (decision 4).** `/v1/catalog` reshaped from a flat `{ items: [...] }` to `{ games: [{ code, name, packages: [{ code, name, price_sen }] }] }` — `code`/`name` are the game's public `reseller_code` + name (never `id`/`slug`/image). `price_sen` cast `(int)` in both the catalog and order responses; Scramble now infers `integer` for it. No tier name/`markup_percent` is exposed anywhere (decision 2) — deferred as a future additive field on `/v1/balance` if a reseller asks.
- **Scramble annotations (decision 11).** `#[Endpoint(title, description)]` + `#[Response(status, description, type: 'array{error: string, message: string}', examples: [...])]` on all four methods. `php artisan scramble:export` verified: every endpoint emits `200`/`201` + its full `401/403/404/409/422/429` set with proper `{error, message}` object schemas; `config/scramble.php`'s `api_path` still confines the spec to `api/reseller/*` (no admin/storefront leak).
- Tests: `+12` — `ReviewCatalogControllerTest` untouched; new `EnsureResellerApiKeyTest` (allowlist: empty/null = any, on-list pass, off-list 403 + `IP_NOT_ALLOWED`, IP recorded on rejection); `ResellerApiKeyServiceTest` +2 (`last_used_ip`); `ResellerOrderPlacementServiceTest` +2 (payload-hash conflict, null-hash never conflicts) + result-DTO updates; `OrderControllerTest`/`CatalogControllerTest` rewritten for the envelope + grouped shape (`409` conflict, `Idempotent-Replayed` header, every error code asserted). Full fast suite **1655/1655**, full concurrency **13/13** (real MySQL), Pint clean, `scramble:export` clean. Local dev DB migrated.

**PR-3 build addendum — the delivery webhook, 2026-09-10 (`feature/adr-084-pr-3-delivery-webhook`, PR to `staging`).** Delivers decision 4 (and decision 10's portal/admin surface for it). Two deliberate deviations from decision 4's literal wording, both recorded below; the founder pre-approved both in the pre-build recap. Not re-grilled — same outcome, better seam.

- **Deviation 1 — `secret` is `encrypted` at rest, not sha256-hashed.** Decision 4 said "sha256 at rest" by analogy with the API key. But the API key is verify-only (client sends it, we hash-and-compare — `ResellerApiKeyService`); the webhook secret is *sign*-only — every outbound `DeliverResellerWebhook` must reproduce the plaintext to compute `hmac-sha256(secret, rawBody)`. A hash cannot be un-hashed, so hashing it would make signing impossible. Stored `encrypted` (Laravel cast) on `ResellerWebhook`, `$hidden`, shown to the reseller exactly once at set/rotate time — the identical trust model `Supplier.api_config` (Digiflazz/OpenWA inbound webhook secrets) and `AdminUser.mfa_secret` already use for the same "we need the plaintext later" reason.
- **Deviation 2 — `order.delivered` / `order.failed` dispatch from an `OrderStatusUpdated` listener, not an explicit call inside `OrderFulfillmentService`.** Decision 4 said "from `OrderFulfillmentService`". Instead a new queued listener `DispatchResellerOrderWebhook` rides the ADR-047 single seam (`OrderObserver` → `DB::afterCommit` → `OrderStatusUpdated`) — the exact seam `SendResellerBotOrderNotification` already uses for the Bot channel's terminal-state message. The "dispatched after the fulfillment transaction commits, never inside it" guarantee (decision 4) comes for free, and every `delivery_status` writer (fulfil, finalize-pending, mark-delivered-manually, Resend) is covered without touching any of them. `order.refunded` is NOT on this path — `Admin\OrderController::refundToWallet()` deliberately never changes `delivery_status` (ADR-076 decision 6), so it calls `ResellerWebhookDispatcher` directly, right next to the existing Bot refund-notice block.

- **Schema — two migrations.** `reseller_webhooks` (`reseller_id` unique — one endpoint per account, `url` ≤2048, `secret` text/encrypted, `is_active`). `reseller_webhook_deliveries` (`reseller_id` FK, `order_id` FK, `event`, `event_id` uuid, `payload` json, `attempts`, `status` pending|delivered|failed|exhausted, `last_response_code`, `next_retry_at`; index `(reseller_id, created_at)` for the dead-letter list; **`unique(order_id, event)`** — the structural guarantee a reseller never gets a duplicate `order.delivered`/`.failed`/`.refunded` for one order). Both FK columns keep a usable standalone index (the unique's leftmost column / the composite's leftmost column). Local dev DB migrated; concurrency suite green on real MySQL.
- **Event → dispatch → job.** `ResellerWebhookEvent` enum (`order.delivered`/`order.failed`/`order.refunded` — the string values are the external contract). `ResellerWebhookDispatcher::dispatch(Order, Event)` — no-ops unless the order is `wallet_reseller_id`-owned and its reseller has an `is_active` webhook; `firstOrCreate`-style dedupe on `(order_id, event)` guarded by the DB unique (a lost race → `UniqueConstraintViolationException` caught, treated as already-queued); builds the flat payload `{...ResellerOrderPayload, event, event_id, occurred_at}`; queues `DeliverResellerWebhook`.
- **`DeliverResellerWebhook`** — own `reseller-webhooks` queue + Horizon `supervisor-reseller-webhooks` (ADR-048 decision 3 isolation — a slow/hanging/5xx-ing reseller endpoint must never head-of-line-block an order job). `$tries = 5`, `backoff() = [60, 300, 900, 1800, 3600]` (~1 hour). POST with `X-Hub-Signature-256: sha256=<hmac>` (+ `X-Webhook-Event`, `X-Webhook-Id`), 10s timeout / 5s connect. Updates the delivery row every attempt (`attempts`, `last_response_code`, `status`, `next_retry_at`); 2xx → `delivered`, non-2xx / connection error → `failed` + rethrow to retry, `failed()` hook → `exhausted`. Endpoint removed/disabled since queueing → `failed`, no retry.
- **`ResellerOrderPayload` extracted** — `ResellerApi\OrderController::publicOrder()` (private static) moved verbatim to `App\Support\ResellerOrderPayload::for()`; the API controller and the webhook body now share one shape (decision 2's reseller-private guarantees in one place). No spec change — `scramble:export` byte-identical.
- **Portal (`reseller/` :3002)** — `ResellerPortal\WebhookController` (show / store+update-url / rotate-secret / status / destroy / deliveries-paginated), HTTPS-only `url` FormRequest. Folded into the existing **API Keys** screen as a "Delivery webhook" panel (decision 10 — extend that area, not a new nav item): URL field, secret-shown-once banner (mirrors the API-key block), pause/resume, remove, recent-deliveries table.
- **Admin (`admin/` :3000)** — `Admin\ResellerWebhookController` (same actions, super_admin, `/admin/resellers/{reseller}/webhook*`), `ResellerWebhookModal.tsx` off the resellers page's row actions (mirrors `ResellerApiKeysModal`).
- **Not built here (deferred to PR-4, done there):** the per-key **IP allowlist** portal/admin *UI*. PR-1 shipped the `reseller_api_keys.allowed_ips` + `last_used_ip` columns and `EnsureResellerApiKey`'s enforcement; the self-service editor landed in PR-4 (founder's call).
- Tests: `+44` — `ResellerWebhookServiceTest` (create/rotate/active/remove, secret encrypted-not-hashed at rest, `sign()` scheme), `DeliverResellerWebhookTest` (signs, records each attempt, 2xx→delivered, 5xx→retry, `failed()`→exhausted, inactive→failed-no-throw, already-delivered no-op), `DispatchResellerOrderWebhookTest` (delivered/failed fire; needs_review / non-wallet / no-webhook / inactive don't; once-per-(order,event) dedupe; wired to the real `OrderStatusUpdated`), `OrderControllerTest` +2 (`refund-to-wallet` queues `order.refunded`, no-op without a webhook), portal + admin controller tests (CRUD, ownership scoping, HTTPS-only, `account.type` gate). No subprocess concurrency test — a webhook is a notification, not money (same call the Bot listener makes). Full fast suite **1699/1699**, concurrency green, Pint clean, both frontends `build` + `lint` clean.
- **Forge:** `supervisor-reseller-webhooks` is a new Horizon supervisor — it starts automatically with the existing `php artisan horizon` daemon on deploy (no separate process/‌compose change, Horizon manages its own worker count).

**Addendum — delivery-webhook SSRF guard, 2026-09-29 (Wave 3 S-3; decided without a grill, standard SSRF practice).** PR-3 decision 4's webhook POSTed to whatever HTTPS URL the reseller saved, following redirects — so a URL pointing at (or redirecting to) `127.0.0.1`, the droplet's private network, or DigitalOcean's `169.254.169.254` metadata service made our own server call it, with `last_response_code` visible in the portal as a status-code oracle. Decisions: (1) new `App\Support\OutboundUrlGuard` — a URL is callable only if its host (an IP literal, or **every** address its A/AAAA records resolve to) passes PHP's `FILTER_FLAG_GLOBAL_RANGE` (rejects loopback, RFC 1918, link-local, CGNAT, reserved, ULA, IPv4-mapped); unresolvable = rejected. (2) Checked **at save** (a closure rule shared by the portal and admin `Store*WebhookRequest`s) **and again at send** (DNS can be repointed after saving). A send-time failure is terminal (`failed`, no retry, warning logged) — an internal target never becomes safe by retrying. (3) The send pins curl to the exact address the guard approved (`CURLOPT_RESOLVE`), closing the check-then-connect DNS-rebinding window; verified against a real request, not just `Http::fake`. (4) Redirects are no longer followed — a 3xx is a non-2xx failure like any other. Existing saved URLs are not migrated or notified: no external resellers exist yet, and a now-invalid endpoint simply fails at send with a log line. Tests swap DNS via `TestCase::fakeOutboundDns()` since `*.test` hosts never resolve.
