# ADR-069: Digiflazz supplier hardening — inbound webhook, credential-rotation surfacing, raw-price visibility, balance freshness

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-09-03, grilled with the founder this session via `/mattpocock-skills:grilling` (11 questions over two rounds), before any code touched. **Builds the `DigiflazzWebhookController` half of [ADR-032](./ADR-032-async-supplier-delivery.md) decision 4** that ADR-067 explicitly deferred, and closes four adjacent gaps ADR-067's consequences flagged. **Modifies ADR-032 decision 4** (the IP-allowlist detail) and **modifies [ADR-046](./ADR-046-supplier-management-screen.md) decision 3** (adds a post-save connection probe).

**Context:**
- Consumer top-up delivery through Digiflazz is live-capable but never proven end-to-end against a funded account (both suppliers sit at ~0 balance — Digiflazz `deposit: 0` confirmed 2026-09-02). The founder wants the supplier seam genuinely solid — and easy to debug — *before* funding a deposit and spending real money on a test order, so that a real-order failure lands on a strong, observable foundation rather than a half-built one.
- **Async delivery finalization is only half-built.** ADR-032 decision 4 designed a thin per-supplier `DigiflazzWebhookController` (verify `X-Hub-Signature`, map `ref_id` → order, call `OrderFulfillmentService::finalizePendingDelivery()`); it was deferred through ADR-032's own build, again in ADR-067. The **poll backup exists and works**: `ReconcilePendingDeliveriesCommand::checkStalePending()` dispatches `CheckSupplierDeliveryJob` for a stale `Pending` order, which re-submits `checkStatus()` and routes the outcome through the same `finalizePendingDelivery()`. So a `Pending` Digiflazz order *does* resolve today — within `pending_stale_minutes` (default 10) + the reconcile cadence. The webhook makes it near-instant and, more importantly, gives an inbound audit trail (exactly what Digiflazz reported, and when) that the poll path cannot.
- **The real Digiflazz buyer webhook shape** (re-read `developer.digiflazz.com/api/buyer/webhook/` this session): `POST` to the URL set in *Atur Koneksi > API > Webhook*. Headers — `X-Digiflazz-Event` (`create` = new transaction, `update` = status change, `resend` = hotel only), `User-Agent` (`Digiflazz-Hookshot` = prepaid, `Digiflazz-Pasca-Hookshot` = postpaid, `Digiflazz-Hotel-Hookshot` = hotel), `X-Hub-Signature: sha1=<hex>` = `hash_hmac('sha1', $raw_body, $webhook_secret)`, **present only when a webhook secret is configured** in the panel. Prepaid payload is a `{data: {...}}` envelope: `ref_id` (= our `reference_number`), `customer_no`, `buyer_sku_code`, `message`, `status` (`Sukses`/`Pending`/`Gagal`), `rc`, `buyer_last_saldo`, `sn`, `price`, `tele`, `wa`. The webhook doc does **not** publish a source IP; the `52.74.250.133` in ADR-032 decision 4 is the Digiflazz IP named in their API-setup docs (the founder confirmed it exists there), not in the webhook spec.
- `orders.reference_number` is `nullable`, **globally `unique`** (not per-supplier), assigned once delivery starts. `ChipWebhookController` is the existing webhook precedent: no `auth:sanctum` (the signature check *is* the auth), `throttle:120,1,webhook-chip`, `payment_status` update done inline, only the supplier call (`FulfillOrderJob`) queued. `finalizePendingDelivery()` is itself a `DB::transaction()` + `lockForUpdate()` + `creditProfit()` + `vouchers->commit()`, idempotent (a second call observes the finalized state and throws `InvalidOrderTransitionException`), and `CheckSupplierDeliveryJob` already catches that exception as an expected race outcome.
- **`Supplier.balance` is only ever refreshed by an admin clicking "Refresh Balance"** (`SupplierController` — `checkBalance()` → `$update['balance']`). Nothing scheduled. The Dashboard Health panel shows `Supplier.balance` verbatim — it can be days stale. Every Digiflazz delivery webhook carries `buyer_last_saldo` (balance after the transaction) for free.
- **`ADR-046` decision 3's masked-field merge** (`array_merge($supplier->api_config ?? [], $data['api_config'])` after the FormRequest strips blank secrets) is the kind of path a *key rotation* can silently no-op through — an admin enters a new `api_key`, it fails to persist for any reason, and the adapter keeps using the old one with no signal until an order fails. ADR-067's own consequence flagged this as "worth a follow-up look, not fixed here."
- **Raw supplier price is stored only as converted MYR sen** (`supplier_products.price_sen`); the original amount + currency (Digiflazz `price` in IDR, Gamevion's own source value) is discarded. ADR-067's consequence: a "Rp 20,000 = RM 4.56" sanity line in the Product Manager would need `raw_price` + `raw_currency` columns — "a tracked backlog item, not this ADR." This ADR picks it up.
- The founder also wants a **historical ledger of supplier deposits** (date, IDR amount, MYR cost, FX rate at the time, running balance) for finance tracking. That is a cross-supplier finance feature with its own design surface (manual vs auto-detected entries, `ledger_entries` vs its own table, interaction with owner-profit reporting, FX source) — **out of scope here, tracked as a future ADR** (see Consequences).

**Decision (each point grilled this session):**

*Packaging*

1. **One ADR, three PRs off `staging`.** PR-1 = the webhook controller + `webhook_secret` config + concurrency test (money-path, the critical piece). PR-2 = `raw_price`/`raw_currency` columns + the credential-rotation probe (debuggability/safety, no money-path change). PR-3 = scheduled balance refresh + low-balance visibility. **Explicitly out of scope:** Digiflazz price-change / postpaid / hotel webhook events; a Gamevion webhook; any new alerting platform (use `Log` + the existing Dashboard); the supplier-deposit finance ledger.

*PR-1 — inbound webhook*

2. **`POST /api/webhooks/digiflazz`**, `throttle:120,1,webhook-digiflazz`, route name `webhooks.digiflazz`, no `auth:sanctum` — mirrors `ChipWebhookController` exactly. A thin controller: verify, resolve the order, hand off to `finalizePendingDelivery()`, return.

3. **Auth is signature + IP, both hard gates.**
   - `X-Hub-Signature` must equal `'sha1='.hash_hmac('sha1', $request->getContent(), $secret)` where `$secret = Supplier` (slug `digiflazz`) `api_config['webhook_secret']`. Mismatch or missing header → `401`.
   - The request IP must be in `config('services.digiflazz.webhook_ips')` (an array, default `['52.74.250.133']`, env-overridable) — **config-driven, not hardcoded in the controller**, so Digiflazz adding an IP is a config change, not a deploy. IP not in the list → `403`.
   - `webhook_secret` absent from `api_config` → reject **every** call (`503` + `Log::warning`) — no window where unverified payloads are accepted.
   - This **modifies ADR-032 decision 4**: the IP allowlist is kept (the founder's call) but demoted to a config-driven second gate behind the signature, not the primary mechanism.

4. **Order match:** `Order::query()->where('reference_number', $data['ref_id'])->first()`.
   - Not found → `404` + `Log::warning` (the daily reconcile poll is the backstop — nothing is lost, only delayed).
   - Found but `order->supplier->slug !== 'digiflazz'` → `409` + `Log::error` (defence against a `reference_number` collision across suppliers, cheap even though the column is globally unique).
   - Found but `$data['buyer_sku_code'] !== $order->supplier_product_ref` → `409` + `Log::error` (the amount-mismatch analogue from `ChipWebhookController`). `customer_no` is **not** cross-checked — per-game normalization can legitimately differ.

5. **Event handling:** process **both** `X-Digiflazz-Event: create` and `update` (identical, idempotent logic). Ignore `resend`. Check `User-Agent` contains `Digiflazz-Hookshot` — **soft**: `Log::warning` on a mismatch but still process (the signature is the real gate).

6. **Outcome routing** (on `$data['status']`):
   - `Sukses` → `finalizePendingDelivery($order, SupplierOutcome::Success, $data['sn'] ?? null, $data)`.
   - `Gagal` → `finalizePendingDelivery($order, SupplierOutcome::Failure, null, $data)`.
   - `Pending`, or any other value → acknowledge `200`, no-op.
   - `finalizePendingDelivery()` throws `InvalidOrderTransitionException` (order already finalized synchronously, or by the poll, or by a prior webhook delivery) → **catch it**, acknowledge `200` `{"message":"already finalized"}`, no-op. Same reasoning `CheckSupplierDeliveryJob` already uses.
   - **Finalize runs inline in the request** — unlike `ChipWebhookController`'s `FulfillOrderJob` dispatch, `finalizePendingDelivery()` makes no external call, so there is nothing to move off the request thread; its own lock + idempotency already hold. (A future customer-notification on finalize would be the queued part, not the finalize itself.)

7. **Balance fold-in:** on a `Sukses` webhook, write `$data['buyer_last_saldo']` to `Supplier.balance` (slug `digiflazz`) — same column `checkBalance()` writes, last-value-wins, no history. Keeps the Dashboard Health figure fresh for the one supplier that actually has live traffic.

8. **`webhook_secret` lives in `SupplierConfigSchema::OPTIONAL['digiflazz']`** (type `secret`), **not** `REQUIRED` — it is irrelevant to outbound API calls (`createOrder`/`checkBalance` work without it), so it must not block the "fully configured" gate or the adapter binding. The admin Supplier form renders it (masked, merge-on-save, per ADR-046 decision 3); `SUPPLIER_FIELD_DEFINITIONS` (frontend) is updated by hand in the same PR. The Suppliers screen shows a "Webhook not configured" warning chip when the key is absent.

9. **Concurrency test:** `tests/Concurrency/DigiflazzWebhookReconcileConcurrencyTest.php` (mirrors `MembershipCheckoutWebhookReconcileConcurrencyTest` / `OrderFulfillmentServiceConcurrencyTest`, real MySQL, `DatabaseMigrations`): a webhook `Sukses` and a `CheckSupplierDeliveryJob` for the same `Pending` order hit `finalizePendingDelivery()` concurrently → exactly one transition, one `creditProfit()`, one `vouchers->commit()`, order ends `Delivered`. Plus feature tests: bad signature → 401, unknown IP → 403, missing secret → 503, unknown `ref_id` → 404, wrong supplier → 409, `buyer_sku_code` mismatch → 409, `Sukses` → `Delivered` + balance written, `Gagal` → `Failed`, `create` vs `update` parity, already-finalized → 200 no-op, `Pending` status → 200 no-op.

*PR-2 — raw price + credential-rotation surfacing*

10. **`supplier_products` gains `raw_price` (decimal, nullable) + `raw_currency` (string(3), nullable)** — no index (display-only, never filtered/queried). `SupplierCatalogItem` gains `rawPrice` + `rawCurrency`; **each adapter fills them from its own catalog shape** (`DigiflazzAdapter`: `price` + `'IDR'`; `GamevionAdapter`: its pre-conversion value + that currency). `ProductSyncService` writes `$item->rawPrice` / `$item->rawCurrency` with **no per-supplier branching**. **Forward-only** — populated on the next sync of each row, no backfill (the scheduled sync runs often; a backfill would add a one-off script for no lasting value). The Product Manager shows `raw_price raw_currency` under the converted MYR price when present. FX conversion itself is unchanged — this is a visibility line, not a correction; ADR-033's rate handling is not reopened.

11. **After any `api_config` change, `SupplierController::update()` runs a `checkBalance()` probe and returns its result** — `{ connection_ok: bool, balance: number|null, error: string|null }` — which the Supplier form surfaces ("Credentials saved — connection OK, balance Rp X" / "Saved, but the connection failed: rc 45"). **Not** a hard block on saving (a founder may deliberately save a partial config). Applies to `digiflazz` **and** `gamevion`. This **modifies ADR-046 decision 3** — the merge behaviour is unchanged, but a silently-broken credential now shows immediately instead of only at the next order.

*PR-3 — balance freshness + low-balance visibility*

12. **`app:refresh-supplier-balances`** — a new console command, `daily()` in `routes/console.php` (same inert-until-real-cron pattern as the other scheduled commands; on Forge the scheduler is live). Loops active, fully-configured suppliers, calls `checkBalance()` (read-only — calling the adapter directly from a scheduled command is fine here, the same footing as the smoke tests; `CircuitBreakingSupplierAdapter` + `TransientFailureRetryPolicy` already wrap it), writes `Supplier.balance`, and emits `Log::warning('supplier balance low', [...])` when the balance is below `api_config['low_balance_threshold']`.

13. **`low_balance_threshold`** in `SupplierConfigSchema::OPTIONAL` for **both** `digiflazz` and `gamevion` (type `text` — a bare number in the supplier's own balance currency). Absent/empty = no low-balance warning at all (fail-safe to silent, never to false alarms). The Dashboard Health supplier row shows a yellow "Low balance" chip when `Supplier.balance` is set and below the threshold — no new UI surface, no new alert channel.

**Rationale:** The webhook is the one designed-but-unbuilt piece of the async-delivery path, and it is a new *caller* of an already concurrency-proven method (`finalizePendingDelivery()`), not new money-path logic — the same shape ADR-032 anticipated and `ChipWebhookController` already demonstrates. Keeping the IP allowlist config-driven and the secret optional-in-schema respects the two real constraints (Digiflazz can rotate IPs; the webhook secret is orthogonal to outbound auth) without weakening the signature gate. The three non-webhook items are each a direct answer to a consequence ADR-067 already recorded, are cheap (two nullable columns, one probe call, one daily command), and touch no money path. The deposit-history ledger is genuinely bigger and cross-cutting — separating it keeps this ADR shippable before the funded test order.

**Consequence to track:**
- **ADR-032 decision 4's IP detail is now config-driven and secondary to the signature.** If Digiflazz starts sending webhooks from an IP not in `config('services.digiflazz.webhook_ips')`, deliveries `403` silently until the config is updated — the daily reconcile poll is the backstop (orders still finalize within ~a day), but watch the `webhooks.digiflazz` 403 log line after go-live.
- **New migration** (`supplier_products.raw_price` / `raw_currency`) — run **plain `php artisan migrate`** against the local dev DB, not just the test suites (`backend/AGENTS.md` gotcha). No new index, but confirm the two columns land.
- `webhook_secret` and `low_balance_threshold` must be added to **both** `SupplierConfigSchema` (PHP) and `SUPPLIER_FIELD_DEFINITIONS` (`admin/src/lib/suppliers.ts`) — they are mirrored by hand, per `SupplierConfigSchema`'s own doc comment.
- The webhook controller change is money-adjacent: the concurrency test (decision 9) is the gate. It must also prove a webhook for a *non-Digiflazz* order (Gamevion, same `reference_number` value forced) is rejected `409`, not mis-finalized.
- `finalizePendingDelivery()` is called with `$data` (the raw webhook `{data:...}` body) as `supplier_response` — confirm the existing `Order.supplier_response` cast/column handles it and that `sn` / `price` (informational only — profit is never computed from the webhook, exactly as the synchronous path never trusts the supplier's echoed price) are stored, not acted on.
- **Supplier deposit & cost-of-inventory ledger** (date, IDR in, MYR cost, FX rate, running balance history) — the founder's finance-tracking ask, deferred here. Its own ADR: entry mechanism (manual admin vs balance-jump detection), storage (`ledger_entries` type vs a dedicated `supplier_deposits` table), owner-profit-report interaction, FX source. Tracked in `prd.md` §15.
- PRD §14 build-log + §15 status (Supplier Adapter / Middleware Panel rows) update owed on each PR ship. `docs/prd.md` §13 Glossary may want a "supplier deposit" term once ADR-070 lands.

**Stress-test addendum — 2026-09-03, same session, re-grilled via `/mattpocock-skills:grilling` (8 findings, 1 round)**, per this ADR's own "stress-test before built" instruction. All folded into the 3 PRs (as a follow-up commit on the PR-3 branch); none reopens the scope.

- **Q1 (changes decision 3) — the IP allowlist is now a SOFT signal, not a gate.** `DigiflazzWebhookController` logs a warning for an unlisted source IP but **still processes** (the HMAC signature already passed). Rationale: `$request->ip()` stops being the real client IP the instant anything sits in front (the planned Cloudflare-for-SaaS migration, a load balancer), and a hard 403 there is a silent webhook outage that only the ~10-min poll would paper over. An empty `services.digiflazz.webhook_ips` disables the check entirely. **Added to the ADR-060 migration checklist:** wire `CF-Connecting-IP` / trusted-proxy handling for `/api/webhooks/*` before the Cloudflare cutover.
- **Q2 — a 404 from `/api/webhooks/digiflazz` is BENIGN and expected.** `fulfill()` writes `reference_number` and calls Digiflazz inside one `DB::transaction()`, so a `create` event racing that uncommitted transaction finds no row. The `update` event (post-commit) or the reconcile poll finalizes it. Softened `Log::warning('Rejected …')` → `Log::info('… a create event likely raced fulfillment …')`; noted in the controller docblock. Monitoring must not alarm on 404s here.
- **Q3 (tightens decision 11) — a `CIRCUIT_OPEN` probe result is not a credential failure.** `probeConnection()` detects `errorCode === 'CIRCUIT_OPEN'`, returns `breaker_open: true` with distinct wording ("check skipped — breaker open from earlier failures"), and does **not** stamp `last_test_result`. The Edit form shows it as a neutral "Credentials saved. …" not an amber "connection check failed". The modal already shows a "Saving…" state during the (synchronous) probe. A dedicated shorter probe timeout was considered and dropped — it needs a `SupplierAdapter` interface change for marginal gain; the breaker-open case already returns instantly, and a genuinely dead supplier taking ~13s to surface is acceptable.
- **Q4 (tightens decision 10) — the Product Manager only renders the raw-price line when a real conversion happened.** Hidden when `raw_currency` is null, is `MYR`, or `round(raw*100) === price_sen` — so Gamevion (MYR-native, raw == converted) shows nothing; only Digiflazz's `IDR 20,000` line renders. The columns are still populated uniformly.
- **Q5 (tightens decision 12) — `app:refresh-supplier-balances` logs every skipped supplier + its missing keys** (`Log::info` + a console `warn`), instead of only printing "No active, fully-configured supplier" when *all* are skipped. `customer_no_separator` is REQUIRED for digiflazz but shows a default-looking placeholder — a partially-configured row dropping out of the daily refresh is now greppable, not silent.
- **Q6 — `SupplierConfigSchema::normalizeConfig()` now trims every scalar string value** (`text` + `secret`), not just `list` fields. A trailing newline in `webhook_secret` → every signature 401s; a trailing space in `low_balance_threshold` → `is_numeric()` false → the warning silently never fires. Both closed.
- **Q7 (accepts the decision-9 deviation formally) — no dedicated `DigiflazzWebhookReconcileConcurrencyTest`.** `FinalizePendingDeliveryConcurrencyTest` (ADR-032) already spawns two real OS processes hitting `finalizePendingDelivery()` — the exact seam both the webhook and the poll call — and asserts one credit / one transition; its docblock now names ADR-069. The webhook controller's own request-level guards are covered by `DigiflazzWebhookControllerTest` (18 cases). A webhook-specific subprocess test would add HTTP-server plumbing for zero new invariant.
- **Q8 — `DashboardService::health()` reads `low_balance_threshold` out of the encrypted `api_config`** (PR-3 changed its `->get([cols])` to `->get()`). The per-supplier decryption cost on the 60s System Health poll is accepted (2 suppliers, ~microseconds); a regression test now asserts the health response's supplier rows are a fixed key whitelist with no `api_config`.

**ADR-069 is fully built (PR-1..3 + the stress-test addendum).** The supplier-deposit / FX-history ledger remains split out as a future ADR (ADR-070 candidate).
