# ADR-094: Combo Package — assembling several existing catalog Packages into one opaque, sellable SKU above a game's native max denomination

**2026-09-15 resilience addendum — two real bugs found via a real local smoke test (3-component combo, real admin API, real order, simulated leg failure), grilled, fixed, not just reasoned about in the abstract.**

*Bug 1 — "Resend Delivery…" silently no-ops for a combo order.* The admin panel's only resend/retry action (`ResendDeliveryModal`, "Resend Delivery…") always calls `POST /orders/{id}/resend` — `OrderResendService::assertSameGamePackage()` (decision 10) unconditionally rejects that for any combo order, even a same-package non-swap request. But `Admin\OrderController::resend()` has no pre-check of its own — it queues `ResendOrderDeliveryJob` and returns 200 "Resend queued." immediately; the rejection only fires later, inside the job, and `ResendOrderDeliveryJob::handle()` *catches* that `ValidationException` and just logs it ("Resend rejected at attempt time" — its own existing, correct-for-the-ordinary-case behavior, since a guard failing between "admin clicked" and "job ran" is meant to be a quiet no-op there). Net effect for a combo order: the admin sees a false success message, nothing happens, no `order_resend_attempts` row, no visible error anywhere — confirmed live via a real dispatched job against the real local dev queue. Decision 10's own text already named the correct path ("use the ordinary Resend Delivery retry instead") — it just had no UI trigger (the founder's 2026-07-27 revision merged the old plain "Retry Delivery" button into this same modal, before ADR-094 existed). **Fix (no grill — decision 10 already specifies the right endpoint):** `/admin/orders` now routes any order with `delivery_legs.length > 0` to a direct "Retry Delivery…" action (`retryOrderDelivery()` → `POST /retry-delivery`, no package picker — a combo can't swap package anyway) instead of ever opening `ResendDeliveryModal`. New test `test_retry_delivery_queues_a_fulfillment_job_for_a_combo_order`.

*Bug 2 — a combo order can get stuck at `Processing` forever.* `fulfillCombo()`'s first transaction (advancing the *order* to Processing) commits before the per-leg loop starts, by design (decision 7 — holding a lock across up to 3 sequential HTTP calls would repeat the exact lock-contention class ADR-077 already fixed once in production). But `attemptLeg()`'s own per-leg transaction had no catch around the adapter call — a genuinely unexpected exception (not a clean `SupplierResponse::failure()`: a network-level failure the adapter didn't normalize, an unconfigured supplier, a bug) propagated straight out, and since the order-level Processing commit already happened, `resolveComboOutcome()` never ran and the order was left stranded. Confirmed live: bound a deliberately-unconfigured supplier slug in a real local smoke test, the leg threw `UnsupportedSupplierException`, the real order in the real local dev DB sat at `Processing` with zero automatic or admin-UI recovery path (Resend/Retry only render for `Failed`/`NeedsReview`, never `Processing`). This is specific to combo — the ordinary single-supplier `fulfill()` wraps the Processing transition and the one adapter call in the *same* transaction, so an equivalent exception there rolls both back to a safe, retryable pre-attempt state.

Grilled before fixing (`/mattpocock-skills:grilling`), since this touches `OrderFulfillmentService`, the platform's single most money-critical file. Decisions:
- An unexpected exception mid-`attemptLeg()` marks the leg **NeedsReview, never Failed** — same reasoning as `duplicate_reference` above: we genuinely don't know whether the supplier received the request before things broke, so "safe to retry from scratch" (Failed's implicit meaning) isn't a safe assumption. A subsequent retry re-submits under the same `{reference_number}-L{n}` idempotency key; if the supplier really did see it, `duplicate_reference` detection (already in place) catches that safely, same as it always has — no new idempotency machinery needed.
- The catch is scoped to the delivery-attempt transaction only, **not** `recordOrderDrawdown()` (which already runs after that transaction, per ADR-083 decision 3's own pattern) — a drawdown-recording failure is a bookkeeping concern (already self-logging, non-fatal by its own design), never a reason to relabel a delivery that genuinely already succeeded back to "needs review."
- **No top-level catch needed in `fulfillCombo()`'s loop** — once `attemptLeg()` itself never lets a `Throwable` escape, the loop always reaches `resolveComboOutcome()`, which is the entire fix; a belt-and-suspenders outer catch would add real complexity (what leg-set state to assume mid-loop) for no remaining failure mode.
- **No reconciliation safety-net job** (a combo-`Processing`-staleness watcher, analogous to `ReconcilePendingDeliveriesCommand`) — the fix above closes the actual root cause; a backstop for hypothetical failure modes nobody's identified is exactly the kind of speculative-trigger machinery decision 17 was itself parked for. Revisit only against a real observed stuck-order case.
- The admin-UI "`Processing` has no visible recovery action" question became moot — after this fix, `Processing` is purely transient (resolved within one `fulfillCombo()` call every time), so no order can sit there long enough to need one.

New tests: `test_a_leg_that_throws_unexpectedly_lands_in_needs_review_not_stranded_at_processing`, `test_retrying_a_leg_that_previously_threw_completes_the_order_normally` (both `OrderFulfillmentServiceComboTest`). Full backend suite **1928/1928** green, concurrency suite green (real MySQL), Pint clean. `admin/` `tsc --noEmit`/`eslint`/`next build` all clean.

**Context:**

The founder is fielding real demand from resellers he's approaching for denominations above a game's native supplier ceiling (MLBB Malaysia's largest native SKU is 7502 Diamonds). The underlying motivation isn't pure convenience: guest/reseller checkout is currently single-package-per-order (`Order belongsTo Package`, 1:1, ADR-011), so reaching, say, 15000 Diamonds today means two separate checkouts — and CHIP FPX charges a flat RM1 fee **per transaction**, so two checkouts cost the customer/reseller RM2 in gateway fees where one would cost RM1. A Combo Package (several existing Packages delivered under one checkout, shown as a single native-looking SKU) removes that doubled fee.

Both supplier adapters are confirmed fixed-SKU only (`GamevionAdapter`/`DigiflazzAdapter::createOrder()` take a `productRef`/`buyer_sku_code`, no arbitrary-amount field) — there is no shortcut where a bigger denomination could be requested directly from the supplier. A combo has to be assembled from multiple real supplier calls, one per component.

**Facts checked against real code before deciding (this grill's own discipline, matching ADR-093's):**
- `packages.supplier_id` (FK, `restrictOnDelete()`) and `packages.supplier_package_ref` (string) are both **NOT NULL** in the original migration, with a `UNIQUE(supplier_id, supplier_package_ref)` index added later — every `Package` row is hardwired to exactly one supplier SKU today.
- `OrderFulfillmentService::fulfill()` throws immediately if `Order.supplier_product_ref` or `Order.supplier_id` is null (before resolving an adapter), and makes exactly one `$adapter->createOrder(...)` call per invocation, inside one `DB::transaction()` holding `Order::lockForUpdate()` for the call's full duration. No leg/sub-order concept exists anywhere in this class.
- `OrderFactory::create()` copies a single `supplier_id`/`supplier_product_ref` from the resolved `Package` onto the new `Order` row at creation time — the `Order` itself has no room for more than one supplier reference.
- `OrderResendService::resend()` (the admin "swap to a different package/supplier" action, distinct from the plain "Resend Delivery" retry) blindly copies `$targetPackage->supplier_package_ref` onto the order; its only compatibility guard, `assertSameGamePackage()`, checks `game_id` alone.
- Idempotency is order-scoped: `reference_number` (`REF-`+ULID) is generated once, reused unchanged on every retry, and is the literal string both adapters key their dedup off (Gamevion's `409 duplicate_reference`, Digiflazz's `ref_id`-signed requests).
- Digiflazz has a real inbound webhook (HMAC-SHA1, matches `Order` by `reference_number` exact-column lookup); **Gamevion has no webhook at all** — its only backstop is `ReconcilePendingDeliveriesCommand`'s poll, and an ambiguous Gamevion outcome already lands in `needs_review` for a human today, with no automated resolution.
- `DeliveryStatus` values (`not_started/processing/delivered/failed/needs_review/pending`) are already channel-agnostic; the storefront's `StatusBadge.tsx` maps most of them to friendly copy but has **no entry for `needs_review`** (falls through to the raw string) — a pre-existing gap, not one this ADR introduces, but one a combo order could hit more often via its own retry path if not handled with care.
- ADR-073's refund policy (refund-to-wallet) applies only to `wallet_reseller_id`-owned orders; guest/Affiliate orders still follow ADR-004 (Voucher, never cash). `Admin\OrderController`'s "Issue Voucher" action always uses `order->final_amount` — **the whole order's value, with no partial-amount input today.**
- `ResellerCatalogService::resolveByCode()`, the Reseller REST API (`ResellerApi\OrderController::store()`), and the WhatsApp Bot (`ResellerBotService::handleOrder()`) all resolve **one** `Package` and feed its singular fields into the same `OrderFactory`/`OrderFulfillmentService` path as the storefront — **zero type-check exists on any `Package` attribute** in any of the three; a combo `Package` dropped in today would flow through silently and submit whatever singular `supplier_package_ref` happened to be on the row (or null) as a real SKU.
- `SupplierFundingService::recordOrderDrawdown(Order $order, float $price)` (ADR-083) is called exactly once per successful `fulfill()`, taking one `Order` and one `$price` — it is the ledger row that reconciles against the supplier's own real balance drawdown.
- `ReportService`'s money aggregates (`ReportService.php:27`'s own comment: profit is "never read off... a JOIN — they are already correct") sum `orders.final_amount`/`platform_profit`/`affiliate_profit` directly off the stored `Order` row, never recomputed from `packages`. Group-bys key on `orders.package_id`, so a combo's own row is never merged into its components' figures.
- `llm_report_catalog` (ADR-087's curated read-only view) already exposes `package_id, denomination, is_active, cost_price, standard_selling_price, game_id, supplier_id` — enough columns for the Report Assistant to self-join and surface "cheapest pair of active packages whose combined denomination clears X" candidates **today, with zero new build** — `SqlGuard` permits self-joins on an allowed view (only multi-statement/non-SELECT/off-list tables are rejected).
- Checked against real production catalog data (MLBB Malaysia, `game_id=1`): summing two components' already-marked-up `standard_selling_price` values (the only pricing formula this ADR accepts, decision 4) lands within a few sen of the native 7502 SKU's own price while sometimes delivering meaningfully more diamonds (e.g. 4810+2976 = 7786 diamonds for RM496.25 vs native 7502 for RM495.07) — a real, supplier-tier-pricing-driven customer/reseller selling point, but **not** extra platform profit: profit stays proportional to summed cost by construction (margin is a cost-weighted blend of the components' own `markup_percent`, not a new number), and it isn't guaranteed to persist past the next Price Sync run.

**Decision:**

1. **Data model — minimal, reuses existing mechanisms rather than inventing new ones.** New `Package.is_combo` boolean (fulfillment-engine signal only). New `package_components` table (`combo_package_id`, `component_package_id`, `quantity`, `sort_order`). New `order_delivery_legs` table (`order_id`, `component_package_id`, `supplier_id`, `status`, `supplier_reference`, `delivered_at`, `failure_reason`) — one row per leg, giving admin the exact per-leg supplier reference needed to manually check with the supplier.
2. **Combo identity reuses `denomination` (the sum of components), not a synthetic `catalog_code`.** Rejected the ADR-075-precedent instinct to treat this like the bundle/pass problem: a bundle/pass is **not** truly fungible with a raw diamond amount (that's exactly why `catalog_code` exists, to avoid false equivalence), but a combo's output genuinely *is* — 7502+2976 diamonds has the identical real-world effect on the player's account as a native 10478 SKU would. Reusing `denomination` costs zero new columns, lets ADR-034's storefront dedup and ADR-075's reseller product-code scheme (`{reseller_code}-{denomination}`) both work on a combo Package unmodified, and is the correct mechanism precisely because combo output is a true substitute good.
3. **`Package.supplier_id`/`supplier_package_ref` become nullable specifically for `is_combo=true` rows**, enforced mutually-exclusive-with-components at the `FormRequest` layer — mirroring the exact `denomination`/`catalog_code` `prohibits`-each-other pattern ADR-075 already established, not a new validation idiom.
4. **Same-supplier-only components in v1, no nested combos.** A combo cannot contain another combo (blocked at the data layer). Cross-supplier combos are out of scope for v1 — they would multiply the webhook/poll-routing and atomicity work for comparatively little gain, since ADR-034's best-price dedup usually already concentrates one denomination onto one winning supplier. `package_components.quantity` lets the same component repeat (e.g. 7502 ×2) without duplicate-row awkwardness.
5. **Pricing — Method 3, hybrid.** Default combo price is the literal sum of each component's own already-computed `standard_selling_price` (i.e. component A's profit-after-its-own-markup + component B's) — zero new pricing logic, ORD-9-safe by construction since each addend was already server-computed correctly. An optional per-combo override (custom markup or price) exists for the founder to deliberately price a specific combo more aggressively or more profitably, without forcing every combo through a manual pricing decision by default.
6. **Combo pricing is stored, refreshed on the same cadence as every other `Package`** — recomputed as an additional step inside Price Sync's existing per-package loop whenever a referenced component's `cost_price` changes, or immediately when an admin edits the composition. No separate job/schedule. Price Sync's Sync Details modal also gains each changed package's product code, plus a line for any combo recomputed as a consequence — visibility, not a silent cascade.
7. **Fulfillment — `OrderFulfillmentService::fulfill()` gains an explicit `is_combo` branch inserted before its existing single-ref null-guards**, diverting to a leg-loop sub-flow that reads `package->components` (via `sort_order`) instead of `Order.supplier_product_ref`. **Each leg gets its own short lock+transaction+one-HTTP-call cycle**, sequential, not one transaction spanning every leg — holding `lockForUpdate()` across N outbound HTTP round-trips would be a worse repeat of the exact lock-contention class ADR-077 already fixed once in production. Per-leg idempotency key is `{order.reference_number}-L{n}`, extending (not replacing) the existing scheme; Digiflazz's webhook/Gamevion's poll backstop both learn to parse a `-L{n}` suffix off the inbound reference before falling back to today's exact-column `Order` lookup, then update the matching `order_delivery_legs` row.
8. **Combo orders get their own queue-timeout tier**, sized to the maximum allowed component count, rather than inheriting the `orders` queue's existing 60s/tries=3 (tuned for one HTTP call) — avoids Horizon killing a job mid-leg-sequence, which would leave an order in a worse, unclassified state than the `needs_review` this design deliberately routes failures to.
9. **Partial delivery (some legs succeed, at least one exhausts retries) lands in `needs_review` and requires a human decision before any refund path fires** — no auto-issued partial Voucher. Rejected auto-issuing a Voucher for just the failed leg's value: the player has already received the succeeded legs' goods, and an automated "partial" message is new customer-facing surface that doesn't exist today; a human already has to look at every ambiguous Gamevion `needs_review` case regardless, and order volume is still low pre-launch, so the manual step is cheap. **"Issue Voucher" gains a custom-amount input for this case** (prefilled with the failed leg's price, admin-adjustable) — today's Voucher action always uses `order->final_amount`, which would over-compensate a customer who already received part of the goods.
10. **`OrderResendService::assertSameGamePackage()` gains an explicit `is_combo` guard**, rejecting a resend-swap into or out of a combo Package. The existing "swap this order to a different single package/supplier" tool assumes exactly one supplier reference to copy onto the `Order` — nonsensical for a multi-leg entity — and doing nothing here would silently write a null/garbage `supplier_product_ref` onto a real order. The ordinary "Resend Delivery" retry (no package swap) stays fully usable for a combo order once decision 7 ships — it already only re-attempts legs without a recorded `supplier_reference`, by construction of decision 7's per-leg idempotency key.
11. **`SupplierFundingService::recordOrderDrawdown()` is called once per leg (its own real component price), not once per order.** A combo genuinely draws down the supplier balance N times — recording one entry per order would silently under-report against the supplier's own statement and defeat the drift-check ADR-083 built specifically to catch this class of discrepancy.
12. **Combo is fully opaque to the customer and the reseller — neither is ever told, in any UI or API response, that a package is a combo.** `is_combo`/`package_components`/leg detail never appear in any public storefront response or any Reseller API/Bot/portal response (the same narrow-response-shape discipline `Package.id`/`supplier_package_ref` already get). A direct, welcome consequence: the tracking page needs **zero** new customer-facing states — decision 9's `needs_review` partial case is handled entirely admin-side, so the existing binary Processing/Delivered/Failed copy is untouched. **Admin**, by contrast, gets full precision: the Order detail page gains a leg breakdown (component, supplier, status, `supplier_reference` per leg) — the two per-supplier reference numbers a combo order produces are exactly what admin needs to manually check against the supplier's own dashboard when something looks wrong.
13. **Component Package churn is guarded, not silent.** An admin manually deactivating a `Package` referenced by an active combo gets a warn-and-acknowledge prompt ("N active combo(s) use this package — deactivating will deactivate them too"); proceeding cascades the deactivation to every dependent combo. Price Sync's own automated deactivation (SYNC-6, no human present to acknowledge) cascades the same way without a prompt, but the deactivation is surfaced in that sync run's own report — never a silent side effect.
14. **All consuming channels ship together, not phased** — storefront, Affiliate (same storefront codebase, per-brand), and Reseller (Portal, REST API, WhatsApp Bot) all gain combo-awareness in the same release, once this is actually built. The founder's own reasoning: the core `OrderFulfillmentService` leg-engine (decisions 7-11) is shared infrastructure regardless of channel — the remaining channel-specific work is a thinner "resolve the product, create the Order" layer at each entry point (`CatalogController`/`CheckoutController` for storefront+Affiliate; `resolveByCode()`/`ResellerApi\OrderController`/`ResellerBotService` for Reseller), so there's no real saving from staging channels separately, and staging them would leave the very channel the real demand is coming from (reseller) deliberately unsupported first.
15. **Reporting requires zero changes.** `ReportService`'s aggregates already sum stored `Order`-level `final_amount`/`platform_profit`/`affiliate_profit` (never recomputed via a `packages` JOIN, per decision 5/6 keeping those columns correct at write time) and group by `orders.package_id`, so a combo order is automatically counted once, correctly, on its own row — never double-counted into its components' figures.
16. **No new tooling needed for combo *curation* discovery either** — the existing LLM Report Assistant (ADR-087) can already answer "which active packages for game X combine to clear denomination Y at the lowest summed cost" today, ad hoc, via a self-join over `llm_report_catalog` within `SqlGuard`'s existing single-SELECT/read-only/row-limit rules. Noted for whoever builds decisions 1-3: once a combo `Package` row exists, it will itself appear in `llm_report_catalog` (via the same `packages` table) — add a filter (or expose `is_combo`) so the Assistant doesn't get asked to combine a combo with another combo.
17. **Parked, not built.** Revisit trigger: real recurring demand, detectable from existing order data with zero new code — repeated guest/reseller checkouts for the same `game_id`+`player_id` within a short window, run as an ad-hoc query (or via the Report Assistant, decision 16) rather than assumed from this grill's single reseller conversation. Building ahead of that signal would add real fulfillment-path complexity (decisions 7-11 touch the platform's single most money-critical service) for a pattern not yet observed in real traffic.

**Rationale:**

The core engineering insight across nearly every decision here is the same one AGENTS.md already names as this project's convention: extend an existing seam with a new implementation rather than reshape it. `SupplierAdapter::createOrder()`'s interface is untouched — a combo just calls it N times through a new orchestration layer (decision 7). `denomination`/ADR-034's dedup, ADR-075's reseller code scheme, the `denomination`/`catalog_code` mutual-exclusion FormRequest pattern, `needs_review`'s existing channel-agnostic semantics, and ADR-004/ADR-073's existing terminal refund actions are all reused as-is rather than duplicated. The one place this ADR does add real new machinery — the per-leg fulfillment loop, its own short-transaction discipline, and its own queue-timeout tier (decisions 7-8) — is deliberately isolated to exactly the seam AGENTS.md flags as money-critical, sized and reasoned about on its own, not smuggled in as a side effect of a "just add a flag" change. Decision 17's parking is itself consistent with that discipline: a stress-test pass surfaced six concrete, previously-unaddressed gaps (schema NOT NULL conflict, the fulfillment branch, the resend-swap corruption risk, lock-duration, Voucher over-compensation, and per-leg ledger drawdown) against a feature whose demand signal is currently one conversation, not measured traffic — building now would be absorbing that whole risk surface speculatively.

**Consequence to track:**

- Whoever builds this needs a dedicated e2e test (the existing golden-path suite has no multi-leg coverage) before this can ship, covering at minimum: full success, one-leg failure landing in `needs_review`, and the custom-amount Voucher path.
- Fraud/velocity checks (the 2026-07-29 Blacklist/Fraud build) were not audited against a combo order in this grill — check whether any existing check assumes "one order = one supplier submission" before building decision 7.
- Decision 9's `needs_review` reuse inherits `StatusBadge.tsx`'s pre-existing missing-label gap (falls through to the raw string) — not introduced by this ADR, but worth fixing in the same PR since a combo order is now somewhat more likely to visit that state than before.
- Decision 14's "ship all channels together" is a bigger single release than a phased rollout would be — accepted deliberately (see decision 14's own rationale) but worth remembering if the eventual build estimate balloons; splitting Reseller-first vs. storefront-first was considered and rejected here, not overlooked.
- This ADR's own profit-neutrality finding (Context's last bullet) should be re-explained to the founder at build time if a long gap passes before decision 17's trigger fires — the "same price, more diamonds" pitch is a genuine reseller-facing selling point, but it is not a lever for platform profit, and no decision here should quietly get reinterpreted as one.

**2026-09-15 addendum — pre-build stress-test pass, 6 findings, all resolved, no design decision reopened.** A dedicated grill session re-checked decisions 1-16 against real current code (migrations, `OrderFulfillmentService`, `SupplierFundingService`, `ResellerCatalogService`, `CheckoutVelocityGuard`) one more time immediately before build. One Consequence-to-track item closed as a non-issue in the process: `CheckoutVelocityGuard` is IP-based and counts only blacklist-triggered rejections, pre-`Order`-creation — it carries no "one order = one supplier submission" assumption, so decision 7 needs no change on its account.

18. **`SupplierFundingService::recordOrderDrawdown()` gains an optional leg identifier, dedup key becomes leg-aware.** Real bug caught against current code: the method's existing dedup guard (`reference_type='order', reference_id=$order->id`) is satisfied by the *first* `recordOrderDrawdown()` call for a given order — decision 11's "once per leg" would make every call after the first silently no-op, so only leg 1's drawdown would ever reach `SupplierLedgerEntry`, defeating the exact drift-check ADR-083 built to catch this class of gap. Fix: an optional `?int $legId` param; when given, dedup keys on `reference_type='order_delivery_leg', reference_id=$legId` instead of the order. The order-level call path (every non-combo order today) is unchanged.
19. **`order_delivery_legs` gains a `leg_number` column** (`unsignedTinyInteger`, `unique(order_id, leg_number)`), populated 1..N at order-creation time in `sort_order`+quantity-expansion order. Decision 1's original column list had no way to distinguish two legs generated from the same repeated component (`package_components.quantity` > 1, decision 4's own example) — same `component_package_id` on both rows, nothing to anchor the `{reference_number}-L{n}` idempotency suffix (decision 7) or a partial-retry lookup to. `leg_number` is `n` in that suffix, and its row's own `id` is what decision 18's `$legId` now points at.

Narrow scenario (needs two genuinely different component assemblies summing identically), not worth new machinery for; noted so a future "why isn't this combo ever ordered" question has a fast answer.

### Addendum (2026-09-24) — reverses decision 22: component reactivation now cascades onto a dependent combo

**Context:** Founder-requested continuation of the same session's ADR-100 Pending Reactivation audit. PRD §16 item 21 (added 2026-09-22) had already found decision 22 above left a real gap: a combo cascade-deactivated by decision 13's automated path (`deactivated_reason='combo_component_deactivated'`) never appears in `PendingReactivationFinder`'s queue (that query only ever matches `deactivated_reason='supplier_sync'`), so it has zero admin visibility, and even if an admin found it manually in `/admin/games`, `PackageController::updateStatus()`'s own decision-22 guard only let them reactivate the combo directly, never as a consequence of fixing its components. Decision 22's "one-directional" call addressed the *action* only; the *visibility* gap was an unrecorded side effect, not a decision.

**Decision:** Reverse decision 22. `ComboPricingService::cascadeReactivate(Package $component, ?int $priceSyncRunId, ?int $adminUserId)` reactivates a `combo_component_deactivated` combo the instant **every** one of its components is confirmed active — not just the one that just changed. Called from every site a component's `is_active` can flip false→true: `PendingReactivationController::approve()`/`bulkApprove()`, `DismissedPackageController::restore()`, `PendingPriceChangeController::approve()`/`dismiss()`, `PackageController::updateStatus()`, and `PendingReactivationAutoApprover::approve()` — symmetric with decision 13's `cascadeDeactivate()` being called from both the automated and manual deactivation paths. A no-op when the package isn't part of any combo, or its combo isn't in that exact state (safe to call unconditionally). Founder's own call, chosen over the "manual-but-visible" alternative (add combo rows to Pending Reactivation, require an explicit approve) — the visibility gap is moot once reactivation is automatic, and the founder had just relaxed ADR-100's own flap-count gate in the same session, favoring less manual toil over extra manual confirmation once the underlying signal (every component genuinely active) is already trustworthy.

**New `package_reactivation_logs.admin_user_id`** (nullable FK, migration `2026_09_24_051204`) — mirrors `deactivation_logs`' own two-provenance shape: null when the cascade's last triggering component came back via `PendingReactivationAutoApprover` (no admin involved), set to the acting admin's ID when it came back via any manual path. Every cascade reactivation still writes a `PackageReactivationLog` row (`trigger='combo_components_all_active'`) — no human ever directly decides *the combo's own* status, so the table's existing "not a direct human decision on this row" scope still holds even for the manual-provenance case.

**Rationale:** A combo's checkout depends on every leg succeeding — reactivating on anything less than "all components active" would silently offer an unfulfillable combo, which `cascadeReactivate()`'s all-active check guards against structurally (same guard `updateStatus()`'s pre-existing direct-reactivate check already used, just now triggered automatically instead of only blocking a premature manual attempt). The remaining asymmetry — `SupplierController::updatePackagesStatus()`'s bulk supplier on/off toggle uses a raw mass `Package::query()->update()` and has never called `cascadeDeactivate()` either — is a pre-existing, separate gap from before this addendum, out of scope here; flagged for whoever next touches that endpoint.

**Consequence to track:** `reactivation_stability_syncs`/cutoff-window trust (ADR-100, its own 2026-09-24 addendum) now transitively governs how fast a combo can come back too, since a combo's reactivation timing is fully derived from its slowest-reactivating component — no new tuning surface, but worth remembering when reading a combo's `PackageReactivationLog` timestamp.

### Addendum (2026-09-29) — corrects the 2026-09-15 addendum's claim about single-supplier `fulfill()`; bugfix from the 2026-09-28 full-system audit (finding M-1)

**Context:** the 2026-09-15 addendum's decision-7 rationale (above) claimed `fulfill()`'s ordinary single-supplier path "doesn't have this gap" — an exception during the supplier call was said to roll the Processing transition and the reference_number back together to "a safe, retryable pre-attempt state." A 2026-09-28 full-system audit (money/security/burst, all channels) traced this claim against the real code and found it backwards: `reference_number` was generated and persisted **inside the same transaction** as the supplier HTTP call, with no try/catch anywhere in `fulfill()`. A `ConnectionException` on a slow/timing-out supplier rolled the whole transaction back, including the reference — a job retry then called `resolve(null)`, which mints a **brand-new** reference (reuse only happens when a non-null value is already stored). If the supplier had actually processed the exception-interrupted attempt despite the timeout, the retry could submit and deliver the same order a second time under the new reference, with no dedup protection since the two references never matched.

**Fix (root-cause bugfix, not a new decision — restores the invariant ORD-8/decision-9's reference-reuse mechanism already assumes):** `fulfill()`'s non-combo path is now split into the same two-phase shape `attemptLeg()` already uses — phase 1 (guard checks, reference resolution, the NotStarted/Failed/NeedsReview → Processing transition) commits on its own, before the supplier call; phase 2 (the actual `createOrder()` call and outcome handling) runs in its own transaction, wrapped in a try/catch mirroring `attemptLeg()`'s own catch exactly: on any `Throwable`, re-lock the order, skip if a faster concurrent attempt already reached Delivered/Pending, otherwise transition to NeedsReview while keeping the reference phase 1 already persisted (`markNeedsReview()` only accepts Processing/Failed/Pending as the FROM state, which phase 1 committing before the throw is what makes valid). A resend from NeedsReview reuses the same reference per the existing ADR-102 decision 9 carve-out, so the supplier's own dedup-by-reference is what actually protects against a real double delivery if the interrupted attempt genuinely reached them.

Proven with `test_fulfill_persists_the_reference_number_and_moves_to_needs_review_when_the_supplier_call_throws` and `test_fulfill_reuses_the_persisted_reference_on_retry_after_a_supplier_exception` (`tests/Feature/Services/Fulfillment/OrderFulfillmentServiceTest.php`) — both fail against the pre-fix code (the exception propagates uncaught) and pass against the fix. Full fast suite 2316/2316 green, full concurrency suite (real MySQL, `OrderFulfillmentConcurrencyTest` included) green — the existing "exactly one of two simultaneous fulfillment attempts succeeds" guarantee is unaffected: a second concurrent call now gets rejected by phase 1's `startDelivery()` guard as soon as phase 1 commits Processing, same protection as before, just with a shorter lock hold (no longer spanning the HTTP call) rather than a longer one.

This addendum's fix is single-order-scoped; `attemptLeg()`'s own per-leg version of this same pattern (built 2026-09-15) was already correct and is unchanged. Decisions 1-27 and every prior addendum above are otherwise unaffected — this note only corrects the one sentence quoted above and records the fix.

### Addendum (2026-10-04) — partial delivery gets its own terminal status and one settlement path for every channel (revises decisions 9, 25, 26)

**Status:** Accepted — grilled 2026-10-03/04 (2 rounds, 8 decisions) + money code-trace pass (3 parallel forks: write side, read side, frontends/docs/tests). **Built 2026-10-04** on `fix/2026-10-03-combo-partial-delivery-settlement` (see `docs/build-log.md`). Build-time refinements: a wallet refund is based on `final_amount` (decision 33's text, updated); a partial restore keeps the redemption's `status = 'restored'` with `restored_amount` < `amount`, so every existing "was it restored" reader stays correct; quota debits restored before this column exist with `restored_amount_sen` null.

**Context.** A 2026-10-03 pre-launch money audit (4 forks, one per layer) found a Reseller-wallet combo with a genuine partial delivery has **no compensation path at all**: `VoucherController::storeFromOrder()` rejects every wallet order (2026-09-29 guard), `refundToWallet()` accepts only `Failed`, `confirmFailed()` and `markDelivered()` both refuse a partial combo. Combos are sold through the API and Bot (decision 14), so a failed leg strands the reseller's money; the only workaround (admin manual wallet credit) is invisible to `isAlreadyCompensated()`, so a later Retry could deliver on top of it. Root-causing it showed this is a symptom of three gaps shared by **every** channel, not a wallet bug:

1. **Partial delivery had no terminal state.** The order model knew two outcomes (all delivered → credit profit; all failed → compensate). Decision 9 parked the third outcome in `NeedsReview`, whose own definition is "outcome unknown". Every action gates on `Failed`, so a partial order falls through all of them except decision 9's one carve-out — added to the voucher path only, which is exactly where the wallet path got left behind. The Reseller API also exposes the raw status, and its public docs say `needs_review` = "ambiguous, being confirmed manually" — false for a settled partial order, forever.
2. **"Compensable, and for how much" was hand-rolled twice** (`storeFromOrder()`, `refundToWallet()`), with different gates and different amount formulas.
3. **The ledger never closed for the delivered part.** `creditProfit()` runs only on a path into `Delivered`, so a partial order never credited platform profit or the affiliate's commission for legs that really reached the player.

The trace also confirmed a live over-compensation bug on the retail side: `storeFromOrder()` calls `VoucherService::restore()` (all-or-nothing) for a partial order too, giving back the **whole** paid-with voucher X while the new voucher Y already covers the cash share — over-credit = `voucher_discount × delivered share`. Production at decision time: 2 combo orders ever (1 retail, 1 wallet), both fully delivered; 0 partial deliveries; 2 reseller API keys, 0 registered reseller webhooks.

**Principle (founder, during the grill):** a combo must behave like an ordinary package. For an ordinary package, `delivery_status` is supplier truth and compensation is a separate fact (a `Failed` order that got a voucher stays `Failed`). An earlier draft that flipped a settled partial order to `Delivered` was rejected for breaking that parity — compensation must never change the status.

**Decisions (28 onward, continuing this ADR's numbering):**

28. **New terminal `DeliveryStatus::PartiallyDelivered` (`partially_delivered`)** — the order-level rollup when every leg is final with ≥1 `Delivered` and ≥1 `Failed`. `resolveComboOutcome()`'s mixed branch lands here instead of `NeedsReview`. A mix containing a `NeedsReview` leg stays `NeedsReview` (genuine ambiguity). Leg status never takes this value. The column is a plain string — no status migration.
29. **Transitions:** `Processing|Pending|NeedsReview → PartiallyDelivered`; `PartiallyDelivered → Processing` via Retry Delivery of the failed legs, only while not compensated (`isAlreadyCompensated()` inside `fulfillCombo()`'s lock stays the final guard); compensation itself never changes the status.
30. **One compensability rule, in one place:** `DeliveryStatus::isCompensable()` = `Failed` or `PartiallyDelivered`. `scopeNeedsAction()`, both compensation endpoints, the admin detail payload and the admin buttons all read it. `Order::isPartialComboDelivery()` and decisions 25/26's carve-outs are deleted — the status replaces them.
31. **Confirm Failed on a combo** flips every `NeedsReview`/`NotStarted` leg to `Failed` (keeping the admin's note), then rolls up: ≥1 `Delivered` leg → `PartiallyDelivered`, else `Failed`. Refused while any leg is `Pending`. A later retry mints fresh leg references, the same rule ADR-102 decision 9 gives an ordinary confirmed-Failed order.
32. **One settlement service for both instruments.** The instrument comes from the order, not the button: `wallet_reseller_id` → `wallet_refund` credit; otherwise → voucher (restore part of paid-with voucher X + issue Y). `VoucherController::storeFromOrder()` and `OrderController::refundToWallet()` become thin callers. One transaction under the existing `Order::lockForUpdate()`. An ordinary package is the same formula with u = 1 (the full failed amount).
33. **Amount is locked to a formula; the admin-typed `amount` is removed.** Notation: S = `selling_price`, D = `voucher_discount`, C = `final_amount − transaction_fee` (S = C + D), A = `affiliate_profit`, and u = Σ failed legs' frozen `selling_price_sen` ÷ Σ all legs' (u = 1 for a non-combo or an all-failed combo). Then U_cash = round(C × u), U_vouch = round(D × u), U = U_cash + U_vouch. Voucher instrument: restore U_vouch onto X, issue Y = U_cash (skipped when 0). Wallet instrument: refund round(`final_amount` × u) — what actually left the wallet (fee and D are 0 on wallet orders today; build-time refinement so a non-zero fee could never be kept back from a wallet). The fee is never refunded, same as today's Failed path. Goodwill above the formula goes through the existing standalone voucher (Path A `store()`), which has its own audit trail. Rationale: profit, net sales and the compensation must agree; an admin-typed V′ ≠ U breaks that for both instruments.
34. **Paid-with voucher X is restored proportionally**, keeping ADR-024 decision 7's "two un-merged vouchers". Rejected: committing X in full and issuing one Y = U, which double-books U_vouch (X's liability was already booked once at X's issuance). New nullable `voucher_redemptions.restored_amount` (the unique `order_id` index rules out splitting into two rows). `VoucherService` gains a partial restore; a full restore also writes `restored_amount` so there is one model. `isVoucherRestored()` and every redemption-status reader switch to it.
35. **Profit for the delivered legs is credited at settlement, inside the same transaction — not when the order reaches `PartiallyDelivered`.** `order_profit` is once-per-order (`dedupe_key`, 2026-09-29), so crediting early would collide when a later retry delivers the remaining legs and `Delivered` credits again. Crediting at settlement is parity with `Failed`, which credits nothing until it is settled. Formula, identical for both instruments: `affiliate_profit = A − round(A × u)` (decision 36), `platform_profit = (S − U) − C_d − affiliate_profit`, where C_d = Σ delivered legs' cost, using ADR-111's real per-leg cost when present (same helper `resolveComboOutcome()` uses, extracted, not copied). Both columns are persisted on the order row before `creditProfit()` (the CSV export, the affiliate "Your margin" column and `comboCostReconciliation()` all read the columns). The ledger credit is split from the "delivered" WhatsApp receipt, so settlement never sends that receipt.
    *Worked check (retail, affiliate brand):* S = 5000 (legs 3000/2000), A = 500, D = 1000, C = 4000, fee = 100; leg 1 delivered at real cost 2400, leg 2 failed; u = 0.4. Then U_cash = 1600, U_vouch = 400, platform profit = 3000 − 2400 − 300 = 300, affiliate = 300. The customer receives goods worth 3000 plus credit 400 + 1600 = 5000 = S. The old code would have given 1000 + 1600 = 2600 of credit (600 over). *Wallet:* S = 5000, R = U = 2000, platform profit = 3000 − 2400 = 600; net sales = 5000 − 2000 = 3000.
36. **The affiliate earns commission on the delivered share** (A × (1 − u)), the same rule as an ordinary order: commission when goods are delivered.
37. **Membership quota is given back on every compensation, proportionally** (full on a Failed order, × u on a partial one). This also closes the existing gap where a Failed Member order compensated with a voucher never restored quota (audit fork B #3). `membership_quota_debits` gains `restored_amount_sen`, the same shape as decision 34. A debit from a previous quota cycle stays a no-op, as today.
38. **Reseller API and Bot:** a new webhook event `order.partially_delivered` fires when the status is reached. `order.refunded` carries the actual partial amount. The Bot sends a final update with its own Malay label and the real refund amount (`refundNotice()` reads the `wallet_refund` entry, not `selling_price`). The API docs make `partially_delivered` a final status and add a v1.2.0 changelog entry; the versioning policy's "additive" list gains new enum values and new webhook events. Cheapest moment: 0 registered webhooks in production.
39. **Customer messages:** no "delivered" receipt for a partial order. The WhatsApp status card gets its own branch ("part of your order couldn't be completed"). On settlement, one message names the voucher code and amount for the balance. Nothing ever says "combo" or "leg" (decision 12 holds — the status reveals only that part of an order was completed). The storefront track page treats the status as terminal with the same wording.
40. **No review for a partial order** — `ReviewController` stays Delivered-only, and no rating popup.
41. **Readers that must ship in the same release** (from the trace), so nothing reads the new value wrong:
    - **Monthly accounting summary:** sales, COGS and FX variance include `PartiallyDelivered`, and COGS uses the delivered legs' cost, not `orders.cost_price`.
    - **Analytics and register:** `TransactionRegisterService` cost, and `CustomerAnalyticsService` revenue, cost and profit.
    - **Order cost display:** `Order::comboCostReconciliation()` sums delivered legs only.
    - **Reports and assistant:** a reports-funnel key, the admin summary cards and filters, and the LLM assistant prompt.
    - **Storefront:** the track-order Zod enum (an unknown value silently drops the realtime push and leaves the page polling forever), `isTerminal` and the stepper.
    - **Admin and reseller portal:** status unions, severity maps and filter lists.
    - **API docs:** the docs-site status tables, and a regenerated `openapi.json` (the CI drift guard).

**Rejected alternatives.** (a) Keep `NeedsReview` and treat "settled" as a compensation fact — rejected: the status would lie, including in the public API contract. (b) Flip to `Delivered` on settlement — rejected: compensation would drive the status, which breaks ordinary-package parity, and `Delivered` would also be untrue. (c) Separate profit formulas per instrument — rejected after the trace: a normal Failed order already credits zero `order_profit` under both instruments, so one formula conserves money for both. The voucher-vs-wallet difference (where the undelivered value's liability is booked) stays inside each instrument.

**Consequence to track.**
- **Unsettled partial order:** shows no profit until settled. It stays visible through Need Action (decision 30), so check that Need Action is actually being worked.
- **Ordinary Failed orders now use the locked formula too:** their voucher/refund amount is unchanged (u = 1), but they also go through the new service.
- **Combo opacity at the edges:** decision 12 is narrowed, not broken. A customer can now see "partly completed", but never why.
- **Found during the trace, not part of this decision** (tracked in the PR):
  - The storefront `StatusBadge` already leaks a raw `NEEDS_REVIEW` label to customers.
  - `refundNotice()` used `selling_price` as the refund amount.
