**Context:** The founder asked for a critique, not a copy — which of the reference's ideas are real upgrades versus scope creep or a design mistake this ADR already deliberately avoided. Each item below was judged on its own merits against this codebase's existing conventions, not adopted because the reference had it.

11. **Per-game SEO's *UI* moves out of `EditGameModal` into its own list+edit screen on the new SEO page — decision 1's data placement (`Game.seo_*` columns) is unchanged, only where it's edited.** A dedicated `Game SEO` list (search, complete/incomplete/missing filter, per-row completeness) with its own edit view mirrors this codebase's own established list-page-plus-edit pattern (`/admin/vouchers`, `/admin/withdrawals`) better than bolting SEO fields onto an unrelated catalog-editing modal — the same reasoning that already justified splitting `reseller_footer_settings` out of `reseller_branding` (`ADR-028` addendum decision 10) applies again here: a distinct editing concern gets its own surface.

12. **Structured data (JSON-LD) added — `Product`/`Organization`/`Breadcrumb` schema toggles on `reseller_seo_settings`, plus `schema_brand`/`schema_category` columns on `Game`.** Real rich-snippet value or search-result quality, not a vanity add. No new dependency — JSON-LD is a `<script type="application/ld+json">` tag with a computed object, natively supported by `generateMetadata()`'s existing approach (decision 5). `schema-dts` (types only, zero runtime cost) is worth adding for authoring safety, not required.

13. **Scripts manager replaces decision 2's flat `custom_head_script`/`custom_body_end_script` column pair with a new `seo_scripts` table** (`name`, `location` enum `head`/`body_end`, `code`, `priority` int, `reseller_id` nullable — null means global, `is_active`). A real upgrade over two flat fields: ordered, multiple scripts, reseller-scoped even with only one reseller today — the identical "build the real shape ahead of a stated future direction" reasoning `ADR-028`'s `reseller_branding` already used. Basic pre-save validation (well-formed `<script>`/tag balance, not a full HTML parser) mirrors the reference's own "Validate Script" affordance.

14. **Crawler / `robots.txt` management added** — a new `crawler_rules`-shaped config (per-bot allow/block covering search engines, social-preview bots, and AI-training bots, plus crawl-delay and disallow-path lists), rendered through Next.js's **native** `app/robots.ts` (`MetadataRoute.Robots`) — no library, the framework already generates `robots.txt` from a typed config object. Genuinely timely (AI-scraper blocking is a real, current concern), not scope creep for its own sake. A curated default bot list plus an "Add Custom Rule" escape hatch, matching the reference's own pattern, rather than trying to enumerate every bot that will ever exist.

15. **Redirects gain a `hit_count` column, incremented every time the `middleware.ts` lookup (decision 9) actually fires one.** Cheap, real operational value — shows which old URLs are still being followed versus safe to prune. Regex matching and CSV bulk-import (also in the reference) are explicitly **not** adopted — exact-path matching (decision 3, unchanged) already covers the realistic slug-rename case, and neither earns its complexity for a single-reseller MVP with a handful of redirects; revisit only if a real need surfaces, not preemptively.

16. **Sitemap generation is fully automatic via Next.js's native `app/sitemap.ts`, with no admin-configurable priority/changefreq controls — explicitly rejecting that part of the reference.** Google has long since stopped meaningfully using `<priority>`/`<changefreq>` — exposing them as admin knobs would be config with no real SEO effect, the same "don't invent a metric without real basis" reasoning this ADR's own decision 4 already applied to the vanity score below. "No admin controls" doesn't mean "invisible" — the SEO Overview page (decision 17) gets one read-only status line (URL count) plus a direct link to `/sitemap.xml`, so the admin can actually see what's in it without needing a shell/curl. A status line, not a setting — nothing on it is editable.

17. **The reference's single weighted "Overall Score % + letter grade" is explicitly rejected, not adopted — it's exactly the vanity metric this ADR's own decision 4 already ruled out.** Its **Recommendations** (actionable, severity-tagged suggestions with a "Fix Now" jump-link) and **Recent Issues** (a scannable, per-row-actionable table) panels *are* adopted for the Overview page — a real improvement over a static checklist alone, and consistent with this codebase's existing severity-pill dashboard convention (`/admin/blacklist`'s blocked-attempt history). Both are computed views over existing data (`Game.seo_*` completeness, redirect/script counts) — no new storage.

18. **Per-game SEO edit view gains: character counters (70/160, matching Google's real truncation points), a "Use Game Image" button that copies the game's existing catalog image into `seo_og_image` instead of requiring a re-paste, and a `no_index` boolean column on `Game`** (renders a per-game `noindex` meta directive). All cheap, all real value, all still inside decision 1's existing `Game.seo_*` scope — `no_index` is the only new column among the three.

19. **The reference's "Analytics Permissions" (a platform-level allow/disallow gate before a reseller may configure their own GA/FB/TikTok pixel) is explicitly rejected.** Decision 6 already established there is no reseller self-service portal — a permission gate for a reseller managing their own tracking solves a problem that doesn't exist yet in this codebase's single-reseller reality; revisit only alongside Phase 2's actual self-service portal, per decision 6's own already-recorded reasoning.

20. **Admin nav placement: "SEO" becomes a collapsible nav *group*, not a single link** — sub-items Overview / Global Settings / Meta Templates / Game SEO / Redirects / Scripts / Crawler. `AppSidebar.tsx` has no existing collapsible-group pattern (every current item is a flat single link) — this is new sidebar UI work the build session needs to add, not a reuse of an existing mechanism.

**Addendum 3, 2026-08-22 (same day, immediately after build+browser-verification) — one refinement, founder-requested during the verification walkthrough.**

21. **`crawler_rules.disallow_paths` (per-row) is joined by a new shared `reseller_seo_settings.crawler_default_disallow_paths` — a single list merged into every `is_allowed` bot's own disallow set at render time (`SeoController::robots()`), covering bots added to `crawler_rules` later too, with zero per-row re-entry.** Surfaced live: the founder asked "so kalau nak block satu route untuk semua bot, kena update satu-satu ke?" while walking through the Crawler page — the honest answer given the ADR's own design (per-row `disallow_paths`) was yes, because a robots.txt `User-agent` block never inherits from `*`; a named bot with its own block ignores whatever `*` disallows entirely. Rather than accept that duplication, added one shared field instead. Seeded with `['/order/status', '/api']` (`CrawlerRuleSeeder`) — a specific customer's order-tracking page (no SEO value, a real privacy concern if indexed) and this app's own Next.js route handlers (not content). `Admin\SeoController::updateSettings()` now calls `PublicSeoController::forgetRobotsCache()` in addition to its own `forgetCache()`, since this field lives on `reseller_seo_settings` but is consumed by the `robots()` endpoint's own separately-cached response.

**Consequence to track (addendum 3):** `crawler_default_disallow_paths` lives on the reseller-scoped `reseller_seo_settings` table, but `crawler_rules` itself is deliberately global (decision 14's own migration doc comment — one robots.txt per domain). Today, with exactly one reseller/domain, merging the one settings row's defaults into the one global rule set is correct by construction. If Phase 2 ever onboards a second reseller with its own domain, this merge needs a real decision — which reseller's defaults apply to a global rule set that doesn't itself know which domain served the request — not an extension of today's single-tenant shortcut. Flag alongside decision 6's already-recorded Phase-2 access-model gap, not a new category of unresolved question.
