# ADR-044: Zod runtime schema validation at the admin/storefront API boundary (built 2026-08-27)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted, built — 2026-08-27 (grilled via `/mattpocock-skills:grilling` before implementation, three rounds).

**Context:** Neither `admin/` nor `storefront/` has ever had a runtime schema-validation layer at the API boundary, despite `AGENTS.md`'s own standing rule ("Zod/equivalent at the frontend's API boundary") — `grep` for `zod`/`yup`/`joi` across both apps' `package.json` returned nothing, and neither app has a single email/phone regex or form-schema check anywhere. Every request payload (`CheckoutPayload`, etc.) is a compile-time-only TypeScript `interface`; every response is blind-cast (`payload as T` in `apiFetch<T>()`) with zero runtime check that the backend actually returned that shape. This is **not** a security gap — every mutating backend route already has full `FormRequest` coverage (44/44) and money is never trusted from the client regardless (ORD-9) — it's a client-side UX and contract-drift-detection gap: a typo currently round-trips to the backend and back before the customer sees an error, and a backend response-shape change would fail silently (wrong/undefined field read) rather than surface anywhere.

Fact-finding before the decision: `storefront/src/lib/api-client.ts` has 2 commits, both from initial scaffold (2026-07-23/26) — essentially frozen since. `OrderForm.tsx`/`checkout.ts` (the checkout-critical files) are touched roughly every 1-2 weeks (7 and 5 commits respectively, last 2026-08-14) — an "opportunistic, only when the file is already being touched" rollout would reach them fine on its own. Neither app has a toast library or any error-monitoring SaaS (Sentry etc.) — the established error-UX pattern is a local `useState<string|null>` populated in a `catch` block, rendered as an inline `<p>` banner (`storefront`'s `Step1AccountInfo.tsx`/`ReviewModal.tsx`, `admin`'s `vouchers/page.tsx`/`withdrawals/page.tsx` — identical shape both apps). Scope-sizing: storefront has 8 files / ~16 functions consuming `apiFetch`/`apiUpload`; admin has 17 files / ~120 functions — a ~7-8x larger surface, making a single big-bang rollout across both apps in one PR an unreasonable lift for admin specifically.

**Decision:**

1. **Add `zod` (latest stable) as a dependency to both `admin/` and `storefront/`.** No shared package/workspace between the two apps (deliberate divergence already established by `api-client.ts` itself, per ADR-011's guest-checkout-vs-Bearer-auth split) — schema duplication across the two apps for overlapping shapes is accepted, not solved with new shared-package infra, matching the existing precedent rather than opening an unrelated monorepo decision inside this ADR.
2. **Storefront: full rollout now, all ~16 `apiFetch`/`apiUpload` consumer functions** (`checkout.ts`, `catalog.ts`, `vouchers.ts`, and the rest of `storefront/src/lib`) — small enough surface to do in one pass, and includes the highest-value target (checkout) immediately rather than waiting for it to be "opportunistically" touched.
3. **Admin: convention-only this ADR, no mass migration.** Same opportunistic trigger `ADR-038` already established for the PrimeReact migration — a file already being touched for an unrelated reason gets zod added to its API calls as part of that same change; a live, tested screen is never migrated solely to add validation. No new lint/CI enforcement — pure discipline, matching this repo's existing solo-founder governance model.
4. **Both request-side and response-side validation, in scope together** — a request schema validates form payload before `apiFetch` is called (client-side UX only, never a security boundary — the backend `FormRequest` remains sole authority); a response schema replaces the current `payload as T` blind cast with `schema.parse()`.
5. **Response schemas run in non-strict (passthrough/strip-unknown) mode and fail soft.** An unrecognized-but-harmless extra field the backend adds later must never crash checkout; a genuine mismatch (missing/wrong-typed field) logs and falls back to using the raw payload as-is rather than throwing — response validation's job here is contract-drift *detection*, not a new production failure mode on the money path.
6. **`z.infer<typeof Schema>` becomes the source of truth for request/response types**, replacing hand-written `interface`s (`CheckoutPayload`, `CheckoutResult`, `ValidatePlayerResult`, etc.) in the files it touches — a schema and a separately-maintained interface would just be two copies of the same fact able to drift from each other, which is the exact problem this ADR exists to close.
7. **Schemas are colocated in the same file as the function that uses them** (e.g. `CheckoutPayloadSchema` inside `checkout.ts`, next to `submitCheckout()`) — no new `lib/schemas/` directory. Matches this codebase's existing pattern (the interfaces they replace already lived inline).
8. **New backend endpoint, `POST /api/client-errors`** — public (no auth; storefront is guest-checkout with no auth concept, and reusing this same endpoint from admin rather than building a second authenticated one keeps this small), throttled (reusing `ADR-014`'s `throttle:` pattern), with its own `FormRequest` per `AGENTS.md`'s "every mutating route gets a FormRequest" rule, accepting `{schema, path, error}` and writing it via `Log::warning` — mirrors `CheckoutController`'s existing structured-logging shape. Purpose is narrow: give the founder backend-log visibility into response-schema drift reports (item 5) that would otherwise only ever appear in a customer's own browser console, invisible to anyone. This is a small bespoke log sink for one specific event type, **not** a general error-monitoring/observability platform (no Sentry-equivalent scope) — it does not catch arbitrary JS exceptions, has no dashboard, and isn't intended to.

**Rationale:** Every piece of this decision traces back to something already established in this codebase rather than inventing new conventions — the opportunistic-rollout trigger (item 3) mirrors `ADR-038`, the FormRequest-per-mutating-route rule (item 8) mirrors `AGENTS.md`'s own standing rule, the inline-banner error surface (item 4/5's UX) reuses the pattern already live in both apps, and the schema-duplication-across-apps trade (item 1) matches `api-client.ts`'s own precedent. The one genuinely new piece of infra is the `/api/client-errors` endpoint (item 8), deliberately scoped as narrowly as possible — a single throttled log sink, not a monitoring platform — specifically to avoid solving a much bigger problem (general frontend observability) inside an ADR whose actual purpose is boundary validation.

**Consequence to track:** Admin's ~120-function surface remains fully unvalidated until individual files are opportunistically touched — unlike storefront (item 2, done in full now), there is no guarantee admin's higher-risk mutating screens (Withdrawals, Vouchers, Price Sync) get zod coverage on any particular timeline. If a real incident traces back to an unvalidated admin form, that's the signal to revisit item 3 rather than continuing to wait opportunistically. Also track: `/api/client-errors` (item 8) is new unauthenticated public surface — its throttle configuration needs the same periodic sanity-check this codebase already gives its other public-throttled routes, so it can't become a spam/log-flood vector.

**Consequence to track (addendum 4):** llms.txt has no confirmed, universal consumer today the way robots.txt does — Google/Bing/social-preview bots are proven; which AI systems, if any, actually fetch and use `/llms.txt` is still an open question industry-wide. Built because it's cheap and harmless (a markdown GET route, `force-dynamic`, no new storage), not because adoption is proven. If the convention is abandoned by the community, this route costs nothing to leave in place or remove later — no data model depends on it.
