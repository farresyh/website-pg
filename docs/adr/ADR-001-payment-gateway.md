# ADR-001 (D1): Payment gateway — Xendit

> **Standing (2026-10-09):** Superseded — CHIP-only (ADR-022 2026-09-01 addendum); xenPlatform dropped (ADR-059). Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-07-23. **FULLY SUPERSEDED.** (1) The xenPlatform clause was dropped entirely by [ADR-059](./ADR-059-reseller-portal.md) decision 6 (not deferred — see the OWNED addendum below). (2) Xendit-as-the-gateway was replaced by [ADR-022](./ADR-022-multi-gateway-payment-strategy.md) — CHIP added alongside 2026-08, then **Xendit removed entirely 2026-09-01** (ADR-022's CHIP-only addendum; code archived to `archive/xendit-gateway` + tag `xendit-archive-2026-09-01`). CHIP is the sole gateway, live in production with real money since 2026-09-03.

**Decision:** MVP uses Xendit's standard Invoice/Payment API only (single merchant account, platform collects 100% of payment). **xenPlatform** (sub-account fund-splitting) is deferred to Phase 2.

**Rationale:** Xendit confirmed available in Malaysia (FPX, DuitNow QR, cards) with xenPlatform available for future marketplace-style splitting once real third-party resellers are onboarded with automatic settlement. Using xenPlatform on day 1 adds sub-merchant KYC/onboarding overhead the MVP doesn't need — all money is the platform owner's in MVP, so no split is required.

**Addendum — payment-gateway seam, 2026-07-23:** Xendit requires business-credential/KYC verification before approving an account, and approval isn't guaranteed — if Xendit rejects the platform's business verification, a fallback gateway with a sub-account/split-payment feature comparable to xenPlatform would be needed (that feature, not just "any gateway," is the actual requirement driving the fallback candidate list). Unlike the Supplier situation (ADR-006), no second payment gateway is confirmed or researched yet, so building a second full implementation now would be guessing at an unconfirmed shape. Instead: build directly against Xendit's Payment Request API, but behind a **thin** `PaymentGateway` interface (`createPayment()`, `getPayment()`, `verifyWebhookSignature()`, `parseWebhookEvent()` — see `app/Services/Payment/`) so that *if* a swap is ever needed, it costs one new adapter implementation, not a rewrite of Order/Ledger business logic. This is a smaller, cheaper seam than the Supplier Adapter (4 methods vs. 5, no capability-flag complexity) precisely because — unlike suppliers — only one gateway is ever actually in use at a time; the interface exists purely to isolate switching risk, not to run multiple gateways concurrently. Does not change the MVP decision above (Xendit only, xenPlatform deferred) — it only changes how the Xendit integration is wired internally.

**Addendum — xenPlatform sub-account type: OWNED, not MANAGED, 2026-07-24.** **⚠️ Superseded — [ADR-059](./ADR-059-reseller-portal.md) decision 6 (2026-08-30):** xenPlatform is dropped from the platform's plans entirely, not deferred. All customer money — platform-owner and every reseller storefront — is collected into one company CHIP account and the ledger does the split; reseller payout is a manual bank transfer via the existing WTH-1..5 flow (the `Withdrawal` bank fields this addendum sized are still the right shape). The rest of this addendum is kept for the research record only.

Researched directly against Xendit's docs (docs.xendit.co/xenplatform/accounts, help.xendit.co) before this decision, not assumed. xenPlatform has two sub-account types with materially different reseller-facing behavior:
- **MANAGED** — the partner (reseller) registers via an invitation email, gets their own real Xendit dashboard login, completes their own onboarding/KYC, and can add their own bank account and withdraw directly through Xendit's own UI, potentially bypassing our Admin Panel entirely for that action.
- **OWNED** — sub-accounts are invisible to partners and fully controlled by the platform ("department store" model — the customer, and here the *reseller*, only ever sees the platform, never Xendit). Minimal KYC. Critically, Xendit has no feature for an OWNED sub-account to register its own withdrawal bank account — payout is pushed by the **Master Account** (us) via the Disbursement/Payout API using a `for-user-id` header identifying the sub-account, or via Batch Disbursement from the Master Account's own dashboard.

**Decision:** Phase 2 reseller sub-accounts will be **OWNED**, not MANAGED. Founder requirement: resellers must never be aware Xendit is the underlying processor — the platform is the only party they interact with for payouts, full stop. MANAGED directly breaks this (separate Xendit login, Xendit-branded dashboard). OWNED matches it exactly — Xendit is invisible to the reseller by design.

**Consequence to track:** because OWNED sub-accounts don't store their own withdrawal bank account with Xendit, the platform must supply the destination bank account on every Disbursement API call. This means the `Withdrawal` model's `bank_name`/`bank_account_no`/`bank_account_holder` fields (built this session for the MVP platform-owner withdrawal flow, WTH-1..5) are **already the right shape for Phase 2** — no rework needed there. The existing Admin Panel approve/reject/complete workflow also carries forward as the reseller-facing "payout" experience: Phase 2 only needs to swap the `complete` action's "admin marks it done after transferring manually" step for "a real Disbursement API call, `for-user-id` = the reseller's sub-account ID" — the reseller still only ever sees our Admin Panel's status, never Xendit's. Also unverified and worth confirming directly with Xendit before Phase 2 build starts, not assumed from documentation research alone: OWNED sub-accounts are reported as disabled by default for Indonesia-based accounts — Malaysia availability wasn't confirmed in this research pass.

**Addendum — multi-gateway seam widened, 2026-07-25:** founder flagged that Xendit's real fee rates (discovered while building the Payment Methods tool, see docs/prd.md §14) are high enough that a gateway swap or running two gateways concurrently side-by-side (not just a one-time future swap) is now a real possibility, not a hypothetical "if Xendit rejects KYC" scenario. This changes the 2026-07-23 addendum's founding assumption ("only one gateway is ever actually in use at a time") — but the fix applied is still schema/plumbing readiness only, **not** a second gateway implementation, for the same reason ADR-006 gives for suppliers: no second gateway is researched or confirmed yet, so building one now would be guessing at an unconfirmed shape.

What changed: `payment_methods` (the SET-7/SET-11 admin tool) gained a `gateway` column — every channel now carries which gateway owns it, not just its fee rate. `CheckoutService::initiate()` no longer constructor-injects one fixed `PaymentGateway`; it takes the resolved gateway as a method parameter instead, so a single checkout can route different channels to different gateways without touching pricing/ledger/order logic at all. A new `PaymentGatewayFactory` resolves an implementation by name through the container (`payment-gateway.<name>` binding keys), throwing `UnsupportedPaymentGatewayException` for anything not registered — today that's every name except `'xendit'`. `PaymentGateway::class`'s own default binding stays Xendit-only, since the webhook route (`/api/webhooks/xendit`) is inherently gateway-specific by URL and doesn't need per-request resolution.

**Consequence to track:** when a second gateway is actually chosen and researched, it costs exactly one new adapter (implementing `PaymentGateway`) plus one new `payment-gateway.<name>` container binding plus admin flipping the right `payment_methods.gateway` values — no changes to `CheckoutController`, `CheckoutService`, the Order model, or the ledger. The webhook side is the one place that *does* need new code per gateway: each gateway's callback verification/parsing is different enough (Xendit's is a plain token comparison, not HMAC) that it gets its own controller + route, mirroring how `XenditWebhookController` is Xendit-specific today, not a shared abstraction.

**Addendum — `customer` object required, fixed and verified live, 2026-07-25 (same session):** the Payment Methods "Test" action (built earlier this same session) immediately surfaced a real gap: Xendit's Payment Request API requires exactly one of `customer`/`customer_id` for at least the FPX channel — confusingly worded as "Only one of 'customer' or 'customer_id' should be present" even when *neither* was sent (a `oneOf`-style JSON Schema validator's generic message, confirmed by re-checking docs.xendit.co/apidocs/create-payment-request). Guest checkout never collected a customer name, only email/phone/player_id, so this required a small, deliberate product decision, not just a code fix: founder chose to **add a real `customer_name` field to checkout** (not a placeholder derived from email) — see the create Order migration and `CreateCheckoutRequest` for where it landed. New `App\Services\Payment\PaymentCustomer` DTO carries `referenceId`/`givenNames`/`email`/`mobileNumber` into `XenditGateway::createPayment()`'s `customer` object (`type: INDIVIDUAL`, matching Xendit's real schema). **Verified live against the real Xendit sandbox** via the Payment Methods "Test" action: `AMBANK_FPX` and `GRABPAY` both now return `last_test_result: "success"` (previously the `customer`/`customer_id` failure) — not just unit-tested against a mock. `CARDS` still fails (needs `channel_properties.card_details`, a separate, expected gap — card entry happens via Xendit-hosted fields per PAY-4, not something the Payment Methods tool itself should supply).
