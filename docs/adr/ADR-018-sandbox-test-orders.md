# ADR-018: Sandbox Test Orders — a middleware-only tool for exercising the real Order lifecycle without touching real data or real money

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted (design) — 2026-07-27 (grilled with the founder one decision at a time, same session as ADR-017's build; explicit founder instruction: record the full plan here for review before writing any code)

**Context:** Testing an order-lifecycle feature (Resend Delivery, order detail, Delivery Logs) today means either driving the real storefront through a real Xendit test-mode checkout every time, or creating an `Order` row by hand via `tinker` against `/admin/orders` and manually deleting it from the DB afterward once done — the exact workflow used to verify ADR-017 live this session. Founder flagged this as untenable for repeated testing and pointed to a real reference: the legacy KeroxShop admin's own middleware "Orders" page (`manage.keroxshop.com`, screenshot reviewed live) has a "Create Test Order" form and a "Test Orders" results table — but by the founder's own account, despite being labeled "test," that table is **not actually isolated** from real order data. That's the specific mistake this ADR exists to not repeat: the goal is a real, working sandbox — not a "test" label that doesn't actually mean anything downstream.

Also confirmed live (not assumed) before deciding the payment approach: fetched `docs.xendit.co/apidocs/simulate-payment-test-mode` directly — Xendit's Payment Request API v3 has no separate test host (test vs. live is purely which secret key is used) and ships an official `POST /v3/payment_requests/{id}/simulate` test-only endpoint that pushes a payment toward `SUCCEEDED` via the normal webhook. Real and useful for testing the *payment* pipeline specifically — but that pipeline is already proven live (`ADR-001`, the Payment Methods "Test" action) and is not what this sandbox exists to exercise, which is why decision #3 below skips it entirely rather than building against it.

**Decision (per sub-area, each grilled with the founder one at a time before being accepted):**

1. **Storage: reuse the real `orders` table, one new `orders.is_test` boolean column (default `false`) — not a parallel schema.** A sandbox order is a real `Order` row. This is what lets `PricingService`, `OrderResendService`, `OrderFulfillmentService`'s status-transition logic, `order_resend_attempts`, and every existing money/delivery code path run **completely unchanged** against it — the only thing that makes it "sandbox" is (a) which controller/page can reach it and (b) two narrow, explicit safety guards (decisions #5/#6). This directly targets the legacy system's actual flaw: a "test" label is worthless unless something concrete enforces exclusion downstream — here that enforcement is a hard, unconditional scope, not a flag anyone has to remember to check.
2. **UI/API placement: fully separate from `/admin/orders`, not a filter/tab inside it.** New page, `/middleware/sandbox` (naming TBD at build time), backed by a new, dedicated `Middleware\SandboxOrderController` (`index`/`store`/`show`/`resend`/`destroy`) whose every query is unconditionally scoped to `is_test = true`. `Admin\OrderController::index()`/`show()` gain a **permanent, unconditional** `where('is_test', false)` — not an admin-toggleable filter — so the real operational queue can never show sandbox data regardless of future changes to that page. Founder's own reasoning: `/admin/orders` is a money-critical tool that must be 100% trustworthy at a glance (e.g. the "Need Action" count); mixing in sandbox data — even filtered, even badged — adds a class of mistake (a filter bug, a future teammate not knowing a toggle exists) that's cheaper to eliminate structurally than to guard against per-screen. This also matches this project's own existing `/middleware` vs `/admin` split (supplier-integration/dev tooling vs. running-the-shop) — DEV-1/DEV-2's raw supplier tester already lives in `/middleware` for the same reason.
3. **Creation skips Xendit entirely — `payment_status` is set to `paid` immediately, no payment call of any kind.** Admin picks a real `Game`/`Package` from our own catalog (via the existing `GET /api/games`/`GET /api/games/{game}/packages` admin endpoints — not raw supplier fields typed by hand, unlike legacy's page) so `PricingService` computes real, consistent money figures. Player ID/Server ID and customer email/name are editable but default to fixed sandbox placeholders. Rejected alternative: Xendit's own `/simulate` endpoint (confirmed to exist, see Context) — not used, since it would add an async payment_status=pending wait for a pipeline already proven live elsewhere, for zero benefit to what this tool actually needs to prove.
4. **Sandbox orders are created directly at `delivery_status = failed`** (skipping `not_started`/`processing`) — framed as "pretend a first delivery attempt already happened and failed." This is deliberate, not an oversight: it's the exact state `OrderResendService`'s existing guard requires before a resend is actionable, so a freshly created sandbox order is immediately usable with the real, unmodified Resend Delivery UI — no separate "first delivery" affordance needs to be built.
5. **Delivery never calls the real `GamevionAdapter` — a new `FakeSupplierAdapter` (`App\Services\Supplier\`, implements the existing `SupplierAdapter` interface) is used instead, swapped in by construction, not by branching inside the fulfillment/resend services.** `Middleware\SandboxOrderController::resend()` builds its own `OrderResendService`/`OrderFulfillmentService` instance directly (constructor-injecting `FakeSupplierAdapter`) rather than resolving `SupplierAdapter` through the container's default binding (which stays `GamevionAdapter`, untouched, for the real `Admin\OrderController` path) — the same substitution the Adapter pattern (`ADR-006`) exists to make cheap. Runs **synchronously, inline, no queue dispatch** — `ResendOrderDeliveryJob`/`FulfillOrderJob` are not involved at all for sandbox orders, since there's no real network latency to hide from the admin request, and it means a sandbox order never depends on a queue worker actually running (a real, documented gotcha that already bit a live session this week per `prd.md`'s Price Sync founder-testing note). The admin chooses the simulated outcome (success, or failure with a canned error code/message) each time via an extra control in the reused Resend Delivery modal, visible only in the sandbox context — a fake adapter that only ever "succeeds" would make it impossible to test the exact `need_action` → `Resend Delivery` → outcome loop this tool exists to exercise.
6. **One new, narrow guard in existing fulfillment code — the only touch to money-critical logic this ADR makes:** `OrderFulfillmentService::creditProfit()` gets `if ($order->is_test) { return; }` before it writes any `LedgerEntry`. This is deliberately the single, explicit, easy-to-audit place a sandbox order is stopped from ever reaching the real ledger — chosen over a parallel "sandbox fulfillment service" specifically so the real status-transition/reference-number logic stays 100% shared and unduplicated between real and test orders (only the money-writing tail end is skipped), and chosen over swapping `LedgerService` itself (a `final` class, not behind an interface — substituting it would be a much larger change for the same guarantee).
7. **Cleanup is a real delete action in the sandbox page itself** (single row, and a "Delete All Test Orders" bulk action) — hard-deletes the `Order` row; `order_resend_attempts` cascade-deletes with it (existing FK). Safe with no residue precisely because of decision #6: a sandbox order, by construction, never had a real `LedgerEntry` to leave behind.
8. **Frontend: extract, don't duplicate.** The order-detail cards, the Resend Delivery modal, and the Delivery Logs table (already built for `/admin/orders`, ADR-017) are pulled into shared components consumed by **both** `/admin/orders` and the new `/middleware/sandbox` page, each against its own backend endpoint (`Admin\OrderController` vs. `Middleware\SandboxOrderController`). This is what actually delivers the founder's stated goal — "output yang sama macam workflow production" — without the two pages' behavior silently drifting apart over time the way two independently-maintained UIs would.

**Rationale:** Every decision above keeps `PricingService`, `OrderStatusService`, `OrderResendService`'s validation logic, and the `order_resend_attempts` audit trail completely unchanged and shared — the only new, sandbox-specific code is the `is_test` scope, the `FakeSupplierAdapter`, one guard line in `creditProfit()`, and the dedicated controller/page. This is the same "deepen the module, don't reshape the seam" discipline `ADR-001`/`ADR-006`/`ADR-014`/`ADR-017` already established, applied to a testing concern instead of a business feature — and it's the concrete difference between this design and the legacy page it was prompted by: isolation enforced at the query/ledger boundary, not left as an unenforced label.

**Consequence to track:** this ADR records *design intent only* — no code exists yet, matching this project's own established practice (`ADR-013`/`ADR-015`/`ADR-016`/`ADR-017`). Update `prd.md` §14/§15 once this actually ships. Decision #5's exact `FakeSupplierAdapter` outcome-picker UI and decision #8's exact shared-component boundaries are implementation details to finalize during the build session, not decisions still open — the founder-facing behavior (mock delivery, admin picks the outcome, fully separate page, real delete) is what's confirmed here.

**Addendum — shipped, 2026-07-30/31 (build session, same day as the founder's 2026-07-30 pointer marking this item 1 of the next-session order) — every decision above built exactly as designed, no deviations:** `orders.is_test` (boolean, default `false`) added via migration; `Order::$fillable`/`$casts` updated. `App\Services\Supplier\FakeSupplierAdapter` implements `SupplierAdapter` with zero network calls — `createOrder()` branches on a constructor-supplied `simulateSuccess` flag, returning a canned `SANDBOX-*` supplier_ref on success or the admin's chosen error_code/error_message on failure; `validatePlayer()` throws `ValidationNotSupportedException` (sandbox orders never validate against a real supplier). `Middleware\SandboxOrderController` (index/store/show/resend/destroy/destroyAll), every query unconditionally scoped `is_test = true`; route-model-bound actions (`show`/`resend`/`destroy`) additionally `abort(404)` if the resolved Order isn't a sandbox row, since binding alone only knows the primary key. `store()` mirrors `CheckoutController`'s own game/package/reseller resolution (`Reseller::platformOwner()`, `PricingService::calculate()`) but skips Xendit entirely and creates directly at `payment_status=paid`/`delivery_status=failed`. `resend()` builds `OrderFulfillmentService`/`OrderResendService` via `new` (not container resolution), constructor-injecting `FakeSupplierAdapter` — confirmed live that this correctly bypasses the container's real `GamevionAdapter`/`CircuitBreakingSupplierAdapter` binding entirely, synchronously, no queue. `OrderFulfillmentService::creditProfit()` gained the one-line `is_test` guard (decision #6). `Admin\OrderController::index()`/`show()` gained the permanent `where('is_test', false)`/`abort(404)` scope (decision #2) — and, found only while implementing (not in the original decision list, but directly implied by it): the same guard was added to `retryDelivery()`/`resend()` too, since a sandbox order id could otherwise reach the real, queued `GamevionAdapter` path via those two endpoints despite never being visible through `index()`/`show()` — closing a real isolation gap decision #2's original wording didn't explicitly call out.

Frontend (decision #8): `OrderDetailCards`/`DeliveryLogsTable` extracted from `/admin/orders`'s page component into `admin/src/components/orders/`, now consumed by both `/admin/orders` and the new `/middleware/sandbox` page unchanged. `ResendDeliveryModal` gained an optional `sandbox` prop — when set, renders a "Simulated Outcome" success/failure toggle (plus optional error code/message fields on failure) and posts to the sandbox endpoint instead of the real one; every other field (package picker, live cost reconciliation, player-ID re-validation gate) behaves identically in both contexts, confirmed live: a sandbox order against a game with `player_validator_enabled` correctly rejected the resend with the same "Please re-validate this Player ID" message the real flow gives, since `OrderResendService`'s validation logic runs completely unchanged. New `CreateSandboxOrderModal` (game/package pickers via the existing `lib/games.ts`, not shared with `/admin/orders` since real orders have no equivalent admin-creation flow). New `/middleware/sandbox` page + `lib/sandboxOrders.ts` API client; new "Sandbox" nav entry in the Middleware Panel layout.

19 new backend tests (`SandboxOrderControllerTest` 14, `OrderFulfillmentServiceTest` +1 is_test-guard case, `Admin\OrderControllerTest` +4 sandbox-exclusion cases); full backend suite **483/483 green**. `npx tsc --noEmit`/`next build` clean on `admin/`. Verified live end-to-end, twice — once via direct API calls against the real local Herd backend (create → resend-success → resend-failure → delete, confirming zero `LedgerEntry` rows and a real `404` from every `Admin\OrderController` action against the sandbox order id), once through the actual browser UI (create a test order via the modal, resend with a simulated failure showing the typed error code/message in Supplier response, resend again with simulated success reaching `delivered` with a `SANDBOX-*` supplier_ref and the Resend Delivery button correctly disappearing once no longer resendable, Delivery Logs showing both attempts with the real admin's name, delete, and confirmed `/admin/orders` shows only real orders throughout).
