# ADR-028: Platform & Reseller Settings — reseller-scoped branding vs. platform-wide config split (built 2026-08-22)

> **Standing (2026-10-09):** In force. Build and live status: [`prd.md` §15](../prd.md). The text below is a dated record; a later addendum in this file overrides earlier text, including the **Status** line.

**Status:** Accepted — 2026-08-21 (grilled with the founder one decision at a time via `/mattpocock-skills:grilling`, before any code touched); **built and browser-verified 2026-08-22**, see its addendum below and `docs/prd.md` §14's matching entry. **2026-10-02 addendum:** decision 4's bulk markup scope widened + a combo pricing-corruption bug fixed, cross-ref `ADR-094`

**Context:** Two live storefront backlog items — dead links in `SeoBlurb.tsx`/`SiteFooter.tsx` (real destination URLs never supplied) and a placeholder WhatsApp number in `OrderStatusTracker.tsx`/`BottomNav.tsx` plus a missing Terms & Conditions/Privacy Policy page — were sitting in `prd.md`'s standing pointer as "blocked on the founder." The founder pushed back on that framing: these values are hardcoded directly in storefront component code today because no admin-editable settings mechanism exists at all (`prd.md` §6.17 SET-1..11 / §6.16 SEO-1..7 are ✅ tracked MVP-priority requirements, currently 100% ⬜ not started per §15) — not because the founder is withholding the actual values. Building the settings mechanism turns "blocked on a dev session every time a link changes" into "founder edits it in the admin panel," which is the real fix; the two backlog items are downstream symptoms, not the thing to solve directly.

`Reseller` (`ADR-013`: the platform owner is the first row, not a parallel single-tenant concept) has no branding/contact/SEO fields today — only business/pricing columns (`business_name`, `contact_name`, `email`, `phone`, `markup_pct`, `max_markup_pct`, `domains`, `status`, `xendit_subaccount_id`, `notes`). `prd.md` §6.17 describes SET-1/SET-5/SET-10 as flat "Admin Settings" with no reconciliation against the `Reseller` table's existence, and multi-reseller domain-routing is itself still an open question (§12: "Will reseller domains (Phase 2) use subdomains or custom domains... needs a design pass before Phase 2 starts") — so today's storefront is a single deployment serving exactly one `Reseller` row, resolved via the existing `Reseller::platformOwner()` helper (already used by `CheckoutController`/`CatalogController`).

**Decision:**

1. **Split SET-1..11 into two homes by nature, not by numbering: `reseller_branding` (per-reseller, customer-facing) and `platform_settings` (global singleton, ops-facing).** Grouping by "does a future second reseller need their own copy of this, or is it inherently one-per-deployment" cleanly separates every item — see decisions 2/3 below for the actual split.

2. **`reseller_branding` — a new table, 1:1 with `Reseller` (`reseller_id` FK), not columns added directly onto `Reseller`.** Holds: store display name, description, support email, support phone/WhatsApp, Telegram contact link, footer content, social media links (JSON), Terms & Conditions content, Privacy Policy content (SET-1's customer-facing subset, SET-5, SET-10, plus the T&C/Privacy page content the missing-page backlog item needs). Kept as its own table rather than bloating `Reseller` with ~8-10 unrelated columns — mirrors this codebase's existing convention of splitting a distinct concern into its own table rather than growing an existing model (`deactivation_logs`/`price_change_logs` beside `packages`), and keeps `Reseller` itself focused on the business/pricing fields it already has. Deliberately built now, ahead of any real second reseller existing, because a future affiliate/reseller program is a real, stated direction (not a hypothetical) — the founder's own reasoning for accepting this shape over a simpler global-only table.

3. **`Reseller.email`/`Reseller.phone` and `reseller_branding`'s own support-contact fields are deliberately separate, not reused.** The former is internal (admin's own contact channel to reach that reseller); the latter is customer-facing (what a guest sees on the storefront). Conflating them would mean an admin editing their own internal contact record accidentally changes what customers see, or vice versa.

4. **`platform_settings` — a new table, singleton row (not a generic key-value `key`/`value`/`type` store).** Holds: currency, system-wide markup % (SET-2's "apply to all packages" bulk action — likely a default-for-new-packages value plus a triggered bulk-update, not just a stored number; exact mechanics left to the build session), maintenance mode flag + custom message (SET-6), Telegram bot integration (SET-9 — confirmed by the founder as an ops tool, admins receiving order notifications via Telegram, not a customer-facing reseller bot). Fixed columns, not key-value: matches this codebase's own established house style (money is always a typed `_sen` column, never a generic `value` field; every existing settings-shaped model — `Reseller`, `PaymentMethod` — uses fixed columns) and there is no existing precedent anywhere in this codebase for a generic settings-value pattern to extend instead.

5. **SET-4 (backup schedule/retention) excluded from this ADR's scope — genuinely blocked by deployment, not just unbuilt.** `prd.md` §12's own still-open question ("Will backups be stored on local server or cloud storage?") depends on `ADR-020`'s hosting decision, which isn't provisioned yet. A retention-period setting with no real backup job running anywhere to consume it would be inert — the founder's own bar from Q1 of this grilling session ("kalau perkara lain tu tak di block oleh deployment... worth buat") explicitly excludes this. Revisit once `ADR-020` provisioning happens.

6. **SET-8 (email notification toggles) and SET-9's actual sending mechanism excluded — no notification-sending infrastructure exists anywhere in this codebase today.** Confirmed by a direct grep, not assumed: zero `Mail::`/`Notification::` usage anywhere in `app/`; `AdminUser`'s `Notifiable` trait is unused default Laravel scaffolding. SET-9's own *setting* (a stored bot token/chat-id row) is kept in `platform_settings` per decision 4 above since it's cheap and the right home once built, but the feature that would actually consume it — a real notification-sending mechanism (provider choice, queue job, templates) — is a separate, unscoped piece of work, matching this codebase's own established principle against designing a setting for a mechanism that doesn't exist yet (the same reasoning as decision 5).

7. **SET-7 (payment gateway toggle) and SET-11 (transaction fee config) stay exactly where they already are — the Payment Methods tool (`/middleware/payment-methods`), a founder decision from 2026-07-25 predating this ADR — not folded into either new table.** SET-3 (reseller default/max markup, auto-approve) stays Phase 2, unchanged, no real second reseller to configure yet.

8. **Maintenance mode blocks new checkout submissions only — browsing, order tracking, and payment/webhook routes stay live.** A customer who already paid must still be able to check their order status during a maintenance window, and an in-flight payment's webhook must still be able to land and fulfil — freezing those would risk a paid, undelivered order with no way to recover it without manually flipping the flag back off first. Enforced at the specific write endpoint (`POST /api/checkout`), not a blanket route-group gate.

9. **`Reseller::platformOwner()` is reused for the new public branding endpoint, not a second lookup mechanism invented alongside it — with its own risk of being missed later written down twice, not once.** Same hardcoded-to-the-single-MVP-row pattern `CheckoutController`/`CatalogController` already use, and the same caveat `ADR-013` already recorded for those two call sites now explicitly extends to a third: `Reseller::platformOwner()`'s own doc comment gets updated to enumerate every call site once this is built, so a future session replacing it for real Phase 2 domain-routing has one place that lists everywhere it needs to change — not a call site quietly missed because the ADR that mentioned it wasn't re-read.

**Rationale:** The reseller-scoped/platform-wide split (decisions 1-4) isn't cosmetic — it's the same distinction `ADR-013` already drew for pricing/ledger (every Order references a `Reseller`, but ledger accounting itself is platform-wide infrastructure) applied to a new area, and building `reseller_branding` as its own table now means a real second reseller (Phase 2, or sooner if the affiliate/reseller direction the founder mentioned materializes) gets working branding for free, no later data migration out of a global-only settings table. Decisions 5/6 both trace back to one principle stated repeatedly elsewhere in this codebase's own history (`ADR-015`/`ADR-016`/`ADR-020` decision #1): don't design a setting for a mechanism that doesn't exist yet — a toggle with nothing behind it is worse than no toggle, since it implies a capability the platform doesn't actually have.

**Addendum, 2026-08-22 — Footer Settings split into its own tab/table, three new legal-page routes, rich text + templating for legal content, and a bounded Footer Games feature (grilled with the founder via `/mattpocock-skills:grilling`, mockup-driven — reviewing a working HTML skeleton of the Settings screen surfaced every decision below).**

**Context:** Reviewing a visual mockup of this ADR's Settings screen, the founder identified two real gaps decision 2 didn't anticipate: (a) footer content (footer text, legal-page text) is conceptually distinct from "branding" (store identity/contact info) and deserves its own tab/table rather than crowding Store Branding further, and (b) the missing-legal-page backlog item (`prd.md`'s standing pointer, items 1/2) needs an **About Us** page too, not just T&C/Privacy — `SiteFooter.tsx`'s "Company" column links to all three (`About Us`, `Terms & Conditions`, `Privacy Policy`), all three equally unlinked plain text today. Separately, the founder specified the legal content needs real rich-text formatting (a specific toolbar: bold/italic/underline/strikethrough/ordered+unordered list/link/clear-formatting) and a `{store_name}` template variable, so the same legal text template can be reused by a future second reseller (the affiliate/reseller direction decision 2 already anticipated) without manually rewriting the store name throughout the prose for each one.

**Decision:**

10. **Split decision 2's `reseller_branding` further: legal/footer content moves to a new `reseller_footer_settings` table (1:1 `Reseller`, same shape convention as `reseller_branding`), leaving `reseller_branding` holding only store identity/contact fields.** `reseller_branding` keeps: store name, description, support email/phone, WhatsApp, social links. `reseller_footer_settings` gains: `footer_text` (moved out of `reseller_branding`), `terms_content`, `privacy_content` (both moved — decision 2 originally put these in `reseller_branding`; this addendum relocates them), `about_us_content` (new — not in the original ADR). The Settings screen gains a third tab, **Footer Settings**, alongside Store Branding and Platform Settings.

11. **Three new storefront routes — `/terms`, `/privacy`, `/about-us` — render `reseller_footer_settings`'s three content fields.** None exist today (confirmed: zero files under `storefront/src` for any of the three; `SiteFooter.tsx`'s footer links for all three are plain unlinked `<li>` text). Closes the missing-legal-page half of `prd.md`'s standing pointer items 1/2 (the WhatsApp-number half is unaffected — still `reseller_branding`, per decision 2).

12. **Legal content is rich text (HTML), not plain text — stored sanitized, sanitized again at render (defense in depth).** Persisted format is HTML, not Markdown: the founder's required toolbar includes Underline, which CommonMark/GFM has no native syntax for — storing Markdown would still need raw `<u>` HTML passthrough, reopening the same sanitization problem while adding a conversion layer for no benefit. `league/commonmark` (an existing but *transitive*, not direct, dependency of `laravel/framework` — confirmed via `composer why`) is not relevant here; it converts Markdown → HTML and nothing in this feature stores Markdown. Sanitization uses a **new direct dependency, `mews/purifier`** (no HTML sanitizer/purifier exists anywhere in this codebase today — confirmed via `composer.json`) — chosen over hand-rolled `strip_tags()` because the allowlist includes `a[href]`, and `strip_tags()` only strips disallowed *tags*, not disallowed *attributes/schemes* (a `javascript:` href on an allowed `<a>` tag would survive it untouched). Allowlist: `b/strong, i/em, u, s/strike, ol, ul, li, a[href], p, br`.

13. **`{store_name}` is a template token, substituted at storefront render time only (not at admin save time), resolving to that reseller's own `reseller_branding.store_name`.** Render-time substitution (not save-time) means a future store-name change is reflected in legal pages automatically, without re-editing every legal field. The admin editor shows a live preview with the token already resolved, for proofreading, but the stored value keeps the raw `{store_name}` token. Any other brace sequence (a typo, an unrecognized token) is left verbatim — no error, no "did you mean" detection; `{store_name}` is the only recognized token today.

14. **Footer Games: admin picks up to 4 currently-active games, stored as an ordered list, to feature in the storefront footer's "Top Up Games" section.** Stored as an ordered JSON array of `game_id` on `reseller_footer_settings` (order = display order — footer position matters, same reasoning `hero_slides.sort_order` already established for an analogous "admin picks N items, order matters for display" case, confirmed as existing precedent). Only games with `Game.is_active = true` are selectable (no named `scopeActive` exists on `Game` today, unlike `HeroSlide::scopeLive()` — confirmed live; a build-time detail whether to add one). A reseller with fewer than 4 active games, or none picked yet, renders however many are actually picked (0–4); zero picked hides the entire "Top Up Games" footer block rather than showing an empty heading.

15. **`reseller_footer_settings` gets the same edit rigor as `reseller_branding` — a single-admin save, no maker-checker.** This is customer-facing copy/config, not money movement; no reason to hold it to `Withdrawals`/`Vouchers`-level review.

16. **Both new dependencies are built as reusable primitives from day one, not inlined into this one feature — justified by this feature's own 3x internal reuse (T&C/Privacy/About Us all need the same rich-text editing), not speculative future-proofing.** Frontend: one shared `<RichTextEditor>` component (`admin/src/components/ui/RichTextEditor.tsx`, wrapping `@tiptap/react` + `@tiptap/starter-kit` + `@tiptap/extension-underline` + `@tiptap/extension-link`) — any future admin-authored rich-text field (e.g. `ADR-027`'s VIP Membership terms) reuses this component rather than re-integrating Tiptap from scratch. Backend: one named `mews/purifier` config profile (`config/purifier.php`, key `rich_text`) holding this addendum's allowlist — a future feature needing the *same* allowlist reuses this profile; one needing a different allowlist adds a new named profile alongside it rather than loosening this one.

**Rationale:** Splitting footer/legal content out of `reseller_branding` (decision 10) follows the same "distinct concern gets its own table" convention decision 2 itself already used to justify `reseller_branding` as separate from `Reseller` — footer/legal content is a genuinely different editing surface (long-form formatted text vs. short identity fields) from store branding, and letting it crowd `reseller_branding` indefinitely would eventually force the same split later, with a real migration this time instead of a clean design-time decision. Decisions 12-13 (HTML storage, render-time templating) both trace back to reasoning already established elsewhere in this codebase: money is computed at the moment of use, not trusted from storage (`ORD-9`) — `{store_name}` follows the identical shape, resolved live rather than baked in, so the two systems (branding, legal content) can never silently drift out of sync.

**Addendum, 2026-10-02 — Bulk markup widened to every Package regardless of `is_active`, and a pre-existing combo pricing-corruption bug fixed (cross-ref `ADR-094`).**

**Context:** A founder question ("does bulk markup touch inactive packages too?") led to re-checking decision 4's "existing active packages" scoping. No entry anywhere in this file ever recorded *why* inactive packages should be excluded — the original PRD item (SET-2) literally said "apply to all packages," and decision 4's own Consequence-to-track entry above just states the active-only mechanic as settled, with no rationale beyond mirroring `PackageController::updateMarkup()`. Checked against the rest of the codebase and found the exclusion was the actual outlier, not the norm: `PackagePriceSyncService::propagate()` already updates an *inactive* package's `standard_selling_price` on every supplier cost change ("regardless of `is_active`... nothing is exempt from it," its own docblock), and `updateMarkup()` itself (the per-package equivalent of this bulk action) was never active-gated either. An inactive package's markup was simply left to go stale indefinitely — no reactivation path (manual toggle, `ADR-100`'s auto-approver, Pending Reactivation/Dismissed restore, `ComboPricingService::cascadeReactivate()`) recomputes `standard_selling_price` from `markup_percent` on its own.

Investigating further surfaced a second, more serious, pre-existing bug: `bulkMarkup()`'s query had no `is_combo` exclusion, so it was flat-overwriting every active combo Package's `standard_selling_price` with `cost × (1+markup%)` — bypassing `ADR-094`'s `ComboPricingService::recompute()` entirely, the one place that ADR establishes combo pricing is ever computed. Checkout charges a combo's stored `standard_selling_price` verbatim (`CheckoutController::store()` → `OrderPricingResolver::resolveStorefront()` → `PricingService`, no combo-aware recompute anywhere in that path), so this wasn't a cosmetic drift — it was the real price a customer would pay. Confirmed on production: the last `bulkMarkup()` run (2026-09-30 12:20:25, found via `PriceChangeLog::whereNull('price_sync_run_id')`) corrupted 47 combo packages, both "Sum of Components" and "Custom Markup %" modes alike; ~25 were still sitting on the wrong price as of this addendum. A cross-check of `orders` for those package IDs since that run found **zero** real orders placed against any of them — caught before a customer was actually charged the wrong price.

**Decision:**

17. **Remove the `is_active` filter entirely — `bulkMarkup()` now runs over every Package, active or inactive.** Supersedes decision 4's "existing active packages" scoping; a package's markup no longer silently drifts from platform policy just because it happened to be off when the action last ran.

18. **Non-combo packages are updated first, combos second, as two sequential passes inside the same `DB::transaction()`.** A combo's default "Sum of Components" price must see its components' *already-updated* selling prices before it recomputes — never a stale snapshot from before this run. Safe without any further dependency ordering because nesting a combo inside another combo is rejected at creation (`StoreComboPackageRequest`: "A combo cannot contain another combo") — there is no deeper chain than "components, then the one combo level above them."

19. **A combo with an active `combo_override_price` (Custom Price) or `combo_override_markup_percent` (Custom Markup %) is skipped entirely — only a combo in default "Sum of Components" mode (both overrides `null`) is touched by this action.** Both overrides represent a deliberate per-combo pricing decision an admin made for that specific combo (a discount price point, a different margin than the platform default); a platform-wide bulk action shouldn't silently erase either one, any more than it should silently erase the other. A touched combo is always updated via `ComboPricingService::recompute()` — never the flat formula — so the below-cost-floor fallback (`ADR-094`'s 2026-09-29 addendum) stays in effect.

20. **One-time production remediation, not a backfill migration:** every combo the 2026-09-30 run corrupted was individually recomputed via `ComboPricingService::recompute()` directly against production (no code change needed to do this — the service already computes each combo's objectively-correct price for whichever mode it's actually in today), restoring each to its correct Sum of Components/Custom Markup/Custom Price value. No order-level correction was needed — confirmed zero orders existed against the affected package IDs in the corrupted window.

21. **Admin UI copy (`admin/src/components/settings/PlatformSettingsSection.tsx`) and this endpoint's own doc comment updated** to stop claiming "every active package" and to describe the combo carve-out, so the confirm dialog and help text describe what the action now actually does.

**Rationale:** The active-only exclusion was an unexamined build-time default, not a reasoned decision — nothing in this ADR ever argued for letting an inactive package's pricing drift, and the pattern elsewhere in this codebase (`PackagePriceSyncService`, `updateMarkup()`) already treats a package's stored price as something that should stay current regardless of `is_active`. The combo fix is a root-cause correction, not new scope: `ADR-094` already established `ComboPricingService::recompute()` as the single place combo pricing is computed; this action simply never routed through it. Skipping a combo with an active override (decision 19) mirrors this project's existing principle that a stored per-row override represents a deliberate admin decision that a platform-wide action must not silently overwrite — the same reasoning `ADR-094`'s own override-floor addendum already applies to a single combo's pricing logic, extended here to protect it from this bulk action too.
